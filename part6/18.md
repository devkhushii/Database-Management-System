### 18.2 Connection to Indexes

**What we deferred:** When discussing row-level locking (Module 6) and phantom reads (Module 5.6), we mentioned that preventing a phantom requires locking a **range** of values, not just existing rows — but *how* does the database even know which rows fall in a range without scanning the whole table? The answer lies in **indexes**.

**What Part 7 will cover:** How an index (most commonly a B+ Tree, Section 18.3) provides an ordered, efficiently-searchable structure over a column's values, and — critically for this Part's concerns — how **index entries themselves can be locked** (via **next-key locking**, the exact mechanism InnoDB uses to prevent phantom reads under Repeatable Read, which we flagged as a notable engine-specific behavior back in Module 11.4).

**Why this connects:** Locking a data row is not enough to prevent a phantom insert — a *new* row doesn't exist yet to be locked. The trick, which Part 7 will make concrete, is locking the **gap in the index** where a new row *would* be inserted, preventing exactly that insertion until the lock is released.

---

### 18.3 Connection to B+ Trees

**What we deferred:** We've referred to "the lock manager tracking resources by page or row ID" (Module 6.1) without explaining what a **page** actually is, or how rows are physically organized to make lookups fast.

**What Part 7 will cover:** The **B+ Tree** data structure — the backbone of virtually every relational database index — including its node structure, how searches/insertions/deletions maintain balance, and how it supports both fast point lookups and fast range scans (directly relevant to the phantom-read/gap-locking discussion above).

**Why this connects:** Every lock we've discussed at "row granularity" (Module 6.7) is, physically, a lock on a specific **leaf entry** or **data page** within a B+ Tree-organized table or index — understanding the tree structure demystifies exactly what's being locked and why range-based locking requires special handling (next-key locks span the gap *between* adjacent leaf entries).

---

### 18.4 Connection to Storage Structures

**What we deferred:** Module 10 (MVCC) described PostgreSQL's "heap" storage of row versions and InnoDB's "undo log reconstruction" approach fairly abstractly — what does a **heap** actually look like on disk? What's a **tuple** physically composed of?

**What Part 7 will cover:** File organization strategies (heap files, sorted/clustered files, hash files), how PostgreSQL's tuple format includes the `xmin`/`xmax` system columns we discussed in Module 10.3 as literal bytes in each row's on-disk representation, and how InnoDB's **clustered index** (where the table's primary key IS the physical storage order — a distinctive InnoDB architectural choice) affects both performance and locking behavior compared to PostgreSQL's heap-based approach.

**Why this connects:** Every "row version" and "lock granularity" discussion in this Part has been implicitly assuming a specific physical storage model — Part 7 makes that model explicit and shows precisely how storage layout decisions (heap vs. clustered index) ripple back into the concurrency control behaviors we've studied.

---

### 18.5 Connection to the Buffer Manager

**What we deferred:** Module 2.5 (Durability) mentioned that "actual data pages can be flushed to disk lazily" after the WAL commit record is flushed — but what manages this in-memory-vs-on-disk distinction for every single page the database touches?

**What Part 7 will cover:** The **Buffer Manager** (also called the buffer pool) — the component responsible for caching frequently-accessed disk pages in memory, deciding which pages to evict under memory pressure (replacement policies like LRU), and coordinating with the Write-Ahead Log to ensure the WAL's fundamental rule is honored: **a dirty (modified) page must never be written to disk before its corresponding WAL log record has been flushed** — this is the precise mechanical enforcement of the Atomicity/Durability guarantees from Module 2.

**Why this connects:** Understanding the buffer manager explains *why* WAL works at all — it's the component enforcing the "log before data" discipline that makes crash recovery (undoing uncommitted changes, redoing committed ones) possible and correct.

---

### 18.6 Connection to File Organization

**What we deferred:** Throughout this Part, we've talked about "tables" and "rows" as if their physical layout on disk were a settled, obvious matter — it isn't. How rows are grouped into files, and files into pages, has major performance implications for exactly the concurrency patterns we've studied (Module 16's lock contention and hot-row discussions, in particular).

**What Part 7 will cover:** Different file organization schemes (heap files with free-space maps, sorted files, hash-organized files, clustered index-organized tables) and their trade-offs for insertion speed, lookup speed, and — tying directly back to this Part — how physical row placement affects lock granularity and contention patterns (e.g., rows physically co-located on the same disk page may contend for page-level locks even if they're logically unrelated, in engines that lock at page granularity, Module 6.7).

### 18.8 A Final Consolidating Thought

Every mechanism in this Part — locking, MVCC, timestamp ordering, OCC — exists to answer one question: **how do we let many transactions run at once without corrupting correctness?** Part 7 answers the complementary question: **how does the database physically organize and access data fast enough, and recover it reliably enough, to make any of this worthwhile at scale?** Together, these two Parts form the complete picture of what it means for a database to be simultaneously **correct**, **concurrent**, and **fast** — the three properties every production database must balance continuously.

---

### 18.9 Chapter Summary

- **Indexes** (specifically B+ Trees) are what make range-based locking (next-key locks, preventing phantoms) physically possible.
- **B+ Trees** are the structural backbone underlying "row" and "page" level locking discussed throughout this Part.
- **Storage structures** (heap vs. clustered) explain the physical reality behind MVCC's version chains and `xmin`/`xmax` tuple metadata.
- **The Buffer Manager** enforces the "log before data" WAL discipline that makes Atomicity and Durability (Module 2) actually work.
- **File organization** choices directly affect the lock contention and hot-row patterns discussed in Module 16.
