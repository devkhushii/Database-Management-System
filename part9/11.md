## 11.1 PostgreSQL

### 11.1.1 WAL Segments

PostgreSQL's WAL (Module 4) is physically stored as a sequence of **WAL segment files**, each 16 MB by default (configurable via `--wal-segsize` at initialization time), located in the `pg_wal/` directory (renamed from `pg_xlog/` in PostgreSQL 10+, a naming change worth knowing if you encounter older documentation or systems).

- Each segment is named using a 24-character hexadecimal identifier encoding the timeline ID and segment number.
- WAL records within segments are identified by LSNs formatted as two hexadecimal numbers separated by a slash (e.g., `16/B374D848`), representing a 64-bit log position.
- Segments are recycled (renamed and reused) once no longer needed for crash recovery, replication, or archiving — directly connecting to Module 6's checkpoint-driven log truncation discussion.

### 11.1.2 Checkpoints

PostgreSQL implements **fuzzy checkpoints** exactly as described in Module 6, controlled primarily by two parameters:

- `checkpoint_timeout` — maximum time between automatic checkpoints (default 5 minutes).
- `max_wal_size` — a soft limit on WAL size that, if approached, triggers an earlier checkpoint than the timeout would (default 1 GB, though production systems often tune this much higher).
- `checkpoint_completion_target` — controls how the checkpoint's I/O (flushing dirty pages) is *spread out* over the checkpoint interval, smoothing I/O rather than bursting it — a direct, practical refinement toward the Incremental Checkpoint spirit discussed in Module 6, Section 6.5, even though PostgreSQL's core mechanism is still fundamentally a fuzzy checkpoint.

### 11.1.3 Archive Logs

For PITR (Module 9) and replication, PostgreSQL supports **WAL archiving** — copying completed WAL segments to a separate, durable location before they're recycled locally.

- Configured via `archive_mode = on` and an `archive_command` (a shell command PostgreSQL runs for each completed segment) — or, in more modern setups, via WAL archiving modules/tools that stream segments continuously to remote storage.
- Archived WAL, combined with a base backup (`pg_basebackup`), is exactly what enables the PITR mechanism detailed in Module 9, Section 9.7.

### 11.1.4 PITR in PostgreSQL — Concretely

Building directly on Module 9's general PITR explanation, here's the PostgreSQL-specific mechanism:

1. Take a base backup: `pg_basebackup`.
2. Ensure continuous WAL archiving is enabled throughout.
3. To restore: place the base backup in a new data directory, create a `recovery.signal` file (in modern PostgreSQL versions), and set a recovery target in `postgresql.conf`, such as:
   - `recovery_target_time = '2026-07-15 14:46:59'`
   - or `recovery_target_xid`, `recovery_target_lsn`, or `recovery_target_name` (a named restore point) as alternatives.
4. On startup, PostgreSQL replays archived WAL up to (but not including) the specified target, then stops and opens for normal use.

### 11.1.5 Replication Slots (Overview)

**Replication Slots** are a PostgreSQL mechanism ensuring that WAL segments needed by a connected replica (or logical replication consumer) are **not recycled/deleted** until that replica has confirmed it no longer needs them — directly preventing a scenario where the primary "gets ahead" of a temporarily lagging or disconnected replica and deletes WAL the replica still requires to catch up.

- **Physical replication slots:** used for streaming replication (the mechanism underlying PostgreSQL's HA/DR architecture from Module 10).
- **Logical replication slots:** used for logical decoding (streaming changes in a more portable, row-level format) — connecting to Module 9's logical backup concepts, but for continuous streaming rather than point-in-time snapshots.
- **Risk:** an unmonitored replication slot for a permanently disconnected replica will cause WAL to accumulate indefinitely, potentially filling disk — a real, frequently-seen PostgreSQL production incident, and a direct, practical illustration of Module 6's "long-running transaction preventing log truncation" edge case, applied to replication instead.

## 11.2 MySQL InnoDB

### 11.2.1 Redo Log

InnoDB's WAL implementation (Module 4) is the **Redo Log**, historically stored in a small, fixed number of circular files (`ib_logfile0`, `ib_logfile1`, ...), though modern MySQL versions (8.0.30+) manage redo log capacity via the single `innodb_redo_log_capacity` parameter instead of separately sized files.

- "Circular" means InnoDB reuses (overwrites) old redo log space once it's confirmed the corresponding data pages are safely flushed — directly connected to Module 6's checkpoint mechanism, since a checkpoint is precisely what confirms it's safe to reclaim that redo log space.
- `innodb_flush_log_at_trx_commit` — InnoDB's key durability tunable (Module 4, Section 4.5's commit protocol, applied concretely):
  - `1` (default): full ACID durability — redo log flushed and `fsync`'d on every commit.
  - `0`: redo log written and flushed only once per second — fastest, but up to 1 second of committed transactions can be lost on crash.
  - `2`: redo log written on every commit, but only `fsync`'d once per second — survives a MySQL process crash (since the OS buffer still has it) but not an OS/power-level crash.

### 11.2.2 Undo Log

Unlike PostgreSQL, InnoDB maintains a **separate Undo Log**, stored in undo tablespaces, holding before-images needed to:
- Roll back uncommitted transactions (the Undo phase from Module 5/7's Undo/Redo Logging and ARIES).
- Support MVCC (Multi-Version Concurrency Control, from Part 6) — providing older row versions to transactions that need a consistent snapshot view, even while newer versions exist.

This dual purpose — recovery *and* concurrency control — is a distinctive InnoDB design choice worth remembering for engine-comparison interview questions: InnoDB's undo log directly serves both Module 5's recovery needs and Part 6's isolation needs simultaneously.

### 11.2.3 Doublewrite Buffer

Introduced conceptually in Module 4, Section 4.8 — here's the mechanism in full:

1. Before InnoDB writes a modified page to its real, final location on disk, it first writes that page to a contiguous **doublewrite buffer** area (a reserved, sequentially-written region of the system tablespace or a separate doublewrite file, in modern versions).
2. Only after this doublewrite write is confirmed does InnoDB write the page to its actual final location.
3. If a crash causes a **torn page** (Module 2, Section 2.5) at the final location, InnoDB detects this via page checksums (Module 3, Section 3.9) during crash recovery, and repairs the torn page using the intact copy from the doublewrite buffer.

This is a clean, concrete, fully worked example of exactly the abstract "torn page defense" concept introduced back in Module 2 and Module 4.

### 11.2.4 Crash Recovery

InnoDB's crash recovery process follows the ARIES-style Analysis/Redo/Undo structure (Module 7) closely:

1. On restart, InnoDB scans the redo log from the last checkpoint LSN.
2. **Redo phase:** reapplies all logged changes since the checkpoint (repeating history, exactly as in Module 7's principle).
3. **Undo phase:** uses the Undo Log to roll back any transactions that were active (uncommitted) at crash time.
4. Doublewrite buffer repairs any torn pages encountered along the way, before the redo/undo logic even needs to reason about their content.

## 11.3 Oracle

### 11.3.1 Redo Logs

Oracle's WAL implementation is also called the **Redo Log**, organized into **Redo Log Groups**, each typically containing multiple identical **members** (physical files) for redundancy — meaning even a single member's media failure (Module 2, Section 2.4) doesn't lose that redo data, since other members of the same group still have it.

- **LGWR (Log Writer)** is Oracle's dedicated background process performing the log buffer flush described generically in Module 4, Section 4.5 — it's a real, named, observable OS process in any Oracle instance.
- **SCN (System Change Number):** Oracle's version of the LSN (Module 3, Section 3.3) — a globally, monotonically increasing number assigned to every committed transaction, used for ordering, recovery, and read consistency.
- Oracle **switches** between redo log groups in a round-robin fashion as each fills up — a log switch is itself an event that can trigger checkpoint activity, connecting directly to Module 6's checkpoint scheduling discussion.

### 11.3.2 Archive Logs

When Oracle is run in **ARCHIVELOG mode**, filled redo log groups are archived (copied) to a separate location **before** being overwritten/reused — directly analogous to PostgreSQL's WAL archiving (Section 11.1.3) and serving the same PITR-enabling purpose from Module 9.

- In **NOARCHIVELOG mode**, filled redo logs are simply overwritten with no archival — meaning PITR is not possible, and recovery is limited to whatever's still within the current redo log groups. Production Oracle databases requiring PITR capability always run in ARCHIVELOG mode.

### 11.3.3 Flashback (Overview)

**Oracle Flashback** is a family of features providing fast, often near-instantaneous access to past versions of data, without requiring a full restore-and-replay PITR operation (Module 9, Section 9.7) for many common scenarios:

- **Flashback Query:** Query a table *as it existed* at a specific past point in time (`SELECT ... AS OF TIMESTAMP ...`), using retained undo information.
- **Flashback Table:** Rewind an entire table to a previous point in time, in place — directly and elegantly solving Module 2's "committed human error" (Section 2.9) problem for many cases, often far faster than a full PITR restore.
- **Flashback Database:** Rewind the *entire* database to a previous point in time using specialized flashback logs — a middle ground between a targeted Flashback Table operation and a full PITR restore.

> 💡 **Interview Insight:** Flashback is frequently cited as Oracle's answer to the Module 2/Module 9 "human error" problem — instead of the full "restore backup + replay logs to just before the mistake" PITR dance, Flashback can often surgically reverse just the affected table or query, dramatically reducing recovery time for exactly this common failure category.

## 11.4 SQL Server (Brief Addition for Completeness)

While not originally scoped in the module outline, a brief, honest mention rounds out the "big four" comparison consistently used throughout this handbook:

- SQL Server's WAL implementation is the **Transaction Log** (`.ldf` file), internally divided into **Virtual Log Files (VLFs)**.
- **Recovery Models** (`SIMPLE`, `FULL`, `BULK_LOGGED`) directly control log retention/truncation behavior and PITR capability — `SIMPLE` mode truncates the log aggressively after each checkpoint (no PITR possible), while `FULL` mode retains log records until a log backup is taken, enabling PITR exactly as described in Module 9.

## 11.5 Cross-Engine Master Comparison Table

| Feature | PostgreSQL | InnoDB (MySQL) | Oracle | SQL Server |
|---|---|---|---|---|
| WAL name | Write-Ahead Log | Redo Log | Redo Log | Transaction Log |
| Log unit | WAL Segment (16 MB) | Redo Log (circular, capacity-based) | Redo Log Group (multiple members) | Virtual Log File (VLF) |
| Sequence ID | LSN | LSN | SCN | LSN |
| Commit durability tunable | `synchronous_commit` | `innodb_flush_log_at_trx_commit` | `COMMIT WRITE` options | Recovery Model + log backup frequency |
| Torn-page defense | Full Page Writes | Doublewrite Buffer | Block checksums + redo | Page checksums + torn-page detection |
| Undo mechanism | MVCC row versions + WAL | Separate Undo Log (dual-purpose: recovery + MVCC) | Undo Segments | Version store (tempdb, for RCSI) / log-based rollback |
| Archiving for PITR | `archive_command` / WAL archiving | Binary log (`binlog`) + backups | ARCHIVELOG mode | FULL recovery model + log backups |
| Dedicated flush process | WAL writer | Log thread | LGWR | Log writer thread |
| "Undo a mistake fast" feature | PITR (restore + replay) | PITR via binlog replay | Flashback (Query/Table/Database) | PITR via log backup replay |
| Fixed checkpoint pointer | `pg_control` | Redo log header | Control file | Boot page / log sequence |

## 11.6 Advantages of Studying Real Engine Implementations

- Converts abstract textbook knowledge (Modules 1–10) into concrete, interview-ready, resume-relevant expertise tied to specific, widely-used production systems.
- Prepares you to read and reason about real configuration files, error messages, and monitoring dashboards you'll actually encounter on the job.
- Makes engine-comparison and migration discussions ("should we move from MySQL to PostgreSQL?") grounded in genuine architectural understanding, not just marketing claims.

## 11.7 Disadvantages / Costs of This Level of Detail

- Configuration parameters, defaults, and even architecture change across major versions — content here should be treated as a strong conceptual foundation, always verified against current official documentation for the exact version in production use.
- Deep engine-specific knowledge doesn't always transfer directly between engines — a PostgreSQL expert must still learn InnoDB's distinct undo/redo split before claiming equivalent MySQL expertise.

## 11.8 Best Practices

- Always know your production database's exact durability tunable setting (`synchronous_commit`, `innodb_flush_log_at_trx_commit`, or equivalent) and be able to articulate, in a sentence, exactly what data-loss window it permits.
- Monitor replication slot / archive log accumulation proactively (Section 11.1.5) — this is one of the most common, avoidable real-world PostgreSQL incidents.
- For Oracle systems, evaluate whether Flashback features can replace slower, more disruptive full PITR restores for common human-error recovery scenarios.

## 11.9 Common Mistakes

- Assuming all engines handle undo the same way — InnoDB and Oracle use dedicated undo logs/segments; PostgreSQL primarily leans on MVCC row versions, a meaningfully different architecture worth being able to explain precisely.
- Running Oracle in NOARCHIVELOG mode in production without realizing this eliminates PITR capability entirely.
- Forgetting to monitor PostgreSQL replication slots, leading to unbounded WAL accumulation and eventual disk exhaustion — a real, well-documented, entirely preventable class of production incident.

## 11.10 Edge Cases

- A PostgreSQL replica falling permanently offline while its replication slot remains active will silently accumulate WAL on the primary indefinitely — this is a genuine, frequently-tested operational scenario worth understanding deeply, not just memorizing as a fact.
- InnoDB's doublewrite buffer itself must be written durably before the real page write — meaning it, too, must obey a "log/stage before final write" discipline conceptually identical to WAL's own core rule (Module 4), just applied one layer deeper.

## 11.11 Chapter Summary

- **PostgreSQL** implements textbook WAL and fuzzy checkpoints closely, using `pg_wal` segments, `synchronous_commit`, Full Page Writes for torn-page defense, and replication slots to protect WAL needed by replicas.
- **InnoDB** uses a Redo Log (WAL) plus a separate Undo Log serving dual recovery/MVCC purposes, and defends against torn pages via its Doublewrite Buffer.
- **Oracle** uses Redo Log Groups with redundant members, SCNs as its LSN equivalent, ARCHIVELOG mode for PITR capability, and Flashback features as a fast alternative to full PITR restores for many human-error scenarios.
- **SQL Server** uses a Transaction Log with VLFs and exposes Recovery Models directly controlling log retention/PITR capability.
- Despite different names, all four engines implement the same fundamental principles covered in Modules 1–10 of this handbook.
