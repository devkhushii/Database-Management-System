### 13.1 Theory Questions

**Q1: What is the difference between a database and a DBMS?**
A database is the organized collection of data itself; a DBMS (Database Management System) is the software that manages, stores, retrieves, and secures that data — the engine, not the data.

**Q2: What are the three levels of data abstraction (ANSI-SPARC architecture)?**
Physical (how data is actually stored on disk), Logical/Conceptual (the schema — tables, relationships, constraints), and View/External (what different user groups see, often via views).

**Q3: What is data independence, and what are its two types?**
The ability to change one level of abstraction without affecting the levels above it. **Logical data independence** — changing the conceptual schema without affecting external views/applications. **Physical data independence** — changing physical storage without affecting the logical schema.

**Q4: What is the difference between a primary key and a candidate key?**
A candidate key is any minimal set of columns that uniquely identifies a row; a table can have multiple candidate keys. The primary key is the one candidate key chosen as the table's main identifier; the rest become alternate/unique keys.

**Q5: What is a surrogate key vs. a natural key?**
A natural key is derived from real-world data (e.g., an email address or SSN). A surrogate key is an artificially generated identifier (e.g., an auto-incrementing integer or UUID) with no business meaning — generally preferred for primary keys because natural keys can change or contain sensitive data.

### 13.2 SQL Questions

**Q1: Write a query to find the second-highest salary in an `employees` table.**
```sql
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
-- Alternative using window functions:
SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) t WHERE rnk = 2;
```

**Q2: Explain the difference between `WHERE` and `HAVING`.**
`WHERE` filters individual rows **before** grouping/aggregation; `HAVING` filters groups **after** aggregation (e.g., `HAVING COUNT(*) > 5`).

**Q3: What's the difference between `UNION` and `UNION ALL`?**
`UNION` combines result sets and removes duplicates (requires a sort/dedup step, slower). `UNION ALL` combines without deduplication (faster, use when you know there are no duplicates or duplicates are acceptable).

**Q4: Explain `INNER JOIN` vs `LEFT JOIN` vs `FULL OUTER JOIN`.**
`INNER JOIN` returns only matching rows from both tables. `LEFT JOIN` returns all rows from the left table plus matches from the right (NULLs where no match). `FULL OUTER JOIN` returns all rows from both tables, matched where possible, NULLs elsewhere.

**Q5: Write a query to find duplicate rows in a table based on a specific column.**
```sql
SELECT email, COUNT(*) FROM users
GROUP BY email
HAVING COUNT(*) > 1;
```

**Q6: What is a correlated subquery, and why can it be slow?**
A subquery that references a column from the outer query, re-executed once per outer row (conceptually) rather than once total — can be slow on large tables unless the optimizer rewrites it as a join internally (which modern optimizers often do).

**Q7: Explain window functions and give an example use case.**
Window functions perform calculations across a set of rows related to the current row **without collapsing rows** (unlike `GROUP BY`). Example: `ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC)` ranks employees within each department without losing individual row detail.

### 13.3 Normalization Questions

**Q1: Define 1NF, 2NF, and 3NF.**
- **1NF:** Atomic values only (no repeating groups/arrays in a single column).
- **2NF:** 1NF + every non-key attribute is fully functionally dependent on the **entire** primary key (relevant only for composite keys — eliminates partial dependency).
- **3NF:** 2NF + no transitive dependencies (a non-key attribute must depend on the key, the whole key, and nothing but the key).

**Q2: What is BCNF (Boyce-Codd Normal Form), and how does it differ from 3NF?**
BCNF is a stricter version of 3NF: for every functional dependency `X → Y`, `X` must be a superkey. 3NF has a narrow exception allowing certain dependencies on non-superkeys when the dependent attribute is part of a candidate key; BCNF closes that exception.

**Q3: Why would you deliberately denormalize a schema?**
To improve read performance by reducing expensive joins, at the cost of some data redundancy and more complex write logic to keep redundant copies in sync (Module 5 recap).

**Q4: Given a table `Orders(OrderID, ProductID, ProductName, Quantity)`, identify the normalization violation and fix it.**
`ProductName` depends only on `ProductID`, not the full key `(OrderID, ProductID)` — this is a partial dependency, violating 2NF. Fix: split into `Orders(OrderID, ProductID, Quantity)` and `Products(ProductID, ProductName)`.

### 13.4 Transaction Questions

**Q1: What is a transaction, and what are its key properties?**
A transaction is a sequence of operations executed as a single logical unit of work, guaranteeing ACID properties (Section 13.5).

**Q2: Explain the four transaction isolation levels and the anomalies each prevents.**

| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| Read Uncommitted | Possible | Possible | Possible |
| Read Committed | Prevented | Possible | Possible |
| Repeatable Read | Prevented | Prevented | Possible (varies by engine — PostgreSQL's implementation prevents phantoms too via MVCC snapshot) |
| Serializable | Prevented | Prevented | Prevented |

**Q3: What is a dirty read, non-repeatable read, and phantom read?**
- **Dirty read:** Reading uncommitted data from another transaction that might later be rolled back.
- **Non-repeatable read:** Reading the same row twice within a transaction and getting different values because another transaction modified and committed in between.
- **Phantom read:** Re-running the same query twice within a transaction and getting a different **set of rows** because another transaction inserted/deleted matching rows in between.

**Q4: What is a savepoint?**
A named point within a transaction that you can roll back to without aborting the entire transaction — useful for partial recovery within a larger transaction.

### 13.5 ACID Questions

**Q1: Define each ACID property with a one-line explanation.**
- **Atomicity:** All operations in a transaction succeed, or none do.
- **Consistency:** A transaction moves the database from one valid state to another, respecting all constraints.
- **Isolation:** Concurrent transactions don't interfere with each other's intermediate states.
- **Durability:** Once committed, a transaction's changes survive even a crash immediately after.

**Q2: How does a database achieve Durability internally?**
Via Write-Ahead Logging (WAL) — changes are written to a durable log **before** being applied to data files, so after a crash, the log can be replayed to recover committed transactions (Part 7 / Module 7 recap).

**Q3: How does a database achieve Atomicity internally?**
Via undo logs / rollback segments (or MVCC's multi-version approach) that let the database reverse partial changes if a transaction aborts, plus the commit protocol ensuring all-or-nothing visibility.

**Q4: Can a system be "ACID-compliant" without being fully serializable?**
Yes — ACID's "Isolation" property is satisfied by any of the four standard isolation levels, not just Serializable; most production systems run at Read Committed by default, trading some isolation strength for performance, while still being considered ACID-compliant.

### 13.6 Index Questions

**Q1: What is an index, and why does it speed up reads?**
A separate, sorted (or otherwise organized) data structure that lets the database find rows matching a condition without scanning the entire table — analogous to a book's index letting you jump to a page instead of reading cover to cover.

**Q2: What's the trade-off of adding an index?**
Faster reads on the indexed column(s), but slower writes (every `INSERT`/`UPDATE`/`DELETE` must also update the index) and additional storage.

**Q3: What is a composite (multi-column) index, and what is the "leftmost prefix rule"?**
An index on multiple columns, e.g., `(a, b, c)`. The leftmost prefix rule states the index can efficiently serve queries filtering on `a`, `(a,b)`, or `(a,b,c)`, but **not** efficiently serve a query filtering only on `b` or `c` alone — the index is only useful when the leftmost column(s) are part of the filter.

**Q4: What's the difference between a clustered and non-clustered index?**
A clustered index determines the **physical storage order** of the table's rows (only one per table, since data can only be physically sorted one way). A non-clustered index is a separate structure pointing back to the row's location — a table can have many.

**Q5: When would you NOT want to add an index?**
On columns with very low selectivity (e.g., a boolean column with 90% one value) where a sequential scan is often faster than using the index; on write-heavy tables where index maintenance overhead outweighs the read benefit; on rarely-queried columns.

**Q6: What is a covering index?**
An index that includes all columns needed by a query (in the index itself, via included columns or the index key), letting the database satisfy the query **entirely from the index** without a separate lookup to the table's actual row data ("index-only scan").

### 13.7 B+ Tree Questions

**Q1: Why do most relational databases use B+ Trees for indexes instead of binary search trees or hash tables?**
B+ Trees are optimized for **disk-based storage** — each node maps to a disk page, and the tree's high fan-out (many children per node) keeps the tree shallow, minimizing disk I/O per lookup. Binary trees would require far more levels (more disk reads) for the same number of keys. Hash tables support O(1) exact-match lookups but can't efficiently support range queries (`WHERE age > 30`) or sorted output, which B+ Trees handle naturally via their linked leaf nodes.

**Q2: What's the difference between a B-Tree and a B+ Tree?**
In a B-Tree, data can be stored in internal nodes as well as leaf nodes. In a B+ Tree, **all actual data (or row pointers) lives only in leaf nodes**, and leaf nodes are linked together sequentially — this makes B+ Trees better for range scans (just walk the linked leaves) and keeps internal nodes smaller/denser (more keys per page, shallower tree).

**Q3: What is the time complexity of a B+ Tree lookup, insert, and delete?**
O(log n) for all three, where the base of the logarithm is the tree's fan-out (often in the hundreds), making the actual number of disk reads very small even for huge tables (a tree with fan-out 200 can index over a billion rows in just ~4 levels).

**Q4: Why does inserting into a B+ Tree sometimes cause a "page split"?**
When a leaf node is full and a new key needs to be inserted, the node splits into two, and the split propagates upward if the parent is also full — this is why bulk-inserting into an index in **non-sorted order** can be slower and cause more fragmentation than inserting in sorted order.

### 13.8 Query Optimization Questions

**Q1: What is a query execution plan, and how do you view one?**
The step-by-step physical plan the database will use to execute a query (which indexes to use, join order, join algorithm). Viewed via `EXPLAIN` (shows the *planned* execution) or `EXPLAIN ANALYZE` (actually runs the query and shows *actual* execution stats alongside the plan).

**Q2: What's the difference between a sequential scan and an index scan, and when does the optimizer choose each?**
A sequential scan reads every row in the table; an index scan uses an index to jump directly to matching rows. The cost-based optimizer chooses based on estimated **selectivity** — if a query matches a large percentage of rows, a sequential scan can actually be faster (avoiding index-lookup overhead per matching row) despite reading more data overall.

**Q3: Explain the three common join algorithms.**
- **Nested Loop Join:** For each row in the outer table, scan the inner table for matches — good for small tables or when an index supports the inner lookup.
- **Hash Join:** Build a hash table from the smaller table, then probe it with rows from the larger table — good for large, unsorted, unindexed joins.
- **Merge Join:** Both inputs are sorted on the join key, then merged in a single pass — good when both inputs are already sorted (e.g., via an index).

**Q4: What are database statistics, and why do stale statistics cause bad query plans?**
Statistics are metadata about data distribution (row counts, value histograms, cardinality estimates) that the cost-based optimizer uses to estimate the cheapest plan. If statistics are stale (e.g., after a large bulk insert without running `ANALYZE`), the optimizer's cost estimates are wrong, potentially choosing a badly-suited plan (e.g., a sequential scan when an index would now be far better, or vice versa).

**Q5: What is query plan caching, and what risk does it introduce?**
Reusing a previously-computed execution plan for a parameterized query to save re-planning overhead. Risk: **parameter sniffing** — a plan optimized for one set of parameter values (e.g., a highly selective filter) may be badly suited for a different set of values on the same query (e.g., a filter matching most of the table), causing inconsistent performance.

### 13.9 MVCC Questions

**Q1: What is MVCC, and what problem does it solve?**
Multi-Version Concurrency Control — instead of readers blocking writers (and vice versa) via locks, the database keeps multiple **versions** of each row, letting readers see a consistent snapshot of data as of when their transaction/statement started, while writers create new versions rather than overwriting in place. Solves the problem of read/write lock contention that would otherwise serialize all access.

**Q2: How does PostgreSQL implement MVCC at a row level?**
Each row (tuple) has hidden `xmin`/`xmax` system columns recording the transaction IDs that created and (if applicable) deleted/superseded it. A transaction only "sees" rows where `xmin` is committed and visible to its snapshot, and `xmax` is either unset or not yet committed/visible — this is what lets readers never block on writers.

**Q3: Why does MVCC require a cleanup process like `VACUUM`?**
Old row versions (dead tuples) aren't immediately physically removed when superseded/deleted — they must be cleaned up later once no active transaction could still need to see them, or they accumulate as bloat (Module 1/11 recap).

**Q4: Does MVCC eliminate the need for locks entirely?**
No — MVCC eliminates most **read-write** lock contention, but **write-write** conflicts (two transactions trying to modify the same row) still require locking/conflict detection to maintain consistency.

### 13.10 Recovery Questions

**Q1: What is Write-Ahead Logging (WAL), and why must the log be written before the data?**
The rule that changes must be recorded in a durable log **before** being applied to the actual data files — this guarantees that if a crash happens mid-write, the log has a complete record to either redo (roll forward) or undo the change during recovery, ensuring Durability and Atomicity even across crashes.

**Q2: Explain the ARIES recovery algorithm's three phases at a high level.**
**Analysis** (scan the log to determine which transactions were in-progress at crash time), **Redo** (replay all logged changes to bring the database to the exact state at the moment of the crash, including uncommitted changes), **Undo** (roll back any transactions that were still in-progress/uncommitted at crash time).

**Q3: What is a checkpoint, and why does it speed up recovery?**
A periodic point where all dirty (modified) in-memory pages are flushed to disk, and the checkpoint's position is recorded in the log. During recovery, you only need to replay the log **from the last checkpoint forward**, not from the beginning of time — dramatically reducing recovery time.

**Q4: What's the difference between crash recovery and Point-in-Time Recovery (PITR)?**
Crash recovery automatically restores the database to its exact state at the moment of an unexpected crash, using the same logs. PITR is a deliberate, manual/scripted process to restore to **any chosen point in the past** (Module 7 recap), typically to undo a human error rather than a crash.

### 13.11 Distributed Database Questions

**Q1: State the CAP theorem.**
In the presence of a network Partition, a distributed system must choose between Consistency (every read sees the latest write) and Availability (every request gets a response, even if it might not be the latest data) — you cannot guarantee both simultaneously during a partition.

**Q2: What is the difference between strong consistency and eventual consistency?**
Strong consistency guarantees any read after a write immediately sees that write, everywhere. Eventual consistency guarantees that if no new writes occur, all replicas will *eventually* converge to the same value, but reads may temporarily see stale data.

**Q3: What is a distributed transaction, and what problem does Two-Phase Commit (2PC) solve?**
A transaction spanning multiple independent nodes/databases. 2PC coordinates commit across all participants: a **prepare phase** (all nodes confirm they *can* commit) followed by a **commit phase** (all nodes actually commit) — ensuring all nodes commit or all abort, even though they're independent systems.

**Q4: What is the main weakness of Two-Phase Commit?**
It's a **blocking protocol** — if the coordinator crashes after the prepare phase but before sending the commit decision, participants are left holding locks indefinitely, unable to proceed, until the coordinator recovers (or a timeout/manual intervention occurs).

**Q5: What is consistent hashing, and why is it used for sharding?**
A hashing technique that minimizes data movement when nodes are added/removed from a cluster — instead of `hash(key) % N` (which reshuffles nearly all keys when `N` changes), consistent hashing maps both keys and nodes onto a hash ring, so adding/removing a node only affects the keys in its immediate neighborhood on the ring.

### 13.12 NoSQL Questions

**Q1: What does "schema-less" actually mean in a document database like MongoDB?**
The database doesn't enforce a rigid, pre-defined schema at the engine level — different documents in the same collection can have different fields. The schema still conceptually exists (defined by application expectations), it's just not enforced by the database itself (schema-on-read rather than schema-on-write).

**Q2: What is the difference between horizontal and vertical scaling, and which do NoSQL databases typically favor?**
Vertical scaling = bigger single machine (more CPU/RAM). Horizontal scaling = more machines sharing the load. Most NoSQL databases are architecturally designed for horizontal scaling as a first-class feature (native sharding), whereas traditional single-node RDBMSs historically favored vertical scaling, requiring more manual effort (or a distributed SQL engine — Module 10) for horizontal write scaling.

**Q3: Explain eventual consistency with a concrete example.**
In a system with 3 replicas, a write to replica A might take a few hundred milliseconds to propagate to replicas B and C. During that window, a read from replica B might return the old value. Given enough time with no further writes, all three replicas converge to the same value.

**Q4: When is a document database a poor fit compared to a relational database?**
When data is highly relational with many-to-many relationships requiring complex joins across entities, or when strong multi-record transactional consistency across different collections/entities is a frequent, core requirement.

### 13.13 Database Internals Questions

**Q1: What is a heap file, and how does it differ from an index-organized table?**
A heap file stores rows in no particular guaranteed order (typically insertion order, with some reuse of freed space) — this is MySQL InnoDB's and Oracle's *non-default* option, though InnoDB actually defaults to storing tables clustered by primary key (index-organized). An index-organized table physically sorts row data by a key (e.g., the primary key), as InnoDB does by default and PostgreSQL does not (PostgreSQL heap-organizes by default, with indexes as separate structures).

**Q2: What is a buffer pool / buffer cache, and why is its size such an important configuration parameter?**
An in-memory cache of frequently-accessed disk pages — since memory access is orders of magnitude faster than disk, a well-sized buffer pool (Module 3 recap) dramatically reduces the number of actual disk I/O operations needed to serve queries, directly determining the buffer cache hit ratio metric (Module 4).

**Q3: What is a page (or block), and why do databases operate in fixed-size pages rather than reading individual rows?**
The fixed-size unit of I/O between disk and memory (commonly 4KB, 8KB, or 16KB depending on the engine). Reading/writing in pages amortizes disk I/O overhead (seek time dominates for small reads) and aligns with B+ Tree node sizing (Section 13.7) for efficient index traversal.

### 13.14 Cloud Database Questions

**Q1: What is the difference between a managed database service (like RDS) and a cloud-native database (like Aurora or Spanner)?**
A managed service typically runs the standard open-source/commercial engine (PostgreSQL, MySQL) with the cloud provider handling operational tasks (patching, backups). A cloud-native database is architecturally re-built specifically for the cloud's distributed infrastructure (e.g., Aurora separates compute from a distributed, self-healing storage layer), often achieving better scalability/durability than the standard engine running on traditional infrastructure.

**Q2: What is "serverless" in the context of databases?**
A deployment model where the database automatically scales compute capacity up/down (sometimes to zero) based on load, and billing is based on actual usage rather than a fixed provisioned instance size — eliminates the need for manual capacity planning (Module 3) for variable/unpredictable workloads.

**Q3: What are the trade-offs of using a cloud-native database over a self-managed open-source engine?**
Gains: reduced operational burden, often better built-in durability/scaling. Costs: potential vendor lock-in (Module 9/10 recap), sometimes subtle behavioral differences from the standard engine (compatibility isn't always 100%), and typically higher cost per unit of compute/storage.

### 13.15 Production Incident Questions

*(Full diagnostic depth covered in Module 11 — condensed interview-format recap below)*

**Q1: The application is throwing "too many connections" errors. What's your diagnostic process?**
Check current connection count vs. `max_connections`; check for a connection leak (many "idle in transaction" states); check if connection pooling is in place/properly sized; check for a recent traffic spike or deployment correlating with the onset.

**Q2: Replication lag suddenly spiked. What are the top three things you check first?**
(1) A long-running query on the replica blocking WAL/log replay. (2) A sudden write-volume spike on the primary (check WAL/binlog generation rate). (3) Network connectivity/bandwidth between primary and replica.

**Q3: The database ran out of disk space and halted. What's your immediate action, and what's your root-cause check?**
Immediate: expand storage if possible (often can be done online on managed services) to restore write capability. Root cause: check for stuck/unused replication slots retaining WAL, unexpected data growth, or runaway temp files — don't just expand and move on without finding the cause.

### 13.17 HR + Behavioral Questions (Database-Work-Related)

**Q1: Tell me about a time you had to make a difficult trade-off between consistency and availability (or performance and cost).**
*What interviewers look for:* A specific real scenario, the concrete trade-off considered, the reasoning behind the final decision, and (ideally) the outcome/lesson learned — not a hypothetical or purely textbook answer.

**Q2: Describe a production incident you were involved in. What was your role, and what would you do differently?**
*What interviewers look for:* Ownership without excessive self-blame, a clear diagnostic narrative (echoing Module 11's structured approach), and evidence of follow-through (post-incident prevention measures), not just "we fixed it."

**Q3: How do you approach reviewing a teammate's risky database migration before it goes to production?**
*What interviewers look for:* Awareness of the concepts from Module 8 (locking behavior, backward compatibility, rollback plan) applied as a concrete review checklist, and collaborative, constructive communication style.

**Q4: Tell me about a time you disagreed with a technical decision about database architecture. How did you handle it?**
*What interviewers look for:* Ability to make a reasoned technical argument, respect for the eventual decision (even if it wasn't yours), and evidence of collaborative rather than combative disagreement.
