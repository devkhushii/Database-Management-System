# DBMS Handbook — Part 7: Indexing, File Organization & Storage Structures
## Module 10: Index Selection & Optimization

> **Where we are:** Modules 1–9 gave you every storage structure and its exact engine implementation. Module 10 asks the question that sits between storage and query processing: **given all these indexes, how does the database decide which one (if any) to actually use for a given query?** This module is the bridge into Part 8 (Query Processing & Optimization).

---

## 10.0 Why This Module Exists

Creating an index does not guarantee the optimizer will use it. A query planner makes a **cost-based decision**, weighing the estimated cost of using an index against the cost of alternatives (like a full sequential scan) — and that decision hinges entirely on **statistics** the engine maintains about the data's actual shape. Get the statistics wrong (or stale), and even a perfectly-designed index will be silently ignored.

---

## 10.1 How Query Optimizers Choose Indexes

### The core decision process (simplified)

```
For each candidate access path (seq scan, index scan on Index A, index scan on Index B, ...):
    1. Estimate how many rows will match the query's filter conditions (selectivity/cardinality)
    2. Estimate the I/O cost of that access path (how many pages touched, using Module 1's cost model)
    3. Estimate the CPU cost (comparisons, sorting, etc.)
    4. Sum these into a total estimated cost
Choose the access path with the LOWEST total estimated cost
```

This is precisely the **Cost-Based Optimization** model previewed in Section 15 of this module list and covered in full depth in Part 8 — this module focuses specifically on the storage-structure-facing half of that decision: selectivity, cardinality, statistics, and which index-related access patterns exist to choose from.

---

## 10.2 Selectivity

### What is it?

**Selectivity** is the fraction of a table's rows that satisfy a given predicate (`WHERE` condition) — expressed as a ratio between 0 and 1 (or as a percentage).

```
Selectivity = (number of matching rows) / (total number of rows)
```

### Why it matters

**Low selectivity** (a predicate matches very few rows, e.g., `WHERE id = 5` on a table with millions of rows, selectivity ≈ 0.0000001) makes an index **highly beneficial** — jumping directly to those few matching rows via an index is far cheaper than scanning everything.

**High selectivity** (a predicate matches a large fraction of rows, e.g., `WHERE is_active = true` on a table where 95% of rows are active, selectivity ≈ 0.95) often makes an index **counterproductive** — if almost every page contains at least one matching row anyway, a sequential scan (Section 10.10) reading pages in bulk, sequentially, can be cheaper than the overhead of jumping around via an index (especially for a non-clustered/non-covering index requiring extra row fetches, Module 5's "double lookup" and "bookmark lookup" concepts).

### Real-life analogy

If you're looking for one specific person's name in a phone book (low selectivity — very few matches), flipping directly to the right page (using the book's alphabetical index/ordering) is clearly faster than reading every page. But if you're looking for "everyone whose name starts with a consonant" (extremely high selectivity — nearly everyone matches), you might as well just read through the whole book once, since you'd end up visiting nearly every page regardless.

### Interview Importance
⭐⭐⭐⭐⭐ — "Why might the optimizer ignore an index that exists on the exact column you're filtering on?" — Answer: low selectivity for that particular filter value; the optimizer correctly judges a full/sequential scan cheaper in that specific case.

---

## 10.3 Cardinality

### What is it?

**Cardinality** refers to the **number of distinct values** in a column (sometimes also used loosely to mean the estimated number of rows a query will return, closely related to but distinct from selectivity — selectivity is normalized to a 0-1 ratio, cardinality is often an absolute count).

### Relationship to Selectivity

```
Approximate selectivity for an equality predicate on a UNIFORMLY distributed column
  ≈ 1 / (number of distinct values, i.e., cardinality)

Example: a 'country' column with 195 distinct values (assuming uniform distribution)
  -> selectivity of WHERE country = 'India' ≈ 1/195 ≈ 0.005 (0.5%)
```

### High-Cardinality vs Low-Cardinality Columns

| | High Cardinality (many distinct values) | Low Cardinality (few distinct values) |
|---|---|---|
| Example | `email`, `user_id`, `order_id` | `gender`, `is_active`, `status` (with only a few possible states) |
| Index usefulness (typical) | Usually very useful — each value tends to match few rows | Often not useful for a plain B+ Tree (Module 8's Bitmap/specialized index types can help more here) |

### Common Mistake
- Assuming cardinality alone determines index usefulness, ignoring **data distribution skew** — a column can have high overall cardinality (e.g., `city`) but still have a few extremely common values (e.g., most users are from one metro area) where filtering on THAT specific value has poor selectivity even though the column overall is high-cardinality. This is exactly why histograms (Section 10.4) exist — a single cardinality number can't capture this nuance.

---

## 10.4 Statistics and Histograms

### What is it?

**Statistics** are metadata the database engine periodically collects about each column's data distribution — including cardinality (distinct value count), most common values and their frequencies, and (critically) a **histogram**: a bucketed summary of how values are distributed across the column's value range, enabling much more accurate selectivity estimates than a single overall cardinality number could provide.

### How Histograms Work (conceptual)

```
Column: 'age', range 0-100, table has 1,000,000 rows

Histogram (10 equal-frequency buckets, illustrative):
  Bucket 1: ages 0-12   -> ~100,000 rows
  Bucket 2: ages 13-19  -> ~80,000 rows
  Bucket 3: ages 20-35  -> ~300,000 rows   <- notice: uneven bucket WIDTH, roughly equal FREQUENCY
  Bucket 4: ages 36-50  -> ~250,000 rows
  ... etc.

Query: WHERE age BETWEEN 20 AND 35
  -> optimizer consults histogram -> estimates ~300,000 matching rows directly from Bucket 3
  -> (much more accurate than assuming uniform distribution across the full 0-100 range)
```

### Why Histograms Matter So Much

Without a histogram, the optimizer must assume a **uniform distribution** across a column's min/max range — which is frequently wrong in real data (ages cluster around certain ranges, prices cluster around common price points, timestamps cluster around business hours, etc.). Histograms let the optimizer make dramatically more accurate cardinality/selectivity estimates for range predicates specifically, not just equality predicates.

### Keeping Statistics Fresh

Statistics are **snapshots**, not live-updated on every write — they must be periodically refreshed. *(Full detail on `ANALYZE`, auto-analyze, and the operational consequences of stale statistics is covered in Module 11: Index Maintenance.)*

### Interview Importance
⭐⭐⭐⭐⭐ — "The query plan changed dramatically after a large data load, even though no schema or index changed — why?" — Answer: statistics became stale relative to the new data distribution; running `ANALYZE` (PostgreSQL) or updating statistics (MySQL) refreshes the optimizer's cardinality estimates, often restoring the expected (better) plan.

## 10.5 Composite Index Ordering (Optimizer Perspective)

### Recap and Extension

Module 5 (Section 5.6) and Module 8 (Section 8.1) already covered the leftmost prefix rule and column-order strategy from the *index design* perspective. From the **optimizer's** perspective, the key additional insight is: **the optimizer estimates the combined selectivity of a composite index's usable prefix** to decide whether using that index at all is cheaper than a sequential scan or a different index.

```
Composite index (status, created_at):
  Query: WHERE status = 'active' AND created_at > '2026-01-01'

  Optimizer estimates: selectivity(status='active') AS the "how much does the index narrow things down"
                        THEN estimates additional narrowing from created_at range WITHIN that subset
                        (using the histogram for created_at, ideally a histogram conditioned on
                         status='active' specifically -- multi-column/dependent statistics, an
                         advanced feature some engines support to avoid assuming independence)
```

### The Independence Assumption (a subtle, important limitation)

Many optimizers, by default, assume **column independence** — i.e., that a row's `status` value and `created_at` value are statistically unrelated. When this assumption is wrong (e.g., `status='archived'` rows are heavily correlated with older `created_at` values), the optimizer's combined selectivity estimate can be significantly off, leading to a suboptimal plan choice. Modern PostgreSQL versions support **extended statistics** (`CREATE STATISTICS`) specifically to capture such column correlations when the default independence assumption proves inaccurate for a particular table.

---

## 10.6 Leftmost Prefix Rule (Optimizer Enforcement Recap)

Fully defined in Module 5, Section 5.6. From the optimizer's viewpoint: if a query's predicates don't include the leftmost column(s) of a composite index, the optimizer typically **cannot** use that index for an efficient B+ Tree traversal at all (it may, in some engines, still perform a **full index scan** reading every entry — sometimes cheaper than a full table scan if the index is narrower than the full row, but never as efficient as a proper prefix-matched traversal).

---

## 10.7 Covering Queries and Index-Only Scans (Optimizer Perspective)

### Recap and Extension

Module 5 (Section 5.7) defined covering indexes; Module 9 (Section 9.3) explained PostgreSQL's Visibility Map caveat in full. From the optimizer's perspective: an **Index-Only Scan** is chosen specifically when the optimizer determines (a) the index contains every column the query needs, AND (b) (PostgreSQL specifically) enough of the relevant pages are expected to be marked all-visible in the Visibility Map to make the strategy worthwhile — if the Visibility Map coverage is poor (e.g., a heavily-updated table where VACUUM hasn't run recently), the optimizer may correctly choose a regular Index Scan (with heap fetches) instead, anticipating that the Index-Only Scan's theoretical benefit won't materialize in practice.

---

## 10.8 Index-Only Scans — Full Definition

### What is it?

An **Index-Only Scan** is a query execution strategy that retrieves all needed data directly from an index structure, without ever reading the underlying table's heap/data pages — the direct execution-level payoff of a covering index (Module 5, Section 5.7).

### Cost Comparison

| Access Path | I/O Pattern |
|---|---|
| Sequential Scan | Read every page of the table, once, sequentially |
| Regular Index Scan | Traverse index (few pages) + fetch each matching row's page individually (potentially many scattered, random-access page reads) |
| Index-Only Scan | Traverse index (few pages) ONLY — no heap/table fetches needed at all (subject to Visibility Map caveat in PostgreSQL) |

---

## 10.9 Sequential Scan vs Index Scan — The Core Trade-off

### When Sequential Scan Wins

- **High selectivity** queries (large fraction of rows match) — Section 10.2.
- **Small tables** — the overhead of index traversal isn't worth it if the whole table already fits in just a few pages.
- Queries needing **most/all columns of most/all rows** anyway — reading the table directly is unavoidable regardless.

### When Index Scan Wins

- **Low selectivity** queries (few rows match).
- Composite/covering indexes enabling **Index-Only Scans** (Section 10.8), regardless of selectivity, since the heap is skipped entirely.
- Queries needing **sorted output** matching an index's natural order, avoiding an explicit separate sort step.

### Real-World Debugging Pattern

A very common real interview/production scenario: **"Why is my query doing a sequential scan even though I have an index on that column?"** The systematic answer, drawing on this entire module:
1. Check selectivity — is the filtered value actually common (high selectivity)?
2. Check statistics freshness — are they stale, causing a wrong cardinality estimate? (Module 11)
3. Check for a **functional mismatch** — is the query filtering on a transformed expression without a matching expression index? (Module 5, Section 5.11)
4. Check the leftmost prefix rule — does the query skip the leftmost column(s) of a composite index?
5. Check table size — is the table simply too small for the optimizer to bother with an index at all?

### Interview Importance
⭐⭐⭐⭐⭐ — This five-point debugging checklist is one of the single most practically valuable things in this entire handbook — memorize it, it will come up in real interviews and real production work constantly.

## 10.10 Bitmap Scan (Overview)

### What is it?

A **Bitmap Scan** (specifically, PostgreSQL's "Bitmap Index Scan" followed by "Bitmap Heap Scan") is an execution strategy where the engine first builds an **in-memory bitmap** of which heap pages contain at least one matching row (using one or more indexes), then visits those heap pages **in physical page order** (not in index-key order), reading each qualifying page exactly once even if multiple matching rows exist on it.

### Why it exists — solving the "many scattered index hits" problem

A regular Index Scan on a moderately-selective predicate might need to jump to many scattered heap pages, potentially revisiting the same page multiple times if several matching rows happen to live on it (since the index visits entries in **key order**, not **physical page order**). A Bitmap Scan avoids this by first collecting **all** the matching page locations into a bitmap, then reading the heap in efficient, page-order sequence, visiting each needed page **exactly once** — combining some of the sequential-scan's I/O efficiency with the index's targeted precision, ideal for moderate selectivity where neither pure sequential nor pure index scan is optimal.

### Also Useful For Combining Multiple Indexes

A Bitmap Scan can also **combine multiple separate indexes** for a single query (e.g., `WHERE status = 'active' AND category = 'electronics'`, with separate indexes on each column) by building a bitmap from each index separately and then performing a bitwise AND/OR between them — something a traditional single-index B+ Tree traversal cannot do as naturally.

*(Full execution-plan-level detail and cost formulas are covered in Part 8: Query Processing & Optimization — this module introduces it from the storage/index-usage perspective only.)*

### Interview Importance
⭐⭐⭐⭐ — Recall Module 5, Section 5.13's important distinction: PostgreSQL's Bitmap Scan is a **runtime execution strategy**, not a persistent stored index type (unlike Oracle's Bitmap Index) — this module is where that distinction pays off with full execution-level context.

## 10.11 Chapter Summary

- The optimizer chooses among candidate access paths (sequential scan, various index scans) using a **cost-based model**, driven fundamentally by **selectivity** and **cardinality** estimates.
- **Selectivity** (fraction of matching rows) and **cardinality** (distinct value count) determine whether an index helps — low selectivity favors indexes, high selectivity favors sequential scans.
- **Histograms** give the optimizer much more accurate selectivity estimates than assuming uniform distribution, especially for range predicates; **stale statistics** are one of the most common real-world causes of unexpectedly bad query plans.
- The **independence assumption** (columns are statistically unrelated) can mislead composite-index selectivity estimates; extended/multi-column statistics exist to correct this in modern engines.
- **Index-Only Scans** are the execution-level payoff of covering indexes, subject to PostgreSQL's Visibility Map coverage.
- The **five-point debugging checklist** (selectivity, stale stats, functional mismatch, leftmost prefix violation, table too small) is the practical toolkit for "why isn't my index being used?" — one of the most valuable takeaways in the entire handbook.
- **Bitmap Scans** bridge the gap between sequential and index scans for moderate selectivity, and can combine multiple indexes via in-memory bitmap AND/OR operations.

---

## 10.12 Cheat Sheet

```
Selectivity      = matching_rows / total_rows   (LOW selectivity -> index helps; HIGH -> seq scan often wins)
Cardinality      = number of DISTINCT values in a column
Histogram        = bucketed data distribution summary -> accurate selectivity for RANGE predicates
Stale Statistics = #1 real-world cause of "plan suddenly got worse" -> fix: ANALYZE / update stats
Independence Assumption = optimizer assumes columns are unrelated by default; extended stats can fix this

Index-Only Scan  = answered ENTIRELY from index, no heap fetch (needs covering index + PG Visibility Map OK)
Sequential Scan wins when: high selectivity, small table, most columns/rows needed anyway
Index Scan wins when: low selectivity, covering/composite index usable, sorted output needed

5-POINT "WHY ISN'T MY INDEX USED" CHECKLIST:
  1. Selectivity too high for this specific value?
  2. Statistics stale?
  3. Functional/expression mismatch (filtering on transformed column, no expression index)?
  4. Leftmost prefix rule violated (composite index)?
  5. Table too small to bother?

Bitmap Scan = build in-memory bitmap of matching PAGES -> visit heap in PAGE order, once each
              -> can COMBINE multiple indexes via bitwise AND/OR
              (PostgreSQL: runtime strategy, NOT a stored index type -- contrast Oracle's Bitmap Index)
```

**Q1.** Low selectivity means:
A) A predicate matches most rows  B) A predicate matches very few rows  C) The column has no distinct values  D) The table has no index
*(Answer: B)*

**Q2.** What is the most common real-world cause of a sudden, unexplained query plan regression after a large data load?
A) Disk failure  B) Stale statistics  C) Buffer pool eviction  D) Network latency
*(Answer: B)*

**Q3.** An Index-Only Scan requires:
A) Any index on the filtered column  B) A covering index containing all needed columns (and, in PostgreSQL, sufficient Visibility Map coverage)  C) A hash index specifically  D) A sequential scan first
*(Answer: B)*

**Q4.** A Bitmap Scan primarily helps by:
A) Avoiding any use of indexes  B) Visiting each needed heap page exactly once, in physical page order, after building an in-memory bitmap from one or more indexes  C) Replacing the need for statistics entirely  D) Sorting the entire table
*(Answer: B)*

**Q5.** The optimizer's "independence assumption" refers to:
A) Assuming each table is independent of others  B) Assuming different columns' values are statistically unrelated, which can misestimate composite predicate selectivity  C) Assuming indexes are independent of the buffer pool  D) Assuming all queries run independently
