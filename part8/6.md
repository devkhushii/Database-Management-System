> **Prerequisite check:** This module assumes Modules 1–5. You should be comfortable with access paths (Module 5), cost estimation (Module 2, §2.4), and cardinality (Module 4). Joins are typically the **most expensive** operators in a plan — this module is one of the highest-interview-value modules in the entire handbook.

## 6.0 Why This Module Exists

A join combines rows from two (or more) inputs based on a matching condition. The *result* is always the same, mathematically, regardless of algorithm — but the **cost** to produce that result varies enormously depending on which algorithm is used, how much memory is available, whether indexes exist, and how large each input is.

### The Three Classic Join Algorithms (Preview)

```
┌─────────────────────────────────────────────────────────┐
│  NESTED LOOP JOIN    →  "for each row in A, scan B"        │
│  SORT-MERGE JOIN     →  "sort both, then merge like zipper"│
│  HASH JOIN           →  "hash one side, probe with other"  │
└─────────────────────────────────────────────────────────┘
```

Every join algorithm covered in this module is a variation or refinement of one of these three core ideas.

## 6.1 Nested Loop Join

### Definition

**Nested Loop Join** is the simplest join algorithm: for **every row** in the **outer** input, scan the **entire inner** input, emitting a joined row for each match.

### Internal Working (Pseudocode)

```
FOR EACH row_outer IN outer_table:
    FOR EACH row_inner IN inner_table:
        IF join_condition(row_outer, row_inner):
            EMIT (row_outer, row_inner)
```

### Execution Tree

```
        Nested Loop Join
        (outer.id = inner.outer_id)
        /                        \
   outer_table              inner_table
   (scanned once)         (scanned ONCE PER
                            outer row!)
```

### Complexity Analysis

| Metric | Value |
|---|---|
| Time Complexity | O(N × M) — N = outer rows, M = inner rows |
| I/O (naive, no index, no buffering) | O(N × pages(inner)) — inner table re-read from scratch for every single outer row! |
| Memory Usage | Minimal — O(1) extra memory (just current row pointers) |

### Why It Exists Despite Being "Slow"

For **small** inputs (especially a small outer input), Nested Loop Join has **near-zero overhead** — no sorting, no hashing, no extra memory structures. It's also the **only** join algorithm that naturally supports **non-equi-join conditions** (`<`, `>`, `BETWEEN`, arbitrary expressions) — Hash Join and Sort-Merge Join fundamentally require equality conditions (§6.4, §6.5).

### Real-Life Analogy

Imagine matching guests to seat assignments by walking through a **small guest list** (10 people) and, for each guest, checking a **long seating chart** (1,000 seats) one by one to find their assigned seat. Painfully slow for large inputs — but if the guest list has only 2 people, it's over almost instantly regardless of the seating chart's size.

### When the Optimizer Chooses It
- One input (outer) is **very small**.
- No equality join condition exists (non-equi joins — Hash/Merge Join can't handle these at all).
- Combined with an index on the inner table (→ **Indexed Nested Loop Join**, §6.3 — dramatically changes the complexity picture).

### Interview Importance: ⭐⭐⭐⭐⭐
The baseline join algorithm every interview conversation about joins starts from.

## 6.2 Block Nested Loop Join

### Definition

**Block Nested Loop Join** is an optimization of naive Nested Loop Join that reads the outer input in **blocks/chunks** (as many rows as fit in available memory) rather than one row at a time, comparing each **block** of outer rows against the inner table in a single pass — dramatically reducing how many times the inner table must be re-scanned.

### Why It Exists

Naive Nested Loop Join re-scans the *entire* inner table once **per outer row** — for an outer table of 1,000 rows, that's 1,000 full scans of the inner table! Block Nested Loop reduces this to roughly `(outer rows / block capacity)` scans of the inner table instead.

### Internal Working

```
Divide outer_table into BLOCKS that fit in available memory
(e.g., block_size = 100 rows per block)

FOR EACH block_of_100_outer_rows:
    FOR EACH row_inner IN inner_table:        ← inner table scanned ONCE per BLOCK,
        FOR EACH row_outer IN current_block:     not once per outer ROW
            IF join_condition(row_outer, row_inner):
                EMIT (row_outer, row_inner)
```

### Complexity Improvement

| Metric | Naive Nested Loop | Block Nested Loop |
|---|---|---|
| Inner table scans | N (once per outer row) | `⌈N / block_capacity⌉` (once per block) |
| I/O cost | O(N × pages(inner)) | O((N / B) × pages(inner)), where B = rows per block |

### Worked Example

Outer table: 10,000 rows. Inner table: 100 pages. Block capacity: 500 rows/block.

- **Naive Nested Loop:** 10,000 × 100 = 1,000,000 page reads of the inner table.
- **Block Nested Loop:** (10,000 / 500) × 100 = 20 × 100 = 2,000 page reads — a **500x reduction**.

### PostgreSQL vs MySQL vs Oracle

| Aspect | PostgreSQL | MySQL (InnoDB) | Oracle |
|---|---|---|---|
| Block Nested Loop | Not a distinct named strategy (PostgreSQL relies more heavily on Hash Join/Merge Join for large unindexed joins instead) | Yes — explicit **Block Nested-Loop (BNL) Join** algorithm, especially pre-8.0.18 (largely superseded by Hash Join as the default fallback in 8.0.18+) | Yes, conceptually present within Oracle's Nested Loop optimizations |

### Interview Importance: ⭐⭐⭐
Good to know as the natural "obvious optimization" once someone identifies naive Nested Loop's core weakness — a good follow-up depth question.

## 6.3 Indexed Nested Loop Join

### Definition

**Indexed Nested Loop Join** replaces the inner loop's **full scan** with an **index lookup** — for each outer row, instead of scanning the entire inner table, the algorithm probes an index on the inner table's join column directly.

### Internal Working

```
FOR EACH row_outer IN outer_table:
    matching_rows = INDEX_LOOKUP(inner_table_index, row_outer.join_key)
    FOR EACH row_inner IN matching_rows:
        EMIT (row_outer, row_inner)
```

### Complexity Analysis

| Metric | Value |
|---|---|
| Time Complexity | O(N × log M) if inner index lookup is O(log M) (B+Tree), vs. O(N × M) for naive Nested Loop |
| I/O Cost | O(N × index_lookup_cost) — each lookup pays the random-I/O cost from Module 5, §5.2 |

This is a **dramatic** improvement — turning what could be a catastrophic O(N×M) operation into something close to O(N log M), **provided** a suitable index exists on the inner table's join column.

### Execution Tree

```
        Nested Loop Join
        /                \
   outer_table    Index Scan on inner_table
   (Seq Scan,      (probed once per outer row,
    small table)    using outer_table.join_key
                     as the lookup value each time)
```

### Real-Life Analogy

Instead of flipping through every page of a phone book for each of your 10 contacts (naive Nested Loop), you use the phone book's **alphabetical index** to jump directly to each contact's entry — 10 fast lookups instead of 10 full read-throughs.

### When the Optimizer Chooses It

- The **outer** side is relatively small (or highly filtered).
- A **usable index** exists on the inner table's join column.
- This is often the winning strategy for **highly selective joins** — e.g., fetching a handful of order rows for a specific, small set of customer IDs.

### Cost Trade-off vs. Hash Join

Indexed Nested Loop tends to win when the **outer side is small** (few probes needed); Hash Join (§6.4) tends to win when **both sides are large** (a single hash-build + single probe pass beats N separate index lookups). This exact trade-off is a **very common interview whiteboard question.**

### Interview Importance: ⭐⭐⭐⭐⭐
One of the most important, most practically relevant join algorithms — directly explains why "add an index" so often fixes slow joins in production.

## 6.4 Hash Join

### Definition

**Hash Join** builds an in-memory **hash table** from one input (the "build side," typically the smaller one) keyed on the join column, then scans the other input (the "probe side") and looks up each row in the hash table for matches.

### Internal Working (Two Phases)

```
PHASE 1: BUILD
  Scan the smaller input (build side).
  FOR EACH row: insert into hash table, keyed by join_column.

  Hash Table:
  ┌─────────────────────────────┐
  │ hash(5)  → [row A, row F]    │
  │ hash(12) → [row B]           │
  │ hash(9)  → [row C, row D]    │
  └─────────────────────────────┘

PHASE 2: PROBE
  Scan the larger input (probe side).
  FOR EACH row: compute hash(join_column), look up matching bucket,
                emit joined rows for any matches found.
```

### Execution Tree

```
            Hash Join
        (a.id = b.a_id)
        /              \
   Hash (build)     probe input (b)
        │             (scanned once,
   build input (a)     each row hashed
   (scanned once,       & looked up)
    smaller side)
```

### Complexity Analysis

| Metric | Value |
|---|---|
| Time Complexity | O(N + M) — each input scanned once (assuming hash table fits in memory) |
| Memory Usage | O(size of smaller/build-side input) — must fit hash table in `work_mem` (PG) or equivalent |
| I/O Cost (in-memory case) | O(pages(A) + pages(B)) — each table read exactly once |

**This O(N+M) is dramatically better than Nested Loop's O(N×M) for large, unindexed joins** — this is the single most important complexity comparison in this entire module.

### Why the Build Side Should Be the Smaller Input

The hash table must fit comfortably in memory for best performance — building it from the **smaller** input minimizes memory pressure and the risk of needing to spill to disk (§6.5's Grace Hash Join handles the spill case).

### Requirements & Limitations

- **Only works for equality join conditions** (`=`) — cannot handle `<`, `>`, `BETWEEN`, or arbitrary expressions (unlike Nested Loop Join, §6.1).
- Requires enough memory to hold the build-side hash table (or must degrade to disk-based partitioning — §6.5, §6.6).

### Real-Life Analogy

Imagine sorting your small pile of business cards (build side) into a labeled organizer by last-name-initial (the hash function) — A-C in one slot, D-F in another, etc. Then, going through a large stack of meeting notes (probe side), for each note you just check the organizer slot matching that name's initial — one quick lookup instead of re-scanning your whole card pile for every note.

### When the Optimizer Chooses It

- **Equality join** condition.
- Both inputs are **large** (no small, indexable outer side that would favor Indexed Nested Loop, §6.3).
- Sufficient memory available for the build side (or the database's disk-spilling variant is acceptable — §6.5/§6.6).

### Interview Importance: ⭐⭐⭐⭐⭐
**The single most important join algorithm to understand deeply.** Expect detailed questions on build-vs-probe side selection, memory requirements, and the O(N+M) complexity argument.

## 6.5 Grace Hash Join

### Definition

**Grace Hash Join** is the disk-based variant of Hash Join used when **neither input fits comfortably in memory** — it works by first **partitioning** both inputs into smaller matching buckets (using the same hash function on the join key) small enough to fit in memory individually, then performing an in-memory Hash Join (§6.4) on each corresponding pair of partitions independently.

### Why It Exists

A plain in-memory Hash Join (§6.4) assumes the build side fits in `work_mem`. For genuinely large tables (both sides too big for memory), Grace Hash Join provides a way to still achieve roughly linear-time joining by breaking the problem into smaller, memory-sized pieces.

### Internal Working (Two-Phase Partition-Then-Join)

```
PHASE 1: PARTITIONING
  Using hash function h1(join_key), partition BOTH inputs into
  the same number of buckets, writing each partition to disk.

  Input A (large) → h1() → [A-Partition0] [A-Partition1] [A-Partition2] ...
  Input B (large) → h1() → [B-Partition0] [B-Partition1] [B-Partition2] ...

  KEY INSIGHT: All rows with the same join key hash to the SAME
  partition number in BOTH inputs — so matching rows can ONLY
  exist within corresponding partition pairs (A-Partition_i,
  B-Partition_i). Different partition numbers can NEVER match.

PHASE 2: JOIN EACH PARTITION PAIR INDEPENDENTLY
  FOR EACH partition i:
      Perform an in-memory Hash Join (§6.4) between
      A-Partition_i and B-Partition_i
      (each individual partition is now small enough to fit in memory!)
```

### Diagram

```
   Input A (huge)                    Input B (huge)
        │                                  │
   Partition by hash(join_key)      Partition by hash(join_key)
        │                                  │
   ┌────┼────┬────┐                  ┌────┼────┬────┐
   ▼    ▼    ▼    ▼                  ▼    ▼    ▼    ▼
  A0   A1   A2   A3                 B0   B1   B2   B3
   │    │    │    │                  │    │    │    │
   └────┼────┼────┼──────────────────┘    │    │    │
        └────┼────┼─────────────────────────────────┘
             (each Ai only ever joined with matching Bi)

   Join(A0,B0)  Join(A1,B1)  Join(A2,B2)  Join(A3,B3)
   (each pair processed as an independent, small, in-memory Hash Join)
```

### Complexity

| Metric | Value |
|---|---|
| Time Complexity | O(N + M) overall (same asymptotic complexity as in-memory Hash Join — the partitioning pass adds a constant-factor overhead, not a complexity class change) |
| I/O Cost | Higher than in-memory Hash Join due to writing/reading partitions to/from disk (each row written and read at least twice — once during partitioning, once during the join phase) |

### Real-Life Analogy

Imagine sorting a massive stack of mixed mail into regional bins first (partitioning) before having each regional office (with limited desk space) individually match sender-to-recipient within just their own bin — rather than trying to cram the entire country's mail onto one overwhelmed desk at once.

### Interview Importance: ⭐⭐⭐⭐
A strong "goes beyond the basics" topic — shows you understand what happens when data **doesn't fit in memory**, a very real production concern.

## 6.6 Hybrid Hash Join

### Definition

**Hybrid Hash Join** is a practical refinement of Grace Hash Join (§6.5) that keeps the **first partition** entirely **in memory** (skipping the disk write/read round-trip for that one partition) while the remaining partitions are still written to disk and processed as in Grace Hash Join — getting partial benefits of pure in-memory Hash Join without requiring the *entire* dataset to fit in memory.

### Why It Exists

Pure Grace Hash Join writes **every** partition to disk, even when memory conditions are only *slightly* insufficient for a fully in-memory join. Hybrid Hash Join recognizes that available memory is rarely "zero" — it's usually "not quite enough for everything, but enough for a good chunk." Keeping one partition resident in memory reduces total I/O compared to naively partitioning everything.

### Internal Working

```
Available memory = enough to hold hash table for 1 partition + I/O buffers
                    for writing the remaining partitions to disk

PHASE 1: PARTITION (with partition 0 kept in memory)
  Input A → partition by hash(key) →
      Partition 0 → KEPT IN MEMORY (build hash table immediately, no disk write)
      Partition 1 → written to disk
      Partition 2 → written to disk
      ...

  Input B → partition by hash(key) →
      Partition 0 → PROBED IMMEDIATELY against in-memory Partition-0
                     hash table from A (no disk round-trip needed at all!)
      Partition 1 → written to disk (joined later, Grace-Hash-style)
      Partition 2 → written to disk (joined later, Grace-Hash-style)

PHASE 2: JOIN REMAINING DISK PARTITIONS (same as Grace Hash Join, §6.5)
```

### Why This Is Strictly Better Than Pure Grace Hash Join

Partition 0's rows (for **both** inputs) **never touch disk at all** — saving I/O for that fraction of the data, while the remaining partitions still get the memory-bounded correctness guarantee of Grace Hash Join. As available memory increases, more partitions can be kept resident, gracefully approaching pure in-memory Hash Join performance — this is the essence of it being a genuine "hybrid."

### PostgreSQL vs MySQL vs Oracle: Real Implementations

| Aspect | PostgreSQL | MySQL (InnoDB, 8.0.18+) | Oracle |
|---|---|---|---|
| Hash Join implementation | Hybrid Hash Join, spills to disk in batches when `work_mem` exceeded | Uses a form of Hash Join since 8.0.18 (replacing Block Nested Loop as the default fallback for equi-joins without usable indexes) | Sophisticated hybrid hash join with adaptive multi-pass partitioning for very large joins |

### Interview Importance: ⭐⭐⭐⭐
Excellent depth-signal topic — "how does Hash Join actually behave when data doesn't perfectly fit in memory" is exactly the kind of nuanced follow-up senior interviewers ask after a candidate correctly explains basic Hash Join.

## 6.7 Sort-Merge Join (Sort Merge Join)

### Definition

**Sort-Merge Join** works by first **sorting** both inputs on the join key (if not already sorted), then scanning both sorted streams **simultaneously**, advancing pointers in a "merge" pattern (like the merge step of merge sort) to find matching rows.

### Internal Working (Two Phases)

```
PHASE 1: SORT (if not already sorted, e.g., via an index)
  Sort input A by join_key
  Sort input B by join_key

PHASE 2: MERGE
  ptr_A = start of sorted A
  ptr_B = start of sorted B

  WHILE ptr_A and ptr_B haven't reached the end:
      IF A[ptr_A].key == B[ptr_B].key:
          EMIT matching rows (handle duplicate keys carefully — see below)
          advance appropriately
      ELIF A[ptr_A].key < B[ptr_B].key:
          advance ptr_A
      ELSE:
          advance ptr_B
```

### Visual Walkthrough

```
Sorted A (by key):  [1, 3, 3, 5, 8]
Sorted B (by key):  [1, 3, 4, 8, 9]

ptr_A=1, ptr_B=1  → MATCH (1=1) → emit, advance both
ptr_A=3, ptr_B=3  → MATCH (3=3) → emit ALL A-rows with key=3 against
                                    ALL B-rows with key=3 (duplicate
                                    handling — a "mini nested loop"
                                    within matching key groups)
ptr_A=5, ptr_B=4  → 5 > 4 → advance ptr_B
ptr_A=5, ptr_B=8  → 5 < 8 → advance ptr_A
ptr_A=8, ptr_B=8  → MATCH (8=8) → emit, advance both
                     (ptr_B continues: 9 has no match in A → done)
```

### Complexity Analysis

| Metric | Value |
|---|---|
| Time Complexity (if already sorted) | O(N + M) — pure merge pass, extremely efficient |
| Time Complexity (needs sorting first) | O(N log N + M log M) — dominated by the sort cost |
| Memory Usage | Low for the merge phase itself; sorting phase may require external sort (Module 7) if inputs don't fit in memory |

### The Killer Feature: "Sort for Free" via Index

If an index already exists on the join column for one or both tables, that index can be scanned **in sorted order directly** (§5.2/§5.7), completely **skipping the explicit sort phase** — making Sort-Merge Join extremely cheap, essentially O(N+M), with no sort overhead at all.

### Sort-Merge Join vs. Hash Join: When Each Wins

| Scenario | Winner | Why |
|---|---|---|
| Both inputs already sorted (e.g., via index) | Sort-Merge Join | No sort cost at all — pure O(N+M) merge |
| Result needs to be sorted anyway (e.g., for a later `ORDER BY` or `GROUP BY`) | Sort-Merge Join | "Sort is already needed elsewhere" — reuse it |
| Neither input sorted, no relevant index, large unsorted data | Hash Join | Avoids paying an explicit O(N log N) sort cost just for the join |
| Non-equality join conditions (`<`, `BETWEEN`) | Sort-Merge Join (can be adapted) or Nested Loop | Hash Join fundamentally cannot handle non-equality conditions |
| Highly skewed join keys with huge duplicate groups | Can degrade — the "match all duplicates" step becomes expensive | Both Hash Join and Sort-Merge Join can suffer here, though for different underlying reasons |

### Real-Life Analogy

Imagine two people each holding a **sorted stack** of numbered tickets, standing side by side. They compare their top tickets: if equal, they set them aside as a match and both draw their next ticket; if one ticket number is smaller, that person draws their next ticket alone (skipping ahead) while the other waits. They proceed in lockstep — a "zipper" merge — until one stack runs out.

### PostgreSQL vs MySQL vs Oracle

| Aspect | PostgreSQL | MySQL (InnoDB) | Oracle |
|---|---|---|---|
| Sort-Merge Join support | Yes, mature, used especially when inputs are pre-sorted via index or `ORDER BY` needs align | Historically **not supported** as a distinct strategy until relatively recent versions; relies primarily on Nested Loop/Block Nested Loop/Hash Join instead | Yes, mature, commonly used for large joins with pre-sorted or indexed inputs |

### Interview Importance: ⭐⭐⭐⭐⭐
Very commonly tested, especially the **"sort for free via index"** insight, and the Hash-Join-vs-Sort-Merge-Join decision trade-offs.

## 6.8 Adaptive Join (Overview)

### Definition

**Adaptive Join** refers to modern optimizer features that **defer or revise** the join algorithm choice based on **actual runtime behavior**, rather than committing irrevocably to a single algorithm purely from pre-execution cost estimates — directly addressing Module 4's core problem: estimates can be wrong, sometimes badly so.

### Why It Exists

As established extensively in Module 4 (§4.12), cardinality estimates can be significantly wrong, leading the optimizer to pick a join algorithm that turns out to be a poor fit once real execution begins. Adaptive Join mechanisms attempt to **course-correct mid-execution**, rather than being permanently locked into a potentially bad decision made before any data was actually touched.

### Example Pattern: SQL Server's Adaptive Join

SQL Server's Adaptive Join literally starts execution **without committing** to Nested Loop vs. Hash Join — it begins reading the build-side input, and only **after** seeing the actual row count does it decide (via a threshold) which join algorithm to actually execute:

```
                    Adaptive Join Operator
                            │
              Read build-side input, count rows as they arrive
                            │
              ┌─────────────┴─────────────┐
        rows < threshold              rows ≥ threshold
              │                             │
              ▼                             ▼
      Execute as Nested Loop Join    Execute as Hash Join
      (build side turned out small)  (build side turned out large)
```

### Other "Adaptive" Concepts Across Databases

| Database | Adaptive Mechanism |
|---|---|
| SQL Server | Adaptive Join operator (row-count-threshold-based algorithm switch, as above) |
| Oracle | Adaptive Query Optimization — includes **Adaptive Plans** (can switch Nested Loop ↔ Hash Join mid-execution based on actual cardinality observed) and **SQL Plan Directives** (persist learned corrections for future executions of similar queries) |
| PostgreSQL | No true mid-execution adaptive join switching in core PostgreSQL as of this writing — relies primarily on accurate upfront statistics (Module 4) and extended statistics for correlated columns instead |

### Interview Importance: ⭐⭐⭐
Good "staying current with modern optimizer research" signal — mention this as the natural evolution beyond pure static cost-based optimization, directly motivated by the cardinality estimation challenges from Module 4.

## 6.9 Master Comparison Table: All Join Algorithms

| Algorithm | Time Complexity | Memory Usage | Handles Non-Equi Joins? | Best Use Case |
|---|---|---|---|---|
| Nested Loop Join | O(N × M) | O(1) | Yes | Very small outer input |
| Block Nested Loop Join | O((N/B) × M) | O(block size) | Yes | Small-medium inputs, no index |
| Indexed Nested Loop Join | O(N log M) | O(1) | Limited (index-supportable conditions) | Small outer + indexed inner |
| Hash Join | O(N + M) | O(size of smaller input) | No — equality only | Large unsorted inputs, equi-join |
| Grace Hash Join | O(N + M), higher I/O constant | O(memory per partition) | No — equality only | Large inputs, insufficient memory |
| Hybrid Hash Join | O(N + M), lower I/O than Grace | O(1 partition + buffers) | No — equality only | Large inputs, partial memory available |
| Sort-Merge Join | O(N log N + M log M), or O(N+M) if pre-sorted | O(sort buffer), or O(1) if pre-sorted | Yes (adaptable) | Pre-sorted/indexed inputs, or result needs sorting anyway |
| Adaptive Join | Varies (chooses at runtime) | Varies | Depends on chosen sub-algorithm | Uncertain/unreliable cardinality estimates |

## 6.11 Best Practices, Common Mistakes & Edge Cases

### Best Practices
- Ensure join columns are indexed when one side of a join is expected to be small/highly selective — enables Indexed Nested Loop, often the fastest option in that scenario.
- Keep statistics fresh (Module 4) — join algorithm selection is entirely dependent on accurate size/selectivity estimates for both inputs.
- Be aware of your database's memory configuration (`work_mem` in PostgreSQL, join buffer settings in MySQL) — undersized memory forces disk-based Grace/Hybrid Hash Join variants, adding I/O overhead.
- When a query already needs sorted output (`ORDER BY` on the join key), check whether the optimizer is reusing that sort for a Sort-Merge Join rather than paying for it twice.

### Common Mistakes
- Assuming Hash Join is *always* better than Nested Loop — for a very small outer input with a good index, Indexed Nested Loop is typically far cheaper.
- Forgetting that Hash Join **cannot** handle non-equality conditions at all — a `BETWEEN` or `<` join condition forces Nested Loop or (partially) Sort-Merge Join instead.
- Under-provisioning memory for hash joins on large tables, causing unexpected spills to Grace/Hybrid Hash Join disk-based execution, with associated I/O overhead.

### Edge Cases
- **Highly skewed join keys** (a few keys with enormous numbers of duplicates) can cause a single hash bucket or sort-merge duplicate-group to become a bottleneck, regardless of algorithm — sometimes requiring specialized skew-handling techniques in distributed systems (beyond this module's single-node scope).
- **Very large numbers of NULLs** in the join key: NULLs never match anything in a standard equi-join (`NULL = NULL` is not true in SQL's three-valued logic) — this affects both Hash Join bucket sizing and Sort-Merge Join's duplicate-group handling.

## 6.12 Chapter Summary

- **Nested Loop Join** is simple, O(N×M), best for tiny outer inputs; **Block Nested Loop** amortizes the inner-scan cost across blocks; **Indexed Nested Loop** replaces the inner scan with an index probe, achieving O(N log M).
- **Hash Join** achieves O(N+M) for equality joins by building a hash table on the smaller input and probing with the larger — the default workhorse for large, unsorted, unindexed equi-joins.
- **Grace Hash Join** partitions both inputs to disk when neither fits in memory; **Hybrid Hash Join** improves on this by keeping the first partition resident in memory, avoiding unnecessary disk round-trips.
- **Sort-Merge Join** sorts both inputs then merges them in a single O(N+M) pass — and can get this sort "for free" if an index already provides sorted order, making it extremely competitive in that scenario.
- **Adaptive Join** mechanisms (SQL Server, Oracle) defer the final algorithm choice until actual runtime cardinality is observed, directly mitigating Module 4's cardinality estimation risk — not present in core PostgreSQL.

```
JOIN ALGORITHM SELECTION CHEAT SHEET
──────────────────────────────────────
Tiny outer input, no index         → Nested Loop Join
Tiny outer input, index on inner   → Indexed Nested Loop Join  (often FASTEST)
Large unsorted equi-join           → Hash Join                 (O(N+M), workhorse)
Large equi-join, insufficient RAM  → Grace / Hybrid Hash Join  (disk partitioning)
Inputs already sorted (via index)  → Sort-Merge Join           ("sort for free")
Non-equality join condition        → Nested Loop (or adapted Sort-Merge)
Uncertain/risky cardinality est.   → Adaptive Join (SQL Server/Oracle only)

COMPLEXITY CHEAT SHEET
────────────────────────
Nested Loop:          O(N × M)
Indexed Nested Loop:  O(N log M)
Hash Join:             O(N + M)
Sort-Merge (sorted):   O(N + M)
Sort-Merge (unsorted): O(N log N + M log M)
```
