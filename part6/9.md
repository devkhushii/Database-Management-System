# Part 6: Transactions & Concurrency Control

## Module 9: Optimistic Concurrency Control (OCC)

> Locking (Modules 6–7) is **pessimistic**: it assumes conflicts are likely, so it blocks proactively. Timestamp Ordering (Module 8) checks conflicts eagerly on every operation. **Optimistic Concurrency Control (OCC)** takes the opposite philosophy entirely: assume conflicts are **rare**, let transactions run completely freely without any blocking or per-operation checking, and only verify correctness once, at the very end, right before commit.

---

### 9.1 Why OCC? The Core Philosophy

**Definition:** **Optimistic Concurrency Control** is a concurrency control approach where transactions execute without acquiring any locks and without any per-operation conflict checks. Instead, each transaction proceeds through three distinct phases — **Read, Validation, Write** — and conflicts are detected (and resolved via abort) only during the **Validation phase**, just before the transaction would commit.

**Why it exists:** In workloads where **conflicts are genuinely rare** (e.g., most transactions touch completely different data, or the read-heavy nature of the workload means write-write conflicts are uncommon), the overhead of pessimistic locking — acquiring/releasing locks for every single operation, maintaining a lock table, checking compatibility on every access — is pure waste most of the time. OCC bets that "it's cheaper to just let everyone run freely and occasionally redo the rare conflicting transaction, than to pay the constant tax of locking on every single operation."

**Real-world analogy:**
Think of OCC like **writing a research paper draft assuming no one else is editing the shared document**, working entirely offline, and then — right before you submit your final version — checking whether anyone else has published a conflicting edit in the meantime. If no one has, you submit and you're done. If someone *has* made a conflicting change, you discard your draft and start over based on the latest version — rather than requiring everyone to take turns editing one at a time (locking) or checking with a central clock before every single sentence you write (timestamp ordering).

---

### 9.2 The Three Phases of OCC

```
┌─────────────┐      ┌──────────────┐      ┌─────────────┐
│  READ PHASE │ ───► │  VALIDATION  │ ───► │ WRITE PHASE │
│             │      │    PHASE     │      │             │
└─────────────┘      └──────────────┘      └─────────────┘
      │                     │
      │              if validation FAILS
      │                     │
      │                     ▼
      │              ┌─────────────┐
      └─────────────►│    ABORT    │
     (transaction     │  & RESTART  │
      re-attempted)   └─────────────┘
```

---

### 9.3 Read Phase

**What happens:** The transaction executes **all** of its operations — reads AND writes — but critically, **writes are NOT applied to the actual, shared database.** Instead:
- All values **read** are taken from the current committed state of the database (or a locally cached snapshot).
- All values the transaction wants to **write** are computed and stored in a **private, local workspace** (sometimes called a "shadow copy" or local buffer) — completely invisible to any other transaction.

**Why writes are deferred:** Because no other transaction can see this transaction's writes yet, there's zero risk of dirty reads or dirty writes during this phase — by construction, no interference is even *possible*, since nothing has touched shared state yet.

**Example:**

```
T1 (Read Phase):
  local_balance_A = READ(A)          -- reads from DB: 1000
  local_balance_A = local_balance_A - 100   -- computed locally: 900
  -- (NOT written to the real database yet — stored in T1's private workspace)
```

---

### 9.4 Validation Phase

**What happens:** Just before the transaction is ready to commit, the system checks whether the transaction's Read Phase would have been "safe" if it had executed **serially** relative to all other transactions that have validated (and potentially committed) since this transaction began. This is the **only** point at which conflict detection happens in OCC.

**The validation test (a simplified, standard formulation):**

For a transaction Ti being validated, and every other transaction Tj such that `TS(Tj) < TS(Ti)` (Tj started before Ti, using timestamps assigned — commonly — at the *start* of the Validation phase rather than the start of the transaction, a subtlety covered in 9.5), **one of the following must hold**:

1. **Tj completes its entire Write Phase before Ti even begins its Read Phase.** (No overlap at all — trivially safe.)
2. **The set of data items Ti reads (`ReadSet(Ti)`) does not intersect with the set of items Tj wrote (`WriteSet(Tj)`), AND Tj completes its Write Phase before Ti begins its Write Phase.** (Ti never read anything Tj changed, even though their execution overlapped in time.)
3. **`ReadSet(Ti)` does not intersect `WriteSet(Tj)`, AND `WriteSet(Ti)` does not intersect `WriteSet(Tj)`, AND Tj completes its Read Phase before Ti completes its Read Phase.** (A more permissive condition allowing greater overlap, used in some formulations.)

**If none of these conditions hold** for some Tj, validation **fails** — Ti is **aborted** and must restart (typically with a fresh read phase against the now-current database state).

**Simplified, exam-friendly version of the core check:** *"Did any transaction that committed after I started my Read Phase write to something I read?"* — if yes, abort; if no, validation succeeds.

---

### 9.5 Write Phase

**What happens:** If validation succeeds, all of the transaction's buffered writes (from its private workspace) are now **applied to the real, shared database**, atomically, and the transaction commits.

**Why this final step is safe:** Validation already confirmed that no conflicting transaction interfered during the read phase — so applying the writes now cannot introduce any anomaly that validation would have caught.

---

### 9.6 Full Worked Example — OCC in Action

```
Time    T1 (Read Phase)              T2 (Read Phase)
----    ---------------------------  ---------------------------
t1      begin, local_A = READ(A)=100
t2                                   begin, local_A = READ(A)=100
t3      local_A = 100 - 20 = 80
t4                                   local_A = 100 + 50 = 150
t5      → VALIDATION for T1:
          ReadSet(T1) = {A}
          No other txn has committed
          writes to A since T1 began.
          ✔ VALIDATION SUCCEEDS
t6      → WRITE PHASE: A is now 80 in the real DB. T1 COMMITS.
t7                                   → VALIDATION for T2:
                                        ReadSet(T2) = {A}
                                        T1 committed a write to A
                                        AFTER T2 began its read phase!
                                        ✘ VALIDATION FAILS
t8                                   → T2 is ABORTED, must restart.
                                        On restart, T2 re-reads A=80
                                        and recomputes: 80+50=130.
```

This demonstrates OCC's core behavior precisely: both transactions ran **completely unblocked** through their read phases (no locks, no waiting), but the *second* one to validate (T2) discovered a genuine conflict and had to redo its work — exactly the "lost update" scenario from Module 5.2, except here it's **caught and prevented** via validation, rather than silently corrupting data.

---

### 9.7 Validation Rules — Deeper Formalization

To make the validation condition from Section 9.4 more precise for exam purposes, define for each transaction Ti three timestamps, all assigned during its lifecycle:

- **`Start(Ti)`**: when Ti began its Read Phase.
- **`Validation(Ti)`**: when Ti finished its Read Phase and began Validation.
- **`Finish(Ti)`**: when Ti completed its Write Phase (i.e., committed).

**The formal validation condition** for validating Ti against every earlier-validated Tj (where `Validation(Tj) < Validation(Ti)`):

```
EITHER:
   Finish(Tj) < Start(Ti)                      -- completely serial, no overlap
OR:
   [ WriteSet(Tj) ∩ ReadSet(Ti) = ∅ ]
   AND
   Finish(Tj) < Validation(Ti)                  -- Tj finished writing before Ti tries to validate
```

If this holds for **every** previously-validated Tj, Ti's validation succeeds.

### 9.8 Use Cases for OCC

OCC shines specifically when:
1. **Read-heavy, write-light workloads** — most transactions are reads, so write-write and read-write conflicts are naturally rare.
2. **Low contention** — transactions tend to touch different, non-overlapping data.
3. **Short transactions** — the shorter the Read Phase, the smaller the window during which a conflicting transaction could commit and invalidate it.
4. **Distributed / high-latency environments** where acquiring and releasing locks across a network would be prohibitively slow — OCC avoids that round-trip cost entirely during normal execution, paying the cost only at validation/commit time.

**Industry usage:** OCC-style validation is used heavily in:
- **Application-level "optimistic locking"** patterns using a version number or `updated_at` column (`UPDATE ... WHERE id=? AND version=?`) — an extremely common pattern in web application backends and ORMs (Hibernate's `@Version`, Django's optimistic locking extensions, etc.).
- **In-memory databases** and certain **NewSQL** systems (e.g., early designs inspired by the classic Kung & Robinson OCC paper).
- **Git** itself is conceptually an OCC-like system for concurrent code changes — everyone edits their local copy freely (Read Phase equivalent), and a `push` is validated against the remote's current state before being accepted (Validation Phase equivalent) — a great teaching analogy for interviews.

### 9.9 Performance Trade-offs

| Aspect | OCC | 2PL (Pessimistic) |
|---|---|---|
| Blocking during execution | None | Frequent, proportional to contention |
| Conflict detection timing | Only at validation (end) | Continuously (every lock request) |
| Cost of a conflict | Entire transaction re-executed | Transaction merely waits |
| Best for | Low contention | Moderate-to-high contention |
| Worst case | High contention → high abort/retry rate, wasted work, possible **livelock**-like thrashing under very high contention | High contention → blocking chains, possible deadlocks |
| Deadlocks? | **No** — nothing ever waits on a lock | Yes, requires separate handling (Module 12) |

**Key exam/interview point:** *OCC's performance is a direct bet on low contention.* Under high contention, OCC can perform **significantly worse** than locking, because instead of a transaction simply waiting a short time (as it would under 2PL), it does its **entire** read phase of work, only to have it **thrown away** at validation and redone — potentially repeatedly. This makes OCC a poor choice for hot, highly-contended data (e.g., a single row incremented by thousands of concurrent transactions per second), where locking or specialized atomic-increment mechanisms perform far better.

---

### 9.10 Advantages, Disadvantages, Best Practices

**Advantages:**
- Zero blocking during normal execution — excellent for low-contention, read-heavy workloads.
- No deadlocks possible (like Timestamp Ordering, no transaction ever waits on another).
- No lock manager overhead during execution — simpler runtime path for the common case.
- Naturally suited to distributed/high-latency systems where lock round-trips are expensive.

**Disadvantages:**
- Wasted work on abort — an entire transaction's read-phase computation is discarded on validation failure.
- Poor performance under high contention (can degrade badly, sometimes described informally as thrashing).
- Starvation risk: a transaction that repeatedly conflicts with others (e.g., a long-running report against frequently-updated data) might never successfully validate.
- Requires careful application design to handle retries gracefully (idempotency, bounded retry counts).

**Best Practices:**
- Use OCC-style optimistic locking (version columns) specifically for scenarios with **infrequent** concurrent edits to the same row (e.g., user profile updates), not for hot, high-throughput counters.
- Always implement a **retry loop with a reasonable maximum attempt count** and clear failure handling when using application-level optimistic locking.
- Keep the Read Phase as **short** as possible to minimize the window of potential conflict.

**Common Mistakes:**
- Using OCC/optimistic locking for genuinely high-contention resources (e.g., a global "total orders processed" counter incremented by every transaction) — this virtually guarantees a high abort rate and poor performance; a dedicated atomic counter or sequence is far more appropriate.
- Forgetting to implement retry logic at the application layer — an OCC conflict must be handled explicitly (unlike a lock wait, which resolves "automatically" once the lock is released).
- Not communicating to end users why an "optimistic locking failure" occurred (e.g., "someone else updated this record — please refresh and try again"), leading to a confusing user experience if handled poorly.

**Performance Implications:** See Section 9.9's comparison table — this is fundamentally a contention-dependent trade-off, one of the most important "it depends" answers in concurrency control interviews.

### 9.11 Chapter Summary

- **OCC** has three phases: **Read** (execute freely, buffer writes locally), **Validation** (check for conflicts against transactions that validated earlier), **Write** (apply buffered writes if validation succeeds).
- Validation succeeds if no overlapping, already-committed transaction wrote to something this transaction read (roughly speaking).
- OCC has **zero blocking** and is **deadlock-free**, but pays for this with **wasted work on abort** under contention.
- Best suited for **low-contention, read-heavy** workloads; poor fit for **high-contention hot data**.
- Widely used in practice as **application-level optimistic locking** (version columns) and conceptually mirrors systems like Git.

---

### 9.12 Revision Notes / Cheat Sheet

```
READ PHASE       : execute freely, buffer writes locally, NOTHING visible to others
VALIDATION PHASE : check ReadSet(Ti) against WriteSet(Tj) for overlapping, earlier-validated Tj
WRITE PHASE       : apply buffered writes atomically if validation passed; else ABORT & RETRY

OCC guarantees:      Serializability ✔ (via validation), Deadlock-freedom ✔
OCC trade-off:        Low contention = great. High contention = wasted work, poor throughput.
```

### 9.15 GATE-Style Questions

**Q1.** Two transactions T1 and T2 both read data item X during overlapping Read Phases. T1 validates and commits first, writing to X. What happens when T2 attempts to validate?
<details><summary>Answer</summary>T2's validation fails, because a transaction (T1) that validated/committed after T2 began its Read Phase wrote to something (X) that T2 read. T2 is aborted and must restart.</details>

**Q2.** True/False: OCC can result in deadlock if two transactions both read and want to write the same data item.
<details><summary>Answer</summary>False — OCC never blocks, so deadlock (a circular wait condition) cannot occur; conflicts result in abort, not waiting.</details>
