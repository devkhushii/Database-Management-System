### 14.1 Case Study: `SELECT` with a Sequential Scan

```sql
SELECT * FROM orders WHERE total_amount > 10000;
```
*(Assume no index on `total_amount`, or the optimizer estimates low selectivity for it.)*

**Trace:**
1. **Parser** (Module 1, §1.4.1) builds an AST from the SQL text.
2. **Analyzer** confirms `orders` and `total_amount` exist via the **Catalog Manager** (Module 1, §1.4.9; Module 11).
3. **Optimizer** (Module 1, §1.4.2) considers a Sequential Scan vs. an Index Scan (if any index exists); using statistics from `pg_statistic`/InnoDB's persistent stats tables (Module 11, §11.5), it estimates the predicate matches a large fraction of rows, making a **Sequential Scan** cheaper (avoids per-row random heap lookups an index path would otherwise incur).
4. **Transaction Manager** (Module 1, §1.4.6) ensures a snapshot/Read View exists (Module 5) — for `READ COMMITTED`, likely a fresh one for this statement.
5. **Executor** (Module 8) invokes the `Seq Scan` node's `next()` in a loop, driven from above by a `Filter` node.
6. For each page: **Buffer Manager** (Module 6) is asked for it — checked against the buffer pool (clock-sweep in Postgres, young/old LRU in InnoDB); on a miss, **Storage Manager** reads it from the relevant data file (Module 2, 12), likely benefiting from **sequential prefetch/read-ahead** (Module 6, §6.8; Module 13, §13.2) since access is sequential.
7. For each tuple on the page: **MVCC visibility check** (Module 5, §5.4) applied against the snapshot — `xmin`/`xmax` check (Postgres) or `DB_TRX_ID` + undo-chain walk if needed (InnoDB) — to determine if this row version is visible.
8. Visible rows passing the `total_amount > 10000` predicate are returned upward through `Filter` to the client, streamed as they're produced (no blocking operator in this simple query).
9. On completion, the implicit read-only transaction commits trivially (Module 1, §1.6, Example 1).

**Key mechanisms cited:** Optimizer cost estimation, Buffer Manager + sequential prefetch, MVCC visibility, pipelining Filter/Scan execution.

### 14.2 Case Study: `SELECT` with an Index Scan (High Selectivity)

```sql
SELECT name, email FROM users WHERE id = 42;
```

**Trace:** *(This is Module 1's Example 1, restated here with full cross-references for completeness.)*
1–4. Parse/Analyze/Optimize as above, but the **Optimizer** sees a unique index on `id`, estimates a single-row match (very high selectivity), and chooses an **Index Scan** over `users_pkey`.
5. **Executor** invokes `Index Scan.next()`.
6. B-Tree traversal: root page (Module 8, §8.4) — likely a **Buffer Manager hit** since root pages are extremely hot (Module 6). Descends to the leaf page containing key `42`.
   - **PostgreSQL:** the leaf entry gives a `(block, offset)` TID (Module 2, §2.4) pointing directly into the heap.
   - **InnoDB:** since the table is clustered by primary key (Module 4, §4.10), the "index" traversed here *is* the table itself — no separate heap lookup is needed at all; the row data lives at the leaf.
7. **PostgreSQL only:** an additional **Buffer Manager** fetch for the heap page at that TID, then an **MVCC visibility check** on the found tuple.
8. Row is projected to just `name, email` (Module 2's tuple-header/column-layout discussion, §2.9) and returned.

**Key mechanisms cited:** B-Tree traversal, the structural difference between Postgres's heap+index-pointer model and InnoDB's clustered-index model (Module 4, §4.10) — this contrast is exactly the kind of detail a strong answer volunteers unprompted.

### 14.3 Case Study: `INSERT`

```sql
INSERT INTO employees (name, dept, salary) VALUES ('Alice', 'Eng', 95000);
```

**Trace:**
1. Parse/Analyze as usual — the **Catalog Manager** validates column names/types against `pg_attribute`/the InnoDB Data Dictionary (Module 11).
2. **Transaction Manager**: a new (or existing) transaction context, XID/TRX_ID assigned (Module 5, §5.2).
3. **Free Space Map** (Postgres) or extent/segment free-space tracking (InnoDB) is consulted to find a page with room (Module 2, §2.7) — for InnoDB specifically, the row must be placed in **primary-key order** within the clustered index (Module 4, §4.10), which is *why* monotonic primary keys avoid expensive page splits here while random keys (e.g., raw UUIDs) can trigger them.
4. A **WAL/Redo Log record** describing the insert is generated and written to the log buffer (Module 1, 3, 4) — **before** the data page itself is modified (the write-ahead invariant, Module 6, §6.4).
5. The new tuple is written into the chosen page's slot directory (Module 2, §2.4), with its **tuple header** set (`xmin` = this transaction's XID for Postgres; `DB_TRX_ID` for InnoDB — Module 5, §5.2-5.3). The page is marked **dirty** in the Buffer Pool.
6. Any **secondary indexes** must also be updated:
   - **InnoDB:** if the index page isn't currently buffered, the **Change Buffer** (Module 4, §4.5) may defer this write rather than incurring immediate random I/O.
   - **PostgreSQL:** every index is updated synchronously on insert (HOT, Module 3 §3.12, applies only to `UPDATE`s, not fresh `INSERT`s).
7. On `COMMIT`: the WAL/Redo record is durably flushed (subject to `synchronous_commit`/`innodb_flush_log_at_trx_commit`, Modules 3, 4), success returned to the client.
8. The dirtied page(s) are eventually flushed by the Background Writer/Page Cleaner, later bounded by a Checkpoint (Modules 3, 4, 6, 10).

**Key mechanisms cited:** Free space allocation, write-ahead invariant, clustered-index insert-order sensitivity, Change Buffer deferral.

### 14.4 Case Study: `UPDATE`

```sql
UPDATE employees SET salary = salary * 1.1 WHERE emp_id = 101;
```

*(This is Module 1's Example 2 and Module 3's §3.16 write-path, restated here with the InnoDB side fully filled in for direct comparison.)*

**PostgreSQL trace:**
1. Index/heap lookup locates the current row version (as in §14.2's index-scan trace).
2. WAL record generated and buffered.
3. Old tuple's `xmax` set to this transaction's XID; a **new tuple version** is inserted.
4. **HOT check** (Module 3, §3.12): if `salary` isn't indexed and the new version fits on the same page (aided by `FILLFACTOR` headroom, Module 9 §9.6), the update is a **HOT update** — no index maintenance needed at all, just an in-page chain link.
5. If HOT doesn't apply (e.g., `salary` *is* indexed, or no room on the page), every index referencing changed columns gets a new entry pointing at the new tuple location.
6. On commit: WAL flushed, locks released. Old tuple version becomes dead weight, eventually reclaimed by **Autovacuum** (Modules 3, 5, 10).

**InnoDB trace:**
1. Clustered index traversal locates the current row (direct — no separate heap lookup, §14.2).
2. Redo log record generated and buffered.
3. **Undo log record** written, capturing the old `salary` value, linked via a new `DB_ROLL_PTR` (Module 5, §5.3, §5.5).
4. The row is updated **in place** in the clustered index (unlike Postgres — no new physical tuple elsewhere) — `DB_TRX_ID` updated to this transaction's ID.
5. If `salary` isn't part of any secondary index, no secondary index maintenance is needed at all. If it is, the relevant secondary index entries are updated (possibly deferred via the **Change Buffer** if non-unique and the page isn't currently buffered).
6. On commit: Redo Log flushed (per `innodb_flush_log_at_trx_commit`), locks released. The old value remains reconstructable via the undo log until the **Purge Thread** determines it's safe to reclaim (Modules 4, 5, 10).

**This is the single most valuable comparative trace in the entire handbook** — a strong interview answer should be able to produce both sides fluently and explain *why* they diverge (in-heap versioning vs. undo-log versioning, Module 5, §5.3).

### 14.5 Case Study: `DELETE`

```sql
DELETE FROM sessions WHERE expires_at < now();
```

**PostgreSQL trace:**
1. Matching rows located (via scan or index, as in §14.1/§14.2).
2. WAL record generated.
3. Each matching tuple's `xmax` is set to this transaction's XID — **the row is not physically removed**, merely marked as deleted-as-of this transaction (Module 5, §5.3). It remains fully intact on the page.
4. On commit: WAL flushed. The row is now invisible to any *future* snapshot but remains visible to any *concurrent* transaction whose snapshot predates this commit (MVCC visibility rule, Module 5, §5.4).
5. Physical removal only happens later, via **Autovacuum**, once no snapshot could still need it (Module 5, §5.6).

**InnoDB trace:**
1. Matching rows located via the clustered index.
2. Redo log record generated; an **undo log record** capturing the full row (needed to reconstruct it for any older snapshot, or to roll back if this transaction aborts) is written.
3. The row is marked as **delete-marked** in the clustered index (a flag, not immediate physical removal) — conceptually parallel to Postgres's `xmax` approach, but recorded via a flag plus the undo log rather than an in-tuple `xmax` field.
4. On commit: Redo Log flushed. Physical removal from the index happens later, via the **Purge Thread**, once no Read View could still need the old version (Module 5, §5.6).

**Key synthesis point:** Both engines treat `DELETE` as fundamentally an **MVCC-versioning operation**, not an immediate physical erasure — this is *why* Module 5's garbage-collection discussion (VACUUM/Purge) applies just as much to `DELETE` as it does to `UPDATE`.

### 14.6 Case Study: `JOIN` (Hash Join, Concrete Trace)

```sql
SELECT o.order_id, c.name
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE o.order_date > '2026-01-01';
```

**Trace, assuming the Optimizer chooses a Hash Join** (Module 8, §8.5) — likely because `customers` (the smaller table, becomes the build side) has no useful index for a nested-loop-with-index strategy, and both inputs lack pre-existing sort order suiting a merge join:

1. **Optimizer** estimates `customers` is smaller (via catalog statistics, Module 11 §11.5) and designates it the **build side**.
2. **Executor**, at the **build phase** (blocking, Module 8 §8.2): scans `customers` (via Seq Scan or Index Scan, whichever the optimizer chose for that leg), and builds an **in-memory hash table** keyed on `customer_id`, bounded by `work_mem`/`join_buffer_size` (Module 7, §7.2).
   - If `customers` doesn't fit in that memory budget, the build **spills to disk** via hash partitioning (Module 7, §7.5) — the classic case where you'd see evidence of this in `EXPLAIN ANALYZE`/slow-query-log output.
3. **Probe phase** (pipelining once build completes): the `orders` side is scanned (with its own `Filter: order_date > '2026-01-01'` applied first, ideally via an index on `order_date` if selective enough), and each qualifying row is hash-probed against the in-memory `customers` hash table.
4. Matching pairs are emitted upward, projected to `order_id, name`.

**Where Buffer Manager, MVCC visibility, and WAL all still apply:** Every page touched on either side of the join still goes through the Buffer Manager (Module 6) with MVCC visibility checks per tuple (Module 5) — a `JOIN`, at its core, is just two (or more) scans feeding into a join operator; nothing about the underlying page/tuple access mechanics changes.

### 14.7 Case Study: Aggregation

```sql
SELECT department, COUNT(*), AVG(salary)
FROM employees
GROUP BY department;
```

**Trace, assuming a Hash Aggregate** (Module 8, §8.6) is chosen (no useful pre-sorted index on `department`):
1. **Executor** scans `employees` (Seq Scan or Index Scan), each row flowing into the aggregate operator.
2. A hash table keyed on `department` is built/updated incrementally as rows arrive — for each incoming row, the corresponding group's running `COUNT` and running sum-for-`AVG` (numerator, plus a separate running count for the denominator) are updated in place.
3. This is **blocking**: no output group can be finalized and emitted until the entire input has been consumed, since any row could still update any group's running total.
4. Once input is exhausted, each group's final `AVG` is computed (sum ÷ count) and all groups are emitted.
5. If the number of distinct `department` values (and thus hash table entries) is very large, this can exceed `work_mem`, triggering a **spill** (Module 7, §7.5) — partitioning groups across temporary files.

**Alternative — if an index on `department` already provides sorted order:** a **Sort-based (Group) Aggregate** (Module 8, §8.6) could instead be used, computing each group's aggregate as soon as its contiguous run of sorted rows ends, needing memory for only the *current* group rather than all groups simultaneously — a trade-off the optimizer weighs against the cost of the sort itself if no such ordering already exists.

### 14.8 Case Study: Complete End-to-End — A Multi-Statement Transaction

Bringing everything together — a realistic multi-statement transaction, traced completely:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
COMMIT;
```

1. `BEGIN`: **Transaction Manager** starts a new transaction context; XID/TRX_ID assigned (Module 5, §5.2). Isolation level determines snapshot timing (Module 5, §5.7) — under `READ COMMITTED`, each statement below gets its *own* fresh snapshot; under `REPEATABLE READ`, one snapshot covers the whole transaction.
2. First `UPDATE`: full update trace as in §14.4 — WAL/Redo record, MVCC version creation (new tuple in Postgres / in-place + undo record in InnoDB), row-level **lock acquired** (Module 1, §1.4.7) on `account_id=1`'s row, held until commit.
3. Second `UPDATE`: same trace, lock acquired on `account_id=2`'s row. *(If another concurrent transaction were simultaneously trying to update `account_id=2` and had already locked it, this statement would **block** here until that other transaction commits/rolls back and releases its lock — Module 1, §1.4.7's Lock Manager in action.)*
4. `COMMIT`: **Transaction Manager** writes a commit WAL/Redo record; **Recovery Manager** ensures it's durably flushed (`fsync`, subject to `synchronous_commit`/`innodb_flush_log_at_trx_commit` settings, Modules 3, 4); **Lock Manager** releases both row locks; success returned to the client.
5. Later: dirtied pages flushed by background writer/page cleaner, eventually checkpoint-bounded (Module 6, §6.6-6.7); old row versions from both updates eventually reclaimed by VACUUM/Purge (Module 5, §5.6).

**Why this example matters:** It demonstrates that a "transaction" isn't a separate mechanism bolted onto individual statement execution — it's the same per-statement machinery (locking, WAL, MVCC) simply spanning multiple statements under one shared XID/TRX_ID and one commit/rollback boundary.

### 14.10 Advantages, Disadvantages, Best Practices (of Thinking in Traces)

**Advantages of the "complete trace" mental model:**
- Converts abstract knowledge of individual components into a concrete, testable understanding of how they cooperate
- Directly mirrors how `EXPLAIN`/`EXPLAIN ANALYZE` output should be read — each plan node corresponds to a step in one of these traces

**Disadvantages / limits:**
- Real production plans are often more complex (multiple joins, subqueries, CTEs, parallel workers) than these simplified traces — the traces here are templates to extend, not exhaustive coverage of every possible plan shape
- Precise internal mechanics can vary meaningfully across major versions of either engine — always verify specifics against current documentation for production decision-making, not just this handbook's snapshot

**Best practices:**
- When preparing for interviews, practice producing these traces **out loud, from memory**, for both engines, without looking at notes — the fluency of the delivery matters as much as the content's correctness
- When debugging a real production query, use `EXPLAIN ANALYZE` (or `EXPLAIN` in MySQL) output as a scaffold, and mentally fill in the underlying mechanism at each node using these traces as a reference

**Common mistakes:**
- Reciting facts about individual components in isolation, without being able to connect them into a coherent sequence — interviewers specifically probe for this connective fluency, not just component-level trivia
- Forgetting to mention the **background/eventual** consequences of an operation (VACUUM/Purge cleanup, Background Writer/Page Cleaner flush, Checkpoint) — a complete trace includes what happens *after* the client gets its response, not just up to that point

### 14.11 Chapter Summary

- Every SQL operation — `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `JOIN`, aggregation — follows the same underlying skeleton from Module 1 (Parse → Optimize → Execute, with Buffer Manager, Lock Manager, MVCC, and WAL/Redo Log all engaged as appropriate), specialized by the specific mechanisms covered in Modules 2–13.
- The **`UPDATE`/`DELETE` comparison** between Postgres's in-heap MVCC versioning and InnoDB's undo-log-based versioning (§14.4, §14.5) is the single highest-value trace to have fully memorized and fluently reproducible.
- A complete trace includes not just the synchronous, client-visible steps, but also the **eventual background consequences** — dirty page flushing, checkpointing, and dead-version garbage collection — which is often what a strong interview answer is specifically checking for.
- Multi-statement transactions (§14.8) use the exact same per-statement mechanisms (locking, WAL, MVCC) as single-statement operations, simply scoped to a shared transaction boundary.

### 14.12 Cheat Sheet

```
UNIVERSAL SKELETON (every operation):
  Parse → Analyze (Catalog) → Optimize (stats) → Lock/Snapshot → Execute
    → Buffer Manager (± disk I/O) → [MVCC visibility check, if reading]
    → WAL/Redo record (± Undo record, if writing) → Commit (flush + unlock)
    → [LATER] background flush → checkpoint → VACUUM/Purge cleanup

UPDATE — the #1 comparative trace:
  PostgreSQL: old xmax set + NEW tuple inserted elsewhere/same page (HOT if lucky)
              → old version cleaned by VACUUM later
  InnoDB:     row updated IN PLACE in clustered index + undo record captures old value
              → old version cleaned by PURGE later

DELETE = versioning operation, NOT physical erasure, in BOTH engines
  (xmax set / delete-mark flag) → physical removal deferred to VACUUM/Purge

JOIN/AGGREGATE: still just scans + Buffer Manager + MVCC underneath,
                 wrapped in Hash/Merge/Sort/Nested-Loop operator logic (Module 8)
```
