# Part 6: Transactions & Concurrency Control

## Module 3: Transaction Schedules

> In Module 2 we learned Isolation is one of the four ACID guarantees. But *how* do we formally reason about whether a particular interleaving of concurrent transactions is "safe"? The answer is the concept of a **schedule** — a precise, formal way to describe the order in which operations from multiple transactions actually execute. This module builds the vocabulary and classification system we'll use for the rest of Part 6, especially Module 4 (Serializability).

---

### 3.1 What Is a Schedule?

**Definition:** A **schedule** is a chronological sequence (an ordering) of the read/write operations from one or more transactions, as they are actually executed by the database system.

Formally, if T1 has operations `R1(A), W1(A)` and T2 has operations `R2(A), W2(A)`, a schedule `S` is any valid interleaving of these operations that preserves the *internal* order of each transaction (i.e., T1's operations must appear in T1's own order relative to each other; same for T2).

**Why does it exist?**
The database engine runs many transactions concurrently for performance (to use CPU/disk in parallel and reduce waiting), but this concurrency means operations from different transactions can interleave in almost any order. We need a formal notation to:
1. Describe *exactly* what happened (or could happen).
2. Reason mathematically about whether that interleaving is "equivalent to some safe, non-interleaved execution."

**Notation used throughout this module:**

- `R_i(X)` = Transaction i reads data item X
- `W_i(X)` = Transaction i writes data item X
- `C_i` = Transaction i commits
- `A_i` = Transaction i aborts

**Practical example:**

```
S1: R1(A)  W1(A)  R2(A)  W2(A)  C1  C2
```

This reads as: T1 reads A, T1 writes A, T2 reads A, T2 writes A, T1 commits, T2 commits.

**Real-world analogy:**
Think of a schedule like the **minute-by-minute security camera log** of two bank tellers (T1, T2) both working on the same drawer of cash at overlapping times. The schedule is simply the literal, observed order of "teller 1 opened drawer," "teller 2 counted cash," "teller 1 closed drawer," etc. — it doesn't judge whether that sequence was *safe*; it just records what happened. Judging safety is what Module 4 (Serializability) does.

---

### 3.2 Serial Schedule

**Definition:** A **serial schedule** is one in which transactions execute **one completely after another**, with absolutely no interleaving of operations between them.

```
Serial Schedule (T1 then T2):
T1: R1(A) W1(A) C1
T2:                R2(A) W2(A) C2

Timeline:
|--------- T1 ---------||--------- T2 ---------|
R1(A)  W1(A)  C1        R2(A)  W2(A)  C2
```

**Why it matters:** A serial schedule is, by definition, always **correct** — because each transaction sees a database state exactly as if it were the only one running. There is zero possibility of interference. The problem is that serial execution gives up all concurrency, and thus all the performance benefits of running transactions in parallel.

**The central goal of concurrency control** (the entire rest of this Part) is: *allow transactions to interleave for performance, but only in ways that produce a result equivalent to some serial schedule.* That equivalence concept is exactly what Serializability (Module 4) formalizes.

**Disadvantage:** Serial schedules underutilize hardware — while T1 is waiting on a disk read, T2 could be doing useful CPU work, but a serial schedule forbids that entirely.

---

### 3.3 Non-Serial Schedule

**Definition:** A **non-serial schedule** is any schedule where operations from different transactions are interleaved.

```
Non-Serial Schedule:
T1: R1(A)         W1(A)              C1
T2:       R2(A)          W2(A)  C2

Timeline:
R1(A)  R2(A)  W1(A)  W2(A)  C1  C2
```

Non-serial schedules are what actually happen in any real concurrent database system. The question the rest of this module (and Module 4) answers is: **which non-serial schedules are "safe" (equivalent to some serial schedule), and which are not?**

---

### 3.4 Read/Write Operations & Conflict Basics

Before classifying schedules, we need to know when two operations **conflict**. Two operations conflict if **all** of the following are true:
1. They belong to **different transactions**.
2. They operate on the **same data item**.
3. **At least one of them is a write.**

| Operation Pair | Conflict? | Why |
|---|---|---|
| R1(A), R2(A) | No | Both are reads — reading doesn't change anything, so order doesn't matter |
| R1(A), W2(A) | Yes | A read and a write on the same item — order affects what's read |
| W1(A), R2(A) | Yes | Same reasoning, reversed |
| W1(A), W2(A) | Yes | Two writes to the same item — order determines the final value |
| R1(A), W2(B) | No | Different data items — no interaction at all |

This conflict definition is the foundation for **Conflict Serializability**, covered fully in Module 4.

---

### 3.5 Blind Writes

**Definition:** A **blind write** is a write operation on a data item performed by a transaction **without that transaction having read the item first** in the same transaction.

```
T1: W1(A)     -- T1 never read A before writing it — this is a blind write
```

**Why it matters:** Blind writes are important for a subtle reason: two schedules can be **conflict-equivalent or not** depending on whether they contain blind writes, and blind writes are precisely the case where **View Serializability** (Module 4) can classify a schedule as "safe" even though **Conflict Serializability** would reject it. This distinction is a classic GATE/exam trick topic.

**Example:**

```
S: W1(A)  W2(A)  W1(B)  ...
```

Both W1(A) and W2(A) are blind writes if neither T1 nor T2 read A beforehand. We revisit this exact scenario in Module 4 (View Serializability section) with a full worked example showing why blind writes matter.

---

### 3.6 Recoverable Schedule

**Definition:** A schedule is **recoverable** if, for every pair of transactions Ti and Tj where Tj reads a data item previously written by Ti, **Tj's commit occurs after Ti's commit** (i.e., Tj does not commit before the transaction whose data it depended on has itself committed).

**Why it exists / what problem it solves:**
If Tj commits *before* Ti (the transaction it read dirty data from), and Ti later **aborts**, there is no way to fix Tj's already-committed result — because commits are permanent (Durability, Module 2). Tj's result depended on data that turned out to never actually exist in the final database. This is an unrecoverable situation — the database cannot undo a commit.

**Example — a Recoverable schedule:**

```
T1: R1(A)  W1(A)                    C1
T2:              R2(A)  W2(A)              C2

Order: R1(A) W1(A) R2(A) W2(A) C1 C2
```

Here, T2 reads a value written by T1, but T2's commit (`C2`) happens *after* T1's commit (`C1`) — this is recoverable. If T1 had aborted instead of committing, T2 (still uncommitted at that point) could also be aborted safely.

**Example — an Irrecoverable schedule (see 3.9):**

```
Order: R1(A) W1(A) R2(A) W2(A) C2 C1
                                 ↑ T2 commits BEFORE T1!
```

If T1 later aborts, T2 has already committed based on a value that no longer "officially" existed — this cannot be fixed. This is called **irrecoverable** — it must be prevented by the concurrency control system.

---

### 3.7 Cascadeless Schedule (Avoids Cascading Aborts)

**Definition:** A schedule is **cascadeless** (also called "avoiding cascading rollback") if every transaction only reads values that were written by transactions that have **already committed** — i.e., no transaction reads *uncommitted* (dirty) data from another transaction at all.

**Why it exists:** Even in a recoverable schedule, if T2 reads T1's *uncommitted* write, and T1 later aborts, then T2 must **also** be aborted (since its read was based on a value that never really existed) — and if some T3 read from T2, T3 must abort too. This chain reaction is called a **cascading rollback**, and it can be expensive and complex to manage. Cascadeless schedules eliminate this problem entirely by forbidding dirty reads outright.

**Example — a Cascading Rollback scenario (recoverable, but NOT cascadeless):**

```
T1: R1(A)  W1(A)                     A1 (abort!)
T2:              R2(A)  W2(A)  C2

Order: R1(A) W1(A) R2(A) W2(A) C2 A1
```

T2 read T1's uncommitted write to A. When T1 aborts, T2's read was based on data that no longer exists — T2 must be aborted too, even though T2 already thought it was done (but crucially, T2 had **not yet committed** in this scenario — if it had, we'd be in the irrecoverable case from 3.6). This forced rollback of T2 because of T1's abort is the "cascade."

**Example — a Cascadeless schedule (safe):**

```
T1: R1(A)  W1(A)  C1
T2:                    R2(A)  W2(A)  C2
```

T2 only reads A *after* T1 has committed — no cascading is possible, because T1 can no longer abort at that point.

**Relationship between these classes:**

```
                Irrecoverable
                     ⊂
                Recoverable
                     ⊂
             Cascadeless (Avoids Cascading Abort)
                     ⊂
                Strict
                     ⊂
                  Serial
```

(Read as: Serial ⊆ Strict ⊆ Cascadeless ⊆ Recoverable ⊆ All Schedules; irrecoverable schedules fall entirely outside the recoverable set.)

---

### 3.8 Strict Schedule

**Definition:** A schedule is **strict** if a transaction can neither **read nor write** a data item until the transaction that last wrote that item has either **committed or aborted**.

This is a stronger condition than cascadeless — cascadeless only forbids *dirty reads*; strict schedules forbid *both dirty reads AND dirty writes* (writing over a value written by an as-yet-uncommitted transaction).

**Why it exists:** Strict schedules make **recovery trivially simple** — because you know that any value currently in the database that hasn't been committed can simply be overwritten with its "before image" on rollback, without worrying about any other transaction having read or written it in the meantime. This is why most real production databases (via their locking protocols — Module 7's **Strict 2PL**) implement strictness in practice, not just cascadelessness.

**Example — Strict schedule:**

```
T1: W1(A)                C1
T2:            (must wait until C1 to touch A)  R2(A)  W2(A)  C2
```

**Industry relevance:** Strict Two-Phase Locking (Strict 2PL), which we cover fully in Module 7, is the mechanism virtually every commercial database uses to *guarantee* strict schedules by holding all locks until commit/abort.

---

### 3.9 Irrecoverable Schedule

**Definition:** A schedule is **irrecoverable** if it violates the recoverability condition from Section 3.6 — that is, some transaction Tj reads a value written by Ti and Tj **commits before Ti commits (or while Ti is still uncommitted, and Ti later aborts)**.

**Why it's dangerous:** As explained in 3.6, this makes rollback impossible once discovered — you cannot "un-commit" Tj. Database systems must **never allow** irrecoverable schedules to occur; this is a hard, non-negotiable requirement, unlike cascadelessness/strictness which are more about efficiency and simplicity of recovery.

**Example (repeated for clarity):**

```
Order: R1(A) W1(A) R2(A) W2(A) C2 C1
```

T2 commits before T1. If T1 now aborts, T2's committed result is based on a value (T1's write to A) that officially never happened. **This schedule must never be permitted by any correct database engine.**

```
        │  │  │  │   ┌───────────────────┐   │   │   │   │
        │  │  │  │   │      SERIAL        │   │   │   │   │
        │  │  │  │   └───────────────────┘   │   │   │   │
        │  │  │  └───────────────────────────┘   │   │   │
        │  │  └─────────────────────────────────┘   │   │
        │  └───────────────────────────────────────┘   │

```

This nested-circle diagram is one of the single most commonly reproduced diagrams in GATE and university DBMS exams — memorize the nesting order: **Serial ⊂ Strict ⊂ Cascadeless ⊂ Recoverable**.

### 3.11 Schedule Analysis — Full Worked Example

Let's classify the following schedule:

```
S: R1(A)  R2(A)  W1(A)  R1(B)  W2(A)  W1(B)  C1  C2
```

**Step 1 — Is it recoverable?**
Does any transaction read a value written by another transaction? T2 reads A at the start (`R2(A)`) — but at that point, T1 hasn't written A yet (`W1(A)` happens after `R2(A)`), so T2's read isn't dependent on T1's write here. Checking the full schedule: no transaction reads a value that another *specific* transaction wrote before it committed. So this schedule is trivially recoverable (no read-from dependency to violate).

**Step 2 — Is it cascadeless?**
Same reasoning — since there's no dirty read dependency at all in this particular schedule, it's cascadeless by default.

**Step 3 — Is it strict?**
Check if any transaction writes to a data item that was previously written by an uncommitted transaction. `W2(A)` occurs after `W1(A)`, and T1 has **not yet committed** at that point (`C1` comes later) — T2 is writing over T1's uncommitted write to A. This **violates strictness** (a "dirty write"). So: **Recoverable ✔, Cascadeless ✔ (trivially), NOT Strict ✘**.

This example demonstrates why you must check conditions layer by layer, and why a schedule can be recoverable and cascadeless (in the absence of dependency) while still failing strictness due to write-write conflicts on uncommitted data.

### 3.12 Advantages, Disadvantages, Best Practices

**Why these classifications matter in practice:**
- Real databases don't explicitly "check" whether a schedule is recoverable/cascadeless/strict at runtime by analyzing operation sequences — instead, they use **concurrency control protocols** (locking, MVCC) that are *designed* to only ever produce schedules within the desired class (usually strict schedules, via Strict 2PL).
- Understanding these classes helps you reason about **why** certain protocols exist and what guarantees they provide.

**Common Mistakes:**
- Confusing "recoverable" with "correct" — a schedule can be recoverable but still **not serializable** (i.e., producing a logically wrong result even though it's technically safe to roll back). Recoverability is about *safety of rollback*, not about *correctness of the final answer* — that's what Serializability (Module 4) addresses.
- Forgetting that irrecoverable schedules are not just "bad practice" — they are **schedules that must never be allowed to occur** by a correct DBMS.

**Performance implications:**
- Strict schedules (via Strict 2PL) are simplest to recover but can reduce concurrency, since locks are held until commit/abort.
- Cascadeless-but-not-strict schedules allow slightly more concurrency (dirty writes aren't blocked, only dirty reads) but are rarely used in mainstream commercial engines because dirty writes create their own subtle correctness issues.

**Industry usage:** Virtually all mainstream RDBMS engines (PostgreSQL, InnoDB, Oracle, SQL Server) are engineered to only ever produce **strict** schedules by default under their standard concurrency control protocols — this is precisely why Strict 2PL (Module 7) and MVCC-based strict-write conflict detection (Module 10) are so central to their designs.

### 3.13 Chapter Summary

- A **schedule** is the actual (or hypothetical) interleaved order of transaction operations.
- **Serial schedules** run transactions one at a time — always correct, but no concurrency benefit.
- **Non-serial schedules** interleave operations — need further analysis for safety.
- Two operations **conflict** if they're from different transactions, touch the same item, and at least one is a write.
- **Blind writes** are writes without a preceding read in the same transaction — relevant to View Serializability (Module 4).
- **Recoverable**: no transaction commits before a transaction it read dirty data from.
- **Cascadeless**: no transaction ever reads uncommitted (dirty) data at all.
- **Strict**: no transaction reads OR writes a data item until the last writer has committed/aborted.
- **Irrecoverable**: violates the recoverable condition — must never be allowed.
- Nesting: **Serial ⊂ Strict ⊂ Cascadeless ⊂ Recoverable ⊂ All Schedules**.

### 3.14 Revision Notes / Cheat Sheet

| Class | Rule | Real DB uses this? |
|---|---|---|
| Serial | No interleaving at all | Only as a theoretical baseline |
| Recoverable | Reader commits after the writer it depended on | Bare minimum requirement |
| Cascadeless | No dirty reads allowed at all | Common goal |
| Strict | No dirty reads AND no dirty writes | **Standard in production DBs** (via Strict 2PL / MVCC) |
| Irrecoverable | Violates recoverability | **Forbidden — never allowed** |

### 3.17 GATE-Style Questions

**Q1.** Consider schedule `S: R1(A) W1(A) R2(A) W2(A) C1 C2`. Classify it (recoverable / cascadeless / strict).
<details><summary>Answer</summary>Recoverable (T2 reads A after T1's write, and T2 commits after T1 commits) — but NOT cascadeless, because T2 read A while T1 was still uncommitted at the time of the read (R2(A) happens before C1). It is therefore also NOT strict.</details>

**Q2.** Consider `S: W1(A) W2(A) C2 C1`. Is this schedule recoverable?
<details><summary>Answer</summary>There's no read-from dependency here (no transaction *reads* a value written by the other), so the recoverability condition is trivially satisfied — it is recoverable. However, note it violates strictness, since W2(A) overwrites T1's uncommitted write — a dirty write.</details>
