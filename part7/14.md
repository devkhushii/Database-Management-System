## 14.1 B+ Tree Interview Questions (Full Reference: Module 6)

**Q1. Why do databases use B+ Trees instead of plain B-Trees?**
> Model Answer: B+ Trees store data only at leaf nodes, letting internal nodes hold more keys (pure signposts) per page — this gives higher fan-out, a shorter/flatter tree, and fewer disk reads per search. Additionally, B+ Tree leaves are linked together, making range scans and full sorted traversal extremely efficient, which plain B-Trees don't support as cleanly.

**Q2. What determines a B+ Tree's fan-out, and why does it matter?**
> Model Answer: Fan-out is the number of children per internal node, driven by how many (key, pointer) pairs fit in one page — determined by page size divided by key+pointer size. Higher fan-out means a shorter tree (lower height), and since height directly equals the number of disk I/Os per search, higher fan-out means faster queries. Realistic fan-outs (hundreds per node) keep even billion-row tables at 3–4 levels.

**Q3. Walk through what happens when a B+ Tree leaf overflows during insertion.**
> Model Answer: The leaf splits into two, dividing its keys roughly in half. The first key of the new right leaf is copied (not moved — it stays in the leaf too) up to the parent as a new signpost. If the parent then overflows, it also splits, but this time the promoted key is moved (removed from the node) up, since internal nodes are pure signposts. If the root itself splits, a new root is created and tree height increases by exactly one.

**Q4. Walk through what happens when a B+ Tree leaf underflows during deletion.**
> Model Answer: First, check if an immediate sibling has more than the minimum required keys — if so, redistribute (borrow one key from the sibling), updating the parent's signpost. If no sibling has spare keys, merge the underflowing node with a sibling, removing the corresponding signpost from the parent. This can cascade upward; if the root ends up with only one child, that child becomes the new root and height decreases by one.

**Q5. Given an 8 KB page, 8-byte keys, and 8-byte pointers, estimate the height needed for 1 billion rows.**
> Worked Solution: Fan-out ≈ 8192 / 16 ≈ 512. log₅₁₂(1,000,000,000) ≈ ln(1e9)/ln(512) ≈ 20.7/6.24 ≈ 3.3 → height ≈ 4 levels (rounding up). **Answer: approximately 4 levels.**

## 14.2 Hash Index Interview Questions (Full Reference: Module 7)

**Q1. When would you choose a hash index over a B+ Tree?**
> Model Answer: Only when the workload is guaranteed to be pure equality lookups with no range queries or sorting ever needed — hash indexes give O(1) average lookup versus a B+ Tree's O(log n), but provide zero support for ranges/sorting since the hash function deliberately destroys key ordering. In practice this exact guarantee is rare, which is why B+ Trees remain the default in almost every production RDBMS.

**Q2. Explain extendible hashing's directory-doubling rule.**
> Model Answer: Each bucket has a local depth (bits used to determine its membership); the directory has a global depth (bits used to index into it, directory size = 2^global_depth). If an overflowing bucket's local depth equals the current global depth, the directory must double (global depth +1) before the bucket can split, because there aren't enough distinct directory entries yet to point to two separate buckets at that prefix length. If local depth is already less than global depth, the bucket can split without any directory change.

**Q3. Why might a bucket in linear hashing have a long overflow chain even though buckets are actively splitting elsewhere in the table?**
> Model Answer: Linear hashing splits buckets in a fixed round-robin order via a split pointer — not necessarily the bucket that most needs it. A bucket that overflows before its scheduled turn simply gets a temporary overflow chain and must wait until the split pointer reaches it.

**Q4. What is InnoDB's Adaptive Hash Index, and why is it "adaptive"?**
> Model Answer: It's an automatic, in-memory-only hash structure InnoDB builds over frequently-accessed portions of existing B+ Tree indexes, letting hot equality lookups bypass full tree traversal. It's "adaptive" because InnoDB decides which pages to accelerate based on observed real-time access patterns, not a fixed, user-specified column.

## 14.3 Clustered vs Non-Clustered Index (Full Reference: Modules 3, 5, 9)

**Q1. Can a table have more than one clustered index? Why or why not?**
> Model Answer: No — a clustered index determines the physical storage order of rows, and rows can only be physically ordered one way at a time. Any additional indexes on that table must be non-clustered.

**Q2. Is PostgreSQL's primary key a clustered index?**
> Model Answer: Not in the persistent, automatically-maintained sense. PostgreSQL tables are heap-organized by default; the `CLUSTER` command can physically reorder a table to match an index once, but subsequent writes revert to unordered heap placement. This contrasts with InnoDB, where every table is mandatorily and continuously clustered on its primary key.

**Q3. Why does InnoDB's secondary index lookup require two B+ Tree traversals?**
> Model Answer: Because InnoDB's actual row data lives in the primary key's clustered B+ Tree leaves, a raw physical page/slot pointer would go stale every time a page split relocates rows. So secondary indexes instead store the primary key value (which never changes) — meaning a secondary index lookup must first traverse the secondary index to get the primary key value, then traverse the primary (clustered) index to get the actual row: two traversals total.

## 14.4 Composite Index Interview Questions (Full Reference: Modules 5, 8, 10)

**Q1. State the leftmost prefix rule and give an example of a query that CANNOT use a composite index efficiently.**
> Model Answer: A composite index on `(a, b, c)` can efficiently support queries filtering on `a` alone, `a AND b`, or `a AND b AND c` — but NOT a query filtering only on `b` or only on `c`, since the index is physically sorted by `a` first, making it impossible to binary-search/traverse efficiently while skipping the leading column.

**Q2. How should you order columns in a composite index?**
> Model Answer: Generally, place equality-filtered columns before range-filtered or sort columns — this maximizes how much of the index's sorted structure remains useful after the equality columns narrow the search.

**Q3. What is a descending index, and when is it needed?**
> Model Answer: A composite index where one or more columns are explicitly stored in descending order, needed when a query's `ORDER BY` mixes directions (e.g., `ORDER BY created_at DESC, id ASC`) — a single index can't satisfy a mixed-direction sort by scanning forward or backward as a whole unless it was built with the matching per-column directions explicitly.

## 14.5 Covering Index Interview Questions (Full Reference: Modules 5, 9, 10)

**Q1. What is a covering index, and what execution strategy does it enable?**
> Model Answer: An index that contains every column a query needs (filter, select, sort columns) so the query can be answered entirely from the index without touching the underlying table — this enables an Index-Only Scan.

**Q2. Why might a covering index NOT fully avoid a heap fetch in PostgreSQL?**
> Model Answer: PostgreSQL must still confirm each candidate row's MVCC visibility to the current transaction's snapshot. This check is skipped only if the Visibility Map confirms the relevant page is "all-visible" (no dead/uncommitted tuples needing per-row checking). If the Visibility Map isn't up to date (e.g., due to insufficient VACUUM activity), PostgreSQL falls back to a regular Index Scan with heap fetches despite having a technically covering index.

## 14.6 Storage Engine Interview Questions (Full Reference: Module 9)

**Q1. Explain PostgreSQL's HOT update optimization.**
> Model Answer: If an UPDATE doesn't change any indexed column's value AND the new tuple version fits on the same page as the old one, PostgreSQL can skip updating any index entirely — the new version is linked via an in-page "HOT chain" from the old tuple's location, and existing index entries (pointing at the original ctid) can still find the current version by following that chain.

**Q2. What is InnoDB's Change Buffer, and why can't it be used for unique indexes?**
> Model Answer: The Change Buffer defers writes to secondary index pages that aren't currently cached, batching the change in memory (redo-logged for durability) until the page is naturally loaded for some other reason. It can't be used for unique indexes because uniqueness must be verified immediately against the actual current data — deferring that check risks silently allowing a duplicate.

**Q3. Why does VACUUM (without FULL) not shrink a PostgreSQL table's file size?**
> Model Answer: Plain VACUUM reclaims dead tuple space for reuse WITHIN the existing file (updating the Free Space Map), but doesn't physically rewrite/compact the file — the freed space becomes available for future inserts but isn't returned to the OS. VACUUM FULL physically rewrites the entire table into a new, compact file, actually shrinking disk usage, but requires an exclusive lock.

## 14.7 Whiteboard Problems

**Problem 1: Draw a B+ Tree, order 4, after inserting keys 10, 20, 30, 40, 50, 60, 70 one at a time.**
> Approach: Insert 10, 20, 30 into a single node (fits, max 3 keys). Insert 40 → overflow → split: root becomes `[30]`, children `[10|20]` and `[30|40]`. Insert 50 → goes into `[30|40]`, becomes `[30|40|50]` (fits). Insert 60 → `[30|40|50]` overflows → split: promote 50 up. Root becomes `[30|50]`, children `[10|20]`, `[30|40]`, `[50|60]`. Insert 70 → goes into `[50|60]` → becomes `[50|60|70]` (fits). **Final: Root `[30|50]`, leaves `[10|20]`, `[30|40]`, `[50|60|70]`.**

**Problem 2: Simulate LRU (4 frames) on reference string: 7,0,1,2,0,3,0,4,2,3,0,3,2 and count faults.**
> Approach: Track 4 frames, evicting least-recently-used on a miss.
> 7(miss,[7]) 0(miss,[7,0]) 1(miss,[7,0,1]) 2(miss,[7,0,1,2]) 0(hit,[7,1,2,0]) 3(miss,evict 7,[1,2,0,3]) 0(hit,[1,2,3,0]) 4(miss,evict 1,[2,3,0,4]) 2(hit,[3,0,4,2]) 3(hit,[0,4,2,3]) 0(hit,[4,2,3,0]) 3(hit,[4,2,0,3]) 2(hit,[4,0,3,2])
> **Total faults: 6** (7,0,1,2,3,4 each caused one miss; all subsequent references were hits).

**Problem 3: Explain, end to end, the physical journey of `SELECT * FROM orders WHERE id = 5` on an indexed InnoDB table.**
> Approach (talk through out loud): Parser/planner identifies an available index on `id` (likely the clustered primary key itself if `id` is the PK) → since `id` IS the clustering key, this is a single B+ Tree traversal directly to the leaf containing the full row data → no secondary lookup needed. Contrast this explicitly with a query filtering on a *secondary*-indexed column, which would require the double lookup (Section 14.3, Q3).

## 14.8 Performance Tuning Scenarios

**Scenario 1: A query using an existing index suddenly starts doing a sequential scan after a bulk data load.**
> Diagnosis path: (1) Check statistics freshness — a bulk load likely changed the data distribution significantly; run `ANALYZE`. (2) Re-check the query plan. **Root cause is almost always stale statistics (Module 10/11).**

**Scenario 2: Insert throughput on a table has degraded significantly over the past few months with no schema changes.**
> Diagnosis path: (1) Check for index bloat (Module 11/12) — likely caused by sustained high-frequency updates to indexed columns. (2) Check whether the primary key is monotonic or random (Module 3/6/9) — a random-order PK on a clustered table causes expensive page splits scattered throughout the tree rather than clean append-only growth. (3) Check autovacuum health (Module 11) — if disabled or under-tuned, bloat accumulates unchecked.

**Scenario 3: A covering index exists for a query, but EXPLAIN shows a regular Index Scan (with heap fetches) instead of an Index-Only Scan.**
> Diagnosis path: Check the table's Visibility Map coverage (Module 9/10) — if VACUUM hasn't run recently enough, many pages aren't marked all-visible, forcing PostgreSQL to fall back to heap fetches for the MVCC visibility check despite the index technically covering the query.

**Scenario 4: A write-heavy table with 10 indexes is experiencing severe latency spikes during checkpoint operations.**
> Diagnosis path: This connects Module 4 (dirty pages, checkpoints) and Module 12 (write amplification) — 10 indexes means every write touches up to 11 structures (heap + 10 indexes), producing a large volume of dirty pages that then get flushed in bursts during checkpoints. Recommend: audit whether all 10 indexes are actually necessary (Module 12's Step 1), and tune checkpoint/background-writer aggressiveness to smooth out the I/O burst (Module 4).

## 14.9 GATE-Style Numerical Questions — Fully Worked

**Q1. A disk has average seek time 5 ms, rotational latency 4 ms, transfer rate 40 MB/s. Calculate time to read a 4 KB block.**
> Worked Solution:
> Transfer time = 4 KB / 40 MB/s = (4/1024) MB / 40 MB/s = 0.0000977 s ≈ 0.0977 ms
> Total time = seek time + rotational latency + transfer time = 5 + 4 + 0.0977 ≈ **9.1 ms**

**Q2. A B+ Tree has order 5 (max 4 keys/node). Height = 3, maximum fan-out utilization at every level. Calculate maximum keys.**
> Worked Solution:
> Order 5 → max 5 children per internal node, max 4 keys per node.
> At height 3 (root, one internal level, leaf level — 3 levels total), maximum number of leaves = 5² = 25 (root has up to 5 children, each of those has up to 5 children = leaves).
> Maximum keys = 25 leaves × 4 keys/leaf = **100 keys** (this is a simplified estimate assuming a specific height-counting convention; always clarify with the interviewer whether "height 3" counts the root level, and adjust the exponent accordingly).

**Q3. Extendible hashing: global depth = 3 (directory size 8). A bucket at local depth 3 overflows. What's the new directory size?**
> Worked Solution: Since local depth (3) equals global depth (3), the directory must double: new global depth = 4, new directory size = 2⁴ = **16 entries.**

**Q4. A composite index is on 3 columns (a, b, c). A query filters only on b and c (skipping a). Can it use the full index traversal efficiently?**
> Worked Solution: **No.** The leftmost prefix rule requires column `a` to be part of the filter for the index's sorted structure to be searchable via traversal. Skipping `a` means the index cannot be used for an efficient B+ Tree descent on this query (though some engines might still perform a full index scan as an alternative to a full table scan, if the index is narrower than the full row — but this is not the same as efficient prefix-matched traversal).

**Q5. A table has 1,000,000 rows and a column with 500 distinct, uniformly-distributed values. Estimate the selectivity and matching row count for an equality predicate.**
> Worked Solution: Selectivity ≈ 1/500 = 0.002 (0.2%). Matching rows ≈ 1,000,000 × 0.002 = **2,000 rows.**

## 14.10 Consolidated Quick-Reference — "If Asked This, Say This"

| Question Pattern | One-Sentence Answer |
|---|---|
| Why B+ Tree over B-Tree? | Higher fan-out (data only at leaves) + linked leaves for fast range scans |
| Why does InnoDB do a double lookup? | Secondary indexes store the primary key value, not a raw RID, because InnoDB's data lives in the clustered PK tree |
| Why avoid random UUID primary keys in InnoDB? | Random insert order scatters writes across the clustered B+ Tree, causing frequent, expensive page splits |
| Why doesn't PostgreSQL have a true clustered index? | Tables are heap-organized by default; `CLUSTER` is a one-time, non-persistent reordering |
| Why use a hash index over B+ Tree? | Only for pure equality-only workloads — B+ Trees are the safer default since they also handle ranges/sorting |
| Why might my index not be used? | Check: selectivity, stale statistics, functional mismatch, leftmost prefix violation, table too small |
| Why is VACUUM needed in PostgreSQL? | MVCC never overwrites rows in place; dead tuple versions accumulate and must be reclaimed |
| Why does BRIN work well for logs? | Append-only data is naturally physically correlated with time, letting tiny per-page-range summaries suffice |
| Why can too many indexes hurt performance? | Every index adds a physical write to every INSERT/UPDATE/DELETE — this is write amplification |
| Why does a covering index sometimes still hit the heap in PostgreSQL? | The Visibility Map must confirm the page is all-visible, or PostgreSQL falls back to a heap fetch for MVCC visibility checking |
