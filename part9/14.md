## 14.1 WAL Interview Questions

### Q1. What is Write-Ahead Logging, and why does it exist?
**Model Answer:** WAL requires that a log record describing a change be durably written before the corresponding data page change is made durable on disk. It exists because data pages live in volatile memory before being lazily flushed to disk for performance, so a cheap, sequential log write is used to guarantee durability and atomicity without requiring expensive, synchronous full-page writes on every change.

### Q2. What are the two WAL rules, and which ACID properties do they protect?
**Model Answer:** The Undo Rule (before-images must be logged before a dirty page is flushed) protects Atomicity. The Redo Rule (a transaction's commit record must be flushed before acknowledging commit) protects Durability.

### Q3. Walk through exactly what happens when a client issues COMMIT.
**Model Answer:** A commit log record is appended to the log buffer; the log buffer is force-flushed to durable storage up to and including that commit record; only after the flush is confirmed does the DBMS acknowledge "commit successful" to the client; the actual data pages are flushed lazily, later, independent of this sequence.

### Q4. Why is Group Commit an important optimization?
**Model Answer:** Because the disk flush operation has a largely fixed cost regardless of how much data it writes, batching multiple transactions' commit flushes into one physical I/O operation amortizes that fixed cost across many transactions, dramatically improving throughput under concurrent workloads — though it provides minimal benefit for low-concurrency, serial workloads.

### Q5. What is a torn page, and how do different engines defend against it?
**Model Answer:** A torn page occurs when a crash happens mid-write, leaving a data page partially updated — part old content, part new, potentially garbage. PostgreSQL defends against this with Full Page Writes (logging the entire page after each checkpoint's first modification); InnoDB uses a Doublewrite Buffer (writing pages to a staging area before their final location, enabling repair from an intact copy).

## 14.2 ARIES Questions

### Q1. Name and briefly describe ARIES's three phases.
**Model Answer:** Analysis (forward scan from the last checkpoint, rebuilding the Transaction Table and Dirty Page Table, identifying winners/losers), Redo (forward scan from the smallest RecLSN, reapplying every logged change — "repeating history" — using PageLSN checks to skip already-durable changes), and Undo (backward scan through losing transactions' PrevLSN chains, reversing their changes and writing CLRs).

### Q2. Why does ARIES redo the actions of transactions that will later be undone?
**Model Answer:** This is the "repeat history" principle — it's simpler and more robust to first reconstruct the exact physical state that existed at crash time (including in-progress, uncommitted work), and then cleanly undo the losers using the normal, well-defined undo logic. Trying to skip redoing changes that will later be undone introduces fragile special-casing.

### Q3. What is physiological logging, and why does ARIES use it?
**Model Answer:** It's a hybrid between physical logging (byte-level, page-specific) and logical logging (higher-level operation descriptions). ARIES logs are physical to a specific page (enabling fast, unambiguous redo via PageLSN comparison) but logical in describing the operation within that page (allowing flexibility in internal page layout).

### Q4. Explain how CLRs make the Undo phase idempotent.
**Model Answer:** When Undo reverses a change, it writes a Compensation Log Record documenting that the undo occurred, including an UndoNextLSN field pointing to what should be undone next. If the system crashes again mid-undo, the next Analysis phase sees these CLRs and correctly skips already-completed undo work, never double-undoing or corrupting data.

### Q5. What's the role of RecLSN in the Dirty Page Table, and how does it optimize Redo?
**Model Answer:** RecLSN records the LSN of the log record that first made a page dirty — the earliest point at which that page's on-disk copy could be stale. Redo starts scanning from the smallest RecLSN across all dirty pages, rather than the beginning of the log, and uses each page's RecLSN plus its actual on-disk PageLSN to skip redoing changes that are already reflected on disk.

## 14.3 Checkpoint Questions

### Q1. Why can't recovery just scan the entire log from the very beginning every time?
**Model Answer:** For a long-running, active database, this would make recovery time grow unboundedly with the database's age and activity — directly violating the "minimize recovery time" recovery goal. Checkpoints provide a periodic "resume point" so recovery only needs to scan from the last checkpoint forward.

### Q2. What's the difference between a sharp and a fuzzy checkpoint?
**Model Answer:** A sharp checkpoint pauses all transaction activity and flushes every dirty page before resuming — simple, but causes a visible service disruption, making it unsuitable for production OLTP. A fuzzy checkpoint captures a snapshot of the Transaction Table and Dirty Page Table without pausing anything, at the cost of requiring more sophisticated recovery logic (which ARIES's Analysis phase provides).

### Q3. How does recovery quickly find the most recent checkpoint without scanning the whole log?
**Model Answer:** A small, fixed, well-known on-disk location (e.g., PostgreSQL's pg_control file) is updated at the end of every completed checkpoint to point to that checkpoint's LSN, giving recovery an O(1) way to jump directly to the correct starting point.

### Q4. What's the trade-off in choosing checkpoint frequency?
**Model Answer:** More frequent checkpoints reduce recovery time and log retention needs but add more I/O overhead during normal operation; less frequent checkpoints reduce that overhead but increase recovery time and log volume that must be retained.

## 14.4 Undo/Redo Questions

### Q1. What's the fundamental difference between pure Undo Logging and pure Redo Logging?
**Model Answer:** Undo Logging requires all of a transaction's dirty pages to be flushed to disk before commit (FORCE) — recovery then only ever needs undo. Redo Logging forbids flushing any uncommitted transaction's dirty pages to disk at all (NO-STEAL) — recovery then only ever needs redo. They impose opposite constraints on buffer management timing.

### Q2. Why do virtually all production databases use Undo/Redo Logging instead of either pure technique?
**Model Answer:** Undo/Redo Logging removes both constraints, allowing dirty pages to be flushed to disk at any time (STEAL + NO-FORCE) — giving the buffer manager maximum flexibility for memory management and giving commits maximum performance (no forced synchronous data flush). This flexibility is what makes it the industry standard, at the cost of requiring both undo and redo logic during recovery — a cost ARIES is specifically engineered to handle efficiently.

### Q3. What buffer policy does STEAL + NO-FORCE require in terms of recovery logic?
**Model Answer:** Both undo (because STEAL allows uncommitted changes to reach disk early) and redo (because NO-FORCE allows committed changes to remain un-flushed at commit time) are required during recovery.

## 14.5 Recovery Algorithm Questions

### Q1. Design, from memory, a complete recovery workflow from crash to consistent database.
**Model Answer:** (1) System restarts and detects an abnormal previous shutdown. (2) Analysis phase scans forward from the last checkpoint, rebuilding the Transaction and Dirty Page Tables. (3) Redo phase scans forward from the smallest RecLSN, reapplying all logged changes using PageLSN checks. (4) Undo phase scans backward through losing transactions' chains, reversing changes and writing CLRs. (5) Database is now consistent; normal operation resumes.

### Q2. What makes a recovery algorithm idempotent, and why does that property matter?
**Model Answer:** Idempotency means the algorithm produces the same correct result even if interrupted and restarted any number of times — critical because a crash could occur *during* recovery itself. ARIES achieves this primarily through CLRs, which record undo actions so they're never mistakenly repeated on a subsequent recovery attempt.

## 14.6 Backup Strategy Questions

### Q1. Compare Full, Incremental, and Differential backups.
**Model Answer:** Full backups capture everything, are simplest to restore (single self-contained file) but largest/slowest to create. Incremental backups capture only changes since the last backup of any kind — fastest/smallest to create, but restore requires the entire dependency chain (full plus every subsequent incremental, in order), making them fragile to any missing link. Differential backups capture changes since the last full backup — restore only ever needs two files (full plus latest differential), a good middle ground, though each differential grows larger over time.

### Q2. What is PITR, and what specific failure category is it uniquely suited for?
**Model Answer:** Point-in-Time Recovery restores a database to any specific moment by combining a base backup with replayed archived logs up to that exact point. It's uniquely suited for Human Error — a committed but mistaken operation (like an accidental DROP TABLE) is durably, correctly logged by ordinary crash recovery, which would faithfully redo it, not undo it. PITR lets you replay logs only up to the moment just before the mistake.

### Q3. Why is backup verification non-negotiable?
**Model Answer:** Backups can silently fail for many reasons (corruption, incomplete jobs, tool bugs, misconfiguration) without any visible symptom until an actual restore is attempted. A backup that has never been successfully restored in a test should not be trusted as a reliable recovery option.

## 14.7 Whiteboard Scenarios

### Scenario 1: "Our database took 45 minutes to recover after a crash. Diagnose and fix."
**Approach:** Check checkpoint frequency and the time elapsed since the last checkpoint before the crash (Module 6/12) — a long gap means a large log-replay window. Check for long-running transactions that might have prevented checkpoint progress or extended the Undo phase. Check log storage speed (recovery is largely sequential I/O-bound). Propose: more frequent checkpoints (weighed against live overhead), faster log storage, and investigation/mitigation of any abnormally long-running transactions.

### Scenario 2: "A junior engineer wants to disable fsync-on-commit to improve write throughput. Evaluate this."
**Approach:** Explain that this relaxes or eliminates the Redo Rule (Module 4) — a crash could then lose committed transactions the client was told succeeded, directly violating Durability. Frame this as an explicit RPO decision (Module 10) that must be consciously accepted by the business, not silently defaulted into for a performance win. Suggest Group Commit tuning as a durability-preserving alternative to explore first.

### Scenario 3: "Design the recovery strategy for [industry X]." (Use Module 13's framework)
**Approach:** Always start with RPO/RTO (Module 10) — ask or state what data loss and downtime are actually tolerable, and why, given the business context. Then select: durability setting (Module 4), buffer policy (Module 8, almost always STEAL+NO-FORCE unless there's an unusual constraint), checkpoint frequency (Module 6/12), backup strategy and type (Module 9), and HA/DR architecture (Module 10) — justifying each choice against the stated RPO/RTO, not defaulting to "maximum safety everywhere."

### Scenario 4: "Explain why redo happens for transactions that get undone anyway — isn't that wasteful?"
**Approach:** Acknowledge the apparent waste, then explain the "repeat history" principle (Module 7): reconstructing exact crash-time physical state first, then cleanly undoing losers via well-defined logic, is simpler and more robust than trying to cleverly skip redundant work — avoiding exactly the kind of special-casing that makes recovery algorithms fragile and bug-prone.

## 14.8 Production Incident Discussions

### Incident Type 1: Disk Full Due to Unbounded WAL/Redo Log Growth
**Root Cause Pattern:** Often caused by a stuck replication slot (PostgreSQL, Module 11), a long-running/idle transaction preventing checkpoint progress (Module 6), or archiving falling behind due to network/storage issues (Module 9/12).
**Discussion Points:** How would you detect this proactively (monitoring log growth rate, replication slot lag)? How would you resolve it safely in the moment (without losing data)? What structural changes would prevent recurrence?

### Incident Type 2: Accidental Production Data Deletion
**Root Cause Pattern:** Human error (Module 2, Section 2.9) — often a script run against the wrong environment, or a missing WHERE clause.
**Discussion Points:** Walk through the exact PITR steps (Module 9) to recover. Discuss preventative measures (access controls, staging/production separation, confirmation prompts) as the real long-term fix, since recovery is a safety net, not a substitute for prevention.

### Incident Type 3: Split-Brain After a Network Partition
**Root Cause Pattern:** An automated failover system incorrectly determines the primary has failed during a network partition, promoting a standby while the original primary is actually still healthy and accepting writes (Module 10, Section 10.15).
**Discussion Points:** How do you detect and resolve the split-brain (reconciling divergent writes, choosing which side "wins")? What quorum/consensus mechanisms (previewed for Part 10) could prevent this?

### Incident Type 4: Backup Restore Failure During an Actual Disaster
**Root Cause Pattern:** An unverified backup (Module 9, Section 9.9) turns out to be corrupted or incomplete exactly when it's needed most.
**Discussion Points:** What immediate options remain (older backup, replica promotion if available)? What process failure allowed this to go undetected, and how would you build mandatory verification into the backup pipeline going forward?

## 14.11 Best Practices for the Interview Itself

- **Always state assumptions explicitly** in open-ended design questions ("I'll assume this system needs an RPO of roughly X, given Y — let me know if that's off") — this demonstrates the RPO/RTO-first thinking emphasized throughout Module 10 and Module 13.
- **Draw diagrams** even in a verbal/whiteboard interview — the WAL timeline, the checkpoint recovery-window diagram, and the STEAL/FORCE 2x2 grid from this handbook are all excellent, fast-to-draw visual aids that demonstrate structured thinking.
- **Connect concepts across modules** — the strongest answers explicitly link, e.g., "this is exactly the STEAL+NO-FORCE trade-off, which is why ARIES needs both redo and undo" — showing you understand the *system*, not just isolated facts.

## 14.12 Common Interview Mistakes to Avoid

- Confusing RPO and RTO (Module 10) — a very frequent, easily avoidable error.
- Claiming ARIES's Redo phase only applies to committed transactions — a classic, high-visibility mistake that immediately signals shallow understanding.
- Giving a "maximum safety, no trade-offs" answer to every design question — real senior answers always articulate the trade-off being made and why it's appropriate for the stated context.
