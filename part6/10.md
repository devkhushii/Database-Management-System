# Part 6: Transactions & Concurrency Control

## Module 10: Multi-Version Concurrency Control (MVCC)

> We've now seen three philosophies: locking (block), timestamp ordering (abort eagerly), and OCC (abort late, at validation). **MVCC** introduces a fourth, radically different idea: instead of forcing readers and writers to coordinate over a *single* copy of the data, **keep multiple versions of each row** so that readers almost never have to wait for writers at all. MVCC is the dominant mechanism behind PostgreSQL, InnoDB (MySQL), and Oracle's read consistency — understanding it deeply is essential for any modern backend/database interview.

---

### 10.1 What Is MVCC?

**Definition:** **Multi-Version Concurrency Control (MVCC)** is a concurrency control mechanism in which, instead of updating a row "in place" (overwriting the old value), a **write creates a new version** of the row, while the **old version is retained** — tagged with information about which transactions can "see" it. Readers are then given a **consistent snapshot** of the database as of a specific point in time, and they read whichever version of each row was valid at that snapshot, without ever needing to acquire a lock or block a concurrent writer.

**Core principle:** *"Readers never block writers, and writers never block readers."* (Writers can still block other *writers* — write-write conflicts are still resolved via locking or validation, covered in 10.10.)

---

### 10.2 Why MVCC? What Problem Does It Solve?

Under pure locking (Module 6–7), a reader wanting a Shared lock must wait if a writer holds an Exclusive lock on the same row — even though the reader might be perfectly happy reading the *old*, still-valid-as-of-a-moment-ago value instead of waiting for the writer to finish. In read-heavy systems (the vast majority of real-world OLTP and web application workloads), this reader-blocked-by-writer behavior is a major performance bottleneck.

**MVCC's insight:** If we keep the **old version** of a row around even after it's been updated, readers who started before the update can just keep reading that old version — completely unaffected by the concurrent write, with **zero waiting**.

**Real-world analogy:**
Think of MVCC like a **published book with multiple editions**. If you're partway through reading the 3rd edition of a book, and a new 4th edition gets published while you're still reading, you don't have to stop reading or somehow have pages ripped out from under you — you simply keep reading your copy of the 3rd edition to the end. Meanwhile, new readers who pick up the book *after* the 4th edition is published get the new edition instead. Everyone reads a **consistent, complete** version, and no one has to wait for anyone else.

---

### 10.3 Version Chains

**Definition:** For each row, the database maintains a **version chain** — a linked sequence of versions of that row over time, each tagged with metadata identifying which transaction created it and (often) which transaction, if any, superseded it.

**Conceptual structure (simplified, PostgreSQL-style):**

```
Row with id=42, version chain over time:

┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ Version 1        │     │ Version 2        │     │ Version 3        │
│ balance = 1000    │────►│ balance = 900     │────►│ balance = 850     │  (latest / "head")
│ xmin = T1 (created)│     │ xmin = T5         │     │ xmin = T9         │
│ xmax = T5 (deleted)│     │ xmax = T9         │     │ xmax = (none)     │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

- **`xmin`**: the ID of the transaction that **created** this version (via `INSERT` or `UPDATE`).
- **`xmax`**: the ID of the transaction that **deleted/superseded** this version (via `UPDATE` or `DELETE`) — empty/null if this version is still the current one.

An `UPDATE` in MVCC is conceptually implemented as: **create a new version with the updated values (setting its `xmin` to the updating transaction), and set the old version's `xmax`** to that same transaction — logically "closing off" the old version's validity range while opening the new one's.

---

### 10.4 Visibility Rules

**Definition:** **Visibility rules** determine, given a specific transaction's snapshot, **which version** of a row that transaction is allowed to see.

**Simplified general visibility rule:** A version of a row is visible to a transaction T if:
1. `xmin` (the version's creator) **has committed**, and committed **before** T's snapshot was taken (or `xmin` = T itself, seeing its own uncommitted write).
2. `xmax` (the version's "closer," if any) is **either empty, OR belongs to a transaction that has NOT committed as of T's snapshot** (i.e., the version hasn't *really* been superseded yet, from T's point of view).

**Worked example:**

```
T1 (xmin=T1, committed at time 5) inserts row R with balance=1000.
T2 (xmin=T2) begins at time 10, reads R → sees balance=1000 (T1 committed before T2's snapshot).
T2 updates R: creates new version with balance=900, xmin=T2, sets old version's xmax=T2. (T2 has NOT committed yet.)

T3 begins at time 12 (before T2 commits):
  - Checks OLD version (balance=1000): xmin=T1 (committed, visible) ✔;
    xmax=T2, but T2 has NOT committed as of T3's snapshot → OLD version still counts as valid! VISIBLE.
  - Checks NEW version (balance=900): xmin=T2, but T2 has NOT committed → NOT VISIBLE to T3.
  → T3 sees balance = 1000 (the OLD version) — completely unaffected by T2's in-progress update. No blocking!

T2 now COMMITS at time 15.

T4 begins at time 20 (after T2 committed):
  - OLD version (1000): xmax=T2, and T2 HAS committed by T4's snapshot → OLD version is no longer valid. NOT VISIBLE.
  - NEW version (900): xmin=T2, committed before T4's snapshot → VISIBLE.
  → T4 sees balance = 900.
```

This trace is the single most important mental model to internalize for MVCC — practice reasoning through it until it's automatic.

---

### 10.5 Snapshot Isolation

**Definition:** **Snapshot Isolation (SI)** is the isolation level naturally provided by MVCC: a transaction sees a **consistent snapshot** of the database as it existed at the moment the transaction began (or, in some implementations, at the moment of its first statement) — and this snapshot never changes for the duration of the transaction, no matter what other transactions commit in the meantime.

**Key guarantees of Snapshot Isolation:**
- Prevents **Dirty Reads** (Module 5.3) — trivially, since uncommitted versions are never visible.
- Prevents **Non-Repeatable Reads** (Module 5.5) — the snapshot is fixed, so re-reading the same row within the transaction always returns the same version.
- Prevents most forms of **Phantom Reads** (Module 5.6) in practice, since new rows inserted by other committed transactions after the snapshot was taken aren't visible either.
- Prevents **Incorrect Summary / Read Skew** (Module 5.7/5.9) — the whole snapshot is internally consistent.

**Critical limitation — Snapshot Isolation does NOT prevent Write Skew** (Module 5.8): as established in Module 5, two transactions can each read a consistent snapshot, each independently decide (based on that snapshot) that their intended write is safe, and both commit successfully because their writes touch **different** rows — even though the combined effect violates an invariant. **This is why "Snapshot Isolation" and "Serializable" are NOT the same thing**, despite Snapshot Isolation preventing every *other* classic anomaly. We revisit this precise distinction in Module 11's isolation level breakdown.

### 10.6 Write Conflicts Under MVCC

**Question:** if readers never block on writers, what happens when **two transactions try to write to the same row concurrently**?

**Answer:** MVCC still needs write-write conflict detection — this is where MVCC borrows ideas from locking and/or OCC-style validation:

**First-committer-wins rule (the standard approach, used by PostgreSQL and InnoDB):**
- When a transaction T attempts to update a row, it checks if the row's current version was modified by **another transaction that committed after T's snapshot began**.
- If yes → T's write is rejected, and T typically receives a **serialization failure error** (must retry) or, in some engines, T simply waits for the other transaction to finish and then re-checks.
- If no → T's write proceeds, creating a new version.

**Example:**

```
T1 begins, reads balance=1000.
T2 begins, reads balance=1000.
T1 updates balance to 900, COMMITS.
T2 attempts to update balance to 800 based on its (now stale) read of 1000.
  → T2's write conflicts with T1's already-committed write to the same row.
  → T2 is ABORTED with a serialization failure (PostgreSQL: "could not serialize access due to concurrent update").
  → Application must retry T2.
```

This is conceptually very similar to OCC's validation-phase write-write check (Module 9) — MVCC's write-conflict detection is, in a real sense, a form of optimistic concurrency control specifically for the **write** path, layered on top of the purely non-blocking **read** path.

**Database-specific behavior:**
- **PostgreSQL:** Under `REPEATABLE READ`/`SERIALIZABLE`, a concurrent update to a row already updated by a committed transaction causes an immediate serialization error. Under `READ COMMITTED` (the default), PostgreSQL instead **re-reads the latest committed version and retries the update** against it automatically (no error raised to the application) — an important, frequently-tested behavioral nuance.
- **InnoDB (MySQL):** Similar first-committer-wins logic under its default `REPEATABLE READ`, combined with actual row-level **locking** for writes (InnoDB is a hybrid: MVCC for reads, real locks for writes) — meaning a second writer to the same row under InnoDB typically **waits** (lock-based) rather than immediately erroring out, and only fails if a deadlock or lock-wait-timeout occurs.

---

### 10.7 Undo Records

**Definition:** In many MVCC implementations (notably **Oracle** and **InnoDB**), rather than keeping full old *row versions* directly in the table's storage, the engine keeps the row updated **in place** and instead writes an **undo record** (or "rollback segment" entry in Oracle terminology) describing how to reconstruct the *previous* version of the row, should some other transaction's snapshot require seeing it.

**Why this matters:** This is a key architectural difference from PostgreSQL's approach (Section 10.9):
- **InnoDB/Oracle style:** the "current" table data always reflects the latest version; older versions are reconstructed **on demand** by applying undo records in reverse when an older-snapshot transaction needs to see them.
- **PostgreSQL style:** old versions are kept **directly** in the table's heap storage itself (no separate undo log needed for MVCC purposes) — old row versions simply accumulate as "dead tuples" until cleaned up.

Both achieve the same visibility semantics from the application's point of view, but the storage-level mechanics — and consequently, the cleanup/maintenance story — differ significantly.

---

### 10.8 Vacuum (Overview — PostgreSQL-specific)

**Definition:** Because PostgreSQL's MVCC approach leaves old, no-longer-visible-to-anyone row versions ("dead tuples") physically sitting in the table's storage, PostgreSQL requires a background maintenance process called **VACUUM** to periodically scan tables and **reclaim the space** used by dead tuples that are no longer visible to *any* active transaction's snapshot.

**Why it's necessary:** Without vacuuming, a table's physical storage would grow indefinitely as updates/deletes keep leaving old versions behind — this is often called **"table bloat."** Vacuum also updates internal statistics used by the query planner and, critically, prevents **transaction ID wraparound** (a serious failure mode where PostgreSQL's internal 32-bit transaction counter could wrap around and cause old committed data to appear as if it were "in the future" and invisible — an advanced topic, but worth knowing this is *why* vacuum is non-optional in PostgreSQL).

**Interview-relevant point:** A very common real-world PostgreSQL production issue is **"vacuum falling behind"** — often caused by a long-running transaction holding an old snapshot open, which prevents vacuum from cleaning up any dead tuple that might still be visible to that old snapshot, no matter how old it is. This directly ties back to Module 1's "keep transactions short" best practice — a single idle, forgotten open transaction can cause severe table bloat and performance degradation cluster-wide. Full internals of vacuum and storage are covered in Part 7.

### 10.9 PostgreSQL MVCC — Summary of Mechanics

- Old row versions stored **directly in the table heap** (as "dead tuples") alongside live ones.
- Each tuple has `xmin`/`xmax` system columns (visible via `SELECT xmin, xmax, * FROM table` for debugging).
- No separate "undo log" for MVCC purposes — cleanup handled by **VACUUM**.
- Default isolation level: `READ COMMITTED` (a fresh snapshot is taken for **each statement**, not for the whole transaction).
- Under `REPEATABLE READ`, one snapshot is taken for the **entire transaction** at its first statement.

---

### 10.10 InnoDB MVCC — Summary of Mechanics

- Rows updated **in place**; old versions reconstructed on-demand via the **undo log / rollback segment**.
- Each row has hidden system columns (`DB_TRX_ID`, `DB_ROLL_PTR`) pointing to the transaction that last modified it and to the relevant undo log entry, respectively.
- Default isolation level: `REPEATABLE READ` — notably **stricter than PostgreSQL's default**, a frequently-tested fact.
- InnoDB additionally uses **gap locks** and **next-key locking** under `REPEATABLE READ` to prevent most phantom-read scenarios at the storage engine level — a genuinely distinctive InnoDB behavior compared to pure MVCC-only phantom prevention.
- Writers still use actual row-level **locks** (hybrid MVCC + locking model) rather than pure OCC-style validation for write-write conflicts.

---

### 10.11 Read Consistency — Comparison Table

| Aspect | PostgreSQL | InnoDB (MySQL) | Oracle |
|---|---|---|---|
| Old version storage | In table heap (dead tuples) | Reconstructed via undo log | Reconstructed via undo/rollback segments |
| Cleanup mechanism | VACUUM (manual/auto) | Automatic purge of undo log | Automatic purge of undo segments |
| Default isolation | READ COMMITTED | REPEATABLE READ | READ COMMITTED (effectively) |
| Snapshot granularity (default) | Per-statement | Per-transaction | Per-statement |
| Phantom protection at REPEATABLE READ | Not fully (needs SERIALIZABLE) | Largely yes (gap/next-key locks) | N/A (doesn't use this level by that name) |
| Write conflict handling | Serialization error (strict levels) or auto-retry (READ COMMITTED) | Row-level locking (waits) | Row-level locking (waits) |

### 10.12 Advantages, Disadvantages, Best Practices

**Advantages of MVCC:**
- Readers never block writers, writers never block readers — dramatically improves concurrency for read-heavy workloads (the vast majority of real applications).
- Naturally provides Snapshot Isolation, preventing most classic anomalies "for free."
- Simplifies long-running analytical/reporting queries — they get a consistent view without needing to hold locks across their entire (potentially long) execution.

**Disadvantages:**
- Storage/cleanup overhead — old versions must be tracked and eventually cleaned up (Vacuum in PostgreSQL, undo log purge in InnoDB/Oracle).
- Does NOT prevent write skew by default — a true `SERIALIZABLE` guarantee requires additional mechanisms (e.g., PostgreSQL's Serializable Snapshot Isolation, which tracks read/write dependencies beyond simple version visibility).
- Long-running transactions can cause severe bloat/performance issues by preventing cleanup of old versions still technically "visible" to them (PostgreSQL vacuum issue, Section 10.8).
- Write-write conflicts still require some form of resolution (locking or validation) — MVCC solves the read/write blocking problem, not the write/write conflict problem.

**Best Practices:**
- Keep transactions short, especially in PostgreSQL, to avoid holding old snapshots open and blocking vacuum cleanup.
- Understand your specific engine's default isolation level and snapshot granularity — don't assume all MVCC databases behave identically (PostgreSQL's per-statement default snapshot under READ COMMITTED vs. InnoDB's per-transaction default under REPEATABLE READ is a critical, frequently-misunderstood distinction).
- For invariants spanning multiple rows, don't rely on Snapshot Isolation alone — use explicit locking (`SELECT ... FOR UPDATE`) or a true serializable isolation level to prevent write skew.

**Common Mistakes:**
- Assuming "MVCC" automatically means "fully serializable" — a very common and dangerous misconception (directly tied to write skew, Module 5.8).
- Not monitoring for long-running/idle-in-transaction sessions in PostgreSQL, leading to unexpected table bloat.
- Assuming InnoDB and PostgreSQL have identical default isolation behavior — they don't (REPEATABLE READ vs. READ COMMITTED defaults).

**Performance Implications:** MVCC shifts the cost from "readers waiting on writers" to "storage and cleanup overhead for old versions" — an excellent trade for most OLTP/web workloads, but it introduces its own operational considerations (vacuum tuning, undo log sizing) covered further in Module 16 and Part 7.

**Industry Usage:** MVCC (in some form) is the concurrency control backbone of PostgreSQL, MySQL/InnoDB, Oracle, SQL Server's optional snapshot isolation mode, and virtually every modern high-throughput OLTP system — understanding it deeply is essential for any serious backend or database engineering interview.

### 10.13 Chapter Summary

- **MVCC** keeps multiple versions of each row so **readers never block writers and writers never block readers**.
- **Version chains** track each version's creator (`xmin`) and superseder (`xmax`).
- **Visibility rules** determine which version a transaction's snapshot can see, based on commit status and timing relative to the snapshot.
- **Snapshot Isolation** is the natural isolation level MVCC provides — prevents dirty reads, non-repeatable reads, most phantoms, and read skew — but **NOT write skew**.
- Write-write conflicts are resolved via **first-committer-wins** logic (serialization errors) or actual row locking, depending on the engine.
- **PostgreSQL** stores old versions in the heap directly (cleaned by **VACUUM**); **InnoDB/Oracle** reconstruct old versions from **undo logs**.
- PostgreSQL defaults to `READ COMMITTED` (per-statement snapshot); InnoDB defaults to `REPEATABLE READ` (per-transaction snapshot) — a key, frequently-tested difference.

---

### 10.14 Revision Notes / Cheat Sheet

```
MVCC core rule:  Readers see a consistent snapshot; never blocked by writers.
Version tags:    xmin = creator txn, xmax = superseder txn
Visibility:      xmin committed before my snapshot AND (xmax empty OR xmax not committed before my snapshot)

PostgreSQL: old versions in heap, cleaned by VACUUM, default = READ COMMITTED (per-statement snapshot)
InnoDB:     old versions via undo log,  default = REPEATABLE READ (per-transaction snapshot), gap locks fight phantoms

Snapshot Isolation prevents: dirty read, non-repeatable read, most phantoms, read skew
Snapshot Isolation does NOT prevent: WRITE SKEW  ← classic interview trap
```
