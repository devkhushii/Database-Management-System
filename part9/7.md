# Part 9: Database Recovery, Logging & Durability
## Module 7: ARIES Recovery Algorithm

> **Recap:** This is the module everything else in Part 9 has been building toward. Module 3 gave us log records, LSNs, and CLRs. Module 4 gave us WAL. Module 5 gave us Undo/Redo Logging. Module 6 gave us checkpoints, Transaction Tables, and Dirty Page Tables. **ARIES** (Algorithm for Recovery and Isolation Exploiting Semantics) is the formal, precise, industry-standard algorithm that stitches all of these pieces into one coherent, provably correct recovery procedure. If you understand this module deeply, you understand how PostgreSQL, MySQL, Oracle, and SQL Server actually recover from a crash.

---

## 📍 What ARIES Is and Why It Matters

**ARIES** was developed at IBM in the late 1980s (Mohan et al.) and has since become the de facto blueprint for crash recovery in essentially every serious relational database engine. When PostgreSQL's `StartupXLOG` process runs, or when InnoDB's crash recovery thread kicks in, they are running algorithms that are — in spirit, and often near-literally — ARIES.

Why did ARIES win? Because it elegantly solves the exact problems this handbook has been circling:

- How do you recover efficiently, without scanning the whole log (Module 6's checkpoint problem)?
- How do you recover correctly under STEAL + NO-FORCE (Module 5's most flexible, highest-performance buffer policy)?
- How do you make recovery **idempotent** — safe even if it crashes again, mid-recovery (Module 1 and 3's CLR foreshadowing)?

ARIES answers all three with one unified design.

---

## 7.1 What is ARIES?

### Definition

**ARIES** is a recovery algorithm built around three core phases — **Analysis**, **Redo**, and **Undo** — combined with a specific logging discipline (**physiological logging**, Section 7.2) and specific data structures (the **Dirty Page Table** and **Transaction Table**, introduced in Module 6, formalized fully here).

### Why ARIES? — The Three Guiding Principles

ARIES is built on three foundational design principles, each solving a specific problem we've encountered earlier in this handbook:

1. **Write-Ahead Logging** (Module 4) — every change is logged before it's made durable on disk. ARIES assumes and enforces this rule strictly.
2. **Repeating History During Redo** (Section 7.6) — on restart, ARIES redoes *every* logged action since the relevant point, including those belonging to transactions that will later be undone. This might sound wasteful, but it's actually what makes the algorithm dramatically simpler and more robust — more on this counterintuitive but crucial idea below.
3. **Logging Changes During Undo** (Module 3's CLR concept, formalized fully in Section 7.7) — ensuring recovery is idempotent, safe to interrupt and restart any number of times.

---

## 7.2 Physiological Logging

### What is Physiological Logging?

**Physiological Logging** is ARIES's hybrid approach to what information a log record actually contains, sitting between two extremes:

- **Physical Logging:** Log records describe exact byte-level changes to a specific page (e.g., "bytes 40–48 of page P22 changed from X to Y"). Very precise, but can be verbose and inflexible.
- **Logical Logging:** Log records describe the operation in higher-level terms (e.g., "inserted a row into table Orders"). Compact, but reconstructing the exact resulting state can be ambiguous or expensive, especially under concurrent structural changes.

**Physiological logging** takes the best of both: log records are **physical to a specific page** (they say exactly which page was affected, enabling fast, unambiguous redo) but **logical in their description of the operation within that page** (they don't necessarily record every single byte offset — e.g., "record with key=42 was deleted from this page" rather than raw byte diffs), which allows flexibility in how a page's internal layout is organized while still allowing precise, fast, page-scoped redo.

### Why This Matters

This design choice directly enables ARIES's efficiency: because every log record is tied to exactly one page, the recovery algorithm can use each page's own **PageLSN** (introduced in Module 3, Section 3.3) to instantly determine "has this specific log record's change already been applied to this specific page or not?" — a comparison that drives the entire Redo phase (Section 7.6).

## 7.3 Core Data Structures — Formalized

Module 6 introduced these informally as part of checkpointing. Now we define them precisely, as ARIES uses them.

### Transaction Table (TT)

Tracks every transaction that is currently active (not yet committed or aborted) as of the point being examined.

| Field | Meaning |
|---|---|
| TransID | Transaction identifier |
| Status | Running / Committing / Aborting |
| LastLSN | The LSN of the most recent log record written by this transaction |

### Dirty Page Table (DPT)

Tracks every page that has been modified in the buffer pool but not yet flushed to disk.

| Field | Meaning |
|---|---|
| PageID | Identifier of the dirty page |
| RecLSN | The LSN of the log record that **first** caused this page to become dirty |

> 💡 **Why RecLSN matters so much:** RecLSN represents the earliest point in the log at which this page's on-disk copy could possibly be out of date. This single number is what allows the Redo phase (Section 7.6) to skip huge swaths of the log for pages it already knows are safely up to date.

## 7.4 The Three Phases of ARIES — Overview

```
                    CRASH!  System restarts.

  ┌──────────────────────────────────────────────────────────┐
  │  PHASE 1: ANALYSIS                                          │
  │  Scan forward from the last checkpoint.                      │
  │  Rebuild the Transaction Table and Dirty Page Table            │
  │  as they existed at the moment of the crash.                  │
  │  Determine: which transactions need redo? which need undo?      │
  └──────────────────────────┬───────────────────────────────────┘
                              ▼
  ┌──────────────────────────────────────────────────────────┐
  │  PHASE 2: REDO                                               │
  │  Scan forward from the OLDEST RecLSN in the Dirty Page Table.  │
  │  Reapply EVERY logged change since that point —                │
  │  "repeating history" — regardless of whether the owning          │
  │  transaction ultimately committed or will be undone.             │
  └──────────────────────────┬───────────────────────────────────┘
                              ▼
  ┌──────────────────────────────────────────────────────────┐
  │  PHASE 3: UNDO                                               │
  │  Scan BACKWARD through the log (via PrevLSN chains),          │
  │  undoing every change made by transactions that were NOT       │
  │  committed at crash time. Write CLRs as each undo happens.       │
  └──────────────────────────┬───────────────────────────────────┘
                              ▼
                  Database is now consistent.
                  Normal operation resumes.
```

Each phase reads the log in a different direction and for a different purpose. Let's go through each in careful, standalone detail before assembling the full numeric example.

---

## 7.5 Phase 1: Analysis

### Purpose

The Analysis phase's job is to answer, precisely: *"What was the state of the world at the exact moment of the crash?"* It reconstructs the Transaction Table and Dirty Page Table as they would have looked right before the crash, starting from the last checkpoint (Module 6) rather than the beginning of the log.

### Algorithm

```
1. Start reading the log from the LSN recorded in the most
   recent completed checkpoint (found via the fixed pointer
   location, e.g., PostgreSQL's pg_control — Module 6, Section 6.8).

2. Initialize Transaction Table (TT) and Dirty Page Table (DPT)
   from the checkpoint's saved snapshot.

3. Scan FORWARD through the log from that point to the end
   (where the crash occurred):

   For each log record encountered:
     - If it's an UPDATE record for transaction T:
         → Add/update T in TT (update LastLSN)
         → If the affected page is not already in DPT,
           add it with RecLSN = this record's LSN
     - If it's a COMMIT record for transaction T:
         → Mark T's status as "Committing" (or remove from TT
           if fully completed) in TT
     - If it's an ABORT record for transaction T:
         → Mark T's status as "Aborting" in TT (it still needs
           its undo to complete, if it hadn't already)
     - If it's a CLR (Compensation Log Record):
         → Treat similarly to an update for bookkeeping purposes

4. At the end of this scan, TT contains exactly the transactions
   that were active (neither committed nor fully aborted) at
   crash time — these need UNDO.
   DPT contains exactly the pages that might not be safely on
   disk — these need consideration during REDO.
```

### Output of Analysis

- A finalized **Transaction Table**: the definitive list of "losers" (transactions to undo).
- A finalized **Dirty Page Table**: the starting point (oldest RecLSN) for where Redo must begin scanning.

---

## 7.6 Phase 2: Redo — "Repeat History"

### Purpose

The Redo phase's job is to bring the database's **physical, on-disk state** back to exactly what it was at the instant of the crash — including the effects of transactions that will later be undone in Phase 3.

### The Counterintuitive Idea: Redo Everything, Even Losers

This is the single most commonly misunderstood aspect of ARIES, and a favorite senior-level interview probe:

> **ARIES redoes the actions of transactions that will later be undone.**

Why would you redo something you're about to undo anyway? Because it's **simpler and safer** to first reconstruct the exact physical state that existed at crash time — including all the "in-progress mess" — and *then* cleanly undo the losing transactions using the normal, well-defined undo logic (which itself generates CLRs, Section 7.7). Trying to be "smart" and skip redoing changes that will be undone anyway introduces exactly the kind of special-casing and fragility that makes recovery algorithms buggy. ARIES deliberately avoids that temptation. This principle is called **"Repeating History."**

### Algorithm

```
1. Start reading the log from the SMALLEST RecLSN found in the
   Dirty Page Table (produced by Analysis) — this is provably
   the earliest point any redo could possibly be needed.

2. Scan FORWARD through the log from that point to the end.

3. For each UPDATE (or CLR) record affecting page P:

   a. If P is NOT in the Dirty Page Table → skip (this page was
      never dirty at crash time / already flushed — no redo needed).

   b. If P IS in the Dirty Page Table, but this record's LSN is
      LESS than P's RecLSN → skip (this specific change predates
      when P became dirty in a way that matters — already captured).

   c. Otherwise: fetch page P from disk, check its PageLSN
      (Module 3, Section 3.3).
        - If PageLSN >= this record's LSN → skip (the change is
          ALREADY reflected on disk — don't reapply it, that
          would cause incorrect double-application for
          non-idempotent physical operations).
        - If PageLSN < this record's LSN → REDO: reapply the
          change described in this record to page P, and update
          P's PageLSN to this record's LSN.
```

### Why the PageLSN Check Matters So Much

This check is the crux of ARIES's efficiency and correctness under STEAL + NO-FORCE (Module 5): because pages can be flushed to disk at any arbitrary time, by the time recovery runs, some pages might *already* physically contain a given change (if they happened to be flushed before the crash), while others might not. Blindly reapplying every change to every page regardless of its current state could corrupt pages that are already correct (imagine "redoing" an increment operation on data that was already incremented — you'd double-count). The **PageLSN comparison** is precisely what makes redo safe and idempotent, giving each page the exact right set of changes, no more, no less.

## 7.7 Phase 3: Undo — Rolling Back the Losers

### Purpose

The Undo phase reverses the effects of every transaction that was **not committed** at the time of the crash (the "losers" identified by Analysis) — restoring atomicity.

### Algorithm

```
1. Build a "to-undo" set from the Transaction Table: every
   transaction that was active (Running or Aborting, but not
   Committed) at crash time.

2. For each such transaction, start from its LastLSN and walk
   BACKWARD through the log using PrevLSN pointers (Module 3,
   Section 3.3).

3. For each UPDATE record encountered while walking backward:
   a. Undo the change (apply the before-image).
   b. Write a CLR (Compensation Log Record) describing this
      undo action, including an UndoNextLSN field pointing to
      the LSN that should be undone NEXT for this transaction
      (skipping anything already compensated for).

4. Continue walking backward (via PrevLSN, or UndoNextLSN if
   resuming from a CLR) until reaching that transaction's
   BEGIN record.

5. Write an END record for that transaction — its undo is
   now fully, durably complete.

6. Repeat for all transactions in the to-undo set (this can
   be interleaved across multiple transactions' backward
   chains, not necessarily done one full transaction at a time).
```

### Why CLRs Make This Idempotent (Direct Callback to Module 3)

If the system crashes **again**, mid-undo, the next Analysis phase will find these CLRs already in the log. Because a CLR's `UndoNextLSN` field explicitly tells recovery "the next thing to undo for this transaction is X, not the record right before this CLR," recovery correctly skips over everything already compensated for — never double-undoing, never getting confused. This is precisely the guarantee promised back in Module 3, Section 3.8, now shown as a concrete mechanism within the full algorithm.

## 7.8 Full Numeric Walkthrough — Step by Step

Let's now trace a complete, concrete example from checkpoint through crash through full recovery, using everything defined above.

### Setup: The Log

```
LSN   Record
────  ──────────────────────────────────────────
100   BEGIN_CHECKPOINT
102   END_CHECKPOINT   TT: { T1: LastLSN=98 }
                        DPT: { P1: RecLSN=95 }
105   T1  UPDATE  P1   (before=10, after=20)
110   T2  BEGIN
112   T2  UPDATE  P2   (before=50, after=60)
115   T1  COMMIT
120   T3  BEGIN
122   T3  UPDATE  P1   (before=20, after=30)
125   T2  UPDATE  P3   (before=5,  after=9)
130   T3  UPDATE  P2   (before=60, after=70)
      ────────────  CRASH!  ────────────
```

**Additional facts for this example:**
- Assume, at crash time, only **P3** had actually been flushed to disk (with its PageLSN correctly showing 125). P1 and P2 are still dirty in the (now-lost) buffer pool, meaning their on-disk copies are stale.
- P1's on-disk PageLSN = 95 (its state from before this log excerpt even began — matching the checkpoint's DPT entry).
- P2's on-disk PageLSN = 0 (never yet written — this is P2's very first change).

### Step 1: Analysis Phase

Start at LSN 100 (the checkpoint), initialize TT = `{T1: LastLSN=98}`, DPT = `{P1: RecLSN=95}`, then scan forward:

| LSN | Action | TT after | DPT after |
|---|---|---|---|
| 105 | T1 UPDATE P1 | `{T1: LastLSN=105}` | `{P1: RecLSN=95}` (already present, RecLSN unchanged) |
| 110 | T2 BEGIN | `{T1:105, T2:110}` | `{P1:95}` |
| 112 | T2 UPDATE P2 | `{T1:105, T2:112}` | `{P1:95, P2:RecLSN=112}` |
| 115 | T1 COMMIT | `{T2:112}` (T1 removed — committed) | `{P1:95, P2:112}` |
| 120 | T3 BEGIN | `{T2:112, T3:120}` | `{P1:95, P2:112}` |
| 122 | T3 UPDATE P1 | `{T2:112, T3:122}` | `{P1:95, P2:112}` (P1 already dirty, RecLSN unchanged) |
| 125 | T2 UPDATE P3 | `{T2:125, T3:122}` | `{P1:95, P2:112, P3:RecLSN=125}` |
| 130 | T3 UPDATE P2 | `{T2:125, T3:130}` | `{P1:95, P2:112, P3:125}` (P2 already dirty) |

**Analysis Result:**
- **Final Transaction Table:** `{T2: LastLSN=125, T3: LastLSN=130}` → **T1 is a "winner" (committed) — not here. T2 and T3 are "losers" — need UNDO.**
- **Final Dirty Page Table:** `{P1: RecLSN=95, P2: RecLSN=112, P3: RecLSN=125}` → **Redo must start from LSN 95, the smallest RecLSN.**

### Step 2: Redo Phase

Start scanning from LSN 95 (smallest RecLSN in DPT) forward to the end. For each record, apply the PageLSN check from Section 7.6:

| LSN | Record | In DPT? | LSN vs RecLSN | On-disk PageLSN | Action |
|---|---|---|---|---|---|
| 105 | T1 UPDATE P1 (→20) | Yes (P1, RecLSN=95) | 105 ≥ 95 ✓ | P1's disk PageLSN=95 | 95 < 105 → **REDO**: write 20 to P1, set P1 PageLSN=105 |
| 112 | T2 UPDATE P2 (→60) | Yes (P2, RecLSN=112) | 112 ≥ 112 ✓ | P2's disk PageLSN=0 | 0 < 112 → **REDO**: write 60 to P2, set P2 PageLSN=112 |
| 122 | T3 UPDATE P1 (→30) | Yes (P1) | 122 ≥ 95 ✓ | P1's PageLSN now 105 (just updated above) | 105 < 122 → **REDO**: write 30 to P1, set P1 PageLSN=122 |
| 125 | T2 UPDATE P3 (→9) | Yes (P3, RecLSN=125) | 125 ≥ 125 ✓ | P3's disk PageLSN=125 (recall: P3 was already flushed!) | 125 ≥ 125 → **SKIP** (already reflected on disk — redoing would be redundant/wrong) |
| 130 | T3 UPDATE P2 (→70) | Yes (P2) | 130 ≥ 112 ✓ | P2's PageLSN now 112 (just updated above) | 112 < 130 → **REDO**: write 70 to P2, set P2 PageLSN=130 |

**Redo Result:** P1 = 30, P2 = 70, P3 = 9 — this is exactly the physical state the database had **at the instant of the crash**, including T3's uncommitted change to P1 and P2, and T2's uncommitted change to P2 and P3. Remember: **redo doesn't care who committed — it reconstructs everything, per the "repeat history" principle.**

### Step 3: Undo Phase

From Analysis, the losers are **T2** (LastLSN=125) and **T3** (LastLSN=130). Walk backward via PrevLSN for each, undoing and writing CLRs:

```
Undo T3 (starting at LSN 130):
  LSN 130: T3 UPDATE P2 (before=60, after=70)
     → UNDO: write 60 back to P2
     → Write CLR at (new) LSN 131: "Compensates LSN 130, P2 := 60"
  LSN 122: T3 UPDATE P1 (before=20, after=30)
     → UNDO: write 20 back to P1
     → Write CLR at (new) LSN 132: "Compensates LSN 122, P1 := 20"
  LSN 120: T3 BEGIN → reached start, write LSN 133: "T3 END"

Undo T2 (starting at LSN 125):
  LSN 125: T2 UPDATE P3 (before=5, after=9)
     → UNDO: write 5 back to P3
     → Write CLR at (new) LSN 134: "Compensates LSN 125, P3 := 5"
  LSN 112: T2 UPDATE P2 (before=50, after=60)
     → UNDO: write 50 back to P2
       (Note: P2 is currently 60 after T3's undo above — this
        correctly continues from there, since T2's and T3's
        changes to P2 were sequential in the log, and undo
        respects that same order in reverse)
     → Write CLR at (new) LSN 135: "Compensates LSN 112, P2 := 50"
  LSN 110: T2 BEGIN → reached start, write LSN 136: "T2 END"
```

### Final State After Full Recovery

| Page | Value | Explanation |
|---|---|---|
| P1 | 20 | T1's committed change (20) preserved; T3's uncommitted change (30) undone |
| P2 | 50 | Both T2's (60) and T3's (70) uncommitted changes fully undone, back to original |
| P3 | 5 | T2's uncommitted change (9) undone, back to original |

This final state is **exactly correct**: T1 committed, so its effect (P1=20) survives. T2 and T3 never committed, so all their effects are completely gone. The database is now consistent, and normal operation can resume.

## 7.9 Why This Example Proves ARIES's Core Claims

- **Redo reconstructed crash-time state faithfully**, including uncommitted changes — exactly as the "repeat history" principle promises.
- **The PageLSN check correctly skipped P3's redundant redo** (LSN 125), because it was already durable — demonstrating ARIES's efficiency under STEAL + NO-FORCE, where some pages may already be flushed and others may not.
- **Undo correctly reversed only the losers (T2, T3)**, leaving T1's committed work intact — demonstrating atomicity preservation.
- **CLRs were generated for every undo action** — if a second crash had occurred at, say, LSN 133 (mid-undo), the next Analysis phase would see these CLRs and correctly resume undo from exactly where it left off, never repeating work — demonstrating idempotency.

## 7.10 PostgreSQL vs MySQL (InnoDB) vs Oracle — ARIES Adoption

| Aspect | PostgreSQL | InnoDB (MySQL) | Oracle |
|---|---|---|---|
| ARIES-based? | Yes, WAL replay closely follows ARIES principles | Yes, explicitly documented as ARIES-based | Yes, conceptually equivalent (roll-forward/roll-back) |
| Analysis phase equivalent | Startup process scans from last checkpoint | Recovery reads redo log from checkpoint LSN | SMON reconstructs state from redo/undo |
| Redo phase equivalent | WAL redo (`StartupXLOG`) | Redo log apply | Roll-forward using redo logs |
| Undo phase equivalent | Uses MVCC row versions + WAL, not classic CLR-based undo in the exact same way | Uses Undo Log (Module 5, 11) with rollback segments | Uses Undo Segments with SMON-driven rollback |
| CLR equivalent | Compensating WAL records exist for certain operations | Explicit CLR-like mechanism in the redo log | Similar rollback-tracking mechanism |

> Note: PostgreSQL's approach differs somewhat from textbook ARIES in its handling of undo, because it primarily relies on MVCC (old row versions, covered in Part 6) rather than classic in-place undo — but its Analysis and Redo phases are extremely close to textbook ARIES. This nuance is a great "I actually understand the real systems, not just the textbook" point to raise in a senior interview.

## 7.11 Advantages of ARIES

- **Efficient:** Bounded recovery time via checkpoints (Module 6) and the PageLSN skip-check.
- **Correct under STEAL + NO-FORCE:** Works flawlessly regardless of when dirty pages happen to be flushed — the most flexible, highest-performance buffer policy (Module 5, formalized fully in Module 8).
- **Idempotent:** Safe to interrupt and restart recovery any number of times, thanks to CLRs.
- **Conceptually simple despite power:** The "repeat history, then undo losers" approach avoids fragile special-casing.

## 7.12 Disadvantages / Costs

- **Implementation complexity:** Correctly implementing Analysis, Redo, and Undo with all their bookkeeping (TT, DPT, PrevLSN chains, CLR/UndoNextLSN logic) is genuinely one of the hardest parts of building a database engine.
- **Redo work on losers is "wasted" in one sense:** Time is spent reapplying changes that will immediately be undone — though, as explained, this trade-off buys enormous simplicity and robustness elsewhere.

## 7.13 Best Practices

- When debugging or reasoning about a real production crash-recovery incident, always ask the three ARIES questions in order: *What does Analysis say about active transactions? What does Redo need to reconstruct? What does Undo need to reverse?*
- Understand your specific database engine's documented deviations from textbook ARIES (like PostgreSQL's MVCC-based undo) — this nuance frequently appears in senior interviews and real production debugging.

## 7.14 Common Mistakes

- Believing Redo only applies to committed transactions — as this module's numeric example proves, **Redo applies to everyone**, "repeating history" regardless of eventual commit/abort status.
- Forgetting the PageLSN check and assuming Redo blindly reapplies every log record to every page — this would break idempotency and could corrupt already-current pages.
- Assuming Undo happens strictly one transaction at a time, sequentially — in reality, ARIES interleaves the backward walk across all losing transactions simultaneously, processing whichever has the highest remaining LSN to undo next.

## 7.15 Edge Cases

- A transaction that appears in the checkpoint's Transaction Table but committed *before* the crash (its commit record exists later in the log, before the crash) — correctly removed from TT during Analysis, per the walkthrough's handling of T1's commit at LSN 115.
- A page appearing in the Dirty Page Table that was, in fact, already fully flushed before the crash (like P3 in the example) — correctly and efficiently skipped during Redo via the PageLSN check, avoiding any unnecessary or incorrect work.

---

## 7.16 Chapter Summary

- **ARIES** unifies WAL, Undo/Redo Logging, and checkpointing into one formal, three-phase recovery algorithm: **Analysis, Redo, Undo**.
- **Physiological Logging** gives ARIES page-scoped precision with operation-level flexibility.
- **Analysis** reconstructs the Transaction Table and Dirty Page Table from the last checkpoint forward, identifying winners (committed) and losers (to undo).
- **Redo** "repeats history" — reapplying every logged change since the earliest relevant point, using the PageLSN check to skip already-durable changes, regardless of eventual transaction outcome.
- **Undo** walks backward through losers' PrevLSN chains, reversing their changes and writing CLRs to guarantee idempotency even if recovery itself is interrupted.
- The full numeric walkthrough demonstrated all three phases cooperating to reconstruct an exactly correct final database state.

## 7.17 Cheat Sheet

| Phase | Direction | Starts From | Goal |
|---|---|---|---|
| Analysis | Forward | Last checkpoint | Rebuild TT + DPT, identify winners/losers |
| Redo | Forward | Smallest RecLSN in DPT | Reconstruct exact crash-time physical state (repeat history) |
| Undo | Backward | Each loser's LastLSN, via PrevLSN | Reverse losers' changes, write CLRs |

| Term | One-Line Meaning |
|---|---|
| Physiological Logging | Physical to a page, logical within it |
| PageLSN | LSN of the last change applied to a specific page |
| RecLSN | LSN that first dirtied a page (in DPT) |
| Repeating History | Redo applies to ALL transactions, winners and losers alike |
| UndoNextLSN | In a CLR, points to the next LSN still needing undo |
