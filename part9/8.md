# Part 9: Database Recovery, Logging & Durability
## Module 8: Buffer Recovery

> **Recap:** Modules 5 and 7 kept referencing "STEAL," "NO-STEAL," "FORCE," and "NO-FORCE" as if you already knew what they meant — this was deliberate foreshadowing. Now we formalize that entire framework. This module is shorter than Module 7, but don't mistake that for lower importance: this is the exact axis along which every recovery technique in this handbook can be classified, and it's one of the most reliably asked conceptual frameworks in database interviews.

---

## 📍 The Buffer Manager's Dilemma

Recall the architecture diagram from Module 1: the Recovery Manager and Buffer Manager sit side by side, constantly coordinating. The Buffer Manager's job (fully covered in Part 7 — Storage Engines) is to keep frequently used pages in fast RAM and only write to slow disk when necessary. But this creates two fundamental, unavoidable questions that every DBMS must answer with a definite policy:

1. **Can the buffer manager write a dirty page belonging to an *uncommitted* transaction to disk, if it needs to free up memory?**
2. **Must the buffer manager write *all* of a transaction's dirty pages to disk *before* that transaction is allowed to commit?**

These two questions, and their four possible yes/no combinations, are exactly what this module formalizes.

---

## 8.1 Dirty Pages vs Clean Pages

### What is a Dirty Page?

A **Dirty Page** is a page currently sitting in the buffer pool (RAM) whose contents have been modified by a transaction but **not yet written back to its corresponding location on disk**. The in-memory copy and the on-disk copy are, at this moment, different.

### What is a Clean Page?

A **Clean Page** is a page in the buffer pool whose in-memory contents are **identical** to what's currently on disk — either because it was never modified since being loaded, or because any modifications have already been flushed.

### Why This Distinction Matters for Recovery

This is precisely the concept behind the **Dirty Page Table** you formalized in Module 7 — a page's "dirtiness" status, and the LSN at which it became dirty (RecLSN), is the entire basis on which ARIES's Redo phase decides what work is needed. Dirty pages represent **risk**: if the system crashes before they're flushed, their in-memory changes vanish unless the log can reconstruct them.

```
┌─────────────────────────┐
│      BUFFER POOL (RAM)     │
│                               │
│  Page A: CLEAN (matches disk) │
│  Page B: DIRTY  (modified,     │
│           not yet flushed)      │
│  Page C: CLEAN                  │
│  Page D: DIRTY                    │
└─────────────────────────┘
              │
              ▼  (eventually, lazily)
┌─────────────────────────┐
│         DISK                 │
│  Page A: (same as memory)      │
│  Page B: (STALE — doesn't        │
│           reflect memory yet)     │
│  Page C: (same as memory)          │
│  Page D: (STALE)                     │
└─────────────────────────┘
```

---

## 8.2 Flush Policies — The Two Core Questions, Formalized

### STEAL vs NO-STEAL

**Question:** *Can the buffer manager write ("steal" the frame of) a dirty page belonging to an uncommitted transaction to disk?*

- **STEAL:** Yes — the buffer manager is free to evict any dirty page, flushing it to disk, **regardless of whether the owning transaction has committed yet.** This is necessary when the buffer pool runs low on memory and needs to reclaim space (it "steals" the frame from a still-active transaction's page).
- **NO-STEAL:** No — an uncommitted transaction's dirty pages must remain in the buffer pool (or otherwise be prevented from reaching disk) until that transaction commits. This is precisely the constraint pure Redo Logging imposed back in Module 5, Section 5.3.

### FORCE vs NO-FORCE

**Question:** *Must all of a transaction's dirty pages be written to disk before that transaction is allowed to commit?*

- **FORCE:** Yes — every dirty page touched by a transaction must be flushed to disk as part of the commit process itself, before commit is acknowledged. This is precisely the constraint pure Undo Logging imposed back in Module 5, Section 5.2.
- **NO-FORCE:** No — a transaction can commit even while its dirty pages remain unflushed in the buffer pool; they'll be written to disk later, lazily, at the buffer manager's convenience.

---

## 8.3 The Four Combinations

Combining these two independent yes/no questions produces exactly four possible policies:

```
                        FORCE                          NO-FORCE
              ┌─────────────────────────┬─────────────────────────┐
   STEAL       │  STEAL + FORCE            │  STEAL + NO-FORCE          │
              │  (Rare — pays both costs)  │  (INDUSTRY STANDARD)          │
              ├─────────────────────────┼─────────────────────────┤
   NO-STEAL   │  NO-STEAL + FORCE           │  NO-STEAL + NO-FORCE          │
              │  (Simplest, but most         │  (Pure Redo Logging'style —      │
              │   restrictive — rarely         │   memory-constrained,              │
              │   used in practice)            │   Module 5's Redo Logging)         │
              └─────────────────────────┴─────────────────────────┘
```

Let's examine each quadrant individually, connecting back to Module 5's techniques wherever relevant.

---

## 8.4 STEAL + FORCE

### What It Means

Uncommitted pages **can** be flushed early (STEAL), and **all** of a transaction's dirty pages **must** be flushed before commit (FORCE).

### Recovery Implications

- Because pages can be flushed early (STEAL), some **uncommitted** changes might end up durably on disk → **Undo is needed** during recovery.
- Because everything is forced to disk by commit time (FORCE), **all committed data is guaranteed already on disk** → **Redo is NEVER needed** during recovery.

### Trade-offs

- **Pros:** Recovery is simple — undo only, and there's no need for a Redo phase at all.
- **Cons:** Pays the worst of both worlds performance-wise: no memory flexibility benefit is fully exploited (since FORCE still adds heavy commit latency), and the complexity of dealing with STEAL's undo requirement is still present. This combination is rarely used in practice precisely because it doesn't offer a compelling trade-off compared to the other options.

---

## 8.5 STEAL + NO-FORCE — The Industry Standard

### What It Means

Uncommitted pages **can** be flushed early (STEAL, giving the buffer manager maximum memory flexibility), and a transaction can commit **without** waiting for its dirty pages to be flushed (NO-FORCE, giving maximum commit performance).

### Recovery Implications

- Because pages can be flushed early (STEAL) → uncommitted changes might be on disk → **Undo is needed.**
- Because commit doesn't force a flush (NO-FORCE) → committed changes might NOT yet be on disk → **Redo is needed.**

This is **exactly** the combination that Module 5's **Undo/Redo Logging** technique supports, and precisely what **ARIES** (Module 7) was designed to handle efficiently and correctly.

### Why This Wins in Practice

| Benefit | Explanation |
|---|---|
| Maximum buffer manager flexibility | Never blocked on flushing decisions — can evict any page, anytime, based purely on memory pressure (LRU or similar policies from Part 7) |
| Maximum commit performance | Commit only requires the log flush (Module 4's Commit Protocol) — no data page I/O required synchronously |
| Well-understood recovery cost | ARIES handles the resulting redo/undo requirement efficiently, using checkpoints (Module 6) to bound the work |

### Real-World Usage

**PostgreSQL, InnoDB, Oracle, and SQL Server all use STEAL + NO-FORCE.** This single fact ties together nearly everything covered from Module 4 onward: WAL exists specifically to make STEAL + NO-FORCE safe; Undo/Redo Logging exists specifically because STEAL + NO-FORCE requires both; ARIES exists specifically to make recovery under STEAL + NO-FORCE efficient and correct.

> 💡 **Interview Insight:** If an interviewer asks *"What buffer management policy do production databases use, and why?"* — the complete, senior-level answer is: **STEAL + NO-FORCE**, because it maximizes both buffer manager flexibility and commit-time performance, at the cost of requiring both undo and redo during recovery — a cost that WAL and ARIES are specifically engineered to handle efficiently.

---

## 8.6 NO-STEAL + FORCE

### What It Means

Uncommitted pages **cannot** be flushed early (NO-STEAL), and **all** dirty pages **must** be flushed before commit (FORCE).

### Recovery Implications

- Because uncommitted pages never reach disk (NO-STEAL) → **Undo is never needed.**
- Because everything is on disk by commit time (FORCE) → **Redo is never needed either.**

### Trade-offs

- **Pros:** The simplest possible recovery — literally nothing to do! On restart, the on-disk state is already guaranteed to reflect exactly the last set of committed transactions, with zero ambiguity.
- **Cons:** Severely restrictive in practice. NO-STEAL means the buffer pool must hold *every* dirty page of *every* active transaction until it commits — a serious problem for large transactions (exactly the concern raised in Module 5, Section 5.3). FORCE means every commit pays a potentially large, synchronous I/O cost. Combining both restrictions simultaneously is rarely worthwhile for any real production workload, though it's an excellent teaching example of "maximally simple recovery, maximally poor performance."

### When Might This Be Used?

Extremely simple, low-throughput, single-transaction-at-a-time embedded systems where recovery simplicity matters far more than performance might reasonably choose this combination — but it's essentially absent from mainstream production RDBMS engines.

---

## 8.7 NO-STEAL + NO-FORCE

### What It Means

Uncommitted pages **cannot** be flushed early (NO-STEAL), but a transaction **can** commit without its pages being flushed yet (NO-FORCE).

### Recovery Implications

- Because uncommitted pages never reach disk (NO-STEAL) → **Undo is never needed.**
- Because commit doesn't force a flush (NO-FORCE) → committed changes might not yet be on disk → **Redo is needed.**

This is exactly Module 5's **pure Redo Logging** technique (Section 5.3), formalized in this framework's terms.

### Trade-offs

- **Pros:** Recovery only ever needs a Redo phase — no undo logic required at all, somewhat simpler than full STEAL + NO-FORCE recovery.
- **Cons:** The NO-STEAL constraint remains a serious limitation for large transactions, exactly as discussed in Module 5 — the buffer pool must accommodate every dirty page of every active transaction simultaneously, which doesn't scale to workloads with large or numerous concurrent write-heavy transactions.

---

## 8.8 Master Comparison Table

| Policy | STEAL? | FORCE? | Undo Needed? | Redo Needed? | Real-World Usage |
|---|---|---|---|---|---|
| STEAL + FORCE | Yes | Yes | Yes | No | Rare — worst of both performance-wise |
| **STEAL + NO-FORCE** | **Yes** | **No** | **Yes** | **Yes** | **Industry standard — PostgreSQL, InnoDB, Oracle, SQL Server** |
| NO-STEAL + FORCE | No | Yes | No | No | Rare — simplest recovery, poor performance |
| NO-STEAL + NO-FORCE | No | No | No | Yes | Occasionally used; maps to pure Redo Logging |

## 8.9 Connecting Back to Module 5's Recovery Techniques

This table makes the relationship between Module 5's techniques and this module's framework completely explicit:

| Module 5 Technique | Corresponding Buffer Policy |
|---|---|
| Undo Logging | NO-STEAL + FORCE, or STEAL + FORCE depending on exact variant taught — but always requires FORCE |
| Redo Logging | NO-STEAL + NO-FORCE |
| Undo/Redo Logging | **STEAL + NO-FORCE** |
| Shadow Paging | Not applicable — entirely different model (no in-place dirty pages in the traditional sense) |

If this table feels like a satisfying "click" connecting two earlier modules together, that's exactly the intent — Module 5 introduced these techniques through the lens of *what the log must contain*, while this module introduces the identical underlying trade-offs through the lens of *what the buffer manager is allowed to do*. They're two views of the same coin.

---

## 8.10 Performance Implications

- **STEAL** improves memory management flexibility — critical for handling large transactions and high buffer-pool contention gracefully — at the cost of requiring undo logic in recovery.
- **NO-FORCE** improves commit latency dramatically — commit only needs the (comparatively cheap) log flush, not full data page I/O — at the cost of requiring redo logic in recovery.
- Together, **STEAL + NO-FORCE** essentially says: *"Let the buffer manager do whatever is fastest and most memory-efficient during normal operation; pay a bounded, well-engineered recovery cost (via WAL + ARIES + checkpoints) only in the rare event of a crash."* This is a deliberate, industry-wide bet that optimizing for the common case (normal operation) is worth a more complex, but still fast and bounded, uncommon case (recovery).

---

## 8.11 Advantages of Understanding This Framework

- Gives you a precise vocabulary to classify *any* recovery technique or database engine's behavior in four words or less.
- Makes clear *why* WAL, Undo/Redo Logging, and ARIES exist together as a coherent package — they're not arbitrary design choices, they're the necessary consequences of choosing STEAL + NO-FORCE for performance reasons.
- Frequently the exact framework interviewers use to test whether a candidate understands recovery at a systems-design level, not just a memorized-fact level.

## 8.12 Disadvantages / Trade-offs to Articulate

- STEAL + NO-FORCE is not "free" — it's a deliberate trade of recovery-time complexity (borne rarely, during crashes) for normal-operation performance (paid constantly, on every transaction). Being able to articulate this trade-off explicitly is itself an interview-valuable skill.

## 8.13 Best Practices

- When evaluating or designing any storage/recovery subsystem, explicitly ask: "What's our STEAL policy? What's our FORCE policy?" — the answers immediately tell you what kind of recovery logic (if any) is required.
- Use this framework as a mental checklist when learning about a new or unfamiliar database engine's recovery approach — it applies universally, even to non-relational systems with their own recovery mechanisms.

## 8.14 Common Mistakes

- Confusing STEAL (about *when data can be flushed*) with FORCE (about *when data must be flushed*) — they answer two independent questions, and mixing them up is one of the most common conceptual errors students make on this topic.
- Assuming NO-STEAL + NO-FORCE requires no recovery logic at all — it still requires Redo (Section 8.7), just not Undo.
- Assuming STEAL always implies poor performance — in reality, STEAL is what *enables* good performance under memory pressure; it's NO-STEAL that constrains and often hurts performance for large transactions.

## 8.15 Edge Cases

- A transaction so large that even under STEAL, the buffer manager struggles to keep up with flushing its pages fast enough to free memory for other transactions — a real operational concern connecting to Module 12's performance tuning discussion.
- Systems with mixed policies for different data (e.g., certain in-memory-optimized tables using different flush behavior than standard disk-based tables) — a nuance seen in some modern hybrid engines, worth knowing exists even if it's beyond this handbook's core scope.

---

## 8.16 Chapter Summary

- **Dirty pages** have been modified in memory but not yet flushed to disk; **clean pages** match their on-disk copy exactly.
- **STEAL vs NO-STEAL** answers: can uncommitted pages be flushed early?
- **FORCE vs NO-FORCE** answers: must all pages be flushed before commit?
- Combining these gives four policies; **STEAL + NO-FORCE** is the industry standard, requiring both undo and redo during recovery — precisely why WAL, Undo/Redo Logging, and ARIES exist as a coordinated package.
- This framework is the unifying lens connecting Module 5's recovery techniques to the buffer manager's real, concrete operational behavior.

---

## 8.17 Cheat Sheet

| Policy | Meaning |
|---|---|
| STEAL | Buffer manager MAY flush uncommitted dirty pages early |
| NO-STEAL | Buffer manager must NEVER flush uncommitted dirty pages |
| FORCE | All dirty pages MUST be flushed before commit |
| NO-FORCE | Commit does NOT require dirty pages to be flushed yet |
| STEAL + NO-FORCE | Industry standard — needs BOTH undo and redo |
| NO-STEAL + FORCE | Simplest recovery — needs NEITHER undo nor redo |
