# DBMS Handbook — Part 7: Indexing, File Organization & Storage Structures
## Module 7: Hash Indexing

> **Where we are:** Module 6 gave you the B+ Tree — the default, general-purpose index structure. Module 7 covers the *other* major family: **hash-based indexing** — a structure that trades away range-query and sort support entirely, in exchange for the best possible average-case performance on pure equality lookups.

---

## 7.0 Why Hashing?

A B+ Tree's O(log_f n) search is fast, but it's still a **multi-step traversal**. Hashing asks a more aggressive question:

> **"Can I compute, directly from the key itself, exactly which page to go to — with no traversal at all?"**

If yes, equality lookups become **O(1) average case** — genuinely faster than even a 3–4 level B+ Tree traversal, at the cost of losing all ordering information (Module 3, Section 3.5 already introduced this trade-off at the file-organization level; this module covers the actual algorithms).

---

## 7.1 Static Hashing

### What is it?

**Static hashing** uses a **fixed number of buckets**, determined at index-creation time, and a hash function that maps each key to one of those buckets. The number of buckets does **not** change as the table grows.

### How it works

```
hash(key) mod B  = bucket number      (B = fixed total bucket count)

Example: B = 8 buckets
key = 42  -> hash(42) = 42 -> 42 mod 8 = 2  -> Bucket 2
key = 17  -> hash(17) = 17 -> 17 mod 8 = 1  -> Bucket 1
```

### The core weakness

Because *B* is fixed, as the table grows well beyond its originally-anticipated size, buckets accumulate more and more keys, and **bucket overflow** (Section 7.6) becomes increasingly frequent, degrading average lookup time from O(1) toward O(n/B) and eventually toward a long overflow-chain scan.

### Why it's rarely used alone in production

Choosing *B* correctly requires knowing the table's eventual size **in advance** — real-world tables grow unpredictably, so static hashing alone is fragile. This exact weakness is what **dynamic hashing** and **extendible/linear hashing** (Sections 7.2–7.4) were invented to solve.

### Interview Importance
⭐⭐⭐⭐ — "What's the main weakness of static hashing, and how do dynamic hashing schemes fix it?" is a very standard follow-up question after any hashing discussion.

---

## 7.2 Dynamic Hashing (Overview)

### What is it?

**Dynamic hashing** is the general term for hashing schemes that allow the number of buckets to **grow and shrink as the table's actual data volume changes**, avoiding static hashing's fixed-bucket-count fragility. **Extendible Hashing** and **Linear Hashing** (Sections 7.3–7.4) are the two classical, most widely-taught concrete implementations of this idea.

### The shared core idea

Instead of committing to a fixed bucket count upfront, dynamic hashing schemes use only **part of a key's hash value** at any given time (a prefix of bits, or an equivalent scheme), progressively using **more bits** of the hash as the data grows and more buckets are needed — allowing controlled, incremental growth instead of a single catastrophic full-table rehash.

---

## 7.3 Extendible Hashing

### What is it?

**Extendible Hashing** is a dynamic hashing scheme that uses a **directory** of pointers to buckets, where the directory's size doubles (2^d entries, where *d* is called the **global depth**) whenever a bucket overflows and needs to split, but individual **buckets only split when they specifically overflow** — avoiding a full rehash of the entire table.

### Key Concepts

- **Global Depth (d):** The number of bits (from the start/prefix of each key's hash) used by the directory to decide which directory slot points to which bucket. Directory size = 2^d.
- **Local Depth (d_bucket):** The number of bits actually used to determine membership within a *specific* bucket. A bucket's local depth is always ≤ the global depth.
- When a bucket's local depth **equals** the global depth and it overflows, the **directory itself must double** (global depth increases by 1) before the bucket can split, because the current directory doesn't have enough distinct entries to point to more buckets at that prefix.
- When a bucket's local depth is **less than** the global depth and it overflows, the bucket can simply **split** without needing to double the directory (since existing directory entries can be repointed to the two new buckets without adding new directory slots).

### Diagram — Extendible Hashing Structure

```
Global Depth d = 2  ->  Directory has 2^2 = 4 entries (using first 2 bits of hash)

Directory:                Buckets (local depth shown):
  00  ---------\
                +----> Bucket A (local depth = 1) [keys with hash prefix 0*]
  01  ---------/
  10  --------------->  Bucket B (local depth = 2) [keys with hash prefix 10]
  11  --------------->  Bucket C (local depth = 2) [keys with hash prefix 11]

Note: Bucket A is pointed to by TWO directory entries (00 and 01) because its
local depth (1) is less than the global depth (2) -- it hasn't needed to
distinguish between hash-prefix '0' followed by a 0 or 1 yet.
```

### Worked Example — Bucket Split WITHOUT Directory Doubling

```
Bucket A (local depth 1, shared by directory entries 00 and 01) overflows.

Since local depth (1) < global depth (2):
  Split Bucket A into Bucket A1 and Bucket A2, each now local depth = 2.
  Directory entry 00 now points to A1 (keys matching prefix '00')
  Directory entry 01 now points to A2 (keys matching prefix '01')
  NO directory doubling needed -- directory size stays at 4.
```

### Worked Example — Bucket Split WITH Directory Doubling

```
Bucket B (local depth 2, EQUAL to global depth 2) overflows.

Since local depth == global depth, the directory must DOUBLE first:
  Global depth becomes 3 -> directory grows from 4 entries to 8 entries.
  Every existing bucket now has TWO directory entries pointing to it
  (except the bucket that's about to split, which gets its own two entries
   pointing to its two new halves).
  THEN Bucket B splits into B1 and B2, each with local depth = 3.
```

### Why Extendible Hashing Is Efficient

Directory doubling is a relatively cheap, localized metadata operation (the directory is typically small enough to fit comfortably in memory even at large sizes) — the **actual data buckets themselves are NOT all rehashed** on directory doubling, only the one bucket that specifically overflowed gets split. This avoids the catastrophic "rehash everything" cost that naive resizing would otherwise require.

### Advantages
- No full-table rehash ever required — growth is always localized to the one overflowing bucket (plus, occasionally, cheap directory doubling).
- Lookup remains O(1) — directory lookup is O(1) (direct array index using the first *d* bits of the hash), followed by one bucket read.

### Disadvantages
- The directory itself can grow large for skewed data distributions (many buckets needing high local depth), consuming more memory.
- Somewhat more complex to implement correctly than static hashing or linear hashing.

## 7.4 Linear Hashing

### What is it?

**Linear Hashing** is a different dynamic hashing scheme that grows the bucket count **one bucket at a time, in a fixed, predetermined round-robin order**, rather than using a directory — avoiding the extra directory-lookup indirection that extendible hashing requires, at the cost of sometimes still needing overflow chains temporarily even for buckets that haven't been "reached" yet in the split order.

### Key Concepts

- A **split pointer** tracks which bucket will be split **next**, cycling through all buckets in order (bucket 0, then 1, then 2, ... then wrapping back to 0 after a full round, at which point the number of hash bits used effectively increases by one, similar in spirit to extendible hashing's global depth increment).
- Splits happen **on a schedule** (e.g., every time a bucket overflows, OR based on a load-factor threshold, depending on the specific variant), **not necessarily the exact bucket that just overflowed** — meaning a bucket that overflows might get a temporary **overflow chain** attached to it even though it isn't the bucket scheduled to split next; that bucket will only actually split when the split pointer reaches it in its round-robin order.

### Diagram — Linear Hashing Split Progression

```
Initial buckets: [0] [1] [2] [3]     Split pointer -> Bucket 0 (next to split)

Bucket 2 overflows (but split pointer is at Bucket 0, not Bucket 2):
  -> Bucket 2 gets a temporary OVERFLOW CHAIN attached, no split happens yet

[0] [1] [2 -> overflow chain] [3]     Split pointer still -> Bucket 0

Eventually, split pointer reaches Bucket 0 (its scheduled turn):
  Bucket 0 splits into Bucket 0 and a NEW Bucket 4
  Split pointer advances -> Bucket 1 (next to split)

[0] [1] [2 -> overflow chain] [3] [4-new]     Split pointer -> Bucket 1
```

### Why Linear Hashing Is Used

It avoids the **extra indirection** of a directory (unlike extendible hashing, there's no separate directory structure to consult before reaching a bucket) — bucket location can often be computed with simple arithmetic (a hash function plus a check against the current split pointer position), making it somewhat simpler and more memory-efficient for the "pointer to buckets" bookkeeping, at the cost of tolerating temporary overflow chains on buckets that haven't had their scheduled turn to split yet.

### Comparison: Extendible Hashing vs Linear Hashing

| Aspect | Extendible Hashing | Linear Hashing |
|---|---|---|
| Extra indirection structure | Directory (array of pointers) | None — direct computation + split pointer check |
| Split order | Exactly the bucket that overflowed | Round-robin order (may not be the bucket that just overflowed) |
| Temporary overflow chains | Rare/avoided by design (split happens immediately at the overflowing bucket) | Common — non-scheduled buckets that overflow must wait, using an overflow chain in the meantime |
| Memory overhead | Directory can grow large for skewed data | No directory, generally lower structural overhead |

## 7.5 Hash Functions

### What is it?

A **hash function** maps an input key (of arbitrary size/type) to a fixed-size output value (the "hash"), ideally distributing keys **as uniformly as possible** across the available output range/buckets.

### Properties of a good hash function for database indexing

1. **Deterministic** — same input always produces the same output (required for consistent lookups).
2. **Uniform distribution** — spreads keys evenly across buckets, minimizing clustering (a poorly-distributed hash function causes some buckets to overflow constantly while others stay nearly empty).
3. **Fast to compute** — since it's computed on every insert and every lookup.
4. **Avalanche effect (for cryptographic-strength hash functions, though not always required for simple DB hashing)** — small input changes cause large, unpredictable output changes, though for basic DB hash indexes this is a nice-to-have rather than a strict requirement (unlike security-focused hash functions).

### Common Mistakes
- Using a hash function poorly suited to the actual key distribution (e.g., a naive modulo on sequential integer IDs with a bucket count that shares common factors with the ID pattern) can cause severe clustering — always validate hash function behavior against real data distributions, not just theoretical uniform-random assumptions.

## 7.6 Collision Resolution and Bucket Overflow

### What is a collision?

A **collision** occurs when two different keys hash to the **same bucket**. Since hash functions map a large key space onto a much smaller bucket space, collisions are **mathematically inevitable** (pigeonhole principle) — every practical hashing scheme must handle them.

### Collision Resolution Strategies

| Strategy | How it works |
|---|---|
| **Separate Chaining** | Each bucket holds a linked list (or similar structure) of all keys hashing to it; on collision, simply append to the list. Simple, and the most common approach in database hash indexes. |
| **Open Addressing** | On collision, probe for the next available slot using a defined probing sequence (linear probing, quadratic probing, double hashing) — more common in in-memory hash tables (e.g., hash join implementations in Part 8) than in on-disk database hash indexes. |

### Bucket Overflow

**Bucket overflow** occurs when a bucket (already using chaining or otherwise) exceeds its capacity for one physical page, requiring an **overflow page** (a separate, linked page holding the "spillover" entries) — directly analogous to the linked-list chaining idea, but implemented at the physical page level rather than as an in-memory pointer structure.

```
Bucket 3 (fits ~10 entries per page, currently has 10):
  Page for Bucket 3: [10 entries, FULL]
        |
        v (overflow pointer)
  Overflow Page 1: [3 more entries that didn't fit]
        |
        v (if this ALSO fills up)
  Overflow Page 2: [more entries...]
```

### Performance Impact of Overflow Chains

Every additional overflow page in a chain adds **one more potential disk I/O** to any lookup that needs to search that chain — meaning heavily-overflowed buckets degrade toward O(chain length) instead of the ideal O(1), which is precisely why dynamic hashing schemes (Sections 7.3–7.4) exist: to **minimize how often and how deep overflow chains form** by proactively splitting buckets before they get too deep.

## 7.7 Performance Analysis — Hash Indexes vs B+ Tree Indexes

| Operation | Hash Index | B+ Tree Index |
|---|---|---|
| Equality lookup (`= X`) | O(1) average (degrades with overflow chains) | O(log_f n), typically 3-4 I/Os |
| Range query (`BETWEEN X AND Y`) | Not supported — must scan all buckets | O(log_f n) + sequential leaf scan, very efficient |
| Sorted output (`ORDER BY`) | Not supported | Naturally sorted via leaf-level traversal |
| Worst-case degradation | Can degrade toward O(n) with severe collisions/skew and long overflow chains | Bounded at O(log_f n) even in worst case, due to self-balancing structure |
| Storage overhead | Generally lower per entry (no internal-node signpost overhead) | Slightly higher (internal nodes consume extra space purely for signposts) |

### Advantages of Hash Indexes
- Best possible average-case performance for pure equality-lookup-only workloads.
- Simpler underlying structure than a self-balancing tree (no split/merge/redistribution logic to maintain sorted invariants).

### Disadvantages of Hash Indexes
- Zero support for range queries or sorted output — an enormous limitation for most real-world query patterns, which is why hash indexes are the **exception**, not the default, in production databases.
- Vulnerable to performance degradation from poor hash distribution or insufficient dynamic resizing.

### PostgreSQL and MySQL Support (brief, industry-relevance note)

PostgreSQL supports hash indexes as an explicit index type (`CREATE INDEX ... USING HASH`), historically limited by a lack of crash-recoverable write-ahead logging support in older versions (a historical PostgreSQL limitation, since resolved in modern versions where hash indexes are WAL-logged and crash-safe) — but hash indexes remain far less commonly used than B+ Tree (`btree`, PostgreSQL's default index type) in practice, precisely because most real workloads eventually need range queries or sorting that hash indexes cannot serve. MySQL/InnoDB does not expose a persistent, user-creatable hash index type directly for standard tables, but internally maintains an **Adaptive Hash Index** (a self-tuning, in-memory-only hash structure built automatically over "hot" portions of existing B+ Tree indexes to accelerate their equality lookups) — covered in Module 9's InnoDB internals discussion.

### Interview Importance
⭐⭐⭐⭐⭐ — "When would you choose a hash index over a B+ Tree, and why do most databases default to B+ Trees anyway even for equality-heavy workloads?" — expected answer: hash indexes only make sense when you can **guarantee** no range/sort queries will ever be needed on that column, which is rare enough in practice that B+ Trees' "good enough at everything" property usually wins as the safer default.

## 7.8 Chapter Summary

- **Static hashing** uses a fixed bucket count, degrading over time as tables outgrow their originally-planned size — leading to increasingly deep, costly overflow chains.
- **Dynamic hashing** (the general category) allows bucket count to grow incrementally, avoiding a catastrophic full-table rehash.
- **Extendible Hashing** uses a directory (indexed by a growing number of hash-prefix bits, the "global depth") pointing to buckets (each with its own "local depth"); the directory only doubles when a bucket at maximum local depth overflows, and only the overflowing bucket itself splits.
- **Linear Hashing** grows buckets one at a time in a fixed round-robin order via a "split pointer," avoiding a directory but tolerating temporary overflow chains on buckets not yet scheduled to split.
- **Collisions are mathematically inevitable**; resolved via **separate chaining** (most common in DB hash indexes) or **open addressing** (more common in in-memory structures like hash joins, Part 8).
- **Bucket overflow** is handled via linked overflow pages, and every additional overflow page adds a potential extra disk I/O — the entire motivation for dynamic hashing schemes.
- Hash indexes give the best possible **average-case equality lookup** performance (O(1)) but provide **zero support** for range queries or sorted output — this fundamental trade-off is why B+ Trees remain the default index type in virtually every production RDBMS, with hash indexes reserved for narrow, equality-only use cases.

---

## 7.9 Cheat Sheet

```
Static Hashing         = fixed bucket count -> degrades as table grows (more overflow chains)
Dynamic Hashing        = general term for growable bucket-count schemes

Extendible Hashing:
  Global Depth (d)     = bits used by DIRECTORY (size = 2^d)
  Local Depth          = bits used by a specific BUCKET (always <= global depth)
  local < global       -> bucket splits WITHOUT directory doubling
  local == global      -> DIRECTORY DOUBLES first, then bucket splits

Linear Hashing:
  Split Pointer        = tracks NEXT bucket to split, round-robin order
  Overflow ≠ scheduled split -> temporary overflow chain until pointer reaches that bucket

Collision Resolution:
  Separate Chaining    = linked list per bucket (most common in DB hash indexes)
  Open Addressing      = probe for next free slot (more common in in-memory hash tables)

Bucket Overflow        = linked overflow pages; each one = potential extra disk I/O

Hash Index vs B+ Tree:
  Equality lookup: Hash O(1) avg   |   B+ Tree O(log_f n)
  Range query:     Hash NOT supported  |  B+ Tree O(log_f n) + efficient leaf scan
  Default choice in production: B+ Tree (safer, handles both patterns)

InnoDB: Adaptive Hash Index = automatic, in-memory-only, built OVER existing B+ Tree hot spots
```

## 7.11 MCQs

**Q1.** What is the main limitation of static hashing?
A) It cannot support equality lookups  B) Fixed bucket count causes degrading performance as the table grows  C) It requires a directory structure  D) It cannot be used with disk-based storage
*(Answer: B)*

**Q2.** In extendible hashing, when does the directory need to double?
A) Every time any bucket overflows  B) Only when a bucket's local depth equals the current global depth and it overflows  C) Only when the table is first created  D) Never — directories are fixed size
*(Answer: B)*

**Q3.** In linear hashing, what determines which bucket splits next?
A) Whichever bucket has the most collisions  B) A round-robin split pointer, in a predetermined fixed order  C) The bucket with the lowest local depth  D) A random selection
*(Answer: B)*

**Q4.** Why can't a hash index efficiently support `ORDER BY` or range queries?
A) Hash indexes don't store enough data  B) The hash function deliberately scrambles key order to distribute entries evenly, destroying any ordering relationship between keys and bucket location  C) Hash indexes are always slower than B+ Trees  D) Hash indexes don't support NULL values
*(Answer: B)*

**Q5.** InnoDB's Adaptive Hash Index is best described as:
A) A user-created persistent index type  B) An automatic, in-memory-only structure built over hot portions of existing B+ Tree indexes  C) A replacement for InnoDB's clustered B+ Tree  D) A disk-based static hash structure
*(Answer: B)*
