## 15.1 Capstone: Banking System

### Requirement Analysis
Core entities: customers, accounts, transactions (deposits/withdrawals/transfers), branches. **Non-negotiable requirement:** money must never be created or destroyed — every transfer must debit one account and credit another atomically. Strong consistency mandatory; regulatory audit trail mandatory (Module 2.12).

### ER Diagram (simplified)
```
Customer ──1:N── Account ──1:N── Transaction
                     │
                     └──N:1── Branch
```

### Normalization
3NF throughout — no redundant balance calculations stored (balance is derived from summing transactions, or maintained via a carefully-audited running balance column updated only within the same transaction as the ledger entry, never independently).

### Schema Design
```sql
CREATE TABLE customers (
    customer_id BIGINT PRIMARY KEY,
    full_name TEXT NOT NULL,
    kyc_verified BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE accounts (
    account_id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(customer_id),
    branch_id INT NOT NULL,
    account_type TEXT NOT NULL CHECK (account_type IN ('checking','savings')),
    balance NUMERIC(18,2) NOT NULL DEFAULT 0 CHECK (balance >= 0),
    version INT NOT NULL DEFAULT 0  -- optimistic concurrency control
);

CREATE TABLE ledger_entries (
    entry_id BIGINT PRIMARY KEY,
    account_id BIGINT NOT NULL REFERENCES accounts(account_id),
    transaction_id BIGINT NOT NULL,
    amount NUMERIC(18,2) NOT NULL,  -- positive = credit, negative = debit
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Indexing Strategy
Index `accounts(customer_id)` for account lookup; index `ledger_entries(account_id, created_at)` for statement generation; index `ledger_entries(transaction_id)` for audit reconciliation (Module 5/13 recap on composite index leftmost-prefix design).

### Transactions
A transfer is a single ACID transaction (Part 6-7 / M13 recap): debit ledger entry + credit ledger entry + both balance updates, at **Serializable** or **Repeatable Read** isolation with row-level locking (`SELECT ... FOR UPDATE`) to prevent lost updates on concurrent transfers to the same account.

### Security
Column-level encryption for SSN/tax ID; RLS not typically needed (single-tenant per bank, but branch-level access scoping via roles); exhaustive audit logging on every balance-affecting operation (Module 2.7); PCI DSS scope if card data involved.

### Scaling Strategy
Read replicas for statement/reporting queries (Module 5); primary remains single-writer per shard given consistency requirements; consider sharding by `customer_id` range/hash for very large banks, accepting that cross-shard transfers need distributed transaction coordination (2PC or a saga pattern — M13.11 recap).

### Replication & HA
Active-Passive with synchronous replication to at least one standby for zero data loss on failover (Module 6) — banking RPO tolerance is typically at or near zero.

### Backup & DR
Continuous PITR (Module 7), backups retained 7+ years for regulatory compliance, geo-redundant DR site with regularly rehearsed drills — often a regulatory mandate, not just best practice.

### Monitoring
Real-time balance-reconciliation checks (sum of all ledger entries per account must equal `accounts.balance` — an automated integrity job); standard latency/lock/replication dashboards (Module 4).

### Deployment Architecture
```
[App Servers] → [Connection Pooler] → [Primary DB (sync replica)] → [DR Region (async)]
                                              │
                                    [Read Replicas - reporting]
```

## 15.2 Capstone: E-commerce Platform

### Requirement Analysis
Entities: customers, products, inventory, orders, payments, reviews. Requires strong consistency for inventory/orders/payments, but can tolerate eventual consistency for product search/recommendations (Module 10.8 polyglot recap).

### ER Diagram
```
Customer ──1:N── Order ──1:N── OrderItem ──N:1── Product ──1:1── Inventory
                    │
                    └──1:1── Payment
```

### Normalization
3NF for transactional tables; deliberate denormalization of `product_display` (cached price/name) into `OrderItem` at order time — order history must reflect the price *at time of purchase*, not the current product price (a common, important normalization exception).

### Schema Design
```sql
CREATE TABLE products (
    product_id BIGINT PRIMARY KEY,
    name TEXT NOT NULL,
    price NUMERIC(10,2) NOT NULL
);

CREATE TABLE inventory (
    product_id BIGINT PRIMARY KEY REFERENCES products(product_id),
    quantity_available INT NOT NULL CHECK (quantity_available >= 0)
);

CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status TEXT NOT NULL DEFAULT 'pending',
    total_amount NUMERIC(10,2) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
    order_id BIGINT NOT NULL REFERENCES orders(order_id),
    product_id BIGINT NOT NULL REFERENCES products(product_id),
    quantity INT NOT NULL,
    price_at_purchase NUMERIC(10,2) NOT NULL,
    PRIMARY KEY (order_id, product_id)
);
```

### Indexing Strategy
`orders(customer_id, created_at DESC)` for order history; `order_items(product_id)` for sales analytics; product search offloaded to Elasticsearch (Module 10) rather than indexed heavily in the relational store.

### Transactions
Checkout is a single transaction: decrement inventory (`WHERE quantity_available >= requested_qty` to prevent overselling), create order + order_items, create payment record — all-or-nothing (Module 13.5 Atomicity recap).

### Security
PCI DSS scope for payment data (never store full card numbers — Module 2.12); RLS if multi-tenant (marketplace model with multiple sellers).

### Scaling Strategy
Read replicas for browsing/order-history (Module 5); Redis cache for cart/session and hot product pages; Elasticsearch for search; Cassandra/DynamoDB for clickstream feeding recommendations (Module 10.8 composite architecture recap).

### Replication & Sharding
Primary Active-Passive for orders/payments; consider sharding orders by `customer_id` hash at very large scale, keeping a customer's full order history co-located on one shard.

### Backup & DR
Standard PITR + geo-redundancy (Module 7); payment data backups meet PCI retention/encryption requirements.

### Monitoring
Cart abandonment / checkout latency dashboards; inventory-decrement lock contention monitoring (a classic hot-row risk on popular products — Module 11.13).

### Deployment Architecture
See the composite e-commerce diagram in Module 12.12 — this capstone is that architecture instantiated.

## 15.3 Capstone: Hospital Management System

### Requirement Analysis
Entities: patients, appointments, medical records, prescriptions, billing, staff. HIPAA compliance mandatory (Module 2.12) — every access to patient data must be audited.

### ER Diagram
```
Patient ──1:N── Appointment ──N:1── Doctor
    │
    ├──1:N── MedicalRecord
    └──1:N── Prescription
```

### Normalization
3NF; medical records separated from demographic/billing data into distinct tables with **independently scoped access controls** (column/table-level security, Module 2.2.7-2.2.8) — a clinician needs medical history, billing staff needs only billing data, and neither role should default to seeing both.

### Schema Design
```sql
CREATE TABLE patients (
    patient_id BIGINT PRIMARY KEY,
    full_name TEXT NOT NULL,
    date_of_birth DATE NOT NULL
);

CREATE TABLE medical_records (
    record_id BIGINT PRIMARY KEY,
    patient_id BIGINT NOT NULL REFERENCES patients(patient_id),
    doctor_id BIGINT NOT NULL,
    diagnosis TEXT,
    notes TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE appointments (
    appointment_id BIGINT PRIMARY KEY,
    patient_id BIGINT NOT NULL REFERENCES patients(patient_id),
    doctor_id BIGINT NOT NULL,
    scheduled_at TIMESTAMPTZ NOT NULL,
    status TEXT NOT NULL DEFAULT 'scheduled'
);
```

### Indexing Strategy
`appointments(doctor_id, scheduled_at)` to check doctor availability without double-booking (a hot-row-adjacent concern — use row locking within the booking transaction); `medical_records(patient_id, created_at DESC)` for chart review.

### Transactions
Appointment booking uses row-level locking (`SELECT ... FOR UPDATE` on the doctor's time slot) to prevent double-booking, structurally identical to Airbnb's booking-consistency requirement (Module 12.6 recap).

### Security
Full HIPAA compliance: encryption at rest/transit, mandatory audit logging of every medical record access (who viewed which patient's record, when — Module 2.7), RLS scoping records to the patient's care team, data masking in any non-production environment (Module 2.10).

### Scaling Strategy
Moderate scale typically (a hospital system, not a global consumer app) — vertical scaling + read replicas for reporting usually sufficient; specialized document/imaging store for radiology/scan data separate from the relational core.

### Replication & HA
Active-Passive with automatic failover (Module 6); uptime is safety-critical during active patient care hours.

### Backup & DR
Long mandatory retention periods (often 7-10+ years depending on jurisdiction); PITR for accidental record corrections; DR drills mandatory given patient-safety stakes.

### Monitoring
Audit log completeness monitoring (any gap in audit coverage is itself a compliance incident); standard availability/latency dashboards.

### Deployment Architecture
```
[Clinical App] → [VPN/Private Network] → [Primary DB - encrypted, audited]
                                                │
                                    [Standby - automatic failover]
                                                │
                                    [Encrypted, long-retention backups]
```

## 15.4 Capstone: Food Delivery App

### Requirement Analysis
Entities: restaurants, menu items, orders, delivery drivers, real-time location tracking. High write volume for location updates; strong consistency needed for order/payment, eventual consistency acceptable for driver location display.

### ER Diagram
```
Restaurant ──1:N── MenuItem
Customer ──1:N── Order ──1:N── OrderItem ──N:1── MenuItem
Order ──1:1── Delivery ──N:1── Driver
```

### Normalization
3NF for orders/menu; driver location updates handled **outside** the relational schema entirely (see Scaling below) — this is a case where forcing high-frequency, low-value writes into the same store as transactional data would be an anti-pattern (Module 11.12 WAL explosion risk).

### Schema Design
```sql
CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    restaurant_id BIGINT NOT NULL,
    status TEXT NOT NULL DEFAULT 'placed',
    total_amount NUMERIC(10,2) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE deliveries (
    delivery_id BIGINT PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES orders(order_id),
    driver_id BIGINT,
    status TEXT NOT NULL DEFAULT 'unassigned'
);
```

### Indexing Strategy
`orders(restaurant_id, status)` for restaurant order queues; `orders(customer_id, created_at DESC)` for order history.

### Transactions
Order placement: create order + order_items + decrement any restaurant-side item availability, in one transaction; driver assignment is a separate, short transaction to minimize lock duration on the deliveries table.

### Security
PCI scope for payment; standard RBAC for restaurant-partner dashboard access (each restaurant should see only its own orders — RLS).

### Scaling Strategy
**Driver location tracking is the standout scaling challenge**: extremely high write frequency (every few seconds per active driver), low durability requirement per individual update (only the latest position matters). This workload is a textbook fit for Redis (key-value, in-memory, Module 10 recap) or a wide-column store, explicitly NOT the primary relational database — directly illustrating the Module 10.8 polyglot persistence principle.

### Replication & Sharding
Orders database: Active-Passive with read replicas for restaurant/customer dashboards; location store: horizontally sharded by geographic region for locality.

### Backup & DR
Standard PITR for orders/payments; location data typically doesn't need long-term backup (ephemeral, low value after a delivery completes) — a good example of **not every dataset needing the same backup rigor** (Module 7 principle applied selectively).

### Monitoring
Delivery-assignment latency; driver-location update throughput; order-to-delivery SLA tracking dashboard.

### Deployment Architecture
```
[Customer/Restaurant Apps] → [Order Service] → [(PostgreSQL - orders, payments)]
                            → [Location Service] → [(Redis/Cassandra - driver GPS)]
```

## 15.5 Capstone: Ride-Sharing App

### Requirement Analysis
Entities: riders, drivers, trips, real-time location, pricing/surge. Similar profile to food delivery but with tighter real-time matching latency requirements and a critical **hot-partition risk** around geographic/temporal concentration (e.g., a concert ending, flooding one area with simultaneous ride requests — Module 11.13 recap, and directly the Uber case study from Module 12.4).

### ER Diagram
```
Rider ──1:N── Trip ──N:1── Driver
Trip ──1:1── Payment
```

### Schema Design
```sql
CREATE TABLE trips (
    trip_id BIGINT PRIMARY KEY,
    rider_id BIGINT NOT NULL,
    driver_id BIGINT,
    status TEXT NOT NULL DEFAULT 'requested',
    pickup_lat DOUBLE PRECISION,
    pickup_lng DOUBLE PRECISION,
    fare_amount NUMERIC(10,2),
    requested_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Indexing Strategy
Geospatial indexing (PostGIS `GiST` index, or a dedicated geo-index in a specialized store) for "find nearby available drivers" queries — a fundamentally different index type from standard B+ Tree (Module 13.6-13.7 recap: not every access pattern is B+ Tree-shaped).

### Transactions
Trip matching (assigning a driver) uses optimistic concurrency or row-level locking to prevent two riders from being matched to the same driver simultaneously — directly the hot-row concern from Module 11.13.

### Security
Location data is sensitive PII requiring careful access scoping and retention limits (varies by jurisdiction, GDPR-relevant — Module 2.12).

### Scaling Strategy — Sharding
**Shard key choice is the central design decision**, echoing Module 12.4's Uber case study directly: sharding by geographic region (e.g., city/metro area) distributes both trip-matching load and location-update load evenly, and keeps most queries ("find nearby drivers") within a single shard — avoiding the cross-shard query complexity a naive `trip_id`-based shard would create.

### Replication & HA
Active-Active across regions is attractive here (each city's traffic is naturally regional — Module 6.3 recap), reducing latency for real-time matching and improving regional-failure survivability.

### Backup & DR
Standard PITR for trips/payments; less critical for raw location pings (similar reasoning to food delivery).

### Monitoring
Match-time latency (rider request → driver assigned); per-shard/per-region load distribution dashboard specifically watching for hot-partition formation during high-demand events (concerts, weather events).

### Deployment Architecture
```
[Rider/Driver Apps] → [Regional Load Balancer] → [Region-sharded Trip Service + DB]
                                                          │
                                              [Geo-index for driver matching]
```

## 15.6 Capstone: Chat Application

### Requirement Analysis
Entities: users, conversations, messages, read receipts, presence. Extremely high write volume (every message), low per-message latency requirement, eventual consistency acceptable for presence/read-receipts, but message ordering within a conversation must be preserved.

### ER Diagram
```
User ──N:N── Conversation ──1:N── Message
```

### Schema Design
```sql
CREATE TABLE conversations (
    conversation_id BIGINT PRIMARY KEY,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE messages (
    message_id BIGINT PRIMARY KEY,
    conversation_id BIGINT NOT NULL REFERENCES conversations(conversation_id),
    sender_id BIGINT NOT NULL,
    content TEXT NOT NULL,
    sent_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Indexing Strategy
`messages(conversation_id, sent_at)` is the dominant access pattern (load a conversation's message history in order) — this is precisely the shard/partition key candidate too.

### Transactions
Individual message sends are single-row inserts — minimal transactional complexity per message, but at massive aggregate scale (this is WhatsApp's core workload, Module 12.9 recap).

### Security
End-to-end encryption (application-layer, beyond database-layer encryption) is standard for modern chat apps; message content should never be readable by database administrators in a true E2E design — a security requirement that shapes the schema itself (the database stores encrypted blobs, not plaintext).

### Scaling Strategy — Sharding
Shard by `conversation_id` (keeps a full conversation's messages co-located, matching the dominant read pattern) — a wide-column store like Cassandra (Module 10.3.2) is a strong fit given the write-heavy, simple-key-based access pattern, mirroring Module 12.3's Netflix/Cassandra reasoning applied to a different workload.

### Replication & HA
Multi-region active-active for global user base; message delivery should degrade gracefully (queue and retry) during partition rather than reject entirely (an AP-leaning choice, similar reasoning to Module 12.2's Amazon cart example).

### Backup & DR
Message history backup with user-controlled retention/deletion (GDPR right-to-erasure implications — Module 2.12).

### Monitoring
Message delivery latency (send → recipient delivery confirmation); per-shard write throughput; presence-system heartbeat health.

### Deployment Architecture
```
[Client] → [WebSocket Gateway] → [Message Service] → [(Cassandra - sharded by conversation_id)]
                                → [Presence Service] → [(Redis - ephemeral online status)]
```

## 15.7 Capstone: Video Streaming Platform

### Requirement Analysis
Entities: videos, users, watch history, subscriptions, recommendations. Metadata (titles, descriptions) is relational; actual video files live in object storage (not a database concern per se); watch history and recommendations are massive-scale, write-heavy, and benefit from a Netflix-style architecture (Module 12.3 recap).

### ER Diagram
```
User ──1:N── WatchHistory ──N:1── Video ──N:1── Category
User ──1:N── Subscription
```

### Schema Design
```sql
CREATE TABLE videos (
    video_id BIGINT PRIMARY KEY,
    title TEXT NOT NULL,
    duration_seconds INT NOT NULL,
    storage_url TEXT NOT NULL
);

CREATE TABLE watch_history (
    user_id BIGINT NOT NULL,
    video_id BIGINT NOT NULL REFERENCES videos(video_id),
    watched_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    progress_seconds INT NOT NULL DEFAULT 0,
    PRIMARY KEY (user_id, video_id)
);
```

### Indexing Strategy
`watch_history(user_id, watched_at DESC)` for "continue watching"; video metadata search offloaded to Elasticsearch (Module 10) for title/genre/actor search.

### Transactions
Minimal — watch-progress updates are simple upserts, not multi-table transactions; this workload rarely needs strong ACID guarantees beyond single-row consistency.

### Security
DRM/content-licensing concerns are largely outside the database layer; standard access control for subscription/billing data (Module 2).

### Scaling Strategy
Watch history is the dominant write volume — a wide-column store (Cassandra, directly echoing Module 12.3) handles this well; relational metadata store remains small and easily replicated; a separate recommendation pipeline consumes watch-history events (via CDC or streaming) to build ML-driven suggestions asynchronously.

### Replication & HA
Multi-region active-active for global content delivery, paired with a CDN (outside database scope) for actual video bytes; metadata database uses standard Active-Passive HA.

### Backup & DR
Metadata backed up normally; watch history durability requirements are lower (losing a few minutes of watch-progress data is a minor UX issue, not a business-critical loss) — another example of tiered backup rigor by dataset criticality (Module 7 principle).

### Monitoring
Video start latency, buffering rate (application-level, not strictly database, but correlated with backend query latency for manifest/metadata lookups).

### Deployment Architecture
```
[Client] → [CDN - video bytes, outside DB scope]
        → [Metadata Service] → [(PostgreSQL - videos, subscriptions)]
        → [Watch History Service] → [(Cassandra - sharded by user_id)]
        → [Recommendation Pipeline] → [(streaming/ML infra, consumes CDC events)]
```

## 15.8 Capstone: Social Media Platform

### Requirement Analysis
Entities: users, posts, follows, likes, comments. The "social graph" (who follows whom) plus a massive read-heavy news feed generation problem — directly the Meta case study pattern (Module 12.5: relational core + massive caching).

### ER Diagram
```
User ──N:N── User (follows, self-referencing)
User ──1:N── Post ──1:N── Comment
Post ──N:N── User (likes)
```

### Schema Design
```sql
CREATE TABLE posts (
    post_id BIGINT PRIMARY KEY,
    author_id BIGINT NOT NULL,
    content TEXT,
    like_count BIGINT NOT NULL DEFAULT 0,  -- denormalized counter, Module 5/11 recap
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE follows (
    follower_id BIGINT NOT NULL,
    followee_id BIGINT NOT NULL,
    PRIMARY KEY (follower_id, followee_id)
);

CREATE TABLE likes (
    user_id BIGINT NOT NULL,
    post_id BIGINT NOT NULL REFERENCES posts(post_id),
    PRIMARY KEY (user_id, post_id)
);
```

### Indexing Strategy
`follows(followee_id)` to find a user's followers (feed fan-out); `posts(author_id, created_at DESC)` for profile timelines.

### Transactions
Liking a post: insert into `likes` + increment `posts.like_count` — this is exactly the **hot-row risk** from Module 11.13 for viral posts; the resolution (sharded sub-counters, summed on read) applies directly.

### Security
Privacy settings drive row-level visibility rules (a private account's posts should only be visible to approved followers — RLS-style enforcement, Module 2.2.6).

### Scaling Strategy
News feed generation is the classic hard problem: **fan-out on write** (pre-compute each follower's feed when a post is made — fast reads, expensive/slow writes for high-follower-count accounts) vs. **fan-out on read** (compute the feed at request time by querying all followed users' recent posts — slow reads, cheap writes). Most large platforms use a **hybrid**: fan-out on write for typical users, fan-out on read for "celebrity" accounts with millions of followers (avoiding a massive write amplification storm on every celebrity post) — directly a hot-partition/hot-row avoidance pattern (Module 11.13) applied at the architecture level.

### Replication & Sharding
Heavy caching layer (Redis) in front of the relational core, mirroring Module 12.5's Meta pattern; social graph itself is a candidate for a graph database (Module 10.3.5) if relationship-traversal queries (e.g., "friends of friends") become a dominant, complex access pattern.

### Backup & DR
Standard PITR; user-content deletion requests (GDPR) must propagate through caches as well as the primary store — cache invalidation becomes a compliance concern, not just a performance one.

### Monitoring
Feed-generation latency; cache hit ratio (critical here — Module 4/5 recap); like/comment write throughput on viral content specifically watched for hot-row contention.

### Deployment Architecture
```
[Client] → [Feed Service] → [Redis - cached feeds] → [(PostgreSQL - posts, follows, likes)]
                                                              │
                                              [Sharded like-counters for viral posts]
```

## 15.9 Capstone: Inventory Management System

### Requirement Analysis
Entities: warehouses, products, stock levels, purchase orders, stock movements. Strong consistency mandatory — overselling or double-counting inventory has direct financial consequences; multi-warehouse tracking adds complexity.

### ER Diagram
```
Warehouse ──1:N── StockLevel ──N:1── Product
StockLevel ──1:N── StockMovement
PurchaseOrder ──1:N── PurchaseOrderItem ──N:1── Product
```

### Schema Design
```sql
CREATE TABLE stock_levels (
    warehouse_id INT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INT NOT NULL CHECK (quantity >= 0),
    PRIMARY KEY (warehouse_id, product_id)
);

CREATE TABLE stock_movements (
    movement_id BIGINT PRIMARY KEY,
    warehouse_id INT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity_change INT NOT NULL,  -- positive = inbound, negative = outbound
    reason TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Indexing Strategy
`stock_movements(warehouse_id, product_id, created_at)` for audit trail and reconciliation queries; `stock_levels` primary key already supports the most common "current stock" lookup.

### Transactions
Every stock change is a transaction combining a `stock_movements` insert **and** the corresponding `stock_levels` update, at Serializable or row-locked isolation to prevent lost updates when multiple warehouse operations happen concurrently on the same product — structurally identical to the banking ledger pattern (Section 15.1), reinforcing that "inventory count" and "account balance" are the same underlying problem shape.

### Security
Role-based access per warehouse (a warehouse worker should only modify their own warehouse's stock — RLS); audit logging for all stock adjustments (shrinkage/loss investigation relies on this).

### Scaling Strategy
Moderate scale typically (bounded by warehouse and product count, not user count) — vertical scaling with read replicas for reporting/analytics usually sufficient; real-time stock-level queries must always hit the primary (or a synchronously-consistent replica) to avoid overselling from stale replica reads (Module 5.4's read-your-own-write concern, applied to inventory).

### Replication & HA
Active-Passive with synchronous or near-synchronous replication given the financial stakes of stock accuracy.

### Backup & DR
Standard PITR; stock_movements table serves as its own audit/reconciliation mechanism (similar to the banking ledger's dual role as both transactional record and audit trail).

### Monitoring
Reconciliation job comparing `SUM(stock_movements.quantity_change)` per product/warehouse against `stock_levels.quantity` — should always match; any drift indicates a bug or data integrity issue (directly mirroring the banking capstone's balance-reconciliation monitoring).

### Deployment Architecture
```
[Warehouse App] → [Inventory Service] → [(PostgreSQL - stock_levels, stock_movements)]
                                                │
                                    [Reporting Replica - analytics/dashboards]
```

## 15.10 Capstone: Payment Gateway

### Requirement Analysis
Entities: merchants, transactions, payment methods, refunds, settlements. The strictest requirements of any capstone here: PCI DSS mandatory, idempotency mandatory (network retries must never double-charge), strong consistency mandatory, extremely high audit/compliance bar — synthesizing the Stripe/PayPal case studies from Module 12.7-12.8 directly.

### ER Diagram
```
Merchant ──1:N── Transaction ──1:N── Refund
Transaction ──N:1── PaymentMethod (tokenized, never raw card data)
```

### Schema Design
```sql
CREATE TABLE transactions (
    transaction_id BIGINT PRIMARY KEY,
    idempotency_key TEXT NOT NULL UNIQUE,  -- prevents duplicate processing on retry
    merchant_id BIGINT NOT NULL,
    amount NUMERIC(12,2) NOT NULL,
    status TEXT NOT NULL DEFAULT 'pending',
    payment_token TEXT NOT NULL,  -- tokenized reference, NEVER raw card data (PCI DSS)
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE refunds (
    refund_id BIGINT PRIMARY KEY,
    transaction_id BIGINT NOT NULL REFERENCES transactions(transaction_id),
    amount NUMERIC(12,2) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Indexing Strategy
Unique index on `idempotency_key` is the single most important index in this entire schema — it's the mechanism that makes retried requests safe (an `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING`-style pattern returns the existing result instead of double-processing).

### Transactions
Every payment operation is wrapped in a transaction that first checks the idempotency key, then processes the charge, at Serializable isolation given the zero-tolerance for double-charging or race-condition-induced inconsistency.

### Security
The strictest section of any capstone here: full PCI DSS compliance (Module 2.12.3) — card data is tokenized via a payment processor/vault and never stored raw; encryption at rest and in transit mandatory; exhaustive audit logging of every transaction state change; network segmentation isolating this system from the rest of the company's infrastructure.

### Scaling Strategy
Moderate write volume relative to social/chat-scale systems, but every single write is high-stakes — the design bias is toward **correctness and auditability over raw throughput optimization**; horizontal scaling via merchant-based sharding is feasible since transactions rarely span merchants.

### Replication & HA
Synchronous replication mandatory (near-zero RPO — Module 6 recap), automatic failover with extremely conservative promotion criteria (never promote a standby that might be missing a committed transaction).

### Backup & DR
PITR mandatory with very tight RPO targets; geo-redundant DR site; backups encrypted and access-restricted even more tightly than production (Module 2/7 recap); regular DR drills are typically a compliance requirement, not optional.

### Monitoring
Idempotency-conflict rate (a spike could indicate a client-side retry storm or an upstream network issue); transaction success/failure rate as a real-time business-critical dashboard; reconciliation jobs comparing internal transaction records against the external payment processor's records (a cross-system consistency check beyond what any single database can guarantee alone).

### Deployment Architecture
```
[Merchant App] → [API Gateway - rate limited] → [Payment Service]
                                                        │
```

### 15.11 Cross-Capstone Pattern Recognition

A key interview skill is recognizing that these ten "different" systems share a small number of **recurring underlying patterns**:

| Pattern | Appears In |
|---|---|
| Ledger/balance consistency (never lose money/inventory) | Banking, Inventory, Payment Gateway |
| Hot-row/hot-partition avoidance via sharded counters | Social Media (likes), Ride-Sharing (matching) |
| High-frequency, low-durability data kept OUT of the primary relational store | Food Delivery (location), Ride-Sharing (location), Video Streaming (watch progress) |
| Booking/scheduling consistency (no double-booking) | Hospital (appointments), Ride-Sharing (driver matching) |
| Idempotency keys preventing duplicate processing | Payment Gateway (explicitly), applicable to any retry-prone system |
| Polyglot persistence (relational core + specialized stores) | E-commerce, Food Delivery, Video Streaming, Social Media, Chat |
| Fan-out trade-offs (write-time vs. read-time computation) | Social Media (feed generation) |
| Strict compliance shaping architecture before performance | Banking, Hospital, Payment Gateway |

**Interview takeaway:** When facing a novel "design X" question, first ask **which of these recurring patterns does this system resemble**, then apply the corresponding, already-reasoned-through solution rather than starting from zero.
