## 📍 Why Logging Comes Before Everything Else

Think back to Module 1's core question: *"The power just went out mid-write. Is my data still correct?"* The only reason a DBMS can even attempt to answer that question is because, before the power went out, it had already been quietly writing down a **history of everything that happened** — a journal, a diary, a black box flight recorder. That journal is the **log**.

Without logging, "recovery" isn't really recovery — it's guessing. With logging, recovery becomes a deterministic, provable, replayable process. This module is entirely about how that journal is structured.

---

## 3.1 What is Logging?

### Definition

**Logging** is the practice of recording every change made to the database — before or as it happens — into a separate, sequential, append-only file called the **log** (also called the **transaction log**, **write-ahead log**, or **redo log**, depending on the engine).

Each entry in this file is called a **log record**, and it describes one discrete piece of information: "transaction T5 changed page P12 from value X to value Y."

### Why Logging Exists

Directly building on Module 1's durability discussion: because data pages live in fast-but-volatile RAM before eventually reaching slow-but-persistent disk, the DBMS needs *some* durable trace of what happened that doesn't require the full data page to be flushed immediately. The log is that trace — small, sequential, and cheap to write durably, compared to scattered random writes across large data pages.

### Real-Life Analogy

Think of a ship's **logbook** (this is literally where the term "log" in computing comes from!). A ship's captain doesn't repaint the entire ship's hull to record "we changed course at 3 PM." Instead, they write one line in the logbook: *"15:00 — course changed from 090° to 120°, reason: storm avoidance."* If the ship's systems ever need to be reconstructed or audited, the logbook alone tells the complete story, chronologically, without needing to inspect the ship's physical state at every moment.

A database's transaction log works exactly the same way: a compact, chronological, append-only record of every meaningful change.

### The Core Property: Sequential and Append-Only

This is one of the most important — and most interview-tested — properties of the log:

> The log is **never modified in place**. New records are only ever **appended** to the end.

This matters enormously for performance: sequential writes to disk are dramatically faster than random writes (especially on traditional spinning disks, though the benefit persists even on SSDs due to reduced write amplification and simpler flush guarantees). It also matters for **correctness**: an append-only structure is easy to reason about — you always know exactly where "the truth so far" ends.

```
Log File (append-only, grows left to right over time)

┌────────┬────────┬────────┬────────┬────────┬────────┬─────►
│ LSN=1  │ LSN=2  │ LSN=3  │ LSN=4  │ LSN=5  │ LSN=6  │  ...new records
│ T1 beg │ T1:upd │ T2 beg │ T1 cmt │ T2:upd │ T2 cmt │  appended here
└────────┴────────┴────────┴────────┴────────┴────────┴─────►
                                                              ▲
                                                     "Tail" of the log —
                                                     grows as new writes occur
```

## 3.2 Log Records

### What is a Log Record?

A **Log Record** is the atomic unit of the log — a single, self-contained entry describing one specific event in the database's history. Log records are the "sentences" written in the ship's logbook.

### What Information Does a Log Record Contain?

While exact formats vary by engine (explored in Module 11), a typical log record contains:

| Field | Meaning |
|---|---|
| **LSN** | Log Sequence Number — a unique, monotonically increasing identifier for this record (Section 3.3) |
| **Transaction ID** | Which transaction generated this record |
| **Type** | What kind of event this is (update, commit, abort, checkpoint, CLR, etc.) |
| **Page ID** | Which data page was affected (for update records) |
| **Before Image (Old Value)** | The value before the change — needed for **undo** |
| **After Image (New Value)** | The value after the change — needed for **redo** |
| **Previous LSN** | A pointer to this transaction's previous log record, forming a backward chain (crucial for efficient undo — detailed in Module 7) |

### Types of Log Records

- **Update Record:** Describes a single data modification (insert, update, or delete), typically containing both before and after images.
- **Commit Record:** Marks that a transaction has successfully finished and should be considered permanent (Section 3.6).
- **Abort Record:** Marks that a transaction was rolled back (Section 3.7).
- **Compensation Log Record (CLR):** A special record generated *during* undo itself, recording "I am undoing this change" (Section 3.8 — this one trips up a lot of learners, so we give it a full section).
- **Checkpoint Record:** Marks a checkpoint event, bounding how far back recovery needs to look (fully covered in Module 6).

### Example Log Record (Simplified, Conceptual Format)

```
LSN: 104
TxnID: T7
Type: UPDATE
PageID: P22
Offset: 40
BeforeImage: balance = 1500
AfterImage:  balance = 1000
PrevLSN: 101   (T7's previous log record)
```

This single record tells the recovery algorithm everything it needs: *if T7 committed, redo means "set balance to 1000 on page P22." If T7 didn't commit, undo means "set balance back to 1500 on page P22."*

### Real-Life Analogy

Each log record is like a single receipt from a cash register. One receipt says "sold 1 item, ₹500, at 3:04 PM, cashier #2." You don't need to re-inspect the entire store's inventory to know what happened at 3:04 PM — the receipt alone tells the whole story of that one event.

## 3.3 Log Sequence Number (LSN)

### What is an LSN?

A **Log Sequence Number (LSN)** is a unique, strictly increasing identifier assigned to every log record, in the exact order it was written. Think of it as a page number in the ship's logbook — LSN 1 comes before LSN 2, which comes before LSN 3, forever.

### Why LSNs Exist

LSNs give the recovery system (and various other DBMS internals) a precise, comparable notion of **"before" and "after"** in the database's history. Without LSNs, you'd only have a pile of log records with no reliable way to determine their exact order or to efficiently locate a specific point in the log.

### What LSNs Are Used For

- **Ordering:** Determining which change happened first.
- **Page versioning:** Each data page can store the LSN of the last log record that modified it (often called the page's **PageLSN**). This lets the recovery algorithm instantly tell whether a given log record's change is already reflected on disk or still needs to be redone — a cornerstone idea in ARIES (Module 7).
- **Checkpoint bookkeeping:** Checkpoints record "recovery only needs to start from LSN X onward," dramatically shrinking recovery time (Module 6).
- **Chaining transactions:** Each log record can store the LSN of the same transaction's previous record (`PrevLSN`), forming a linked list that undo can walk backward through, efficiently, without scanning the entire log.

### Visual: LSN Ordering and PrevLSN Chains

```
LSN:        1        2        3        4        5        6
            │        │        │        │        │        │
Record:  T1 begin  T1:upd   T2 begin  T1:upd   T1 commit  T2:upd
                    (PrevLSN=1)        (PrevLSN=2)         (PrevLSN=3)

T1's chain: LSN 4 ──► PrevLSN 2 ──► PrevLSN 1 (begin)
T2's chain: LSN 6 ──► PrevLSN 3 (begin)
```

Notice how T1's records (LSN 2, 4, 5) and T2's records (LSN 3, 6) are **interleaved** in the log — this is completely normal and expected, because multiple transactions run concurrently (a direct callback to Part 6's concurrency control). The `PrevLSN` chain lets recovery reconstruct each transaction's individual history even though their records are physically mixed together.

### Real-Life Analogy

LSNs are like sequentially numbered pages in a logbook — page 104 always comes after page 103, no ambiguity, no guessing. Even if entries about "Ship A" and "Ship B" are mixed together on different pages, you can always tell their exact chronological order at a glance.

## 3.4 Log Buffer

### What is the Log Buffer?

The **Log Buffer** is a small area of volatile memory (RAM) where new log records are first written before being flushed to the persistent log file on disk. It exists for exactly the same performance reason that data pages live in a buffer pool: writing to RAM is orders of magnitude faster than writing to disk, and batching many small writes into fewer, larger disk flushes is far more efficient.

### Why the Log Buffer Exists

If every single log record triggered an immediate, individual disk write, performance would collapse under concurrent workloads — imagine forcing a physical disk I/O for every single row update in a transaction, one at a time. Instead:

1. Log records accumulate quickly in the in-memory log buffer.
2. Periodically — and crucially, **whenever a transaction commits** — the buffer's contents (or the relevant portion) are flushed to durable storage in one efficient batch write.

### The Critical Rule

> **A transaction cannot be considered committed until its commit log record has been flushed from the log buffer to durable storage.**

This single rule is the seed of the entire Write-Ahead Logging protocol you'll study in full in Module 4. If the DBMS acknowledged "commit successful" to the client *before* flushing, and then the machine lost power, the commit record itself could be lost from volatile memory — and upon restart, the DBMS would have no way of knowing that transaction was ever supposed to be permanent. Durability would be broken.

### Log Buffer Flush Triggers

| Trigger | Description |
|---|---|
| **Transaction commit** | Mandatory, synchronous flush of at least that transaction's records |
| **Buffer full** | The in-memory buffer reaches capacity and must be flushed to make room |
| **Periodic timer** | Many engines flush every N milliseconds regardless, to bound exposure |
| **Checkpoint** | A checkpoint operation forces relevant log records to disk (Module 6) |
| **Explicit force** | The recovery manager or another subsystem explicitly requests a flush |

### Visual: Log Buffer to Disk Flow

```
   Transactions writing log records
            │
            ▼
   ┌─────────────────────┐
   │     LOG BUFFER        │   (Volatile RAM — fast, but lost on crash)
   │  [LSN5][LSN6][LSN7]   │
   └──────────┬────────────┘
              │  flush (triggered by commit, buffer-full, timer, or checkpoint)
              ▼
   ┌─────────────────────┐
   │   PERSISTENT LOG FILE │   (Durable disk storage — survives crash)
   │  [LSN1]...[LSN7]      │
   └────────────────────────┘
```

### Group Commit — A Performance Optimization Preview

Because flushing to disk has a fixed overhead per flush operation (not just per byte), many engines delay a commit's flush *very slightly* to see if other transactions are also about to commit, then flush all their commit records together in a **single disk write**. This technique, called **Group Commit**, dramatically increases throughput under concurrent load and is explored in depth in Module 12 (Performance Considerations).

## 3.5 Persistent Log

### What is the Persistent Log?

The **Persistent Log** (or **durable log**) is the on-disk file (or set of files/segments) where flushed log records permanently live, surviving crashes, restarts, and power loss. This is the actual "ship's logbook" itself — not the temporary notepad (log buffer) the captain scribbles on before copying entries in.

### Key Properties

- **Append-only:** New records are always added at the end; existing records are (almost) never modified.
- **Sequential on disk:** Physically laid out in the order records were written, which is what makes writes to it fast.
- **Segmented:** In practice, the log isn't one infinitely growing file — it's broken into fixed-size **segments** (e.g., PostgreSQL's 16 MB WAL segments by default) that can be individually archived, recycled, or deleted once no longer needed (fully explored in Modules 4, 6, 9, and 11).
- **The single source of truth for recovery:** Everything the Analysis/Redo/Undo phases (Module 7) do is driven entirely by reading this file.

### Why It Must Be Durable Before Data Pages

This connects directly back to the WAL principle (fully detailed next module): the persistent log must contain a record of a change **before** the corresponding data page's modification is allowed to become durable. If this order were reversed, a crash between the two writes could leave a data page changed on disk with **no corresponding log record** to explain or undo it — an unrecoverable, inconsistent state.

## 3.6 Commit Record

### What is a Commit Record?

A **Commit Record** is a special log record written when a transaction successfully finishes all its operations and requests to be made permanent via `COMMIT`.

### Why It's Special

The commit record is the **single most important record in the entire log**, because its presence or absence is literally the deciding factor in whether a transaction's changes are kept (redone) or discarded (undone) during recovery:

> **If a transaction's commit record made it to the persistent log before the crash → REDO its effects.**
> **If a transaction's commit record is missing from the persistent log → UNDO its effects.**

This is the fundamental litmus test the Analysis phase of ARIES (Module 7) applies to every transaction it finds in the log.

### What Happens When `COMMIT` is Issued

```
Client: COMMIT;
   │
   ▼
1. DBMS writes a COMMIT log record to the log buffer
   │
   ▼
2. DBMS forces (flushes) the log buffer up to and including
   this COMMIT record to durable storage
   │
   ▼
3. ONLY NOW does the DBMS acknowledge "commit successful" to the client
```

This three-step sequence is non-negotiable in any durability-respecting DBMS — skipping step 2, or acknowledging the client before step 2 completes, is a durability bug.

## 3.7 Abort Record

### What is an Abort Record?

An **Abort Record** is a log record written when a transaction is rolled back — either because the application explicitly issued `ROLLBACK`, or because the DBMS itself aborted it (e.g., due to a deadlock, a constraint violation, or a crash-recovery undo).

### Why It's Needed

Just as the commit record proves "this transaction is permanent," the abort record proves "this transaction's effects must never be considered part of the database's history — and if recovery is interrupted partway through undoing it, recovery must know to finish the job (or know it's already done)." It marks the definitive end of a transaction's story in the log, just via a different ending than commit.

### Abort Record in the Recovery Timeline

```
LSN 10: T5 BEGIN
LSN 11: T5 UPDATE (balance 1000 → 800)
LSN 12: T5 UPDATE (balance2 500 → 700)
LSN 13: T5 ABORT   ← rollback requested
LSN 14: CLR for LSN 12 (undoing balance2 back to 500)
LSN 15: CLR for LSN 11 (undoing balance back to 1000)
LSN 16: T5 END      ← undo complete, transaction fully closed
```

Notice the **CLR** records appearing during the undo — which brings us to one of the most conceptually important (and most confused) topics in this entire module.

## 3.8 Compensation Log Record (CLR)

### What is a CLR?

A **Compensation Log Record (CLR)** is a special type of log record written **while undoing** a transaction's changes — it records the fact that an undo operation itself took place, essentially saying: *"I am now compensating for (reversing) the change originally described in log record LSN=X."*

### Why CLRs Exist — The Idempotency Problem

Recall from Module 1's edge cases: a recovery algorithm must be **idempotent** — safe to run repeatedly, even if the system crashes *during* recovery itself (Module 2 and this callback are directly connected). CLRs are the mechanism that makes this possible.

Consider this scenario without CLRs:

1. System crashes. T5 was uncommitted, so recovery begins undoing its changes.
2. Recovery undoes LSN 12 (balance2 back to 500).
3. **The system crashes again**, right in the middle of recovery!
4. On restart, recovery starts over from the log. But how does it know LSN 12 was already undone? If it blindly undoes LSN 12 *again*, using the same before-image, that's probably still safe by luck here — but in general, **re-undoing an already-undone change can corrupt data**, especially for operations that aren't simple value overwrites (e.g., decrementing a counter twice instead of once).

With CLRs, the answer is clean and precise:

1. When recovery undoes LSN 12, it writes a **CLR** to the log recording "LSN 12 has now been undone."
2. If the system crashes again mid-recovery, the *next* recovery attempt's Analysis phase sees this CLR in the log and knows: *"LSN 12 was already undone — skip it, don't undo it again."*

> 💡 **Interview Insight:** This is one of the most commonly asked "explain like I'm a senior engineer" ARIES questions: *"Why does ARIES write log records even during undo, and how does this guarantee idempotency?"* The answer is precisely the CLR mechanism described above. We'll revisit this with a full step-by-step numeric example in Module 7.

### Key Property: CLRs Are Never Undone Themselves

A CLR redoes what it says (if needed during a future redo pass) but is **never itself the target of a further undo** — undoing an undo would create an infinite loop. CLRs typically point back (via a special field, often called `UndoNextLSN`) to the *next* record that still needs undoing in that transaction's chain, allowing undo to skip over regions of the log that are already known to be handled.

### Visual: CLR in Action

```
Normal log record (forward operation):
   LSN 12: T5 UPDATE balance2: 500 → 700   [Undo this = set back to 500]

CLR (compensating for LSN 12, written during undo):
   LSN 14: CLR for LSN 12: balance2: 700 → 500   [This CLR itself is never undone]
```

## 3.9 Checksum

### What is a Checksum?

A **Checksum** is a small, computed value derived from the contents of a log record (or a data page) that allows the DBMS to detect whether that record has been **corrupted or partially written** — for example, due to the torn-page problem introduced in Module 2.

### How It Works (Conceptually)

When a log record is written, the DBMS computes a checksum (using an algorithm like CRC32 or similar) over its contents and stores that checksum alongside the record. When the record is later read back — especially during crash recovery — the DBMS recomputes the checksum from the stored bytes and compares it to the stored checksum value.

- **Match:** The record is intact and trustworthy.
- **Mismatch:** The record was corrupted (e.g., a partial write during a power failure) — and critically, this tells the recovery algorithm **exactly where to stop reading the log**, because everything at or after this point is unreliable.

### Why Checksums Matter for Recovery Specifically

Recall from Module 2: a power failure can leave a *partial* write at the very tail of the log — the last record being written when power died. Without a checksum, the recovery algorithm might try to interpret this garbage as a legitimate log record, potentially causing bizarre and dangerous behavior. With a checksum, the corrupted trailing record is cleanly detected and discarded, and recovery proceeds confidently using only the verified, intact portion of the log.

### Real-Life Analogy

A checksum is like a tamper-evident seal on a courier package. You don't need to open and inspect every item inside to know whether the package was tampered with in transit — the seal itself tells you instantly and cheaply.

## 3.10 Log Format

### What is Log Format?

**Log Format** refers to the specific, engine-defined binary or structured layout used to encode log records on disk — field ordering, sizes, headers, and how records of different types are distinguished from one another.

### Why Log Format Design Matters

A well-designed log format must balance several competing goals:

- **Compactness:** Smaller records mean less I/O and less disk space consumed — directly affecting the performance overhead discussed in Section 3.4 and expanded in Module 12.
- **Self-describing structure:** Each record typically includes its own length and type, so the log reader can parse records sequentially without needing an external index.
- **Forward compatibility:** Engines must often support reading log formats written by slightly older versions of themselves (important during version upgrades).
- **Physiological logging support (preview of Module 7):** Modern engines like those implementing ARIES use a hybrid logging style — physical enough to allow byte-level redo, logical enough to keep records compact — which places specific demands on format design.

### Simplified Generic Log Record Layout

```
┌─────────┬─────────┬──────┬─────────┬──────────┬───────────┬──────────┬──────────┐
│  LSN     │ PrevLSN  │ TxnID│  Type    │  PageID   │  Offset    │ Before/  │ Checksum │
│ (8 bytes)│ (8 bytes)│      │(1 byte)  │           │            │  After   │          │
└─────────┴─────────┴──────┴─────────┴──────────┴───────────┴──────────┴──────────┘
```

This is a simplified, conceptual layout for teaching purposes — real engines (PostgreSQL's XLOG record format, InnoDB's redo log record format) have additional fields for things like resource managers, record-specific payloads, and backup-block indicators, which we cover with engine-specific detail in Module 11.

## 3.11 Advantages of the Logging Approach

- **Small, fast writes:** Logging a change is far cheaper than immediately persisting an entire modified data page.
- **Sequential I/O:** Append-only writes are dramatically faster than the random I/O pattern of writing scattered data pages directly.
- **Complete history:** Enables not just crash recovery, but also replication, point-in-time recovery, and auditing — the same log often powers multiple features.
- **Precise, provable recovery:** LSNs, CLRs, and checksums together create a recovery process that is deterministic and mathematically reasoned about, not a best-effort guess.

## 3.12 Disadvantages / Costs

- **Every write now costs two writes:** once to the log, once (eventually) to the actual data page.
- **Storage growth:** Logs consume disk space continuously and must be actively managed (archived or discarded) — mismanagement can fill up disks and even halt the database.
- **Complexity:** Designing a correct log format, buffer management, and flush protocol is genuinely one of the harder parts of database engineering to get exactly right.

## 3.13 Best Practices

- Keep log files on fast, dedicated storage, separate from data files, both for performance and for the media-failure isolation reasoning from Module 2.
- Monitor log buffer flush frequency and size — too-frequent small flushes hurt throughput; too-large buffers increase the amount of potentially-lost work if a true, unrecoverable disaster strikes mid-buffer (though committed data is still always safe, per the commit-flush rule).
- Enable and never disable checksums on production systems, despite the small CPU overhead — the corruption-detection value is worth it.

## 3.14 Common Mistakes

- Assuming "data is in the buffer pool" means "data is safe" — only the **log record**, once flushed, provides that guarantee, not the data page itself.
- Confusing the log buffer (volatile) with the persistent log (durable) — a very common source of confusion for beginners, and a favorite interview clarifying question.
- Forgetting that CLRs exist and assuming undo is a "one-shot, un-logged" operation — in a correct ARIES-style system, undo *itself* generates new log records.

## 3.15 Edge Cases

- What happens if a checksum mismatch is found **not** at the very tail of the log, but somewhere in the middle? This typically indicates real corruption (not just a torn tail-write) and is treated far more seriously — often requiring backup restoration rather than simple recovery.
- Extremely long-running transactions generate enormous `PrevLSN` chains, which can slow down undo — this motivates checkpoint and buffer-management strategies covered in Modules 6 and 8.

## 3.16 PostgreSQL vs MySQL (InnoDB) vs Oracle — Logging Terminology

| Concept | PostgreSQL | MySQL (InnoDB) | Oracle |
|---|---|---|---|
| Log record identifier | LSN (e.g., `16/B374D848`) | LSN (64-bit integer) | SCN (System Change Number) + Redo byte address |
| Log file unit | WAL Segment (16 MB default) | Redo Log File (fixed size, circular) | Redo Log File (grouped into log groups) |
| Undo information | Stored via old row versions + WAL | Separate Undo Log (in Undo Tablespace) | Separate Undo Segments |
| Corruption detection | Per-record CRC checksum | Per-block checksum | Redo block checksums |

## 3.17 Chapter Summary

- **Logging** is the practice of recording every database change into a sequential, append-only file before/as it happens.
- **Log Records** are the atomic units of the log, containing before/after images, transaction ID, LSN, and a PrevLSN chain link.
- **LSNs** provide a strict, comparable ordering over all log records and underpin page versioning, checkpointing, and undo chaining.
- The **Log Buffer** holds records in fast volatile memory before they're flushed; the **Commit Rule** mandates that the commit record must be durably flushed before acknowledging commit to the client.
- The **Persistent Log** is the durable, on-disk, append-only source of truth recovery relies on entirely.
- **Commit Records** and **Abort Records** mark the definitive fate of a transaction.
- **CLRs** make undo idempotent — safe to interrupt and restart without corruption — by logging the act of undoing itself.
- **Checksums** protect against torn/corrupted records, especially at the log's tail after a power failure.
- **Log Format** design balances compactness, self-description, and compatibility.
