# Part 10 — Database Internals & Storage Engine Architecture

## Module 11: Database Metadata

> **Recap:** Module 1 introduced the Catalog/Metadata Manager as a component every other subsystem depends on. This module opens that box fully — how metadata is actually stored, queried, cached, and kept consistent as schemas evolve.

---

### 11.0 Why This Module Exists

Metadata is easy to overlook because it's "just bookkeeping" — but every single query you've traced through this Part touched it: the Parser validated column names against it, the Optimizer pulled statistics from it, the Executor used it to know column offsets and types. Understanding how metadata itself is stored and managed closes the loop on the entire architecture from Module 1.

---

### 11.1 What Is Database Metadata?

**Definition:** Metadata is **data about data** — schema definitions (tables, columns, types, constraints), object relationships (foreign keys, dependencies), access-control information (users, privileges), and statistical summaries of the actual data (row counts, value distributions) — everything the engine needs to know *about* a database's structure and characteristics, as distinct from the data itself.

**Why does it exist / what problem does it solve?** Every other component in Module 1's architecture is fundamentally *blind* without it:
- The Parser can't validate `SELECT name FROM users` without knowing `users` exists and has a `name` column.
- The Optimizer can't estimate that `WHERE status = 'active'` matches 5% of rows without stored statistics.
- The Executor can't correctly interpret raw tuple bytes (Module 2) without knowing the column types and their byte offsets/order.

**Real-life analogy:** A shipping company's inventory database — not the actual physical packages themselves, but the records describing what's in each package, its dimensions, its destination format requirements. Losing the physical packages is bad; losing (or corrupting) the *records describing* them is arguably worse, because it makes the packages themselves unusable/unfindable even if physically intact.

---

### 11.2 Catalog Tables (PostgreSQL: `pg_catalog`)

**What is it?** In PostgreSQL, metadata is stored as **ordinary tables** — `pg_class` (tables/indexes/sequences and other relation-like objects), `pg_attribute` (columns), `pg_index` (index definitions), `pg_constraint` (constraints), `pg_proc` (functions), and dozens more — all living in the `pg_catalog` schema.

**Why this design choice matters (a distinctly Postgres philosophy):** Because catalog tables are *just regular tables* (albeit special, system-managed ones), they can be queried with **ordinary SQL** — `SELECT * FROM pg_class WHERE relname = 'users';` works exactly like querying any user table. This is a deliberate architectural elegance: no separate, special-purpose metadata query language is needed; the same `SELECT`/`JOIN` machinery that handles user data handles metadata too.

**A concrete example — finding all columns of a table via raw catalog queries:**
```sql
SELECT a.attname AS column_name, t.typname AS data_type
FROM pg_attribute a
JOIN pg_class c ON a.attrelid = c.oid
JOIN pg_type t ON a.atttypid = t.oid
WHERE c.relname = 'employees' AND a.attnum > 0 AND NOT a.attisdropped;
```
(In practice, most users would use `\d employees` in `psql` or the standardized `information_schema` instead — but knowing the raw catalog exists underneath is valuable internals knowledge.)

**Key catalog tables to know by name (high interview value):**

| Table | Contains |
|---|---|
| `pg_class` | Tables, indexes, sequences, views — anything "relation-like" |
| `pg_attribute` | Column definitions for every relation |
| `pg_index` | Index-specific metadata (which columns, uniqueness, etc.) |
| `pg_constraint` | Primary keys, foreign keys, check constraints |
| `pg_statistic` | Raw statistics data used by the optimizer (populated by `ANALYZE`) |
| `pg_type` | All data types, built-in and user-defined |
| `pg_namespace` | Schemas |

**Interview importance:** ⭐⭐⭐⭐ Knowing that Postgres catalogs are queryable SQL tables (not a separate special format) — and being able to name `pg_class`/`pg_attribute` specifically — is a strong, easy-to-verify signal of real Postgres experience.

### 11.3 Information Schema

**What is it?** A **standardized** (SQL-standard-defined) set of views providing metadata in a portable, engine-agnostic format — `information_schema.tables`, `information_schema.columns`, `information_schema.key_column_usage`, and similar — implemented by essentially every major relational database (Postgres, MySQL, SQL Server, and others), all exposing largely the same view names and column names.

**Why does it exist alongside engine-specific catalogs?** Portability. Application code, ORMs, and database-management tooling that needs to introspect schema information can query `information_schema` views and get broadly consistent results regardless of *which* underlying database engine is running — insulating that code from each engine's own internal catalog table naming and structure (`pg_catalog` vs. InnoDB's data dictionary internals).

**Relationship to the underlying engine-native catalog:** `information_schema` views are typically implemented as a **thin layer on top of** the engine's actual native metadata storage — in Postgres, `information_schema.columns` is effectively a view built from joins across `pg_attribute`, `pg_class`, `pg_type`, and others; it doesn't store anything independently, it's a standardized *presentation* of the same underlying facts.

**Trade-off:** `information_schema` is more portable but sometimes less complete/less performant than querying the native catalog directly for engine-specific details (e.g., Postgres-specific index storage parameters aren't part of the SQL standard and thus aren't exposed via `information_schema` — you'd need `pg_catalog` directly for those).

**Interview importance:** ⭐⭐⭐ Knowing the relationship (thin standardized layer over native catalogs, not independently stored) is the key insight worth demonstrating.

### 11.4 System Catalog (InnoDB / MySQL's Data Dictionary — Recap + Detail)

Already introduced in Module 4, Section 4.13 — here in fuller context alongside Postgres's approach for direct comparison.

**Pre-MySQL 8.0:** Metadata was scattered across non-transactional `.frm` files (one file per table, storing its definition) on disk, plus various InnoDB-internal-only structures for storage-engine-specific details — meaning a `CREATE TABLE` or `ALTER TABLE` wasn't a single atomic, crash-safe transaction the way a Postgres catalog update naturally is (since Postgres catalog changes are just ordinary transactional row changes to ordinary tables).

**MySQL 8.0+: the unified transactional Data Dictionary.** All metadata now lives in **InnoDB tables themselves** (not flat `.frm` files), meaning DDL operations benefit from the same transactional guarantees as any other InnoDB table modification — a genuinely significant reliability improvement, eliminating a historically real class of "half-applied schema change after a crash" problems.

**Exposure to users:** Via `information_schema` (the standardized layer, Section 11.3) — MySQL does not expose an equivalent to Postgres's directly-queryable `pg_catalog` raw tables in quite the same open, documented way; `information_schema` is the primary sanctioned interface.

### 11.5 Statistics Tables (Recap + Formalized)

**What is it?** The specific subset of metadata capturing **data distribution characteristics** — not the schema's structure, but facts about the *actual current contents* — row counts, most-common-values lists, histograms, correlation between physical storage order and logical column order, null fractions, and distinct-value estimates.

**PostgreSQL: `pg_statistic` (and its more readable view, `pg_stats`)** — populated by `ANALYZE` (run manually or automatically via Autovacuum, Module 3), consumed directly by the cost-based optimizer (Module 1, Section 1.4.2) to estimate selectivity and choose plans.

**MySQL/InnoDB: persistent InnoDB statistics tables** (`mysql.innodb_table_stats`, `mysql.innodb_index_stats`) — by default automatically updated based on table change thresholds, though manual `ANALYZE TABLE` can force a refresh; historically MySQL also supported non-persistent, in-memory-only statistics estimated on the fly, though persistent statistics (stored durably, surviving restarts) are the modern default and generally preferred for plan stability.

**Why stale statistics are a recurring real-world problem (tying back to Module 1's optimizer discussion):** A bulk data load, a sudden shift in data distribution, or simply statistics that haven't been refreshed after significant growth can cause the optimizer to make badly wrong cardinality estimates — leading directly to poor plan choices (e.g., choosing a sequential scan when an index would now be far better, or vice versa) even though the *engine itself* is functioning correctly; the problem is purely in the metadata being out of date relative to reality.

**Interview importance:** ⭐⭐⭐⭐⭐ "Why would `ANALYZE`/updated statistics fix a slow query without any schema or index change?" is an extremely common, high-value practical question.

### 11.6 Metadata Caching

**What is it?** Because metadata is consulted on essentially *every single query* (Parser, Optimizer, and Executor all need it — Module 1), re-reading catalog tables from the Buffer Pool/disk on every single query would itself be wasteful overhead — so engines maintain dedicated, fast, in-memory caches of frequently-used metadata.

**PostgreSQL's relcache and syscache:**
- **relcache (relation cache):** Per-backend cached copies of `pg_class`-derived information for relations that backend has recently used, avoiding repeated catalog table lookups for the same table across multiple queries within a connection's lifetime.
- **syscache (system cache):** A more general-purpose cache for individual catalog tuple lookups (e.g., "look up this specific `pg_type` row by OID"), backed by an internal hash-table-like structure for fast repeated access.

**Why caching metadata specifically requires careful invalidation:** Unlike caching arbitrary query results (which can often tolerate some staleness), metadata caches **must** be correctly invalidated the moment a schema change occurs (`ALTER TABLE`, `DROP INDEX`, etc.) — a backend continuing to use a stale cached column list or index definition after a concurrent schema change could produce outright incorrect query results or crashes, not just suboptimal ones. This makes metadata cache invalidation a correctness-critical mechanism, not merely a performance optimization detail.

**InnoDB's Data Dictionary Cache:** Similarly maintains an in-memory cache of frequently-accessed table/index definitions from the unified transactional Data Dictionary (Section 11.4), avoiding repeated reads from the underlying InnoDB system tables for every query — with analogous invalidation requirements on DDL.

**Interview importance:** ⭐⭐⭐⭐ "Why does metadata need to be cached, and what happens if that cache becomes stale after a schema change?" tests genuine depth beyond surface-level catalog knowledge.

### 11.7 Dependency Tracking

**What is it?** The mechanism by which a database engine tracks **relationships between objects** — which views depend on which tables, which foreign keys reference which primary keys, which functions reference which types — specifically so that dropping or altering an object can either be correctly blocked (if dependents would break) or correctly cascaded (if the user explicitly requests `CASCADE`).

**Why does it exist?** Without dependency tracking, `DROP TABLE users;` could silently leave a `VIEW active_users AS SELECT * FROM users` referencing a now-nonexistent table, only to fail confusingly the next time someone queries that view — dependency tracking allows the engine to catch this *at drop time* instead, either refusing the drop (default, safe behavior) or explicitly cascading it (`DROP TABLE users CASCADE;`, which would also drop the dependent view, if the user explicitly opts into that).

**PostgreSQL's `pg_depend`:** A catalog table explicitly recording dependency edges between database objects — every view-on-table, every foreign-key-to-referenced-table, every function-using-a-type relationship is a recorded row here, queried whenever a `DROP` (or certain `ALTER`) operations need to check for dependents.

**Interview importance:** ⭐⭐⭐ A good "have you actually hit this in practice" question — most engineers have encountered a `DROP TABLE` failing due to a dependent view/foreign key at some point; connecting that lived experience to `pg_depend` specifically shows real depth.

### 11.8 PostgreSQL vs. MySQL — Metadata Summary

| Aspect | PostgreSQL | MySQL (InnoDB) |
|---|---|---|
| Native metadata storage | `pg_catalog` — ordinary, directly SQL-queryable tables | Unified transactional Data Dictionary (8.0+), stored in InnoDB tables internally, not directly exposed the same way |
| Pre-modern-version legacy | N/A (has always used transactional catalog tables) | Pre-8.0: non-transactional `.frm` files — a real historical pain point |
| Standardized cross-engine access | `information_schema` (thin layer over `pg_catalog`) | `information_schema` (primary sanctioned interface) |
| Statistics storage | `pg_statistic` / `pg_stats`, populated by `ANALYZE` | `mysql.innodb_table_stats` / `innodb_index_stats`, auto-updated or via `ANALYZE TABLE` |
| In-memory metadata caching | relcache (per-relation) + syscache (general catalog tuple cache) | Data Dictionary Cache |
| Dependency tracking | `pg_depend` (explicit, queryable dependency graph) | Enforced via foreign key/view mechanisms, less exposed as a directly queryable unified graph in the same explicit way |

### 11.9 Advantages, Disadvantages, Best Practices

**Advantages of the "metadata as ordinary transactional data" philosophy (both engines, to varying historical degrees):**
- DDL changes benefit from the same atomicity/crash-safety guarantees as any other transactional change
- Metadata can be queried using the same familiar SQL tools as regular data (especially true in Postgres's `pg_catalog` design)

**Disadvantages:**
- Metadata caching, while necessary for performance, adds real invalidation complexity — a source of genuinely subtle bugs historically in any sufficiently complex database engine's development
- Statistics, being a *summary* of data rather than the data itself, can drift out of sync with reality between refreshes — an inherent staleness risk that must be actively managed (Autovacuum's `ANALYZE` bundling; InnoDB's auto-statistics thresholds)

**Best practices:**
- After large bulk data loads or significant data distribution shifts, explicitly run `ANALYZE` (Postgres) or `ANALYZE TABLE` (MySQL) rather than waiting for automatic thresholds, if query performance immediately after the load matters
- Understand `information_schema` vs. native catalog trade-offs — use `information_schema` for portable tooling, native catalogs (`pg_catalog`) when you need engine-specific detail not exposed by the standard
- Be deliberate about `CASCADE` drops — dependency tracking exists precisely to make you *stop and think* before an operation with wider blast radius than intended

**Common mistakes:**
- Assuming statistics are always current — a very common root cause of "the query plan doesn't make sense" investigations that's purely a metadata-staleness issue, not a genuine query or index design problem
- Not realizing `information_schema` queries can sometimes be *slower* than native catalog queries for the same logical information, due to the additional view/join layer — relevant for tooling built to introspect large schemas frequently

### 11.10 Chapter Summary

- Metadata (schema definitions, statistics, dependencies) is the information every other engine component (Parser, Optimizer, Executor — Module 1) depends on to function correctly.
- PostgreSQL stores metadata as **ordinary, directly SQL-queryable catalog tables** (`pg_class`, `pg_attribute`, and others in `pg_catalog`); MySQL, since 8.0, stores it in a **unified transactional Data Dictionary**, a major improvement over the pre-8.0 non-transactional `.frm` file approach.
- `information_schema` provides a **standardized, portable, engine-agnostic** view of metadata, implemented as a thin layer over each engine's native storage — not an independent source of truth.
- **Statistics** (a distinct subset of metadata, capturing actual data distribution) directly feed the query optimizer and are a very common, purely-metadata-level root cause of unexpectedly poor query plans when stale.
- **Metadata caching** (relcache/syscache in Postgres, Data Dictionary Cache in InnoDB) is necessary for performance but requires correctness-critical invalidation on any DDL change.
- **Dependency tracking** (`pg_depend` in Postgres) prevents silently breaking dependent objects (views, foreign keys) when dropping or altering a referenced object.

### 11.11 Cheat Sheet

```
Metadata = data ABOUT data: schema, stats, dependencies, privileges

PostgreSQL catalog: pg_catalog — ORDINARY, SQL-queryable tables
  pg_class (relations) | pg_attribute (columns) | pg_index | pg_constraint
  pg_statistic/pg_stats (stats, via ANALYZE) | pg_type | pg_depend (dependencies)

MySQL/InnoDB: unified transactional Data Dictionary (8.0+)
  BEFORE 8.0: non-transactional .frm files (real historical pain point)
  Statistics: mysql.innodb_table_stats / innodb_index_stats

information_schema = STANDARDIZED, cross-engine, thin layer over native catalog
  (NOT an independent source of truth — just a portable presentation)

Metadata Caching:
  PostgreSQL → relcache (per-relation) + syscache (general catalog tuples)
  InnoDB     → Data Dictionary Cache
  → MUST be invalidated on DDL — correctness-critical, not just perf

Dependency Tracking: pg_depend (PG) → blocks/cascades DROP based on dependents

Stale statistics = classic root cause of "optimizer picked a bad plan"
  Fix: manual ANALYZE / ANALYZE TABLE after bulk loads or big data shifts
```
