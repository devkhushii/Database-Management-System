# Part 8: Query Processing & Query Optimization
## Module 2: Query Optimizer

> **Prerequisite check:** This module assumes you've completed Module 1 (Query Processing Fundamentals). You should be comfortable with Query Trees, relational algebra notation (σ, π, ⋈), and the idea that a Logical Plan describes *what* to do while a Physical Plan describes *how*.

---

## 2.0 Why This Module Exists

At the end of Module 1, we had a rewritten **Query Tree** — a logically correct, simplified representation of the query. But a query tree alone doesn't tell the database *how* to physically execute each operation. For a single query like:

```sql
SELECT * FROM orders o JOIN customers c ON o.cust_id = c.id WHERE c.country = 'IN';
```

There could be **dozens of physically different ways** to compute the exact same result:
- Scan `orders` first or `customers` first?
- Use a sequential scan or an index scan on each?
- Join using Nested Loop, Hash Join, or Sort-Merge Join?

All of these produce the **same correct result** — but their execution time can differ by **orders of magnitude** (milliseconds vs. minutes on large tables). The **Query Optimizer** is the component responsible for picking the best one.

---

## 2.1 What is a Query Optimizer?

### Definition

A **Query Optimizer** is the database component that examines a logical query tree, considers multiple alternative ways to physically execute it (different access paths, join orders, join algorithms), estimates the **cost** of each alternative, and selects the plan expected to be **cheapest** to execute.

### Why It Exists

SQL guarantees a *correct* result regardless of how it's executed — but it says nothing about performance. Without an optimizer, the database (or worse, the application developer) would need to manually pick access paths and join strategies for every query — exactly the burden relational databases were built to remove. The optimizer automates the search for an efficient execution strategy so users only need to describe *what* they want.

### Real-Life Analogy

Think of a **GPS navigation app**. You tell it your destination (the "what") — it doesn't ask you to specify which roads to take. Internally, it considers many possible routes (highway vs. side streets, tolls vs. no tolls), estimates the cost (time, distance, traffic) of each, and picks the best one. If traffic conditions change (like table statistics changing), it may pick a different route next time. The **Query Optimizer is the GPS of the database** — the query tree is your destination, and the execution plan is the chosen route.

### Why Optimization Matters (The Stakes)

Consider a join between a 10-row table and a 10-million-row table:

| Strategy | Approx. Cost |
|---|---|
| Nested Loop Join, wrong table as outer, no index | Can be **catastrophically slow** — potentially billions of comparisons |
| Indexed Nested Loop Join, small table as outer | Extremely fast — ~10 index probes |
| Hash Join with proper memory | Fast, single pass over both tables |

The *same query*, depending on the plan chosen, can run in **10 milliseconds or 10 minutes**. This is why the optimizer is considered one of the most complex and critical components of any RDBMS — arguably more intellectually demanding to build than the storage engine itself.

## 2.2 Logical Plan vs. Physical Plan (Critical Distinction)

Before diving into optimization strategies, let's cement a distinction that interviewers probe constantly.

| | Logical Plan | Physical Plan |
|---|---|---|
| Describes | *What* operations to perform | *How* to perform them, concretely |
| Example node | "Join orders and customers" | "Hash Join(orders, customers)" or "Nested Loop Join with index" |
| Contains algorithm choice? | No | Yes |
| Contains access method? | No (just "read table X") | Yes (SeqScan vs IndexScan vs Bitmap Scan) |
| Analogous to | Relational algebra expression (σ, π, ⋈) | Concrete operator tree executed by the Iterator/Volcano engine (Module 1, §1.9) |

```
   LOGICAL PLAN                          PHYSICAL PLAN
   (what)                                (how — one of many possible choices)

      π (name)                              Project (name)
         │                                       │
      σ (age>18)                            HashJoin(id=cust_id)
         │                        →         /                  \
      ⋈ (id=cust_id)              IndexScan(orders,        SeqScan(customers)
       /        \                  cust_id idx)              Filter: age>18
   orders    customers
```

> 💡 **Key Insight:** One Logical Plan can map to **many** possible Physical Plans. The optimizer's job is to explore this space and pick the cheapest physical plan.

## 2.3 Rule-Based Optimization (RBO)

### Definition

**Rule-Based Optimization** chooses execution strategies using a **fixed set of heuristic rules** and priority rankings, **without** consulting actual data statistics (like table sizes or data distribution).

### How It Works

RBO assigns each possible access path a fixed **rank** (this is literally how Oracle's legacy RBO worked — it had ~15 hardcoded ranks, e.g., "unique index scan" always ranked better than "full table scan," regardless of actual table size). The optimizer picks the plan using the best-ranked available access path — always, blindly, regardless of whether the table has 10 rows or 10 billion rows.

### Example of RBO Ranking (Oracle's legacy system, illustrative)

| Rank | Access Path |
|---|---|
| 1 (best) | Single row by ROWID |
| 2 | Single row by unique/primary key index |
| 4 | Composite index unique scan |
| ... | ... |
| 15 (worst) | Full table scan |

### Why It Exists (Historically)

Early databases (1970s–1980s) lacked reliable statistics infrastructure or the compute budget to evaluate many plans at query time. Fixed heuristic rules were cheap to apply and "good enough" in an era of small, predictable datasets.

### Disadvantages (Why RBO Was Abandoned)

- **Blind to data reality:** An index scan is ranked "better" than a full scan *even when the index scan would touch 90% of the table* (at which point a sequential scan is actually faster due to less random I/O).
- **No adaptability:** Doesn't respond to changing data volume, skew, or distribution.
- **Data-size ignorance:** Treats a 100-row table identically to a 100-million-row table if the same access paths are available.

### Where RBO Still Matters Today

Pure RBO is largely **obsolete** in modern engines (Oracle deprecated its RBO starting Oracle 10g, though remnants of rule-based *heuristics* persist everywhere as a first-pass filter before cost-based search, e.g., "always push predicates down" is a rule-based heuristic used even in cost-based optimizers).

### Interview Importance: ⭐⭐⭐
Know that RBO existed historically, why it was abandoned, and that modern optimizers use it only as a lightweight heuristic layer, not as the primary decision mechanism.

## 2.4 Cost-Based Optimization (CBO)

### Definition

**Cost-Based Optimization** evaluates multiple candidate physical plans by estimating a numeric **cost** for each (based on statistics — table sizes, index selectivity, data distribution, I/O and CPU cost models) and selects the plan with the **lowest estimated cost**.

### Why It Exists

CBO exists to fix exactly what RBO couldn't do: **adapt to actual data**. Whether a sequential scan or index scan is faster genuinely *depends* on how many rows match a filter, how the data is distributed, how much memory is available, and current table sizes. CBO makes this decision using real (or estimated) numbers rather than fixed assumptions.

### How CBO Works (High-Level Pipeline)

```
┌───────────────────────────────────────────────────────────┐
│                  COST-BASED OPTIMIZATION                    │
└───────────────────────────────────────────────────────────┘

  Rewritten Query Tree
          │
          ▼
  ┌───────────────────┐
  │ 1. Generate         │   Enumerate alternative access paths
  │    Candidate Plans  │   (SeqScan/IndexScan) & join orders
  └─────────┬───────────┘
            ▼
  ┌───────────────────┐
  │ 2. Estimate Cost    │   Uses table/column statistics
  │    for Each Plan     │   (Module 4: cardinality estimation)
  └─────────┬───────────┘
            ▼
  ┌───────────────────┐
  │ 3. Compare & Prune  │   Discard dominated plans early
  │                     │   (dynamic programming pruning)
  └─────────┬───────────┘
            ▼
  ┌───────────────────┐
  │ 4. Select Cheapest  │   Final physical plan chosen
  └─────────┬───────────┘
            ▼
     Best Execution Plan
```

### The Cost Model

Cost is typically a **weighted combination** of:

| Resource | What It Measures |
|---|---|
| I/O Cost | Number of disk page reads (sequential vs. random — random I/O is weighted more expensive) |
| CPU Cost | Number of tuple comparisons, function evaluations |
| Memory Cost | Sort/hash buffer usage, likelihood of spilling to disk |
| Network Cost (distributed systems) | Data shuffled between nodes |

**PostgreSQL's cost model** (illustrative, real config parameters):

| Parameter | Default | Meaning |
|---|---|---|
| `seq_page_cost` | 1.0 | Cost of reading one page sequentially |
| `random_page_cost` | 4.0 | Cost of reading one page randomly (higher = disk seeks are expensive) |
| `cpu_tuple_cost` | 0.01 | Cost of processing one row |
| `cpu_index_tuple_cost` | 0.005 | Cost of processing one index entry |
| `cpu_operator_cost` | 0.0025 | Cost of evaluating one operator/function per row |

> 💡 On modern SSD-backed servers, DBAs often **lower `random_page_cost`** (e.g., to 1.1) because random I/O is no longer as punishing as it was on spinning disks — a very real, practical tuning lever.

### Example Cost Calculation (Simplified, illustrative)

For a **Sequential Scan** on a table with 10,000 pages:
```
cost = (pages × seq_page_cost) + (rows × cpu_tuple_cost)
     = (10,000 × 1.0) + (1,000,000 × 0.01)
     = 10,000 + 10,000
     = 20,000
```

For an **Index Scan** matching only 100 rows, needing ~100 random page fetches:
```
cost = (100 × random_page_cost) + (100 × cpu_index_tuple_cost) + (100 × cpu_tuple_cost)
     = (100 × 4.0) + (100 × 0.005) + (100 × 0.01)
     = 400 + 0.5 + 1
     ≈ 401.5
```

Here, the Index Scan (~401) is dramatically cheaper than the Sequential Scan (~20,000) — the optimizer picks the Index Scan. But flip the selectivity (say, 900,000 of 1,000,000 rows match), and the sequential scan usually wins because random I/O costs add up fast. This is the essence of cost-based decision-making — **it depends on the data**, which is exactly what RBO couldn't account for.

### Advantages of CBO
- Adapts automatically as data grows, shrinks, or becomes skewed.
- Makes genuinely data-driven decisions instead of blind heuristics.
- Enables sophisticated join reordering and access path selection that would be impossible to hardcode.

### Disadvantages of CBO
- **Depends entirely on statistics quality** — stale or missing statistics lead to bad cardinality estimates and, consequently, bad plans (Module 4 covers this deeply — this is the #1 real-world cause of "the optimizer picked a terrible plan").
- **Computationally expensive** — evaluating many candidate plans takes time; for very complex queries (many joins), the search space can explode combinatorially (§2.6).
- **Estimation errors compound**, especially across multiple joins — small errors at the bottom of a plan tree can multiply into wildly wrong estimates at the top.

### PostgreSQL vs MySQL vs Oracle

| Aspect | PostgreSQL | MySQL (InnoDB) | Oracle |
|---|---|---|---|
| Optimizer type | Pure CBO | CBO (historically weaker statistics, greatly improved in 8.0+) | CBO (RBO deprecated since 10g); one of the most sophisticated CBOs in the industry |
| Statistics command | `ANALYZE` | `ANALYZE TABLE` | `DBMS_STATS` package |
| Plan caching | Generic + custom plans for prepared statements | Query cache removed in 8.0; relies on re-optimization | Cursor sharing + plan baselines |
| Adaptive features | Adaptive query execution (limited) | Histogram support added in 8.0 | Adaptive Query Optimization (adaptive plans, SQL Plan Directives) |

### Interview Importance: ⭐⭐⭐⭐⭐
CBO is **the** central concept of query optimization interviews. Be ready to explain the cost model, why statistics matter, and to reason through a simple cost calculation by hand.

## 2.5 Heuristic Optimization

### Definition

**Heuristic Optimization** refers to transformation rules applied because they are *almost always* beneficial, applied **without** full cost comparison — a middle ground between pure RBO and full CBO.

### Why It Exists

Not every decision needs an expensive cost-based search. Some transformations are so reliably beneficial that computing their cost is a waste of optimizer time. For example: **"filter rows as early as possible"** (predicate pushdown) is essentially always a win — the fewer rows flowing through later operators, the less work everywhere downstream. Heuristics apply such "obviously good" rules immediately, reserving expensive cost-based search only for genuinely ambiguous decisions (like join order or algorithm choice).

### Examples of Heuristic Rules (Detailed in Module 3)

- Push selections (`WHERE` filters) down as close to the base tables as possible.
- Push projections down to avoid carrying unused columns through the plan.
- Perform selections before joins whenever possible (reduces the size of join inputs).
- Combine multiple selections into a single filter pass.

### Heuristic vs Cost-Based: Where's the Line?

```
┌─────────────────────────────────────────────────────────┐
│  "Always good" transformations → HEURISTIC (rule-based)   │
│  e.g., predicate pushdown, projection pushdown             │
│                                                             │
│  "Depends on data" decisions → COST-BASED                  │
│  e.g., join order, join algorithm, access path selection   │
└─────────────────────────────────────────────────────────┘
```

Modern optimizers (PostgreSQL, Oracle, SQL Server) use a **hybrid approach**: apply heuristic rewrite rules first (cheap, always-beneficial), *then* run cost-based search over the remaining genuinely ambiguous choices — this dramatically shrinks the search space CBO has to explore.

### Interview Importance: ⭐⭐⭐
Interviewers often ask: *"Why not make everything cost-based?"* Answer: cost estimation itself has overhead; for transformations that are provably always beneficial, skipping cost evaluation saves optimizer time without any risk of a worse plan.

## 2.6 Search Space

### Definition

The **Search Space** is the complete set of all possible physical execution plans the optimizer *could* generate for a given logical query, considering every combination of access paths, join orders, and join algorithms.

### Why It Matters

The search space for even moderately complex queries is **enormous**, and understanding its growth rate explains why optimizers use pruning, heuristics, and dynamic programming rather than brute-force enumeration.

### The Combinatorial Explosion of Join Ordering

For a join of **N** tables, the number of possible **join orders** (ignoring join algorithm choice, just table order) is related to counting the number of distinct **binary tree shapes** with N leaves, times the N! orderings of tables:

$$\text{Number of join orders} = \frac{(2(N-1))!}{(N-1)!} \quad \text{(for the general "bushy tree" case)}$$

In practice, a simpler and commonly cited figure: the number of **left-deep join trees** alone (a restricted, simpler subset — see §2.6.1) for N tables is **N!**.

| Number of Tables (N) | N! (left-deep orderings) |
|---|---|
| 3 | 6 |
| 5 | 120 |
| 7 | 5,040 |
| 10 | 3,628,800 |
| 15 | ~1.3 trillion |

And this is **before** even considering:
- Which access path to use per table (SeqScan vs. multiple possible IndexScans)
- Which join algorithm to use per join (Nested Loop vs. Hash vs. Merge)

Multiplying these factors together, the *true* search space for a 10-table join query can reach into the **billions to trillions** of possible plans. Clearly, no optimizer can evaluate all of them for every query — this motivates §2.7 (Plan Enumeration strategies) and §2.8 (Dynamic Programming).

### 2.6.1 Left-Deep Trees vs. Bushy Trees

```
LEFT-DEEP TREE                          BUSHY TREE
(one table joined at a time,            (subtrees can be joined
always on the right)                     with other subtrees)

        ⋈                                       ⋈
       / \                                     /   \
      ⋈   D                                   ⋈     ⋈
     / \                                      / \   / \
    ⋈   C                                    A   B C   D
   / \
  A   B
```

**Left-deep trees** are heavily favored by most optimizers (including PostgreSQL and, historically, most systems) because:
1. They dramatically **reduce the search space** (N! instead of a much larger bushy-tree count).
2. They map naturally onto **pipelined execution** (Module 1's Iterator model) — the right-hand input of each join can often be pipelined without needing to be fully materialized.
3. They work especially well with **Nested Loop** and **Hash Join** strategies where one side streams.

**Bushy trees** are considered in more exhaustive optimizers (or for specific cases like parallel/distributed execution) because they can sometimes produce genuinely better plans — e.g., joining two small tables together first, independently of the rest of the query — but at the cost of a vastly larger search space.

### Interview Importance: ⭐⭐⭐⭐
"Why does join order matter, and how large is the search space for N tables?" is a **very common** senior interview question. Know the N! left-deep intuition and be able to explain left-deep vs. bushy trees with a diagram.

## 2.7 Plan Enumeration

### Definition

**Plan Enumeration** is the systematic process by which the optimizer generates candidate plans from the search space to evaluate. Because exhaustive enumeration is infeasible for complex queries (§2.6), real optimizers use structured, efficient enumeration strategies.

### Common Enumeration Strategies

| Strategy | Description | Used By |
|---|---|---|
| Exhaustive enumeration | Try literally every plan | Only feasible for very small queries (few tables) |
| Dynamic Programming (bottom-up) | Build optimal plans for larger subsets from optimal plans of smaller subsets | PostgreSQL (for ≤ `join_collapse_limit` tables, default 8), classic System R optimizer |
| Greedy / Heuristic search | Make locally good choices without guaranteeing global optimum | Fallback for very large joins |
| Genetic Algorithm | Evolve a population of candidate plans over generations | PostgreSQL's **GEQO** (Genetic Query Optimizer) — kicks in automatically above `geqo_threshold` (default 12 tables) |
| Top-down / Rule-based search (Cascades style) | Explore plan space via rule application with memoization | SQL Server, Cascades-derived research optimizers |

### PostgreSQL's Threshold Behavior (Real, Practical Detail)

```
Number of tables in join
        │
        ▼
   ≤ join_collapse_limit (default 8)?
        │
    Yes │                     No
        ▼                      ▼
Dynamic Programming      ≥ geqo_threshold (default 12)?
(exhaustive within            │
 left-deep space)          Yes│              No
                               ▼               ▼
                    Genetic Algorithm    Still Dynamic
                    (GEQO)               Programming
                                          (just slower)
```

This is a genuinely important, practical fact: **queries joining a very large number of tables (12+) in PostgreSQL may get a *different, non-deterministic* plan** across runs because GEQO involves randomization! This is a real production gotcha worth knowing.

### Interview Importance: ⭐⭐⭐⭐
Know that exhaustive search doesn't scale, and that real systems switch strategies (DP → heuristic/genetic) past certain thresholds. PostgreSQL's GEQO is a great concrete, citable example in interviews.

## 2.8 Dynamic Programming (Overview)

### Definition

**Dynamic Programming (DP)**, as applied to query optimization, is an algorithmic technique that avoids redundant work by computing and caching the **best plan for every subset of tables**, building up from smaller subsets to the full join.

> This technique traces back to the seminal **System R optimizer** (IBM, 1979) — one of the most influential papers in database history, and a very likely interview reference point.

### Why It Exists

Without DP, computing the best plan for a 5-table join by brute-force recursion would repeatedly re-solve the same sub-problems (e.g., "best plan to join {A, B, C}" might be needed multiple times while exploring different overall orderings). DP applies the classic **memoization** principle: solve each sub-problem once, store the result, and reuse it.

### How It Works (Conceptual Walkthrough)

For tables `{A, B, C, D}`:

```
Step 1: Base case — best access path for each single table
   best(A), best(B), best(C), best(D)

Step 2: Best plan for every pair
   best(A,B), best(A,C), best(A,D), best(B,C), best(B,D), best(C,D)
   — computed by trying: best(A) ⋈ best(B), considering both join algorithms
     and both join orders (A⋈B and B⋈A, if not commutative in cost)

Step 3: Best plan for every triple, built from best pairs + single tables
   best(A,B,C) = min over:
       best(A,B) ⋈ best(C)
       best(A,C) ⋈ best(B)
       best(B,C) ⋈ best(A)

Step 4: Best plan for all four, built from best triples + single tables
   best(A,B,C,D) = min over:
       best(A,B,C) ⋈ best(D)
       best(A,B,D) ⋈ best(C)
       best(A,C,D) ⋈ best(B)
       best(B,C,D) ⋈ best(A)

Final answer: best(A,B,C,D)
```

At each step, the optimizer **prunes** any candidate whose cost is already provably worse than an existing candidate covering the same table subset — this pruning is what keeps DP tractable even though the raw search space is enormous.

### Complexity

Dynamic programming for join ordering runs in **O(3ᴺ)** time in the general case (each subset can be split in multiple ways) — still exponential, but *far* better than naive exhaustive enumeration, which is why it remains practical up to roughly 8-15 tables depending on the system (hence PostgreSQL's `join_collapse_limit` and `geqo_threshold` defaults from §2.7).

### Real-Life Analogy

Think of planning a road trip through 4 cities. Instead of separately calculating the total driving time for every possible full order of visiting all 4 cities from scratch, you first figure out (and remember) the best route between every *pair* of cities, then use those results to efficiently figure out the best route through every *triple*, and finally the best route through all four — never recomputing a segment you've already solved.

### Interview Importance: ⭐⭐⭐⭐⭐
This is a **classic Senior SDE-2/SDE-3 whiteboard question**: *"How would you design an algorithm to find the optimal join order for N tables?"* Expect to explain bottom-up DP with subset composition, and to discuss its exponential complexity and why real systems cap it.

## 2.9 Volcano / Cascades Optimizer (Overview)

> This is an **overview** as scoped by this handbook — deep internals of building a Cascades-style optimizer are a topic for advanced/specialized study, but the *concepts* are essential interview knowledge.

### Definition

**Volcano** and its successor **Cascades** are influential optimizer *architectures* (research frameworks from Goetz Graefe) that formalize cost-based optimization as a **rule-driven, top-down search with memoization**, rather than the more rigid bottom-up dynamic programming of System R-style optimizers.

### Key Concepts

| Concept | Meaning |
|---|---|
| **Logical/Physical rules** | Transformation rules explicitly separated into logical-to-logical (e.g., join reordering) and logical-to-physical (e.g., "implement this join as Hash Join") |
| **Memo structure** | A compact data structure that stores *groups* of logically-equivalent expressions, avoiding redundant re-exploration (similar spirit to DP's memoization, but structured around equivalence classes) |
| **Top-down search** | Optimization starts from the goal (the full query) and recursively asks "what's the best way to implement this sub-goal," applying rules on demand — as opposed to bottom-up DP, which builds strictly from small subsets upward |
| **Cost-based pruning** | Branches of the search that can't beat the current best-known cost are pruned early (branch-and-bound style) |
| **Physical properties** | Tracks not just cost but also *properties* of intermediate results (e.g., "is this already sorted by X?") so downstream operators (like a merge join or `ORDER BY`) can exploit them without redundant sorting |

### Why This Architecture Matters

The Volcano/Cascades model is **extensible** — new rules (new transformations, new physical operators) can be added without redesigning the whole optimizer, because everything is expressed as composable rules operating over a shared memo structure. This is why it became the dominant architecture for modern production optimizers.

### Who Uses This Architecture

| System | Optimizer Architecture |
|---|---|
| SQL Server | Cascades-derived |
| Microsoft's original Cascades research | Direct origin |
| Apache Calcite (used by many modern big-data/SQL engines) | Volcano/Cascades-style |
| CockroachDB, many newer distributed SQL engines | Cascades-inspired |
| PostgreSQL | **Not** Cascades — uses classic System-R-style bottom-up DP + GEQO (important distinction!) |
| Oracle | Proprietary CBO, incorporates many Cascades-like ideas (adaptive plans) but not a textbook Cascades implementation |

> ⚠️ **Common Interview Trap:** Don't assume every modern database uses Cascades. PostgreSQL, one of the most commonly discussed databases in interviews, explicitly uses the **older System R-style dynamic programming approach** (plus GEQO for large joins), *not* Cascades. Getting this distinction right signals real depth of knowledge.

### Volcano vs. Cascades vs. System R (Quick Comparison)

| Aspect | System R (1979) | Volcano (1990s) | Cascades (1995+) |
|---|---|---|---|
| Search direction | Bottom-up DP | Top-down, rule-based | Top-down, rule-based (refined) |
| Extensibility | Low (hardcoded join enumeration) | Moderate | High (clean separation of rules & engine) |
| Used in | Original influence on most classic optimizers (incl. PostgreSQL's approach) | Research prototype, influenced later systems | SQL Server, Calcite, many modern engines |

### Interview Importance: ⭐⭐⭐⭐
Senior/staff-level interviews (especially at companies building custom data systems) may ask *"What optimizer architecture does system X use, and why?"* Know the System R vs. Cascades distinction and that PostgreSQL is System R-style, not Cascades.

## 2.10 Full Comparison: RBO vs. CBO vs. Heuristic

| Dimension | Rule-Based (RBO) | Heuristic | Cost-Based (CBO) |
|---|---|---|---|
| Uses statistics? | No | No | Yes |
| Adapts to data size/skew? | No | Partially (rules chosen for general applicability) | Yes, fully |
| Computational overhead | Very low | Very low | Higher (must evaluate multiple plans) |
| Risk of bad plans | High (blind to reality) | Low (only applies "always good" rules) | Low, but *sensitive to bad statistics* |
| Example decision | "Always prefer index scan over full scan" | "Always push filters down" | "Choose Hash Join vs. Nested Loop based on estimated row counts" |
| Modern usage | Mostly obsolete (legacy) | Universal, as pre-processing before CBO | Universal, as the core optimization strategy |

## 2.11 Best Practices, Common Mistakes & Edge Cases

### Best Practices
- Keep table/column statistics fresh (`ANALYZE` / `DBMS_STATS`) — CBO is only as good as its input statistics (Module 4 covers this deeply).
- For very wide joins (10+ tables), be aware your database may switch optimization strategies (e.g., PostgreSQL's GEQO) — consider restructuring the query or using explicit join order hints/`JOIN` syntax if plan instability becomes a real production issue.
- Understand your database's `join_collapse_limit`/equivalent settings if working with generated queries (e.g., from ORMs) that produce many joins.

### Common Mistakes
- Assuming the optimizer always finds the *true* optimal plan — it finds the plan with the lowest **estimated** cost, which is only as good as the estimates (Module 4).
- Writing extremely large multi-way joins and being surprised when plan choice becomes inconsistent (this is GEQO's randomized nature, not a bug).
- Believing "cost-based" means the optimizer measures real execution time — it does not; it estimates cost using a **mathematical model** before ever running the query.

### Edge Cases
- Queries with **very large numbers of joined tables** (dozens+, common in generated BI/reporting queries) may need explicit restructuring, materialized intermediate results, or optimizer hints because the search space becomes intractable even with DP/GEQO.
- **Correlated subqueries** and complex `OR` conditions can defeat clean cost estimation and force the optimizer into more conservative (sometimes suboptimal) plan choices.

## 2.12 Chapter Summary

- The **Query Optimizer** searches for the cheapest **physical plan** implementing a given **logical plan**.
- **RBO** picks plans via fixed heuristic rankings, ignoring actual data — mostly obsolete today.
- **CBO** estimates numeric cost (I/O + CPU + memory) for candidate plans using statistics, and picks the cheapest — the dominant strategy in all modern databases.
- **Heuristic optimization** applies "always beneficial" rules (like predicate pushdown) without cost comparison, reducing the burden on CBO.
- The **search space** for join ordering grows combinatorially (~N! for left-deep trees), motivating smarter enumeration.
- **Dynamic Programming** (System R style) builds optimal plans bottom-up from subsets, with pruning, in O(3ᴺ) — practical up to a threshold, after which systems like PostgreSQL fall back to **GEQO** (genetic algorithm).
- **Volcano/Cascades** are top-down, rule-driven optimizer architectures used by systems like SQL Server and Calcite — **not** PostgreSQL, which remains System R-style.

```
OPTIMIZATION STRATEGY DECISION TREE

  YES → Apply as HEURISTIC RULE (no cost calc needed)
  NO  → Requires COST-BASED comparison

Is the join has ≤ ~8-12 tables?
  YES → Dynamic Programming (exhaustive within left-deep space)
  NO  → Genetic Algorithm / heuristic search (e.g. GEQO)

Remember:
  RBO      = fixed rules, blind to data        (mostly obsolete)
  Heuristic = "always good" rules, no cost calc (used everywhere, cheap)
  CBO      = statistics-driven cost comparison  (the real workhorse)
  DP       = bottom-up subset composition, O(3^N)
  GEQO/Cascades = strategies for when DP doesn't scale
```
