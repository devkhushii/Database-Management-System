# Part 6: Transactions & Concurrency Control

## Module 5: Concurrency Problems

> Modules 3 and 4 gave us the *theory* to classify and judge schedules. Now let's get concrete: what actually goes wrong, in practice, when concurrency control is weak or absent? This module walks through every classic concurrency anomaly with a full transaction timeline, so you can instantly recognize each one — a core skill for both exams and real production debugging.

---

### 5.1 Why Study These Problems Explicitly?

Every isolation level (Module 11) is defined *precisely* by which of these anomalies it prevents and which it still allows. If you don't deeply understand each anomaly individually, isolation levels will feel like arbitrary trivia. Once you understand the anomalies, isolation levels become simple: "Read Committed prevents dirty reads but allows non-repeatable reads," etc. — a direct mapping.

---

### 5.2 Lost Update

**Definition:** A **lost update** occurs when two transactions read the same data item, then both compute a new value based on that read, and the second transaction's write **overwrites** the first transaction's write — silently discarding the first transaction's update entirely.

**Real-world analogy:** Two people editing the same spreadsheet cell offline, both starting from the same value, both changing it independently, and whoever "saves" last wins — the other person's edit vanishes without anyone being warned.

**Timeline:**

```
Time  T1                          T2
----  --------------------------  --------------------------
t1    BEGIN
t2                                BEGIN
t3    R(balance) → 1000
t4                                R(balance) → 1000
t5    balance = 1000 + 100 = 1100
t6    W(balance = 1100)
t7                                balance = 1000 + 200 = 1200
t8                                W(balance = 1200)
t9    COMMIT
t10                               COMMIT

Final balance = 1200
T1's +100 update is LOST — it's as if it never happened!
```

**Why it happens:** Both transactions read the *same* stale value and computed their new values independently, without knowing about each other's concurrent write.

**How it's prevented:** Locking protocols (Module 6–7) prevent this by making T2 wait until T1 releases its lock on `balance` (so T2 reads T1's updated value, 1100, not the stale 1000). MVCC systems (Module 10) detect this as a **write-write conflict** and abort one of the transactions.

### 5.3 Dirty Read (Reading Uncommitted Data)

**Definition:** A **dirty read** occurs when a transaction reads data that has been written by another transaction that **has not yet committed** — and that other transaction might still abort, making the read value never actually "real."

**Timeline:**

```
Time  T1                          T2
----  --------------------------  --------------------------
t1    BEGIN
t2    W(balance = 500)   -- uncommitted
t3                                BEGIN
t4                                R(balance) → 500  -- DIRTY READ
t5                                -- T2 acts on 500, e.g., approves a loan
t6    ROLLBACK            -- T1 aborts! balance reverts to original
t7                                COMMIT

T2 made a decision based on a value (500) that officially never existed.
```

**Why it's dangerous:** T2's entire decision-making was based on data that is later proven to have never been "true" — this is a direct violation of Isolation (Module 2).

**Prevention:** Only allowed under the `READ UNCOMMITTED` isolation level (Module 11) — every other standard isolation level prevents this.

---

### 5.4 Dirty Write

**Definition:** A **dirty write** occurs when a transaction **overwrites** a data item that was written by another, still-uncommitted transaction.

**Timeline:**

```
Time  T1                          T2
----  --------------------------  --------------------------
t1    BEGIN
t2    W(price = 100)      -- uncommitted
t3                                BEGIN
t4                                W(price = 200)   -- DIRTY WRITE, overwrites T1's uncommitted value
t5    ROLLBACK             -- T1 aborts
t6                                COMMIT

Now: was T1's rollback supposed to restore price to its ORIGINAL value,
or to 100 (T1's own write)? T2's write is now hopelessly entangled
with a transaction that never should have "counted."
```

**Why it's dangerous:** Dirty writes make rollback semantics ambiguous and corrupt — this is exactly what the **Strict** schedule class (Module 3.8) is designed to prevent entirely, by disallowing any write to an item until the previous writer commits or aborts.

**Prevention:** Virtually every production database prevents dirty writes unconditionally (even at the weakest isolation levels) via basic locking on writes — this is considered a baseline requirement, not something you can opt out of like a dirty read.

---

### 5.5 Non-Repeatable Read (Fuzzy Read)

**Definition:** A **non-repeatable read** occurs when a transaction reads the **same row twice** and gets **different values** each time, because another transaction **committed** an update to that row in between the two reads.

**Timeline:**

```
Time  T1                          T2
----  --------------------------  --------------------------
t1    BEGIN
t2    R(price) → 100
t3                                BEGIN
t4                                W(price = 150)
t5                                COMMIT
t6    R(price) → 150       -- DIFFERENT VALUE from t2!
t7    COMMIT

T1 read the same row twice within one transaction and got two
different answers, even though T2's write was a "legitimate,"
fully committed change.
```

**Difference from a dirty read:** Here, T2's write was **committed** (it's a real, permanent change) — the issue is only that T1 saw two *different, both technically valid* values within a single transaction, which can break assumptions in reporting or calculations that expect stability within one transaction.

**Prevention:** Prevented starting from `REPEATABLE READ` isolation level (Module 11) upward; allowed under `READ COMMITTED` and `READ UNCOMMITTED`.

---

### 5.6 Phantom Read

**Definition:** A **phantom read** occurs when a transaction re-executes a **range query** (e.g., `WHERE amount > 1000`) twice, and the **set of rows returned** differs between the two executions — because another transaction **inserted or deleted** rows matching that range condition in between, and committed.

**Timeline:**

```
Time  T1                                       T2
----  ---------------------------------------  --------------------------
t1    BEGIN
t2    SELECT * FROM orders WHERE amount > 1000
      → returns 5 rows
t3                                              BEGIN
t4                                              INSERT INTO orders (amount) VALUES (2000)
t5                                              COMMIT
t6    SELECT * FROM orders WHERE amount > 1000
      → returns 6 rows -- a "phantom" row appeared!
t7    COMMIT
```

**Why it's subtly different from Non-Repeatable Read:** Non-repeatable read is about a **specific existing row** changing value. Phantom read is about the **set of rows matching a condition** changing — new rows appearing or existing ones disappearing from a range — which is a fundamentally harder problem to solve with simple row-level locking, since you can't "lock a row that doesn't exist yet." This is exactly why **range locks / next-key locking** and **predicate locking** exist (touched on in Module 6, detailed further alongside indexing in later parts).

**Prevention:** Fully prevented only at `SERIALIZABLE` isolation level in the strict theoretical sense (though `REPEATABLE READ` in some engines — notably InnoDB — uses gap locks to prevent most phantom scenarios in practice, a well-known engine-specific nuance covered fully in Module 11).

---

### 5.7 Incorrect Summary (Inconsistent Analysis)

**Definition:** An **incorrect summary** anomaly occurs when one transaction is computing an **aggregate** (e.g., `SUM`, `COUNT`, `AVG`) over a set of rows while another transaction concurrently modifies some of those rows — resulting in the aggregate reflecting an inconsistent, partially-updated view that never existed as a real, complete state.

**Timeline:**

```
Time  T1 (computing total balance across accounts)   T2 (transferring money)
----  ----------------------------------------------  --------------------------
t1    BEGIN
t2    R(A) → 500    -- reads A before transfer
t3                                                    BEGIN
t4                                                    W(A = 400)  -- debit 100 from A
t5                                                    W(B = 600)  -- credit 100 to B
t6                                                    COMMIT
t7    R(B) → 600    -- reads B AFTER transfer
t8    SUM = 500 + 600 = 1100  -- WRONG!
      (should be 500+500=1000 before, or 400+600=1000 after — never 1100)
t9    COMMIT
```

**Why it happens:** T1 read A *before* the transfer and B *after* the transfer — straddling the transfer's boundary — producing a sum that reflects **neither** the pre-transfer nor post-transfer state. The total is simply wrong by the transferred amount.

**Prevention:** This is prevented by any isolation mechanism that gives T1 a **consistent snapshot** across its entire duration — this is precisely what MVCC's **Snapshot Isolation** (Module 10) provides, and it's also prevented by holding appropriate locks across the whole aggregate computation under 2PL-based `REPEATABLE READ`/`SERIALIZABLE`.

---

### 5.8 Write Skew

**Definition:** **Write skew** is a subtle anomaly where two transactions **each read overlapping data, and each writes to a *different* item**, based on a check against the *combined* state — but because neither transaction's write conflicts directly with the other's write (they write different rows), naive concurrency control (including some snapshot-isolation implementations) allows both to commit, even though the combined result violates an invariant that was supposed to hold.

**Classic example — the on-call doctor problem:**

Rule: *At least one doctor must always be on call.* Currently, Dr. Alice and Dr. Bob are both on call.

```
Time  T1 (Alice wants to go off-call)          T2 (Bob wants to go off-call)
----  ----------------------------------------  --------------------------------------
t1    BEGIN
t2    R(on_call_count) → 2  -- sees Alice+Bob both on call
t3                                              BEGIN
t4                                              R(on_call_count) → 2  -- also sees 2
t5    -- Alice checks: "2 on-call, safe for me to go off"
t6                                              -- Bob checks: "2 on-call, safe for him to go off"
t7    W(alice.on_call = false)
t8                                              W(bob.on_call = false)
t9    COMMIT
t10                                             COMMIT

RESULT: Both go off-call! Zero doctors on call — the invariant
"at least one doctor on call" is VIOLATED, even though neither
transaction's write directly conflicted with the other's (they wrote
DIFFERENT rows — alice's row vs bob's row).
```

**Why it's dangerous and hard to detect:** Standard write-write conflict detection (used by many MVCC implementations under plain Snapshot Isolation) only looks for two transactions writing the **same** row — it completely misses this case because Alice's write and Bob's write touch different rows. This is precisely why plain **Snapshot Isolation ≠ Serializable** (a critical distinction covered in Module 11), and why databases offering a true `SERIALIZABLE` guarantee (like PostgreSQL's Serializable Snapshot Isolation, Module 9's OCC-style validation) must track **read-based predicates**, not just written rows, to catch this.

---

### 5.9 Read Skew

**Definition:** **Read skew** occurs when a transaction reads **two related data items** that are supposed to be logically consistent with each other (e.g., linked by a constraint or invariant), but due to a concurrent committed update in between the two reads, it sees them in a mutually **inconsistent** combination.

**Timeline (a classic example — linked account balances that must always sum to a fixed total):**

```
Invariant: A + B must always equal 1000.

Time  T1 (auditor checking A + B)   T2 (transferring 200 from A to B)
----  -----------------------------  --------------------------------
t1    BEGIN
t2    R(A) → 500
t3                                   BEGIN
t4                                   W(A = 300)
t5                                   W(B = 700)
t6                                   COMMIT
t7    R(B) → 700
t8    SUM = 500 + 700 = 1200 -- violates the invariant! (should be 1000)
t9    COMMIT
```

**Relationship to "Incorrect Summary":** Read skew is essentially the general form of the incorrect-summary anomaly (5.7) — reading related items at different logical points in time. Some textbooks treat them as the same anomaly; others distinguish "incorrect summary" as specifically about aggregate functions and "read skew" as the more general two-(or-more)-item consistency case. Both are fixed by the same mechanism: a **consistent snapshot** for the whole transaction (Snapshot Isolation / `REPEATABLE READ`+ / `SERIALIZABLE`).

---

### 5.10 Race Conditions (General Category)

**Definition:** A **race condition**, in the database context, is the umbrella term for *any* scenario where the final outcome depends on the precise, uncontrolled timing/interleaving of concurrent operations, rather than being deterministic based on the logical operations alone. Lost Update, Dirty Read, Dirty Write, Non-Repeatable Read, Phantom Read, Write Skew, and Read Skew are all specific, named instances of database race conditions.

**Interview framing tip:** If an interviewer asks "what's a race condition in a database context?", the strongest answer walks through 2–3 of the specific named anomalies above as concrete examples, rather than giving only the abstract definition — this demonstrates depth.

---

### 5.11 Master Comparison Table — Anomalies at a Glance

| Anomaly | What's read/written | Root cause | Prevented starting at |
|---|---|---|---|
| Dirty Read | Reads uncommitted data | No isolation from in-progress writes | `READ COMMITTED` |
| Dirty Write | Overwrites uncommitted data | No write-write ordering protection | Always prevented (baseline) |
| Lost Update | Two txns overwrite each other's update | No write-write conflict detection on read-then-write | `REPEATABLE READ` (with proper locking) / detected by MVCC write-conflict check |
| Non-Repeatable Read | Same row, two different committed values | No snapshot stability across the transaction | `REPEATABLE READ` |
| Phantom Read | Range query returns different row sets | No protection against new rows entering/leaving a range | `SERIALIZABLE` (or engine-specific gap locking) |
| Incorrect Summary | Aggregate spans pre- and post-update states | No consistent snapshot across a multi-row read | Snapshot Isolation / `REPEATABLE READ`+ |
| Read Skew | Related items read at inconsistent points | Same as above, generalized | Snapshot Isolation / `SERIALIZABLE` |
| Write Skew | Disjoint writes based on a shared invariant | No predicate/invariant-level conflict detection | True `SERIALIZABLE` only |

*(Full formal isolation-level-to-anomaly mapping table is presented in Module 11.)*

### 5.12 Advantages, Disadvantages, Best Practices

There's no "advantage" to these anomalies themselves — they represent the *costs of insufficient isolation*, traded off against performance. The real discussion is about **managing the trade-off deliberately**:

**Best Practices:**
- Identify which anomalies your specific business logic can tolerate (e.g., a dashboard "approximate revenue today" metric can tolerate read skew; a funds transfer absolutely cannot).
- Use the weakest isolation level that still prevents the anomalies relevant to your use case — this maximizes throughput without sacrificing correctness (full framework in Module 11).
- For invariants spanning multiple rows (write skew scenarios), consider explicit `SELECT ... FOR UPDATE` locking or a true `SERIALIZABLE` isolation level rather than assuming default Snapshot Isolation will catch the conflict.

**Common Mistakes:**
- Assuming "my database uses MVCC, so I'm safe from all concurrency anomalies" — MVCC-based Snapshot Isolation is **not** immune to write skew, a very common and dangerous misconception.
- Not recognizing phantom reads as a distinct category from non-repeatable reads, leading to under-protecting range-based business rules (e.g., "no more than 3 concurrent bookings for this slot").
- Debugging a "random," hard-to-reproduce production data bug without recognizing it as a named concurrency anomaly, and thus fixing it with an ad hoc patch instead of the correct isolation/locking mechanism.

**Performance Implications:**
Preventing every anomaly (full Serializable isolation) can meaningfully reduce throughput due to increased blocking or higher abort/retry rates under contention (Module 16 covers this trade-off with real numbers and scenarios).

**Industry Usage:** Write skew is a famous, real-world cause of production bugs in booking/reservation systems (e.g., double-booking a meeting room believed to be "available" by two concurrent checks) and healthcare on-call scheduling systems (exactly the doctor example above) — both covered further in Module 15's case studies.

### 5.13 Chapter Summary

- **Dirty Read**: reading another transaction's uncommitted write.
- **Dirty Write**: overwriting another transaction's uncommitted write.
- **Lost Update**: two transactions read-then-write the same item, one update silently overwrites the other.
- **Non-Repeatable Read**: re-reading the same row within a transaction yields a different (but committed) value.
- **Phantom Read**: re-running the same range query yields a different set of rows.
- **Incorrect Summary / Read Skew**: reading related data items that straddle another transaction's commit, producing a logically impossible combination.
- **Write Skew**: two transactions read overlapping data and write to *different* items based on a shared invariant that ends up violated, because plain write-write conflict detection can't see it.
- **Race Condition**: the general umbrella term for all of the above.

### 5.14 Revision Notes / Cheat Sheet

```
READ UNCOMMITTED  → allows: dirty read, non-repeatable read, phantom
READ COMMITTED    → prevents: dirty read | allows: non-repeatable read, phantom
REPEATABLE READ   → prevents: dirty read, non-repeatable read | allows: phantom (mostly)
SERIALIZABLE      → prevents: everything, including write skew
```
(Full detail with exceptions like InnoDB's gap locks in Module 11.)
