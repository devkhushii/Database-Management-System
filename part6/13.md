# Part 6: Transactions & Concurrency Control

## Module 13: Transaction Control Language (TCL)

> We've spent twelve modules on theory and mechanisms. This module is the practical toolkit — the actual SQL commands you'll type every day to control transaction boundaries, create rollback checkpoints, and configure transaction-level behavior. If Modules 1–12 were the "why" and "how it works internally," this module is the "how do I actually write this."

---

### 13.1 What Is TCL?

**Definition:** **Transaction Control Language (TCL)** is the subset of SQL commands used to manage transactions explicitly — starting them, ending them (successfully or not), and creating intermediate rollback points within them. TCL sits alongside DDL (Data Definition Language: `CREATE`, `ALTER`, `DROP`) and DML (Data Manipulation Language: `SELECT`, `INSERT`, `UPDATE`, `DELETE`) as one of the standard SQL command categories.

**The TCL commands covered in this module:**
`BEGIN` / `START TRANSACTION`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `RELEASE SAVEPOINT`, `ROLLBACK TO SAVEPOINT`, `SET TRANSACTION`, `SET CONSTRAINTS`.

---

### 13.2 BEGIN / START TRANSACTION

**Definition:** Marks the start of an explicit transaction (Module 1.6), suspending autocommit (if it was active) until an explicit `COMMIT` or `ROLLBACK` is issued.

```sql
-- PostgreSQL / standard SQL
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
  UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
COMMIT;

-- MySQL (equivalent, standard SQL keyword)
START TRANSACTION;
  UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
  UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
COMMIT;
```

**Note:** In PostgreSQL, `BEGIN` and `START TRANSACTION` are both accepted and functionally identical — `BEGIN` is PostgreSQL's traditional/shorter form, while `START TRANSACTION` is the standard SQL keyword also supported for portability.

---

### 13.3 COMMIT

**Definition:** Finalizes the current transaction, making all its changes **permanent and durable** (Module 2.5), and releasing all locks held by the transaction (per whichever 2PL variant, Module 7, the engine implements — typically Strict or Rigorous 2PL, releasing everything at commit).

```sql
BEGIN;
  INSERT INTO orders (customer_id, total) VALUES (42, 250.00);
COMMIT;   -- durably recorded; visible to all other transactions henceforth
```

**What happens internally at COMMIT (recap from Module 2.5):** the commit log record is written and flushed (`fsync`'d) to durable storage before the client receives acknowledgment — this is the mechanical basis of the Durability guarantee.

---

### 13.4 ROLLBACK

**Definition:** Aborts the current transaction, **undoing** all of its changes as if they never happened, and releasing all locks it held.

```sql
BEGIN;
  UPDATE accounts SET balance = balance - 1000000 WHERE id = 'A';
  -- Oops, wrong amount!
ROLLBACK;   -- balance is restored to its pre-transaction value; nothing was ever visible to others
```

**When ROLLBACK happens automatically:** A transaction is also rolled back automatically (without an explicit `ROLLBACK` statement) when:
- The client connection is lost/closed before commit.
- The database crashes before the commit record is flushed (handled by crash recovery, Part 7).
- A serialization failure or deadlock-victim error occurs under stricter isolation levels (Module 11, Module 12) — though the application must still typically issue an explicit `ROLLBACK` (or the driver does so automatically) to clean up the session state before retrying.

---

### 13.5 SAVEPOINT

**Definition:** Creates a **named point within the current transaction** to which you can later roll back **partially** — undoing only the changes made *after* that savepoint, without discarding the entire transaction (Module 1.8's simulated nested-transaction mechanism).

```sql
BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE id = 'A';

    SAVEPOINT before_risky_update;

    UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
    -- suppose we discover this second update was based on wrong data

    ROLLBACK TO SAVEPOINT before_risky_update;
    -- the second UPDATE (crediting B) is undone;
    -- the first UPDATE (debiting A) is STILL intact

    UPDATE accounts SET balance = balance + 100 WHERE id = 'C';  -- corrected recipient

COMMIT;   -- final result: A debited, C credited (not B)
```

**Multiple savepoints:** A transaction can create multiple, even nested, savepoints:

```sql
BEGIN;
  SAVEPOINT sp1;
  -- some work
  SAVEPOINT sp2;
  -- more work
  ROLLBACK TO SAVEPOINT sp1;  -- undoes work done under BOTH sp2 and after sp1
COMMIT;
```

Rolling back to an earlier savepoint automatically discards any savepoints created **after** it (like `sp2` in the example above) — they no longer exist once you've rolled back past them.

---

### 13.6 RELEASE SAVEPOINT

**Definition:** Explicitly **removes** a savepoint (without rolling back to it) — essentially saying "I no longer need this checkpoint; I'm confident everything up to and beyond this point is fine." Once released, you can no longer roll back to that specific savepoint (though rolling back to an *earlier* savepoint, if one exists, still works normally, and the released savepoint's changes are simply subsumed).

```sql
BEGIN;
    SAVEPOINT sp1;
    UPDATE inventory SET qty = qty - 1 WHERE sku = 'X123';

    RELEASE SAVEPOINT sp1;   -- we're confident this update was correct, discard the checkpoint

    UPDATE orders SET status = 'confirmed' WHERE id = 555;
COMMIT;
```

**Why use RELEASE explicitly?** In long transactions with many savepoints, releasing ones you no longer need frees up any internal bookkeeping resources associated with tracking them — a minor but real performance/memory consideration in transactions with dozens of savepoints (e.g., generated automatically by an ORM's nested-transaction emulation, Module 1.8).

---

### 13.7 ROLLBACK TO SAVEPOINT

**Definition:** (Already demonstrated in 13.5) Rolls back all changes made **since** the specified savepoint, but keeps the **transaction itself active** — you can continue issuing new statements after this, and eventually still `COMMIT` or fully `ROLLBACK` the whole transaction.

**Critical distinction from a full `ROLLBACK`:** `ROLLBACK TO SAVEPOINT x` does **not** end the transaction — it's a partial undo within an ongoing transaction. A bare `ROLLBACK` (no savepoint specified) ends the entire transaction completely.

**A very important, frequently-tested PostgreSQL nuance:** Recall from Module 1.3 that in PostgreSQL, once **any** statement inside a transaction errors out, the **entire transaction** is marked as aborted, and every subsequent command is rejected until you issue `ROLLBACK` — **except** if you roll back to a savepoint created **before** the error occurred! This is precisely the practical use case for savepoints in PostgreSQL: **isolating a risky statement so a single failure doesn't poison the whole transaction.**

```sql
BEGIN;
    INSERT INTO logs (message) VALUES ('starting batch');

    SAVEPOINT before_risky_insert;
    INSERT INTO accounts (id, balance) VALUES ('A', 100);  -- suppose this VIOLATES a UNIQUE constraint and errors!

    ROLLBACK TO SAVEPOINT before_risky_insert;   -- recovers the transaction from the "aborted" state
    -- transaction is now healthy again, can continue:

    INSERT INTO logs (message) VALUES ('batch continued after handling conflict');
COMMIT;   -- succeeds! Both log inserts are committed; the failed accounts insert is not.
```

### 13.8 SET TRANSACTION

**Definition:** Configures properties of the **upcoming or current** transaction, most commonly its **isolation level** (Module 11) and, in some engines, whether it's read-only or read-write.

```sql
-- Standard SQL / PostgreSQL
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  -- transaction body here
COMMIT;

-- Read-only transaction (an optimization hint — the engine can skip
-- certain write-related bookkeeping, e.g., avoiding taking a transaction ID in
-- some PostgreSQL versions for purely read-only work)
BEGIN;
SET TRANSACTION READ ONLY;
  SELECT * FROM large_report_table;
COMMIT;

-- MySQL
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;  -- applies to all future transactions in this session
-- or, for just the next transaction:
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
  -- ...
COMMIT;
```

**Best Practice:** Set the isolation level as close as possible to the actual `BEGIN`/`START TRANSACTION` for clarity, and be aware of whether your syntax sets it for just the **next** transaction or for the **entire session** going forward — a subtle but important scoping difference across engines that has caused real production bugs (a `SET SESSION` intended as one-off ends up silently affecting every subsequent transaction on that connection).

### 13.9 SET CONSTRAINTS

**Definition:** Controls **when** constraint checks (e.g., foreign key checks, `CHECK` constraints declared as `DEFERRABLE`) are actually evaluated — either **immediately** after each statement, or **deferred** until the transaction's `COMMIT`.

**Why it exists — the problem it solves:** Sometimes, a transaction needs to **temporarily** violate a constraint in an intermediate step, as long as the constraint is satisfied by the time the transaction commits. A classic example: **reordering a list of items** where each item has a `UNIQUE` `position` column — swapping two items' positions requires briefly having two rows with the same position value (or one row with a duplicate/invalid intermediate value) *during* the transaction, even though the final state is perfectly valid and unique.

```sql
-- Assume 'position' has a UNIQUE constraint declared as DEFERRABLE INITIALLY DEFERRED
CREATE TABLE playlist_items (
    id SERIAL PRIMARY KEY,
    position INT UNIQUE DEFERRABLE INITIALLY DEFERRED
);

BEGIN;
    -- Swap positions of item 1 (currently position=1) and item 2 (currently position=2)
    UPDATE playlist_items SET position = 2 WHERE id = 1;  -- TEMPORARILY creates a duplicate position=2!
    UPDATE playlist_items SET position = 1 WHERE id = 2;  -- now positions are valid again (1 and 2, swapped)
COMMIT;   -- constraint is checked HERE, at commit — and it passes, since duplicates no longer exist
```

Without `DEFERRABLE`, the **first** `UPDATE` statement above would fail immediately with a unique constraint violation, because standard (non-deferred) constraints are checked **after each statement**, not just at commit.

**Explicit control within a transaction:**

```sql
BEGIN;
    SET CONSTRAINTS ALL DEFERRED;     -- defer ALL deferrable constraints to commit time
    -- or, for a specific named constraint:
    SET CONSTRAINTS playlist_items_position_key DEFERRED;

    -- ... perform temporarily-violating operations ...

COMMIT;   -- constraints checked now
```

**Engine support:** PostgreSQL and Oracle both fully support `DEFERRABLE` constraints and `SET CONSTRAINTS`. MySQL/InnoDB historically has **more limited support** for deferred constraint checking — this is a notable, real-world engine capability gap worth knowing for cross-database work.

### 13.10 Full Worked Example — Combining Multiple TCL Commands

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

  INSERT INTO audit_log (event) VALUES ('order_processing_started');

  SAVEPOINT before_payment;

  UPDATE payments SET status = 'processing' WHERE order_id = 555;
  -- suppose the payment gateway call (application-side) fails here

  ROLLBACK TO SAVEPOINT before_payment;
  UPDATE payments SET status = 'failed' WHERE order_id = 555;

  INSERT INTO audit_log (event) VALUES ('order_processing_failed');

COMMIT;   -- the audit trail (both log entries) and the 'failed' status are committed;
          -- the transient 'processing' status update was cleanly rolled back
```

This example demonstrates a realistic pattern: using a savepoint to attempt a risky operation, cleanly reverting just that portion on failure, and still committing a coherent, correct final state — all within a single transaction boundary.

### 13.11 Advantages, Disadvantages, Best Practices

**Advantages of TCL / Savepoints specifically:**
- Enables fine-grained error recovery within a transaction without discarding all prior work.
- `DEFERRABLE` constraints (via `SET CONSTRAINTS`) enable legitimate intermediate states that are corrected by commit time, supporting patterns like reordering/swapping that would otherwise require awkward workarounds.

**Disadvantages:**
- Overusing savepoints (e.g., one per statement) can add unnecessary overhead and complexity.
- Deferred constraints, if misused, can hide bugs until commit time, making debugging intermediate application logic harder (a constraint violation you might have wanted to catch immediately is instead silently allowed until the very end).

**Best Practices:**
- Use `SAVEPOINT` specifically around genuinely "risky" operations (e.g., an `INSERT` that might hit a `UNIQUE` violation) where you have a planned fallback, rather than sprinkling them everywhere defensively.
- Be explicit and deliberate about isolation level scoping (`SET TRANSACTION` vs `SET SESSION TRANSACTION`) to avoid accidentally affecting unrelated subsequent transactions.
- Only mark constraints `DEFERRABLE` when you have a genuine, understood use case (like the reordering example) — don't defer constraints by default, since immediate checking catches bugs earlier.

**Common Mistakes:**
- Forgetting that in PostgreSQL, any error inside a transaction poisons the whole transaction **unless** you roll back to a preceding savepoint — a frequent source of confusing "current transaction is aborted" errors for developers unfamiliar with this behavior.
- Confusing `ROLLBACK TO SAVEPOINT` (partial undo, transaction continues) with a full `ROLLBACK` (entire transaction ends).
- Not realizing that `RELEASE SAVEPOINT` doesn't commit anything — it simply removes the ability to roll back to that specific point; the transaction as a whole is still uncommitted until `COMMIT`.

**Performance Implications:** Savepoints have some overhead (internal bookkeeping to track the rollback point), so extremely fine-grained savepointing (e.g., one per row in a large batch loop) can add up — but this cost is usually small compared to the correctness/recovery benefits for genuinely risky operations.

**Industry Usage:** ORMs frequently use savepoints under the hood to implement "nested transaction" APIs (Module 1.8) — understanding TCL directly demystifies what your ORM's `transaction.atomic(nested=True)`-style calls are actually doing under the hood.

### 13.12 Chapter Summary

- **BEGIN / START TRANSACTION**: starts an explicit transaction.
- **COMMIT**: finalizes and durably records all changes.
- **ROLLBACK**: undoes all changes in the current transaction.
- **SAVEPOINT**: creates a named partial-rollback checkpoint within a transaction.
- **RELEASE SAVEPOINT**: discards a savepoint without rolling back.
- **ROLLBACK TO SAVEPOINT**: partially undoes work since a savepoint, keeping the transaction alive — crucially useful in PostgreSQL to recover from a poisoned transaction.
- **SET TRANSACTION**: configures isolation level (and read-only/read-write) for a transaction.
- **SET CONSTRAINTS**: controls whether deferrable constraints are checked immediately or at commit — enabling legitimate temporary constraint violations mid-transaction.

### 13.13 Revision Notes / Cheat Sheet

```
BEGIN / START TRANSACTION   → open explicit transaction
COMMIT                      → finalize, durable, releases locks
ROLLBACK                    → undo everything, ends transaction
SAVEPOINT name              → checkpoint
RELEASE SAVEPOINT name      → discard checkpoint (no rollback)
ROLLBACK TO SAVEPOINT name  → partial undo, transaction STAYS ALIVE
SET TRANSACTION ISOLATION LEVEL x  → set isolation level for this txn
SET CONSTRAINTS ALL DEFERRED       → defer constraint checks to COMMIT

PostgreSQL gotcha: any error poisons the WHOLE transaction —
   only a ROLLBACK TO an earlier SAVEPOINT can recover it (not a plain retry of the statement).
```
