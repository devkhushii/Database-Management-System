## 13.1 Banking

### Dominant Query Patterns
- `WHERE account_id = X` (point lookups — extremely common, extremely low selectivity).
- `WHERE account_id = X AND transaction_date BETWEEN ... AND ...` (statement generation, range queries).
- Strict consistency and durability requirements (connects forward to Part 9's ACID/transaction isolation).

### Read/Write Profile
Moderate write volume (transactions happen continuously but not at extreme social-media scale), **extremely high correctness requirements** — no tolerance for lost writes or inconsistent reads.

### Indexing Strategy
- **Clustered index** (InnoDB) or primary key index (PostgreSQL) on `account_id` (or a surrogate transaction ID with `account_id` as a composite leading column) — since almost every query starts with "for this account."
- **Composite index** on `(account_id, transaction_date)` — equality-filtered `account_id` first, range-filtered `transaction_date` last (Module 5/10's ordering rule).
- Avoid indexing highly sensitive columns unnecessarily (e.g., don't index raw account numbers if a tokenized/hashed equivalent can serve lookups — a security-adjacent consideration layered on top of pure performance).
- **Unique index** on transaction reference numbers to prevent duplicate transaction processing (idempotency enforcement at the storage layer).

### Key Part 7 Concepts Applied
Composite index ordering (Module 5/10), unique indexes (Module 5), clustered index choice (Module 3/9), and the "avoid random-order primary keys" lesson (Module 3/6/9/12) — since sequential transaction IDs (not random UUIDs) keep the clustered B+ Tree insert-friendly.

## 13.2 E-commerce

### Dominant Query Patterns
- Product search/browse: `WHERE category = X AND price BETWEEN Y AND Z ORDER BY popularity`.
- `WHERE customer_id = X` (order history).
- Full-text search on product names/descriptions.
- Faceted filtering (multiple simultaneous filter conditions: brand, size, color, price range).

### Read/Write Profile
Extremely read-heavy (browsing vastly outnumbers purchasing), with periodic write bursts (flash sales, inventory updates).

### Indexing Strategy
- **Composite index** on `(category, price)` for the common browse pattern, following the equality-then-range ordering rule.
- **GIN index** (Module 8) on product description/name for full-text search.
- **Covering index** (Module 5/10) on frequently-displayed order-summary columns to enable Index-Only Scans for order history pages.
- **Bitmap Scan-friendly** design (Module 10) — multiple separate single-column indexes on facet columns (brand, color, size) can be combined via bitmap AND at query time, avoiding the need for one giant composite index covering every possible facet combination.
- Consider **partial indexes** (Module 5/8) on `WHERE in_stock = true`, since out-of-stock products are rarely relevant to browse queries.

### Key Part 7 Concepts Applied
GIN full-text indexing (Module 8), Bitmap Scans for multi-facet filtering (Module 10), partial indexes (Module 5), covering indexes for Index-Only order-history scans (Module 5/9's Visibility Map caveat relevant here too).

## 13.3 Inventory Management

### Dominant Query Patterns
- `WHERE warehouse_id = X AND sku = Y` (stock level checks — very frequent, low latency required).
- Bulk updates during stock reconciliation (large batch `UPDATE` operations).
- Low-stock alerting: `WHERE quantity < reorder_threshold`.

### Read/Write Profile
High write frequency (every sale/restock updates quantity), moderate read frequency, strong consistency needs (avoiding overselling).

### Indexing Strategy
- **Composite unique index** on `(warehouse_id, sku)` — enforces one row per warehouse/SKU pair while also serving as the primary lookup path.
- Be **cautious about over-indexing** here (Module 12) — this table sees extremely frequent `UPDATE`s to `quantity`; each additional index on `quantity` itself would be actively harmful (an index on a constantly-changing numeric value rarely helps and directly increases write amplification).
- Consider whether `quantity < reorder_threshold` alerting can be handled via a periodic batch query (sequential scan, Module 10) rather than a dedicated index, given this is typically a background/analytical check rather than a latency-critical user-facing path.

### Key Part 7 Concepts Applied
Composite unique indexes (Module 5), the "too many indexes hurts write-heavy tables" lesson applied directly (Module 12), and recognizing when NOT to index a frequently-changing column (Module 12's write-cost-budget step).

## 13.4 Healthcare

### Dominant Query Patterns
- `WHERE patient_id = X` (patient record lookups — extremely frequent).
- `WHERE patient_id = X AND record_date BETWEEN ...` (historical record ranges).
- Strict access control and audit logging requirements (every access must be logged — a write-heavy audit table alongside the read-heavy patient data).

### Read/Write Profile
Read-heavy for patient records themselves; the audit/access-log side is write-heavy and append-only.

### Indexing Strategy
- **Composite index** on `(patient_id, record_date)` for patient record history, same equality-then-range pattern as banking.
- The **audit log table** is an ideal candidate for a **BRIN index** (Module 8) on its timestamp column, since it's append-only and naturally physically correlated with insertion time, and the log is likely enormous relative to how often specific old entries are individually queried.
- Sensitive columns (diagnoses, medications) may warrant careful consideration of whether indexing them creates inappropriate query-pattern visibility even to database administrators — a security/compliance consideration intersecting with, but distinct from, pure performance indexing decisions.

### Key Part 7 Concepts Applied
Composite indexing for the primary record table (Module 5/10), BRIN for the audit log (Module 8) — a direct, realistic application of BRIN's "huge, append-only, time-correlated" ideal use case.

## 13.5 Ride Sharing

### Dominant Query Patterns
- **Geospatial**: "find nearby available drivers" (`WHERE location near (lat, lng)`).
- `WHERE driver_id = X` and `WHERE rider_id = X` (trip history).
- High-frequency location updates (drivers' positions update every few seconds).

### Read/Write Profile
Extremely high write frequency for location updates; latency-critical reads for "find nearby driver" matching.

### Indexing Strategy
- **GiST index** (Module 8) on driver location (point/geometry type) for efficient nearest-neighbor and radius queries — this is the textbook ideal GiST use case.
- Given the **extremely high write frequency** of location updates, consider whether every single position update needs to update the spatial index immediately, or whether a periodic batch/micro-batch update pattern (trading a small amount of location staleness for dramatically reduced write amplification, Module 12) is acceptable for this specific product requirement.
- Trip history tables benefit from composite indexes on `(driver_id, trip_date)` and `(rider_id, trip_date)` separately, following the equality-then-range pattern.

### Key Part 7 Concepts Applied
GiST spatial indexing (Module 8) as the centerpiece, combined with a real-world write-amplification trade-off discussion (Module 12) specific to extremely high-frequency location updates.

## 13.6 Social Media

### Dominant Query Patterns
- Feed generation: "posts from people I follow, most recent first" — a complex, often denormalized/fan-out query pattern.
- `WHERE user_id = X ORDER BY created_at DESC` (a user's own post history).
- Full-text search on post content, hashtags, mentions.
- Extremely skewed data distribution (a small number of "celebrity" accounts have vastly more followers/posts/engagement than typical accounts) — a direct, real-world example of Module 10's "cardinality alone doesn't capture skew" warning.

### Read/Write Profile
Extremely read-heavy for feed viewing, extremely write-heavy for post creation and engagement (likes/comments) at large scale.

### Indexing Strategy
- **Composite index** on `(user_id, created_at DESC)` (Module 8's descending index) for a user's own post history and profile pages.
- **GIN index** on hashtags/mentions arrays (Module 8) for hashtag search and mention notifications.
- Feed generation itself is often **not** solved by indexing alone at large scale — it typically requires denormalization/fan-out architectures (writing a post's reference into every follower's precomputed feed at post-time) that trade significant write amplification (Module 12) for dramatically simpler, faster feed-read queries — an explicit real-world instance of the read/write trade-off this entire handbook has emphasized.
- Given the extreme skew (celebrity accounts), naive "fan-out on write" doesn't scale for accounts with millions of followers — hybrid approaches (fan-out on write for typical accounts, fan-out on read/merge for celebrity accounts) are common in practice.

### Key Part 7 Concepts Applied
Descending composite indexes (Module 8), GIN for hashtag/mention search (Module 8), and — most importantly — a concrete real-world illustration of the fundamental read/write trade-off (Module 5/12) playing out at an architectural level beyond just "add an index."

## 13.7 Analytics / OLAP

### Dominant Query Patterns
- Aggregate queries over huge historical datasets: `SELECT SUM(...), AVG(...) GROUP BY ... WHERE date_range`.
- Rarely single-row point lookups; almost always large-range or full-table aggregation.

### Read/Write Profile
Very read-heavy (large batch queries), write activity often confined to periodic bulk ETL loads rather than continuous transactional writes.

### Indexing Strategy
- **BRIN indexes** (Module 8) are frequently ideal here — analytics tables are often enormous, append-mostly (new data periodically loaded), and naturally time-correlated.
- **Bitmap-index-style thinking** (Module 5/10) is highly relevant — low-cardinality dimension columns (region, category, product line) benefit from either PostgreSQL's runtime Bitmap Scan combining several single-column indexes, or (in dedicated OLAP engines like Oracle/columnar systems) genuine stored Bitmap Indexes.
- Since queries are aggregate-heavy rather than point-lookup-heavy, **columnar storage** (a concept beyond this module's row-store-focused scope, but worth knowing exists) often outperforms traditional B+ Tree indexing entirely for this workload shape — a good example of "sometimes the answer isn't a better index, it's a fundamentally different storage model."

### Key Part 7 Concepts Applied
BRIN (Module 8) as the star structure, Bitmap Scans (Module 10) for combining low-cardinality dimension filters, and recognizing indexing's limits relative to storage-model choice for this workload type.

## 13.8 Logging Systems

### Dominant Query Patterns
- Almost pure append (`INSERT`), extremely rarely `UPDATE`/`DELETE`.
- Reads are typically: recent-time-range lookups (`WHERE timestamp > NOW() - INTERVAL '1 hour'`), or occasional targeted searches (`WHERE trace_id = X` or full-text search over log messages).

### Read/Write Profile
Extremely write-heavy, append-only; reads are comparatively rare and often only touch recent data (older logs are frequently archived/deleted after a retention period).

### Indexing Strategy
- **Minimal indexing** is often correct here (Module 12's core lesson, applied to its most extreme case) — an append-only, write-dominated table benefits enormously from having as few indexes as possible.
- **BRIN index** (Module 8) on `timestamp` is close to ideal — extremely cheap to maintain on inserts, and naturally matches the physically-correlated, time-ordered nature of log data.
- If `trace_id` lookups are a genuine hot-path requirement, a dedicated B+ Tree or hash index (Module 6/7) on `trace_id` may be justified, but should be added deliberately (Module 12's Step 1: "do you actually need this?"), not by default.
- Consider **partitioning** by time range (a technique connecting forward to Part 8/9's broader architecture discussions) so that old, rarely-queried partitions can be dropped entirely (instant, cheap deletion) rather than requiring row-by-row `DELETE` + VACUUM cleanup (Module 11) for retention enforcement.

### Key Part 7 Concepts Applied
This case study is the purest real-world demonstration of Module 12's central warning: for extreme write-heavy, append-only workloads, the correct number of indexes is often **as close to zero as your actual query requirements allow** — BRIN (Module 8) being the rare exception that's cheap enough to almost always be worth it for the time column specifically.

## 13.9 Master Comparison Table — All Eight Domains

| Domain | Read/Write Profile | Primary Indexing Tool | Key Lesson Applied |
|---|---|---|---|
| Banking | Balanced, correctness-critical | Composite (account_id, date) + unique constraints | Sequential PKs, composite ordering |
| E-commerce | Read-heavy | Composite + GIN + partial + Bitmap Scan combos | Multi-facet filtering without one giant index |
| Inventory | Write-heavy on quantity | Composite unique (warehouse, sku), minimal extra indexing | Don't index constantly-changing columns |
| Healthcare | Read-heavy (records) + write-heavy (audit) | Composite (patient, date) + BRIN (audit log) | Right tool per sub-workload within one system |
| Ride Sharing | Extremely write-heavy (location) | GiST spatial index | Spatial indexing + write-amplification trade-off |
| Social Media | Extremely read + write heavy, skewed | Descending composite + GIN + fan-out architecture | Trade-off goes beyond indexing into architecture |
| Analytics/OLAP | Read-heavy, bulk-loaded | BRIN + Bitmap Scan + (columnar, beyond scope) | Sometimes a different storage model beats indexing |
| Logging Systems | Extremely write-heavy, append-only | BRIN only (minimal indexing) + partitioning | Fewest indexes is often correct |

## 13.10 Chapter Summary

- **Banking**: composite indexes ordered (equality, then range), unique constraints for idempotency, sequential (not random) primary keys.
- **E-commerce**: composite + GIN + partial indexes + Bitmap Scans for multi-facet, read-heavy browsing.
- **Inventory**: deliberately minimal indexing beyond the composite unique lookup key, given extreme write frequency on `quantity`.
- **Healthcare**: composite indexing for patient records, BRIN for the append-only audit log — different tools for different sub-workloads in the same system.
- **Ride Sharing**: GiST spatial indexing as the centerpiece, with an explicit write-amplification trade-off for high-frequency location updates.
- **Social Media**: descending composite + GIN indexes, but the deeper lesson is that feed generation at scale is often solved architecturally (fan-out), not purely through indexing.
- **Analytics/OLAP**: BRIN + Bitmap Scans, with columnar storage noted as sometimes superseding indexing entirely for this workload shape.
- **Logging Systems**: the purest case for minimal indexing — BRIN on timestamp, near-zero elsewhere, plus partitioning for cheap retention management.
- Across all eight domains, the same Module 12 framework applies — but the *correct answer* to "how much should I index?" varies dramatically based on read/write ratio, data correlation, and query pattern shape.

## 13.12 MCQs

**Q1.** Why should an inventory table's `quantity` column generally NOT be indexed?
A) It's a numeric type, which can't be indexed  B) It changes extremely frequently, making index maintenance costly relative to its query benefit  C) InnoDB doesn't support indexing numeric columns  D) It's always NULL
*(Answer: B)*

**Q2.** Which index type is the ideal fit for a ride-sharing app's "nearby drivers" query?
A) Hash index  B) BRIN  C) GiST  D) Reverse index
*(Answer: C)*

**Q3.** Why does social media feed generation often require architectural solutions beyond indexing?
A) Indexes don't work on social media data types  B) The query pattern (aggregating posts across many followed users) doesn't map cleanly onto a single table's index, especially at extreme scale with skewed follower counts  C) Social media platforms don't use relational databases  D) GIN indexes are illegal to use for this purpose
*(Answer: B)*

**Q4.** What makes BRIN indexes particularly well-suited to logging systems?
A) Logging systems have low write volume  B) Log data is append-only and naturally physically correlated with the timestamp column  C) BRIN indexes support full-text search natively  D) Logging systems never need to query by time
*(Answer: B)*

**Q5.** In the banking case study, why is a composite index ordered `(account_id, transaction_date)` rather than `(transaction_date, account_id)`?
A) Alphabetical column naming convention  B) `account_id` is typically equality-filtered while `transaction_date` is typically range-filtered, and equality columns should lead in a composite index  C) `transaction_date` cannot be indexed at all  D) It doesn't matter, both orders are equivalent
*(Answer: B)*
