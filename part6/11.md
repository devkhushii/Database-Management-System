# Part 6: Transactions & Concurrency Control

## Module 11: Isolation Levels

> This module is the payoff for everything we've built in Modules 5–10. Isolation levels are simply **named, standardized bundles of anomaly guarantees** — and now that you understand every anomaly (Module 5) and every mechanism used to prevent them (locking, timestamp ordering, OCC, MVCC — Modules 6–10), the isolation levels will make complete, mechanical sense rather than feeling like arbitrary memorization.

---

### 11.1 What Is an Isolation Level?

**Definition:** An **isolation level** is a setting, defined per-transaction (or per-connection as a default), that specifies **which concurrency anomalies the database guarantees to prevent**, and — implicitly — how much concurrency (performance) is sacrificed to provide that guarantee.

**Why they exist:** Not every application needs the strongest possible guarantee for every transaction. A dashboard showing "approximate active users right now" can tolerate anomalies that a funds-transfer transaction absolutely cannot. Isolation levels let developers **choose** the right point on the correctness-vs-performance spectrum, transaction by transaction if needed.

**The SQL standard defines four isolation levels**, ordered from weakest to strongest:

```
READ UNCOMMITTED  →  READ COMMITTED  →  REPEATABLE READ  →  SERIALIZABLE
   (weakest)                                                  (strongest)
```

A fifth, related concept — **Snapshot Isolation** — is not part of the original SQL standard's four levels but is widely implemented (and often used as the practical implementation *behind* `REPEATABLE READ` or even `SERIALIZABLE` labels in some engines) — we cover it explicitly since it's essential to understanding real-world engine behavior (Module 10).

---

### 11.2 Read Uncommitted

**Definition:** The weakest isolation level. Transactions can read data written by other transactions **even if those transactions haven't committed yet.**

**Anomalies allowed:** Dirty Read, Non-Repeatable Read, Phantom Read, Lost Update, Write Skew — essentially everything except Dirty Write (which is prevented at every level, Module 5.4).

**Anomalies prevented:** Dirty Write only.

**Why would anyone use this?** In practice, almost never for correctness-sensitive work. It might be used for:
- Rough, approximate monitoring/reporting queries where exact correctness truly doesn't matter and maximum read throughput is prioritized.
- Historically, some engines used it to avoid blocking on long-running reporting queries — though MVCC-based Snapshot Isolation (Module 10) has largely eliminated the need for this trade-off in modern systems, since MVCC gives you non-blocking reads *without* the dirty-read risk.

**Engine note:** Interestingly, **PostgreSQL does not actually implement true Read Uncommitted behavior** — if you request it, PostgreSQL silently treats it as `READ COMMITTED` instead, since its MVCC architecture makes true dirty reads unnecessary and undesirable to support. This is a well-known, frequently-tested PostgreSQL quirk.

---

### 11.3 Read Committed

**Definition:** A transaction only ever sees data that has been **committed** by other transactions — it never sees another transaction's in-progress, uncommitted changes.

**Anomalies prevented:** Dirty Read, Dirty Write.
**Anomalies allowed:** Non-Repeatable Read, Phantom Read, Lost Update (in some implementations), Write Skew.

**How it's implemented:**
- **Locking-based engines (e.g., SQL Server default):** Shared locks are acquired for reads but released **immediately after each individual statement** (not held for the whole transaction) — this is why a second read of the same row within the same transaction can see a different, newer committed value (non-repeatable read is allowed).
- **MVCC-based engines (PostgreSQL, InnoDB under READ COMMITTED explicitly, Oracle):** Each **statement** gets a fresh snapshot of the database as of the moment that statement begins — so two different statements within the same transaction can see different snapshots, again allowing non-repeatable reads, but without ever blocking on a writer.

**Timeline example (MVCC-based Read Committed):**

```
T1: BEGIN
    SELECT balance FROM accounts WHERE id='A';  -- snapshot taken NOW, sees 1000
    -- (T2 commits an update to 900 here)
    SELECT balance FROM accounts WHERE id='A';  -- NEW snapshot taken for THIS statement, sees 900
    COMMIT
```

**Default in:** PostgreSQL, Oracle, SQL Server (all default to Read Committed). **Notably NOT the default in MySQL/InnoDB**, which defaults to Repeatable Read — a very common interview trivia point.

---

### 11.4 Repeatable Read

**Definition:** In addition to Read Committed's guarantees, a transaction that reads a row **once** is guaranteed to see the **same value** if it reads that **same row again** later in the same transaction — no other transaction's committed update can change what this transaction sees for rows it has already read.

**Anomalies prevented:** Dirty Read, Dirty Write, Non-Repeatable Read.
**Anomalies allowed (in the strict SQL-standard sense):** Phantom Read, Write Skew.

**How it's implemented:**
- **MVCC-based engines:** A **single snapshot** is taken at the **start of the transaction** (or its first statement) and used for **every** statement within that transaction — this is exactly what guarantees repeatable reads: since the snapshot never changes, re-reading the same row always shows the same version.
- **Locking-based engines:** Shared locks on read rows are held until the **end of the transaction** (not released after each statement, unlike Read Committed) — physically preventing any other transaction from modifying a row this transaction has read.

**Important engine-specific nuance — InnoDB and phantom reads:** While the SQL standard says Repeatable Read still *allows* phantom reads, **InnoDB's implementation of REPEATABLE READ actually prevents most phantom-read scenarios in practice**, using its **gap locks** and **next-key locking** mechanisms (Module 6 mentioned this briefly) — a genuinely distinctive, frequently-tested InnoDB behavior that goes beyond the bare SQL-standard requirement for this isolation level.

**Default in:** MySQL/InnoDB (their default isolation level).

---

### 11.5 Serializable

**Definition:** The strongest isolation level. Guarantees that the result of executing a set of concurrent transactions is **equivalent to some serial execution** of those same transactions (Module 4's Serializability, made real).

**Anomalies prevented:** Everything — Dirty Read, Dirty Write, Non-Repeatable Read, Phantom Read, Lost Update, **and Write Skew.**

**How it's implemented (two fundamentally different approaches, both valid):**
1. **Two-Phase Locking (2PL)-based Serializable:** Full Strict/Rigorous 2PL, including range/predicate locks to prevent phantoms — this is the traditional, lock-heavy approach (e.g., SQL Server's `SERIALIZABLE` isolation level).
2. **Serializable Snapshot Isolation (SSI):** An MVCC-based approach (used by PostgreSQL's `SERIALIZABLE` level) that starts from ordinary Snapshot Isolation (Module 10) but **additionally tracks read-write dependencies** between concurrent transactions to detect the specific patterns (including write skew!) that could create a cycle in an implicit "serialization graph" — and aborts one of the transactions involved if such a pattern is detected, **without ever needing predicate locks or heavy blocking**.

**Why SSI matters as an interview topic:** SSI is a relatively modern (2008 paper, adopted by PostgreSQL in version 9.1) and elegant solution to exactly the write-skew gap in plain Snapshot Isolation (Module 5.8, Module 10.5) — it's a great topic to bring up to demonstrate depth beyond textbook 2PL-based serializability.

**Cost:** Serializable isolation, whichever mechanism implements it, typically has the **highest abort/retry rate or the most blocking** of any isolation level — application code using `SERIALIZABLE` must be prepared to **retry transactions** that fail with a serialization error.

### 11.6 Anomaly Prevention Matrix (The Master Table)

| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read | Write Skew |
|---|---|---|---|---|
| Read Uncommitted | ❌ Allowed | ❌ Allowed | ❌ Allowed | ❌ Allowed |
| Read Committed | ✅ Prevented | ❌ Allowed | ❌ Allowed | ❌ Allowed |
| Repeatable Read | ✅ Prevented | ✅ Prevented | ❌ Allowed (SQL standard)* | ❌ Allowed |
| Snapshot Isolation | ✅ Prevented | ✅ Prevented | ✅ Mostly Prevented | ❌ **Allowed** |
| Serializable | ✅ Prevented | ✅ Prevented | ✅ Prevented | ✅ Prevented |

*\*InnoDB's specific REPEATABLE READ implementation prevents most phantoms via gap locks, exceeding the bare SQL-standard requirement.*

**This table is one of the single most important tables in the entire handbook — memorize it completely.** It is asked about, in some form, in nearly every database-related interview at every level.

### 11.7 Default Isolation Levels — Engine Comparison

| Database | Default Isolation Level | Primary Mechanism |
|---|---|---|
| **PostgreSQL** | Read Committed | MVCC (per-statement snapshot) |
| **MySQL (InnoDB)** | Repeatable Read | MVCC + row locking (per-transaction snapshot) |
| **Oracle** | Read Committed | MVCC (per-statement snapshot, via undo segments) |
| **SQL Server** | Read Committed (lock-based by default; snapshot-based if `READ_COMMITTED_SNAPSHOT` is enabled) | Locking by default; optional MVCC |

**This comparison table is asked constantly in interviews** — especially "why does MySQL default to a stricter isolation level than PostgreSQL?" (Historical/engine-design reasons — InnoDB's gap-locking approach was designed to make Repeatable Read practical and safe as a sensible default, whereas PostgreSQL's architecture makes Read Committed's per-statement snapshot cheap and sufficient for most workloads by default.)

### 11.8 Setting Isolation Levels — Syntax

```sql
-- Standard SQL (works in PostgreSQL, SQL Server, Oracle with syntax variations)
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN;
  -- your transaction here
COMMIT;

-- PostgreSQL — per-transaction
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
  -- ...
COMMIT;

-- MySQL — per-session or per-transaction
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- or:
START TRANSACTION;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

### 11.9 Choosing the Right Isolation Level — A Decision Framework

**Ask these questions, in order:**

1. **Does this transaction only read data, with no correctness-critical multi-step logic?** → Read Committed is usually sufficient and offers the best performance.
2. **Does this transaction need to read the same row(s) multiple times and require them to stay consistent throughout?** → Repeatable Read (or Snapshot Isolation).
3. **Does this transaction enforce an invariant that spans multiple rows or involves a check based on the combined state of several items** (the classic write-skew setup, Module 5.8)? → You need **Serializable**, or explicit locking (`SELECT ... FOR UPDATE`) around the invariant check.
4. **Is this a high-throughput, high-contention hot path** (e.g., a popular product's inventory counter)? → Consider whether the strongest correctness guarantee is truly necessary, or whether a narrower, purpose-built mechanism (e.g., an atomic increment, or a dedicated queue) would be more appropriate than blanket `SERIALIZABLE`.

**Best Practice:** Don't default to `SERIALIZABLE` "just to be safe" everywhere — identify the *specific* anomalies relevant to each transaction's business logic and choose the minimum sufficient isolation level, reserving `SERIALIZABLE` (with its retry-handling requirements) for the specific transactions that truly need it.

### 11.10 Full Worked Comparison — Same Scenario, Four Isolation Levels

**Scenario:** T1 reads account balance twice, with T2 committing an update to that balance in between T1's two reads.

```
READ UNCOMMITTED:
  T1 Read 1: sees T2's value even BEFORE T2 commits (dirty read possible)
  T1 Read 2: sees T2's committed value
  → Two DIFFERENT values seen, and possibly one that was never truly committed.

READ COMMITTED:
  T1 Read 1: sees pre-T2 committed value (T2 hasn't committed yet)
  T1 Read 2: sees T2's NEW committed value (fresh snapshot per statement)
  → Two DIFFERENT (but both legitimately committed) values — non-repeatable read.

REPEATABLE READ:
  T1 Read 1: sees pre-T2 value; snapshot fixed for the whole transaction
  T1 Read 2: STILL sees the pre-T2 value (same snapshot, T2's commit is invisible to T1)
  → SAME value both times — non-repeatable read prevented.

SERIALIZABLE:
  Same as Repeatable Read for this specific 2-read scenario, PLUS: if T1 later
  tries to WRITE based on its reads in a way that would conflict with T2's
  concurrent write (e.g., a write-skew-style invariant), the system detects
  and aborts one of the transactions to preserve full serializability.
```

### 11.11 Advantages, Disadvantages, Best Practices

**Advantages of understanding isolation levels deeply:**
- Enables precise, deliberate correctness-vs-performance trade-offs rather than guessing or over-engineering.
- Prevents both under-protection (subtle production bugs from anomalies like write skew) and over-protection (unnecessary throughput loss from blanket Serializable usage).

**Disadvantages / risks of getting it wrong:**
- Choosing too weak a level: silent data corruption bugs that may not surface until specific concurrent timing occurs — often extremely hard to reproduce and debug.
- Choosing too strong a level: unnecessary throughput loss, increased abort/retry rates, more complex application-level retry logic required.

**Best Practices:**
- Always know and document which isolation level your application relies on, and why, for each critical transaction.
- Test concurrent scenarios explicitly (not just single-threaded correctness) — many concurrency bugs simply never appear in normal single-user testing.
- Implement retry logic for any transaction run under `SERIALIZABLE` (or under MVCC engines' write-conflict serialization errors), since aborts are an expected, normal part of using stronger isolation levels.

**Common Mistakes:**
- Assuming your ORM's default isolation level matches your intent — many ORMs simply use the database's default (often Read Committed), which may be insufficient for specific business-critical operations.
- Forgetting that MySQL's default (Repeatable Read) is stricter than PostgreSQL's default (Read Committed) when porting application logic between the two — a very common, real production migration bug source.
- Believing "Snapshot Isolation" and "Serializable" are synonyms — they are **not**, due to write skew (Module 5.8, Module 10.5).

**Performance Implications:** Each step up the isolation ladder generally trades some concurrency/throughput for stronger correctness guarantees — the exact cost depends heavily on the engine's specific implementation mechanism (locking vs. MVCC vs. SSI), covered further with concrete numbers in Module 16.

**Industry Usage:** Financial transaction systems and inventory/booking systems with strict invariants typically use `SERIALIZABLE` for their most critical operations, while using `READ COMMITTED` for the bulk of ordinary read/write traffic — a hybrid, deliberate strategy rather than a single blanket setting.

### 11.12 Chapter Summary

- Isolation levels are standardized bundles of anomaly-prevention guarantees, from weakest (**Read Uncommitted**) to strongest (**Serializable**).
- **Read Uncommitted**: allows dirty reads (rarely truly implemented — PostgreSQL maps it to Read Committed).
- **Read Committed**: prevents dirty reads only; default for PostgreSQL, Oracle, SQL Server.
- **Repeatable Read**: also prevents non-repeatable reads; default for MySQL/InnoDB; InnoDB additionally fights phantoms via gap locks.
- **Serializable**: prevents everything, including write skew; implemented via full 2PL+predicate locking OR Serializable Snapshot Isolation (PostgreSQL's approach).
- **Snapshot Isolation** (MVCC's natural level) prevents everything except **write skew** — a critical, frequently-tested distinction from true Serializable.
- Choose isolation level deliberately, per-transaction, based on the specific anomalies that matter for that transaction's business logic.

### 11.13 Revision Notes / Cheat Sheet

```
READ UNCOMMITTED  : prevents DIRTY WRITE only
READ COMMITTED    : + prevents DIRTY READ
REPEATABLE READ   : + prevents NON-REPEATABLE READ
SNAPSHOT ISOLATION: + prevents most PHANTOMS, READ SKEW  |  still allows WRITE SKEW
SERIALIZABLE      : + prevents WRITE SKEW and everything else

Defaults: PostgreSQL=Read Committed | MySQL/InnoDB=Repeatable Read | Oracle=Read Committed | SQL Server=Read Committed
```
