## 3.0 Why This Module Exists

Module 2 briefly introduced Query Rewrite as a rule-based pre-processing phase. This module is a **deep dive** into every major transformation technique — the actual rules real optimizers apply, each shown with **before/after query trees** so you can see exactly how a query is reshaped before cost-based search even begins.

These transformations matter because they:
1. **Shrink the search space** the cost-based optimizer must explore (Module 2, §2.6).
2. **Reduce intermediate result sizes**, which is often the single biggest lever for query performance.
3. Turn queries that *look* different but are *logically equivalent* into a **canonical form**, so the optimizer doesn't have to separately "learn" every possible way a developer might phrase the same intent.

## 3.1 Predicate Pushdown

### Definition

**Predicate Pushdown** moves filter conditions (`WHERE`/`ON` predicates) as close as possible to the base tables (the leaves of the query tree), so rows are eliminated **before** expensive operations like joins, sorts, or aggregations touch them.

### Why It Exists

The later a filter is applied, the more rows survive to be processed by expensive intermediate operators. If you can discard 99% of rows via a filter *before* a join, the join only has to process 1% of the data — a massive win, since joins are typically the most expensive operators in a plan.

### Real-Life Analogy

Imagine a factory assembly line: workers upstream inspect and reject 90% of defective raw materials **before** they reach the expensive final-assembly machine, rather than assembling everything first and discarding the finished (but defective) products at the end. Filtering early avoids wasting expensive downstream work on rows that will just get thrown away.

### Before / After Example

```sql
SELECT u.name, o.amount
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.country = 'IN';
```

**BEFORE (naive tree — filter applied after join):**

```
        π (name, amount)
              │
        σ (country = 'IN')
              │
        ⋈ (u.id = o.user_id)
        /                  \
     users                orders
```
*Problem: the join processes ALL users × orders combinations, THEN filters. If only 5% of users are from 'IN', 95% of join work was wasted.*

**AFTER (predicate pushed down to the leaf):**

```
        π (name, amount)
              │
        ⋈ (u.id = o.user_id)
        /                  \
  σ(country='IN')          orders
       │
     users
```
*Now the filter runs first, shrinking `users` before it ever reaches the join — the join processes far fewer rows.*

### Internal Working / Optimizer Behavior

The optimizer walks the query tree and, for each selection (σ) node, checks whether the predicate references columns from only **one side** of a join. If so, and the predicate doesn't change semantics (careful with outer joins — see Edge Cases below), it's algebraically valid to move the σ below the join, closer to the relevant table.

### PostgreSQL vs MySQL vs Oracle

| Aspect | PostgreSQL | MySQL | Oracle |
|---|---|---|---|
| Support | Full, including into subqueries/CTEs (materialized CTEs historically blocked this — see §3.7) | Full ("Condition Pushdown"), including into derived tables since 8.0 | Full, very mature, includes pushdown into views |
| Terminology | "Predicate pushdown" / qual propagation | "Condition pushdown" | "Predicate pushing" |

### Edge Cases
- **Outer Joins:** Pushing a predicate below a `LEFT JOIN` can silently change semantics! `WHERE o.amount > 100` in a `LEFT JOIN` context, if naively pushed below the join, would turn it into an inner join behavior for NULL-producing rows. Optimizers must prove the predicate is **NULL-rejecting** (i.e., it can never be true for a NULL) before safely pushing it past an outer join.
- Predicates involving **non-deterministic functions** (e.g., `RANDOM()`) generally cannot be pushed, since re-evaluating them at a different point would change results.

### Common Mistakes
- Assuming pushdown *always* happens automatically for every predicate — complex expressions, certain function calls, or predicates spanning multiple tables may block pushdown.
- Writing filters in application code (fetch-all-then-filter) instead of `WHERE`, bypassing pushdown entirely — a very common real-world performance anti-pattern.

### Interview Importance: ⭐⭐⭐⭐⭐
One of the **most commonly cited** optimization techniques in interviews. Know the outer-join caveat — it's a favorite "gotcha" follow-up question.

## 3.2 Projection Pushdown

### Definition

**Projection Pushdown** eliminates unused columns as early as possible in the query tree, so intermediate results carry only the columns actually needed downstream.

### Why It Exists

Carrying unnecessary columns through joins, sorts, and aggregations wastes memory bandwidth, buffer space, and (for column-store engines) disk I/O. Trimming columns early reduces the "width" of intermediate tuples flowing through the plan.

### Before / After Example

```sql
SELECT u.name
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.amount > 100;
```

Suppose `users` has 20 columns (address, phone, email, etc.) but we only need `name` and `id` (for the join).

**BEFORE (no projection pushdown):**
```
     π (name)
        │
     ⋈ (id = user_id)
     /              \
  users (ALL 20      orders (ALL columns)
   columns carried)
```

**AFTER (projection pushed down):**
```
     π (name)
        │
     ⋈ (id = user_id)
     /              \
π(id, name)        π(user_id, amount)
   │                    │
 users                orders
```
*Only the columns actually needed flow into the join — dramatically less data movement, especially impactful for wide tables.*

### Optimizer & Engine Behavior

This is especially powerful for **columnar storage engines** (like analytical extensions or OLAP systems) where reading fewer columns literally means reading fewer disk blocks. Even in row-store engines (like standard PostgreSQL/MySQL/Oracle heap tables), projection pushdown reduces the size of tuples copied through each operator, saving CPU and memory bandwidth.

### Interview Importance: ⭐⭐⭐
Less flashy than predicate pushdown but frequently paired with it in "name two ways the optimizer reduces intermediate data size" questions.

## 3.3 Join Reordering

### Definition

**Join Reordering** changes the order in which tables are joined (while preserving the result's correctness, since inner joins are commutative and associative) to minimize the size of intermediate results and overall cost.

### Why It Exists

Joining tables in a *bad* order can produce enormous intermediate results, even if the final result is small. Join reordering seeks the order that keeps intermediate results as small as possible at every step.

### Before / After Example

```sql
SELECT *
FROM small_table s      -- 100 rows
JOIN medium_table m ON s.id = m.small_id     -- 10,000 rows
JOIN huge_table h ON m.id = h.medium_id      -- 10,000,000 rows
WHERE s.category = 'X';   -- matches only 5 rows of small_table
```

**BEFORE (naive left-to-right order as written, huge_table joined last against a big intermediate):**
```
                ⋈ (m.id = h.medium_id)
               /                      \
        ⋈ (s.id = m.small_id)      huge_table (10M rows)
        /                  \
  σ(category='X')       medium_table
   small_table
   (→ 5 rows)
```
*If `medium_table` joined against the 5 filtered rows produces, say, 500 rows, then joining 500 rows against 10M is manageable — but a poor plan might instead join `medium_table` and `huge_table` FIRST (10,000 × 10,000,000 potential combinations before ever touching the small, highly selective filter), producing a massive, wasteful intermediate result.*

**AFTER (optimizer reorders to filter+join the smallest/most selective relations first):**
```
                ⋈ (m.id = h.medium_id)
               /                      \
        ⋈ (s.id = m.small_id)      huge_table
        /                  \
  σ(category='X')       medium_table
  (5 rows — tiny!)
```
*By ensuring the highly selective filter and smallest table combine first, every subsequent join operates on the smallest possible intermediate result — this is the essence of good join ordering.*

### How the Optimizer Decides

This connects directly to Module 2's **Dynamic Programming** (§2.8) and **cardinality estimation** (Module 4) — the optimizer computes/estimates the size of every possible intermediate join result and picks the ordering that minimizes cumulative cost, not just the final result size.

### Interview Importance: ⭐⭐⭐⭐⭐
Extremely common. Be ready to explain *why* join order matters using an intermediate-result-size argument, and connect it explicitly to Module 2's DP algorithm.

## 3.4 Constant Folding

### Definition

**Constant Folding** evaluates expressions involving only constant values **at optimization time**, replacing them with their precomputed result, so the expression isn't re-evaluated for every row during execution.

### Why It Exists

If an expression's inputs are all constants, its value is fixed and known before execution even starts — there is zero reason to recompute it millions of times, once per row.

### Before / After Example

```sql
SELECT * FROM orders WHERE amount > 50 + 50;
```

**BEFORE:**
```
σ (amount > 50 + 50)     ← "50 + 50" evaluated PER ROW, wastefully
     │
   orders
```

**AFTER (constant folded at optimization time):**
```
σ (amount > 100)         ← computed ONCE, at optimization time
     │
   orders
```

### Another Example (Date Arithmetic — very common in practice)

```sql
WHERE order_date > CURRENT_DATE - INTERVAL '30 days'
```
Depending on the database, this may be folded once per query execution (since `CURRENT_DATE` is fixed for the duration of a single statement in most systems) rather than recomputed per row.

### Interview Importance: ⭐⭐
Simple but foundational — often asked as a quick "what's the difference between constant folding and constant propagation" pairing (next section).

## 3.5 Constant Propagation

### Definition

**Constant Propagation** takes a known constant value bound to a variable/column (typically via an equality predicate) and substitutes that constant into *other* expressions/predicates referencing the same column, enabling further simplification or even additional pushdown/pruning.

### Why It Exists

If we know `x = 5` from one predicate, and another predicate elsewhere uses `x`, we can substitute `5` directly — potentially enabling constant folding, pruning of dead branches, or even index usage that wouldn't otherwise be recognized as applicable.

### Before / After Example

```sql
SELECT * FROM orders o, order_limits l
WHERE o.region = 'APAC'
  AND l.region = o.region
  AND l.max_amount > 1000;
```

**BEFORE:**
```
σ(o.region='APAC' AND l.region=o.region AND l.max_amount>1000)
              │
      ⋈ (some join condition)
      /                      \
   orders                order_limits
```

**AFTER (constant propagated: since o.region = 'APAC', substitute into l.region = o.region):**
```
σ(o.region='APAC' AND l.region='APAC' AND l.max_amount>1000)
              │
      ⋈ (some join condition)
      /                      \
σ(region='APAC')        σ(region='APAC', max_amount>1000)
   orders                 order_limits
```
*Now BOTH tables can be filtered by the literal `'APAC'` value independently — and each filter can be pushed down (§3.1) to its own base table, and potentially use an index on `region` directly, whereas before, `l.region = o.region` alone (a column-to-column comparison) could not be pushed down or use an index seek on a literal.*

### Interview Importance: ⭐⭐⭐
Good follow-up depth after discussing predicate pushdown — shows you understand *why* some predicates become push-able only after another transformation enables them (transformations often **compose**).

## 3.6 Expression Simplification

### Definition

**Expression Simplification** applies algebraic and logical identities to reduce the complexity of expressions in the query tree — removing redundant conditions, simplifying boolean logic, and eliminating dead branches.

### Common Simplification Rules

| Original | Simplified | Rule |
|---|---|---|
| `WHERE TRUE AND age > 18` | `WHERE age > 18` | Identity elimination |
| `WHERE FALSE OR age > 18` | `WHERE age > 18` | Identity elimination |
| `WHERE age > 18 AND age > 18` | `WHERE age > 18` | Duplicate elimination |
| `WHERE NOT (NOT (age > 18))` | `WHERE age > 18` | Double negation elimination |
| `WHERE 1 = 0` | Query returns **no rows** (short-circuit; plan can skip execution) | Contradiction detection |
| `WHERE age > 18 OR TRUE` | Entire predicate collapses to always-true (no filter needed) | Tautology detection |
| `WHERE x IN (5)` | `WHERE x = 5` | IN-list-of-one simplification |

### Before / After Example

```sql
SELECT * FROM users WHERE 1=1 AND age > 18 AND (TRUE OR age < 0);
```

**BEFORE:**
```
σ (1=1 AND age>18 AND (TRUE OR age<0))
        │
      users
```

**AFTER (fully simplified):**
```
σ (age > 18)
     │
   users
```

### Interview Importance: ⭐⭐
Usually a quick conceptual question, but valuable for understanding how generated SQL (e.g., from ORMs, which often produce redundant conditions like `1=1` as a query-building convenience) gets cleaned up automatically before optimization.

## 3.7 View Merging

### Definition

**View Merging** (also called **view expansion** or **inlining**) replaces a reference to a view with the view's underlying defining query, merging it directly into the outer query's tree — so the optimizer can reason about (and optimize) the whole thing as a single unified query, rather than treating the view as an opaque black box.

### Why It Exists

Without view merging, predicates in the outer query couldn't be pushed *into* the view's logic, and the optimizer would be forced to materialize the entire view's result before applying outer filters — often catastrophically wasteful.

### Before / After Example

```sql
CREATE VIEW active_orders AS
  SELECT * FROM orders WHERE status = 'ACTIVE';

SELECT * FROM active_orders WHERE amount > 1000;
```

**BEFORE (naive — view treated as a black box):**
```
     σ (amount > 1000)
            │
     [active_orders VIEW]     ← treated opaquely, entire view materialized
            │                    first (ALL active orders), then filtered
     σ (status='ACTIVE')
            │
         orders
```

**AFTER (view merged — becomes one unified tree, predicates combine):**
```
     σ (status='ACTIVE' AND amount > 1000)
            │
         orders
```
*Now this can be further optimized as a single query — e.g., if there's a composite index on `(status, amount)`, the optimizer can use it directly, which was impossible when the view was an opaque boundary.*

### When View Merging Is NOT Possible

- Views containing `GROUP BY`, `DISTINCT`, `UNION`, aggregate functions, or `LIMIT` often **cannot** be freely merged (merging could change semantics) — these are handled with more restricted transformation rules, or the view is executed as a separate, materialized step.
- **Materialized Views** (Part 3/10 territory) are, by design, pre-computed and stored — they're a different mechanism entirely (persisted results vs. logical inlining) and are not "merged" the same way.

### PostgreSQL vs MySQL vs Oracle

| Aspect | PostgreSQL | MySQL | Oracle |
|---|---|---|---|
| View merging | Yes, extensive, including many complex cases | Yes ("merge" algorithm for views, vs. "temptable" algorithm as fallback) | Yes, very mature (`_complex_view_merging` and related mechanisms) |
| Fallback when merging isn't possible | View executed as subquery/CTE-like separate step | MySQL's "temptable" algorithm materializes the view separately | Similar materialization fallback |

### Interview Importance: ⭐⭐⭐⭐
Common question: *"Does querying a view hurt performance?"* — Correct answer: generally **no**, because of view merging; the optimizer usually "sees through" it and optimizes the combined query as a whole. Know the exceptions (aggregates, `DISTINCT`, etc.).

## 3.8 Subquery Unnesting

### Definition

**Subquery Unnesting** (also called **subquery flattening**) transforms a nested subquery (in `WHERE`, `FROM`, or elsewhere) into an equivalent **join**, allowing the cost-based optimizer's full join-ordering and access-path machinery to apply — machinery that often doesn't apply to a subquery executed as a separate, isolated nested step.

### Why It Exists

A naive execution of a subquery-as-written can be executed **once per outer row** (if correlated — see §3.10) or as a separate materialized step (if uncorrelated) — both of which can be far more expensive than an equivalent join, which the optimizer knows how to reorder, index, and hash-join efficiently.

### Before / After Example (Uncorrelated Subquery)

```sql
SELECT name FROM users
WHERE id IN (SELECT user_id FROM orders WHERE amount > 1000);
```

**BEFORE (naive — subquery as a separate step):**
```
     σ (id IN <subquery result>)
            │
          users
     
     [Subquery executed separately, materialized as a list:]
            σ (amount > 1000)
                  │
                orders
```
*The subquery result must be fully computed (potentially as a large list) before the outer filter can even begin checking membership.*

**AFTER (unnested into a semi-join):**
```
     ⋉ (SEMI-JOIN: users.id = orders.user_id)
     /                                       \
   users                          σ (amount > 1000)
                                        │
                                     orders
```
*A **semi-join** (⋉) returns rows from the left side that have **at least one** match on the right, without duplicating rows even if multiple matches exist (unlike a regular join) — exactly matching `IN`/`EXISTS` semantics, but now the optimizer can choose the best join algorithm and access paths for this operation, and reorder it relative to other joins in the query.*

### The Semi-Join and Anti-Join Operators

| SQL Construct | Relational Algebra Operator | Meaning |
|---|---|---|
| `WHERE x IN (subquery)` | Semi-Join (⋉) | Keep left rows with ≥1 match on right |
| `WHERE EXISTS (correlated subquery)` | Semi-Join (⋉) | Same as above, correlated form |
| `WHERE x NOT IN (subquery)` | Anti-Join (▷, careful with NULLs!) | Keep left rows with **zero** matches on right |
| `WHERE NOT EXISTS (subquery)` | Anti-Join (▷) | Same as above |

### Edge Case: NOT IN and NULLs (Famous Gotcha)

```sql
SELECT name FROM users WHERE id NOT IN (SELECT user_id FROM orders);
```
If `orders.user_id` contains **even a single NULL**, `NOT IN` returns **zero rows** for the entire query — a three-valued-logic (NULL) trap, because `id <> NULL` evaluates to `UNKNOWN`, not `TRUE`, breaking the `NOT IN` entirely. Optimizers must be extremely careful transforming `NOT IN` into an anti-join and typically add an explicit NULL-check guard clause to preserve correct semantics. **This is one of the most notorious SQL correctness gotchas**, frequently asked in interviews.

### Interview Importance: ⭐⭐⭐⭐⭐
The `NOT IN` + NULL gotcha is an **extremely common interview and real-world bug question**. Know it cold, and know that `NOT EXISTS` is the generally safer alternative.

## 3.9 Common Subexpression Elimination (CSE)

### Definition

**Common Subexpression Elimination** detects when the same expression is computed multiple times within a query and replaces redundant computations with a single, shared evaluation.

### Before / After Example

```sql
SELECT price * quantity AS subtotal,
       (price * quantity) * 0.18 AS tax
FROM order_items;
```

**BEFORE:** `price * quantity` computed **twice** per row (once for `subtotal`, once inside the `tax` expression).

**AFTER (CSE applied):** The optimizer/executor computes `price * quantity` **once** per row, storing it in a temporary slot, and reuses that value for both output columns.

```
Compute once:  tmp = price * quantity
Output:        subtotal = tmp
               tax = tmp * 0.18
```

### Where This Also Applies: Repeated Subqueries

```sql
SELECT * FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders)
  AND amount < (SELECT AVG(amount) FROM orders) * 2;
```
A smart optimizer recognizes `(SELECT AVG(amount) FROM orders)` appears twice and computes it **once**, reusing the cached scalar result — rather than scanning the entire `orders` table twice for the same aggregate.

### Interview Importance: ⭐⭐⭐
Good to mention as a general compiler-optimization concept applied to SQL — shows breadth of understanding connecting to general CS principles (this exact concept exists in compiler design for programming languages too).

## 3.10 Query Decorrelation

### Definition

**Query Decorrelation** transforms a **correlated subquery** (one that references columns from the outer query) into an equivalent **join-based** form, removing the row-by-row dependency so it can be executed efficiently as a set-based operation instead of "once per outer row."

### Why It Exists

A correlated subquery, executed naively, runs **once for every row of the outer query** — this is effectively a Nested Loop pattern with a (potentially expensive) subquery as the "inner loop body," which can be catastrophic for large outer tables. Decorrelation converts this into a single join, letting the optimizer apply hash joins, proper indexing, and join reordering.

### Before / After Example

```sql
SELECT u.name
FROM users u
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.user_id = u.id AND o.amount > 1000
);
```

**BEFORE (naive correlated execution — conceptually "once per outer row"):**
```
FOR EACH row in users:
    run subquery: SELECT 1 FROM orders 
                  WHERE user_id = <this row's id> AND amount > 1000
    IF subquery returns ≥1 row: KEEP this user row
```
*If `users` has 1,000,000 rows, this could mean 1,000,000 separate subquery executions — extremely expensive without decorrelation.*

**AFTER (decorrelated into a semi-join, §3.8):**
```
     ⋉ (SEMI-JOIN: u.id = o.user_id)
     /                              \
   users                   σ (amount > 1000)
                                  │
                               orders
```
*Now this executes as a **single** set-based join operation (which can use a Hash Join, Module 6) instead of a million separate subquery invocations.*

### A Harder Case: Correlated Subquery in SELECT list

```sql
SELECT u.name,
       (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) AS order_count
FROM users u;
```

This is decorrelated by transforming into a **LEFT JOIN with a pre-aggregated subquery**:

**AFTER (decorrelated):**
```sql
SELECT u.name, COALESCE(agg.cnt, 0) AS order_count
FROM users u
LEFT JOIN (
  SELECT user_id, COUNT(*) AS cnt FROM orders GROUP BY user_id
) agg ON u.id = agg.user_id;
```
```
        π (name, COALESCE(cnt, 0))
                  │
        ⟕ (LEFT JOIN: u.id = agg.user_id)
        /                              \
      users                    γ (GROUP BY user_id, COUNT(*))
                                        │
                                     orders
```
*The aggregate is computed **once, for all users at once** (via `GROUP BY`) rather than once per outer row — this is a textbook, very high-value transformation.*

### PostgreSQL vs MySQL vs Oracle

| Aspect | PostgreSQL | MySQL | Oracle |
|---|---|---|---|
| Decorrelation maturity | Strong for `EXISTS`/`IN`; historically weaker for complex correlated scalar subqueries (steadily improving across versions) | Historically weak; MySQL 8.0+ significantly improved subquery optimization (semi-join strategies) | Very mature — one of the most sophisticated decorrelation/unnesting engines in the industry |

### Interview Importance: ⭐⭐⭐⭐⭐
**Very high.** "Why is a correlated subquery often slow, and how would you rewrite it as a join?" is an extremely common interview question at all levels — practice rewriting correlated subqueries into joins fluently by hand.

| Query Decorrelation | Removes row-by-row subquery dependency | Converts N executions into 1 set operation | Heuristic → enables Cost-based |

## 3.12 Best Practices, Common Mistakes & Edge Cases

### Best Practices
- Prefer `EXISTS`/`NOT EXISTS` over `IN`/`NOT IN` when subqueries might involve nullable columns — sidesteps the `NOT IN` + NULL trap entirely (§3.8).
- Write predicates directly in `WHERE`/`ON` clauses rather than filtering in application code, so pushdown can actually apply.
- Don't be afraid of views for readability — trust view merging in modern optimizers, but verify with `EXPLAIN` for views containing aggregates/`DISTINCT`/`UNION`, where merging may not apply.
- When you spot a correlated subquery in a code review, ask: "Can this be rewritten as a JOIN or a decorrelated aggregate subquery?" — often a very high-leverage manual optimization.

### Common Mistakes
- Using `NOT IN` with a subquery that can produce NULLs — silently returns zero rows instead of erroring, a dangerous, hard-to-detect bug.
- Assuming the optimizer will *always* decorrelate every complex correlated subquery — some (especially deeply nested, multi-level correlated subqueries with aggregates and conditionals) may not be fully decorrelated by every database, leading to real performance cliffs.
- Wrapping indexed columns in functions (e.g., `WHERE YEAR(order_date) = 2024`) which can block predicate pushdown *and* prevent index usage (sargability — covered further in Module 5).

### Edge Cases
- Predicate pushdown past **outer joins** requires NULL-rejection proof (§3.1).
- View merging is blocked by `GROUP BY`, `DISTINCT`, `UNION`, window functions in many systems.
- `NOT IN`/`NOT EXISTS` semantics diverge sharply in the presence of NULLs — always double-check with test data containing NULLs.

## 3.13 Chapter Summary

- **Predicate pushdown** and **projection pushdown** minimize the size/width of data flowing through the plan — among the highest-value, most universal transformations.
- **Join reordering** is the cost-based counterpart, choosing the sequence that minimizes cumulative intermediate result size (built on Module 2's DP algorithm).
- **Constant folding**, **constant propagation**, and **expression simplification** clean up and simplify predicates, often *enabling* other transformations to apply.
- **View merging** lets the optimizer see through views as if they were inlined directly into the query — with important exceptions (aggregates, `DISTINCT`, `UNION`).
- **Subquery unnesting** converts `IN`/`EXISTS`/`NOT IN`/`NOT EXISTS` into semi-joins/anti-joins, unlocking full join-order optimization — watch the `NOT IN` + NULL trap.
- **Common Subexpression Elimination** avoids redundant computation of repeated expressions.
- **Query Decorrelation** transforms correlated (row-by-row) subqueries into set-based joins/aggregations — one of the single highest-value manual and automatic optimizations in practice.

## 3.14 Cheat Sheet

```
TRANSFORMATION QUICK-REFERENCE
───────────────────────────────
Filter early           → Predicate Pushdown       (careful: outer joins!)
Carry fewer columns    → Projection Pushdown
Reorder joins          → Join Reordering           (cost-based, DP-driven)
Precompute constants   → Constant Folding
Substitute known values→ Constant Propagation
Simplify booleans       → Expression Simplification
See through views       → View Merging             (blocked by GROUP BY/DISTINCT/UNION)
Turn subquery → join    → Subquery Unnesting         (IN/EXISTS → semi-join)
Avoid recomputation      → Common Subexpression Elimination
Remove row-by-row deps   → Query Decorrelation        (correlated subquery → join)

⚠️ GOTCHA: NOT IN + NULL in subquery = returns ZERO rows. Use NOT EXISTS instead.
```
