# The Ultimate DBMS Handbook — Part 13: Research & Advanced Engineering

## Module 6 — HTAP Databases (Hybrid Transactional/Analytical Processing)

> **Goal of this module:** Go from "HTAP is OLTP + OLAP in one system" (Module 1.8's definition) to understanding the specific engineering mechanisms that make it work, the guarantees each approach can and can't offer, and how to evaluate an HTAP system's real-world tradeoffs versus a traditional OLTP+ETL+OLAP pipeline.

---

### 6.1 Restating the Problem Precisely

The traditional two-system architecture: an OLTP database (row store, optimized for point reads/writes) feeds a data warehouse (column store, optimized for scans) via a periodic **ETL (Extract, Transform, Load)** pipeline, often running hourly or nightly.

**What this costs you, precisely:**
- **Staleness**: analytics queries see data that is minutes to hours old, unusable for use cases needing near-real-time insight (fraud detection, live dashboards, operational analytics).
- **Operational burden**: the ETL pipeline itself is a system to build, monitor, and fix when it breaks — a whole category of "pipeline is stuck/broken" incidents that wouldn't exist without it.
- **Duplicated infrastructure cost**: running two full database systems, often over largely overlapping data.
- **Schema/semantic drift**: the OLTP schema and the warehouse schema tend to diverge over time as each evolves independently, creating a second problem of reconciling meaning, not just timing.

**HTAP's promise:** eliminate the ETL pipeline by making one system serve both access patterns directly against (nearly) the same live data.

---

### 6.2 Why This Is Hard — The Physical Contradiction

Module 5 established that OLTP wants row-oriented storage (whole-record access) and OLAP wants column-oriented storage (single-column, many-row access) — these are **physically opposite** optimal layouts for the same data. HTAP systems must resolve this contradiction; there is no free lunch, only different ways of paying the cost. Three broad strategies exist:

**Strategy A — Single storage format, accept the compromise.** Use one format (usually row-oriented, sometimes a hybrid page layout) for both, accepting that analytical queries will be slower than a dedicated column store would give. Simplest to build, weakest analytical performance.

**Strategy B — Dual storage format, real-time synchronized.** Maintain both a row store and a column store simultaneously, keeping them synchronized via the transaction/replication log (not batch ETL) so the columnar copy lags by milliseconds-to-seconds, not hours. This is the dominant modern approach (TiDB/TiFlash, Module 3.18).

**Strategy C — In-memory delta + columnar main store.** Keep very recent writes in a small, row-oriented (or unsorted) in-memory delta buffer, and periodically merge them into a large, compressed columnar main store (previewed in Module 5.7) — used by SAP HANA and Hekaton-style engines. This differs from Strategy B in that there's typically one logical store with two internal representations, rather than two fully separate physical stores kept in sync.

---

### 6.3 Strategy B in Depth — Real-Time Synchronized Dual Storage (TiFlash Pattern)

This is worth re-deriving in full since it's the dominant production pattern (Module 3.18 introduced it; this section explains the general mechanism independent of TiDB specifically).

**The mechanism:**
1. All writes go to the primary, row-oriented, transactional store (replicated via consensus — Raft/Paxos — for durability, as in any NewSQL system, Module 1.7/3.17).
2. A **columnar replica** subscribes to the *same replication log* the row-store replicas consume — in Raft terms, it can literally be a non-voting **learner** replica (Module 3.18), receiving the log stream but not participating in quorum/voting for writes.
3. The columnar replica applies the log entries **asynchronously**, converting each batch of row-oriented writes into columnar format (applying compression, building column files, per Module 5's mechanics) — typically with a lag of milliseconds to low seconds under normal load.
4. The query optimizer inspects each incoming query and **routes** it: point lookups and small-range scans go to the row store; large aggregate/analytical scans go to the columnar replica. Some queries can even be **split**, with different sub-plans executing against each store and results merged.

**Why "learner replica" is such an elegant solution:** it reuses existing, already-correct consensus/replication machinery (built for the primary use case of fault-tolerant row-store replication) to solve an unrelated problem (row-to-column real-time conversion), rather than inventing a new synchronization mechanism from scratch. This is a recurring pattern worth internalizing: **check whether your system's existing replication log can be repurposed before building a new pipeline.**

**What you give up:** the columnar replica is never *exactly* as fresh as the row store (there's always some replication lag, even if small) — so HTAP systems using this pattern typically offer **read-your-writes** consistency on the row store but only **bounded staleness** (not strict consistency) on the columnar replica, and applications needing strict consistency for analytical queries must explicitly query the row store instead.

---

### 6.4 Strategy C in Depth — Delta/Main Store Merge (HANA/Hekaton Pattern)

**The mechanism:**
1. Writes land in a small, memory-resident **delta store** — often just a row-oriented or lightly-indexed structure, prioritizing fast insert over compression or scan speed, since it's small enough that scanning it entirely is still cheap.
2. Reads (both point lookups and analytical scans) must consult **both** the delta store and the main store, merging results — similar in spirit to an LSM-tree's memtable + SSTable read path (Module 4.4), but applied at a much coarser granularity and across fundamentally different physical formats (row-oriented delta vs. columnar main) rather than two instances of the same format.
3. Periodically, a **merge** operation consolidates the delta store into the main columnar store, re-compressing and rebuilding column files — this is analogous to LSM compaction (Module 4.6) but typically far more expensive per operation (since it involves format conversion, not just merging sorted files of the same format), so it runs less frequently and at coarser granularity.

**Key tuning tension:** a larger delta store means less frequent (cheaper, amortized) merges but slower analytical scans (more unsorted/uncompressed data to scan on every query); a smaller delta store means the opposite. This is directly analogous to the memtable-size tuning tradeoff in LSM-trees (Module 4.9) but for a different underlying reason (format-conversion cost vs. read cost, rather than write-buffering vs. flush frequency).

---

### 6.5 Concurrency Control Implications for HTAP

Analytical queries typically **scan millions of rows and run for seconds to minutes**; transactional queries need **millisecond point lookups/writes**. If both use the same locking-based concurrency control, a long-running analytical scan can block transactional writers for its entire duration — an unacceptable outcome for OLTP latency SLAs.

**The standard solution: MVCC (Multi-Version Concurrency Control).** Every HTAP system covered in this handbook (Hekaton, HANA, TiDB) relies on MVCC specifically *because* it lets a long analytical query read a **consistent snapshot** (as of the moment it started) without acquiring locks that would block concurrent writers, and without being blocked by them either — the analytical reader simply sees an older version of any row that a concurrent transaction is in the process of updating.

**The cost MVCC introduces for HTAP specifically:** because analytical queries can run for a long time, and MVCC requires retaining old row versions until no active transaction might still need them, HTAP systems under heavy concurrent analytical load can accumulate a large backlog of old versions that need **garbage collection** — a long-running analytical query can inadvertently force the system to retain far more historical versions than it would need to for OLTP alone, increasing storage pressure and GC cost. This is a real, frequently-encountered production tuning problem in HTAP deployments, not a theoretical concern.

---

### 6.6 Query Optimizer Considerations Unique to HTAP

A traditional OLTP optimizer or OLAP optimizer only ever sees one storage format and one cost model. An HTAP optimizer must additionally decide:
- **Which physical store to route a query (or sub-plan) to** — based on estimated selectivity, scan size, and each store's differing cost characteristics (point lookup cost on row store vs. columnar scan cost on the analytical replica).
- **How stale the columnar replica currently is**, and whether that staleness is acceptable for the specific query's consistency requirements (some systems expose this as an explicit query hint or session setting, e.g., "read from the analytical replica, tolerate up to N seconds of staleness").
- **Whether to split a single query** across both stores (e.g., a query joining a small, frequently-updated dimension table best served by the row store with a huge fact table best served by the columnar store) — a genuinely harder planning problem than routing a whole query to one store or the other.

---

### 6.7 HTAP vs. "Just Use a Fast ETL Pipeline" — When HTAP Isn't Worth It

HTAP systems are more operationally complex than a single-purpose OLTP or OLAP database — it's worth being explicit about when the tradeoff doesn't pay off:
- If your analytics genuinely only need hourly/daily freshness, a well-run batch ETL pipeline into a dedicated warehouse (Snowflake, BigQuery) is simpler to operate and gives you access to a mature, specialized analytical query engine, without paying HTAP's concurrency-control and dual-storage complexity tax.
- If your OLTP and analytical workloads have very different scaling needs (e.g., a small OLTP dataset but massive analytical history spanning years), separating them lets each scale independently (recall Module 2's compute-storage separation argument) rather than being coupled inside one HTAP system's architecture.
- HTAP earns its complexity specifically when the **business requirement is near-real-time analytics on live transactional data** — fraud detection, live operational dashboards, real-time personalization — where ETL staleness is a genuine product-breaking problem, not merely an inconvenience.

### 6.8 Production Examples & Industry Usage

| System | HTAP strategy | Notable production usage |
|---|---|---|
| TiDB / TiFlash | Strategy B — Raft-learner columnar replica | Large e-commerce/fintech platforms needing real-time inventory + analytics |
| SAP HANA | Strategy C — delta/main store merge | SAP ERP customers running operational reporting directly against live transactional data |
| SQL Server (Hekaton + Columnstore Indexes) | Strategy C variant — in-memory OLTP engine plus separate columnstore indexes | Enterprises wanting both in-memory OLTP speed and analytical columnstore queries in one product |
| Google Spanner + BigQuery federation | Strategy A/B hybrid — external federated queries from BigQuery directly against Spanner | Google Cloud customers wanting live analytics without a separate ETL job |
| SingleStore (formerly MemSQL) | Strategy B — row store + columnar store, unified query engine | Real-time analytics dashboards over operational data |

### 6.10 MCQs

**Q1.** HTAP systems primarily aim to eliminate:
A) The need for SQL
B) The ETL pipeline and its associated staleness between OLTP and OLAP systems
C) The need for indexes
D) Replication

*Answer: B*

**Q2.** In the Raft-learner-based HTAP pattern (Strategy B), the columnar replica:
A) Participates in write quorum voting
B) Receives the same replication log as voting replicas but does not vote, converting entries to columnar format asynchronously
C) Is always perfectly up to date with zero lag
D) Replaces the row store entirely

*Answer: B*

**Q3.** MVCC is essential to HTAP systems primarily because:
A) It reduces storage space
B) It lets long-running analytical scans read a consistent snapshot without blocking or being blocked by concurrent OLTP writes
C) It eliminates the need for a columnar store
D) It speeds up compaction

*Answer: B*

**Q4.** A key operational cost unique to HTAP's use of MVCC is:
A) Slower point lookups
B) Increased garbage collection burden from long-running analytical queries retaining many row versions
C) Loss of SQL compatibility
D) Inability to use indexes

*Answer: B*

**Q5.** HTAP is least justified when:
A) Fraud detection requires real-time transactional analytics
B) Analytics only need daily freshness and OLTP/analytical scaling needs differ significantly
C) Live operational dashboards are a core product requirement
D) ETL staleness breaks a real-time personalization feature

*Answer: B*

### 6.12 Research Questions

1. Can the row-store-to-columnar-replica staleness bound in Strategy B systems be made adaptive — tightening automatically under detected fraud-risk conditions and loosening under normal load to save resources — without introducing new consistency bugs?
2. Is there a unified cost model that could let a query optimizer split a single query plan across row and columnar stores automatically (rather than the coarser whole-query routing most production systems currently do), and what would make such a model's cost estimates trustworthy enough to use safely?
3. As persistent memory and CXL-attached memory reduce the cost gap between row-oriented and columnar access patterns, does the fundamental "physical contradiction" (Section 6.2) motivating dual storage formats weaken, and would a single hybrid in-memory layout become viable for genuinely mixed HTAP workloads?
