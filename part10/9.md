# Part 10 — Database Internals & Storage Engine Architecture

## Module 9: Storage Optimizations

> **Recap:** Module 2 introduced compression and Fill Factor briefly as previews. This module treats storage optimization as its own subject — the specific compression techniques engines use, and the two fundamental cost metrics (write and read amplification) that every storage optimization decision ultimately trades off against.

---

### 9.0 Why This Module Exists

Every storage optimization in this module exists to answer one question: **how do you make a fixed amount of disk, memory, and I/O bandwidth go further?** Understanding the specific techniques — and, more importantly, the write/read amplification framework for reasoning about their trade-offs — lets you evaluate *any* new storage optimization you encounter in the future, not just the specific ones listed here.

---

### 9.1 Compression: The General Trade-off

**What problem does compression solve?** Storage (disk space) and I/O bandwidth are finite and comparatively expensive relative to CPU cycles, especially as CPUs have grown much faster relative to disk throughput over the past two decades. Compression trades CPU cycles (to compress/decompress) for reduced storage footprint and reduced I/O volume — data that's smaller on disk takes less time to read and write.

**Why this trade-off has become increasingly favorable over time:** Modern CPUs are extremely fast at compression/decompression (especially with hardware-accelerated instructions and highly optimized algorithms like LZ4, Zstandard, and Snappy), while disk I/O — even fast NVMe SSDs — hasn't scaled at nearly the same rate relative to CPU throughput. This is why compression, once considered primarily a "save disk space, pay a performance tax" feature, is increasingly viewed as a **net performance win** in many workloads, not just a space-saving convenience.

**The general cost/benefit framework:**

| Benefit | Cost |
|---|---|
| Less disk space used | CPU cycles for compress (write path) |
| Fewer bytes to read from disk (faster I/O) | CPU cycles for decompress (read path) |
| More data fits in the buffer pool at once (compressed pages take less RAM) | Compression may reduce partial/random-access efficiency in some schemes |

### 9.2 Dictionary Compression

**What is it?** A compression technique where repeated values are replaced with short references into a **dictionary** (a lookup table of distinct values), rather than storing the full value every time it repeats.

**How it works — a concrete example:** A column `status` with values like `'PENDING'`, `'SHIPPED'`, `'DELIVERED'`, `'PENDING'`, `'PENDING'`, `'SHIPPED'`, ... across a million rows might have only 5 distinct values total. Dictionary compression stores:
- A small dictionary: `{0: 'PENDING', 1: 'SHIPPED', 2: 'DELIVERED', ...}`
- The actual column data as a sequence of tiny integer codes: `[0, 1, 2, 0, 0, 1, ...]` — each code potentially just 1 byte (or even fewer bits), instead of storing the full string (7-9+ bytes) every single time.

**Why does it exist / what problem does it solve?** Real-world data is often extremely repetitive in specific columns — status flags, categories, country codes, boolean-like fields. Naive storage wastes enormous space repeating the same few distinct strings millions of times; dictionary compression captures this redundancy directly and very cheaply (encoding/decoding a dictionary lookup is extremely fast).

**Where it's especially effective:** Low-to-medium cardinality columns (relatively few distinct values relative to row count) — this is precisely the profile that also makes such columns attractive for compression in columnar/analytical storage engines, where dictionary encoding is a foundational technique (relevant to later parts of this handbook covering columnar storage).

**Interview importance:** ⭐⭐⭐⭐ A common, concrete compression technique interviewers expect you to be able to explain with an example.

---

### 9.3 Prefix Compression

**What is it?** A compression technique (most commonly applied within **sorted structures**, particularly B-Tree index pages) that exploits the fact that consecutive sorted keys often share a common leading substring (**prefix**), storing that shared prefix only once per page (or per run of similar keys) instead of repeating it in every single key.

**Concrete example — a B-Tree index page holding sorted string keys:**
```
Without prefix compression:
  "customer_10023"
  "customer_10024"
  "customer_10025"
  "customer_10099"

With prefix compression (shared prefix stored once, then just the differing suffix):
  Prefix: "customer_10"
  Suffixes: "023", "024", "025", "099"
```

**Why this matters specifically for index pages:** Because B-Tree leaf/internal pages hold keys in **sorted order** by definition, adjacent keys are extremely likely to share long common prefixes (especially with string keys, or even structured composite keys) — this makes prefix compression a very natural, low-overhead fit for index structures specifically, letting more keys fit per page and thus reducing the tree's overall height/fan-out cost.

**Interview importance:** ⭐⭐⭐ Good to know as a distinct technique from dictionary compression, particularly its natural fit with sorted index structures.

---

### 9.4 Page Compression / Transparent Compression

**What is it?** Compressing an **entire page** as a unit before writing it to disk, and decompressing it transparently (invisibly to the SQL layer) when reading it back into the buffer pool.

**"Transparent" meaning:** The application and even most of the query executor are entirely unaware compression is happening — `SELECT` statements, indexes, and constraints all behave identically whether or not page compression is enabled; it's purely a storage-layer implementation detail.

**Concrete implementation — InnoDB's `ROW_FORMAT=COMPRESSED` (recap from Module 4, now framed within this module's broader compression taxonomy):** Pages are compressed (commonly via zlib) before being written to disk, and an in-memory buffer pool entry may hold *both* the compressed form and, transiently, an uncompressed working copy for active access — a real memory/complexity trade-off engines must manage carefully.

**Trade-offs specific to page-level compression:**
- **Variable compressed size:** Unlike a fixed 8KB/16KB uncompressed page, a compressed page's actual byte size varies depending on how compressible its specific contents are — this complicates free-space and page-allocation bookkeeping (Module 2, Section 2.7) compared to the clean fixed-size assumption those systems are normally built around.
- **In-place update complications:** If a page is updated and its compressed size grows beyond what was originally allocated for it on disk, the engine may need to relocate/reorganize storage — a real operational complexity that fixed-size, uncompressed pages don't face.

**Interview importance:** ⭐⭐⭐ Useful to distinguish from dictionary/prefix compression (which operate at the *value* level) — page compression operates at the *whole-page-byte-stream* level, agnostic to the actual column semantics within.

---

### 9.5 Data Deduplication

**What is it?** A broader storage-optimization technique (not always specific to databases — common in backup/storage systems generally) where **identical blocks/chunks of data** are stored only once, with multiple logical references pointing to that single physical copy, rather than storing duplicate copies redundantly.

**Where this shows up in database contexts:**
- **TOAST/overflow value deduplication** (in some systems/extensions): if the exact same large value appears in multiple rows, some systems can detect and store it only once.
- **Backup and snapshot systems:** database backup tooling often deduplicates across successive backups (much of a large database doesn't change day-to-day, so incremental/deduplicated backups avoid re-storing unchanged data repeatedly).
- **Copy-on-write filesystem/storage layers** (e.g., ZFS, certain cloud block-storage snapshot mechanisms) underneath the database, providing deduplication transparently at a layer *below* the database engine itself.

**Distinction from compression:** Compression reduces the size of *a single copy* of data by exploiting internal redundancy within it; deduplication avoids storing *multiple separate copies* of data that happen to be identical (or near-identical) to each other — related but distinct optimization strategies, often used together.

**Interview importance:** ⭐⭐ Lower priority for core database-internals interviews specifically, but relevant context for broader storage-systems discussions.

### 9.6 Fill Factor (Recap + Full Treatment)

Already introduced in Module 2 (free space) and Module 3 (HOT updates) — here's the complete picture as a deliberate storage optimization technique in its own right.

**What is it?** A configuration setting (`FILLFACTOR` in Postgres, analogous concepts elsewhere) controlling what percentage of each page is filled with data at initial insert/rebuild time, deliberately leaving the remainder as reserved headroom.

**Why deliberately waste space?** Recall Module 3's HOT update mechanism: an in-place-friendly update (same page, no indexed column changed) is only possible if there's room on the page for the new tuple version. A page packed to 100% full at insert time leaves *zero* room for any future update to benefit from this optimization — every single update would be forced off-page, requiring index maintenance. Setting `FILLFACTOR` below 100% (e.g., 90 for a moderately updated table, lower for heavily updated ones) trades a small amount of extra disk space and slightly larger table size for a much higher rate of cheap in-place updates going forward.

**When to use a lower fill factor:** Tables with frequent `UPDATE`s on non-indexed columns. **When NOT to bother:** Append-mostly or read-mostly tables, where the wasted headroom provides no benefit and simply costs extra space/scan I/O for no gain — this is a workload-dependent tuning decision, not a universal default.

**Interview importance:** ⭐⭐⭐⭐ Directly connects Fill Factor to HOT updates — a strong combined-concept question ("why would you deliberately configure a table to waste space?").

### 9.7 Write Amplification

**What is it?** The ratio between the amount of data a logical operation *conceptually* needs to write, and the amount of data the storage system *actually* ends up writing to physical disk as a consequence of that operation.

```
Write Amplification = (Actual Bytes Physically Written) / (Logical Bytes The Application Intended To Write)
```

**Where write amplification comes from in database engines — concrete sources covered elsewhere in this handbook, now unified under this single framework:**

| Source | Mechanism |
|---|---|
| WAL/Redo log | Every logical change is written *twice* conceptually — once to the log, once (eventually) to the actual data page (Modules 1, 3, 4) |
| Doublewrite Buffer (InnoDB) | Pages written *twice* physically to protect against torn writes (Module 4) |
| Full-page writes (Postgres, first WAL write after a checkpoint) | Postgres writes the *entire* page content to WAL (not just the changed bytes) the first time a page is modified after a checkpoint, specifically to protect against torn pages — Postgres's structural equivalent of the same problem InnoDB's doublewrite buffer addresses, solved via the log instead of a separate buffer |
| Index maintenance | A single row update can require writes to multiple secondary indexes, not just the base table (mitigated by HOT in Postgres, the Change Buffer in InnoDB) |
| LSM-tree compaction (Module 2, append-only storage) | Data written once on initial insert, then rewritten repeatedly across multiple compaction passes over its lifetime — LSM-based engines can have particularly high write amplification as a direct, well-known consequence of their design |
| SSD-level write amplification (hardware layer, beneath the database entirely) | Flash storage's own internal block-erase-before-write mechanics add a further layer of write amplification below anything the database controls directly |

**Why this matters practically:** Write amplification directly determines physical disk wear (especially relevant for SSD lifespan) and I/O bandwidth consumption — a workload that seems to write "only" 100MB/s logically might be generating 300-500MB/s or more of actual physical disk writes once WAL, doublewrite/full-page-write protection, and index maintenance are all accounted for.

**Interview importance:** ⭐⭐⭐⭐⭐ A unifying framework question — "what causes write amplification in a database, and name at least three specific sources" ties together material from nearly every prior module in this Part.

### 9.8 Read Amplification

**What is it?** The ratio between the amount of data a query *logically* needs, and the amount of data the storage system actually has to read from disk to satisfy that request.

```
Read Amplification = (Actual Bytes Physically Read) / (Logical Bytes The Query Actually Needed)
```

**Where read amplification comes from — concrete sources:**

| Source | Mechanism |
|---|---|
| Fixed-size page reads | Reading even a single small row still requires reading its *entire* containing page (typically 8-16KB) — Module 2's page model |
| Secondary index bookmark lookups (InnoDB) | A secondary index lookup requires an *additional* full clustered-index page read per matching row (Module 4) unless the index is covering |
| TOAST/overflow reads | Accessing a large out-of-line column requires additional page reads beyond the main row's page (Modules 2, 3) |
| LSM-tree read path | A single logical key lookup may require checking multiple on-disk sorted files (SSTables) plus the in-memory memtable, since the most recent version could be in any of several locations, until compaction consolidates them (Module 2) |
| Lack of covering indexes | A query needing columns not present in the index it's using must additionally fetch the base table row for every match |

**The classic write/read amplification trade-off — LSM-trees vs. B-Trees, revisited:** This is exactly the trade-off previewed in Module 2's append-only storage discussion, now precisely namable: LSM-tree designs generally accept **higher write amplification** (via compaction) in exchange for **turning random writes into sequential writes** (a huge win on the write path specifically), while potentially incurring **higher read amplification** (checking multiple files/levels per lookup) unless mitigated by additional structures (e.g., Bloom filters, to quickly rule out files that definitely don't contain a given key without needing to read them). B-Tree-based engines (Postgres, InnoDB) generally have lower, more predictable read amplification per lookup but pay real write amplification costs of their own (WAL, doublewrite/full-page-writes, index maintenance) as catalogued above.

**Interview importance:** ⭐⭐⭐⭐⭐ Pairing write and read amplification together, and being able to use them to *justify* a storage engine choice (e.g., "why would you pick an LSM-tree engine for this workload") is a hallmark senior-level system-design answer.

### 9.9 Putting It Together: A Compression + Amplification Worked Example

Consider a table with a `status` column (5 distinct values, dictionary-compressible) and a `notes` column (large free-text, often repeated boilerplate across rows).

**Without any storage optimization:**
- `status`: stored as a full string every row → wastes space, more pages needed → more I/O per scan (read amplification from unnecessarily large pages)
- `notes`: stored inline until it exceeds the TOAST/overflow threshold, then moved out-of-line → extra page reads for large values (read amplification)

**With storage optimizations applied:**
- Dictionary compression on `status` → smaller rows → more rows fit per page → **fewer total pages** → less I/O for the same logical data (reduces read amplification for scans touching this column)
- Deduplication or compression on repeated boilerplate text in `notes` → smaller TOAST chunks → fewer overflow page reads
- Appropriate `FILLFACTOR` if this table is update-heavy → more HOT updates possible → **less write amplification** from avoided index maintenance

This worked example is the kind of synthesis interviewers want — showing you can combine multiple techniques from across this module to reason about a single realistic scenario, rather than reciting each technique in isolation.

### 9.10 PostgreSQL vs. MySQL — Storage Optimization Summary

| Technique | PostgreSQL | InnoDB (MySQL) |
|---|---|---|
| Value-level compression | TOAST's automatic compression for large values (Module 2/3) | Row format-dependent; `COMPRESSED` row format compresses at page level |
| Page-level compression | Not built into core (available via some extensions/table access methods) | `ROW_FORMAT=COMPRESSED` (zlib-based) |
| Torn-page protection mechanism (write amplification source) | Full-page writes in WAL (first write after checkpoint) | Doublewrite Buffer |
| Fill Factor equivalent | `FILLFACTOR` (enables HOT updates) | `innodb_fill_factor` (for index/table rebuilds, similar headroom-reservation purpose) |
| Secondary-index write buffering (write amplification mitigation) | HOT updates avoid unnecessary index writes when possible | Change Buffer defers/batches secondary index writes |

### 9.11 Advantages, Disadvantages, Best Practices

**Advantages of storage optimization techniques generally:**
- Reduced disk footprint, often translating directly into reduced I/O time and improved buffer pool effectiveness (more logical data fits in the same RAM)
- Many of these optimizations (dictionary compression, TOAST, page compression) are largely transparent to application code — free performance/space wins once enabled

**Disadvantages:**
- All compression trades CPU for space/I/O — on a CPU-bound workload, this trade can be net negative
- Techniques like page compression and deduplication add real implementation/operational complexity (variable page sizes, relocation on growth)

**Best practices:**
- Measure before enabling aggressive compression — a workload that's already CPU-bound may not benefit, or may even regress, from adding compression overhead
- Tune `FILLFACTOR`/equivalent settings specifically for genuinely update-heavy tables; leave read-mostly/append-only tables at default (100%) fill
- Understand your workload's dominant amplification type (write-heavy → focus on WAL/index/compaction costs; read-heavy → focus on covering indexes, TOAST access patterns, page density) before choosing optimizations to prioritize

**Common mistakes:**
- Applying the same `FILLFACTOR`/compression settings uniformly across every table regardless of actual update/read patterns
- Assuming compression is a "free win" without measuring actual CPU impact under real production concurrency
- Ignoring write amplification sources (WAL, doublewrite/full-page-writes, index maintenance) when trying to explain "why does my database write so much more to disk than my application logically writes"

### 9.12 Chapter Summary

- Compression trades CPU cycles for reduced storage footprint and I/O volume — an increasingly favorable trade as CPU speed has outpaced disk throughput growth.
- **Dictionary compression** replaces repeated values with small codes (best for low-cardinality columns); **prefix compression** exploits shared prefixes in sorted keys (a natural fit for B-Tree index pages); **page/transparent compression** compresses whole pages, invisible to the SQL layer, at the cost of variable compressed page sizes.
- **Fill Factor** deliberately reserves page headroom to enable more in-place updates (HOT updates in Postgres) at the cost of some wasted space and increased page count.
- **Write amplification** (actual physical writes ÷ logical intended writes) comes from WAL/redo logs, doublewrite buffers/full-page writes, index maintenance, and (especially) LSM-tree compaction.
- **Read amplification** (actual physical reads ÷ logical needed data) comes from fixed page-size reads, secondary-index bookmark lookups, TOAST/overflow access, and LSM-tree multi-file lookups.
- The write-vs-read amplification trade-off is the precise, nameable reason LSM-tree engines and B-Tree engines suit different workloads — a unifying lens for evaluating any storage engine choice.

---

### 9.13 Cheat Sheet

```
Dictionary Compression → repeated values → small integer codes + lookup table
                          (best: low-cardinality columns)
Prefix Compression      → sorted keys share leading substrings → store prefix once
                          (natural fit: B-Tree index pages)
Page Compression        → compress whole page before disk write, transparent to SQL
                          (cost: variable compressed size, relocation on growth)
Deduplication            → identical BLOCKS stored once, multiple references
                          (distinct from compression: reduces COPIES, not internal size)

FILLFACTOR → deliberately waste page space → more room for in-place (HOT) updates
             → use for update-heavy tables, skip for read-mostly/append-only

Write Amplification = actual physical writes / logical intended writes
  Sources: WAL/redo log, doublewrite buffer / full-page writes,
           index maintenance, LSM compaction, SSD-level flash mechanics

Read Amplification = actual physical reads / logically needed data
  Sources: fixed page-size reads, secondary-index bookmark lookups,
           TOAST/overflow reads, LSM multi-file lookups

Core trade-off: LSM-trees → higher write amp (compaction) for sequential writes,
                              potentially higher read amp (multi-file lookups)
                B-Trees   → lower, predictable read amp; real but different
                              write amp sources (WAL, doublewrite, index writes)
```
