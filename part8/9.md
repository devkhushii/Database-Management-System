# Part 8: Query Processing & Query Optimization
## Module 9: Query Execution Plans

> **Prerequisite check:** This module assumes Modules 1–8. This is the **capstone practical module** of Part 8 — it ties together everything (query trees, cost models, access paths, joins, sorting, aggregation) into the single most important day-to-day skill for a database-literate engineer: **reading `EXPLAIN` output.**

---

## 9.0 Why This Module Exists

Every concept from Modules 1–8 is *invisible* unless you know how to look at it. `EXPLAIN` (and its execution-based sibling, `EXPLAIN ANALYZE`) is the window into the optimizer's mind — it shows you the actual plan chosen, the algorithms selected (Module 6), the access paths used (Module 5), the estimated vs. actual cardinalities (Module 4), and where time is really being spent. **This is, without exaggeration, one of the highest-ROI skills for any backend/database engineer to master**, and one of the most heavily tested practical skills in senior interviews.

---

## 9.1 Execution Plan

### Definition

An **Execution Plan** is the concrete, detailed tree of physical operators (chosen from Modules 5, 6, 7, 8's catalog of access paths, join algorithms, sort strategies, and aggregation strategies) that the database will use (or did use) to answer a specific query.

### Why It Exists

The execution plan is the tangible, inspectable **output** of everything the optimizer (Module 2) decided — it's the artifact that turns all of this module's abstract theory into something you can literally print to your screen and read.

---

## 9.2 Logical Plan vs. Physical Plan (Revisited, Now With Real Syntax)

Recall Module 2, §2.2's distinction. Here's how it looks in **actual PostgreSQL `EXPLAIN` output**:

```sql
EXPLAIN SELECT name FROM users WHERE age > 18;
```

```
Seq Scan on users  (cost=0.00..18.50 rows=333 width=36)
  Filter: (age > 18)
```

This is a **physical plan** — notice it already tells you the concrete access path (`Seq Scan`, Module 5, §5.1), not just the abstract logical operation ("filter users"). Real `EXPLAIN` output in production databases is **always** physical plan output — the logical plan is an internal optimizer artifact you don't typically see directly (though `EXPLAIN (VERBOSE)` gets closer to exposing some of this internal structure).

## 9.3 Cost: Estimated vs. Actual

### Definition

**Cost** in `EXPLAIN` output is the optimizer's **pre-execution estimate** (Module 2, §2.4's cost formula), expressed in the database's internal cost units — **not** a direct measure of time or bytes. Two numbers are always shown for each node: **startup cost** and **total cost**.

### Reading the Cost Numbers

```
Seq Scan on users  (cost=0.00..18.50 rows=333 width=36)
                          ↑      ↑        ↑        ↑
                     startup  total   estimated  estimated
                      cost    cost      rows    row width (bytes)
```

| Field | Meaning |
|---|---|
| **Startup cost** | Estimated cost before the **first** row can be returned (e.g., for a Sort node, this includes the *entire* sort — you can't return row 1 until sorting is done; for a Seq Scan, this is usually 0.00, since the first row can be returned almost immediately) |
| **Total cost** | Estimated cost to return **all** rows |
| **rows** | Estimated cardinality (Module 4) — the number of rows this node is expected to produce |
| **width** | Estimated average row width in bytes |

### Startup Cost Matters More Than You'd Think

```sql
SELECT * FROM orders ORDER BY amount LIMIT 5;
```
```
Limit  (cost=1234.56..1234.78 rows=5 width=40)
  ->  Sort  (cost=1234.56..1284.56 rows=20000 width=40)
        Sort Key: amount
        ->  Seq Scan on orders  (cost=0.00..800.00 rows=20000 width=40)
```
Notice the `Sort` node's **startup cost (1234.56) is almost equal to its total cost (1284.56)** — because a full sort must complete entirely before even the first sorted row can be returned (Module 7). This is exactly why the outer `Limit` node's cost is dominated by the Sort's startup cost, not by the trivially small work of returning just 5 rows.

> 💡 **Practical insight:** For queries with `LIMIT`, the optimizer heavily favors plans with **low startup cost** (like using an index to read pre-sorted rows and stop early, avoiding a full sort — Module 5 §5.7's "sort for free" + a Top-N shortcut) over plans with low total-but-high-startup cost.

### Interview Importance: ⭐⭐⭐⭐⭐
Understanding startup-vs-total cost, and specifically *why* it matters for `LIMIT` queries, is a frequently tested, high-signal detail.

## 9.4 Estimated Rows vs. Actual Rows (The Most Important Diagnostic in This Module)

### Definition

`EXPLAIN` alone shows only **estimated** values (the optimizer's Module-4-driven predictions, computed *without* running the query). `EXPLAIN ANALYZE` **actually executes** the query and shows both the estimate **and** the real, measured values side by side — the single most powerful diagnostic tool covered in this entire handbook.

### Example

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE status = 'ACTIVE' AND region = 'APAC';
```

```
Seq Scan on orders  (cost=0.00..25000.00 rows=20000 width=80)
                     (actual time=0.015..450.221 rows=300000 loops=1)
  Filter: (status = 'ACTIVE' AND region = 'APAC')
  Rows Removed by Filter: 700000
```

### Decoding Every Field

| Field | Meaning |
|---|---|
| `rows=20000` (in the cost parens) | **ESTIMATED** rows (Module 4's cardinality estimate) |
| `actual rows=300000` | **ACTUAL** rows produced, measured by really running the query |
| `actual time=0.015..450.221` | Actual **startup time..total time**, in milliseconds |
| `loops=1` | How many times this node was executed (relevant for the inner side of Nested Loop Joins — see §9.4.1) |
| `Rows Removed by Filter` | Rows read but discarded by this node's filter condition — tells you how much "wasted" scanning happened |

### The Critical Diagnostic: Estimated vs. Actual Mismatch

```
ESTIMATED: 20,000 rows
ACTUAL:    300,000 rows
                │
                ▼
    15x UNDERESTIMATE — directly connects back to Module 4, §4.12's
    worked example of the independence assumption failing due to
    correlated columns (status and region correlated in this data)
```

**This is exactly the scenario worked through in Module 4, §4.12** — now you can see it concretely in real `EXPLAIN ANALYZE` output. A large estimated-vs-actual gap is the **#1 signal** that statistics are stale, sampling was insufficient, or columns are correlated in ways the optimizer's independence assumption didn't account for.

### 9.4.1 Understanding `loops` (Critical for Nested Loop Joins)

```
Nested Loop  (cost=0.00..5000.00 rows=100 width=80)
             (actual time=0.02..15.30 rows=95 loops=1)
  ->  Seq Scan on customers  (cost=0.00..50.00 rows=10 width=20)
                              (actual time=0.01..0.15 rows=10 loops=1)
  ->  Index Scan on orders  (cost=0.29..8.31 rows=10 width=60)
                              (actual time=0.01..0.05 rows=9.5 loops=10)
```

Notice `loops=10` on the inner `Index Scan` — this is Module 6, §6.3's Indexed Nested Loop Join in action: the inner index scan was executed **once per outer row** (10 outer rows from `customers` → 10 loops of the inner index probe). **Critically:** the `actual time` and `actual rows` shown for a node with `loops > 1` are the **per-loop AVERAGE**, not the total! To get the true total time contributed by this node, you must multiply: `actual time (total) × loops`.

### Interview Importance: ⭐⭐⭐⭐⭐
**The single highest-value practical skill in this entire handbook module.** Interviewers routinely paste real (or hypothetical) `EXPLAIN ANALYZE` output and ask you to diagnose the problem — practice this extensively.

## 9.5 Buffers

### Definition

The `BUFFERS` option in `EXPLAIN (ANALYZE, BUFFERS)` reports actual **I/O activity** — how many pages were read from the **buffer cache** (already in memory — "hit") versus read from **disk** (had to be fetched — "read") — directly connecting to Part 2's buffer pool management concepts.

### Example

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE status = 'ACTIVE';
```

```
Seq Scan on orders  (cost=0.00..25000.00 rows=300000 width=80)
                     (actual time=0.02..320.5 rows=300000 loops=1)
  Filter: (status = 'ACTIVE')
  Buffers: shared hit=1200 read=8800
```

| Field | Meaning |
|---|---|
| `shared hit` | Pages found already in the buffer pool (fast, no disk I/O needed) |
| `shared read` | Pages that had to be physically read from disk (slow, real I/O) |

A high `read` count relative to `hit` suggests this data isn't well-cached (either a cold cache, or a working set larger than available memory) — directly actionable information for diagnosing genuine I/O-bound performance problems versus CPU-bound ones.

### Interview Importance: ⭐⭐⭐⭐
A great "goes beyond the basics" detail — shows awareness that `EXPLAIN ANALYZE`'s timing numbers alone don't tell the whole I/O story.

## 9.6 Timing

### Definition

**Timing** information (`actual time=X..Y`) shows real wall-clock milliseconds measured during `EXPLAIN ANALYZE`'s actual execution — but comes with an important caveat: **the act of measuring timing itself adds overhead**, especially for very fast, high-row-count operations, since the database must call a timing function for every single row.

### The Measurement Overhead Caveat (Important, Often Overlooked)

```sql
EXPLAIN (ANALYZE, TIMING OFF) SELECT ...;   -- disables per-row timing,
                                              -- only shows total rows/loops,
                                              -- reduces measurement overhead
                                              -- for very fast queries
```

For queries executing over **millions of rows very quickly**, the overhead of `EXPLAIN ANALYZE`'s per-row timing instrumentation can itself measurably distort the results (sometimes by a significant percentage!) — a genuinely important, practical caveat that experienced engineers know to account for.

### Interview Importance: ⭐⭐⭐
A nuanced, credibility-building detail — mentioning that `EXPLAIN ANALYZE` timing has measurement overhead (and that `TIMING OFF` exists) signals real hands-on experience, not just textbook knowledge.

## 9.7 Memory Usage

### Definition

Memory-related output in `EXPLAIN ANALYZE` reveals how much memory an operator (typically Sort or Hash-based operators) actually used, and critically, whether it **spilled to disk** — directly connecting to Module 7 (external sorting) and Module 6/8 (hash join/aggregation disk-spilling).

### Example: Sort Spilling to Disk

```
Sort  (cost=... rows=1000000 width=80)
      (actual time=1500.2..2100.5 rows=1000000 loops=1)
  Sort Key: amount
  Sort Method: external merge  Disk: 45000kB
```

`Sort Method: external merge  Disk: 45000kB` is the **exact, direct evidence** of Module 7's External Merge Sort kicking in because the sort didn't fit in `work_mem` — a hugely actionable diagnostic (consider raising `work_mem` for this query, or checking if an index could avoid the sort entirely, per Module 5 §5.7).

### Example: Hash Aggregation/Join Spilling

```
HashAggregate  (cost=... rows=50000 width=40)
               (actual time=800.1..1200.3 rows=50000 loops=1)
  Group Key: customer_id
  Batches: 5  Memory Usage: 4096kB  Disk Usage: 128000kB
```

`Batches: 5` with nonzero `Disk Usage` is direct evidence of Module 6/8's Grace/Hybrid Hash disk-partitioning strategy kicking in — the hash table didn't fit entirely in memory.

### Interview Importance: ⭐⭐⭐⭐⭐
Extremely high-value — being able to point at `Sort Method: external merge Disk: ...kB` or `Batches: N` and immediately explain "this means the operation spilled to disk because of insufficient memory, connecting to [Module 6/7/8]" is a textbook senior-engineer signal.

## 9.8 Parallel Workers

### Definition

Parallel execution plan output shows how work was distributed across multiple **worker processes** (Module 10 will cover this in full depth) — `EXPLAIN` reveals both the **planned** number of workers and (with `ANALYZE`) the **actual** number launched.

### Example

```sql
EXPLAIN (ANALYZE) SELECT COUNT(*) FROM orders WHERE amount > 1000;
```

```
Finalize Aggregate  (cost=... rows=1 width=8)
                     (actual time=180.5..180.6 rows=1 loops=1)
  ->  Gather  (cost=... rows=3 width=8)
              (actual time=175.2..180.4 rows=4 loops=1)
        Workers Planned: 3
        Workers Launched: 3
        ->  Partial Aggregate  (cost=... rows=1 width=8)
                                (actual time=170.1..170.1 rows=1 loops=4)
              ->  Parallel Seq Scan on orders  (cost=... rows=250000 width=0)
                                                 (actual time=0.02..150.3 rows=200000 loops=4)
                    Filter: (amount > 1000)
```

### Key Fields

| Field | Meaning |
|---|---|
| `Workers Planned` | Number of parallel workers the optimizer decided to request |
| `Workers Launched` | Number **actually** started (can be less than planned if the system is under resource pressure!) |
| `Gather` | The node that collects results from all parallel workers back into a single stream (Module 10) |
| `Partial Aggregate` / `Finalize Aggregate` | Exactly Module 8, §8.6's two-level parallel aggregation pattern, now visible in real plan output |
| `loops=4` on the partial nodes | 4 = 3 workers + 1 leader process, each independently executing this subtree on its own data slice |

### Interview Importance: ⭐⭐⭐⭐
Connects directly to Module 8's parallel aggregation theory and previews Module 10 — a good "full circle" moment to demonstrate in an interview.

## 9.9 Full Annotated Walkthrough: Reading a Complex Real Plan

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, SUM(o.amount)
FROM customers c
JOIN orders o ON c.id = o.customer_id
WHERE o.status = 'ACTIVE'
GROUP BY c.name;
```

**Hypothetical output, annotated:**

```
HashAggregate  (cost=15000.00..15200.00 rows=500 width=44)
               (actual time=890.2..895.1 rows=480 loops=1)
  │   ← Module 8, §8.1: Hash Aggregation chosen for GROUP BY c.name
  │   ← ESTIMATE (500) vs ACTUAL (480): very close! Good statistics here.
  Group Key: c.name
  Batches: 1  Memory Usage: 512kB
  │   ← Module 8/6: only 1 batch = fit entirely in memory, no spill
  ->  Hash Join  (cost=5000.00..14000.00 rows=100000 width=40)
                 (actual time=45.2..750.8 rows=95000 loops=1)
      │   ← Module 6, §6.4: Hash Join chosen for the join
      │   ← ESTIMATE (100000) vs ACTUAL (95000): reasonably close estimate
        Hash Cond: (o.customer_id = c.id)
        Buffers: shared hit=8000 read=200
        │   ← Module 9, §9.5: mostly cache hits, some disk reads
        ->  Seq Scan on orders o  (cost=0.00..8000.00 rows=100000 width=20)
                                   (actual time=0.02..300.1 rows=95000 loops=1)
            │   ← Module 5, §5.1: Seq Scan chosen — status='ACTIVE' likely
            │      matched a large fraction of orders (low selectivity)
              Filter: (status = 'ACTIVE')
              Rows Removed by Filter: 905000
        ->  Hash  (cost=3000.00..3000.00 rows=50000 width=24)
                   (actual time=45.0..45.0 rows=50000 loops=1)
            │   ← Module 6, §6.4: Build phase — customers is the BUILD side
            │      (smaller input), hash table built here
              Buckets: 65536  Batches: 1  Memory Usage: 3200kB
              ->  Seq Scan on customers c  (cost=0.00..3000.00 rows=50000 width=24)
                                             (actual time=0.01..20.5 rows=50000 loops=1)
                  │   ← Module 5, §5.1: no filter on customers, full scan needed
```

### The Full Story This Plan Tells (Synthesizing Everything)

1. **Access Paths (Module 5):** Both base tables use Sequential Scan — `orders` because its `status='ACTIVE'` filter isn't selective enough to favor an index, `customers` because there's no filter to leverage at all.
2. **Join Algorithm (Module 6):** Hash Join, with `customers` correctly chosen as the smaller build-side input — exactly the "build side should be the smaller input" principle from §6.4.
3. **Aggregation (Module 8):** Hash Aggregation for the `GROUP BY`, fitting entirely in memory (`Batches: 1`) — no disk spill.
4. **Cardinality Accuracy (Module 4):** Estimated vs. actual row counts are all reasonably close throughout this plan — a sign of healthy, up-to-date statistics (contrast with Module 4 §4.12's pathological example).
5. **I/O (Module 9, §9.5):** Mostly buffer-cache hits, minimal disk reads — this data is well-cached.

### Interview Importance: ⭐⭐⭐⭐⭐
Being able to produce a synthesis like this — reading a full plan and narrating the story it tells, connecting every node back to the relevant module's theory — **is precisely the skill senior database/backend interviews are testing for.** This is the single best exercise to practice repeatedly.

## 9.10 EXPLAIN vs. EXPLAIN ANALYZE: Summary Table

| Aspect | `EXPLAIN` | `EXPLAIN ANALYZE` |
|---|---|---|
| Actually executes the query? | No | **Yes** — real side effects occur for `INSERT`/`UPDATE`/`DELETE`! |
| Shows estimated rows/cost? | Yes | Yes (alongside actual) |
| Shows actual rows/timing? | No | Yes |
| Shows buffer/memory/spill info? | No (unless combined with `BUFFERS`) | Yes, with `BUFFERS` option |
| Safe to run on production write queries? | Yes, always safe (never executes) | ⚠️ **Caution:** actually runs `INSERT`/`UPDATE`/`DELETE` — wrap in a transaction and `ROLLBACK` if you don't want the write to persist! |
| Primary use case | Quick "what plan would be chosen" check | Deep, ground-truth diagnostic investigation |

### ⚠️ Critical Safety Note (Frequently Tested)

```sql
BEGIN;
EXPLAIN ANALYZE DELETE FROM orders WHERE status = 'CANCELLED';
ROLLBACK;   -- undo the actual deletion that EXPLAIN ANALYZE just performed!
```

**`EXPLAIN ANALYZE` genuinely executes the query** — for a `DELETE`, `UPDATE`, or `INSERT`, this means real data changes happen. Wrapping in an explicit transaction with a `ROLLBACK` is a well-known, important safety practice when analyzing write-query performance.

### Interview Importance: ⭐⭐⭐⭐⭐
This safety caveat is a favorite "does this candidate have real production experience" interview question.

## 9.11 PostgreSQL vs MySQL vs Oracle: EXPLAIN Syntax & Output Comparison

| Aspect | PostgreSQL | MySQL | Oracle |
|---|---|---|---|
| Basic command | `EXPLAIN` | `EXPLAIN` | `EXPLAIN PLAN FOR ...` then `SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY)` |
| With real execution | `EXPLAIN ANALYZE` | `EXPLAIN ANALYZE` (added in MySQL 8.0.18+) | `SELECT /*+ GATHER_PLAN_STATISTICS */ ...` then `DBMS_XPLAN.DISPLAY_CURSOR(..., 'ALLSTATS LAST')` |
| Output format options | TEXT (default), JSON, XML, YAML | TEXT (default), TREE, JSON | Text-based, highly detailed via `DBMS_XPLAN` |
| Shows actual vs. estimated by default | Only with `ANALYZE` | Only with `ANALYZE` | Only with the `GATHER_PLAN_STATISTICS` hint + `DISPLAY_CURSOR` approach |

### Interview Importance: ⭐⭐⭐
Good breadth-signal to mention if discussing cross-database experience — the *concepts* (Modules 1-9) transfer universally even though exact syntax differs.

## 9.12 Best Practices, Common Mistakes & Edge Cases

### Best Practices
- Always use `EXPLAIN (ANALYZE, BUFFERS)` (not just plain `EXPLAIN`) when actually diagnosing a real performance problem — estimates alone can be misleading (Module 4).
- Wrap `EXPLAIN ANALYZE` for write queries (`INSERT`/`UPDATE`/`DELETE`) in a transaction with `ROLLBACK` unless you genuinely want the write to persist.
- Look for the biggest estimated-vs-actual row count gaps first — they're usually the root cause of an unexpectedly slow plan, and they cascade (Module 4, §4.6).
- Check for `Sort Method: external merge` / `Batches: N with Disk Usage` — direct evidence of memory-insufficiency-driven disk spilling (Modules 6-8).

### Common Mistakes
- Running `EXPLAIN ANALYZE` on a `DELETE`/`UPDATE` in production without a transaction wrapper — accidentally executing real, permanent data changes.
- Focusing only on the top-level "Total Cost" number without drilling into which specific sub-node is actually responsible for the bulk of real execution time (`actual time`).
- Forgetting that `loops > 1` means `actual time`/`actual rows` are **per-loop averages**, not totals — leading to significant misinterpretation of where time is really being spent.
- Ignoring `Rows Removed by Filter` — a large number here indicates the access path (Module 5) is reading and discarding a lot of "wasted" data, a strong signal a better index might help.

### Edge Cases
- Very fast queries (sub-millisecond) can have their `EXPLAIN ANALYZE` timing numbers meaningfully distorted by measurement overhead (§9.6) — consider `TIMING OFF` or averaging across multiple runs for such cases.
- Plans can differ between a cold cache (first run, mostly `shared read`) and a warm cache (subsequent runs, mostly `shared hit`) — always note whether you're diagnosing cold-cache or warm-cache behavior, since they can look very different.

## 9.13 Chapter Summary

- **Execution Plans** are the physical, concrete operator trees chosen by the optimizer — everything discussed in Modules 1-8 becomes visible and inspectable here.
- **Cost** shown in `EXPLAIN` is estimated (startup..total, in internal cost units) — not a direct time measurement.
- **`EXPLAIN ANALYZE`** actually runs the query, revealing **actual** rows/time alongside the estimates — the single most powerful diagnostic technique in this handbook, but it has a critical safety caveat for write queries.
- **`Buffers`** reveals real I/O activity (cache hits vs. disk reads); **timing** has measurement overhead worth knowing about; **memory/spill indicators** (`external merge`, `Batches: N Disk Usage`) directly evidence Modules 6-8's disk-spilling strategies in action.
- **Parallel worker** output (`Workers Planned`/`Launched`, `Gather`, `Partial`/`Finalize Aggregate`) makes Module 8's parallel aggregation theory concretely visible.
- The highest-value overall skill: reading a full plan and **narrating the complete story** it tells, connecting every single node back to the relevant theoretical module.

## 9.14 Cheat Sheet

```
EXPLAIN OUTPUT DECODER RING
──────────────────────────────
cost=X..Y        → estimated startup..total cost (internal units, NOT ms)
rows=N            → ESTIMATED row count (Module 4)
actual rows=N      → ACTUAL row count (only with ANALYZE)
actual time=X..Y   → real startup..total time in ms (only with ANALYZE)
loops=N            → node executed N times; actual time/rows are PER-LOOP AVERAGES
Rows Removed by Filter → wasted scan work (rows read but discarded)
Buffers: hit=X read=Y   → X pages from cache, Y pages from disk
Sort Method: external merge Disk: NkB  → spilled to disk (Module 7)
Batches: N (>1) Disk Usage: NkB          → hash op spilled to disk (Module 6/8)
Workers Planned/Launched  → parallel execution (Module 10 preview)

DIAGNOSTIC PRIORITY ORDER
──────────────────────────
1. Find the node with the LARGEST actual time contribution
   (remember: multiply by loops if loops > 1!)
2. Check estimated vs actual rows at that node — big gap? → Module 4 issue
3. Check for disk-spill indicators → Module 6/7/8 memory issue
4. Check Buffers hit vs read → cold cache / I/O-bound issue

⚠️ SAFETY: EXPLAIN ANALYZE on INSERT/UPDATE/DELETE REALLY EXECUTES IT.
   Wrap in BEGIN; ... ROLLBACK; unless you want the write to persist.
```
