# Part 6: Transactions & Concurrency Control

## Module 16: Performance Considerations

> This module ties together every mechanism from Modules 6–14 with a single unifying question: **how do these choices actually affect throughput and latency in production?** Understanding the theory is necessary but not sufficient — a senior engineer must be able to diagnose and fix real performance problems rooted in concurrency control decisions.

---

### 16.1 Lock Contention

**Definition:** **Lock contention** occurs when multiple transactions frequently compete for locks on the **same** resource, forcing many of them to wait, serializing work that could otherwise have run in parallel.

**Why it matters:** Contention is the single most common root cause of "our database feels slow" complaints in production OLTP systems — often not because the hardware is underpowered, but because transactions are architecturally forced to queue up behind each other on the same rows.

**Diagnosing contention (conceptual, engine-agnostic signals):**
- Rising average transaction latency without a corresponding rise in CPU or I/O utilization (a strong signal that transactions are *waiting*, not *computing*).
- Database-specific lock-wait views/statistics (e.g., PostgreSQL's `pg_locks` and `pg_stat_activity`, MySQL's `INFORMATION_SCHEMA.INNODB_LOCK_WAITS`, SQL Server's `sys.dm_tran_locks`) showing many transactions blocked on the same resource.

**Mitigation strategies:**
- Shorten transactions (fewer statements, less time between `BEGIN` and `COMMIT`) to reduce the window locks are held.
- Reduce lock granularity where possible (row-level instead of table-level, Module 6.7).
- Reorder operations within a transaction to acquire the most contended locks as late as possible, reducing the time they're held.
- Consider whether the contended resource can be redesigned (e.g., the append-only ledger pattern from Module 15.6) to avoid needing exclusive access to the same row at all.

### 16.2 Hot Rows

**Definition:** A **hot row** is a specific row that a disproportionately large fraction of concurrent transactions need to read and/or write, making it a natural contention bottleneck regardless of overall system capacity.

**Classic examples:** A single "total inventory count" row for a viral product; a single "wallet balance" row for a high-frequency trading account; a global "sequence counter" row.

**Why hot rows are fundamentally hard:** No amount of additional hardware, read replicas, or connection pooling helps if every transaction ultimately needs to acquire an Exclusive lock (or perform a conflicting MVCC write) on the exact same row — this is a **fundamentally serial** bottleneck by the nature of the data model, not an infrastructure limitation.

**Mitigation strategies:**
1. **Sharding the hot value:** Instead of one `stock_qty` row, maintain N "shard" rows (e.g., `stock_qty_shard_0` through `stock_qty_shard_9`), each holding a fraction of the total. Writes go to a randomly (or hash-)selected shard; reads sum across all shards. This trades a single serialization point for N parallel, much-less-contended points, at the cost of slightly more complex read logic.
2. **Append-only ledger (Module 15.6):** convert updates into inserts of "delta" rows, computing the current value via aggregation (possibly cached/materialized), avoiding row-level write contention entirely.
3. **Application-level batching/queueing:** funnel updates to the hot row through a single-threaded queue/worker that processes them serially but very quickly (e.g., in-memory, with periodic flush to the database) — trading immediate consistency for a controlled, predictable serialization point rather than an uncontrolled database-level lock queue.
4. **Dedicated atomic primitives:** where the database or a specialized system (e.g., Redis `INCR`) offers a genuinely lock-free atomic increment, use it instead of a full row-level `UPDATE ... SET x = x + 1` transaction, if consistency requirements allow.

### 16.3 Long-Running Transactions

**Definition:** A transaction that remains open (between `BEGIN` and `COMMIT`/`ROLLBACK`) for an unusually long time — seconds, minutes, or even longer — compared to the typical sub-second transaction in most OLTP workloads.

**Why they're dangerous, recapping and consolidating points from earlier modules:**
- **Lock-based engines:** any locks held by a long-running transaction (especially under Strict/Rigorous 2PL, Module 7) block every other transaction needing those same resources for the entire duration.
- **MVCC engines (PostgreSQL specifically, Module 10.8):** a long-running transaction holds an old **snapshot** open, which prevents `VACUUM` from cleaning up any row version that might still be visible to that snapshot — even for **completely unrelated tables** the long-running transaction never touches, since vacuum's cleanup horizon is determined by the oldest active snapshot in the *entire* system. This can cause severe, hard-to-diagnose table bloat across the whole database, not just the tables the offending transaction is using.
- **Undo log growth (InnoDB/Oracle):** similarly, a long-running transaction can prevent undo log space from being reclaimed, since old versions must remain reconstructable for as long as any transaction might need to see them.

**Common real-world causes:**
- An application holding a transaction open while waiting on user input, a slow external API call (Module 15.7), or a slow report/export process.
- A forgotten/leaked connection that never explicitly commits or rolls back (an "idle in transaction" session).
- A single, giant batch job processing millions of rows in one transaction instead of smaller batches (Module 6.8's lock escalation concern applies here too).

**Best Practices:**
- Set a reasonable **statement timeout** and/or **idle-in-transaction timeout** at the database level as a safety net (e.g., PostgreSQL's `idle_in_transaction_session_timeout`).
- Monitor for long-running/idle transactions proactively (most engines expose this via system views) rather than discovering the problem only after a production incident.
- Break large batch operations into smaller, separately-committed chunks (Module 6.8).

### 16.4 Transaction Batching

**Definition:** **Batching** refers to grouping multiple logical operations into a smaller number of larger transactions or statements (as opposed to one transaction per single row), to reduce per-transaction overhead (log flushes, round-trips, lock acquisition/release cycles).

**The trade-off — batching is a double-edged sword:**
- **Too little batching** (one transaction per single row insert/update): excessive overhead from repeated commit log flushes (Module 2.5's durability cost) and round-trip latency, especially over a network connection.
- **Too much batching** (one giant transaction for millions of rows): long-running-transaction problems (Section 16.3), potential lock escalation (Module 6.8), and a much larger amount of work lost if the transaction needs to abort/retry.

**Finding the right batch size — general guidance:** Batch sizes in the range of a few hundred to a few thousand rows per transaction are common practical sweet spots for bulk operations, but the right number depends heavily on row size, index maintenance cost, and replication lag tolerance — this is typically tuned empirically for a specific workload rather than derived from a universal formula.

**Practical example:**

```sql
-- ANTI-PATTERN: 1,000,000 individual transactions (very high overhead)
-- for each row: BEGIN; INSERT ...; COMMIT;

-- BETTER: batch commits every 1,000 rows
BEGIN;
  INSERT INTO logs VALUES (...);  -- x1000
COMMIT;
-- repeat for the next 1000, and so on
```

### 16.5 Lock Escalation Effects (Recap and Performance Framing)

Recall from Module 6.8: lock escalation trades granularity for reduced memory overhead. From a pure performance perspective, the key cost is a **sudden, discontinuous drop in concurrency** — a batch job that was only supposed to touch a subset of rows can unexpectedly acquire a full table lock once an internal threshold is crossed, blocking unrelated concurrent read/write traffic on the entire table. Monitoring for and tuning escalation thresholds (where the engine allows it, e.g., SQL Server) is a genuine, practical performance-tuning lever.

### 16.6 Isolation vs. Throughput

**The core trade-off, tying together Module 11 with real performance numbers (illustrative, not universal):**

| Isolation Level | Relative Throughput (illustrative) | Relative Correctness Guarantee |
|---|---|---|
| Read Uncommitted | Highest | Lowest |
| Read Committed | High | Moderate |
| Repeatable Read | Moderate | High |
| Serializable | Lowest (highest abort/blocking rate under contention) | Highest |

**Why this trade-off exists mechanically:**
- Weaker isolation levels allow more concurrent operations to proceed without waiting or aborting, at the cost of allowing more anomalies (Module 5, Module 11.6's matrix).
- Stronger isolation levels (especially Serializable) require either more blocking (2PL-based implementations) or a higher abort/retry rate (SSI/OCC-based implementations, Module 9, Module 11.5) to guarantee full correctness.

**Practical implication — the decision framework from Module 11.9 revisited through a performance lens:** don't pay the Serializable "tax" for transactions that don't need it; reserve it specifically for the operations where write-skew-style anomalies (Module 5.8) genuinely threaten a real business invariant.

### 16.7 MVCC Overhead

Recapping and extending Module 10's coverage with an explicit performance framing:

**Storage overhead:** every update creates a new version rather than modifying in place — this means **more physical storage** is used, at least until cleanup (Vacuum/undo purge) reclaims it.

**Cleanup overhead:** `VACUUM` (PostgreSQL) or undo log purging (InnoDB/Oracle) consumes CPU and I/O resources continuously in the background — under-provisioning for this maintenance work (or letting long-running transactions block it, Section 16.3) is a common, insidious source of gradual performance degradation over time (not an immediate spike, but a slow decline as bloat accumulates).

**Read overhead:** determining row visibility (checking `xmin`/`xmax` against a snapshot, Module 10.4) has a small but real per-row CPU cost — usually negligible compared to the concurrency benefits gained, but it is not literally "free."

**Net assessment:** MVCC's overhead is, for the overwhelming majority of read-heavy OLTP workloads, a very good trade against the alternative (lock-based readers blocking on writers) — but it requires **active, ongoing operational attention** (vacuum tuning, monitoring long-running transactions) rather than being a "set and forget" mechanism.

### 16.8 Choosing Isolation Levels — A Performance-Aware Checklist

Building on Module 11.9's correctness-focused framework, here's the performance-aware version:

1. **Default to Read Committed** for the vast majority of ordinary transactions (this is, not coincidentally, the actual default in most engines) — it offers the best throughput while still preventing dirty reads.
2. **Escalate to Repeatable Read / Snapshot Isolation** specifically for transactions that need internal read consistency (e.g., generating a report, or any multi-step read-then-compute logic where the computed result must reflect one consistent moment in time).
3. **Escalate to Serializable** only for the specific transactions protecting a genuine cross-row invariant (write-skew-prone logic, Module 5.8/15.5) — and ensure the application has proper retry logic for the resulting serialization failures.
4. **Never** apply Serializable blanket-wide "just to be safe" without measuring the throughput impact first — profile before and after, since the cost varies significantly by workload shape and contention level.

### 16.9 Advantages, Disadvantages, Best Practices — Consolidated

**Best Practices (the master list for this module):**
- Keep transactions **short** — this single practice mitigates lock contention, hot-row impact, MVCC bloat, and lock escalation risk simultaneously.
- Batch bulk operations into **moderate-sized chunks**, not one-row-at-a-time and not one-giant-transaction.
- Monitor for **long-running/idle-in-transaction sessions** proactively.
- Choose isolation levels **deliberately, per-transaction**, rather than applying one blanket setting everywhere.
- For genuinely hot rows, consider **architectural mitigations** (sharding the counter, append-only ledgers) rather than relying purely on database tuning.
- Understand and periodically **tune vacuum/undo-log maintenance** settings for your specific write volume, rather than accepting defaults blindly at scale.

**Common Mistakes:**
- Diagnosing a slow system purely by looking at CPU/memory graphs and missing lock-wait time entirely — always check lock-wait statistics specifically when investigating unexplained latency.
- Applying `SERIALIZABLE` everywhere reflexively "for safety," then being surprised by a high abort rate and poor throughput under real load.
- Ignoring "idle in transaction" sessions until they cause a production incident (severe bloat, or a blocked DDL migration that can't proceed while an old transaction holds a conflicting lock).

**Performance Implications — this entire module IS the performance implications section**, applied comprehensively across every mechanism from Modules 6–14.

**Industry Usage:** Every major production database team maintains **active monitoring dashboards** for lock waits, long-running transactions, replication lag, and vacuum/undo health — these are not "nice to have" but standard, essential operational practice for any serious OLTP deployment at scale.

### 16.10 Chapter Summary

- **Lock contention** and **hot rows** are the most common real-world root causes of "slow database" complaints — mitigated via shorter transactions, reduced lock granularity, and architectural redesign (sharding, append-only ledgers) for the hottest resources.
- **Long-running transactions** cause blocking (lock-based engines) and severe bloat (MVCC engines, via blocked vacuum/undo cleanup) — monitor and timeout aggressively.
- **Transaction batching** trades per-transaction overhead against long-running-transaction risk — find a moderate sweet spot, tuned empirically.
- **Lock escalation** can cause sudden, discontinuous concurrency drops in batch jobs.
- **Isolation level choice** is fundamentally a throughput-vs-correctness trade-off — choose deliberately, per-transaction, rather than applying one setting universally.
- **MVCC overhead** (storage, cleanup, visibility-check CPU cost) is generally a good trade for read-heavy workloads but requires active operational maintenance.

### 16.11 Revision Notes / Cheat Sheet

```
Lock Contention  → shorten transactions, reduce granularity, redesign hot resources
Hot Rows         → shard the counter, append-only ledger, dedicated atomic primitives
Long Txns        → block other locks (2PL) AND block vacuum/undo cleanup (MVCC) — TIMEOUT them
Batching         → moderate chunk sizes; avoid both 1-row-per-txn AND giant-single-txn extremes
Lock Escalation  → sudden concurrency drop in batch jobs — batch in smaller chunks to avoid
Isolation Choice → default to Read Committed; escalate ONLY where the specific anomaly matters
MVCC Overhead    → storage + cleanup (vacuum/undo) + visibility-check CPU — monitor, don't ignore
```
