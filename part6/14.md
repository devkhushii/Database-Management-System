# Part 6: Transactions & Concurrency Control

## Module 14: Distributed Transactions (Introduction)

> Module 1.9 previewed this: a local transaction guarantees atomicity within **one** database. But modern systems are rarely built on a single database — microservices, sharded databases, and multi-vendor systems mean a single business operation often spans **multiple independent transactional resources**. This module covers the classic mechanisms for extending atomicity guarantees across those boundaries.

---

### 14.1 Why Distributed Transactions?

**The problem:** Consider an order-processing operation that must, as a single atomic unit:
1. Debit inventory in an **Inventory Service's** database.
2. Charge a customer via a **Payment Service's** database (possibly a third-party system entirely).
3. Create a record in an **Orders Service's** database.

Each of these might be a **separate database**, possibly on separate physical machines, possibly even operated by different companies (e.g., a payment gateway). A plain local transaction (`BEGIN...COMMIT`) only protects operations within **one** database — it has no mechanism to coordinate "all or nothing" across independent systems.

**Real-world analogy:**
Think of a distributed transaction like coordinating a **synchronized wedding ceremony across three different countries via video call**, where the officiant in each country must all say "I now pronounce you married" **at the exact same moment** — if even one country's officiant refuses at the last second, the wedding must be called off **everywhere**, not just in that one country. Coordinating this requires an explicit protocol (someone counting down "3, 2, 1, go" and confirming everyone is ready first) — that's exactly the role of a distributed commit protocol.

---

### 14.2 Two-Phase Commit (2PC) — Overview

**Definition:** **Two-Phase Commit (2PC)** is a protocol for achieving atomic commitment across multiple independent databases (called **participants** or **resource managers**), coordinated by a single **coordinator** (also called the **transaction manager**). As the name suggests, it operates in exactly two phases.

**Phase 1 — Prepare (Voting) Phase:**
1. The coordinator sends a `PREPARE` message to **every** participant.
2. Each participant does everything necessary to be able to commit **if told to** — writing all its changes to its own durable log (Module 2), acquiring/holding all necessary locks — but does **NOT** actually commit yet.
3. Each participant replies to the coordinator with either `YES` (I am prepared and guarantee I can commit if instructed) or `NO` (I cannot commit, e.g., due to a constraint violation or local failure).

**Phase 2 — Commit (Decision) Phase:**
1. **If ALL participants voted `YES`:** the coordinator sends a `COMMIT` message to every participant, and each participant finalizes its local transaction and durably commits.
2. **If ANY participant voted `NO`** (or failed to respond within a timeout): the coordinator sends an `ABORT` message to every participant, and each participant rolls back its local transaction.

```
                    COORDINATOR
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
  Participant A     Participant B     Participant C
   (Inventory)        (Payment)          (Orders)

PHASE 1 (Prepare):
  Coordinator → PREPARE → A, B, C
  A → YES     B → YES     C → YES
  (all say yes → proceed to commit)

PHASE 2 (Commit):
  Coordinator → COMMIT → A, B, C
  A commits   B commits   C commits
  → Distributed transaction SUCCEEDS
```

**Failure scenario:**

```
PHASE 1 (Prepare):
  Coordinator → PREPARE → A, B, C
  A → YES     B → NO (payment declined!)     C → YES

PHASE 2 (Abort):
  Coordinator → ABORT → A, B, C
  A rolls back  B rolls back  C rolls back
  → Distributed transaction ABORTS entirely, nothing is committed anywhere
```

**Why the "Prepare" phase is essential:** By the time a participant votes `YES`, it has made an **irrevocable promise** — it must be able to commit successfully if told to, no matter what (this is why it durably logs everything and holds all locks *before* voting yes). This guarantees that once all participants vote yes, the coordinator can safely tell everyone to commit, knowing none of them can subsequently fail to do so for a "normal" reason (only a true catastrophic failure, like permanent disk loss, could prevent it at that point).

---

### 14.3 2PC — Failure Scenarios and the Blocking Problem

**The central weakness of 2PC:** What happens if the **coordinator itself crashes** after some participants have voted `YES` and are sitting in the "prepared" state, waiting for the final `COMMIT`/`ABORT` decision, but **before** that decision is sent?

```
Coordinator → PREPARE → A, B, C
A → YES     B → YES     C → YES
[COORDINATOR CRASHES HERE, before sending COMMIT/ABORT]

A, B, C are now stuck in the "PREPARED" state:
  - They cannot unilaterally commit (they don't know if EVERYONE voted yes)
  - They cannot unilaterally abort (they promised they COULD commit if told to)
  - They must hold all their locks and wait ... indefinitely, until the coordinator recovers
```

This is called the **blocking problem** — participants are stuck holding locks (blocking other transactions from touching that data) until the coordinator recovers and tells them the final decision. This is 2PC's most significant, widely-cited practical weakness, and it's exactly the motivation for **Three-Phase Commit** (Section 14.4).

**Recovery in practice:** Real systems mitigate this by having the coordinator write its decision to a durable log *before* sending `COMMIT`/`ABORT` messages, so that upon restart, it can figure out what it had already decided and re-send the appropriate messages — but participants are still blocked for the duration of the coordinator's downtime.

---

### 14.4 Three-Phase Commit (3PC) — Overview

**Definition:** **Three-Phase Commit (3PC)** is an extension of 2PC that inserts an **additional intermediate phase** specifically to eliminate (or reduce) the blocking problem, by ensuring that at any point in the protocol, participants have enough information to make a safe, non-blocking decision even if the coordinator fails.

**The three phases:**
1. **CanCommit (Voting) Phase:** Same as 2PC's Prepare phase — coordinator asks, participants vote yes/no.
2. **PreCommit Phase (the new, added phase):** If all participants voted yes, the coordinator sends a `PRE-COMMIT` message (not yet the final commit) — participants acknowledge receipt of this message. This step's purpose is to ensure that **if any participant has received a PRE-COMMIT message, then ALL participants are guaranteed to have voted yes** — meaning if the coordinator subsequently crashes, participants can safely infer "everyone agreed, so it's safe to just commit anyway," rather than being stuck unsure.
3. **DoCommit Phase:** The coordinator sends the final `COMMIT` message, and participants finalize.

**Why this helps:** With 3PC, if the coordinator crashes **after** some participant has received `PRE-COMMIT`, that participant (and, by the protocol's design, all others too) can safely conclude the transaction should commit, without needing to wait for the crashed coordinator to recover — reducing the blocking window significantly compared to 2PC.

**Why 3PC is rarely used in practice despite this improvement:**
- It still cannot fully handle **network partitions** — a participant might be unable to distinguish "the coordinator crashed" from "I'm just disconnected from the coordinator temporarily," and could make an incorrect independent decision in some partition scenarios, potentially leading to inconsistency.
- It adds an **extra round of network communication** (the additional phase), increasing latency for every single distributed transaction.
- Given these practical costs and its incomplete handling of network partitions, most real-world distributed systems either accept 2PC's blocking risk (mitigated with monitoring/alerting for stuck coordinators) or move to fundamentally different approaches like the **SAGA pattern** (Section 14.6) instead of 3PC.

---

### 14.5 XA Transactions — Overview

**Definition:** **XA** is an **open, vendor-neutral standard** (from The Open Group) defining the interface between a **Transaction Manager** (the coordinator) and various **Resource Managers** (individual databases, message queues, etc.) so that **heterogeneous systems from different vendors** can all participate in a single, standardized 2PC-based distributed transaction.

**Why it exists:** Before XA, coordinating a distributed transaction across, say, an Oracle database and a separate MQ message broker required custom, vendor-specific integration code. XA standardizes the `PREPARE`/`COMMIT`/`ROLLBACK` interface so that **any** XA-compliant resource manager can participate in a transaction coordinated by **any** XA-compliant transaction manager, regardless of vendor.

**How it's used in practice:**

```sql
-- Conceptual XA usage (actual syntax varies by driver/language)
XA START 'txn123';
  -- perform operations against this XA-compliant resource
XA END 'txn123';
XA PREPARE 'txn123';    -- this resource's "vote" — durably prepared
-- (coordinator collects votes from ALL resources involved)
XA COMMIT 'txn123';     -- or XA ROLLBACK 'txn123' if any resource voted no
```

**Industry usage:** XA is supported by MySQL (InnoDB), PostgreSQL, Oracle, SQL Server, and major message brokers/application servers (e.g., Java EE's JTA — Java Transaction API — is built directly on XA concepts). It's most commonly seen in enterprise Java applications coordinating a database and a message queue within a single transaction.

**Known drawbacks (this is exactly why many modern architectures avoid XA):**
- Inherits 2PC's blocking problem.
- Significant performance overhead — the coordination round-trips add real latency to every transaction.
- Operational complexity — requires all participating systems to correctly implement and reliably support the XA protocol, and failures in this coordination layer can be genuinely hard to debug.

---

### 14.6 The SAGA Pattern — Overview

**Definition:** The **SAGA pattern** is a fundamentally different approach to managing a business operation that spans multiple independent services/databases — rather than a single atomic all-or-nothing distributed transaction coordinated by 2PC/3PC/XA, a saga breaks the operation into a **sequence of local transactions**, each with an associated **compensating action** that can **undo** its effects if a later step in the sequence fails.

**Why it exists:** 2PC/XA's blocking behavior and heavy coordination overhead make them a poor fit for modern **microservices** architectures, where services are meant to be independently deployable, scalable, and loosely coupled — holding locks across a slow, multi-service coordination protocol works directly against those goals. SAGAs trade strict, immediate atomicity for **eventual consistency**, achieved through a defined sequence of local commits and, if necessary, compensating "undo" actions.

**Example — the order-processing scenario as a SAGA:**

```
Step 1: Inventory Service reserves stock.        [Local commit]
   Compensating action: Release reserved stock.

Step 2: Payment Service charges the customer.    [Local commit]
   Compensating action: Refund the customer.

Step 3: Orders Service creates the order record.  [Local commit]
   Compensating action: Cancel/delete the order record.

If Step 3 FAILS:
   → Run Step 2's compensating action (refund the customer)
   → Run Step 1's compensating action (release reserved stock)
   → The overall business operation is "rolled back," via compensation,
     NOT via a single atomic distributed rollback.
```

```
Success path:  Reserve Stock ──► Charge Payment ──► Create Order ──► DONE
                                                          │
Failure at Step 3:                                       ▼ (fails)
               Reserve Stock ──► Charge Payment ──► [FAILS]
                     ▲                  │
                     │                  ▼
             Release Stock ◄──── Refund Payment   (compensating actions, run in reverse order)
```

**Two common SAGA coordination styles:**
1. **Choreography:** Each service, after completing its local step, publishes an event (e.g., "InventoryReserved") that the next service listens for and reacts to — fully decentralized, no central coordinator.
2. **Orchestration:** A central "saga orchestrator" service explicitly calls each step in sequence and explicitly triggers compensating actions on failure — more centralized, but easier to reason about and debug for complex, multi-step sagas.

**Key trade-off vs. 2PC/XA:**

| Aspect | 2PC / XA | SAGA |
|---|---|---|
| Atomicity | Strict, immediate (all-or-nothing) | Eventual, via compensation |
| Blocking | Yes (participants wait, holding locks) | No — each local transaction commits independently and immediately |
| Complexity | Coordination protocol complexity | Application-level compensation logic complexity |
| Isolation | Full isolation across the whole operation | Intermediate states ARE visible to other transactions/services before the saga completes — a real anomaly risk (e.g., another process could see "stock reserved but payment not yet charged") that must be handled explicitly at the application level |
| Best suited for | Tightly-coupled systems needing strict, immediate consistency | Loosely-coupled microservices prioritizing availability and independent scalability |

**Important caveat about SAGA and Isolation:** Because each step commits independently and immediately, **other transactions can observe intermediate, "in-progress" saga states** — this is a real, application-visible anomaly risk that 2PC/XA's strict isolation would prevent, but that SAGA explicitly accepts as a trade-off for its architectural benefits. Handling this correctly (e.g., using a "pending" status field that other reads are aware of and account for) is an essential, non-optional part of designing a correct SAGA-based system.

### 14.7 Comparison Table — All Four Approaches

| Approach | Atomicity Style | Blocking? | Complexity | Best Fit |
|---|---|---|---|---|
| **2PC** | Strict, coordinator-driven | Yes (coordinator failure blocks participants) | Moderate | Tightly-coupled systems, moderate scale |
| **3PC** | Strict, reduces blocking window | Reduced, but not eliminated; still fails under network partitions | High (extra round-trip) | Rarely used in practice |
| **XA** | Strict, standardized 2PC across vendors | Yes (inherits 2PC's issue) | High (protocol + vendor support complexity) | Enterprise Java, cross-vendor DB+MQ coordination |
| **SAGA** | Eventual, via compensation | No | Application-level compensation logic complexity | Microservices, high availability/scalability priorities |

### 14.8 Advantages, Disadvantages, Best Practices

**Advantages of distributed transaction protocols in general:**
- Enable business operations to span multiple independent systems while still providing *some* form of correctness guarantee.
- 2PC/XA provide strict, immediate all-or-nothing semantics when that's genuinely required.
- SAGA provides a practical, scalable alternative for architectures where 2PC's blocking behavior is unacceptable.

**Disadvantages:**
- 2PC/XA: blocking risk, coordination overhead, operational complexity.
- SAGA: requires careful compensating-action design, exposes intermediate states, shifts complexity from infrastructure to application code.

**Best Practices:**
- Prefer **SAGA** (or simply avoiding distributed transactions altogether via careful service/data boundary design) for modern microservices architectures, given 2PC's known operational risks at scale.
- If using 2PC/XA, monitor coordinator health closely and have clear operational runbooks for handling a stuck/crashed coordinator.
- For SAGA-based systems, design compensating actions to be **idempotent** (safe to run more than once) since failures and retries in a distributed system are inevitable.
- Explicitly design for and communicate the "intermediate state visibility" trade-off inherent in SAGA to anyone building on top of the affected services.

**Common Mistakes:**
- Assuming SAGA provides the same isolation guarantees as a single ACID transaction — it fundamentally does not, and pretending otherwise leads to subtle production bugs.
- Underestimating the operational complexity of running XA in production — many teams adopt it for its theoretical elegance and are surprised by its practical fragility at scale.
- Not designing compensating actions carefully enough to handle partial failures within the compensation itself (e.g., what if the "refund" compensating action also fails?).

**Industry Usage:** Modern large-scale, microservices-based systems (e-commerce platforms, ride-sharing apps, food delivery platforms) overwhelmingly favor the SAGA pattern (or simpler, domain-specific eventual-consistency designs) over 2PC/XA, precisely because of the blocking and scalability concerns discussed here — this is a very common, practical senior-engineer interview discussion topic.

### 14.9 Chapter Summary

- A **distributed transaction** spans multiple independent databases/resource managers, requiring explicit coordination to preserve atomicity.
- **Two-Phase Commit (2PC)**: Prepare (vote) phase, then Commit/Abort (decision) phase — but suffers from the **blocking problem** if the coordinator crashes mid-protocol.
- **Three-Phase Commit (3PC)**: adds a PreCommit phase to reduce blocking, but adds latency and still doesn't fully solve network-partition scenarios — rarely used in practice.
- **XA**: a vendor-neutral standard implementing 2PC across heterogeneous resource managers (e.g., DB + message queue).
- **SAGA pattern**: replaces strict atomicity with a sequence of local transactions plus compensating actions — no blocking, but exposes intermediate states and shifts complexity to the application layer. Implemented via **choreography** (event-driven) or **orchestration** (central coordinator).

### 14.10 Revision Notes / Cheat Sheet

```
2PC:  PREPARE (vote) → COMMIT/ABORT (decision)     | risk: coordinator crash = participants BLOCKED
3PC:  CanCommit → PreCommit → DoCommit             | reduces blocking, adds latency, rare in practice
XA:   standardized 2PC across vendors (DB + MQ)     | inherits 2PC's blocking risk
SAGA: local txns + compensating actions             | no blocking, but exposes intermediate state,
                                                       eventual consistency, NOT strict isolation
```
