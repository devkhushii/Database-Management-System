# Part 6: Transactions & Concurrency Control

## Module 8: Timestamp-Based Concurrency Control

> Modules 6–7 covered locking — a **pessimistic**, blocking approach where transactions physically wait for each other. Now we explore a completely different philosophy: instead of blocking, assign every transaction a unique **timestamp** and use it to order conflicting operations *without any locks at all*. This module covers Timestamp Ordering (TO), the Thomas Write Rule, and Strict Timestamp Ordering.

---

### 8.1 The Core Idea

**Definition:** **Timestamp-Based Concurrency Control** assigns each transaction a unique **timestamp** at the moment it begins (typically derived from a monotonically increasing counter or the system clock). The protocol then enforces that the **order of conflicting operations must match the order of the transactions' timestamps** — effectively simulating a serial schedule ordered by timestamp, without ever using locks.

**Why it exists / what problem it solves:**
Locking-based protocols achieve serializability by physically blocking conflicting operations until it's safe to proceed. Timestamp ordering takes a different approach: it **decides the serial order in advance** (by timestamp) and then **rejects (aborts) any operation that would violate that predetermined order**, rather than making anyone wait. This trades "waiting" for "aborting and retrying" as the mechanism of conflict resolution.

**Real-world analogy:**
Think of timestamp ordering like a **strict "take-a-number" queue system**, except instead of physically waiting in line, everyone is *told in advance* what order they're supposed to be served in (based on when they took their number), and if someone tries to act "out of turn" relative to someone who already acted, their action is simply rejected on the spot — they have to start over with a new number.

---

### 8.2 Timestamps — How They're Assigned

**Definition:** `TS(Ti)` denotes the timestamp of transaction Ti, assigned when the transaction begins. Timestamps must be **unique** and **monotonically increasing** so that if `TS(Ti) < TS(Tj)`, the system treats Ti as if it "logically happened first," even if their actual operations interleave in real time.

**Common ways timestamps are generated:**
1. **System clock** (with a mechanism to break ties/ensure uniqueness, e.g., appending a node ID in distributed systems).
2. **Logical counter** — a simple incrementing integer, incremented and assigned atomically each time a new transaction begins.

---

### 8.3 Read and Write Timestamps on Data Items

For **every data item X**, the system additionally maintains two values:

- **`W-timestamp(X)`**: the timestamp of the **most recent transaction that successfully wrote** X.
- **`R-timestamp(X)`**: the timestamp of the **most recent (i.e., largest-timestamp) transaction that successfully read** X.

These two values are the "memory" the protocol uses to detect when an operation would violate the timestamp order.

---

### 8.4 The Basic Timestamp Ordering (TO) Protocol Rules

**For a Read operation, `R_i(X)` by transaction Ti:**

- **If `TS(Ti) < W-timestamp(X)`:** Ti is trying to read a value that was **already overwritten** by a transaction that (by timestamp) happened *after* Ti "should have" read it. This means Ti is reading a value that's "obsolete" relative to its own logical position in time. **Reject and abort Ti** (it must restart with a new, larger timestamp).
- **Else:** the read is allowed. Set `R-timestamp(X) = max(R-timestamp(X), TS(Ti))`.

**For a Write operation, `W_i(X)` by transaction Ti:**

- **If `TS(Ti) < R-timestamp(X)`:** Some transaction with a *later* timestamp than Ti has already read X — meaning that transaction read a version of X that existed *before* Ti's write "should have" happened. Ti's write would retroactively invalidate a read that already happened from a future perspective. **Reject and abort Ti.**
- **If `TS(Ti) < W-timestamp(X)`:** Some transaction with a later timestamp already wrote a newer value to X. Writing now would mean an "earlier" transaction's write is overwriting a "later" one — violating timestamp order. Under the **Basic** protocol, this write is also **rejected and Ti is aborted**. *(The Thomas Write Rule, Section 8.6, offers an important refinement to this specific case.)*
- **Else:** the write is allowed. Set `W-timestamp(X) = TS(Ti)`.

---

### 8.5 Worked Example — Basic Timestamp Ordering

Let `TS(T1) = 10` and `TS(T2) = 20` (T2 has a later timestamp — logically "comes after" T1).

Initial state: `R-timestamp(A) = 0`, `W-timestamp(A) = 0`.

```
Operation Sequence:  R2(A)   R1(A)   W1(A)   W2(A)

Step 1: R2(A) by T2 (TS=20)
  Check: TS(T2)=20 < W-timestamp(A)=0? No.
  ALLOWED. Set R-timestamp(A) = max(0, 20) = 20.

Step 2: R1(A) by T1 (TS=10)
  Check: TS(T1)=10 < W-timestamp(A)=0? No.
  ALLOWED. Set R-timestamp(A) = max(20, 10) = 20 (unchanged, T2's read was later).

Step 3: W1(A) by T1 (TS=10)
  Check: TS(T1)=10 < R-timestamp(A)=20? YES!
  T1 is trying to write A, but T2 (a "later" transaction) has ALREADY READ A.
  T1's write would retroactively invalidate what T2 read.
  → REJECT. T1 is ABORTED and must restart with a new timestamp.
```

This example demonstrates the classic timestamp-ordering conflict: T2 "jumped ahead" (read first, even though it has a later timestamp — it just happened to execute its read earlier in real time), and then T1 (with the earlier, "should-go-first" timestamp) tried to write, but it's too late — T2 has already committed to having seen the *old* value.

---

### 8.6 The Thomas Write Rule

**Definition:** The **Thomas Write Rule** is an optimization to the Basic Timestamp Ordering protocol's write rule, specifically for the case:

> `TS(Ti) < W-timestamp(X)` — i.e., a transaction with a later timestamp has *already written* a newer value to X.

**The insight:** Under Basic TO, this situation forces Ti to abort. But think about it: if `TS(Ti) < W-timestamp(X)`, it means some transaction Tj with `TS(Tj) > TS(Ti)` has *already* written a value to X that will "win" in the final serial order anyway (since Tj comes after Ti). **Ti's write to X is about to be immediately overwritten/superseded regardless** — so instead of aborting Ti, we can simply **ignore (skip) Ti's write entirely** and let Ti continue executing normally! This is called **"ignoring obsolete writes."**

**Why this is safe:** Since Ti's write to X would have no observable effect anyway (a later-timestamped transaction already wrote a "newer" value that supersedes it in timestamp order), skipping it doesn't change the final serialization-equivalent outcome — it just avoids an unnecessary abort, **improving concurrency** without sacrificing correctness.

**Important caveat:** The Thomas Write Rule does **NOT** apply to the *other* write-rejection case (`TS(Ti) < R-timestamp(X)`) — that case must still cause an abort, because some transaction has already *read* a value, and if we let Ti's write through (even skipped or not), the fact that a later transaction read *before* Ti's logical write position is unfixable; the anomaly there is about reads, not writes, and reads can't be "un-observed."

**Revised Write Rule with Thomas Write Rule applied:**

```
W_i(X) requested:
  IF TS(Ti) < R-timestamp(X):
      REJECT, abort Ti                      -- unchanged from Basic TO
  ELSE IF TS(Ti) < W-timestamp(X):
      IGNORE the write (Thomas Write Rule)   -- NEW: don't abort, just skip
      Ti continues executing normally
  ELSE:
      ALLOW the write
      W-timestamp(X) = TS(Ti)
```

**Worked example — Thomas Write Rule in action:**

```
TS(T1) = 10, TS(T2) = 20
Initial: R-timestamp(A) = 0, W-timestamp(A) = 0

Step 1: W2(A) by T2 (TS=20)
  TS(T2)=20 < R-timestamp(A)=0? No.
  TS(T2)=20 < W-timestamp(A)=0? No.
  ALLOWED. W-timestamp(A) = 20.

Step 2: W1(A) by T1 (TS=10)
  TS(T1)=10 < R-timestamp(A)=0? No.
  TS(T1)=10 < W-timestamp(A)=20? YES!
  Under BASIC TO: T1 would be ABORTED.
  Under THOMAS WRITE RULE: T1's write is simply IGNORED (skipped).
     T1 continues executing its remaining operations normally — no abort needed!
```

**Practical significance:** The Thomas Write Rule is a classic example (and a favorite exam/interview talking point) of how relaxing a protocol slightly (allowing non-conflict-serializable-in-the-strict-sense schedules) can still guarantee correctness (specifically, it guarantees **view serializability**, not just conflict serializability — connecting directly back to Module 4's distinction!) while improving performance.

---

### 8.7 Timestamp Ordering — Guarantees and Trade-offs

**What it guarantees:** The Basic Timestamp Ordering protocol guarantees **conflict serializability** — the equivalent serial order is precisely the order of the transactions' timestamps.

**What it does NOT guarantee by default:** Basic TO does **not** guarantee recoverability! A transaction Ti could read a value written by Tj, and then Ti could commit before Tj — exactly the irrecoverable schedule pattern from Module 3.9 — because the basic protocol has no notion of "commit" in its read/write rules at all, only raw read/write ordering.

---

### 8.8 Strict Timestamp Ordering

**Definition:** **Strict Timestamp Ordering** adds a rule on top of Basic TO to guarantee **strictness** (Module 3.8), analogous to how Strict 2PL added a rule to Basic 2PL: **a read or write operation on data item X must wait (be delayed) until the transaction that last wrote X has committed or aborted**, if that writer's timestamp is smaller (i.e., it "should" have already finished).

**Why it exists:** Just like with locking, guaranteeing raw serializability isn't enough for practical safety — you also need to prevent dirty reads/writes and cascading rollbacks. Strict Timestamp Ordering achieves this by introducing a *brief waiting condition*, even though the overall philosophy of timestamp ordering is otherwise non-blocking. This is a hybrid: mostly abort-based, but with a small dose of blocking specifically to protect against reading/writing uncommitted data.

**Comparison to Strict 2PL:** Both mechanisms exist to solve the exact same problem (avoiding dirty reads/writes and cascading rollbacks) but from different underlying protocols — Strict 2PL achieves it by holding locks until commit; Strict Timestamp Ordering achieves it by making transactions wait specifically on uncommitted writers, without using a general-purpose lock manager.

---

### 8.9 Validation (Preview / Bridge to Module 9)

Timestamp ordering, as described, checks conflicts **eagerly**, at the moment of every single read/write operation. There's a related but distinct family of protocols that instead let a transaction execute freely and only check for conflicts **once, at the end**, right before commit — this is called **Validation**, and it's the defining characteristic of **Optimistic Concurrency Control**, covered fully in **Module 9**. Timestamps are often reused as part of the validation logic there too, so understanding timestamp assignment here directly sets up Module 9.

---

### 8.10 Timestamp Ordering vs. 2PL — Comparison Table

| Aspect | Two-Phase Locking (2PL) | Timestamp Ordering (TO) |
|---|---|---|
| Core mechanism | Locks block conflicting operations | Timestamps reject/abort out-of-order operations |
| Conflict resolution | Waiting | Aborting and restarting |
| Deadlocks possible? | Yes (needs separate detection — Module 12) | **No** — timestamp ordering is inherently deadlock-free, since transactions never wait on each other in a circular way; they simply abort |
| Serial order determined | Emerges dynamically from lock acquisition order | Fixed in advance by timestamp assignment |
| Guarantees serializability? | Yes | Yes |
| Guarantees strictness? | Only Strict/Rigorous variants | Only Strict Timestamp Ordering variant |
| Overhead | Lock table management | Maintaining R-timestamp/W-timestamp per data item; frequent aborts under high contention |
| Best suited for | Moderate-to-high contention workloads where waiting is cheaper than restarting | Low-contention workloads, or where deadlock-freedom is paramount |

**Key exam takeaway:** Timestamp Ordering is **deadlock-free by construction** — a major theoretical advantage over 2PL — but it can suffer from a **high abort rate** under heavy contention, since conflicting transactions are aborted rather than made to wait, which can waste significant work if transactions are long or contention is high.

---

### 8.11 Advantages, Disadvantages, Best Practices

**Advantages:**
- **No deadlocks** — a huge structural advantage over lock-based protocols.
- No lock manager overhead (though it requires maintaining per-item read/write timestamps, which has its own bookkeeping cost).
- The Thomas Write Rule specifically improves concurrency by intelligently skipping obsolete writes instead of aborting.

**Disadvantages:**
- Can produce a **high abort/restart rate** under contention — repeatedly aborting and retrying wastes work compared to simply waiting a bit (as 2PL would).
- **Starvation risk:** a transaction with a very "unlucky" (relatively old, frequently-conflicting) timestamp could theoretically be aborted repeatedly if the system doesn't guarantee it gets a fresh, later timestamp and priority on retry.
- Requires maintaining fine-grained R-timestamp/W-timestamp metadata per data item, which has memory/overhead costs at scale, especially for cold or rarely-accessed items.

**Best Practices:**
- Timestamp ordering suits workloads with relatively **low contention**, where aborts are rare and cheap to retry.
- Combine with the Thomas Write Rule to reduce unnecessary aborts on write-write conflicts.
- Use Strict Timestamp Ordering (not Basic) in any production-grade system, to avoid cascading rollback risk.

**Common Mistakes:**
- Forgetting that Basic Timestamp Ordering does **not** guarantee recoverability — a common exam trap, since students often assume "serializable" automatically implies "safe to use in production."
- Confusing the Thomas Write Rule's *scope* — it only applies to the `W-timestamp` check, never the `R-timestamp` check for writes.

**Performance Implications:** In write-heavy, high-contention workloads, pure timestamp ordering can perform *worse* than locking, because repeated aborts waste more work than the equivalent waiting time under 2PL would have cost. This is why most production RDBMS engines favor lock-based (2PL) or MVCC-based approaches over pure timestamp ordering as their primary mechanism — timestamp ordering concepts, however, live on as a *component* of MVCC's version-visibility logic (Module 10) and OCC's validation phase (Module 9).

**Industry Usage:** Pure timestamp ordering as described here is relatively rare as the sole mechanism in mainstream production RDBMS (most use locking or MVCC as primary mechanisms), but the *concept* of timestamps is foundational and reused pervasively — MVCC's version chains are fundamentally timestamp-ordered, and distributed databases (e.g., Google Spanner) use globally synchronized timestamps (TrueTime) as a first-class concurrency control mechanism at massive scale.

### 8.12 Chapter Summary

- **Timestamp Ordering** assigns each transaction a unique timestamp and enforces that conflicting operations occur in timestamp order — violations cause an **abort**, not a wait.
- Every data item tracks a **R-timestamp** and **W-timestamp**.
- **Read rule:** reject if `TS(Ti) < W-timestamp(X)`.
- **Write rule (Basic):** reject if `TS(Ti) < R-timestamp(X)` OR `TS(Ti) < W-timestamp(X)`.
- **Thomas Write Rule:** if only the write-timestamp check fails (not the read-timestamp check), **ignore** the write instead of aborting — improves concurrency, guarantees view serializability.
- **Strict Timestamp Ordering** adds a wait condition on uncommitted writers to guarantee strictness/no cascading rollback.
- TO is **deadlock-free** by construction but can suffer high abort rates under contention — the opposite trade-off profile from 2PL.

---

### 8.13 Revision Notes / Cheat Sheet

```
READ  R_i(X): if TS(Ti) < W-ts(X)  → ABORT
              else: OK, R-ts(X) = max(R-ts(X), TS(Ti))

WRITE W_i(X): if TS(Ti) < R-ts(X)  → ABORT (always, even with Thomas rule)
              elif TS(Ti) < W-ts(X) → Basic: ABORT | Thomas: IGNORE (skip write)
              else: OK, W-ts(X) = TS(Ti)

TO guarantees:      Serializability ✔, Deadlock-freedom ✔ (by construction)
TO does NOT guarantee (Basic): Recoverability ✘ → use Strict TO for that
```
