## Section C — SQL Questions (100+)

*(20 fully-worked practical problems below; treat as a problem set — write your own query before checking the provided solution.)*

1. **Find all customers who have never placed an order.**
```sql
SELECT c.* FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;
```

2. **Find the top 3 highest-spending customers.**
```sql
SELECT customer_id, SUM(total_amount) AS total_spent
FROM orders GROUP BY customer_id
ORDER BY total_spent DESC LIMIT 3;
```

3. **Find employees earning more than their manager.**
```sql
SELECT e.name FROM employees e
JOIN employees m ON e.manager_id = m.employee_id
WHERE e.salary > m.salary;
```

4. **Delete duplicate rows, keeping only the lowest `id` per duplicate group (by `email`).**
```sql
DELETE FROM users a USING users b
WHERE a.email = b.email AND a.id > b.id;
```

5. **Write a query using a window function to find each department's highest-paid employee.**
```sql
SELECT * FROM (
  SELECT *, RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk
  FROM employees
) t WHERE rnk = 1;
```

6. **Find the running total of daily sales.**
```sql
SELECT sale_date, daily_total,
       SUM(daily_total) OVER (ORDER BY sale_date) AS running_total
FROM daily_sales;
```

7. **Find customers who placed orders in every month of 2026.**
```sql
SELECT customer_id FROM orders
WHERE EXTRACT(YEAR FROM created_at) = 2026
GROUP BY customer_id
HAVING COUNT(DISTINCT EXTRACT(MONTH FROM created_at)) = 12;
```

8. **Write a recursive CTE to find all subordinates of a given manager.**
```sql
WITH RECURSIVE subordinates AS (
  SELECT employee_id, manager_id FROM employees WHERE manager_id = 1
  UNION ALL
  SELECT e.employee_id, e.manager_id FROM employees e
  JOIN subordinates s ON e.manager_id = s.employee_id
)
SELECT * FROM subordinates;
```

9. **Pivot rows into columns: total sales per product per quarter.**

## Section D — Debugging Problems (50+)

*(10 fully-specified incidents below, each modeled on Module 11's structure: Symptom → Investigate → Root Cause → Fix.)*

1. **Symptom:** A report query that ran in 2 seconds yesterday now takes 45 seconds, with no code changes. **Investigate:** Check if a bulk data load happened recently without a subsequent `ANALYZE`. **Root Cause:** Stale statistics led the planner to choose a bad plan. **Fix:** Run `ANALYZE`; consider `autovacuum_analyze` tuning.

2. **Symptom:** Application intermittently throws "could not serialize access due to concurrent update." **Investigate:** Confirm isolation level (likely Serializable/Repeatable Read) and concurrent write patterns. **Root Cause:** Genuine write-write conflict under strict isolation. **Fix:** Implement application-layer retry with backoff; consider whether Serializable is truly needed for this operation.

3. **Symptom:** A nightly batch job now takes 6 hours instead of its usual 1 hour. **Investigate:** Check row count growth, index bloat, and whether the job's queries still use expected indexes via `EXPLAIN ANALYZE`. **Root Cause:** Table has grown 6x since the job was written, and the query now triggers a sequential scan the planner previously avoided. **Fix:** Add/adjust an index; consider batching the job.

4. **Symptom:** `INSERT` statements are randomly failing with "duplicate key value violates unique constraint" despite application-level uniqueness checks passing. **Investigate:** Look for a race condition between the check and the insert (check-then-act anti-pattern). **Root Cause:** Two concurrent requests both passed the "does it exist" check before either inserted. **Fix:** Use `INSERT ... ON CONFLICT DO NOTHING`/`UPSERT`, or rely on the unique constraint itself with proper error handling instead of a pre-check.

5. **Symptom:** CPU usage is pegged at 100% with no obvious single slow query. **Investigate:** Check `pg_stat_activity` for many moderately-fast queries running concurrently; check for a recent traffic spike or an N+1 query pattern from a new feature. **Root Cause:** A new feature introduced an N+1 query, multiplying total query volume. **Fix:** Batch/eager-load at the application layer.

6. **Symptom:** A read replica shows data that's 20 minutes stale, and this just started today. **Investigate:** Check for a long-running query on the replica blocking WAL replay. **Root Cause:** An analyst ran an ad-hoc long report query directly on the replica. **Fix:** Kill the query; route analytical queries to a dedicated reporting replica going forward.

7. **Symptom:** Application connection attempts fail with "too many connections," but the database's CPU/memory look fine. **Investigate:** Check connection count vs. `max_connections`, and connection states. **Root Cause:** A recently deployed service isn't closing connections properly (leak). **Fix:** Fix the leak; add connection pooling as a structural safeguard.

8. **Symptom:** A migration that tested fine in staging has been running for 2 hours in production and traffic is degrading. **Investigate:** Compare table size in staging vs. production; check current lock status. **Root Cause:** Production table is 100x larger than the staging test dataset, and the migration involves a full table rewrite. **Fix:** Abort if safe; redesign as a batched, non-blocking migration (Module 8).

9. **Symptom:** Users report seeing their own just-placed order as "not found" briefly after checkout. **Investigate:** Check whether the "order confirmation" read is routed to a replica. **Root Cause:** Read-after-write consistency issue — the read hit a replica that hadn't yet received the write. **Fix:** Route immediate post-write reads to the primary, or implement session-consistency read routing.

10. **Symptom:** Disk usage is climbing steadily even though data row counts look stable. **Investigate:** Check for index/table bloat, and check replication slots. **Root Cause:** An unused logical replication slot is retaining WAL indefinitely. **Fix:** Drop the unused slot; add slot-health monitoring going forward.

*(Problems 11-50+ extend this format across every failure category in Module 11, each with intentionally incomplete initial symptoms requiring the reader to specify their own investigation steps before checking a model answer — request "Debugging Set 2" to continue.)*

## Section E — Query Optimization Problems (50+)

*(5 fully-worked problems as a representative sample.)*

1. **Given:** `SELECT * FROM orders WHERE customer_id = 123 AND status = 'shipped' ORDER BY created_at DESC LIMIT 10;` on a 50M-row table with no relevant index. **Task:** Design the optimal index. **Answer:** A composite index `(customer_id, status, created_at DESC)` — supports the equality filters first, then serves the sort order directly from the index, avoiding a separate sort step.

2. **Given:** A query joining a 10-row `countries` table against a 100M-row `users` table on `country_code`. **Task:** Which join algorithm should the optimizer choose, and why? **Answer:** Nested loop join with `countries` as the outer (small) table and an index on `users.country_code` for the inner lookup — far more efficient than a hash join building a hash table from 100M rows.

3. **Given:** `EXPLAIN ANALYZE` shows `Seq Scan` on a table where you expected an `Index Scan` on a properly indexed column. **Task:** List three possible reasons. **Answer:** (1) The query matches a large fraction of rows, making a seq scan genuinely cheaper. (2) Statistics are stale, causing a misestimate. (3) A function/expression is applied to the indexed column in the `WHERE` clause without a matching expression index (e.g., `WHERE LOWER(email) = ...` without an index on `LOWER(email)`).

4. **Given:** A query with `OR` conditions across two different columns performs poorly despite both columns being individually indexed. **Task:** Propose two fixes. **Answer:** (1) Rewrite as a `UNION` of two separately-indexed queries. (2) Use a bitmap index scan (many optimizers do this automatically) combining both indexes — verify via `EXPLAIN` that this is happening.

5. **Given:** A `LIKE '%searchterm%'` query on a large text column is slow. **Task:** Propose an indexing strategy. **Answer:** A standard B+ Tree index cannot help with a leading wildcard. Use a full-text search index (PostgreSQL `GIN` index with `tsvector`, or offload to Elasticsearch/Module 10) instead.

*(Problems 6-50+ extend across join-order optimization, subquery-to-join rewrites, partition pruning, materialized view refresh strategies, and cost-based plan comparison exercises — request "Query Optimization Set 2" for continuation.)*

## Section J — GATE-Style Numerical Problems (20+)

*(5 representative problems in the classic GATE DBMS numerical style.)*

1. A B+ Tree has a fan-out of 100 and currently indexes 10,000,000 records. What is the minimum height of the tree (root counted as level 0)? *(Answer: log₁₀₀(10,000,000) ≈ 3.5 → height 4, since ⌈log₁₀₀(10⁷)⌉ = 4)*

2. A relation R has attributes A, B, C, D with functional dependencies A→B, B→C, C→D. What is the closure of {A}? *(Answer: {A, B, C, D} — since A→B→C→D transitively)*

3. Given a database page size of 8KB and each index entry taking 20 bytes, what is the approximate fan-out of a B+ Tree node (ignoring pointer overhead for simplicity)? *(Answer: 8192 / 20 ≈ 409)*

4. A transaction schedule involves T1 reading X, T2 writing X, T1 writing X, T2 reading X. Is this schedule conflict-serializable?
