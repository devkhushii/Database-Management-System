# The Ultimate DBMS Handbook — Part 13: Research & Advanced Engineering

## Module 1 — History of Database Systems

> **Goal of this module:** Give you the historical and architectural vocabulary that every database research paper assumes you already have. Papers rarely re-explain "why shared-nothing" or "why the relational model won" — they assume it. This module builds that foundation.

---

### 1.1 Why History Matters for a Systems Engineer

Every "new" idea in databases — disaggregated storage, schema-on-read, eventual consistency, vectorized execution — is a *return* to an idea that was tried decades ago under different constraints (RAM price, network speed, disk seek time). Reading papers without this timeline makes you think NoSQL "invented" distribution or that Snowflake "invented" separating compute from storage. Neither is true. Knowing the lineage lets you predict where a new system's tradeoffs will bite.

---

### 1.2 Hierarchical DBMS (1960s)

**Representative system:** IBM IMS (Information Management System), built for the Apollo program's Bill of Materials problem.

**Data model:** Records organized as a tree. Each child record has exactly one parent. Relationships are physical, not logical — a record's location on disk *is* its relationship to its parent.

**Internal working:**
- Data stored as parent-child segments; traversal is via explicit pointers (physical addresses or symbolic keys).
- Access is navigational: the application program must know the path from root to the desired record — "get root, get next child, get next child."
- No query language in the modern sense — access logic is embedded in application code (DL/I calls).

**Strengths:** Extremely fast for one-to-many hierarchies that match the physical layout (e.g., Order → OrderLines). Still used today in production (IMS runs inside many banks and airlines because rewriting it is riskier than keeping it).

**Weaknesses:** Many-to-many relationships require data duplication or awkward workarounds. Schema changes require rewriting navigation code across every application. No data independence — the physical structure *is* the logical structure.

---

### 1.3 Network DBMS (late 1960s–1970s)

**Representative system:** IDS (Integrated Data Store), standardized as **CODASYL DBTG** model.

**Innovation over hierarchical:** A record can have *multiple* parents, forming a graph rather than a strict tree — solving the many-to-many problem.

**Internal working:**
- Relationships modeled as explicit **sets**: an owner record and one or more member records, implemented as linked lists of physical pointers.
- Programs navigate using `FIND`, `GET`, `STORE` verbs against a **currency indicator** (a cursor tracking "current record of each record type/set").

**Why it lost to relational:** Navigational programming meant queries were procedural, not declarative. A schema change (adding a new set) could break unrelated application code. There was no algebra to reason about queries or optimize them automatically.

---

### 1.4 The Relational Revolution (1970–1980s)

**The paper that started it:** Edgar F. Codd, *"A Relational Model of Data for Large Shared Data Banks"* (1970).

**Core innovation:** Separate the *logical* view of data (tables, tuples, relations) from the *physical* storage. Data independence: applications write declarative queries (relational algebra / calculus), and the system decides how to execute them.

**Key ideas introduced:**
- **Relations** (tables) as sets of tuples — no inherent ordering, no navigation pointers.
- **Relational algebra**: select, project, join, union, difference — a small closed set of operators that any query can be expressed in.
- **Normalization** (1NF–5NF, later BCNF) to eliminate redundancy and update anomalies.
- **Declarative querying**: you say *what* you want, the system's optimizer decides *how*.

**System race:**
- **System R** (IBM, 1974–1979) — first to implement SQL (originally SEQUEL), introduced cost-based query optimization (Selinger optimizer, 1979 — still the conceptual basis of most optimizers today), and B-tree indexing for relational access.
- **INGRES** (Berkeley, Michael Stonebraker) — used QUEL instead of SQL, introduced rule-based query rewriting, and its lineage directly produced **Postgres** (1986), which is why PostgreSQL still has an "extensible types/rules" DNA distinct from IBM-lineage databases.

**Why it won:** Query optimization meant physical storage could change (add an index, repartition) without breaking application code — true data independence. SQL became an ANSI/ISO standard in 1986, giving vendors (Oracle, IBM DB2, Sybase, Informix) a common target and portability incentive.

---

### 1.5 Object-Oriented / Object-Relational Databases (1980s–1990s)

**Motivation:** CAD/CAM, CASE tools, and multimedia applications had complex nested objects that were painful to flatten into normalized tables — the so-called **object-relational impedance mismatch**.

**Representative systems:** ObjectStore, Gemstone, Versant (pure OODBMS); Postgres/Illustra (object-*relational*, adding user-defined types, inheritance, and array/nested types on top of the relational core).

**Internal working:** Objects with identity (OID) are stored directly, including pointers/references between objects, avoiding the join-heavy reconstruction relational databases require. Some systems made the database transparently persistent to the programming language (persistence by reachability).

**Why pure OODBMS lost the mainstream:** No standard query language as powerful as SQL, weak tooling/reporting ecosystem, and vendor lock-in to a single language runtime. Their ideas survived by being absorbed into relational systems as **object-relational** features: PostgreSQL's user-defined types and table inheritance, Oracle's `VARRAY`/`OBJECT` types, and JSON/JSONB columns are all direct descendants of this era's ideas, now bolted onto a relational core rather than replacing it.

---

### 1.6 NoSQL (2000s)

**Driving pressure:** Web-scale companies (Google, Amazon, Facebook) hit two walls with relational systems simultaneously: (1) vertical scaling of a single relational node became the bottleneck, and (2) rigid schemas slowed iteration on fast-changing web applications.

**Four broad families, and why each shape exists:**

| Family | Data model | Representative systems | Solves |
|---|---|---|---|
| Key-Value | Opaque value by key | Dynamo, Redis, Riak | Maximum horizontal scalability, simplest possible consistency contract |
| Document | Semi-structured JSON/BSON | MongoDB, CouchDB | Schema flexibility, nested objects without joins |
| Wide-Column | Sparse, versioned column families | Bigtable, Cassandra, HBase | Massive sparse datasets, high write throughput |
| Graph | Nodes + edges | Neo4j | Relationship-heavy traversal queries that are join-explosions in SQL |

**Core theoretical justification:** the **CAP theorem** (Eric Brewer, 2000; formally proven by Gilbert & Lynch, 2002) — a distributed system can only guarantee two of Consistency, Availability, and Partition tolerance at once. Since network partitions are unavoidable at scale, NoSQL systems made an explicit engineering choice to favor **A**vailability over strict **C**onsistency (AP systems like Dynamo/Cassandra), trading it for **eventual consistency**, while others (Bigtable, HBase) chose **C**onsistency over Availability (CP systems).

**What NoSQL sacrificed:** most systems dropped multi-row ACID transactions and joins, pushing that logic into application code — a tradeoff many teams later regretted, which is precisely what motivated NewSQL.

---

### 1.7 NewSQL (2010s)

**Motivation:** Give back ACID transactions and SQL, *without* giving up the horizontal scalability NoSQL proved was possible.

**Representative systems and their core trick:**
- **Google Spanner** (2012) — globally consistent distributed transactions using **TrueTime**, a hardware-assisted clock API with bounded uncertainty (GPS + atomic clocks), enabling externally consistent (linearizable) transactions across data centers.
- **CockroachDB** — an open-source Spanner-inspired design, using hybrid logical clocks instead of atomic clock hardware.
- **VoltDB** (descended from H-Store, Stonebraker et al.) — single-threaded, in-memory, partitioned execution that eliminates locking overhead entirely for partition-local transactions.
- **TiDB** — MySQL-compatible, built on the Raft-replicated **TiKV** key-value store, decoupling the SQL layer from the distributed storage layer.

**Internal working (general NewSQL recipe):**
1. Shard data across nodes (like NoSQL).
2. Replicate each shard via a consensus protocol (Paxos/Raft) for durability and failover.
3. Use a distributed transaction protocol (typically **two-phase commit** layered on top of per-shard consensus, e.g., Spanner and CockroachDB) to give cross-shard ACID guarantees.
4. Re-expose all of this behind standard SQL.

### 1.8 HTAP — Hybrid Transactional/Analytical Processing (2010s)

**Motivation:** Traditionally, OLTP (many small transactional writes) and OLAP (large analytical scans) require opposite physical layouts — row-store for OLTP, column-store for OLAP — so businesses ran two systems connected by ETL, incurring hours of staleness.

**Internal working approaches:**
- **Dual storage format, single system**: maintain a row-store for fresh OLTP data and asynchronously convert it to a column-store replica for analytics (TiDB's TiFlash, SAP HANA delta-store-to-main-store merges).
- **In-memory columnar with delta stores**: Hekaton (SQL Server's in-memory OLTP engine) and HANA keep recent writes in a row-oriented delta buffer merged periodically into the immutable columnar main store.

**Tradeoff:** HTAP systems accept some analytical staleness or write-path overhead in exchange for eliminating the ETL pipeline entirely. (Full paper coverage in Module 3 and Module 6.)

---

### 1.9 Serverless Databases (late 2010s–2020s)

**Motivation:** Eliminate capacity planning — pay per query/request, scale to zero, scale up instantly under load.

**Internal working:** Requires **disaggregation of compute and storage** (see Module 2) so that stateless compute nodes can be spun up/down independently of the durable storage layer. Examples: Amazon **Aurora Serverless**, **Neon** (Postgres with storage separated into a multi-tenant network-attached log service), **PlanetScale** (Vitess-based MySQL), **CockroachDB Serverless**.

**Key engineering challenge:** cold-start latency — bringing a compute node online and warming its buffer pool/cache fast enough to feel "always on."

---

### 1.10 Lakehouse Architecture (2020s)

**Motivation:** Data lakes (raw files in object storage — S3, ADLS) were cheap and scalable but lacked transactions, schema enforcement, and fast point queries. Data warehouses had those guarantees but were expensive and closed-format. The lakehouse merges both.

**Internal working:**
- Raw data stored as columnar files (typically **Parquet**) in object storage.
- A **transactional metadata layer** on top adds ACID guarantees, schema evolution, and time travel: **Delta Lake**, **Apache Iceberg**, **Apache Hudi**. These formats keep a log of file-level commits (add/remove file entries) so readers get a consistent snapshot without locking the underlying files.
- Any compute engine (Spark, Trino, Snowflake, DuckDB) can read the same open-format files — decoupling storage format from the query engine, unlike a proprietary warehouse.

---

### 1.11 Data Mesh (2019, Zhamak Dehghani)

**Not a technology — an organizational/architectural paradigm.** Instead of one centralized data team owning a monolithic warehouse/lake, each **domain team** owns and serves its own data as a **product**, with:
1. Domain-oriented decentralized data ownership.
2. Data as a product (documented, discoverable, with SLAs).
3. Self-serve data infrastructure as a platform.
4. Federated computational governance (global standards, locally enforced).

**Why it matters to engineers:** it changes how storage systems are consumed — you'll increasingly see per-domain lakehouses joined via federated query engines rather than one central warehouse.

---

### 1.12 Data Fabric

**Distinct from Data Mesh:** Data Fabric is a *technology/architecture* pattern (often AI/metadata-driven), not an organizational one. It uses active metadata, knowledge graphs, and automation to weave together data across heterogeneous, distributed sources into one integrated access layer — often the technology substrate that a Data Mesh's federated governance runs on top of.

### 1.13 Timeline Summary

```
1960s   Hierarchical  (IMS)              — tree-shaped, navigational
1970s   Network       (CODASYL/IDS)      — graph-shaped, navigational
1970-80 Relational    (System R, INGRES) — declarative, data independence
1980-90 Object(-Rel)  (ObjectStore, Illustra) — impedance mismatch fix
2000s   NoSQL         (Dynamo, Bigtable) — horizontal scale, CAP tradeoffs
2010s   NewSQL        (Spanner, CockroachDB) — scale + ACID + SQL
2010s   HTAP          (HANA, TiDB)       — OLTP + OLAP, one system
2018+   Serverless    (Aurora Serverless, Neon) — compute/storage disaggregation
2020+   Lakehouse     (Iceberg, Delta Lake) — open format + ACID on object storage
2019+   Data Mesh     (organizational)   — decentralized data ownership
2020+   Data Fabric   (metadata-driven)  — unified access across sources
```

### 1.14 Production Examples & Industry Usage

| Era | Still in production today because... |
|---|---|
| Hierarchical (IMS) | Mainframe banking/airline core systems — too risky/costly to migrate |
| Relational | PostgreSQL, MySQL, Oracle, SQL Server — the default for OLTP everywhere |
| NoSQL | DynamoDB (Amazon retail/AWS backbone), Cassandra (Netflix), MongoDB (general web apps) |

### 1.16 MCQs

**Q1.** The primary reason the relational model displaced the network (CODASYL) model was:
A) Relational databases were faster
B) Relational databases offered data independence via declarative querying
C) Relational databases used less disk
D) CODASYL had no standard

*Answer: B*

**Q2.** In the CAP theorem, Amazon Dynamo made which explicit tradeoff?
A) Consistency over Availability
B) Availability over Consistency (under partition)
C) Partition tolerance over both C and A
D) None — Dynamo guarantees all three

*Answer: B*

**Q3.** Google Spanner's TrueTime API primarily enables:
A) Faster disk I/O
B) Bounded-uncertainty global clocks for externally consistent distributed transactions
C) Automatic schema migration
D) Columnar compression

*Answer: B*

**Q4.** What distinguishes a Lakehouse from a traditional Data Lake?
A) It uses cheaper storage
B) It adds a transactional metadata layer (ACID, schema evolution) on top of open file formats
C) It removes the need for object storage
D) It only supports row-oriented storage

*Answer: B*

**Q5.** Data Mesh is best described as:
A) A distributed SQL engine
B) An organizational paradigm for decentralized, domain-oriented data ownership
C) A columnar file format
D) A consensus protocol

*Answer: B*
