## 1.0 Why This Module Exists

Every SQL query you have written since Part 1 eventually turns into a request: *"go get these bytes from somewhere and bring them to the CPU."* Until now we never asked **where** those bytes live or **how far away** they are. This module answers that.

The core tension that the rest of Part 7 exists to solve:

> **CPUs are fast. Disks are slow. Memory is expensive. Data must be durable.**

Every storage decision in a database — pages, buffers, indexes, file organization — is an engineering compromise between these four facts. Keep this sentence in your head; it explains almost every design choice you'll see from here to Module 15.

## 1.1 Why Databases Need Storage Engines

### What is it?

A **storage engine** (also called a **storage manager**) is the layer of the DBMS responsible for how data is physically written to, read from, and organized on non-volatile storage (disk/SSD), independent of the SQL layer sitting above it.

### Why does it exist?

SQL is a *declarative* language — you say **what** you want ("give me all orders from Bangalore"), not **how** to get it. Something underneath SQL has to:

1. Decide the physical layout of every row on disk.
2. Decide how to fetch the minimum number of bytes needed to answer a query.
3. Guarantee that once you say `COMMIT`, the data survives a power cut.
4. Let thousands of concurrent transactions read/write without corrupting each other.

Without a storage engine, every application would have to reinvent file formats, indexing, and crash recovery from scratch — which is exactly what people did before relational databases existed (see Module 3, "why heap files replaced raw flat files").

### What problem does it solve?

It solves the **impedance mismatch** between:
- The **logical model** (tables, rows, columns — what Parts 1–6 taught you)
- The **physical model** (bytes, blocks, pointers — what Part 7 teaches you)

### How does it work? (high-level)

```
┌─────────────────────────────────────────────┐
│              SQL / Query Layer               │  <- Parts 1-6, Part 8
│   Parser → Planner → Optimizer → Executor    │
├─────────────────────────────────────────────┤
│              Storage Engine                  │  <- Part 7 (this Part)
│  Buffer Manager | File Manager | Index Mgr   │
├─────────────────────────────────────────────┤
│         Operating System (File System)       │
├─────────────────────────────────────────────┤
│           Physical Storage (Disk/SSD)        │
└─────────────────────────────────────────────┘
```

### Industry Usage

- PostgreSQL: single, tightly integrated storage engine (heap + WAL).
- MySQL: **pluggable** storage engines — InnoDB (default, transactional) and MyISAM (legacy, non-transactional) both sit under the same SQL layer.
- Oracle, SQL Server: proprietary storage engines with similar layered architecture.

### Interview Importance

⭐⭐⭐⭐⭐ — "Why does MySQL let you choose a storage engine per table but PostgreSQL doesn't?" is a classic Staff/Senior-level systems question. Answer: MySQL's SQL layer and storage layer are decoupled by a formal storage engine API; PostgreSQL's heap access method is baked into the core, though PostgreSQL *does* support pluggable table access methods since v12 (e.g., `zheap`, columnar extensions).

## 1.2 Logical Storage vs Physical Storage

| Aspect | Logical Storage | Physical Storage |
|---|---|---|
| What you see | Tables, rows, columns, relationships | Blocks, pages, byte offsets, pointers |
| Who defines it | Database schema designer (Parts 1–6) | Storage engine + OS + hardware |
| Example unit | A "row" in `orders` table | A tuple stored at byte offset 240 in page 17 |
| Changes when | You run `ALTER TABLE`, normalize schema | You rebuild an index, change fill factor, defragment |
| Query relevance | `SELECT * FROM orders WHERE ...` | Optimizer decides: sequential scan or index scan? |

**Analogy:** Logical storage is the *address written on a letter* ("123 MG Road, Flat 4B"). Physical storage is the *actual GPS coordinates and the postman's walking route* to get there. The sender only needs the address (logical); the postal system needs the route (physical).

### Why the separation matters (Data Independence)

This is **physical data independence**, a concept first introduced in Part 1: applications and SQL queries should not break when the DBMS changes how data is stored on disk (e.g., adding an index, changing page size, switching storage engine). The storage engine's entire job is to preserve this illusion.

## 1.3 Primary Storage vs Secondary Storage

### Definitions

- **Primary storage**: Directly addressable by the CPU — registers, cache (L1/L2/L3), and RAM. Volatile (usually), extremely fast, expensive per GB.
- **Secondary storage**: Not directly addressable by CPU; accessed via I/O operations — HDD, SSD, tape. Non-volatile, slower, cheap per GB.

### The Memory Hierarchy (with real latency numbers)

```
                     Approx. Latency        Approx. Cost/GB      Size
CPU Register          ~0.3 ns                 —                bytes
L1 Cache              ~1 ns                   —                KBs
L2 Cache              ~4 ns                   —                100s of KB
L3 Cache              ~15 ns                  —                MBs
RAM                   ~100 ns                 ~$3               GBs
SSD (NVMe)            ~20,000-100,000 ns      ~$0.08            100s of GB - TBs
HDD                   ~2,000,000-10,000,000ns ~$0.02            TBs
Network (same DC)     ~500,000 ns             —                 —
```

**Why this table matters more than anything else in the module:** RAM is roughly **100,000× faster** than an HDD seek and roughly **1,000× faster** than an SSD. Every algorithm in Modules 4–7 (buffer pools, B+ Trees with high fan-out, hash indexes) exists purely to **minimize the number of trips to secondary storage**, because that's where nearly all the time goes.

### Disk-level behavior

- HDDs: mechanical arm + spinning platter. Sequential reads are fast; random reads are slow (arm has to physically move — "seek time").
- SSDs: no moving parts, uses flash memory cells (NAND). Random reads are much faster than HDD, but writes are more complex (see "write amplification" in Module 12) because flash must be erased in blocks before rewriting.

### Database Engine Behavior

Because secondary storage I/O dominates cost, **every serious DBMS is designed around minimizing disk I/O, not CPU cycles.** This is why:
- The optimizer's cost model (Part 8) is mostly counting **page reads**, not instructions.
- Indexes exist to avoid reading pages you don't need (Module 5 onward).
- The buffer pool exists to avoid re-reading the same page twice (Module 4).

### PostgreSQL vs MySQL (InnoDB)

| Aspect | PostgreSQL | MySQL (InnoDB) |
|---|---|---|
| Default page/block size | 8 KB | 16 KB |
| Configurable at | Compile time only | Instance init time (`innodb_page_size`) |
| Reasoning | Matches common OS/filesystem block sizes | Larger page = fewer page splits for sequential-ish workloads |

### Common Mistakes
- Assuming "more RAM always fixes slow queries" — if the working set doesn't fit in the buffer pool, you're still paying disk cost (Module 4).
- Ignoring random vs sequential I/O difference when designing storage on HDD-backed systems (still relevant for cold storage tiers, backups, tape archives).

### Interview Importance
⭐⭐⭐⭐⭐ — Nearly every DB systems interview will ask you to explain **why disk I/O dominates query cost**, and expects you to connect it forward to indexing and buffer management.

## 1.4 RAM vs SSD vs HDD — Deep Comparison

| Feature | RAM | SSD | HDD |
|---|---|---|---|
| Volatility | Volatile | Non-volatile | Non-volatile |
| Access pattern sensitivity | None (uniform) | Low | High (sequential >> random) |
| Mechanical parts | No | No | Yes (platter, arm) |
| Typical DB usage | Buffer pool, cache, sort/hash work areas | Primary data files (modern default) | Cold storage, backups, archival tiers |
| Failure mode | Data lost on power-off | Wear-out after many writes | Mechanical failure |
| Random read cost | ~Same as sequential | Slightly higher than sequential | Much higher than sequential |

**Real-life analogy:** RAM is your **desk** (everything on it is instantly reachable, but the desk is small and gets wiped clean when you leave the office). SSD is a **filing cabinet in the same room** (a bit of a walk, but organized access is still quick). HDD is a **warehouse across town** (worth it only if you're grabbing many files in one trip — i.e., sequential access).

## 1.5 Volatile vs Non-Volatile Memory

- **Volatile memory**: Loses contents when power is removed (RAM, CPU cache).
- **Non-volatile memory**: Retains contents without power (SSD, HDD, NVRAM, battery-backed cache).

### Why databases care deeply about this distinction

**Durability**, the "D" in ACID (fully explored in Part 9 — Transactions & ACID), requires that once a transaction commits, its effects survive a crash. Since RAM is volatile, the DBMS **must** ensure committed data (or at minimum, a log of it) has reached non-volatile storage before acknowledging the commit to the client.

This is precisely why the **Write-Ahead Log (WAL)** exists — a concept you will use heavily in Part 9, but it originates from this storage-level fact: *"volatile memory cannot be trusted to survive a crash."*

> **Cross-reference forward:** In Part 9 you'll learn WAL guarantees durability by writing log records to non-volatile storage *before* the corresponding data page is written back — this is the "Write-Ahead" rule, and it only makes sense once you understand that data pages usually sit dirty in volatile RAM (the buffer pool, Module 4) for a while before being flushed.

## 1.6 Persistent Storage

**Persistent storage** = storage that outlives the process/application that created the data — i.e., non-volatile storage used specifically to durably hold your database's files (heap files, index files, WAL files, control files).

### Disk-level behavior

A database's persistent storage is not one giant blob — it is broken into a hierarchy:

```
Database Cluster / Instance
 └── Database
      └── Tablespace (logical grouping, maps to physical location)
           └── Data File(s)
                └── Pages / Blocks   <- fixed-size units (Module 2)
                     └── Rows / Tuples  <- your actual data
```

### PostgreSQL vs MySQL

| Concept | PostgreSQL | MySQL (InnoDB) |
|---|---|---|
| Grouping unit | Tablespace | Tablespace (`ibdata1` or file-per-table `.ibd`) |
| Default location | `PGDATA/base/<db_oid>/<relfilenode>` | `datadir` or per-table `.ibd` files |
| One file per table? | Files can split at 1GB segments per relation | Configurable via `innodb_file_per_table` (default ON since 5.6) |

## 1.7 Disk Blocks, Pages, Records, Slots — The Core Vocabulary

This is the single most important vocabulary list in Part 7. Get these exact.

| Term | Definition |
|---|---|
| **Disk Block** | The smallest unit the *operating system/hardware* reads or writes in one I/O operation (commonly 4 KB). |
| **Page** | The smallest unit the *database engine* reads or writes (commonly 8 KB in PostgreSQL, 16 KB in InnoDB). A page is usually a multiple of the OS disk block. |
| **Record / Tuple** | A single row's data, physically encoded as bytes, stored inside a page. |
| **Slot** | A fixed "slot" inside a page's slot array that holds a pointer (offset + length) to where a specific record's bytes actually live inside that page. Slots enable indirection (Module 2 explains why this matters for variable-length records). |
| **Database File** | An OS-level file (or set of files) that stores a sequence of pages belonging to a table, index, or other database object. |

### Why the Page ≠ Disk Block distinction matters

If the database only worked in OS block-sized units (e.g., 4 KB), it would need far more page headers, more index entries, and more I/O calls for the same amount of data. By using a **larger logical page** (8 KB / 16 KB) built from multiple OS blocks, the engine amortizes overhead: fewer page headers, better sequential read throughput, and simpler free-space bookkeeping.

### Diagram: From Row to Disk

```
[SQL Row]                              logical: (id=101, name='Khushi', city='Jamshedpur')
     |
     v
[Tuple/Record bytes]                   physical byte encoding, e.g.:
                                        01100101 | 00000006 'Khushi' | 00000010 'Jamshedpur'
     |
     v
[Slot Array Entry in Page]             Slot 3 -> offset=512, length=42
     |
     v
[Page  (8 KB / 16 KB)]                 Header | Slot Array | Free Space | Tuple Data (grows toward middle)
     |
     v
[Disk Block(s), 4 KB each]             Page = 2 or 4 contiguous OS blocks
     |
     v
[Physical Disk / SSD sectors]          Lowest level, managed by firmware/OS
```

> **Detailed page-internal layout (slotted pages, free space map, fill factor, fragmentation) is covered in full in Module 2 — this module only introduces the vocabulary.**

### Common Mistakes
- Using "block" and "page" interchangeably in an interview — a good interviewer will immediately ask you to clarify which layer (OS vs DB engine) you mean.
- Assuming a "record" and a "row" are always byte-identical — TOAST'd/overflow columns in PostgreSQL (Module 9) and off-page BLOBs in InnoDB break this assumption.

### Interview Importance
⭐⭐⭐⭐⭐ — "What is the difference between a block and a page?" is asked very frequently at Database Engineer interviews (Uber, Oracle, Amazon RDS/Aurora teams).

## 1.8 Real-World Analogy Recap (all of Module 1 in one story)

Imagine a **library** (the database):

- The **city** the library is in = **Physical Storage** (disk/SSD, the actual hardware).
- The **library building's floor plan** = **Logical Storage** (how you, the reader, think about "fiction section," "row 4," independent of which shelf physically holds it).
- Each **shelf** = a **Page** — a fixed physical unit librarians fill and manage.
- Each **book** = a **Record/Tuple**.
- The **card catalog entry** pointing to "Shelf 12, 3rd from left" = a **Slot** (indirection, not the book itself).
- The librarian's **front desk memory of which books were recently requested** = **RAM / Buffer Pool** (Module 4) — fast, but forgotten if the library closes for the night (volatile) unless written into the permanent ledger (non-volatile / durable log).
- The **city's postal/road network** used to bring new book shipments = **Secondary Storage I/O**, where random trips across town (random I/O) cost much more time than one big truck delivering many books in one sequential trip (sequential I/O).

| SSD vs HDD backing | Random read/write cost, viability of index-heavy workloads |
| RAM sizing (buffer pool) | How much of the "working set" avoids disk entirely (Module 4) |
| Sequential vs random access pattern | Whether heap scans or index seeks are cheaper (Module 10) |

## 1.10 Chapter Summary

- A **storage engine** bridges the logical (SQL/table) world and the physical (byte/disk) world, and exists to manage performance, durability, and concurrency.
- **Logical storage** (schema-level, from Parts 1–6) is independent of **physical storage** (bytes on disk) — this separation is called physical data independence.
- The **memory hierarchy** (registers → cache → RAM → SSD → HDD) has latency differences of several orders of magnitude; this single fact drives nearly every design decision in the rest of Part 7.
- **Volatile** memory (RAM) is fast but disappears on crash; **non-volatile** memory (disk/SSD) is slower but durable — this is *why* Write-Ahead Logging exists (previewed here, detailed in Part 9).
- Core vocabulary: **Disk Block** (OS-level unit) vs **Page** (DB-engine-level unit, built from blocks) vs **Record/Tuple** (a row's bytes) vs **Slot** (an indirection pointer to a record inside a page).
- PostgreSQL defaults to 8 KB pages; MySQL/InnoDB defaults to 16 KB pages.

## 1.11 Cheat Sheet

```
Storage Engine        = physical read/write/organize layer under SQL
Logical Storage        = tables/rows/columns (schema view)
Physical Storage        = blocks/pages/bytes (disk view)
Primary Storage         = CPU-addressable (registers, cache, RAM)
Secondary Storage       = disk/SSD, accessed via I/O
Volatile               = lost on power-off (RAM)
Non-Volatile           = survives power-off (disk/SSD)
Disk Block             = smallest OS I/O unit (~4 KB)
Page                   = smallest DB engine I/O unit (PG: 8 KB, InnoDB: 16 KB)
Record/Tuple           = one row's physical bytes
Slot                   = pointer (offset+length) to a record inside a page
Persistent Storage      = non-volatile storage holding DB files durably
```

A) 4 KB  B) 8 KB  C) 16 KB  D) 64 KB

**Q4.** A "slot" in a database page primarily provides:
