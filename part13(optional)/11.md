# The Ultimate DBMS Handbook — Part 13: Research & Advanced Engineering

## Module 11 — AI + Databases

> **Goal of this module:** Understand the two genuinely distinct directions this intersection runs — **databases *for* AI** (retrieval infrastructure like RAG) and **AI *inside* databases** (learned components replacing hand-tuned engineering) — and evaluate the latter's real, current maturity level rather than its marketing narrative.

---

### 11.1 Two Directions, Not One Field

It's easy to blur "AI and databases" into one vague topic. It splits cleanly into two directions with almost nothing in common mechanically:

**Direction A — Databases as infrastructure *for* AI systems.** LLMs have no persistent memory beyond their context window and no access to private/current data by default; databases (especially vector databases, Module 10) are the retrieval layer that gives AI systems access to specific, current, private knowledge. This is **RAG** (11.2).

**Direction B — AI techniques used *inside* database internals** to replace traditionally hand-engineered components — index structures (11.3, Learned Indexes), query optimizers (11.4), and query planning assistance (11.5). This direction is much earlier-stage, more research-heavy, and has seen far less production adoption than Direction A.

Keeping these separate matters because their maturity levels are wildly different: Direction A is mainstream production engineering today; Direction B is still mostly confined to research papers and experimental features, with important, unresolved caveats about robustness.

### 11.2 Retrieval-Augmented Generation (RAG)

**Citation:** Lewis et al., *"Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks,"* NeurIPS 2020 — the paper that named and formalized the pattern, though the core idea (retrieve relevant context, then generate conditioned on it) has older roots in open-domain question answering research.

**The problem RAG solves:** an LLM's knowledge is frozen at training time and has no access to private, proprietary, or newly-created data (e.g., your company's internal documents, or news from after the model's training cutoff) — and simply "telling it everything" isn't feasible because context windows, even large ones, cannot hold an entire knowledge base, and stuffing irrelevant information into context degrades output quality and wastes cost/latency.

**The core architecture:**
1. **Ingestion/indexing (offline)**: source documents are split into **chunks** (a genuinely important, non-trivial design decision — chunk size and boundary choice significantly affects retrieval quality; too large and irrelevant content dilutes the chunk's embedding, too small and necessary context gets split across chunks), each chunk is passed through an embedding model (Module 10.1) to produce a vector, and the vector plus original text is stored in a vector database.
2. **Retrieval (online, per query)**: the user's query is embedded using the same embedding model, and a nearest-neighbor search (Module 10.2's ANN algorithms) retrieves the top-`k` most semantically relevant chunks.
3. **Generation (online)**: the retrieved chunks are inserted into the LLM's prompt as context, alongside the original query, and the LLM generates a response **grounded in** the retrieved content rather than purely from its parametric (trained-in) knowledge.

**Why this is fundamentally a database systems problem, not just a machine-learning problem:** every step above is a database engineering decision — chunking strategy is a data-modeling decision (analogous to schema design), retrieval quality depends directly on the ANN algorithm and index tuning choices from Module 10, and production RAG systems face all the same durability/update/consistency questions as any database (what happens when a source document is updated — do you need to re-embed and re-index the changed chunks? How do you handle deletes? This is directly the CRUD-on-ANN-indexes problem from Module 10.7).

**Advanced RAG patterns worth knowing:**
- **Hybrid search** (directly reusing Module 10.7's concept): combining dense vector retrieval with sparse keyword search (BM25) and fusing rankings, because pure semantic search sometimes misses queries needing exact term matching.
- **Re-ranking**: retrieve a larger initial candidate set via fast ANN search, then apply a more expensive, more accurate re-ranking model (often a cross-encoder that jointly processes the query and each candidate, rather than comparing independently-computed embeddings) to reorder the top candidates before final selection — trading extra compute for improved precision on the final result set, directly analogous to Module 10.5's PQ-then-rerank pattern.
- **Query rewriting/expansion**: using an LLM to reformulate the user's original query into one or more better-suited retrieval queries before running the actual vector search — addressing the common failure mode where a user's literal question phrasing doesn't closely match the phrasing of the relevant source content.
- **GraphRAG**: combining RAG's retrieval pattern with graph-structured knowledge (Module 8) — building a knowledge graph over entities and relationships extracted from source documents, and using graph traversal (potentially combined with vector similarity for entity resolution) to retrieve not just semantically similar text chunks but structurally/relationally connected information — useful for queries requiring multi-hop reasoning across documents that pure chunk-similarity retrieval handles poorly.

### 11.3 Learned Indexes

**Citation:** Kraska, Beutel, Chi, Dean, Polyzotis, *"The Case for Learned Index Structures,"* SIGMOD 2018 — the paper that started this specific research direction.

**The core insight:** a traditional index (B-tree, hash table) is, functionally, a model that maps a key to a position (or approximate position) in sorted/stored data. A B-tree does this via a fixed, hand-designed structure (branching comparisons down a tree); the paper's provocative reframing asks: **what if you replaced that fixed structure with a machine-learned model trained on the actual data's distribution**, predicting a key's position directly?

**How it works for the simplest case (a sorted array, "learned B-tree replacement"):** train a model (the paper's original proposal used a small neural network, though simpler models like linear regression or piecewise-linear approximations are also used in follow-up work) to predict, given a key, its approximate position (or **CDF value** — cumulative distribution function position) within a sorted array. Because the prediction is *approximate*, the model's output is used as a starting point for a small local search (e.g., a bounded binary search within a small error-bounded window around the predicted position) rather than being trusted as the exact final answer — this hybrid "model gets you close, exact search finishes the job" design is what makes learned indexes correct despite using an inherently approximate predictive model.

**Why this can outperform a B-tree for the right data:** if the data's key distribution follows a learnable, reasonably smooth pattern (e.g., many real-world datasets have keys that are roughly linear or piecewise-linear in their distribution, like auto-incrementing IDs or timestamps), a small learned model can predict a key's position far more precisely — and using far less memory — than a B-tree's multi-level branching structure needs to achieve equivalent lookup speed, because the B-tree's structure doesn't exploit any regularity in the actual data distribution at all; it's a general-purpose structure that works the same way regardless of whether the data has learnable patterns.

**Real limitations, stated plainly (this is where hype outpaces production reality most):**
- Learned indexes are **read-optimized and struggle with inserts/updates** — a new insertion can shift the true CDF in ways the trained model no longer predicts accurately, requiring either periodic retraining (expensive, and creates a window of degraded accuracy between retrains) or auxiliary structures (a small buffer of "recent, not-yet-learned" inserts merged in periodically, conceptually similar to an LSM-tree's memtable, Module 4.2) to handle writes without constant retraining.
- Performance is **highly data-distribution-dependent** — a learned index trained on one distribution can perform poorly (worse than a B-tree) if the actual data distribution shifts or was never as learnable/smooth as assumed; this makes learned indexes a much riskier default choice than a B-tree, which has predictable worst-case behavior regardless of data distribution.
- **Production adoption remains limited** relative to the research attention the idea has received — as of this writing, no mainstream production relational database has replaced its default B-tree/LSM engine with a learned index as the primary access method; the idea's biggest real influence has been on specific, narrower applications (e.g., some learned "sorted array index" replacements in read-heavy, append-mostly analytical systems, and academic follow-up systems) rather than becoming the new industry-standard general-purpose index.

**Follow-up work worth knowing:** the **ALEX** index (Ding et al., SIGMOD 2020) directly addressed the original paper's update-handling weakness, designing a learned index structure with efficient in-place updates and inserts via a more sophisticated internal structure (gapped arrays allowing local insertion without full retraining) — a good example of the field maturing from "here's a compelling idea with real limitations" toward "here's an engineered structure addressing those limitations directly," though even ALEX has not displaced B-trees as a default choice in mainstream production databases.

### 11.4 AI Query Optimizers

**The traditional approach (established since System R, Module 1.4):** a cost-based optimizer uses hand-built cost formulas (estimating I/O, CPU cost per operator based on statistics like table cardinality, column value distributions/histograms) to choose among many possible execution plans for a query, searching the plan space via dynamic programming or heuristic search.

**Where hand-built cost models break down:** cost estimates rely on **cardinality estimation** — predicting how many rows will result from each operator, especially joins — and this estimation is notoriously unreliable in practice, particularly for correlated columns (where two columns aren't independent, but the optimizer's statistics typically assume independence for tractability) and complex predicates; a plan chosen based on a wildly wrong cardinality estimate can be dramatically worse than an alternative plan the optimizer rejected.

**The AI-assisted approach — learning cardinality estimation and/or cost models directly from data and query workload history, rather than relying purely on hand-built statistical formulas and independence assumptions.** Representative research directions:
- **Learned cardinality estimators**: train a model (various approaches have used, e.g., deep sets, graph neural networks over query structure, or simpler regression models) on historical query execution data (actual observed cardinalities for past query patterns) to predict cardinalities for new queries more accurately than histogram-based independence-assuming estimates, especially for correlated predicates the traditional approach handles poorly.
- **Learned cost models**: rather than hand-tuning cost formula coefficients (e.g., "how many CPU cycles does a hash join cost per row on this specific hardware"), learn the cost model directly from observed execution telemetry on the actual production hardware/workload — potentially capturing hardware-specific and workload-specific effects a generic formula misses.
- **Reinforcement-learning-based plan search**: rather than the traditional dynamic-programming plan enumeration, treat plan selection as a sequential decision process and train a reinforcement learning agent to choose join orders/access methods, using actual query execution feedback (latency) as the reward signal — Google's internal work and academic systems (e.g., **Neo**, from MIT, and **Bao**, a related bandit-based system for choosing among a small set of query-plan "hints" rather than the full plan space) are representative research directions here.

**Honest state of production adoption:** most production databases still use fundamentally hand-built, histogram/statistics-based cost models as their default — AI-assisted components have seen the most real production traction in narrower, lower-risk roles: **auto-tuning advisors** (recommending indexes, suggesting configuration changes) rather than replacing the core query planner's decision-making at runtime, because a learned cost/cardinality model that's wrong in an unusual, hard-to-debug way is a much scarier production failure mode than a traditional cost model being suboptimal in a well-understood, well-documented way. This is an active, fast-moving research area, but the "AI query optimizer" as a full production replacement for cost-based optimization remains more research trajectory than deployed default.

### 11.5 AI-Assisted Query Planning in Practice Today

Where AI assistance for querying has seen the most *actual* production traction, distinct from the more research-stage "AI query optimizer" (11.4):

- **Natural-language-to-SQL (NL2SQL)**: using an LLM to translate a natural-language question into SQL, given the target database's schema — this doesn't change the query optimizer at all; it operates entirely *upstream* of the traditional optimizer, generating SQL that then goes through the normal cost-based planning process unchanged. This is the most mature, most widely deployed form of "AI + databases" for querying today, precisely because it doesn't touch the database engine's internals at all, limiting the blast radius of the AI component's mistakes to "generates a wrong or inefficient — but still normally-planned and normally-executed — query," which is a much more contained and debuggable failure mode than a learned component silently mis-costing plans inside the optimizer itself.
- **Automated index/schema advisors**: tools that analyze query workload history and recommend indexes, partitioning strategies, or schema changes — increasingly incorporating ML-based workload analysis, but again operating as an advisory layer outside the query execution path itself, not as a runtime replacement for the optimizer.
- **Anomaly detection on query performance**: using ML models to detect when a query's performance has regressed (e.g., due to a plan change, a statistics staleness issue, or a data distribution shift) — an operational/observability use case, not a query-planning-time technique.

### 11.6 Why Direction A (RAG) Matured Faster Than Direction B (AI Inside the Optimizer)

This is worth stating explicitly as the module's central practical takeaway: **RAG succeeded quickly in production because it composes existing, well-understood database components (vector search, chunking, retrieval) around an LLM without requiring the LLM (or any learned model) to be trusted for a correctness-critical internal decision** — if retrieval returns a slightly suboptimal set of chunks, the failure mode is a slightly worse-grounded LLM answer, which is recoverable and debuggable. **Learned indexes and AI query optimizers, by contrast, require trusting a learned model for a decision where being wrong can mean genuinely incorrect results (a learned index failing to find a key it should have found) or catastrophic performance regressions (a badly-chosen query plan)** — a much higher bar for production trust, which is precisely why that direction remains earlier-stage despite years of active research attention.

### 11.7 Production Examples & Industry Usage

| Pattern | Maturity | Notable production usage |
|---|---|---|
| RAG (with vector databases) | Mainstream production | Enterprise knowledge-base assistants, customer support bots, coding assistants with codebase context |
| GraphRAG | Emerging production adoption | Multi-hop document QA, complex knowledge-base reasoning over structured entity relationships |
| NL2SQL | Growing production adoption | BI tools offering natural-language query interfaces over existing warehouses |
| Learned Indexes | Primarily research / narrow niche production | Some specialized read-heavy analytical systems; academic follow-up systems (ALEX and successors) |
| Learned cardinality/cost models | Research-stage, limited production | Auto-tuning advisors in some cloud database offerings; not yet a default optimizer replacement |
| RL-based plan search (Neo, Bao) | Academic research systems | Not widely deployed as production defaults as of this writing |

### 11.9 MCQs

**Q1.** RAG solves the problem that:
A) LLMs cannot generate text
B) LLMs have frozen, non-current knowledge and no access to private data, requiring external retrieval for grounding
C) Databases cannot store text
D) Vector databases are too slow

*Answer: B*

**Q2.** A learned index's local-search correction step exists because:
A) The learned model's predictions are always exact
B) The learned model's predicted position is approximate, requiring a bounded local search to find the exact answer
C) It replaces the need for training data
D) It compresses the index

*Answer: B*

**Q3.** The main real-world limitation of learned indexes compared to B-trees is:
A) They cannot perform reads at all
B) They struggle with inserts/updates and are highly data-distribution-dependent, unlike B-trees' predictable worst-case behavior
C) They require more disk space always
D) They cannot be implemented in any programming language

*Answer: B*

**Q4.** NL2SQL is considered lower-risk than AI-based query optimizer replacement because:
A) NL2SQL doesn't use machine learning
B) NL2SQL operates upstream of the traditional optimizer, so its mistakes produce a normally-planned (if suboptimal) query rather than a mis-costed internal planning decision
C) NL2SQL is always 100% accurate
D) Query optimizers don't affect performance

*Answer: B*

**Q5.** GraphRAG extends standard RAG by:
A) Removing the need for embeddings entirely
B) Combining vector-based chunk retrieval with graph-structured entity/relationship traversal for multi-hop reasoning
C) Only working with numerical data
D) Eliminating the LLM generation step

*Answer: B*

### 11.11 Research Questions

1. Can learned indexes be made robust enough to insert/update-heavy, unpredictable-distribution production OLTP workloads specifically (rather than the read-heavy, stable-distribution analytical niches where they've seen the most success), and what would the failure/fallback mechanism need to look like for production teams to trust them as a default?
2. Is there a hybrid approach where a traditional cost-based optimizer's cardinality estimates are corrected by a learned model only when the model's own confidence is high (a "learned model as a fallback-safe adjustment" rather than a full replacement), and how would optimizer-level uncertainty be measured reliably enough to gate this safely?
3. As GraphRAG and knowledge-graph-based retrieval mature, is there a principled way to decide automatically, per query, whether pure vector retrieval or graph-traversal-augmented retrieval will produce better grounding — and could this decision itself be learned from historical query/answer-quality feedback?
