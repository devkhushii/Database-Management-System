## Module 2: Physical Database Storage

> **Where we are:** Module 1 gave you the vocabulary — blocks, pages, records, slots. Module 2 takes you *inside* a single page and shows exactly how rows are packed, addressed, updated, and moved. Everything in Modules 5–7 (indexes, B+ Trees, hashing) ultimately points at structures defined here — a B+ Tree leaf entry, at the end of the day, is just a **Record ID** pointing into a page you're about to learn how to read.

## 2.0 Why This Module Exists

A page is not a random bag of bytes. It is a **carefully engineered mini-filesystem**, re-invented at a smaller scale, that must answer three questions efficiently:

1. Where exactly does row #42 live inside this 8 KB/16 KB page?
2. If row #42 grows in size (an `UPDATE` made a `VARCHAR` longer), what happens?
3. If row #42 is deleted, how does the freed space get reused without shifting every other row?

Module 2 is the answer to all three.

## 2.1 Page Layout — The Slotted Page Structure

### What is it?

A **slotted page** is the near-universal layout used by PostgreSQL, MySQL/InnoDB, Oracle, and SQL Server to store variable-length records inside a fixed-size page, using a level of indirection (the "slot array") so that records can move around *inside* the page without needing to update every external reference to them.

### Why does it exist?

If rows were stored back-to-back with no indirection, then deleting a row in the middle of a page — or growing a row's size — would force shifting every subsequent row and rewriting every pointer to those rows. That is prohibitively expensive. The slotted page solves this with **one extra layer of indirection**: external references point to a **slot number**, not a byte offset; only the slot entry (small, fixed-size) needs updating when a row moves.

### Anatomy of a Slotted Page

```
 0                                                          PAGE_SIZE (8 KB / 16 KB)
 ┌──────────────┬───────────────┬───────────────────┬─────────────────────────┐
 │  Page Header │  Slot Array   │    Free Space      │      Tuple Data         │
 │ (fixed size) │ (grows RIGHT) │ (shrinks over time)│   (grows LEFT, from     │
 │              │  ->  ->  ->   │                    │    the end of page)     │
 └──────────────┴───────────────┴───────────────────┴─────────────────────────┘
      ^                 ^                                        ^
   metadata:      slot[0] -> offset,len               Tuple N ... Tuple 1
   page LSN,      slot[1] -> offset,len                (packed from the
   checksum,      slot[2] -> DELETED (tombstone)         high address end
   free space      ...                                    downward)
   pointers, etc.
```

**Key insight:** The slot array grows **toward the middle** from one end of the page, and tuple data grows **toward the middle** from the other end. The page is "full" when these two regions meet. This is exactly analogous to a stack and a heap growing toward each other in a process's virtual memory — same trick, different context.

### Page Header contents (representative, engine-specific in practice)

| Field | Purpose |
|---|---|
| Page LSN (Log Sequence Number) | Ties this page's last-modified state to the WAL (crucial in Part 9 for crash recovery) |
| Checksum | Detects corruption (e.g., a torn write) |
| Lower/Upper pointers | Boundaries of free space region |
| Special space pointer | Engine-specific extra area (e.g., PostgreSQL B+ Tree pages use this for sibling links) |
| Flags | Page type: heap page, index page, overflow page, etc. |

### Disk-level behavior

The whole slotted page — header, slot array, free space, tuple data — is read or written **as one atomic unit** in a single I/O operation. You cannot partially read a page; the engine always brings the entire page into the buffer pool (Module 4).

### PostgreSQL vs MySQL (InnoDB)

| Aspect | PostgreSQL Heap Page | InnoDB Page |
|---|---|---|
| Slot array name | "Item pointers" (`ItemIdData`) | "Record directory" / "page directory" (sparse, not one-per-row) |
| Growth direction | Item pointers grow forward from header; tuples grow backward from page end | Similar two-region design, but InnoDB additionally maintains an in-page doubly linked list of records in key order (because InnoDB pages are always part of a B+ Tree — heap tables don't exist in InnoDB the way they do in Postgres) |
| Special note | Non-clustered by default (Module 5); tuple location does not encode key order | InnoDB tables are **always** clustered on the primary key (Module 5, Module 9) — this changes how "physical storage" and "index" relate |

### Best Practices
- Don't assume physical row order matches insertion order once updates/deletes have happened — always rely on explicit `ORDER BY`.
- When bulk-loading, load data in primary-key order for clustered tables (InnoDB) to minimize page splits (Section 2.10).

### Common Mistakes
- Believing `SELECT *` returns rows in a stable, meaningful physical order — the slotted page's internal reordering (row migration, vacuum, page splits) can and will change physical order over time.

### Interview Importance
⭐⭐⭐⭐⭐ — "Explain the slotted page structure and why the slot array uses indirection" is one of the most common Storage Engine interview questions at database-focused companies (Oracle, Snowflake, Yugabyte, TimescaleDB, Amazon RDS teams).

## 2.2 Fixed-Length Records vs Variable-Length Records

### Fixed-Length Records

Every row occupies exactly the same number of bytes (e.g., all columns are `INT`, `CHAR(n)`, `DATE` — no `VARCHAR`, `TEXT`, or `NULL`-bearing variable fields).

**Why it's simpler:** Row *k* on a page can be found with pure arithmetic:
```
offset(k) = page_header_size + (k * record_size)
```
No slot indirection is strictly *required* for pure fixed-length record files (though most engines still use slots uniformly for consistency, tombstones, and easier row migration).

### Variable-Length Records

Rows differ in size because of `VARCHAR`, `TEXT`, `NULL` bitmaps, or optional trailing fields. This is the **overwhelmingly common case** in real schemas.

### How variable-length records are handled

1. **Slot indirection** (Section 2.1) — the standard, universal solution.
2. **Length-prefixing** — each variable-length field is stored with a preceding length value so the engine knows where it ends.
3. **Null bitmap** — a small bitmap at the start of the tuple marking which columns are `NULL` (so `NULL` columns consume ~0 bytes of value storage, just 1 bit in the bitmap).

### Diagram: A Variable-Length Tuple Layout (conceptual)

```
┌───────────────┬────────────┬───────────────┬──────────────────┬────────────┐
│ Tuple Header  │ Null Bitmap│ Fixed-length  │ Variable-length   │ (overflow  │
│ (xmin/xmax in │ (1 bit/col)│ columns       │ columns, each     │  pointer   │
│  PG; trx id   │            │ (INT, DATE..) │ length-prefixed   │  if TOASTed│
│  in InnoDB)   │            │               │ (VARCHAR, TEXT..) │  /off-page)│
└───────────────┴────────────┴───────────────┴──────────────────┴────────────┘
```

### Comparison Table

| Feature | Fixed-Length | Variable-Length |
|---|---|---|
| Offset calculation | Pure arithmetic (O(1), no lookup needed) | Requires slot lookup / length-prefix parsing |
| Storage efficiency | Wastes space if actual values are short | Efficient — stores only what's needed |
| Update-in-place | Always safe (same size before/after) | Only safe if new value ≤ old value's space |
| Real-world usage | Rare in raw form; used internally for fixed-width index keys | Standard for almost all real application tables |

### Edge Cases
- A `VARCHAR(4000)` column storing a 20-byte value: only ~20 bytes + length prefix consumed — NOT 4000 bytes. `VARCHAR(n)` is a *ceiling*, not an allocation.
- Extremely long text/BLOB values exceed the page size entirely — this is where **TOAST** (PostgreSQL, Module 9) and **off-page/overflow pages** (InnoDB, Module 9) come in: the "in-row" tuple stores only a pointer, and the real data lives in a separate storage structure.

### Interview Importance
⭐⭐⭐⭐ — "Does `VARCHAR(255)` vs `VARCHAR(4000)` change storage if both hold a 10-character string?" is a very common trick question. **Answer: No, for the row's on-disk size** (in PostgreSQL/MySQL) — but it can affect maximum row size limits, in-memory buffer allocation during sorts in some engines, and index key size limits.

## 2.3 Record Identifiers (RID)

### What is it?

A **Record Identifier (RID)**, sometimes called a **Row ID / TID (Tuple ID) in PostgreSQL**, is the physical address of a record — typically encoded as **(Page Number, Slot Number)**.

### Why does it exist?

Every index (Modules 5–7) needs *some* way to say "the row matching this key lives *here*." The RID is that universal pointer. Instead of copying the entire row into every index, an index stores just the key + a small fixed-size RID — this is the foundational reason indexes are compact.

### How it works

```
Index Entry: (key = 'Khushi', RID = (Page 17, Slot 3))
                                          |
                                          v
                          Page 17: [Slot Array] slot 3 -> offset 512, len 42
                                          |
                                          v
                                 Actual tuple bytes at offset 512
```

### PostgreSQL vs MySQL

| Aspect | PostgreSQL (`ctid`) | InnoDB |
|---|---|---|
| Name | `ctid` = (block number, item pointer/slot number) | No stable persistent "RID" exposed the same way — because InnoDB's primary structure IS a clustered B+ Tree (Module 5, 9), secondary indexes store the **primary key value**, not a physical page/slot address |
| Stability | **Not stable** — changes on `UPDATE`, `VACUUM FULL`, `CLUSTER` | N/A — secondary index lookups go through primary key, an extra indirection called a "double lookup" (Module 9) |
| Exposed to users? | Yes, queryable as a hidden column `ctid` | No direct equivalent exposed |

> **This single difference is one of the most important architecture facts in all of Part 7**, and drives an entire section of Module 9: because InnoDB secondary indexes store the *primary key* (not a physical RID), every secondary-index lookup in InnoDB requires **two B+ Tree traversals** — one on the secondary index, one on the clustered primary key index. PostgreSQL's non-clustered design means (non-HOT) index lookups instead risk the `ctid` becoming stale after an `UPDATE`, which is why PostgreSQL's HOT (Heap-Only Tuple) optimization exists (Module 9).

### Common Mistakes
- Storing a PostgreSQL `ctid` value persistently in application code (e.g., as a "cheap primary key") — it can change silently after an `UPDATE` or `VACUUM FULL`. Never treat RID/`ctid` as a stable application-level identifier.

### Interview Importance
⭐⭐⭐⭐⭐ — "Why does InnoDB do a 'double lookup' for secondary index queries, but PostgreSQL doesn't (usually)?" is a Staff-level interview question, and the answer is 100% rooted in this RID discussion.

## 2.4 Tuple Storage — Putting It All Together

A **tuple** (one row's bytes), as physically stored, generally contains:

1. **Header metadata** — visibility/transaction info (`xmin`/`xmax` in PostgreSQL MVCC — cross-referenced fully in Part 9's Concurrency Control chapters; a hidden transaction ID + rollback pointer in InnoDB).
2. **Null bitmap** — which columns are NULL.
3. **Fixed-length column values** — stored directly, in schema-declared order (though the engine may reorder physically for alignment; see Best Practices below).
4. **Variable-length column values** — length-prefixed or slot-referenced.
5. **Overflow pointers** — if any column's value is too large to fit in-page (TOAST/off-page storage, Module 9).

### Best Practices
- **Column ordering for storage efficiency**: place fixed-length columns before variable-length columns, and be aware that PostgreSQL/MySQL may introduce padding for alignment — grouping similarly-sized fixed columns together reduces wasted padding bytes (a technique sometimes called "struct packing" borrowed from C).
- Avoid extremely wide tables with dozens of `NULL`-heavy optional columns if row width materially affects how many rows fit per page (fewer rows/page = more pages scanned = more I/O, tying back to Module 1's core lesson).

## 2.5 Free Space Management

### What is it?

**Free space management** is how the storage engine tracks, per page (and often per file/relation as a whole), how much unused space remains, so that `INSERT` operations know **which page** can accept a new row without scanning every page in the table.

### Why does it exist?

Without free-space tracking, every `INSERT` would need to scan pages sequentially until it finds one with room — extremely wasteful for large tables. Free space management gives O(1)-ish or O(log n) lookups for "which page has ≥ X bytes free."

### How it works — PostgreSQL: the Free Space Map (FSM)

PostgreSQL maintains a separate **Free Space Map (FSM)** file per relation (a small forest/tree structure summarizing free space per page), letting an `INSERT` find a page with sufficient free space without touching the heap file's data pages directly.

*(Full detail on FSM's implementation and its relationship to VACUUM is covered in Module 9 and Module 11.)*

### How it works — InnoDB

InnoDB does not use a separate FSM file the way PostgreSQL does; because InnoDB tables are always organized as clustered B+ Trees, free space within a page is managed as part of the B+ Tree page structure itself, and free space across pages is tracked via the tablespace's own extent/segment bookkeeping (extents = groups of pages, tracked in special "bitmap" pages within the tablespace).

### Comparison Table

| Aspect | PostgreSQL | InnoDB |
|---|---|---|
| Mechanism | Separate Free Space Map (FSM) file per relation | Extent/segment bitmap pages inside the tablespace |
| Granularity | Per-page free byte estimate | Per-extent (group of pages) free/used tracking |
| Updated by | VACUUM, INSERT/UPDATE/DELETE operations | Page allocation/deallocation during B+ Tree operations |

### Common Mistakes
- Assuming `DELETE` immediately frees disk space back to the OS — in most engines, deleted row space becomes *reusable free space within the file*, not space returned to the filesystem (this ties directly into fragmentation, Section 2.7, and VACUUM, Module 11).

## 2.6 Fill Factor

### What is it?

**Fill factor** is a configurable percentage that tells the engine to intentionally leave a portion of each page **empty** at initial insert time, reserving room for future in-place updates.

### Why does it exist?

If a table is frequently `UPDATE`d (especially updates that don't change row size, or PostgreSQL's HOT updates), leaving headroom in each page lets those updates happen **in the same page** rather than forcing the new version onto a different page — which matters enormously for update-heavy workloads (Module 9's HOT optimization depends on this).

### How it works

- Fill factor = 100 (default): pack pages as full as possible at insert time — best for insert-only or append-heavy, rarely-updated tables.
- Fill factor = 70, e.g.: only fill each page to 70% capacity initially, reserving 30% headroom for future updates.

### PostgreSQL vs MySQL

| | PostgreSQL | InnoDB |
|---|---|---|
| Setting | `fillfactor` storage parameter (per table/index, default 100 for tables, 90 for B+ Tree indexes) | Similarly `innodb_fill_factor` conceptually mirrored via `MERGE_THRESHOLD`/page filling behavior in `CREATE TABLE ... KEY_BLOCK_SIZE` scenarios; more commonly discussed as B+ Tree page fill during bulk load |

### Best Practice
- Lower fill factor (e.g., 70–90) for tables with frequent updates to non-indexed columns, to encourage in-place updates and reduce fragmentation/page splits.
- Keep fill factor at 100 for append-only/insert-heavy tables (e.g., logging tables) to maximize storage density and minimize page count (fewer pages = fewer I/Os for scans, Module 1's core lesson again).

## 2.7 Fragmentation

### What is it?

**Fragmentation** is the accumulation of unused, non-contiguous, or inefficiently packed space within data files, caused by `DELETE`s, `UPDATE`s that grow rows, and page splits — resulting in the same *logical* amount of data occupying *more* physical pages than necessary.

### Types of Fragmentation

| Type | Cause | Effect |
|---|---|---|
| **Internal fragmentation** | Free space left inside pages (from fill factor, deletes, or unfilled pages after splits) | More pages needed for the same data → more I/O for scans |
| **External fragmentation** | Pages belonging to one table become scattered across non-contiguous disk regions | Increases seek cost on HDD (less relevant on SSD, though still affects OS/filesystem prefetch efficiency) |

### Real-life analogy

Internal fragmentation is like a bookshelf where every shelf has empty gaps between books, so the same number of books takes more shelves. External fragmentation is like those shelves being physically scattered across many different rooms of the library instead of standing side-by-side.

### Common Mistakes
- Ignoring long-term fragmentation on heavily-updated tables — this silently increases query latency over months, and is one of the most common "why did the same query get slower over time" production incidents.
- Running full-table rebuilds (`VACUUM FULL` / `OPTIMIZE TABLE`) during peak traffic hours — these operations lock/rewrite the entire table and are expensive (fully discussed in Module 11: Index Maintenance).

### Interview Importance
⭐⭐⭐⭐ — "A table's query performance degrades over months despite no schema change — what would you investigate?" Expected answer path: check fragmentation → check statistics staleness (Module 10) → check index bloat (Module 12) → check VACUUM/ANALYZE settings (Module 11).

## 2.8 Row Migration

### What is it?

**Row migration** (also called "row chaining" or "forwarding," depending on the engine) happens when an existing row is `UPDATE`d to become **larger** than the free space remaining in its current page, forcing the engine to move it — fully or partially — to a different location.

### How it works (conceptual, engine-general)

```
BEFORE UPDATE:
Page 10: [Slot 4] -> Row data (60 bytes) fits in remaining free space

UPDATE sets a VARCHAR column to a much longer value (now needs 300 bytes)
Page 10 has only 50 bytes of free space left

AFTER UPDATE (row migration):
Page 10: [Slot 4] -> forwarding pointer -> Page 55, Slot 2
Page 55: [Slot 2] -> Full 300-byte row data
```

The **RID in any existing index still points at Page 10, Slot 4**, so instead of updating every index that references this row, the engine leaves a **forwarding pointer** behind. This avoids the (very expensive) alternative of walking every index and rewriting every reference.

### Why this matters for performance

A migrated/chained row now costs **two page reads** instead of one for any access that goes through the old RID (the forwarding page, then the destination page) — this is a hidden, easy-to-miss performance tax that accumulates silently in update-heavy tables with growing variable-length columns.

### PostgreSQL specifics

PostgreSQL does **not** use a persistent physical row-migration/forwarding-pointer mechanism the way Oracle does. Instead, PostgreSQL's MVCC model (Part 9) creates a **brand-new tuple version** on every `UPDATE` (old version marked expired via `xmax`, new version inserted, possibly on a different page) and relies on **VACUUM** to later reclaim the old version's space and on **HOT (Heap-Only Tuple)** chains to minimize the resulting index-update cost when the new version lands on the *same* page.

### Oracle / General RDBMS specifics

Oracle explicitly documents a **row migration** mechanism with real forwarding pointers as described above — this term/pattern originates largely from Oracle's storage engine documentation and is broadly taught as the general RDBMS-agnostic concept.

### Best Practices
- Avoid designing schemas where frequently-updated columns are variable-length and prone to large growth (e.g., appending to a `TEXT` column repeatedly) — consider separating volatile, growable columns into a related table.
- Monitor for high rates of migrated/chained rows (Oracle: `chain_cnt` in table stats; general: rising average I/Os-per-row over time) as an operational health signal.

### Interview Importance
⭐⭐⭐⭐ — Understanding row migration is what lets you correctly explain **why UPDATE can sometimes be more expensive than DELETE + INSERT**, a subtle but common Senior SDE question.

## 2.9 Page Splits — Introduction (Deep Dive in Module 6)

### What is it?

A **page split** occurs when a page (typically a B+ Tree index page, but conceptually possible for any ordered structure) becomes full and a new entry must be inserted, forcing the engine to allocate a new page and redistribute roughly half the entries from the full page into it.

### Why it's introduced here, not fully explained yet

Page splits are a **B+ Tree-specific mechanic** requiring an understanding of tree structure (internal nodes, leaf nodes, parent pointers) that Module 6 has not yet covered. This module only establishes the physical page-management vocabulary (free space, fill factor, fragmentation) that makes page splits *possible* and *costly*. **Full step-by-step page-split diagrams, algorithms, and complexity analysis are covered in Module 6: B-Tree & B+ Tree.**

### Preview diagram (conceptual only — details in Module 6)

```
Before split:          Page P (FULL) -> [k1,k2,k3,k4,k5,k6]   <- new key k4.5 must be inserted

After split:            Page P -> [k1,k2,k3]         Page P' (NEW) -> [k4,k4.5,k5,k6]
                              (parent pointer updated to reference both P and P')
```

### Why fill factor matters here (connects back to Section 2.6)

A B+ Tree index built with a **lower fill factor** (leaving headroom per page at build/rebuild time) delays the point at which pages fill up and split — directly trading some storage space for fewer, less-frequent page splits during heavy insert workloads.

## 2.10 Chapter Summary

- The **slotted page** is the universal layout solving variable-length record storage via one layer of indirection (slot array ↔ tuple data, growing toward each other).
- **Fixed-length records** allow O(1) arithmetic offset lookup; **variable-length records** need slot indirection, length-prefixing, and null bitmaps.
- A **Record Identifier (RID)** — `(page, slot)` — is the physical pointer every index uses; PostgreSQL exposes this as `ctid` (unstable across updates/VACUUM FULL); InnoDB's clustered design means secondary indexes store the primary key instead of a raw RID, causing the "double lookup" pattern.
- **Free space management** (PostgreSQL's FSM, InnoDB's extent bitmaps) lets `INSERT` find a page with enough room without scanning the whole table.
- **Fill factor** intentionally under-fills pages to leave headroom for future in-place updates, reducing fragmentation and page splits.
- **Fragmentation** (internal: wasted space within pages; external: scattered pages on disk) silently degrades performance over time and is fixed via rebuild/vacuum operations (Module 11).
- **Row migration** occurs when an updated row no longer fits its page; a forwarding pointer avoids rewriting every index, at the cost of an extra page read on future access. PostgreSQL instead uses MVCC + HOT chains + VACUUM.
- **Page splits** are introduced conceptually here and fully detailed with algorithms in Module 6.

## 2.11 Cheat Sheet

```
Slotted Page       = Header | Slot Array (grows ->) | Free Space | Tuple Data (<- grows)
Fixed-Length Row   = offset = header_size + (k * record_size)   [O(1) lookup]
Variable-Length    = needs slot indirection / length-prefix / null bitmap
RID (Row ID)       = (Page Number, Slot Number) -- physical address used by indexes
PostgreSQL ctid    = exposed, UNSTABLE across UPDATE/VACUUM FULL
InnoDB secondary   = stores PRIMARY KEY, not raw RID -> "double lookup" on secondary index
Free Space Map(PG) = per-relation structure tracking free bytes per page
Fill Factor        = % to fill page initially, rest reserved for future in-place updates
Fragmentation      = internal (wasted space in pages) vs external (scattered pages on disk)
Row Migration      = old page keeps forwarding pointer -> new page with full updated row
Page Split         = full page divides into two when a new entry won't fit (full detail: Module 6)
```
