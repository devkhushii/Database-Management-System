# DBMS Handbook — Part 7: Indexing, File Organization & Storage Structures
## Module 8: Advanced Index Types

> **Where we are:** Modules 5–7 covered the two universal default index structures — B+ Trees and hash indexes. Module 8 covers everything else: specialized index types built for specific data shapes and query patterns (multicolumn variants, geometric/spatial data, text search, semi-structured data) that a plain B+ Tree or hash index cannot serve well.

---

## 8.0 Why This Module Exists

A B+ Tree is fantastic when your data has a single, natural, **linear (totally-ordered)** sort order — integers, dates, strings. But real-world data often does **not** fit neatly into a single line:

- Geographic coordinates (`(latitude, longitude)`) have **two dimensions** — there is no single "correct" way to sort them that preserves spatial closeness.
- Free-text documents need to be searched by **which words appear inside them**, not by comparing whole strings.
- Extremely large tables sometimes need indexes so small they barely cost anything to maintain, sacrificing precision for size.

Module 8 is a tour of the specialized structures built to solve these non-linear problems.

---

## 8.1 Multicolumn Indexes (Recap + Extension)

Module 5, Section 5.6 already introduced the **composite index** and the **leftmost prefix rule**. This section extends that with additional multicolumn nuances relevant to advanced indexing.

### Column Order Strategy

When designing a multicolumn index, general guidance (expanded fully with optimizer interaction in Module 10) is:

1. Put **equality-filtered** columns first (columns typically compared with `=`).
2. Put **range-filtered or sorted** columns last (columns typically compared with `<`, `>`, `BETWEEN`, or used in `ORDER BY`).

This ordering maximizes how much of the composite index's sorted structure remains useful after the equality columns "pin" the search to a narrow slice.

## 8.2 Descending Indexes

### What is it?

A **descending index** stores its keys sorted in **descending order** rather than the default ascending order — relevant specifically for **composite indexes** where different columns need different sort directions simultaneously (a single-column index can simply be scanned backward by the engine at no extra cost, so descending indexes matter primarily in the multicolumn case).

### Why does it exist?

Consider a query needing `ORDER BY created_at DESC, id ASC`. A composite index on `(created_at, id)` — both ascending — cannot satisfy this mixed-direction sort efficiently by simply scanning forward or backward as a whole; scanning it backward would give `created_at DESC, id DESC`, not the mixed order requested. A composite index explicitly defined as `(created_at DESC, id ASC)` matches the exact required output order, letting the engine avoid a separate sort step entirely.

### Example

```sql
CREATE INDEX idx_desc ON events (created_at DESC, id ASC);

-- This exact query can now use the index and avoid a sort step:
SELECT * FROM events ORDER BY created_at DESC, id ASC;
```

### PostgreSQL vs MySQL

Both PostgreSQL and modern MySQL (8.0+) support explicit `ASC`/`DESC` per column within a composite index definition. Older MySQL versions (pre-8.0) accepted the syntax but silently ignored the direction, always storing ascending — a historical gotcha worth knowing if working with legacy systems.

## 8.3 Reverse Indexes

### What is it?

A **reverse index** (also called a **reverse key index**, an Oracle-specific feature) stores the **byte-reversed** value of a key, rather than the key itself — e.g., indexing `12345` as `54321`.

### Why does it exist?

For **monotonically increasing keys** (like an auto-incrementing sequence), all new inserts hash/sort to the same "hot" region of a B+ Tree (typically the rightmost leaf), causing contention (many concurrent transactions competing to insert into the exact same page) in high-throughput systems. Reversing the key's bytes scatters consecutive key values across **different, unrelated parts of the tree**, spreading insert load evenly and relieving that hot-page contention — at the direct cost of destroying the index's usefulness for range scans (since reversed keys no longer preserve the original numeric ordering).

### Trade-off

| Aspect | Normal Index | Reverse Index |
|---|---|---|
| Insert contention on monotonic keys | High (all inserts hit the same hot page/leaf) | Low (inserts scatter across the tree) |
| Range query support | Full support | Lost — reversed values don't preserve order |

### Industry Usage

Primarily an Oracle feature (`CREATE INDEX ... REVERSE`), historically significant in Oracle RAC (clustered database) deployments to reduce cross-node contention on sequence-generated keys. PostgreSQL and MySQL do not offer a directly equivalent built-in feature (application-level key scrambling or UUIDs are sometimes used instead, with the trade-offs discussed in Module 3/12).

## 8.4 BRIN Indexes (Block Range Index)

### What is it?

A **BRIN (Block Range Index)** is a PostgreSQL-specific index type that stores, for each **range of physical pages** (not each row), a small summary — typically the **minimum and maximum value** of the indexed column across that entire page range.

### Why does it exist?

For extremely large tables where the indexed column's values are **physically correlated with insertion order** (e.g., a `created_at` timestamp column on an append-only log table, where newer rows are naturally inserted later, ending up in later physical pages), a BRIN index can be **orders of magnitude smaller** than a full B+ Tree index, since it stores only one summary entry per page range (e.g., every 128 pages) instead of one entry per row.

### How it works

```
Table physically ordered roughly by insertion time (append-only log):

Page Range 1 (pages 1-128):    min=2026-01-01, max=2026-01-03
Page Range 2 (pages 129-256):  min=2026-01-03, max=2026-01-05
Page Range 3 (pages 257-384):  min=2026-01-05, max=2026-01-08

Query: WHERE created_at = '2026-01-04'
  -> BRIN index checks summaries -> only Page Range 2's range (01-03 to 01-05)
     could possibly contain this value -> scan ONLY that page range,
     skipping Page Ranges 1 and 3 entirely
```

### Advantages
- Extremely small index size (a tiny fraction of a full B+ Tree index for the same table) — enormous storage savings on huge append-mostly tables.
- Very cheap to maintain (updating just a min/max summary per page range is far lighter than B+ Tree splits/merges).

### Disadvantages
- **Only effective when data is physically correlated with the indexed column** — if rows are scattered/unordered with respect to that column (e.g., frequent `UPDATE`s that move rows around, or a naturally uncorrelated column), BRIN's min/max ranges become wide and unhelpful, forcing it to scan far more page ranges than a true B+ Tree would need to touch.
- Not useful for high-selectivity point lookups on uncorrelated data.

### Interview Importance
⭐⭐⭐⭐ — "When would you use a BRIN index instead of a B+ Tree?" — Answer: enormous, append-mostly tables (e.g., IoT sensor logs, time-series data) where the indexed column naturally correlates with physical row order, and where index storage size is a major concern.

## 8.5 GiST (Generalized Search Tree)

### What is it?

**GiST** is a PostgreSQL access method framework — not one specific index algorithm, but a **generalized, extensible tree structure** that can implement many different kinds of indexing strategies (balanced tree, nearest-neighbor search, custom containment/overlap logic) by letting the data type itself define custom comparison and consistency functions.

### Why does it exist?

A plain B+ Tree only understands **linear ordering** (`<`, `=`, `>`). Many real data types don't have a single natural linear order — **geometric shapes** (does a point fall inside a polygon?), **ranges** (do two time intervals overlap?), or **full-text search vectors** need fundamentally different notions of "closeness" or "containment." GiST provides a pluggable framework where any data type can define its own such logic, and PostgreSQL builds a balanced tree structure around it.

### Common Use Cases

- **Geometric/spatial data** — PostGIS (PostgreSQL's spatial extension) uses GiST extensively for spatial containment and nearest-neighbor queries.
- **Range types** — PostgreSQL's native `int4range`, `tsrange` (timestamp ranges), etc., use GiST to efficiently answer overlap queries (`WHERE date_range && '[2026-01-01, 2026-02-01)'`).
- **Full-text search** — GiST can also back `tsvector` full-text search columns (though GIN, Section 8.6, is usually preferred for this specific case).

### Interview Importance
⭐⭐⭐ — Knowing that GiST is a *framework*, not a single algorithm, is the key distinguishing fact interviewers check for.

## 8.6 GIN (Generalized Inverted Index)

### What is it?

**GIN** is a PostgreSQL index type optimized for cases where a single column value **contains multiple component values** to be searched — e.g., an array (`{apple, banana, cherry}`), a full-text search document (many words), or a JSONB document (many keys) — and queries need to find rows where **any or all** of those component values match a search term.

### Why does it exist? (the "inverted index" concept)

A GIN index inverts the usual relationship: instead of storing (row → its full array/document), it stores **(individual component value → list of rows containing it)** — exactly like a search engine's inverted index, or a book's back-of-book index (Module 5's book analogy revisited): for the word "mitochondria," it doesn't tell you which page contains the *whole book*; it directly tells you every page where that specific word appears.

### Example

```sql
CREATE INDEX idx_gin_tags ON products USING GIN (tags);  -- tags is an array column

-- Efficiently finds all rows where 'tags' array contains 'electronics':
SELECT * FROM products WHERE tags @> ARRAY['electronics'];
```

### GiST vs GIN — Comparison Table

| Aspect | GiST | GIN |
|---|---|---|
| Best for | Geometric/spatial data, range overlap, nearest-neighbor | Arrays, full-text search, JSONB containment |
| Lookup speed | Generally slower than GIN for containment queries | Faster lookups for containment (each component value directly maps to matching rows) |
| Index build/update speed | Generally faster to build/update | Slower to build/update (must maintain entries for every component value) |
| Underlying idea | Generalized balanced tree with custom per-datatype logic | True inverted index (component value → row list) |

### Interview Importance
⭐⭐⭐⭐ — "You need to index a JSONB column for fast containment queries — GiST or GIN?" Answer: **GIN**, because of its inverted-index structure being purpose-built for "does this document/array contain X" queries, at the cost of somewhat slower writes.

## 8.7 SP-GiST (Space-Partitioned GiST)

### What is it?

**SP-GiST** is a PostgreSQL access method for data that can be recursively **partitioned into non-overlapping regions** (unlike GiST's overlapping, balanced-tree approach) — well-suited to structures like quad-trees, k-d trees, and radix trees (tries).

### Why does it exist?

Some data naturally partitions into clean, **non-overlapping** subdivisions (e.g., recursively dividing 2D space into quadrants for a quad-tree, or partitioning strings by common prefixes for a trie-like structure) — for such data, SP-GiST's non-overlapping partitioning can be more efficient than GiST's more general, potentially-overlapping tree balancing logic.

### Common Use Cases
- IP address range indexing (`inet`/`cidr` types).
- Certain text pattern-matching scenarios (prefix-based).
- Specialized geometric partitioning (quad-tree-like use cases).

*(Overview only, per this module's scope — SP-GiST is a more niche, specialized access method compared to GiST/GIN/BRIN's broader everyday usage.)*

## 8.8 R-Tree (Overview)

### What is it?

An **R-Tree** is a tree structure specifically designed for indexing **multi-dimensional spatial data** (rectangles, bounding boxes, points), where each internal node stores a **minimum bounding rectangle (MBR)** that encloses all the spatial objects in its subtree.

### How it works (conceptual)

```
Root MBR encloses everything
   |
   +-- Child MBR A (encloses regions 1, 2)
   |       +-- Region 1 (actual spatial object)
   |       +-- Region 2 (actual spatial object)
   +-- Child MBR B (encloses regions 3, 4)
           +-- Region 3
           +-- Region 4

Query: "find all objects overlapping this area"
  -> descend only into child MBRs whose bounding box overlaps the query area,
     skipping entire subtrees whose MBR doesn't overlap at all
```

### Industry Usage

R-Trees are the classical academic structure behind spatial indexing; in practice, PostgreSQL/PostGIS implements spatial indexing via **GiST** (Section 8.5) using R-Tree-like bounding-box logic internally, rather than exposing a separately-named "R-Tree index type." Other systems (e.g., Oracle Spatial, MySQL's spatial extensions) do use R-Tree-based indexes more directly by name.

*(Overview only, per this module's scope — full spatial query processing and GIS-specific optimization is outside Part 7's scope.)*

## 8.9 Full-Text Indexes

### What is it?

A **full-text index** is built specifically to accelerate **natural-language text search** — finding documents containing certain words or phrases, ranking results by relevance, handling stemming (matching "running" to a search for "run"), and ignoring common "stop words" (like "the," "a," "is").

### How it works (conceptual)

1. Text is broken into individual **tokens** (words), often normalized (lowercased, stemmed).
2. An **inverted index** (Section 8.6's GIN concept, or MySQL's dedicated `FULLTEXT` index type) maps each distinct token to the list of documents/rows containing it.
3. Search queries are similarly tokenized, and the inverted index quickly retrieves candidate matching rows, often combined with a relevance-ranking calculation.

### PostgreSQL vs MySQL

| | PostgreSQL | MySQL |
|---|---|---|
| Mechanism | `tsvector`/`tsquery` types, backed by a **GIN** (or GiST) index | Dedicated `FULLTEXT` index type (available on InnoDB and MyISAM tables) |
| Ranking | `ts_rank`/`ts_rank_cd` functions | `MATCH() AGAINST()` with natural-language or boolean mode relevance scoring |

### Interview Importance
⭐⭐⭐ — Knowing that PostgreSQL implements full-text search **on top of** GIN (rather than as an entirely separate index type) reinforces the conceptual connection between Sections 8.6 and 8.9.

## 8.10 Spatial Indexes (Summary)

Spatial indexing (already discussed via GiST in 8.5 and R-Trees in 8.8) exists to answer questions like "which objects are near this point?" or "which regions overlap this polygon?" — fundamentally different from a B+ Tree's single-dimension ordering. The key generalizable idea across all spatial index implementations: **recursively group nearby/overlapping objects together and store a bounding summary (MBR or similar) at each level, allowing large portions of the search space to be skipped (pruned) whenever a query region doesn't intersect a node's bounding summary at all.**

## 8.11 Bloom Filters (Overview)

### What is it?

A **Bloom filter** is a compact, probabilistic data structure that answers the question **"might this value exist?"** using very little memory, at the cost of allowing occasional **false positives** (saying "might exist" for a value that actually doesn't) but **guaranteeing zero false negatives** (if the filter says "definitely does not exist," that is always correct).

### How it works (conceptual, high level)

A Bloom filter is a bit array plus several independent hash functions. Inserting a value sets several bits (determined by the hash functions) to 1. Checking a value's presence checks whether **all** of those same bits are set to 1 — if even one relevant bit is 0, the value is **definitely not present**; if all relevant bits are 1, the value is **probably present** (or, rarely, a false positive caused by other values' bits overlapping by coincidence).

### Why databases use them

Bloom filters are used as a cheap **pre-check** before doing an expensive real lookup (e.g., a disk I/O) — if the Bloom filter says "definitely not present," the engine can skip the expensive lookup entirely with full confidence; only when the filter says "probably present" does the engine pay for the real, authoritative check.

### Industry Usage

Heavily used in **LSM-Tree-based storage engines** (Cassandra, RocksDB, HBase — and conceptually connects back to Module 3, Section 3.2's "sequential file with overflow" ancestor discussion) to avoid checking every on-disk SSTable file for a key that doesn't actually exist in most of them. Less commonly exposed as a user-facing index type in traditional RDBMSs like PostgreSQL/MySQL, though PostgreSQL does offer a `bloom` extension module implementing Bloom-filter-based indexing for specific multicolumn equality-heavy use cases.

*(Overview only, per this module's scope — full LSM-Tree architecture is outside traditional RDBMS-focused Part 7, but the concept is important for well-rounded storage engine knowledge and is increasingly relevant given the rise of distributed/NoSQL systems in modern backend architectures.)*

### Interview Importance
⭐⭐⭐⭐ — "What is a Bloom filter, and why might a database use one?" is an increasingly common question, especially at companies running large-scale distributed storage systems (Cassandra, HBase, RocksDB-backed systems).

## 8.12 Master Comparison Table — Advanced Index Types

| Index Type | Best For | Engine | Underlying Idea |
|---|---|---|---|
| Descending Index | Mixed ASC/DESC composite sort requirements | PostgreSQL, MySQL 8.0+ | Explicit per-column sort direction in composite index |
| Reverse Index | Relieving hot-page insert contention on monotonic keys | Oracle | Byte-reversed key storage, sacrifices range-query support |
| BRIN | Huge, append-mostly, physically-correlated tables (e.g., time-series logs) | PostgreSQL | Per-page-range min/max summaries, extremely small size |
| GiST | Spatial data, range overlap, nearest-neighbor | PostgreSQL | Generalized, extensible balanced tree framework |
| GIN | Arrays, full-text search, JSONB containment | PostgreSQL | True inverted index (component value -> row list) |
| SP-GiST | Non-overlapping partitionable data (quad-trees, tries, IP ranges) | PostgreSQL | Recursive non-overlapping space partitioning |
| R-Tree | Multi-dimensional spatial bounding-box queries | Oracle Spatial, MySQL Spatial (PostgreSQL implements similar logic via GiST) | Minimum Bounding Rectangles (MBR) at each tree level |
| Full-Text Index | Natural language search, relevance ranking | PostgreSQL (`tsvector`+GIN), MySQL (`FULLTEXT`) | Tokenized inverted index + relevance scoring |
| Bloom Filter | Cheap "definitely not present" pre-checks | LSM-Tree systems (Cassandra, RocksDB), PostgreSQL `bloom` extension | Probabilistic bit-array membership test, zero false negatives |

## 8.13 Chapter Summary

- **Descending indexes** let composite indexes match mixed ASC/DESC `ORDER BY` requirements exactly, avoiding a separate sort step.
- **Reverse indexes** (Oracle) scatter monotonically increasing keys across a tree to relieve hot-page insert contention, at the cost of range-query support.
- **BRIN** indexes store tiny per-page-range min/max summaries, ideal for enormous, physically-correlated, append-mostly tables.
- **GiST** is a generalized, extensible tree *framework* (not one fixed algorithm) used heavily for spatial/range/nearest-neighbor queries.
- **GIN** is a true inverted index, ideal for arrays, full-text search, and JSONB containment — faster lookups than GiST, slower writes.
- **SP-GiST** handles non-overlapping, recursively-partitionable data (quad-trees, tries, IP ranges).
- **R-Trees** use Minimum Bounding Rectangles for spatial data; PostgreSQL implements similar logic via GiST rather than a separately-named R-Tree type.
- **Full-text indexes** tokenize text into an inverted index (PostgreSQL: `tsvector` + GIN; MySQL: dedicated `FULLTEXT` type) with relevance ranking.
- **Bloom filters** are compact, probabilistic "might exist?" pre-checks with zero false negatives, heavily used in LSM-Tree-based distributed storage systems.

---

## 8.14 Cheat Sheet

```
Descending Index  = explicit per-column ASC/DESC in composite index -> matches mixed ORDER BY
Reverse Index     = byte-reversed key -> scatters monotonic inserts, LOSES range support (Oracle)
BRIN              = per-PAGE-RANGE min/max summary -> tiny size, needs physical data/key correlation (PostgreSQL)
GiST              = generalized extensible TREE FRAMEWORK -> spatial, ranges, nearest-neighbor (PostgreSQL)
GIN               = TRUE INVERTED INDEX (value -> row list) -> arrays, full-text, JSONB (PostgreSQL)
SP-GiST           = NON-OVERLAPPING partitioning -> quad-trees, tries, IP ranges (PostgreSQL)
R-Tree            = Minimum Bounding Rectangles -> spatial data (Oracle/MySQL explicit; PG via GiST)
Full-Text Index   = tokenized inverted index + ranking (PG: tsvector+GIN | MySQL: FULLTEXT)
Bloom Filter      = probabilistic "might exist?" check, ZERO false negatives, cheap pre-check
                    (LSM-Trees: Cassandra/RocksDB; PostgreSQL has a `bloom` extension)
```
