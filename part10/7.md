# Part 10 — Database Internals & Storage Engine Architecture

## Module 7: Memory Management

> **Recap:** Module 6 covered the buffer pool — the *shared* cache of disk pages. This module covers everything else in a database engine's memory footprint: the private, per-query memory used for sorting, hashing, and aggregation, and what happens when that memory isn't enough.

---

### 7.0 Why This Module Exists

Every "why is my query slow / why did my server run out of memory" investigation eventually leads here. A database server's memory isn't one big pool — it's a layered system with very different sizing rules, and misunderstanding the layers is one of the most common sources of production incidents (OOM kills, disk-spilling sorts, runaway connection memory).

---

### 7.1 The Two Fundamental Categories: Shared vs. Local Memory

**Shared memory:** Memory accessible by *all* backend processes/threads simultaneously — the Buffer Pool (Module 6) is the largest example, alongside lock tables, the WAL/redo log buffer, and (in Postgres) the commit log (CLOG). Allocated once at server startup, sized by fixed configuration parameters.

**Local (private) memory:** Memory allocated per-connection/per-query, used only by that one backend, freed when no longer needed (typically at the end of a query or the end of a connection). This is where sorting, hashing, and aggregation working space lives.

**Why the distinction matters operationally:** Shared memory is a single, predictable, fixed cost, configured once. Local memory's *total* system-wide cost is `per_query_memory_limit × number_of_concurrently_executing_operations_that_need_it` — a number that can spike unpredictably under concurrent load, which is precisely why local memory settings are a frequent source of "worked fine in testing, OOM'd in production under load" incidents.

```
┌─────────────────────────────────────────────────────────┐
│                      SHARED MEMORY                          │
│   (one instance, fixed size, all backends access this)      │
│                                                               │
│   Buffer Pool / Shared Buffers │ WAL/Redo Buffer              │
│   Lock Tables │ CLOG (PG) │ Data Dictionary Cache             │
└─────────────────────────────────────────────────────────┘

┌──────────────┐  ┌──────────────┐  ┌──────────────┐
```

### 7.2 Work Memory / Sort Memory / Hash Memory

**What is it?** The bounded amount of local memory a single operation (a sort, a hash join build phase, a hash aggregation) is permitted to use before it must switch to a disk-based strategy instead.

**PostgreSQL: `work_mem`**
- Applies **per sort/hash operation**, not per query and not per connection. A single complex query with, say, three separate sorts and two hash joins could use up to `5 × work_mem` simultaneously — a frequently misunderstood detail.
- Default is modest (a few MB) precisely *because* of this multiplicative effect — raising it globally is risky; it's often better tuned per-session or per-query-class for specific known-heavy operations (`SET work_mem = '256MB'` for a single session running a reporting query, for example).

**MySQL/InnoDB: `sort_buffer_size` and `join_buffer_size`**
- `sort_buffer_size`: memory allocated per session for sort operations (e.g., `ORDER BY`, `GROUP BY` when a sort-based strategy is chosen).
- `join_buffer_size`: memory used for certain join strategies (particularly when no usable index exists for the join condition, historically associated with "Block Nested Loop" joins).
- Similarly multiplicative in spirit — allocated per operation/session, not shared globally, though the exact accounting details differ from Postgres's `work_mem` model.

**Why bound this at all?** Without a limit, a single poorly-written query (e.g., an accidental full sort of a billion-row table) could consume unbounded memory, potentially starving or crashing the entire server — the limit forces a graceful degradation path (spilling to disk, Section 7.5) instead of unbounded growth.

**Interview importance:** ⭐⭐⭐⭐⭐ "Does `work_mem` apply per query or per operation?" is an extremely common, easy-to-get-wrong Postgres question.

### 7.3 Temp Memory & Maintenance Memory

**Temp memory (general):** Space used for genuinely temporary structures during query execution beyond just sort/hash — e.g., materializing an intermediate result set that will be scanned multiple times within a single plan.

**PostgreSQL's `maintenance_work_mem`:** A separate, typically much larger memory budget specifically for maintenance operations — `VACUUM`, `CREATE INDEX`, `ALTER TABLE` operations that rebuild data. These operations are less frequent and less concurrent than everyday queries, so a larger per-operation budget is safer to configure (you're not multiplying it across hundreds of concurrent connections the way you might with `work_mem`).

**Why a separate setting exists at all:** If maintenance operations shared the same budget as everyday query `work_mem`, you'd face an impossible trade-off — a `work_mem` large enough to make `CREATE INDEX` fast would be dangerously large when multiplied across many concurrent everyday queries, and a `work_mem` safe for everyday concurrent queries would make index builds and vacuum unnecessarily slow.

### 7.4 Memory Contexts (PostgreSQL-Specific)

**What is it?** Postgres's internal memory management abstraction — a hierarchical system of **memory contexts**, each of which can be created, used for a batch of allocations, and then destroyed **all at once**, rather than requiring every individual allocation to be explicitly freed one by one.

**Why does it exist?** Query processing creates enormous numbers of small, short-lived allocations (AST nodes, expression evaluation intermediate values, tuple copies). Manually tracking and freeing every single one individually (as raw `malloc`/`free` would require) is both error-prone (easy to leak memory or double-free) and slow. Memory contexts solve this by grouping related allocations under a parent context with a defined lifetime — when that phase of processing is done, the *entire context* is destroyed in one operation, instantly reclaiming everything allocated within it, with no per-allocation bookkeeping needed at cleanup time.

**Hierarchical structure example (conceptual):**

```
TopMemoryContext (server-lifetime)
  └── PortalContext (one per active query/cursor)
        └── ExecutorState context (one per query execution)
              └── ExprContext (one per tuple being evaluated, reset per tuple!)
```

**Why this matters for performance:** The `ExprContext` being reset *per tuple* is a deliberate design choice — expression evaluation for each row can allocate freely without worrying about accumulating garbage across millions of rows processed in a query; the context reset after each tuple cheaply reclaims everything from that tuple's evaluation in one shot, rather than requiring precise tracking of every intermediate value.

**Real-life analogy:** Instead of individually cleaning up every single piece of trash generated during a large event, you use disposable tablecloths per table — at the end of the event, you simply roll up and discard each entire tablecloth (context) at once, instantly clearing everything on it, regardless of how many individual items accumulated.

**Interview importance:** ⭐⭐⭐ A distinctly Postgres-specific, moderately advanced topic — knowing it exists and its rough purpose (batch allocation lifetime management) is valuable; deep API-level detail is less commonly probed outside of Postgres-extension-development-focused interviews.

### 7.5 Spill to Disk

**What is it?** When an operation's local memory budget (`work_mem`, `sort_buffer_size`, etc.) is exceeded, the engine switches from a pure in-memory algorithm to a **disk-assisted** algorithm, using temporary files to hold data that doesn't fit in the allotted memory.

**Why this matters:** This is the graceful-degradation mechanism referenced in Section 7.2 — without it, exceeding the memory budget would simply be a hard failure. With it, the query still completes correctly, just slower (disk I/O is involved), which is almost always the right trade-off for correctness/availability over hard failure.

**Example — external merge sort (the classic disk-spilling sort algorithm):**

1. Read as much data as fits in `work_mem`, sort it in memory, write this sorted "run" out to a temporary file.
2. Repeat, producing multiple sorted runs, each individually sorted but collectively covering the full dataset.
3. **Merge phase:** Read from all the sorted runs simultaneously (a small buffer per run, fitting within memory), repeatedly taking the smallest available value across all runs — producing a single, fully sorted output stream, without ever needing to hold the entire dataset in memory at once.

```
Data too large for work_mem (e.g., need to sort 10GB with 100MB work_mem):

Phase 1 (Run generation):
  Read 100MB chunk → sort in memory → write sorted Run 1 to temp file
  Read 100MB chunk → sort in memory → write sorted Run 2 to temp file
  ... repeat until all 10GB consumed → ~100 sorted runs on disk

Phase 2 (Merge):
  Open small read buffer on each of the ~100 runs simultaneously
  Repeatedly pick the smallest current value across all open buffers
  → write to final sorted output
  (If too many runs to merge in one pass, do multiple merge passes —
   a "multi-way" or "polyphase" merge)
```

**Hash-based spill (for hash joins/hash aggregation exceeding memory):** Conceptually different but analogous — the build-side input is **partitioned** (via a hash function) into multiple smaller partitions, each small enough to fit in memory individually; partitions are written to temporary files, then processed (built and probed) one at a time.

**PostgreSQL example:** `EXPLAIN ANALYZE` output showing `Sort Method: external merge Disk: 45000kB` is the direct, visible evidence that a sort exceeded `work_mem` and spilled — a very commonly cited diagnostic in real query-tuning work and interviews alike.

**MySQL example:** Slow query log / `EXPLAIN` can reveal `Using temporary; Using filesort` — indicating a temporary table and an on-disk sort were needed, often traceable to insufficient `sort_buffer_size`/`tmp_table_size` for the operation at hand.

**Performance implication:** Disk-based sorts/hashes are typically an order of magnitude (or more) slower than their in-memory equivalents — this is *the* most common, most directly actionable root cause identified when diagnosing an unexpectedly slow `ORDER BY`, `GROUP BY`, or large join in either engine.

**Interview importance:** ⭐⭐⭐⭐⭐ "What happens when a sort doesn't fit in memory, and how would you detect it happened?" is an extremely high-yield, practical interview question.

### 7.6 Memory Pools (General Concept)

**What is it?** A broader design pattern (of which Postgres's memory contexts are one specific implementation) where memory is allocated in larger chunks from the OS upfront, then sub-allocated internally by the application in smaller pieces — avoiding the overhead of calling the OS allocator (`malloc`/`free`) for every small, frequent allocation.

**Why does it exist generically?** OS-level memory allocation calls have real overhead (system call potential, allocator bookkeeping, lock contention in multi-threaded allocators) — for a system making millions of tiny allocations per second (like a query executor processing tuples), batching this work at a coarser granularity is a significant performance win.

**Where this shows up beyond Postgres's memory contexts:** InnoDB similarly uses internal memory pools/heaps for various subsystems (e.g., a dedicated pool for the adaptive hash index's internal structures, separate pools for lock structures) rather than raw `malloc` calls scattered throughout its code — the same underlying motivation, implemented with InnoDB-specific structures rather than Postgres's generalized context hierarchy.

### 7.7 CPU & OS Interaction

**Memory-mapped files vs. explicit read/write:** Some storage engines/configurations use `mmap()` to map data files directly into a process's address space, letting the OS's virtual memory system handle paging in/out transparently. Others (including InnoDB in its typical configuration, and Postgres) prefer explicit `read()`/`write()` calls into their own managed buffer pool, retaining full control over caching decisions rather than delegating to the OS's more generic page-replacement policy. This is a deliberate trade-off: explicit management (what both major engines primarily use for their core data) gives the database precise control tailored to its own access patterns (as covered in Module 6 — clock-sweep, young/old LRU), which a generic OS-level page cache algorithm wouldn't know to apply.

**`O_DIRECT` and double-buffering avoidance:** As mentioned in Modules 3 and 4, InnoDB commonly uses `O_DIRECT` to bypass the OS page cache entirely for its data files, since it maintains its own buffer pool — caching the same page twice (once in the OS page cache, once in InnoDB's buffer pool) wastes RAM without meaningfully improving hit rates. Postgres, by contrast, does *not* use `O_DIRECT` by default and relies on a layered relationship with the OS page cache (a design choice with ongoing community discussion and evolving improvements in newer Postgres versions).

**NUMA awareness (brief mention, full detail in Module 13):** On multi-socket servers, memory access latency differs depending on whether memory is "local" or "remote" to the CPU socket performing the access — large buffer pools spanning NUMA boundaries can suffer from this, motivating NUMA-aware configuration in high-end deployments (previewed here, expanded in Module 13: Performance Engineering).

### 7.8 PostgreSQL vs. MySQL — Memory Configuration Summary

| Concept | PostgreSQL | MySQL (InnoDB) |
|---|---|---|
| Shared page cache | `shared_buffers` | `innodb_buffer_pool_size` |
| Per-operation sort/hash memory | `work_mem` (multiplicative per operation!) | `sort_buffer_size`, `join_buffer_size` (per session/operation) |
| Maintenance operation memory | `maintenance_work_mem` | N/A in the same explicit sense; various operation-specific settings |
| Internal allocation strategy | Hierarchical memory contexts (batch free) | Internal memory pools/heaps, per-subsystem |
| OS page cache interaction | Relies on it as a secondary layer (no `O_DIRECT` by default) | Typically bypasses it (`O_DIRECT` common) to avoid double-buffering |
| Spill-to-disk visibility | `EXPLAIN ANALYZE` shows "external merge Disk" | Slow query log / `EXPLAIN` shows "Using temporary; Using filesort" |

### 7.9 Advantages, Disadvantages, Best Practices

**Advantages of this layered memory model:**
- Shared memory provides a predictable, fixed-cost cache benefiting all connections
- Bounded local memory with disk-spill fallback provides graceful degradation instead of hard failures on large operations
- Batch-lifetime allocation (memory contexts/pools) avoids the overhead of fine-grained manual memory management during hot query-execution paths

**Disadvantages:**
- The multiplicative nature of local memory settings (`work_mem` per operation) makes total memory usage under concurrent load genuinely hard to predict precisely
- Disk-spilling operations, while safe, can be dramatically slower — a workload that "should" fit comfortably in memory can silently degrade if settings are miscalibrated relative to actual data growth over time

**Best practices:**
- Set conservative global local-memory defaults, and raise them **per-session** for specific known-heavy operations (reporting queries, batch jobs) rather than raising the global default and risking multiplicative overload under concurrent everyday load
- Monitor for spill evidence (`external merge Disk` in Postgres; `Using filesort`/temp table creation rate in MySQL) as a direct, actionable performance signal
- Size shared memory (buffer pool) and local memory budgets together, accounting for total system RAM, not independently

**Common mistakes:**
- Setting Postgres's `work_mem` very high globally "to make sorts faster," not accounting for it multiplying across every concurrent sort/hash operation server-wide, leading to OOM under load spikes
- Assuming a query that's fast in isolated testing (low concurrency) will remain fast in production (high concurrency) without accounting for local memory's multiplicative production behavior
- Not distinguishing `maintenance_work_mem`-style settings from everyday query memory settings, leading to either painfully slow index builds or dangerously oversized everyday query memory budgets

### 7.10 Chapter Summary

- Database memory splits into **shared memory** (fixed-size, one instance, includes the Buffer Pool from Module 6) and **local memory** (per-operation, multiplicative across concurrent load — `work_mem` in Postgres, `sort_buffer_size`/`join_buffer_size` in MySQL).
- Local memory for sorts/hashes/aggregations is **bounded**; exceeding the bound triggers a **spill to disk** (external merge sort, hash partitioning) rather than a hard failure — a deliberate graceful-degradation design.
- Postgres uses a hierarchical **memory context** system for internal allocation management, allowing entire batches of allocations to be freed at once rather than tracked individually.
- Maintenance operations (`VACUUM`, `CREATE INDEX`) get their own, typically larger, memory budget (`maintenance_work_mem`) since they're less concurrent than everyday queries.
- Engines differ in their relationship to the **OS page cache**: Postgres layers on top of it; InnoDB typically bypasses it via `O_DIRECT` to avoid double-buffering.

---

### 7.11 Cheat Sheet

```
Shared Memory  → fixed size, ONE instance, all backends access
                 (Buffer Pool, WAL buffer, lock tables)
Local Memory   → per-operation, MULTIPLIES under concurrent load
                 (work_mem [PG, per operation!] / sort_buffer_size [MySQL])

Exceeding local memory budget → SPILL TO DISK, not a hard failure:
  Sort  → external merge sort (generate sorted runs → merge)
  Hash  → partition into smaller hash tables, process one at a time

Detecting spill:
  PostgreSQL → EXPLAIN ANALYZE: "Sort Method: external merge Disk: ..."
  MySQL      → EXPLAIN / slow log: "Using temporary; Using filesort"

maintenance_work_mem (PG) → separate, larger budget for VACUUM/CREATE INDEX
                             (safe because these aren't highly concurrent)

Memory Contexts (PG) → hierarchical, batch-allocate + batch-free
                        (e.g., per-tuple ExprContext reset every row)

OS interaction: PG layers on OS page cache | InnoDB bypasses via O_DIRECT
                (avoids double-buffering the same page twice)
```
