### 15.1 Banking — Funds Transfer

**The scenario:** Transfer ₹10,000 from Account A to Account B.

**Core transaction:**

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;  -- or REPEATABLE READ + explicit locking

UPDATE accounts SET balance = balance - 10000 WHERE id = 'A' AND balance >= 10000;
-- check affected row count == 1; if 0, insufficient funds, ROLLBACK

UPDATE accounts SET balance = balance + 10000 WHERE id = 'B';

INSERT INTO transaction_log (from_acct, to_acct, amount, status) VALUES ('A','B',10000,'completed');

COMMIT;
```

**Concepts in play:**
- **Atomicity (Module 2):** both updates must succeed together, or neither does.
- **Isolation (Module 11):** must prevent Lost Update — two concurrent transfers debiting the same account must not read stale balances (the `WHERE balance >= 10000` guard plus appropriate isolation/locking prevents overdrawing).
- **Durability (Module 2):** once "transfer successful" is shown to the customer, it must survive any crash.

**Failure scenario — crash after debit, before credit:**
If the system crashes after the first `UPDATE` but before `COMMIT`, recovery (Part 7) uses the undo log to restore A's balance — the transaction never partially applied, thanks to Atomicity.

**Failure scenario — concurrent transfers causing Lost Update:**
Two simultaneous transfers both debiting Account A based on a stale read of its balance (Module 5.2) could allow the account to go negative despite the `balance >= 10000` check, if the check-then-update isn't atomic under weak isolation. This is why the single-statement conditional `UPDATE ... WHERE balance >= 10000` (an atomic check-and-update) is safer than a separate `SELECT` followed by an `UPDATE` — it avoids the read-then-write race entirely.

**Best practice reflected here:** Prefer atomic, conditional single-statement updates over "read, check in application code, then write" patterns whenever possible — this sidesteps several concurrency anomalies structurally, rather than relying purely on isolation level tuning.

### 15.2 ATM Systems

**The scenario:** A customer withdraws ₹5,000 from an ATM.

**Key challenge — the debit and cash dispensing are NOT both database operations.** Dispensing cash is a **physical, real-world action** that cannot be "rolled back" the way a database row can.

**Correct sequencing (a critical design decision):**

```
Step 1: BEGIN transaction, debit account balance, COMMIT.  ← database operation, fully ACID
Step 2: Only AFTER commit succeeds, instruct the physical dispenser to release cash.
Step 3: If cash dispensing physically FAILS (jam, hardware fault) AFTER the debit committed,
        this must be handled by a SEPARATE compensating transaction (a REFUND), not a rollback
        of the already-committed debit.
```

**Why this order matters:** If you dispensed cash **before** committing the debit, and the system crashed in between, the customer would receive cash with **no corresponding debit** — a direct financial loss for the bank. By committing the debit first, the worst-case failure (dispenser jam after commit) is a customer service problem (issue a refund) rather than an unrecoverable financial loss.

**Concepts in play:** This is a **real-world instance of the SAGA pattern (Module 14.6)** — the "physical cash dispensing" step is like an external, non-database step in a saga, requiring a compensating action (refund) if it fails after the preceding step has already committed.

### 15.3 E-commerce Checkout

**The scenario:** A customer checks out a cart containing 2 units of a product with only 3 units in stock, while another customer simultaneously checks out with 2 units of the same product.

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;  -- or use SELECT ... FOR UPDATE explicitly

SELECT stock_qty FROM products WHERE id = 'P1' FOR UPDATE;   -- acquire lock, prevent concurrent read-then-write race
-- application checks: stock_qty (3) >= requested (2)? Yes.

UPDATE products SET stock_qty = stock_qty - 2 WHERE id = 'P1';
INSERT INTO orders (product_id, qty, customer_id) VALUES ('P1', 2, 42);

COMMIT;
```

**Concepts in play:**
- **Lost Update (Module 5.2):** without `FOR UPDATE` (an Update Lock, Module 6.5), two concurrent checkouts could both read `stock_qty = 3`, both compute `3 - 2 = 1`, and both write `1` — resulting in 4 units sold from only 3 in stock (an oversold product), even though individually each checkout's math was "correct" based on what it read.
- **Phantom Read considerations (Module 5.6):** for flash-sale scenarios with dynamically added/removed inventory batches, phantom-read protection may also matter.
- **Distributed transaction concerns (Module 14):** if payment processing is a separate external service, this checkout flow often becomes a SAGA — reserve inventory (local commit), charge payment (external call, potentially slow/fallible), confirm order — with compensating "release inventory" and "refund" actions if a later step fails.

**Real production failure this prevents:** The classic "oversold flash sale item" bug, almost always traceable to a missing `FOR UPDATE` or equivalent locking/atomic-decrement mechanism on the stock check-and-decrement step.

### 15.4 Airline Reservation

**The scenario:** Two passengers simultaneously attempt to book the last remaining seat on a flight.

```sql
BEGIN;
SELECT seat_status FROM seats WHERE flight_id='F1' AND seat_no='12A' FOR UPDATE;
-- application checks: seat_status == 'available'? 

UPDATE seats SET seat_status = 'booked', passenger_id = 42 WHERE flight_id='F1' AND seat_no='12A';

COMMIT;
```

**Concepts in play:**
- Same Lost-Update-prevention logic as e-commerce checkout — `FOR UPDATE` ensures only one of the two concurrent booking attempts can "win" the seat; the second correctly sees `seat_status='booked'` after waiting for the first transaction's lock to release, and its booking attempt fails cleanly.
- **Phantom Read (Module 5.6):** a broader "find any available seat in economy class" query is a range query — susceptible to phantom reads if another booking commits an availability change to a *different* seat mid-transaction, changing the result set. This is why availability searches and the final booking commit are often handled as **two distinct steps**, with the final booking re-validating the specific seat's status at commit time (an OCC-style pattern, Module 9) rather than relying purely on the initial broad search's snapshot.

**Interesting design nuance:** Airlines often intentionally allow a **brief overbooking tolerance** (a business decision, not a bug) based on statistical no-show rates — this shows that "correctness" in a business sense isn't always "zero overbooking ever," but the *system's* concurrency control must still correctly enforce whatever the *intended* business rule is (e.g., "never sell more than 105% of seat capacity" rather than "never sell more than 100%").

### 15.5 Hospital Systems

**The scenario:** Ensuring at least one doctor is on-call at all times (the exact **Write Skew** example from Module 5.8), and ensuring a patient's medication record is never read in a partially-updated state.

**Write Skew mitigation:**

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;   -- required to prevent write skew (Module 5.8, 11.5)

SELECT COUNT(*) FROM doctors WHERE on_call = true;
-- application checks: count > 1 (safe for THIS doctor to go off-call)?

UPDATE doctors SET on_call = false WHERE id = 'dr_alice';

COMMIT;
```

Under plain Snapshot Isolation (Module 10.5), as shown in Module 5.8, this exact pattern can allow **both** Dr. Alice and Dr. Bob to go off-call simultaneously, since their writes touch different rows. **True Serializable isolation (via Serializable Snapshot Isolation or 2PL with predicate locking) is required** to correctly detect and prevent this specific anomaly.

**Read Skew concern for medication records:** A nurse reading a patient's "current medications" list must see a fully **consistent** snapshot (Module 5.9) — reading dosage from one still-being-updated record and a drug name from another, straddling a concurrent update, could show a dangerous, non-existent combination. `REPEATABLE READ` or Snapshot Isolation (which guarantee a consistent snapshot across the whole transaction) is the appropriate minimum here.

**Why this case study is a favorite in interviews:** it's the single clearest real-world illustration of *why* "MVCC/Snapshot Isolation" and "true Serializable" are meaningfully different guarantees (Module 10.5, Module 11.5) — a distinction many candidates get wrong.

### 15.6 Inventory Management

**The scenario:** A warehouse management system processing simultaneous stock adjustments from multiple sources — incoming shipments, outgoing orders, and manual corrections.

**Key challenge:** High write contention on popular SKUs ("hot rows," previewed here, detailed in Module 16) — many concurrent transactions want to update the *same* row's quantity simultaneously.

**Design consideration — avoiding lock contention on a single hot row:**

Instead of a single `stock_qty` column updated by every transaction (creating a serialization bottleneck, Module 16), some systems use an **append-only ledger** approach:

```sql
-- Instead of: UPDATE products SET stock_qty = stock_qty - 1 WHERE id='P1';
-- Use an append-only movements table:
INSERT INTO stock_movements (product_id, change, reason, created_at)
VALUES ('P1', -1, 'order_fulfilled', now());

-- Current stock computed as a (possibly cached/materialized) SUM:
SELECT SUM(change) FROM stock_movements WHERE product_id = 'P1';
```

**Trade-off:** This avoids lock contention on a single row (inserts to an append-only table don't conflict with each other the way updates to the same row do), but shifts the cost to needing an efficient way to compute the running total (e.g., periodic materialized aggregation) — a classic **write-scalability vs. read-simplicity** trade-off, directly relevant to Module 16's performance discussion.

**Concepts in play:** Hot-row lock contention (Module 16), Lost Update prevention (Module 5.2), and a practical illustration of how application/schema design choices can sidestep certain concurrency bottlenecks entirely, rather than relying purely on database-level tuning.

### 15.7 Payment Gateways

**The scenario:** Processing a credit card payment that involves calling an **external, third-party payment processor's API** — a slow, potentially-failing network call — as part of completing an order.

**The critical anti-pattern to avoid:**

```sql
-- ANTI-PATTERN — DO NOT DO THIS:
BEGIN;
  UPDATE orders SET status = 'processing' WHERE id = 555;
  -- Call external payment gateway API here, INSIDE the open transaction  ← BAD!
  -- (this could take several seconds, or fail/timeout)
  UPDATE orders SET status = 'paid' WHERE id = 555;
COMMIT;
```

**Why this is dangerous:** Holding a database transaction open while waiting on a slow, unreliable external network call means all locks acquired so far (e.g., on the `orders` row) are held for the **entire duration** of that external call — potentially many seconds, or until a network timeout — blocking any other transaction that needs to touch that row. This directly violates the Module 1.4/6.11 best practice of keeping transactions short, and can cause severe cascading contention under load.

**Correct pattern — separate the external call from the database transaction:**

```sql
-- Step 1: short transaction, mark order as "pending payment"
BEGIN;
  UPDATE orders SET status = 'pending_payment' WHERE id = 555;
COMMIT;

-- Step 2: (OUTSIDE any open transaction) call the external payment gateway

-- Step 3: short transaction, record the actual result
BEGIN;
  UPDATE orders SET status = 'paid' WHERE id = 555;  -- or 'payment_failed'
COMMIT;
```

**Concepts in play:** This is precisely the **SAGA pattern's local-transaction-plus-compensating-action** philosophy (Module 14.6) applied at a single-service level — each database transaction is kept short and self-contained, while the slow/fallible external step happens outside any open transaction, with a follow-up transaction recording its outcome (and a compensating action, like `payment_failed` handling or a refund, if needed).

**Common mistake this prevents:** A very frequent real-world production incident — "checkout is slow/timing out under load" — traced directly back to a payment gateway call sitting inside an open database transaction, discovered via slow-query/lock-wait monitoring (Module 16).

### 15.9 Advantages, Disadvantages, Best Practices (Meta-Level, Across All Case Studies)

**Cross-cutting Best Practices observed across every case study above:**
- Prefer **atomic, conditional single-statement updates** (`UPDATE ... WHERE condition`) over separate read-then-write application logic, wherever the business logic allows it.
- Use `SELECT ... FOR UPDATE` (Update locks, Module 6.5) deliberately whenever a read is immediately followed by a decision-dependent write in the same transaction.
- Recognize **Write Skew** scenarios (invariants spanning multiple rows) and use true Serializable isolation or explicit locking — never assume plain Snapshot Isolation/MVCC alone is sufficient.
- **Never** hold a database transaction open across a slow or unreliable external call — separate these concerns, using patterns inspired by SAGA even within a single service.
- For extremely hot, high-contention data, consider schema/architecture-level mitigations (append-only ledgers, sharding, dedicated atomic counters) rather than relying solely on isolation-level tuning.

**Common Mistakes (repeated across real production incidents):**
- Read-then-write races without proper locking (the single most common root cause of "impossible" data corruption bugs across nearly every case study above).
- Assuming MVCC/Snapshot Isolation alone prevents all anomalies (it doesn't — write skew, Module 5.8/10.5/11.5).
- Holding transactions open across external I/O.

### 15.10 Chapter Summary

- **Banking:** atomic conditional updates prevent lost updates on account balances.
- **ATM:** commit the debit before the physical (non-transactional) cash dispense; use compensation (refund) for post-commit physical failures.
- **E-commerce:** `SELECT ... FOR UPDATE` prevents overselling; external payment calls handled via SAGA-style separation.
- **Airline:** same lost-update protection, plus phantom-read awareness for broad seat searches, re-validated at final booking time.
- **Hospital:** the canonical real-world Write Skew example — requires true Serializable isolation, not just MVCC.
- **Inventory:** hot-row contention mitigated via append-only ledger patterns.
- **Payment Gateways:** never hold a transaction open across a slow external call — separate local commits from external actions, SAGA-style.
