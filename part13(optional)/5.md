# The Ultimate DBMS Handbook — Part 13: Research & Advanced Engineering

## Module 5 — Columnar Databases

> **Goal of this module:** Understand *why* analytical databases physically store data differently from transactional ones, and how that single decision cascades into compression, execution engine design, and query optimizer behavior.

---

### 5.1 The Fundamental Layout Decision

Every table is logically a grid of rows and columns. Physically, you must pick one axis to store contiguously:

- **Row store**: all columns of row 1, then all columns of row 2, then row 3... (`(r1c1, r1c2, r1c3), (r2c1, r2c2, r2c3), ...`)
- **Column store**: all values of column 1 across every row, then all values of column 2... (`(r1c1, r2c1, r3c1, ...), (r1c2, r2c2, r3c2, ...), ...`)

**Why this single choice matters so much:** disk/SSD I/O happens in blocks, and CPU cache lines and prefetching favor contiguous access. If your query touches 3 of a table's 50 columns, a row store must still read every column of every row it touches (then discard 47/50 columns' worth of bytes), while a column store reads *only* the 3 columns needed — for wide analytical tables, this is often a 10-20x reduction in bytes actually read from storage.

---

### 5.2 Row Store — When and Why

**Best fit:** OLTP workloads — point lookups and updates of whole records (`SELECT * FROM orders WHERE id = 123`, `UPDATE orders SET status = 'shipped' WHERE id = 123`). An entire row is fetched/modified together, so storing it together means one contiguous I/O per operation.

**Representative systems:** PostgreSQL, MySQL/InnoDB, Oracle (in default configuration), SQL Server (default heap/clustered index tables).

**Why row stores are poor for analytics:** a query like `SELECT AVG(amount) FROM orders WHERE year = 2025` touching millions of rows but only 2 of 40 columns still forces the engine to read every full row from disk, wasting the vast majority of I/O bandwidth on columns the query doesn't need.

---

### 5.3 Column Store — Internal Mechanics

**Physical layout:** each column is stored as its own contiguous file/segment, often further divided into **row groups** or **stripes** (e.g., Parquet's row groups, ORC's stripes) — a horizontal partition of, say, 1 million rows, within which each column is stored contiguously and independently compressed. This two-dimensional structure (columns × row groups) lets a query engine skip entire row groups using **min/max statistics** stored per row group per column (directly reusing the micro-partition pruning idea from Snowflake, Module 3.12) *and* read only the needed columns within the groups it doesn't skip.

**Representative systems:** ClickHouse, Apache Druid, Vertica (arguably the modern column-store pioneer, descended from Stonebraker's C-Store research project), Amazon Redshift, Snowflake's storage layer, Parquet/ORC as file formats used by Spark/Trino/Presto/Athena.

**The cost column stores pay:** reconstructing a *full row* (needed for `SELECT *` or any row-oriented operation) requires reading and re-joining data from potentially many separate column files — this is why column stores are poor for OLTP-style point-row access, the mirror image of row stores' analytics weakness.

**C-Store / MonetDB lineage:** the two foundational academic column-store research projects. **C-Store** (Stonebraker et al., VLDB 2005) introduced the idea of storing multiple sort-order-optimized "projections" of the same logical table, each covering different query patterns, directly influencing Vertica (a commercial descendant). **MonetDB** pioneered fully vectorized, in-memory columnar execution (5.4) as a research prototype, directly influencing DuckDB's design.

---

### 5.4 Vectorized Execution

**The problem it solves:** traditional query execution engines (the "Volcano" or "iterator" model — each operator's `next()` call returns one row at a time, pulled up through a tree of operators) pay significant per-row function-call and branch-prediction overhead, because the CPU executes the entire operator tree's logic once *per row*.

**The innovation:** instead of processing one row per `next()` call, each operator processes a **batch (vector) of rows at once** — typically hundreds to thousands of values from one column, laid out contiguously in an array. This gives two compounding speedups:
1. **Amortized interpretation overhead** — the operator-dispatch and function-call overhead is paid once per batch, not once per row.
2. **SIMD (Single Instruction, Multiple Data)** — because a batch is a contiguous array of same-typed values, the CPU can apply one instruction (e.g., "add") to multiple values simultaneously using vector CPU instructions (AVX2/AVX-512 on x86), and the contiguous memory access pattern is also far more cache- and prefetcher-friendly than scattered per-row access.

**Why columnar storage and vectorized execution are a natural pair (but not strictly required together):** columnar storage already produces data in the per-column, contiguous-array shape vectorized execution wants to consume — reading a column store's on-disk column directly into a vector/batch requires no reshaping, whereas a row store would need to first "transpose" rows into column-shaped batches before vectorized operators could work on them efficiently. This is why virtually every modern columnar analytical engine (ClickHouse, DuckDB, Vertica, Snowflake, Photon in Databricks) is also vectorized, even though the two ideas are conceptually separable.

**Representative implementations:** DuckDB and ClickHouse are the clearest open-source examples to study source code from directly; Databricks' **Photon** engine is a vectorized C++ rewrite of Spark's originally JVM/row-oriented execution engine, added specifically to close this performance gap.

### 5.5 Compression

**Why column stores compress dramatically better than row stores:** a single column contains values of the *same type and similar distribution* (e.g., a `status` column with only 5 distinct values, a `country` column with ~200, a mostly-sequential `timestamp` column) — homogeneous, repetitive data compresses far better than a row's heterogeneous mix of an integer ID, a string name, a timestamp, and a float amount interleaved together.

**Key columnar compression techniques:**
- **Run-Length Encoding (RLE)**: store `(value, count)` pairs for consecutive repeated values — extremely effective for sorted or naturally clustered low-cardinality columns (e.g., a `status` column sorted by insertion order).
- **Dictionary Encoding**: replace each distinct string/value with a small integer code, storing the code array plus a separate dictionary mapping codes back to original values — effective for low-to-medium cardinality string columns (categories, country codes), and has the added benefit that many query operations (equality filters, group-by) can operate directly on the compact integer codes instead of the original strings, which is faster.
- **Delta Encoding**: store the difference between consecutive values rather than the values themselves — extremely effective for monotonic or near-monotonic columns like auto-increment IDs or timestamps, where deltas are small numbers even when absolute values are large.
- **Bit-Packing**: use the minimum number of bits needed to represent a column's value range (e.g., if a column's max value fits in 12 bits, don't spend a full 32/64-bit word per value) — often combined with delta encoding (delta values tend to be small, so they bit-pack tightly).
- **Frame of Reference (FOR) / Patched FOR**: store a base value plus small deltas from it (a generalization of delta encoding for non-monotonic but locally-clustered values), with an "exception" mechanism for outlier values that would otherwise blow up the bit-width needed for the whole block.

**The crucial follow-on benefit — operating on compressed data directly:** advanced columnar engines don't always decompress before computing — e.g., a `WHERE status = 'active'` filter against a dictionary-encoded column can compare against the dictionary code directly (decompressing the dictionary once, not every row), and RLE-encoded aggregates can sometimes be computed using the `(value, count)` pairs directly rather than expanding to individual rows first. This is a major source of columnar analytical engines' speed advantage beyond just "less disk I/O."

### 5.6 Column Store Query Execution Deep Dive

**Predicate pushdown + zone maps (min/max pruning):** before reading any actual column data, the query engine checks per-row-group min/max statistics (5.3) against the query's `WHERE` predicates — a row group with `max(year) = 2020` can be entirely skipped for a query filtering `year = 2025`, without reading a single byte of that group's data.

**Late materialization:** rather than immediately reconstructing full rows from multiple columns as soon as they're read, advanced column stores keep intermediate results as columns/vectors for as long as possible — applying filters and computing intermediate results purely on the columns actually needed, and only "materializing" (joining columns back into row form) at the very end, right before returning results — minimizing the amount of row-reconstruction work done and letting filters eliminate rows before wasted work is spent materializing columns that get filtered out anyway.

**Column store joins:** joining two column-store tables still requires row-level correlation, typically implemented as building a hash table on one side's join key column, then probing it with the other side's join key column, producing a set of matching *row positions* (not full rows) which are then used to fetch only the specific columns actually needed from both sides — this "join on positions, materialize late" pattern is a direct consequence of late materialization applied to joins specifically.

### 5.7 HTAP Bridge — Where Row and Column Meet

(Full HTAP treatment in Module 6 — this section previews the storage-layer mechanics specific to columnar concerns.)

Systems like **SAP HANA** and **TiDB/TiFlash** (Module 3.18) maintain a small, row-oriented (or unsorted, recently-written) **delta store** for fresh writes, which is periodically merged into the large, compressed, columnar **main store** — because columnar compression techniques (5.5) generally assume large, stable batches of data to compress effectively, and re-compressing on every single-row write would be prohibitively expensive. This delta/main split is the standard columnar-engine answer to "how do you support fast writes when your storage format wants big, static, compressed batches."

### 5.8 Production Examples & Industry Usage

| System | Storage model | Primary use case |
|---|---|---|
| ClickHouse | Columnar, on-disk, vectorized | Real-time analytics, observability/logging dashboards |
| DuckDB | Columnar, in-process, vectorized | Embedded/local analytics, "SQLite for OLAP" |
| Vertica | Columnar, C-Store-derived | Enterprise analytics with multiple sort-order projections |
| Apache Druid | Columnar, inverted-index hybrid | Real-time dashboards over event/time-series data |
| Snowflake | Columnar (Parquet-like micro-partitions) | Cloud data warehousing |
| Parquet / ORC | Columnar file formats (not engines themselves) | The de facto standard columnar format for data lakes, read by Spark/Trino/Presto/Athena |
| Databricks (Photon) | Vectorized columnar execution engine over Delta Lake/Parquet | Lakehouse analytics at scale |

### 5.10 MCQs

**Q1.** Column stores outperform row stores for analytical queries primarily because:
A) They use less RAM
B) They read only the columns actually needed by the query, reducing I/O
C) They don't need indexes
D) They avoid using SQL

*Answer: B*

**Q2.** Vectorized execution improves performance mainly by:
A) Reducing disk space
B) Amortizing per-row interpretation overhead and enabling SIMD over batches of values
C) Removing the need for a query optimizer
D) Increasing write amplification

*Answer: B*

**Q3.** Dictionary encoding is most effective for columns that are:
A) High-cardinality random floats
B) Low-to-medium cardinality strings/categories
C) Binary blobs
D) Already compressed

*Answer: B*

**Q4.** Late materialization in columnar query execution means:
A) Rows are reconstructed as early as possible
B) Row reconstruction is deferred until as late as possible in the query plan, after filters have reduced the data
C) Materialized views are always used
D) Compression happens after the query runs

*Answer: B*

**Q5.** The delta-store/main-store split in HTAP columnar systems exists because:
A) Columnar compression assumes large, stable batches, making single-row writes expensive to compress directly
B) Row stores don't support writes
C) It's required by SQL standards
D) It improves compression of the delta store itself

*Answer: A*
