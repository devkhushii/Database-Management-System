### 3.1 PostgreSQL Process Architecture

**Core design decision:** PostgreSQL uses a **process-per-connection** model (not threads). Every client connection gets its own OS process (a "backend process"), all coordinating through **shared memory**.

**Why processes instead of threads?** Historical and reliability reasons — a crash in one backend process (e.g., a buggy extension) doesn't take down the whole server, since each connection is isolated at the OS process level. The trade-off is higher per-connection memory overhead compared to a thread-per-connection model (this is precisely why **connection pooling** — e.g., PgBouncer — is considered near-mandatory for high-concurrency Postgres deployments).

```
┌───────────────────────────────────────────────────────────────┐
│                         POSTMASTER (PID 1 of the DB)             │
│      Listens on port, accepts connections, forks backends,       │
│         supervises all child processes, restarts on crash        │
└───────────┬──────────────┬──────────────┬───────────────────────┘
            │              │              │
    ┌───────▼───────┐  ┌───▼────────┐  ┌──▼─────────────┐
    │ Backend Proc 1 │  │ Backend #2 │  │  Backend #N ... │  ← one process per client connection
    └───────┬───────┘  └───┬────────┘  └──┬─────────────┘
            │              │              │
            └──────────────┴──────┬───────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │       SHARED MEMORY            │
                    │  - Shared Buffers (page cache) │
                    │  - WAL Buffers                 │
                    │  - Lock Tables                 │
                    │  - CLOG (commit log)            │
                    └─────────────────────────────┘
                                   ▲
       ┌───────────┬───────────┬──┴────────┬───────────────┐
       │           │           │            │               │
┌──────▼──────┐┌───▼──────┐┌───▼───────┐┌───▼──────────┐┌───▼─────────────┐
│  WAL Writer ││Background││Checkpointer││  Autovacuum  ││ Stats Collector │
│             ││ Writer   ││            ││   Launcher    ││ (or via shmem   │
│             ││ (BGWriter)│            ││  + workers    ││  in newer PG)   │
└─────────────┘└──────────┘└───────────┘└──────────────┘└─────────────────┘
```

**Key insight for interviews:** All backend processes and background workers communicate through **shared memory**, not message passing — this is what makes shared buffer access, locking, and the commit log (CLOG) work uniformly across all processes.

### 3.2 The Postmaster

**What is it?** The very first process started when Postgres boots (`postgres` binary run in the primary role); it's the supervisor for the entire instance.

**Responsibilities:**
- Listens on the configured TCP port (default 5432) for incoming connections
- On a new connection, **forks** a dedicated backend process to handle it
- Starts and supervises all background processes (WAL Writer, Background Writer, Checkpointer, Autovacuum Launcher, Stats Collector)
- If any backend crashes unexpectedly, the Postmaster detects it, and — because shared memory could be corrupted by an unclean crash — it terminates *all* other backends and restarts the entire server from the last consistent state (this is why a single backend crash can briefly disrupt an entire Postgres instance, unlike a thread crash in a threaded server).

**Real-life analogy:** A restaurant manager (Postmaster) who greets each customer (connection) and assigns a dedicated waiter (backend process) just for them, while separately managing kitchen staff (background workers) who handle prep work independent of any single customer.

**Interview importance:** ⭐⭐⭐⭐ "Why does one Postgres backend crash affect the whole server?" is a strong signal question.

---

### 3.3 Backend Processes

**What is it?** The process forked by the Postmaster to serve exactly one client connection for its lifetime.

**What it does, per query (recall Module 1's lifecycle):** parses, analyzes, plans, and executes SQL entirely within this process, using shared memory for buffer access and locking, and private (local) memory for query-specific work (`work_mem`-bounded structures — sorts, hash tables, etc.).

**Memory-level behavior:** Each backend has:
- Access to **shared memory** (Shared Buffers, WAL buffers, lock tables) — common to all backends
- Its own **local memory** (`work_mem`, `maintenance_work_mem` when running `VACUUM`/`CREATE INDEX`, temp buffers) — private to that backend, freed when the connection closes

**Why this matters operationally:** Total memory usage scales as roughly `shared_buffers + (num_connections × per-connection local memory)`. This is the core mathematical reason why Postgres deployments with thousands of raw client connections (without pooling) can exhaust server memory even with a modest `work_mem` setting — it gets multiplied by every connection running a sort/hash operation simultaneously.

---

### 3.4 Shared Buffers

**What is it?** Postgres's implementation of the Buffer Manager concept from Module 1 — the in-memory cache of disk pages, sized by the `shared_buffers` configuration parameter, living in the shared memory segment accessible to all backend processes.

**Sizing guidance (widely cited community rule of thumb):** ~25% of system RAM, though this varies with workload and the OS page cache's role (Postgres relies on double-buffering: it reads through the OS page cache in addition to its own Shared Buffers, unlike InnoDB which more aggressively tries to bypass OS caching).

**Deep internals** — pin counts, dirty flags, eviction (clock-sweep algorithm specifically, which Postgres uses) — are covered in full in Module 6: Buffer Pool Internals, since that content applies conceptually to both Postgres and InnoDB. This section focuses on Postgres-specific configuration and behavior.

**Postgres-specific behavior:** Uses a **clock-sweep** algorithm (an approximation of LRU, cheaper to maintain in a highly concurrent shared-memory structure than true LRU) for eviction, with a "usage count" per buffer incremented on access and decremented during the sweep.

---

### 3.5 WAL Writer

**What is it?** A background process whose job is to periodically flush WAL (Write-Ahead Log) buffer contents from shared memory to the WAL files on disk, even before a transaction commit forces a flush.

**Why does it exist?** While every `COMMIT` *must* durably flush its WAL record before returning success to the client (the core durability guarantee), constantly flushing tiny amounts of WAL on every single small operation would be inefficient. The WAL Writer process flushes WAL periodically in the background (`wal_writer_delay`, default 200ms) so that:
1. WAL buffers don't fill up and block backends
2. The *amount* of WAL that must be flushed synchronously at actual commit time is smaller, since much of it may already be on disk

**Interaction with `synchronous_commit`:** If `synchronous_commit = off`, Postgres can return "commit successful" to the client *before* the WAL is durably flushed, relying entirely on the WAL Writer to flush it shortly after — trading a small durability window (data loss possible on crash within that window, typically milliseconds) for significantly higher throughput. This is a deliberate, commonly-used performance/durability trade-off in real deployments.

---

### 3.6 Background Writer (BGWriter)

**What is it?** A background process that proactively writes **dirty pages** (pages modified in Shared Buffers but not yet flushed to disk) out to disk gradually, *before* they're forcibly needed.

**Why does it exist?** Without it, dirty pages would only get flushed at checkpoint time (Section 3.7) or when a backend needs to evict a buffer to make room for a new page — and if that evicted page happens to be dirty, the requesting backend itself must block and perform the write, directly slowing down a user's query. The Background Writer smooths this out by writing dirty pages incrementally during quiet moments, so an unlucky backend is less likely to get stuck doing a synchronous write itself.

**Real-life analogy:** Instead of waiting until every table in a restaurant is dirty and needing a rushed, chaotic mass-cleanup, a bussing staff member (BGWriter) continuously clears a few tables at a time in the background, well before the crunch.

**Interview importance:** ⭐⭐⭐ "What's the difference between the Background Writer and the Checkpointer?" is a common, easy-to-get-wrong distinction — see the comparison table below.

---

### 3.7 Checkpointer

**What is it?** A background process that periodically performs a **checkpoint**: it forces *all* currently dirty pages in Shared Buffers to be flushed to disk, and writes a special checkpoint record to the WAL.

**Why does it exist?** Checkpoints bound crash recovery time. On restart after a crash, Postgres only needs to replay WAL records **from the last checkpoint onward** (not from the beginning of time) — because the checkpoint is a guarantee that everything before it is already safely on disk in the data files. More frequent checkpoints → faster crash recovery, but more I/O overhead during normal operation (a classic tunable trade-off via `checkpoint_timeout` and `max_wal_size`).

**Checkpointer vs. Background Writer — the critical distinction:**

| Aspect | Background Writer | Checkpointer |
|---|---|---|
| Scope | Writes *some* dirty pages, gradually, continuously | Writes *all* currently dirty pages, at defined checkpoint intervals |
| Purpose | Smooth out I/O, reduce backend-blocking evictions | Bound crash-recovery time, create a WAL "restart point" |
| Frequency | Continuous, low-rate background activity | Periodic (time-based `checkpoint_timeout` or WAL-volume-based `max_wal_size`) |
| Writes a WAL checkpoint record | No | Yes |

**Interview importance:** ⭐⭐⭐⭐⭐ Extremely common — "explain what a checkpoint is and why it bounds recovery time" is close to a guaranteed question in Postgres-focused interviews.

### 3.8 Autovacuum

**What is it?** A background subsystem (a launcher process plus worker processes) that automatically runs `VACUUM` and `ANALYZE` on tables as needed, without requiring a DBA to schedule them manually.

**Why does it exist?** Because of Postgres's MVCC design (Section 3.11 and full detail in Module 5), `UPDATE` and `DELETE` never immediately remove old row versions — they just mark them as no-longer-current. Old ("dead") row versions accumulate over time and must be reclaimed, or the table bloats indefinitely and query performance degrades. Autovacuum automates this reclamation.

**How it decides when to run:** Each table has autovacuum thresholds (`autovacuum_vacuum_threshold` + `autovacuum_vacuum_scale_factor × row_count`) — once the estimated number of dead tuples crosses this threshold, the Autovacuum Launcher schedules a worker to vacuum that table.

**Why it's critical beyond just space reclamation:** Autovacuum is *also* what advances the **transaction ID (XID) wraparound horizon** — Postgres transaction IDs are a finite 32-bit counter. If a table is never vacuumed for an extremely long time (e.g., a runaway long-held transaction preventing cleanup), the database can approach **transaction ID wraparound**, a serious failure mode where Postgres must eventually refuse new writes to protect data integrity. This makes autovacuum not just a performance optimization but a correctness-preserving safety mechanism.

**Common mistakes:**
- Disabling autovacuum on large, high-churn tables "because it causes I/O spikes" — this defers the problem and makes eventual manual `VACUUM` (or worse, wraparound protection kicking in) far more painful.
- Very long-running transactions (even idle ones left open, "idle in transaction") block vacuum from cleaning up dead tuples newer than that transaction's snapshot, since MVCC visibility rules require preserving row versions any open transaction might still need to see.

**Interview importance:** ⭐⭐⭐⭐⭐ One of THE most commonly asked Postgres-specific questions: "What is autovacuum and why does Postgres need it?"

---

### 3.9 Statistics Collector

**What is it?** The subsystem responsible for gathering runtime statistics — table/index access counts, cache hit ratios, row counts, tuple insert/update/delete counts — used both for the query optimizer's cost estimates and for operational monitoring (`pg_stat_user_tables`, `pg_stat_activity`, etc.).

**Note on evolution:** In older Postgres versions, this was a dedicated separate OS process communicating via UDP messages. In modern Postgres (10+), statistics are maintained via shared memory directly for efficiency, though it's still conceptually referred to as "the statistics collector" / `pg_stat_*` views.

**Relationship to the Optimizer (Module 1, Section 1.4.2):** `ANALYZE` (run automatically by autovacuum, or manually) populates `pg_statistic` with sampled data distribution info (histograms, most-common-values lists, null fractions) — this is the raw material the cost-based optimizer consumes to estimate selectivity and choose plans.

### 3.10 TOAST (Revisited in PostgreSQL-Specific Depth)

Module 2 introduced TOAST conceptually. Here's the Postgres-specific mechanics:

**The four TOAST strategies per column** (configurable via `ALTER TABLE ... SET STORAGE`):

| Strategy | Behavior |
|---|---|
| `PLAIN` | Never compress or move out-of-line (used for fixed-size types like `int4` where it wouldn't help) |
| `EXTENDED` | Try compression first; if still too large, move out-of-line (the default for most variable-length types like `text`) |
| `EXTERNAL` | Move out-of-line without attempting compression (useful when you know the data won't compress well, e.g., already-compressed binary data, and want faster substring access since out-of-line-but-uncompressed data supports partial reads) |
| `MAIN` | Prefer compression, avoid moving out-of-line unless absolutely necessary |

**Interview importance:** ⭐⭐⭐ Knowing that TOAST strategy is configurable per column (not just an opaque automatic behavior) signals deeper Postgres fluency.

### 3.11 Tuple Versioning & MVCC Foundations (Postgres-Specific Preview)

*(Full MVCC treatment — read views, snapshot visibility rules, version chains — is Module 5. This section covers only the Postgres-specific physical mechanics that set up that discussion.)*

Recall from Module 2's tuple header: every Postgres tuple carries `xmin` (the XID that created this row version) and `xmax` (the XID that deleted/updated it, or 0 if still current).

**What happens on `UPDATE` in Postgres:** Postgres does **not** modify a row in place. Instead:
1. The old tuple's `xmax` is set to the updating transaction's XID (marking it as superseded).
2. A brand new tuple is inserted (possibly on the same page, possibly elsewhere) with `xmin` set to the updating transaction's XID, containing the new column values.
3. Any indexes pointing to the row generally need a new entry pointing at the new tuple's location too — **unless** the HOT optimization applies (next section).

```
BEFORE UPDATE:
┌─────────────────────────────────┐
│ xmin=100  xmax=0     salary=50000│  ← current version
└─────────────────────────────────┘

AFTER "UPDATE ... SET salary = 55000" (by transaction 105):
┌─────────────────────────────────┐
│ xmin=100  xmax=105   salary=50000│  ← old version (now dead once no txn needs it)
├─────────────────────────────────┤
│ xmin=105  xmax=0     salary=55000│  ← new current version
└─────────────────────────────────┘
```

This is precisely *why* Postgres needs VACUUM: that old `xmin=100,xmax=105` version is now dead weight, taking up page space until vacuum reclaims it.

---

### 3.12 HOT Updates (Heap-Only Tuples)

**What is it?** An optimization avoiding the "need to update every index" cost described above, when possible.

**The problem HOT solves:** In the naive update flow above, if a table has 5 indexes, updating one row could mean writing 5 new index entries — even though only one column changed and none of the indexed columns were touched at all. That's wasteful.

**How HOT works:** If (a) the new tuple version fits on the **same page** as the old one, and (b) **none of the updated columns are part of any index**, then Postgres can create the new tuple version on the same page and link it from the old version via an internal chain, **without touching any indexes at all**. The index entry still points at the *original* location, and Postgres follows the in-page HOT chain to find the current live version.

```
Index entry ──► Page 42, slot 3
                       │
                       ▼
              ┌─────────────────┐
              │ old version       │  (xmax set, HOT-chain pointer →)
              │  (redirects to)   │──┐
              └─────────────────┘  │
                                     ▼
              ┌─────────────────┐
              │ new version        │  ← actual current data, but NOT
              │  (HOT tuple)       │     independently indexed
              └─────────────────┘
```

**Why `FILLFACTOR` matters here:** HOT requires the new version to fit on the *same page*. If a page is packed to 100% full, there's no room, and HOT can't apply — this is exactly why setting `FILLFACTOR` below 100 (e.g., 90) on frequently-updated tables deliberately reserves headroom to make HOT updates possible more often.

**Performance implication:** HOT dramatically reduces index bloat and write amplification for update-heavy workloads on tables with several indexes, as long as updates don't touch indexed columns.

**Interview importance:** ⭐⭐⭐⭐ A very common "advanced Postgres" interview differentiator question.

---

### 3.13 Visibility Map

**What is it?** A small, compact auxiliary bitmap (one bit — or two, in newer versions — per page) tracking whether **all** tuples on a given heap page are known to be visible to all current and future transactions (i.e., no dead/uncommitted versions remain on that page).

**Why does it exist?** Two major performance uses:
1. **Index-only scans:** If a query can be satisfied entirely from an index (all needed columns are in the index), Postgres would normally still need to visit the heap page to double-check MVCC visibility of each row — *unless* the visibility map says the whole page is "all visible," in which case that heap visit can be skipped entirely, turning an index-plus-heap-lookup into a pure index-only scan.
2. **VACUUM efficiency:** VACUUM can skip scanning pages already marked all-visible (nothing to clean up there), dramatically speeding up vacuum on large, mostly-static tables where only a small fraction of pages have recently changed.

**Interview importance:** ⭐⭐⭐⭐ "How does an index-only scan avoid visiting the heap?" — the visibility map is the precise answer.

---

### 3.14 Free Space Map (Recap in Context)

Already introduced conceptually in Module 2, Section 2.7 — worth reiterating here as part of Postgres's specific background-process ecosystem: the FSM is a per-relation auxiliary file (`<relfilenode>_fsm`) consulted by backends on `INSERT` to find pages with room, and updated by both regular DML operations and by VACUUM as it reclaims space.

### 3.15 VACUUM Internals

**What does `VACUUM` actually do, mechanically?**

1. **Scan** the table's pages (skipping all-visible pages per the Visibility Map, unless `VACUUM FULL` or a full scan is forced).
2. For each page, identify **dead tuples** — row versions whose `xmax` is older than the oldest transaction any currently-active snapshot might still need to see (this boundary is often called the "OldestXmin").
3. Remove dead tuples' space from the page (compacting live tuples), updating the Free Space Map accordingly.
4. **Clean up dead index entries** pointing to now-removed tuples.
5. Update the **Visibility Map**, marking newly all-visible pages.
6. Update table-level statistics used for planning (`ANALYZE`, which Autovacuum often bundles with `VACUUM`).
7. Advance the table's tracked "frozen" XID horizon as needed to protect against transaction ID wraparound (via **freezing** — rewriting very old `xmin` values to a special "frozen" marker meaning "always visible," so the 32-bit XID counter comparison never has to worry about this row again).

**`VACUUM` vs. `VACUUM FULL`:**

| Aspect | Plain `VACUUM` | `VACUUM FULL` |
|---|---|---|
| Locking | Doesn't block reads/writes (uses a lightweight lock) | Takes an exclusive lock — blocks all access to the table |
| Space returned to OS | Usually not (space is marked reusable *within* the table, not returned to the filesystem) | Yes — rewrites the entire table into a new, compact file, then swaps it in |
| Typical use | Regular, automated maintenance (via autovacuum) | Rare, manual, for reclaiming severe bloat |

**Why plain VACUUM doesn't shrink files on disk:** It marks space as reusable for future inserts within the table's own free space map, but doesn't physically move data to release trailing empty pages back to the OS — doing so would require exclusive locks and data movement, which is exactly what `VACUUM FULL` does at a much higher cost.

**Real-life analogy:** Plain `VACUUM` is like tidying a warehouse — freeing up empty crates in-place so new items can reuse that space, without demolishing and rebuilding the warehouse. `VACUUM FULL` is emptying the entire warehouse and rebuilding it perfectly compact, which requires shutting it down temporarily.

**Interview importance:** ⭐⭐⭐⭐⭐ Extremely high-yield — expect deep questions on VACUUM in any serious Postgres interview.

### 3.16 Complete Postgres Write Path (Tying It All Together)

```
Client sends: UPDATE employees SET salary = salary * 1.1 WHERE id = 101;

1. Backend process (this connection's dedicated process) parses/plans/executes
2. Backend acquires row-level lock context (MVCC handles most read/write conflicts,
   but write-write conflicts on the same row still need coordination)
3. Backend writes WAL record for the change → into WAL buffers (shared memory)
4. Backend modifies the page in Shared Buffers (old tuple xmax set, new tuple inserted,
   HOT chain used if applicable) → page marked dirty
5. On COMMIT: WAL record flushed to disk (fsync) — this is the durability point
6. Backend returns "success" to client
   ... time passes ...
7. Background Writer opportunistically flushes the now-dirty page to disk
   ... more time passes ...
8. Checkpointer eventually forces this (and all other) dirty pages to disk,
   writes a checkpoint WAL record
   ... even more time passes ...
9. Autovacuum eventually notices dead tuples (the old, superseded row version)
   have accumulated past the threshold, vacuums the page, updates the Visibility Map
```

This nine-step flow is the single best "walk me through what happens" answer you can give in a Postgres-focused interview.

### 3.17 Chapter Summary

- Postgres uses a **process-per-connection** model, coordinated via **shared memory** (Shared Buffers, WAL buffers, locks, CLOG) and supervised by the **Postmaster**.
- Several dedicated background processes cooperate: **WAL Writer** (periodic WAL flush), **Background Writer** (gradual dirty page flush), **Checkpointer** (periodic full flush + WAL checkpoint record, bounds recovery time), and **Autovacuum** (reclaims dead tuples, prevents XID wraparound, updates statistics).
- Postgres never updates rows in-place at the MVCC level — `UPDATE` creates a new tuple version and marks the old one's `xmax`, which is exactly why dead tuples accumulate and VACUUM is required.
- **HOT updates** avoid unnecessary index writes when updated columns aren't indexed and the new version fits on the same page — `FILLFACTOR` tuning directly affects how often this optimization can fire.
- The **Visibility Map** enables both faster VACUUM (skip all-visible pages) and **index-only scans** (skip heap visibility checks entirely).
- Plain `VACUUM` reclaims space for reuse without blocking; `VACUUM FULL` physically compacts the file but requires an exclusive lock.

### 3.18 Cheat Sheet

```
Postmaster        → supervises everything, forks one backend per connection
Backend process   → handles one client connection's full query lifecycle
Shared Buffers    → Postgres's buffer pool (shared memory, all backends)
WAL Writer        → periodic WAL flush (independent of commit-time flush)
Background Writer → gradual dirty-page flush (smooths I/O)
Checkpointer      → periodic FULL dirty-page flush + WAL checkpoint record
                     (bounds crash-recovery replay time)
Autovacuum        → reclaims dead tuples, updates stats, prevents XID wraparound
Visibility Map    → tracks all-visible pages → enables index-only scans + VACUUM skip
HOT Update        → same-page update, no indexed column changed → skips index writes
VACUUM            → in-place space reclaim, non-blocking, doesn't shrink files
VACUUM FULL       → full rewrite + compaction, exclusive lock, shrinks files
```
