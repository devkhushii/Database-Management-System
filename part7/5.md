# DBMS Handbook — Part 7: Indexing, File Organization & Storage Structures
## Module 5: Index Fundamentals

> **Where we are:** Modules 1–4 built the physical foundation — pages, records, file organization, buffer pools. Module 5 introduces the single most important performance tool in all of relational database engineering: **the index**. This module covers *what* indexes are and the full taxonomy of index types; Module 6 (B+ Trees) and Module 7 (Hashing) cover *how* they're actually implemented under the hood.

---

## 5.0 Why This Module Exists

Recall Module 3's central fact: a heap file, with no index, requires an **O(n) full table scan** to find a single row. An index exists to turn that O(n) search into an **O(log n)** (or better) search, at the cost of extra storage and extra maintenance work on every write.

> **The one-sentence definition of an index you should never forget:**
> An index is a **separate, auxiliary data structure** that maps key values to the physical location of the rows containing them, trading storage space and write overhead for dramatically faster reads.

---

## 5.1 What is an Index?

### Definition

An **index** is an ordered (or otherwise efficiently searchable) auxiliary structure built on one or more columns of a table, storing (key value → Record Identifier or row location) pairs, so that queries filtering or sorting on that column can avoid scanning the entire table.

### Real-life analogy

A book's **index page** at the back doesn't contain the book's content — it contains **(topic → page number)** pairs. You don't read the whole book to find "mitochondria"; you flip to the index, find "mitochondria — page 214," and jump directly there. A database index works identically: it stores (key → RID) pairs, letting the engine "jump directly" to the relevant page(s) instead of reading the entire table.

### How does it work — conceptual flow

```
Query: SELECT * FROM employees WHERE emp_id = 501;

WITHOUT INDEX:                          WITH INDEX on emp_id:
Scan every page of employees table       1. Look up 501 in the index structure (e.g., B+ Tree)
  Page 1: check every row                     -> O(log n) traversal
  Page 2: check every row                2. Index returns RID: (Page 44, Slot 2)
  Page 3: check every row  <- FOUND      3. Fetch exactly Page 44 directly
  ... (potentially all N pages)          4. Return the row
  = O(n) pages read                         = O(log n) + 1 page read
```

---

## 5.2 Why Indexes Exist

### The problem they solve

Without an index, **every** filter (`WHERE`), join condition, and sort (`ORDER BY`) requires reading every row of a table to know whether it qualifies. As tables grow into millions/billions of rows, this becomes catastrophically slow — turning a query that should take milliseconds into one taking minutes or hours.

### The trade-off they introduce

Indexes are never free. Every index:

1. **Consumes extra storage** — a separate structure, often nearly as large as the underlying data for wide indexes.
2. **Slows down writes** — every `INSERT`/`UPDATE`/`DELETE` must also update every relevant index, not just the underlying heap/clustered table.
3. **Requires maintenance** — indexes can become fragmented/bloated over time (fully covered in Modules 11–12).

> This trade-off — **read speed vs write cost + storage** — is the single most repeated theme across the rest of Part 7, and directly motivates Module 12 ("Why Too Many Indexes Are Bad").

## 5.3 Clustered Index

### What is it?

A **clustered index** determines the *physical* storage order of the table's rows — the table's data itself is organized/sorted according to the index key (directly connecting back to Module 3, Section 3.4's "Clustered Files").

### Key rule

**A table can have at most one clustered index**, because rows can only be physically ordered one way at a time.

### How it works — InnoDB (mandatory)

Every InnoDB table's data pages **are** the leaf level of a B+ Tree built on the primary key — this IS the clustered index; there's no separate step to "add" one; declaring a primary key automatically makes it the clustering key (or, if no primary key exists, InnoDB clusters by a hidden internal row ID instead).

### How it works — PostgreSQL (no true persistent clustered index)

PostgreSQL does not maintain an automatically-updated clustered index. The one-time `CLUSTER` command (Module 3, Section 3.4) can physically reorder a heap table to match a chosen index's order, but subsequent writes go back to unordered heap placement — meaning PostgreSQL indexes (including the primary key's implementing index) are effectively always "non-clustered" in an ongoing sense.

### Interview Importance
⭐⭐⭐⭐⭐ — "Why can a table have only one clustered index?" and "Is PostgreSQL's primary key a clustered index?" (answer: not in the persistent, automatically-maintained sense that InnoDB provides) are extremely common questions.

---

## 5.4 Non-Clustered Index

### What is it?

A **non-clustered index** is a separate structure from the table's physical row storage — it stores (key → RID) pairs, but does **not** dictate the physical order of the underlying rows. Looking up a row via a non-clustered index requires: (1) traverse the index to find the RID, then (2) fetch the actual row using that RID — **two logical steps**, sometimes called a "bookmark lookup."

### Diagram

```
Non-Clustered Index (on 'city' column):        Actual Table Data (heap, unordered):
   [Bangalore] -> RID(Page 8, Slot 1)           Page 8:  [row: id=9, city=Bangalore, ...]
   [Chennai]   -> RID(Page 3, Slot 4)           Page 3:  [row: id=2, city=Chennai, ...]
   [Delhi]     -> RID(Page 12, Slot 0)          Page 12: [row: id=7, city=Delhi, ...]

Lookup 'Bangalore': traverse index -> get RID(Page 8, Slot 1) -> fetch Page 8 -> return row
```

### PostgreSQL vs MySQL

| | PostgreSQL | InnoDB |
|---|---|---|
| Every index (except the implicit clustering structure) | Non-clustered — points via `ctid` (Module 2) back into the heap | Non-clustered — but points via the **primary key value**, not a raw RID (Module 2's "double lookup" discussion), because InnoDB's actual data lives in the primary key's clustered B+ Tree, not in fixed heap pages |

## 5.5 Dense Index vs Sparse Index

### Dense Index

**Definition:** A dense index has **one index entry for every single row** in the table, regardless of whether the underlying file is sorted by that key.

```
Dense Index:
Key: 1 -> RID(P1,S0)
Key: 2 -> RID(P1,S1)
Key: 3 -> RID(P2,S0)
Key: 4 -> RID(P2,S1)
   (every row has its own entry)
```

### Sparse Index

**Definition:** A sparse index has **one entry per page (or per block of rows)**, not per row — it only works correctly when the underlying data is physically sorted by that key, since finding a specific row requires jumping to the right page via the sparse entry, then scanning within that page.

```
Sparse Index (data file MUST be sorted by key):
Key: 1 (first key on Page 1) -> Page 1
Key: 3 (first key on Page 2) -> Page 2
   (only one entry per page; page's remaining rows found by scanning within it)
```

### Comparison Table

| Aspect | Dense Index | Sparse Index |
|---|---|---|
| Entries | One per row | One per page/block |
| Index size | Larger | Smaller |
| Requires sorted data file? | No | Yes |
| Lookup cost | Direct entry found, then one page fetch | Entry found, then scan within the target page |

### Real-world relevance

Most production B+ Tree indexes (Module 6) behave more like a **dense** index at the leaf level (an entry per row/key), though InnoDB's clustered index leaf level, being the actual sorted data, has properties resembling a sparse index's underlying assumption (sorted-by-key data) combined with a dense structure (every row present, since it IS the data).

### Interview Importance
⭐⭐⭐ — GATE and academic interviews frequently test dense vs sparse index definitions and their storage trade-off directly.

## 5.6 Composite Index

### What is it?

A **composite index** (also called a multi-column or concatenated index) is built on **two or more columns together**, with the columns' order in the index definition mattering enormously for which queries can use it efficiently.

### The Leftmost Prefix Rule (critical, high-frequency interview topic — full detail in Module 10)

A composite index on `(last_name, first_name, city)` can efficiently support queries filtering on:
- `last_name` alone
- `last_name AND first_name`
- `last_name AND first_name AND city`

But **cannot** efficiently use the index for a query filtering only on `first_name` or only on `city`, because the index is physically sorted first by `last_name`, then by `first_name` within each `last_name` group, then by `city` within each `first_name` group — skipping the leftmost column breaks the ability to binary-search/traverse efficiently.

```
Composite Index on (last_name, first_name):
  Khan,   Aisha  -> RID
  Khan,   Ravi   -> RID
  Sharma, Divya  -> RID
  Sharma, Rohan  -> RID

Query WHERE last_name='Sharma'                    -> Efficient (leftmost prefix match)
Query WHERE last_name='Sharma' AND first_name='Rohan' -> Efficient (full match)
Query WHERE first_name='Rohan'                    -> NOT efficient (skips leftmost column)
```

> **Full leftmost-prefix-rule practice problems and optimizer interaction are in Module 10.** This module only establishes the structural definition.

### Interview Importance
⭐⭐⭐⭐⭐ — The leftmost prefix rule is one of THE most frequently tested practical SQL performance concepts in real interviews (Amazon, Flipkart, Razorpay-style backend interviews included).

## 5.7 Covering Index

### What is it?

A **covering index** is an index that contains **every column** referenced by a particular query (in its `SELECT`, `WHERE`, `JOIN`, and `ORDER BY` clauses) — meaning the query can be answered **entirely from the index itself**, without ever touching the underlying table/heap data at all.

### Why it matters (performance impact)

Normally, a non-clustered index lookup requires: (1) find the RID in the index, (2) fetch the actual row from the table (an extra page read, Section 5.4). A covering index **eliminates step 2 entirely** — this is called an **Index-Only Scan** (fully explained in Module 10), and can be a dramatic performance win, especially for tables with many rows per page.

### Example

```sql
-- Index: CREATE INDEX idx_covering ON orders(customer_id, order_date, total_amount);

-- This query is FULLY covered by the index above:
SELECT order_date, total_amount FROM orders WHERE customer_id = 501;
-- customer_id (filter), order_date + total_amount (selected columns) -- ALL present in the index
-- -> Index-Only Scan possible, no heap/table fetch needed
```

### PostgreSQL Note — Visibility Map interaction

Even with a covering index, PostgreSQL's MVCC design (Part 9) means the engine must also confirm the row version is visible to the current transaction — this check can sometimes still require consulting the heap, **unless** the page is marked all-visible in PostgreSQL's **Visibility Map** (introduced briefly here, fully detailed in Module 9). This is a subtle but real caveat interviewers at a Senior level may probe.

### Interview Importance
⭐⭐⭐⭐⭐ — "What is a covering index and how does it enable an index-only scan?" is asked very frequently, and the PostgreSQL visibility-map caveat above separates a good answer from a great one.

## 5.8 Primary Index vs Secondary Index

### Definitions

- **Primary Index**: An index built on the table's primary key (or, in some classical textbook definitions, the index built on whatever key determines the file's physical ordering — closely related to, but not always identical terminology to, "clustered index" depending on the textbook).
- **Secondary Index**: Any index built on a non-primary-key column (or set of columns) — always non-clustered, always requires the extra lookup step back to the actual row data.

### Relationship to Clustered/Non-Clustered terminology

| Term Pair | Relationship |
|---|---|
| Primary Index | Often synonymous with "the index enforcing/matching the primary key," commonly (but not always, depending on engine) the clustered index |
| Secondary Index | Always non-clustered by definition — there can be many secondary indexes per table |

> Different textbooks and different engines use "primary index" and "clustered index" with slightly different emphasis — GATE-style materials tend to treat "primary index" as the classical file-organization term (index on the ordering key of a sequentially-ordered file), while industry engineers usually just say "the primary key index" or "clustered index" depending on context. Be prepared to clarify terminology if an interviewer's phrasing is ambiguous.

## 5.9 Unique Index

### What is it?

A **unique index** enforces that no two rows can have the same value for the indexed column(s) (or combination, for composite unique indexes), in addition to providing the standard lookup-acceleration benefit of any index.

### How it works

On every `INSERT`/`UPDATE` affecting the indexed column(s), the engine checks the index structure for an existing matching key **before** allowing the write to complete — if found, the write is rejected with a uniqueness-violation error.

### Relationship to Primary Keys

A `PRIMARY KEY` constraint is implemented, under the hood, as a **unique index** (plus a `NOT NULL` constraint) — this is true in both PostgreSQL and MySQL/InnoDB. Declaring `UNIQUE` on a column and declaring it `PRIMARY KEY` both create a unique index; the primary key additionally forbids `NULL` and (in InnoDB) determines clustering.

### Interview Importance
⭐⭐⭐⭐ — "Is a primary key just a unique index?" — Answer: functionally very close (unique index + NOT NULL), with the added architectural role of determining clustering in InnoDB specifically.

## 5.10 Partial Index

### What is it?

A **partial index** is built on only a **subset of rows** matching a specified condition, rather than indexing every row in the table.

### Why does it exist?

If a query pattern only ever cares about a small, well-defined subset of rows (e.g., `WHERE status = 'active'` out of a table where 95% of rows are `'archived'`), indexing the entire table wastes space and slows down writes to rows that will never benefit from that index.

### Example

```sql
-- PostgreSQL supports this directly:
CREATE INDEX idx_active_orders ON orders(customer_id) WHERE status = 'active';

-- This index is only consulted for queries filtering on status='active',
-- and is much smaller than a full index on all rows.
```

### PostgreSQL vs MySQL

| | PostgreSQL | MySQL (InnoDB) |
|---|---|---|
| Native partial index support | Yes (`WHERE` clause on `CREATE INDEX`) | Not natively supported the same way — workarounds include generated/virtual columns with conditional expressions indexed instead |

### Interview Importance
⭐⭐⭐⭐ — Partial indexes are a strong signal of real production PostgreSQL experience; a common interview scenario is: "You have a `is_deleted` soft-delete flag where 99% of rows are deleted — how would you index this table efficiently?"

## 5.11 Expression / Functional Index

### What is it?

An **expression index** (also called a **functional index**) is built not on a raw column value, but on the **result of a function or expression** applied to one or more columns — enabling fast lookups on queries that filter using that same expression.

### Why does it exist?

A normal index on `email` cannot accelerate `WHERE LOWER(email) = 'khushi@example.com'`, because the index stores raw (unmodified) values, and the query is filtering on a *transformed* value. An expression index solves this by storing the transformed value directly.

### Example

```sql
CREATE INDEX idx_lower_email ON users (LOWER(email));

-- Now this query CAN use the index efficiently:
SELECT * FROM users WHERE LOWER(email) = 'khushi@example.com';
```

### Common Mistake
- Creating a normal index on `email` and expecting it to help a query using `LOWER(email)` in the `WHERE` clause — it will **not** be used by the optimizer, because the stored index values don't match the filtered expression's output. This exact scenario is a very frequent real-world "why isn't my index being used?" debugging story.

### Interview Importance
⭐⭐⭐⭐ — Understanding why a plain index doesn't help a wrapped-column filter, and how an expression index fixes it, is a strong practical signal in interviews.

## 5.12 Invisible Index (Overview)

### What is it?

An **invisible index** is maintained (kept up to date on every write) but is **hidden from the query optimizer** by default — the optimizer will not consider using it unless explicitly told to, allowing engineers to test the impact of "removing" an index without actually dropping it (a safe rollback path if dropping the index turns out to hurt some query).

### Support

MySQL supports invisible indexes explicitly (`ALTER TABLE ... ALTER INDEX ... INVISIBLE`). PostgreSQL does not have a directly equivalent native feature (workarounds involve disabling specific index usage via planner settings, but not a true persistent "invisible" flag on the index itself).

*(This is an overview only, per this module's intended depth — deeper operational usage patterns for invisible indexes as a safe index-removal strategy are referenced again in Module 11: Index Maintenance.)*

## 5.13 Bitmap Index (Overview)

### What is it?

A **bitmap index** represents, for each distinct value of a column, a bitmap (a bit-array the length of the table) where a `1` at position *i* means row *i* has that value. Bitmap indexes are extremely space-efficient and fast for columns with **low cardinality** (few distinct values, e.g., `gender`, `status` with only a handful of possible values), and support extremely fast set operations (AND/OR) across multiple bitmap indexes for combined filters.

### Why they're not the default for high-cardinality columns

For a column with millions of distinct values (e.g., `email`), a bitmap index would need millions of separate bitmaps — completely impractical. Bitmap indexes are specifically a **low-cardinality** tool.

### Industry Usage

Oracle supports bitmap indexes natively and they're heavily used in **data warehousing / OLAP** contexts (star-schema fact tables with low-cardinality dimension columns). PostgreSQL and MySQL do not offer persistent bitmap indexes as a storage structure, but PostgreSQL's query executor does use **dynamically-constructed, in-memory bitmaps** during execution (the "Bitmap Heap Scan" / "Bitmap Index Scan" plan nodes — fully explained in Part 8: Query Processing) — an important, frequently confused distinction: PostgreSQL's bitmap *scan* is an execution strategy, not a persistent index *type*.

*(Overview only, per this module's scope — this is revisited from the query-optimizer's perspective in Module 10 and Part 8.)*

### Interview Importance
⭐⭐⭐⭐ — "What's the difference between Oracle's bitmap index and PostgreSQL's Bitmap Heap Scan?" is an excellent question that separates surface-level knowledge from real engine understanding: one is a stored index type, the other is a runtime execution strategy.

## 5.14 How Indexes Improve Search Performance — Tying It Together

| Without Index | With Index |
|---|---|
| O(n) full scan for point lookup | O(log n) traversal (B+ Tree, Module 6) or O(1) average (hash, Module 7) |
| O(n) for range queries | O(log n) + sequential leaf scan for sorted structures |
| No support for enforcing uniqueness efficiently | Unique index enforces + accelerates in one structure |
| Every row physically checked for a filter condition | Only matching keys' RIDs retrieved, then targeted page fetches |

### The universal cost model

Every index type discussed in this module ultimately reduces to the same underlying trade-off first introduced in Section 5.2:

```
Faster Reads  <---------- TRADE-OFF ----------> Slower Writes + More Storage
```

Choosing which columns to index, and which index type to use, is fundamentally about which side of that trade-off your workload needs more.

## 5.15 Chapter Summary

- An **index** is an auxiliary (key → RID) structure that avoids full table scans, at the cost of storage and write overhead.
- **Clustered indexes** determine physical row order (max one per table); InnoDB always has one (mandatory, on primary key); PostgreSQL has none in a persistent, automatically-maintained sense.
- **Non-clustered indexes** require an extra lookup step back to the row (`ctid` in PostgreSQL, primary key value in InnoDB).
- **Dense indexes** have one entry per row; **sparse indexes** have one entry per page and require sorted underlying data.
- **Composite indexes** are governed by the **leftmost prefix rule** — one of the most important practical SQL performance facts in this entire handbook.
- **Covering indexes** let a query be answered entirely from the index (**Index-Only Scan**), skipping the heap fetch — subject to PostgreSQL's visibility-map caveat.
- **Primary/Secondary indexes**, **Unique indexes** (which underlie every `PRIMARY KEY`), **Partial indexes** (subset of rows, strong PostgreSQL feature), **Expression/Functional indexes** (index a transformed value), and brief overviews of **Invisible indexes** (MySQL-specific, safe rollback tool) and **Bitmap indexes** (Oracle's stored index type vs PostgreSQL's runtime Bitmap Scan) round out the full taxonomy.

## 5.16 Cheat Sheet

```
Index               = auxiliary (key -> RID) structure, avoids full scans
Clustered Index      = determines physical row order; max 1 per table
                       InnoDB: mandatory, automatic | PostgreSQL: no persistent equivalent
Non-Clustered Index  = separate structure + extra lookup step back to row data
Dense Index          = 1 entry per ROW
Sparse Index         = 1 entry per PAGE, requires sorted data
Composite Index      = multi-column; LEFTMOST PREFIX RULE governs usability
Covering Index        = contains all columns a query needs -> Index-Only Scan
Primary Index        = index on/related to primary key
Secondary Index      = any non-primary-key index; always non-clustered
Unique Index          = enforces no-duplicates; PRIMARY KEY = unique index + NOT NULL
Partial Index        = indexes a subset of rows via WHERE clause (strong in PostgreSQL)
Expression Index     = indexes a function's output, e.g. LOWER(email)
Invisible Index       = maintained but hidden from optimizer (MySQL feature, safe rollback)
Bitmap Index          = per-distinct-value bitmap; Oracle = stored index; PostgreSQL = runtime scan strategy only
```

**Q1.** How many clustered indexes can a single table have?
A) As many as needed  B) Exactly one  C) Zero always  D) One per column
