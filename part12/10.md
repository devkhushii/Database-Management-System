# Part 12 — Production Database Engineering & DBA Mastery

## Module 10: Database Selection

> **Recap:** Modules 1-9 assumed you already had a database engine chosen and running. This module steps back to the decision that precedes all of them: **which database should you even use?** This is one of the highest-leverage decisions in system design — get it right and everything downstream is easier; get it wrong and you'll be fighting the tool for years.

### 10.0 Why This Module Exists

**Real-world analogy:** Choosing a database is like choosing a vehicle. A sports car (Redis) is blazing fast but can't carry cargo. A cargo truck (Cassandra) hauls enormous loads but corners badly (poor ad-hoc query flexibility). A sedan (PostgreSQL) is the versatile daily driver that handles most trips well without being the best at any one extreme. **There is no universally "best" database** — only the best fit for a specific workload's shape, and this module builds the judgment to make that call, one of the most common and highest-value System Design interview topics at every seniority level.

---

### 10.1 The Fundamental Question: What Shape Is Your Data and Access Pattern?

Before comparing specific engines, always ask:

1. **What's the data shape?** Tabular/relational? Document-like? Key-value? Graph? Time-series? Full-text?
2. **What's the consistency requirement?** Strong (must always see the latest write) or eventual (can tolerate brief staleness)?
3. **What's the read/write ratio and access pattern?** Point lookups by key? Complex multi-table joins? Range scans? Aggregations?
4. **What's the scale?** Rows/documents count, QPS, geographic distribution?
5. **What's the team's operational capacity?** (Module 9 recap — operational complexity is a real cost)

### 10.2 Relational Databases (SQL)

#### 10.2.1 PostgreSQL

**When to choose it:** The default, versatile choice for most new applications. Strong ACID guarantees, rich feature set (JSONB for semi-structured data, full-text search, `PostGIS` for geospatial, extensibility via extensions), excellent standards compliance, and a strong open-source ecosystem.

**Strengths:** Extensibility, JSONB (blends relational + document flexibility), strong consistency, advanced indexing (GiST, GIN, BRIN), mature replication.
**Weaknesses:** Native horizontal write scaling requires extensions/external tools (Citus) or migrating to a distributed SQL engine (Section 10.5); vertical scaling has a ceiling.

#### 10.2.2 MySQL

**When to choose it:** Web applications (historically the "M" in LAMP), read-heavy workloads, when the team has deep MySQL operational expertise, or when using platforms/frameworks with strong MySQL-first support (e.g., WordPress).

**Strengths:** Extremely mature, huge community, excellent read-replica scaling, `InnoDB` storage engine is robust and well-understood, generally simpler operationally than PostgreSQL for basic use cases.
**Weaknesses:** Historically weaker standards compliance and fewer advanced features than PostgreSQL (gap has narrowed significantly in MySQL 8.0+); native multi-master write scaling has similar limitations to PostgreSQL.

#### 10.2.3 MariaDB

**When to choose it:** A MySQL-compatible fork favored when avoiding Oracle ownership of MySQL is a priority, or for specific storage engines (e.g., `ColumnStore` for analytics) not available in stock MySQL.

**Strengths:** Drop-in MySQL compatibility (mostly), fully open-source governance, additional storage engine options.
**Weaknesses:** Smaller ecosystem/community than MySQL itself; diverging feature sets over time require care during migration between the two.

#### 10.2.4 SQLite

**When to choose it:** Embedded applications, mobile apps, local/desktop software, small-scale single-user or single-process scenarios, or as a lightweight test/dev database (with the caveat from Module 1 that dev/prod parity still matters).

**Strengths:** Zero-configuration, serverless (the entire database is a single file), extremely lightweight, ubiquitous (ships inside countless applications and OSes).
**Weaknesses:** **Not designed for concurrent multi-user production write workloads** (traditionally one writer at a time, though WAL mode improves concurrency); no built-in replication/clustering; wrong choice for any typical server-side production web application backend.

#### 10.2.5 Oracle Database

**When to choose it:** Large enterprises, especially in finance/banking/government, with existing Oracle investment, needing the most mature enterprise features (RAC for active-active clustering, advanced partitioning, mission-critical support contracts).

**Strengths:** Extremely mature, feature-rich (RAC, Data Guard, Advanced Compression, Real Application Testing), strong vendor support/SLAs, proven at the largest enterprise scales.
**Weaknesses:** Very high licensing cost, operational complexity, and a heavier footprint than open-source alternatives — often overkill for startups/mid-size companies.

#### 10.2.6 SQL Server

**When to choose it:** Microsoft-centric enterprise environments (.NET applications, Windows Server infrastructure, existing Microsoft ecosystem investment), strong integration with Azure and enterprise BI tools (Power BI, SSRS).

**Strengths:** Excellent tooling (SSMS), strong Windows/.NET integration, Always On Availability Groups for HA (Module 6 recap), solid enterprise feature set.
**Weaknesses:** Licensing cost, historically Windows-centric (Linux support since 2017 has improved this), less common choice outside Microsoft-centric shops.

**Relational Database Comparison Table**

| Aspect | PostgreSQL | MySQL | MariaDB | Oracle | SQL Server |
|---|---|---|---|---|---|
| License cost | Free | Free (Community) | Free | High (enterprise licensing) | Free (Developer) to High (Enterprise) |
| Best for | General-purpose, feature-rich apps | Web apps, read-heavy | MySQL-compatible, open governance | Large enterprise, mission-critical | Microsoft/.NET ecosystems |
| JSON support | Excellent (JSONB) | Good | Good | Good | Good |
| Extensibility | Excellent (extensions) | Limited | Moderate | Very high (enterprise features) | High (enterprise features) |
| Native horizontal write scaling | Limited (needs Citus/external) | Limited | Limited | RAC (mature, but complex/costly) | Limited |

### 10.3 NoSQL Databases

#### 10.3.1 MongoDB (Document Store)

**When to choose it:** Semi-structured or rapidly evolving schemas, document-shaped data (nested objects naturally map to application objects), content management, catalogs, applications favoring developer velocity over strict schema enforcement.

**Strengths:** Flexible schema, natural fit for JSON-like application data, horizontal scaling via native sharding, rich query language for a NoSQL store.
**Weaknesses:** Historically weaker multi-document transaction support (much improved in recent versions), joins across collections are less natural than SQL joins, easy to accidentally create a poorly-normalized, hard-to-query data model without discipline.

#### 10.3.2 Cassandra (Wide-Column Store)

**When to choose it:** Massive write throughput requirements, multi-datacenter active-active with tunable consistency, time-series data, workloads that are predominantly writes with simple key-based reads (e.g., sensor data, event logging, messaging systems).

**Strengths:** Linear horizontal scalability, no single point of failure (masterless architecture), excellent write performance, tunable consistency per-query.
**Weaknesses:** Query flexibility is limited — you must design your table schema around your query patterns upfront (query-first modeling, very different mindset from relational normalization); ad-hoc queries/joins are essentially unsupported; eventual consistency requires careful application-level handling.

#### 10.3.3 Redis (Key-Value / In-Memory)

**When to choose it:** Caching (Module 5 recap), session storage, real-time leaderboards, rate limiting, pub/sub messaging, any workload needing sub-millisecond latency on simple key-based access patterns.

**Strengths:** Extremely fast (in-memory), rich data structures (lists, sets, sorted sets, hashes, streams), simple operational model for smaller deployments.
**Weaknesses:** Primarily memory-bound (cost scales with RAM, not disk), not designed as a primary system-of-record for complex relational data, persistence options (RDB/AOF) trade off durability vs. performance.

#### 10.3.4 DynamoDB (Managed Key-Value/Document, AWS)

**When to choose it:** AWS-centric architectures needing a fully managed, serverless-scaling NoSQL database with predictable low-latency performance at massive scale, especially for well-understood, key-based access patterns (e.g., user sessions, shopping carts, gaming leaderboards).

**Strengths:** Fully managed (zero operational burden for scaling/HA), single-digit millisecond latency at virtually unlimited scale, seamless integration with AWS ecosystem (Lambda, API Gateway).
**Weaknesses:** Requires careful upfront access-pattern modeling (similar to Cassandra's query-first design), can become expensive at scale if access patterns aren't well-optimized, AWS vendor lock-in, limited ad-hoc query flexibility.

#### 10.3.5 Neo4j (Graph Database)

**When to choose it:** Data whose *relationships* are as important as the data itself — social networks, recommendation engines, fraud detection networks, knowledge graphs, org charts with deep hierarchical/relationship traversal needs.

**Strengths:** Native graph storage makes multi-hop relationship traversal (e.g., "friends of friends of friends") dramatically faster than the equivalent recursive joins in a relational database; expressive query language (Cypher) purpose-built for graph patterns.
**Weaknesses:** Not a good fit for typical tabular/transactional workloads; smaller ecosystem/talent pool than mainstream relational/NoSQL options; horizontal scaling historically more complex than other NoSQL categories.

#### 10.3.6 Elasticsearch (Search Engine)

**When to choose it:** Full-text search, log aggregation/analysis, complex filtering + relevance-ranked search across large text corpora — almost never as a primary system-of-record, but as a specialized search layer alongside a primary database.

**Strengths:** Extremely powerful full-text search and relevance scoring, near-real-time indexing, strong aggregation framework for analytics-style queries over large datasets, the backbone of the "ELK stack" for log analysis.
**Weaknesses:** Not ACID-transactional in the way a primary database is; typically used as a **derived/secondary data store** synced from a primary database (via CDC or dual-writes) rather than the source of truth; operational complexity at scale (shard management, cluster health).

**NoSQL Comparison Table**

| Database | Data Model | Consistency Model | Best For | Scaling Model |
|---|---|---|---|---|
| MongoDB | Document | Tunable (strong by default within a replica set primary) | Flexible/evolving schemas | Native sharding |
| Cassandra | Wide-column | Tunable, eventual by default | Massive write throughput, multi-DC | Masterless, linear horizontal |
| Redis | Key-value (in-memory) | Strong (single-threaded core) | Caching, real-time, low-latency lookups | Clustering (Redis Cluster) |
| DynamoDB | Key-value/Document | Tunable (eventual or strong reads) | AWS-native, massive predictable scale | Fully managed auto-partitioning |
| Neo4j | Graph | Strong (transactional) | Relationship-heavy queries | Causal clustering (more complex) |
| Elasticsearch | Search/Document index | Eventual (near-real-time) | Full-text search, log analytics | Native sharding |

### 10.4 Distributed SQL ("NewSQL")

#### 10.4.1 CockroachDB

**When to choose it:** Applications needing **both** strong relational/SQL semantics (ACID transactions, familiar SQL) **and** horizontal scalability with automatic sharding and multi-region survivability — essentially solving the "PostgreSQL doesn't scale writes horizontally" problem natively.

**Strengths:** PostgreSQL-wire-compatible, automatic sharding and rebalancing, survives node/region failures with strong consistency, geo-partitioning for data residency/latency needs.
**Weaknesses:** Higher write latency than a single-node database for the same operation (distributed consensus overhead), operationally more complex to deeply understand than traditional single-node databases, cost at scale.

#### 10.4.2 YugabyteDB

**When to choose it:** Similar profile to CockroachDB — PostgreSQL-compatible distributed SQL, often considered when needing very high compatibility with existing PostgreSQL tooling/extensions, or when Cassandra-style API compatibility (YCQL) is also desired.

**Strengths:** Strong PostgreSQL compatibility, dual API support (SQL and Cassandra-like), distributed ACID transactions.
**Weaknesses:** Similar operational complexity trade-offs as CockroachDB; smaller ecosystem/community than either PostgreSQL or Cassandra individually.

#### 10.4.3 TiDB

**When to choose it:** MySQL-compatible workloads needing horizontal scale, especially popular for **Hybrid Transactional/Analytical Processing (HTAP)** — running both OLTP and real-time analytics against the same data without a separate ETL pipeline to a data warehouse.

**Strengths:** MySQL wire-compatible, separates compute/storage architecturally, built-in HTAP via a columnar replica (TiFlash) alongside the row-based store.
**Weaknesses:** Operational complexity of a distributed system, smaller community than MySQL itself, best suited to teams ready to invest in understanding a more complex distributed architecture.

#### 10.4.4 Google Cloud Spanner

**When to choose it:** Applications requiring global, strongly-consistent, horizontally-scalable SQL with extremely high availability guarantees, and already committed to Google Cloud — famous for using synchronized atomic clocks (TrueTime) to achieve global strong consistency without the usual trade-offs.

**Strengths:** True global distribution with strong consistency (a historically very hard combination — directly relevant to Part 8's CAP theorem discussion), extremely high availability SLAs, fully managed.
**Weaknesses:** GCP-only (vendor lock-in), premium pricing, SQL feature set differences from PostgreSQL/MySQL require some application adaptation.

**Distributed SQL Comparison Table**

| Database | Wire Compatibility | Special Strength | Cloud Availability |
|---|---|---|---|
| CockroachDB | PostgreSQL | Multi-region survivability, geo-partitioning | Self-hosted or CockroachDB Cloud |
| YugabyteDB | PostgreSQL + Cassandra (YCQL) | Dual API flexibility | Self-hosted or Yugabyte Cloud |
| TiDB | MySQL | Built-in HTAP (OLTP + real-time analytics) | Self-hosted or TiDB Cloud |
| Spanner | Custom SQL (close to standard) | Global strong consistency via TrueTime | GCP only |

### 10.5 The Master Decision Matrix

| Workload Characteristic | Recommended Category | Example Engines |
|---|---|---|
| General-purpose transactional app, moderate scale | Relational (SQL) | PostgreSQL, MySQL |
| Flexible/evolving schema, document-shaped data | Document store | MongoDB |
| Massive write throughput, simple key-based access, multi-DC | Wide-column | Cassandra |
| Sub-millisecond caching/real-time lookups | In-memory key-value | Redis |
| AWS-native, predictable massive scale, key-based access | Managed key-value | DynamoDB |
| Deep relationship traversal (social graphs, fraud detection) | Graph | Neo4j |
| Full-text search / log analytics | Search engine | Elasticsearch |
| Need SQL + ACID + horizontal scale + multi-region | Distributed SQL | CockroachDB, YugabyteDB, Spanner |
| OLTP + real-time analytics on the same data (HTAP) | Distributed SQL (HTAP-focused) | TiDB |
| Embedded/local/mobile | Embedded SQL | SQLite |
| Large enterprise, existing investment, mission-critical | Enterprise RDBMS | Oracle, SQL Server |

### 10.6 Decision Tree — Choosing a Database Category

```
What's the primary shape of your data and access pattern?
│
├─ Tabular, relationships matter, need strong ACID transactions?
│      │
│      ├─ Need horizontal write scaling / multi-region?
│      │      └─ YES → Distributed SQL (CockroachDB/YugabyteDB/Spanner/TiDB)
│      │      └─ NO  → Traditional RDBMS (PostgreSQL/MySQL, or Oracle/SQL Server
│      │                 if enterprise requirements dictate)
│
├─ Schema is flexible/evolving, document-shaped, developer velocity matters most?
│      └─ MongoDB
│
├─ Extremely high write throughput, simple access patterns, must survive multi-DC?
│      └─ Cassandra
│
├─ Need sub-millisecond latency for caching/session/real-time data?
│      └─ Redis
│
├─ Relationships between entities ARE the primary query pattern (multi-hop traversal)?
│      └─ Neo4j (graph)
│
├─ Primary need is full-text search or log/event analytics?
│      └─ Elasticsearch (as a secondary/derived store alongside a primary DB)
│
└─ Embedded, local-only, single-process application?
       └─ SQLite
```

### 10.7 Cost, Latency, and Operational Complexity — The Real Trade-offs

**Cost dimensions to weigh (beyond simple licensing):**

| Dimension | Consideration |
|---|---|
| Licensing/service cost | Open-source (free but engineering-cost-heavy) vs. managed (higher $ cost, lower engineering cost) vs. enterprise licensed (Oracle/SQL Server) |
| Operational complexity cost | Distributed systems (Cassandra, distributed SQL) require deeper expertise (Module 6/9 recap) than a single-node RDBMS |
| Scaling cost curve | Vertical scaling (bigger single node) has diminishing returns and a hard ceiling; horizontal scaling (sharding/distributed) has near-linear cost but higher baseline complexity |
| Talent availability | PostgreSQL/MySQL talent is abundant; Cassandra/graph/distributed SQL expertise is comparatively scarce and often more expensive to hire for |

**Real-world analogy revisited:** Choosing "the most scalable database" for a small startup is like buying an 18-wheeler truck to commute to work alone every day — technically capable of hauling far more than you need, but wildly inefficient and hard to park (operationally complex) for your actual use case. **Match the tool to the actual, current-and-near-future workload, not the theoretical maximum scale you might someday reach.**

### 10.8 Polyglot Persistence (Recap from Module 1's "Database Evolution")

Most mature, large-scale production systems don't use just ONE database — they use several, each suited to a specific sub-workload:

```
┌─────────────────────────────────────────────────────────────────────┐
│                        Example E-Commerce Architecture                 │
├─────────────────────────────────────────────────────────────────────┤
│  PostgreSQL      → Orders, inventory, payments (strong ACID needed)   │
│  Redis           → Session storage, cart cache, rate limiting          │
│  Elasticsearch   → Product search, filtering, relevance ranking        │
│  Cassandra       → Clickstream/event logging (massive write volume)    │
│  Neo4j           → "Customers who bought this also bought" recs        │
└─────────────────────────────────────────────────────────────────────┘
```

**Interview Importance:** ⭐⭐⭐⭐⭐ (Nearly every senior system design interview eventually asks "would you use one database or several, and why?")

### 10.9 Checklist — Database Selection Process

- [ ] Data shape identified (relational/document/key-value/graph/wide-column/search)
- [ ] Consistency requirements defined (strong vs. eventual, per use case)
- [ ] Read/write ratio and access pattern characterized
- [ ] Scale projections made (current and 1-2 year horizon)
- [ ] Team's operational expertise honestly assessed against candidate options
- [ ] Cost model compared across realistic candidates (not just licensing — include ops cost)
- [ ] Vendor lock-in risk considered and explicitly accepted or avoided
- [ ] Polyglot persistence considered if a single engine doesn't fit all sub-workloads well
