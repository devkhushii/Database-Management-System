### 3.1 How to Read a Database Research Paper

Database papers follow a near-universal skeleton once you know to look for it. Reading linearly front-to-back wastes time — read in this order instead:

1. **Abstract + Introduction** — extract the *problem statement* in one sentence and the *claimed contribution* in one sentence. If you can't state both after the intro, re-read it.
2. **Skip straight to Evaluation section headers/graphs** (don't read the numbers yet — just look at *what* is being measured). This tells you what the authors think matters, which tells you what the "hard part" of the system actually was.
3. **Read the Architecture/Design section in full** — this is where the actual engineering lives. Draw the diagram yourself on paper as you read; don't just look at their figure.
4. **Read Related Work last, not first** — it only makes sense once you understand what this paper does differently.
5. **Return to Evaluation numbers** — now interpret them against the design you understand.

**The four-question framework** (use this for every paper, and for Modules 3B's summaries below):
- **Problem**: What broke, at what scale, that existing systems couldn't handle?
- **Innovation**: What is the one (sometimes two) genuinely new idea? Be suspicious of papers claiming more than 1–2 real innovations — usually one idea is central and the rest is engineering to support it.
- **Internal Architecture**: How is the system actually built — components, data flow, failure handling?
- **Impact**: What later systems copied this idea, and what did the idea get renamed to?

**Common pitfall for engineers new to papers:** conflating "this is what they built" with "this is what you should build." Papers report decisions made for a *specific* scale and workload (Google's request volume, Amazon's retail catalog). The correct reading skill is extracting the *general technique*, then asking whether your constraints justify it.

### 3.2 ARIES — Algorithm for Recovery and Isolation Exploiting Semantics

**Citation:** Mohan et al., *"ARIES: A Transaction Recovery Method Supporting Fine-Granularity Locking and Partial Rollbacks Using Write-Ahead Logging,"* ACM TODS, 1992.

**Problem:** Before ARIES, crash recovery algorithms either required repeating *all* work since the last checkpoint (slow) or made strong assumptions about locking granularity that limited concurrency. Databases needed a recovery algorithm that worked correctly with fine-grained (row-level) locking and could recover efficiently regardless of how much time had passed since the crash.

**Innovation:** Three ideas combined:
1. **Write-Ahead Logging (WAL)** as a strict invariant: a log record describing a change must be durable *before* the corresponding data page is written to disk.
2. **Repeating history during REDO** — rather than trying to be clever about what needs redoing, ARIES redoes *everything* since the last checkpoint (including for transactions that will later be undone), then fixes it up in the UNDO phase. This dramatically simplifies the algorithm at negligible cost.
3. **Log Sequence Numbers (LSNs) on every page** — each data page stores the LSN of the last log record that modified it, so recovery can tell *exactly* which log records are already reflected in a page and skip redoing them (idempotent, precise redo).

**Internal Architecture — the three-phase recovery protocol:**
- **Analysis phase**: scan the log forward from the last checkpoint to determine which transactions were active at crash time (the "loser" list) and which pages were dirty.
- **Redo phase**: scan forward from the earliest necessary log record, reapplying *every* logged change (even for eventually-aborted transactions) to bring the database to the exact state at the moment of crash.
- **Undo phase**: scan backward, rolling back all transactions that were active (uncommitted) at crash time, writing **Compensation Log Records (CLRs)** for each undo action so that if the system crashes *again* during recovery, it never re-undoes the same action twice.

**Impact:** ARIES (or a close derivative) is the recovery algorithm inside virtually every production relational database — PostgreSQL, MySQL/InnoDB, SQL Server, Oracle, and even many NewSQL systems' single-node storage layers all implement WAL + fuzzy checkpointing + physiological logging derived directly from this paper. It is the single most-implemented database paper in history.

### 3.3 Bigtable

**Citation:** Chang et al., *"Bigtable: A Distributed Storage System for Structured Data,"* OSDI 2006.

**Problem:** Google needed a storage system for structured data (web crawl results, user data) scaling to petabytes across thousands of commodity machines, with the flexibility to handle very sparse, wide, versioned data that didn't fit a traditional relational schema.

**Innovation:** A **sparse, distributed, persistent multi-dimensional sorted map**, indexed by `(row key, column key, timestamp)`. Rows are ordered lexicographically, and column families group related columns for locality — this design lets Google store, e.g., a webpage's crawl history (many versions over time) and its outbound links (a sparse, huge column family) in the same logical row without wasting space on unused columns.

**Internal Architecture:**
- **Tablets**: the table is horizontally partitioned into row-range tablets, each served by exactly one **tablet server** at a time (this single-writer-per-tablet design avoids write conflicts without needing distributed locking for writes).
- **SSTables**: each tablet's data is stored as an immutable, sorted, indexed file format (SSTable) in **GFS** (Google File System) — this is the direct ancestor of every LSM-tree engine you'll study in Module 4.
- **Chubby** (a Paxos-based lock service) is used for master election, tablet server liveness, and storing the root of the tablet location metadata (a 3-level B-tree-like lookup: root tablet → metadata tablets → user tablets).
- Writes go to an in-memory **memtable** plus a commit log; when the memtable is full, it's flushed to a new SSTable. Reads merge results from the memtable and relevant SSTables.

**Impact:** Directly inspired **HBase** (open-source clone), **Cassandra** (combined Bigtable's data model with Dynamo's replication — see 3.4), and is the conceptual ancestor of nearly all wide-column stores. The SSTable/memtable design became the template for LSM-tree storage engines broadly (LevelDB, RocksDB — Module 4).

### 3.4 Dynamo

**Citation:** DeCandia et al., *"Dynamo: Amazon's Highly Available Key-value Store,"* SOSP 2007.

**Problem:** Amazon's shopping cart and other services needed **always-writable** storage — even during network partitions or data center failures, a customer must always be able to add an item to their cart. Traditional systems that block writes during partitions (choosing C over A in CAP terms) were unacceptable for this use case.

**Innovation:** An **AP (Available, Partition-tolerant)** design combining several techniques into one coherent system:
1. **Consistent hashing** for partitioning — nodes and keys are mapped to points on a hash ring, so adding/removing a node only affects its immediate neighbors' data, not the whole cluster (solving the shared-nothing rebalancing problem from Module 2).
2. **Vector clocks** for conflict detection — instead of a single last-write-wins timestamp, each value carries a vector clock recording causal history, so the system can detect when two writes are genuinely concurrent (conflicting) versus one causally following the other.
3. **Sloppy quorums + hinted handoff** — reads/writes use configurable `R`/`W` quorum sizes out of `N` replicas (not strict majority quorums), and if a target replica node is down, another node temporarily accepts the write and hands it off later — trading strict correctness for availability.
4. **Read repair + anti-entropy (Merkle trees)** — background processes reconcile replicas that have drifted, using Merkle trees to efficiently identify which key ranges differ without comparing every key.

**Internal Architecture:** Every node is functionally identical (no master) — a request for any key can be handled by any node acting as coordinator, which routes to the correct replica set via the hash ring. This peer-to-peer, leaderless design is the core difference from Bigtable's single-master-per-tablet model.

**Impact:** Directly inspired **Cassandra** (Dynamo's replication/gossip model + Bigtable's column-family data model), **Riak**, and Amazon's own **DynamoDB** (a evolved, managed descendant — see 3.5). Popularized vector clocks, consistent hashing, and "eventual consistency with tunable quorums" as mainstream distributed systems vocabulary.

### 3.5 DynamoDB

**Citation:** Elhemali et al., *"Amazon DynamoDB: A Scalable, Predictably Performant, and Fully Managed NoSQL Database Service,"* USENIX ATC 2022 (a retrospective — note this is a different, later paper than the original 2007 Dynamo paper, describing how the *managed service* evolved).

**Problem:** Running the original Dynamo design at Amazon-internal scale as a **multi-tenant public cloud service** exposed new problems the 2007 paper never addressed: unpredictable "noisy neighbor" latency spikes, hot-partition throttling surprises for customers, and the operational burden of self-managing Dynamo clusters.

**Innovation:** 
1. Moved from Dynamo's tunable quorum/eventual-consistency-first model toward **predictable, provisioned (later on-demand) throughput per table**, with **adaptive capacity** to automatically redistribute throughput to hot partitions instead of throttling them.
2. Introduced a **log-structured, replicated storage engine per partition** built on a Multi-Paxos-replicated log (not the original gossip-based sloppy quorum design) — a significant internal rewrite from the original Dynamo paper's leaderless model toward per-partition leader-based replication for stronger guarantees.
3. **Global Secondary/Local Secondary Indexes** and later **DynamoDB Transactions** (2018) added multi-item ACID transactions on top of the key-value core — directly addressing the "NoSQL dropped transactions" gap discussed in Module 1.

**Internal Architecture:** Each table is split into partitions, each replicated 3-way via Paxos-based consensus with a leader replica per partition handling writes; a request router layer directs client requests to the correct partition's leader; a separate metadata/partition-management service (built on its own strongly consistent store) handles partition splits and rebalancing.

**Impact:** Shows the real-world engineering arc from "research paper idea" (2007 Dynamo) to "hardened multi-tenant cloud product" (2022 DynamoDB) — an important lesson for engineers: production requirements (predictability, multi-tenancy) often push systems *away* from their original research design toward stronger consistency primitives.

### 3.6 Spanner

**Citation:** Corbett et al., *"Spanner: Google's Globally-Distributed Database,"* OSDI 2012.

**Problem:** Google needed a database that was simultaneously: globally distributed across data centers on different continents, strongly (externally) consistent, and capable of ACID transactions — a combination widely believed at the time to be impossible to achieve with acceptable latency (this is the tension the CAP theorem describes).

**Innovation: TrueTime.** A global clock API exposing not a single timestamp but a **bounded uncertainty interval** `[earliest, latest]`, backed by GPS receivers and atomic clocks in every data center. Instead of trying to eliminate clock uncertainty, Spanner **exposes and waits out** the uncertainty: before committing a transaction, it waits until it's certain the interval has passed (the "commit wait" technique), guaranteeing that transaction timestamps reflect true global ordering — this gives **external consistency** (linearizability across the whole globe), which was the previously "impossible" property.

**Internal Architecture:**
- Data is split into **directories** grouped into **tablets**, replicated via **Paxos** across data centers (typically 5 replicas across 3+ regions) for fault tolerance.
- **Two-phase commit (2PC)** layered on top of Paxos groups handles transactions spanning multiple Paxos groups (shards) — Paxos gives durability/availability per shard, 2PC gives atomicity across shards.
- The **Paxos leader** of each group also acts as the concurrency control lock manager for that group, using strict two-phase locking combined with TrueTime timestamps to assign a globally meaningful commit timestamp to every transaction.

**Impact:** Directly inspired **CockroachDB** and **YugabyteDB** (open-source Spanner-derivatives using Hybrid Logical Clocks instead of atomic-clock hardware since they can't assume Google's data center infrastructure), and **F1** (3.7) was built as Google's SQL layer on top of Spanner. Proved that strongly consistent global-scale ACID transactions were achievable in production, reshaping the entire NewSQL category (Module 1.7).

### 3.7 F1

**Citation:** Shute et al., *"F1: A Distributed SQL Database That Scales,"* VLDB 2013.

**Problem:** Google's AdWords system had outgrown a traditional sharded MySQL deployment — manual sharding was an enormous ongoing engineering burden, and the business needed full SQL, secondary indexes, and ACID transactions at Google-scale, none of which the earlier sharded-MySQL approach could give without constant manual intervention.

**Innovation:** Build a **full-featured distributed SQL layer on top of Spanner's storage/transaction substrate**, rather than building yet another storage engine — separating "SQL query processing" from "distributed storage and transactions" as two independently evolvable layers (a precursor to the modern SQL-layer-over-KV-storage pattern used by CockroachDB and TiDB).

**Internal Architecture:**
- F1 servers are **stateless** — they hold no persistent data, only in-flight query state, and can be added/removed elastically (an early real-world example of the compute-storage separation pattern from Module 2.6, at the SQL layer specifically).
- Uses a **hierarchical schema** design ("table interleaving") to physically co-locate parent and child rows (e.g., `Customer` and its `Orders`) within Spanner, converting what would be an expensive distributed join into a cheap local read.
- Implements **change history/eventing** as a first-class feature (every transaction's changes are made available as a stream) — an early production example of coupling OLTP writes with streaming consumers (foreshadowing Module 9).

**Impact:** Established the "SQL query layer decoupled from distributed storage layer" architecture that **TiDB** (SQL layer over TiKV) and **CockroachDB** later adopted independently. F1's table interleaving idea reappears as a locality/co-location optimization technique across many distributed SQL systems.

### 3.8 Aurora

**Citation:** Verbitski et al., *"Amazon Aurora: Design Considerations for High Throughput Cloud-Native Relational Databases,"* SIGMOD 2017.

**Problem:** Traditional replicated relational databases (MySQL/PostgreSQL with synchronous replicas) pay a heavy network I/O cost — every replica ships and applies full data pages, and synchronous replication for durability adds significant write latency. At cloud scale, network I/O (not CPU or disk) had become the actual bottleneck for durable, highly available relational databases.

**Innovation:** **"The log is the database."** Aurora's core insight: the only thing that strictly needs to be shipped over the network for durability and replication is the **redo log stream** — data pages themselves can be reconstructed from the log lazily, on demand, by the storage layer. This collapses what used to be multiple separate write paths (redo log + binlog + data pages + double-write buffer, in traditional MySQL) into a single network operation: ship the log record.

**Internal Architecture:**
- The database engine (a modified MySQL/InnoDB, later Postgres) generates log records and ships them to **6 storage nodes across 3 Availability Zones**.
- Storage nodes are "dumb" relative to the database engine — they just durably persist log records and asynchronously materialize them into data pages/segments, handling garbage collection and repair (re-replicating from peers) locally without involving the database engine at all.
- **Quorum-based durability**: a write is considered durable once **4 of 6** storage nodes acknowledge it; reads for availability tolerate **3 of 6** nodes being unreachable — a quorum scheme (4/6 write, 3/6 read overlap) chosen specifically to tolerate a full AZ failure plus one additional node failure without losing availability.
- Storage is segmented into small (10GB) **Protection Groups**, each independently and continuously repaired in the background, so the "unit of failure and repair" is small and fast to heal — unlike traditional systems where a whole-disk or whole-replica failure requires a slow, large resync.

**Impact:** Became the reference architecture for cloud-native relational databases; directly inspired Azure's Hyperscale, Google's AlloyDB, and open-source projects like Neon that build Postgres on a similarly disaggregated, log-centric storage layer. Cemented compute-storage separation (Module 2.6) as the default architecture for new cloud relational databases.

### 3.9 Calvin

**Citation:** Thomson et al., *"Calvin: Fast Distributed Transactions for Partitioned Database Systems,"* SIGMOD 2012.

**Problem:** Traditional distributed transaction protocols (2PC layered over locking, as in Spanner) pay a coordination cost *at commit time* — locks are held across the network round-trips of the commit protocol, which can be slow and, worse, unpredictable (locks held longer under contention). Calvin asked: can we get serializable distributed transactions with **no locking-based coordination at commit time at all**?

**Innovation:** **Deterministic execution.** Instead of letting each node execute transactions in whatever order it naturally processes them (requiring runtime coordination to agree on a consistent order), Calvin **decides the global transaction order in advance**, using a separate **sequencing layer** that runs a consensus protocol (e.g., Paxos) purely to agree on a batch order of incoming transactions *before* any execution happens. Since every node then deterministically executes the *same* agreed-upon sequence of transactions against its local partition, replicas naturally stay consistent without any commit-time coordination — replication becomes "replay the same deterministic log," not "coordinate on each transaction."

**Internal Architecture — three layers:**
1. **Sequencing layer**: batches incoming transaction requests and uses consensus (e.g., Paxos) to agree on a single global order for each batch, replicated to all nodes.
2. **Scheduling layer**: on each node, takes the agreed-upon deterministic order and manages local lock acquisition to allow safe intra-batch parallelism while preserving the required serial order.
3. **Storage/execution layer**: a pluggable local storage engine actually executes the transaction logic against local data, following the schedule handed to it.
- Cross-partition transactions are handled by having every involved node deterministically execute the same transaction logic (including reads that must be forwarded between participating nodes) — avoiding 2PC entirely because determinism guarantees all replicas independently reach the same outcome.

**Impact:** Influenced **FaunaDB** (built directly on Calvin's deterministic execution model) and reframed the distributed transactions research conversation — showing 2PC-based coordination isn't the *only* path to distributed serializability, which subsequent papers (including some FoundationDB design discussions) engage with directly.

### 3.10 FaRM

**Citation:** Dragojević et al., *"FaRM: Fast Remote Memory,"* NSDI 2014 (and the follow-up *"No Compromises: Distributed Transactions with Consistency, Availability, and Performance,"* SOSP 2015).

**Problem:** Standard distributed transaction protocols assume network round-trips are "slow" (milliseconds) relative to local memory access, so their designs accept that cost. But **RDMA (Remote Direct Memory Access)** hardware allows one machine to read/write another machine's RAM directly, bypassing its CPU, at latencies closer to local memory access (single-digit microseconds) — FaRM asked: if the network is no longer the bottleneck, how should a distributed transactional system be redesigned from scratch?

**Innovation:** Treat the RAM of an entire cluster as **one large shared, transactional address space** accessed via RDMA, rather than treating each node's memory as private and communicating via traditional message-passing RPCs. Combined with **optimistic concurrency control (OCC)** tuned specifically for RDMA's read-mostly, low-latency characteristics, and a custom **RDMA-based consensus/replication protocol** for the log, FaRM achieves both strict serializability and very high transaction throughput simultaneously — the "no compromises" of the 2015 title.

**Internal Architecture:**
- All data lives in the (aggregate) RAM of the cluster; RDMA reads let a coordinator node fetch remote objects directly without interrupting the remote CPU, making reads extremely cheap.
- Transactions execute optimistically: read a consistent snapshot, buffer writes locally, then run a lock-and-validate commit protocol using **RDMA atomic operations (compare-and-swap)** issued directly against remote memory locations to acquire locks without any remote CPU involvement.
- Durability comes from replicating log records via RDMA writes to multiple machines' NVRAM/battery-backed memory, achieving both low latency and crash durability without the traditional network-stack overhead of TCP/IP-based replication.

**Impact:** One of the most influential systems papers demonstrating that **hardware assumptions baked into decades of distributed systems design were no longer valid** once RDMA became commodity data center hardware — directly influenced later RDMA-aware database and key-value store designs (including academic follow-ups and internal designs at hyperscalers), and is a canonical example of how a hardware trend can force a full architectural rethink rather than an incremental optimization.

### 3.11 Hekaton

**Citation:** Diaconu et al., *"Hekaton: SQL Server's Memory-Optimized OLTP Engine,"* SIGMOD 2013.

**Problem:** Disk-oriented database engines pay overhead (buffer pool management, latching, locking) that is unnecessary once a working set fits entirely in RAM — for high-throughput OLTP workloads on modern hardware, that overhead, not the disk itself, had become the bottleneck. Microsoft wanted an in-memory engine that could live *inside* SQL Server as an alternative table storage engine, not a separate product.

**Innovation:** Combine three techniques rarely found together at the time: **lock-free (latch-free) data structures**, **multi-version optimistic concurrency control (MVCC)** with no read locks at all, and **query compilation to native machine code** rather than interpretation.

**Internal Architecture:**
- Tables are stored as **lock-free hash indexes or Bw-trees** (a latch-free B-tree variant using atomic compare-and-swap on delta records instead of in-place page updates with latches).
- Every row version carries `Begin-Ts`/`End-Ts` timestamps; transactions read a consistent snapshot via MVCC and validate at commit time (optimistic — no locks acquired during execution), aborting and retrying on conflict rather than blocking.
- Stored procedures accessing Hekaton tables are **compiled to native C code via the SQL Server query compiler**, eliminating interpretation overhead entirely for hot OLTP paths.
- Hekaton tables coexist with traditional disk-based tables in the same SQL Server instance and same transactions — a cross-engine transaction can touch both.

**Impact:** Demonstrated that a fully latch-free, MVCC, compiled in-memory engine could be shipped as a *feature* inside an existing mainstream RDBMS rather than requiring a rewrite — influenced later in-memory engine designs and is frequently cited as the reference for latch-free Bw-tree indexing structures used elsewhere.

### 3.12 Snowflake

**Citation:** Dageville et al., *"The Snowflake Elastic Data Warehouse,"* SIGMOD 2016.

**Problem:** Traditional data warehouses (on-prem MPP systems like Teradata, or early cloud warehouses) coupled compute and storage tightly, forcing customers to provision for peak load and making elastic, pay-per-use analytics impossible; multi-tenant resource contention was also a persistent operational headache.

**Innovation:** A **three-layer disaggregated architecture** purpose-built for public cloud object storage, combined with **independent, isolated "virtual warehouses"** so multiple workloads never contend for the same compute resources even though they share the same underlying data.

**Internal Architecture:**
1. **Storage layer**: immutable, compressed, columnar micro-partition files stored in cloud object storage (S3/Blob) — durable, cheap, infinitely scalable, and completely decoupled from compute.
2. **Compute layer ("Virtual Warehouses")**: independent MPP clusters of stateless worker nodes, each spun up on demand for a workload; multiple virtual warehouses can query the *same* underlying data concurrently with zero resource contention between them, and each can be resized or auto-suspended independently.
3. **Cloud Services layer**: a set of stateless services (metadata catalog, query optimizer/planner, transaction/concurrency manager, security/access control, results cache) coordinating everything — this layer maintains the metadata about micro-partitions (min/max column statistics per file) that enables aggressive partition pruning without scanning data.
- A **global results cache** at the Cloud Services layer can return results for a repeated query without any compute warehouse running at all — an important cost/latency optimization enabled specifically by the disaggregated design.

**Impact:** The canonical reference architecture for modern cloud data warehouses; heavily influenced Databricks SQL, Google BigQuery's later architecture evolution, and virtually every "cloud-native analytics" product built after 2016. Popularized micro-partition pruning via stored min/max statistics as a standard technique.

### 3.13 RocksDB

**Citation:** Facebook/Meta engineering (Dhruba Borthakur et al.), RocksDB originated as a fork of LevelDB (see 3.15), first released 2012; described in various Facebook engineering publications and the RocksDB project documentation rather than a single canonical academic paper.

**Problem:** LevelDB was designed for browser-embedded use (Chrome) with modest throughput needs. Facebook needed an embeddable key-value storage engine that could sustain very high write throughput on SSDs, for server-side workloads like MySQL storage engines (MyRocks), stream processing state stores, and other latency-sensitive services — well beyond what LevelDB's design targeted.

**Innovation:** Take LevelDB's core **LSM-tree** design (full details in Module 4) and make it a highly tunable, multi-threaded, production-hardened storage engine: **multi-threaded compaction**, **column families** (independent LSM trees sharing a single log for atomic cross-family writes), pluggable compaction strategies (leveled vs. **universal/tiered compaction**), and extensive tuning knobs for the memtable, block cache, bloom filters, and compression per use case.

**Internal Architecture:** (Full mechanics in Module 4 — summarized here for paper context)
- Writes go to an in-memory **memtable** (skip-list based) plus a WAL for durability; when full, the memtable is flushed to an immutable, sorted **SSTable** on disk.
- Background **compaction** threads merge SSTables across levels to bound the number of files a read must check and to reclaim space from overwritten/deleted keys — RocksDB made compaction strategy itself pluggable (leveled compaction minimizes read/space amplification at the cost of write amplification; universal compaction favors write throughput at the cost of temporary space amplification).
- **Column families** let logically distinct datasets (e.g., different tables in MyRocks) share the same write-ahead log for atomicity while maintaining separate LSM trees and independent compaction/tuning.

**Impact:** Became the most widely embedded LSM engine in the industry — powers **MyRocks** (MySQL storage engine at Facebook), **CockroachDB**'s original storage layer, **TiKV** (TiDB's storage layer, initially), Apache Kafka Streams' state stores, and many other systems that need an embeddable, high-write-throughput key-value engine.

### 3.14 WiredTiger

**Citation:** WiredTiger originated as an independent storage engine (Michael Cahill, Keith Bostic — Bostic was also a principal author of Berkeley DB), acquired by MongoDB in 2014 and made the default storage engine in MongoDB 3.2; documented primarily via MongoDB/WiredTiger engineering documentation rather than one flagship academic paper.

**Problem:** MongoDB's original default storage engine (MMAPv1) used coarse-grained (database or collection level) locking and had no built-in compression, limiting write concurrency and storage efficiency. MongoDB needed a storage engine supporting document-level concurrency control and modern compression.

**Innovation:** A storage engine offering **both B-tree and LSM-tree table types** (the application/database can choose per collection), **document-level MVCC concurrency control**, and **on-by-default block compression** (snappy/zlib/zstd) — combining the read-optimized characteristics of B-trees with an option for LSM-style write optimization within one engine.

**Internal Architecture:**
- Uses an **MVCC** model where every page has multiple in-memory versions; readers see a consistent snapshot as of their transaction's start without blocking writers, similar in spirit to Hekaton but on a disk-backed B-tree structure rather than a purely in-memory hash/Bw-tree.
- Employs a distinctive **"eviction server"** design: dedicated background threads continuously evict clean/reconciled pages from the in-memory cache under memory pressure, decoupling cache management from the foreground query threads to keep latency predictable.
- Checkpointing writes a consistent snapshot of the B-tree to disk periodically; combined with a write-ahead log for changes since the last checkpoint, giving ARIES-like crash recovery guarantees (Section 3.2) despite being a much younger, independently designed engine.

**Impact:** Powers MongoDB as its default storage engine since 3.2 (2015), significantly improving MongoDB's write concurrency and storage footprint versus MMAPv1; a widely studied example of a **document-level MVCC B-tree** engine as an alternative to the LSM-tree-dominant landscape (RocksDB, LevelDB).

### 3.15 LevelDB

**Citation:** Ghemawat & Dean (Google), first released as open source in 2011; described in Google engineering documentation and the project's own design docs rather than a peer-reviewed paper, but directly derived from the Bigtable SSTable/memtable design (3.3) the same authors built.

**Problem:** Google (and later the broader industry) needed a small, simple, embeddable, single-node persistent key-value library — not a distributed database, just a fast local storage building block, extracting the core single-node storage design from Bigtable without any of Bigtable's distributed machinery.

**Innovation:** A clean, minimal, single-node implementation of the **LSM-tree** (Log-Structured Merge-tree, originally proposed by O'Neil et al. 1996) as a reusable embedded library — proving the SSTable+memtable+compaction pattern from Bigtable was valuable as a standalone component, not just as part of a distributed system.

**Internal Architecture:** (This is the reference architecture Module 4 builds on in full detail)
- **MemTable**: an in-memory sorted skip-list buffering recent writes.
- **Immutable MemTable**: when the active memtable fills, it's frozen and a new one takes over writes, while the frozen one is flushed to disk in the background — a technique that avoids blocking writers during flush.
- **SSTables organized into levels** (`L0` through `L6`): `L0` files come directly from memtable flushes and may have overlapping key ranges (requiring reads to check all of them); `L1` and deeper are compacted into non-overlapping, sorted runs, so a read only needs to check one file per level from `L1` down.
- **Manifest file** tracks which SSTables exist at which level, enabling crash-consistent recovery of the LSM tree's structure.

**Impact:** Directly forked into **RocksDB** (3.13) by Facebook engineers; its leveled compaction design became the textbook reference implementation that essentially every subsequent LSM engine (RocksDB, Badger, Pebble used by CockroachDB) is described and compared against.

### 3.16 FoundationDB

**Citation:** FoundationDB's design is described in Zhou et al., *"FoundationDB: A Distributed Unbundled Transactional Key Value Store,"* SIGMOD 2021 (published after Apple acquired and later open-sourced the project).

**Problem:** Building a correct distributed transactional database is extraordinarily hard to test — subtle bugs in distributed concurrency control and failure handling are rare, hard to reproduce, and catastrophic. FoundationDB's team wanted both an architecturally clean separation of concerns *and* a way to gain extremely high confidence in correctness before shipping.

**Innovation — two, tightly linked:**
1. **"Unbundled" architecture**: strictly separate the roles of **transaction management** (deciding commit order, conflict detection, timestamp assignment), **data storage** (durable persistence of key-value data), and **request routing/proxying** into independently scalable, independently deployable clusters of processes — a more radical decomposition than most distributed databases attempt.
2. **Deterministic simulation testing**: FoundationDB is developed alongside a custom deterministic network/disk/clock simulator that can run an entire simulated multi-node cluster (with injected failures, network partitions, clock skew, and process crashes) *deterministically* inside a single test process — enabling millions of simulated cluster-years of fault injection testing that would be infeasible to run on real hardware, and enabling any discovered failure to be deterministically replayed for debugging.

**Internal Architecture:**
- **Transaction layer**: a small number of stateless proxies and a sequencer assign transactions a read version and validate conflicts optimistically (OCC), using a separate **Resolver** role specifically to check for conflicting key ranges across concurrent transactions.
- **Storage layer**: a horizontally scalable set of storage server processes, each holding a shard of the key space (typically backed by a local B-tree engine now called **Redwood**, historically SQLite), replicated for durability.
- Exposes only a minimal **ordered key-value API with strictly serializable multi-key transactions** — deliberately no SQL, no secondary indexes, no query language built in, leaving those as **layers** built on top (Apple's own document/record layers, and third-party projects, implement richer data models atop FoundationDB's transactional KV core).

**Impact:** The deterministic simulation testing methodology has become widely admired and imitated across the distributed systems community (several newer distributed databases, including some in the Rust ecosystem, cite FoundationDB's simulation approach directly as inspiration for their own testing infrastructure). The "unbundled" layered architecture (transactional KV core + pluggable data-model layers on top) directly foreshadows the SQL-over-distributed-KV pattern used by CockroachDB and TiDB.

### 3.17 CockroachDB

**Citation:** Taft et al., *"CockroachDB: The Resilient Geo-Distributed SQL Database,"* SIGMOD 2020.

**Problem:** Build an open-source database offering Spanner-like properties (global distribution, strong consistency, SQL, horizontal scalability) **without** requiring Google-proprietary infrastructure like TrueTime's atomic clocks/GPS hardware — making Spanner's guarantees achievable on commodity cloud infrastructure.

**Innovation:** Replace TrueTime with **Hybrid Logical Clocks (HLC)** — a clock design combining physical wall-clock time with a logical counter, giving causality tracking without requiring specialized clock hardware, at the cost of needing an explicit **uncertainty window** and occasional transaction restarts (rather than Spanner's "commit wait") when clock uncertainty could affect ordering.

**Internal Architecture:**
- Data is divided into **ranges** (contiguous key spans, similar to Bigtable tablets/tablets), each replicated (typically 3x) via the **Raft consensus protocol** — one Raft group per range, so the cluster runs many independent Raft groups in parallel rather than one global consensus instance.
- A **SQL layer** sits atop a distributed, transactional key-value store built from these Raft-replicated ranges (directly following the F1-over-Spanner and unbundled-KV pattern from 3.7/3.16) — every SQL row and index entry is encoded into KV pairs.
- **Distributed transactions across ranges** use a variant of two-phase commit, with an MVCC timestamp model and a special "transaction record" tracked per transaction to allow other transactions to determine whether a conflicting write should be pushed, aborted, or waited on.
- Ranges automatically **split** when they grow too large and **rebalance** across nodes based on load and disk usage, giving the elasticity property from Module 2.9 without manual sharding.

**Impact:** The most widely deployed open-source Spanner-inspired NewSQL database; demonstrated that geo-distributed strong consistency was achievable without proprietary hardware, at the cost of a more complex uncertainty-handling and retry model in the transaction layer.

### 3.18 TiDB

**Citation:** Huang et al., *"TiDB: A Raft-based HTAP Database,"* VLDB 2020.

**Problem:** Provide MySQL-compatible horizontal scalability with strong consistency, *and* support real-time analytical queries on the same live transactional data — without the ETL-lag problem described in Module 1.8 (HTAP), all while remaining wire-compatible with the existing MySQL ecosystem (drivers, tooling, ORMs) to ease adoption.

**Innovation:** A **three-layer, HTAP-native architecture**: a stateless MySQL-compatible SQL layer (**TiDB**), a distributed transactional row-store built on Raft (**TiKV**), and a separately maintained, real-time-synchronized **columnar replica** (**TiFlash**) — giving one system both a row-store for OLTP and a column-store for OLAP, kept consistent via Raft log replication rather than batch ETL.

**Internal Architecture:**
- **TiDB layer**: stateless SQL processing/query planning nodes (directly analogous to F1's stateless SQL servers, 3.7), horizontally scalable independent of storage.
- **TiKV layer**: a distributed, Raft-replicated transactional key-value store (originally built on RocksDB as its local single-node storage engine, 3.13) holding row-oriented data, sharded into Regions (Raft groups) analogous to CockroachDB's ranges.
- **TiFlash layer**: a columnar storage extension that acts as a **special type of Raft learner** (a non-voting Raft replica) for selected TiKV Regions — it receives the same Raft log stream as the row-store replicas and asynchronously converts it into a columnar format in real time, giving analytical queries near-real-time access to transactional data without impacting OLTP write latency or requiring a separate ETL pipeline.
- The query optimizer can **automatically route** a query (or parts of a query) to TiFlash's columnar engine when it detects an analytical access pattern, or TiKV's row engine for point lookups — transparent to the application.

**Impact:** One of the most concrete production examples of the HTAP architecture described conceptually in Module 1.8/Module 6, and a widely cited example of using Raft's learner-replica mechanism creatively to solve a problem (real-time row-to-column replication) outside Raft's original design intent.

### 3.19 Cross-Paper Synthesis

Reading all 17 papers together reveals recurring, reusable ideas that keep resurfacing under different names:

| Idea | First seen in | Reused/renamed in |
|---|---|---|
| WAL + physiological logging | ARIES | Every production RDBMS; Aurora's "log is the database" is this idea taken to its logical extreme |
| SSTable + memtable + compaction | Bigtable / LevelDB | RocksDB, TiKV, CockroachDB's Pebble, Cassandra |
| Consistent hashing for rebalancing | Dynamo | Cassandra, DynamoDB, many sharded systems |
| Leaderless replication + quorums | Dynamo | Cassandra, Riak |
| Bounded-uncertainty clocks | Spanner (TrueTime) | CockroachDB/YugabyteDB (Hybrid Logical Clocks — a software-only variant) |
| Stateless SQL layer over distributed KV | F1 (over Spanner) | CockroachDB, TiDB, FoundationDB's "layers" |
| Log shipping instead of page shipping | Aurora | Neon, other cloud-native Postgres forks |
| Deterministic execution to skip commit-time coordination | Calvin | FaunaDB |
| RDMA-based low-latency distributed transactions | FaRM | Various academic follow-up systems |
| Raft/Paxos per-shard consensus | Spanner, CockroachDB, TiKV | Nearly all modern NewSQL systems |
| Learner replicas for cross-format replication | (Raft's general design) | TiFlash's row-to-column real-time sync |
| Deterministic simulation testing | FoundationDB | Increasingly adopted across the distributed-systems research/industry community |

**The single biggest lesson:** almost nothing in modern database research is "new" in isolation — the skill this module builds is recognizing which 2–3 papers' ideas a new system is recombining, and why that particular recombination solves a problem the individual pieces couldn't solve alone.
