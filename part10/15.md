### 15.1 PostgreSQL Internal Questions (Rapid-Fire)

1. What forks a new backend process for each connection? *(Postmaster, Module 3 §3.2)*
2. What's the difference between the Background Writer and the Checkpointer? *(Module 3 §3.7 comparison table)*
3. Why does Postgres need Autovacuum? *(MVCC never overwrites in place, dead tuples accumulate — Module 3 §3.8, Module 5 §5.6)*
4. What two conditions must hold for a HOT update to apply? *(Same page fits, no indexed column changed — Module 3 §3.12)*
5. What does the Visibility Map enable? *(Index-only scans + VACUUM page-skipping — Module 3 §3.13)*
6. Why doesn't plain `VACUUM` shrink the file on disk? *(Space marked reusable in-place, not returned to OS — Module 3 §3.15)*
7. What is transaction ID wraparound, and what prevents it? *(32-bit XID exhaustion; Autovacuum's freezing — Module 3 §3.8)*
8. What's stored in `pg_wal`, and what was it called before Postgres 10? *(WAL segments; `pg_xlog` — Module 12 §12.2)*
9. What is `relfilenode`, and when can it change independently of a table's OID? *(VACUUM FULL, TRUNCATE — Module 12 §12.2)*
10. What does `FILLFACTOR` control, and why would you lower it? *(Page fill %, reserved headroom for HOT — Module 9 §9.6)*

**Fully-worked answer — "Explain what happens if Autovacuum can't keep up on a busy table.":**
> Dead tuples (from `UPDATE`/`DELETE`, Module 5 §5.3) accumulate faster than Autovacuum reclaims them. Consequences cascade: (1) table and index **bloat** — physical size grows well beyond the logical data volume, wasting disk and reducing buffer pool cache effectiveness (Module 6); (2) query planner statistics may go stale if `ANALYZE` (usually bundled with vacuum) also falls behind, leading to poor plan choices (Module 1 §1.4.2, Module 11 §11.5); (3) if the underlying cause is old open transactions preventing cleanup (Module 5 §5.6), this same blocking mechanism also delays advancing the frozen-XID horizon, pushing the table closer to transaction ID wraparound (Module 3 §3.8) — the most severe failure mode, where Postgres can eventually refuse new writes to protect data integrity. Mitigation: identify and terminate/investigate long-running or idle-in-transaction sessions first (`pg_stat_activity`), then consider tuning `autovacuum_vacuum_scale_factor`/`cost_limit` settings to let it work more aggressively.

### 15.2 InnoDB Questions (Rapid-Fire)

1. Why does MySQL use threads per connection instead of processes? *(Lower overhead; trade-off: less isolation — Module 4 §4.1)*
2. Why does the InnoDB Buffer Pool split its LRU into young/old sublists? *(Defend against sequential-scan cache pollution — Module 4 §4.2)*
3. Why does InnoDB need a Doublewrite Buffer if it has a Redo Log? *(Redo log replay assumes an intact page; torn pages aren't fixable by redo alone — Module 4 §4.7)*
4. What does the Change Buffer defer, and for which index types? *(Secondary, non-unique index writes — Module 4 §4.5)*
5. What's a "bookmark lookup"? *(Secondary index → primary key → clustered index, second traversal — Module 4 §4.10)*
6. What's InnoDB's default isolation level? *(REPEATABLE READ — Module 5 §5.7, a common gotcha)*
7. What is the Purge Thread's job, and what blocks it? *(Reclaim old undo records; blocked by long-running transactions — Module 4 §4.8, Module 5 §5.6)*
8. What's the difference between the Redo Log and the Binary Log? *(Storage-engine crash recovery vs. server-level replication/PITR — Module 12 §12.4)*
9. Why do random UUID primary keys hurt InnoDB insert performance? *(Random placement in the clustered B-Tree → frequent page splits — Module 2 §2.3.2, Module 4 §4.10)*
10. What changed about MySQL's metadata storage in version 8.0? *(Unified transactional Data Dictionary, replacing non-transactional `.frm` files — Module 4 §4.13, Module 11 §11.4)*

**Fully-worked answer — "Explain exactly how InnoDB recovers from a crash mid-write to a data page.":**
> On restart, InnoDB first checks each page for signs of a **torn write** (partial write, e.g., via checksum mismatch — Module 2 §2.5). If a page is found torn, InnoDB can't safely apply Redo Log records on top of it (redo assumes an intact starting point), so it first restores that page from its last known-good copy in the **Doublewrite Buffer** (Module 4 §4.7), which was written sequentially just before the real write attempt. Once the page is confirmed intact, InnoDB proceeds with normal Redo Log-based recovery: replaying Redo Log records from the last checkpoint forward (Module 6 §6.7) to bring all pages up to their state as of the last durably-committed transaction. Any transactions that were in-progress (uncommitted) at crash time are then rolled back using their **Undo Log** records (Module 5 §5.5).

### 15.3 Buffer Pool Questions (Rapid-Fire)

1. Why can't a pinned page be evicted? *(In active use — correctness violation risk — Module 6 §6.3)*
2. Why is naive LRU a poor fit for a database buffer pool? *(Expensive to maintain under concurrency + vulnerable to scan pollution — Module 6 §6.5.1)*
3. Explain PostgreSQL's clock-sweep algorithm in one sentence. *(Circular hand decrements usage counts, evicts first zero-usage unpinned frame it finds — Module 6 §6.5.2)*
4. What's the "write-ahead invariant" for dirty pages? *(WAL/redo record must be durably flushed before the corresponding dirty page is flushed — Module 6 §6.4)*
5. Name the three triggers for flushing a dirty page. *(Eviction-time, background, checkpoint — Module 6 §6.6)*
6. What does a checkpoint guarantee, precisely? *("Everything before this point in the log is on disk" — bounds recovery replay — Module 6 §6.7)*
7. What's Postgres's separate mechanism for large sequential scans/VACUUM, distinct from InnoDB's young/old LRU split? *(Ring buffers — Module 6 §6.10)*
8. Why is cache hit ratio an incomplete health metric on its own? *(Doesn't account for the caching-layer stack beneath it, or actual latency — Module 13 §13.3)*

**Fully-worked answer — "A buffer pool's hit ratio is 99% but query latency is still poor. What would you investigate?":**
> First, don't assume the buffer pool is the bottleneck just because its own metric looks healthy — check the **full caching stack** (Module 13 §13.3): is the 1% miss rate, multiplied by request volume, still dominating latency due to disk characteristics (Module 13 §13.1)? Second, check for **lock contention** (Module 1 §1.4.7) — a query can be blocked waiting for a row/table lock entirely independent of buffer pool performance. Third, check for **planner/statistics** issues (Module 1 §1.4.2, Module 11 §11.5) — a bad plan can be slow regardless of how fast page access is. Fourth, check whether the query involves **blocking operators** (Sort, Hash Aggregate build phase — Module 8 §8.2) that are **spilling to disk** (Module 7 §7.5) due to insufficient `work_mem`/`sort_buffer_size` — this would show up in `EXPLAIN ANALYZE` output as "external merge Disk" or similar, and is a very common root cause that a buffer-pool-only investigation would completely miss.

### 15.4 MVCC Internals Questions (Rapid-Fire)

1. What does MVCC solve, and what does it NOT solve? *(Readers don't block writers/vice versa; does NOT solve write-write conflicts — Module 5 §5.1)*
2. What are `xmin`/`xmax`, and what's their InnoDB equivalent? *(Creating/deleting XID; `DB_TRX_ID` + roll pointer — Module 5 §5.2-5.3)*
3. Where do old row versions live in Postgres vs. InnoDB? *(In-heap peer tuples vs. separate undo log — Module 5 §5.3)*
4. State the core visibility rule in one sentence (either engine). *(See Module 5 §5.4's precise formulations)*
5. What determines the difference between Read Committed and Repeatable Read, mechanically? *(When the snapshot is taken — per-statement vs. once-per-transaction — Module 5 §5.7)*
6. Why are both VACUUM and Purge blocked by long-running transactions — bug or fundamental property? *(Fundamental — a version can't be reclaimed if any open snapshot might still need it — Module 5 §5.6)*
7. What is write skew, and does snapshot isolation prevent it? *(An anomaly not prevented by pure snapshot isolation alone — Module 5 §5.7)*

**Fully-worked answer — "Walk through, step by step, how InnoDB reconstructs an old row version for a long-running snapshot.":**
> InnoDB's clustered index holds only the **current** version of a row (Module 5 §5.3). When a transaction with an older Read View needs to read that row, InnoDB first checks the current version's `DB_TRX_ID` against the Read View's visibility rule (Module 5 §5.4): is that transaction ID within the visible range, not in the active list, and before the snapshot's upper bound? If the current version is *not* visible, InnoDB follows the row's `DB_ROLL_PTR` to the most recent **undo log** entry, which contains the prior value(s) and its own `DB_TRX_ID` plus its own roll pointer to an even older version. InnoDB repeats the same visibility check against this reconstructed older version, continuing to walk the chain backward until it finds a version whose creating transaction *is* visible to the Read View, or determines the row didn't exist yet at that snapshot's point in time. This chain-walking cost is exactly why very old open snapshots can degrade read performance on frequently-updated rows — the chain to walk grows with every intervening update.

### 15.5 VACUUM Questions (Rapid-Fire)

1. What are the seven things `VACUUM` mechanically does? *(Scan, identify dead tuples, reclaim space, clean index entries, update Visibility Map, refresh stats, advance frozen-XID horizon — Module 3 §3.15)*
2. `VACUUM` vs. `VACUUM FULL` — name two differences. *(Locking; whether space is returned to the OS — Module 3 §3.15)*
3. Why does the Visibility Map let VACUUM skip pages? *(All-visible pages have nothing to clean — Module 3 §3.13, 3.15)*
4. What's "freezing," and why does it matter? *(Rewriting very old `xmin` to a special always-visible marker, protecting against XID wraparound — Module 3 §3.15)*
5. What real-world symptom suggests VACUUM is falling behind? *(High `n_dead_tup`, growing table size disproportionate to row count, `last_autovacuum` stale — Module 3 §3.8, 3.20)*

**Fully-worked answer — "Why doesn't plain VACUUM shrink a table's file size, and when would you need VACUUM FULL?":**
> Plain `VACUUM` reclaims dead tuple space **for reuse within the table** — it updates the Free Space Map (Module 2 §2.7, Module 3 §3.14) so future `INSERT`s can reuse that space, but it doesn't physically relocate live tuples to compact the file and release trailing empty pages back to the OS, because doing so would require an exclusive lock and data movement — exactly what makes `VACUUM FULL` expensive. `VACUUM FULL` rewrites the entire table into a new, compact file and atomically swaps it in, genuinely shrinking on-disk size, but requires an **exclusive lock** blocking all access for its duration (Module 3 §3.15). You'd reach for `VACUUM FULL` only after severe, already-occurred bloat (e.g., from a period of misconfigured/disabled autovacuum) where the wasted space itself is a problem (disk pressure, buffer pool cache dilution) — not as routine maintenance, since well-functioning autovacuum should prevent needing it in the first place.

### 15.6 Storage Engine Questions (Rapid-Fire)

1. Heap vs. clustered vs. append-only/LSM — name the defining trait of each. *(Module 2 §2.3)*
2. What is a slotted page, and why do the slot directory and tuple data grow from opposite ends? *(Independent growth, meeting at a free-space boundary — Module 2 §2.4)*
3. What's in a page header vs. a tuple header? *(Page-level metadata incl. LSN vs. per-row metadata incl. MVCC fields — Module 2 §2.5-2.6)*
4. What happens when a row is bigger than a page? *(TOAST / overflow pages — Module 2 §2.10)*
5. Name three write amplification sources and three read amplification sources. *(Module 9 §9.7-9.8)*

**Fully-worked answer — "Justify choosing an LSM-tree engine over a B-Tree engine for a specific workload.":**
> For a **high-write-throughput, write-once-read-rarely time-series ingestion workload**, an LSM-tree engine (e.g., RocksDB/Cassandra) is well-justified: writes are turned entirely into **sequential I/O** via append-only memtable flushing (Module 2 §2.3.3), avoiding the random-write costs a B-Tree's in-place page updates and index maintenance would otherwise incur at this write volume. The trade-off — higher **write amplification** from background compaction, and potentially higher **read amplification** from checking multiple SSTable levels per lookup (Module 9 §9.8) — is acceptable here specifically *because* reads are rare and writes dominate; the workload profile directly matches the LSM design's core trade-off. Conversely, for a workload with frequent random-key point lookups and comparatively fewer writes, a B-Tree engine's lower, more predictable read amplification would be preferable, even accepting its own real (but different) write amplification sources — WAL/Redo Log, doublewrite/full-page writes, index maintenance (Module 9 §9.7).

### 15.7 Whiteboard Architecture Questions

*(These are open-ended design prompts — no single "correct" answer, but strong answers should explicitly reference the trade-offs and mechanisms covered across this Part.)*

1. Design the on-disk layout for a new storage engine supporting both fast primary-key lookups and fast range scans on a secondary timestamp column. *(Draw on Module 2's storage models, Module 12's file structure.)*
2. Design a minimal key-value store's engine (not full SQL) — which components from Module 1's architecture are still needed, which can be dropped? *(Parser/Optimizer likely simplified or removed; Buffer Manager, Storage Manager, Recovery Manager, Transaction Manager likely still needed depending on durability requirements.)*
3. Design a buffer pool eviction policy for a workload mixing high-concurrency OLTP with periodic large analytical scans. *(Draw on Module 6's clock-sweep, young/old LRU, and ring buffer approaches — justify a hybrid or a choice among them.)*
4. Design an MVCC garbage collector from scratch — in-heap versioning or undo-log versioning, and why? *(Module 5 §5.13 exercise — justify via workload characteristics.)*
5. Design a monitoring dashboard covering every background process from Module 10, specifying the earliest reliable warning-sign metric for each.
6. Design a compression strategy for a multi-column table with mixed cardinality and size characteristics. *(Module 9 — apply dictionary/prefix/page compression to the right columns.)*

**How to structure a whiteboard answer under time pressure:** State your chosen design in one sentence first, *then* justify with trade-offs — don't narrate your thought process linearly before committing to an answer; interviewers want to see decisiveness backed by reasoning, not exploratory rambling. Explicitly name at least one trade-off you're accepting, unprompted — this signals you understand there's no free lunch, which is often the single most differentiating signal in a whiteboard answer.

### 15.8 Performance Scenarios (Consolidated Diagnostic Bank)

For each scenario, the strong answer identifies **which module's mechanism** is the likely culprit and **what specific evidence** would confirm it — not just a guess.

1. **"A query with `LIMIT 10` is still slow."** → Check for blocking operators (Sort, Hash Aggregate) beneath the `Limit` in `EXPLAIN` output (Module 8 §8.2, §8.11) — `LIMIT` can't save you from an expensive blocking subtree.
2. **"Sort/GROUP BY got much slower after the table grew 10x."** → Check for spill-to-disk evidence (`external merge Disk` / `Using filesort`) — the operation likely now exceeds `work_mem`/`sort_buffer_size` (Module 7 §7.5).
3. **"Table size is 5x larger than expected given row count."** → Bloat from insufficient VACUUM/Purge, likely due to a long-running or idle-in-transaction session (Module 3 §3.8, Module 5 §5.6).
4. **"Insert throughput degraded significantly after switching to random UUID primary keys."** → InnoDB clustered-index page splits from non-monotonic insert order (Module 4 §4.10).
5. **"Buffer pool hit ratio dropped sharply after adding a nightly batch report job."** → Sequential-scan cache pollution; check whether ring buffers (Postgres) or young/old LRU promotion delay (InnoDB) are configured/working as expected (Module 6 §6.5.2-6.5.3).
6. **"Undo tablespace/dead tuple count growing unboundedly despite normal write volume."** → A long-running transaction or stuck replication slot blocking garbage collection (Module 5 §5.6, Module 3 §3.8).
7. **"Redo Log/WAL directory growing unboundedly."** → Checkpoint not completing/keeping pace, OR (Postgres-specific) a replication slot holding back WAL removal (Module 6 §6.7, Module 12 §12.4).
8. **"Query performance is inconsistent on a large multi-socket server, uncorrelated with load."** → Possible NUMA memory-locality effects (Module 13 §13.6).
9. **"Disk write throughput is 4x the application's logical write rate."** → Write amplification — investigate WAL/Redo, doublewrite/full-page-writes, and index maintenance as the layered sources (Module 9 §9.7).
10. **"Secondary index writes are creating unexpected random I/O spikes under heavy insert load (InnoDB)."** → Check whether the Change Buffer is effectively engaged, or whether the indexes involved are unique (Change Buffer doesn't apply to unique indexes — Module 4 §4.5).

### 15.9 Production Debugging Scenarios (Extended Practice Set)

1. A Postgres table's `n_dead_tup` is very high and `last_autovacuum` is `NULL`. Diagnose using Module 3 §3.20's guidance (autovacuum settings, long-running transactions, replication slots).
2. A MySQL server's undo tablespace has grown to 200GB against a 20GB working set. Diagnose using Module 4 §4.18 (likely a long-running transaction blocking Purge).
3. A batch job runs 10x slower in Postgres than an equivalent InnoDB job for the same `UPDATE` workload. Compare using Module 14 §14.4's side-by-side trace — check whether HOT updates (Postgres) are firing as expected (`FILLFACTOR`, indexed columns touched) versus InnoDB's in-place update + Change Buffer behavior.
4. A `DROP TABLE` fails with an unexpected dependency error. Use Module 11 §11.7/§11.13 — query `pg_depend` to identify the actual dependent object.
5. Binlog directory growing rapidly while Redo Log and `.ibd` files stay stable. Use Module 12 §12.14 — check binlog retention settings and replication consumer lag.

### 15.11 MCQ Bank (Consolidated — Answers Provided)

1. A HOT update in PostgreSQL requires: **(b)** the new tuple fits on the same page and no indexed column changed.
2. InnoDB's default transaction isolation level is: **(c)** Repeatable Read.

### 15.12 A Final Consolidated Comparison Table (Everything, One Place)

| Concept | PostgreSQL | InnoDB (MySQL) |
|---|---|---|
| Concurrency model | Process per connection | Thread per connection |
| Table organization | Heap | Clustered by primary key |
| MVCC old versions | In-heap | Undo log |
| Garbage collection | VACUUM / Autovacuum | Purge Thread |
| WAL/Redo | WAL, variable segments | Redo Log, fixed circular |
| Torn-page protection | Full-page writes in WAL | Doublewrite Buffer |
| Secondary index write buffering | N/A (HOT avoids some writes) | Change Buffer |
| Buffer pool eviction | Clock-sweep + ring buffers | Young/old LRU split |
| Hot-lookup acceleration | N/A | Adaptive Hash Index |
| Metadata storage | `pg_catalog` (native SQL tables) | Unified Data Dictionary (8.0+) |
| Default isolation level | Read Committed | Repeatable Read |
| Replication/PITR log | WAL (dual-purpose) | Binary Log (separate from Redo) |
| Buffer pool sizing guidance | ~25% RAM | ~50-75% RAM |
| OS page cache relationship | Relies on it | Typically bypasses (`O_DIRECT`) |
