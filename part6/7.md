# Part 6: Transactions & Concurrency Control

## Module 7: Two-Phase Locking (2PL)

> Module 6 gave us the building blocks — lock types, granularity, the lock manager. But knowing *what* locks exist doesn't tell a transaction *when* to acquire and release them. Get that timing wrong, and you can still end up with non-serializable results even though you're using locks correctly in isolation. **Two-Phase Locking (2PL)** is the protocol that answers "when," and it comes with a beautiful theoretical guarantee: **any schedule produced by 2PL is guaranteed to be conflict serializable.**

---

### 7.1 The Core Idea

**Definition:** **Two-Phase Locking (2PL)** is a concurrency control protocol requiring that every transaction's lock acquisitions and lock releases be split into exactly **two phases**:

1. **Growing Phase:** The transaction may **acquire** locks, but may **not release** any.
2. **Shrinking Phase:** The transaction may **release** locks, but may **not acquire** any new ones.

Once a transaction releases its **first** lock, it has entered the shrinking phase and can **never** acquire another lock for the rest of its life.

```
Lock
Count
  │
  │        ╱\
  │       ╱  \
  │      ╱    \
  │     ╱      \
  │    ╱        \
  │   ╱          \
  └──┴────────────┴──────► Time
    Growing      Shrinking
     Phase        Phase
        ▲
   "Lock Point" — the moment the transaction
   holds its maximum number of locks, right
   before the first release
```

**Why this two-phase structure guarantees serializability:** The key theorem (proven via precedence graph analysis, Module 4) is: *if every transaction in a schedule follows the 2PL protocol, the resulting schedule is guaranteed to be conflict serializable.* Intuitively: once a transaction starts releasing locks, it can no longer "reach forward" and grab new resources — this prevents the kind of back-and-forth interleaving that creates cycles in the precedence graph.

---

### 7.2 Basic 2PL

**Definition:** **Basic 2PL** is the plain version described above: growing phase (acquire only), then shrinking phase (release only) — with locks typically starting to release as soon as a transaction is done using a particular data item, **which can happen before commit**.

**The problem with Basic 2PL:** Because locks can be released *before* commit, a transaction might release a lock on item X, allowing another transaction to read/write X — but then the *first* transaction later **aborts**. Now we're back to the **dirty read / cascading rollback** problem from Module 3 and Module 5! Basic 2PL guarantees conflict serializability, but it does **not** guarantee recoverability or cascadelessness on its own.

**Example — Basic 2PL producing a cascading abort risk:**

```
T1: X-lock(A)  W(A)  unlock(A)                    ABORT
T2:                          X-lock(A)  W(A)  COMMIT

T2 read/wrote A after T1 released its lock, but BEFORE T1 committed.
If T1 aborts, T2's work is now invalid — a cascading rollback situation.
```

This is precisely *why* Basic 2PL, despite its theoretical elegance, is rarely used as-is in production systems.

---

### 7.3 Strict 2PL

**Definition:** **Strict 2PL** adds one crucial rule on top of Basic 2PL: **all Exclusive (write) locks must be held until the transaction commits or aborts** — they cannot be released early during the shrinking phase. (Shared locks may still be released earlier in some variants, but the critical protection is on write locks.)

**Why it exists:** By holding X-locks until commit/abort, Strict 2PL **guarantees the schedule is Strict** (Module 3.8) — no other transaction can read or write a value written by an uncommitted transaction, because the lock physically blocks them until that transaction finishes. This eliminates cascading rollbacks entirely.

```
T1: X-lock(A)  W(A)  ......................  COMMIT/ABORT → unlock(A)
                       (X-lock held for the ENTIRE rest of the transaction)
```

**This is the protocol used by virtually every production RDBMS** for guaranteeing both serializability AND strictness (hence recoverability and cascadelessness for free) simultaneously — it's the practical default, not just a textbook variant.

---

### 7.4 Rigorous 2PL

**Definition:** **Rigorous 2PL** is an even stricter variant: **ALL locks — both Shared AND Exclusive — must be held until commit or abort.** No lock of any kind is released early.

**Difference from Strict 2PL:** Strict 2PL only mandates holding **X-locks** until commit; Shared locks could theoretically still be released earlier. Rigorous 2PL holds **everything** (S and X) until the end.

**Why it matters:** Rigorous 2PL has a nice practical property: the order in which transactions **commit** exactly matches the order in which they would appear in an equivalent serial schedule — this makes reasoning about the system's behavior even simpler, at a (usually small) further cost to concurrency (since Shared locks are held slightly longer than strictly necessary under Strict 2PL alone).

**Industry usage:** Rigorous 2PL (or something functionally equivalent to it) is what most commercial databases actually implement in practice when using lock-based concurrency control (e.g., SQL Server's default `READ COMMITTED` using locks, or any engine's `SERIALIZABLE` level implemented via 2PL) — the practical difference between "Strict" and "Rigorous" rarely matters for correctness, but it's a frequent exam/interview distinction question.

---

### 7.5 Conservative 2PL (Static 2PL)

**Definition:** **Conservative 2PL** requires a transaction to acquire **ALL** the locks it will ever need **before it begins executing any operation** — in one atomic step, all at once. If even one of the required locks isn't currently available, the transaction acquires **none** of them and waits.

**Why it exists:** This variant's key benefit is that it **guarantees deadlock-freedom** — a transaction can never be caught in the middle of execution, holding some locks and waiting for others that are held by a transaction that is, in turn, waiting on it. Since all locks are requested atomically upfront, there's no possibility of the circular wait condition needed for deadlock (Module 12).

**The cost:** Conservative 2PL requires a transaction to know, **in advance**, every single data item it will ever touch — which is often impractical or impossible for complex, conditional application logic (e.g., "update this row, then based on its value, decide which other row to touch next"). This severely limits its practical applicability, and it can also reduce concurrency significantly, since transactions must acquire locks on items they might not even end up needing (if their logic is conditional), and other transactions must wait longer for that upfront lock-grab to complete.

**Real-world analogy:** Conservative 2PL is like a chef who must gather **every single ingredient** for a recipe from the shared pantry *before* starting to cook — even ingredients for a "maybe I'll need this" contingency step — rather than grabbing items as needed while cooking. This avoids ever being caught mid-recipe waiting for an ingredient someone else is using (deadlock), but wastes pantry access time upfront and requires knowing the full recipe before starting.

---

### 7.6 2PL Variants — Comparison Table

| Variant | Lock acquisition timing | Lock release timing | Guarantees serializability? | Guarantees strictness/no cascading? | Guarantees deadlock-freedom? |
|---|---|---|---|---|---|
| **Basic 2PL** | Anytime during growing phase | Anytime during shrinking phase (can start before commit) | ✅ Yes | ❌ No | ❌ No |
| **Strict 2PL** | Anytime during growing phase | X-locks held until commit/abort | ✅ Yes | ✅ Yes | ❌ No |
| **Rigorous 2PL** | Anytime during growing phase | ALL locks held until commit/abort | ✅ Yes | ✅ Yes | ❌ No |
| **Conservative 2PL** | All locks acquired atomically upfront | Anytime after use | ✅ Yes | Depends on combination with strict/rigorous rules | ✅ Yes |

**Key exam takeaway:** *Every* 2PL variant guarantees conflict serializability (that's the whole point of the "two-phase" structure) — what differs between variants is whether they **additionally** guarantee strictness (no cascading rollbacks) and/or deadlock freedom. None of the common variants (Basic, Strict, Rigorous) prevent deadlocks on their own — that's a **separate problem** solved by the mechanisms in Module 12 (deadlock detection/prevention/avoidance), except for Conservative 2PL, which sacrifices practicality specifically to buy deadlock-freedom.

---

### 7.7 Growing Phase and Shrinking Phase — Detailed Walkthrough

**Growing Phase mechanics:**
- The transaction executes its operations.
- Before each read, it acquires (if not already held) a Shared lock on the item.
- Before each write, it acquires (if not already held) an Exclusive lock on the item (possibly via lock conversion from Shared, using an Update lock to avoid conversion deadlock — Module 6.5/6.9).
- The transaction may acquire locks in any order and at any pace, as long as it hasn't released anything yet.

**Shrinking Phase mechanics:**
- Triggered the instant the transaction releases its **first** lock.
- From that point forward, the transaction is **forbidden** from acquiring any new lock — if it needs to touch a new data item after this point, the protocol is violated (and most real implementations simply prevent this by holding locks until commit in the Strict/Rigorous variants, sidestepping the issue).

**Why the "no new locks after first release" rule is essential for serializability:** If a transaction could keep acquiring new locks even after starting to release old ones, it could effectively "reach into the future" and interleave with other transactions' operations in a way that creates cycles in the precedence graph — breaking the very guarantee 2PL is designed to provide. The formal proof of this (via contradiction, assuming a cycle exists and showing it violates the two-phase structure) is a classic advanced GATE/exam topic.

---

### 7.8 2PL and Deadlocks — The Fundamental Trade-off

**Critical exam/interview point:** 2PL (in its Basic, Strict, and Rigorous forms) **guarantees serializability but does NOT guarantee freedom from deadlock.** These are two entirely separate concerns:

- **Serializability** = "is the final result correct?" — solved by the two-phase structure itself.
- **Deadlock-freedom** = "will transactions ever get stuck waiting on each other forever?" — NOT solved by 2PL; requires separate deadlock detection, prevention, or avoidance mechanisms (Module 12).

**Example of 2PL leading to deadlock:**

```
T1: X-lock(A)  ... wants X-lock(B) → BLOCKED (T2 holds it)
T2: X-lock(B)  ... wants X-lock(A) → BLOCKED (T1 holds it)

Both are correctly following 2PL (still in growing phase, never released anything),
yet they are DEADLOCKED — each waiting on a lock the other holds.
```

This is exactly why production systems pair Strict/Rigorous 2PL with a **deadlock detection mechanism** (typically a wait-for graph with periodic cycle checks — full detail in Module 12) that can identify this situation and forcibly abort one of the transactions (the "victim") to break the cycle.

---

### 7.9 Full Worked Example — Strict 2PL Trace

```
T1: BEGIN
    X-lock(A)   -- growing phase
    R(A), W(A)
    X-lock(B)   -- still growing (Strict 2PL: no release yet)
    R(B), W(B)
    COMMIT      -- shrinking phase begins AND ends instantly:
                --   unlock(A), unlock(B) happen together at commit

T2: BEGIN
    X-lock(A)   -- BLOCKED until T1 commits and releases A
    ... (waits) ...
    -- after T1 commits:
    X-lock(A)   -- now granted
    R(A), W(A)
    COMMIT      -- unlock(A)
```

Notice: under Strict 2PL, the "shrinking phase" for a well-behaved transaction is often instantaneous — all locks are released together at commit/abort, rather than being spread out over time. This is precisely why Strict 2PL is so widely used: it combines the theoretical elegance of 2PL's serializability guarantee with the practical safety of never exposing uncommitted data.

### 7.10 Advantages, Disadvantages, Best Practices

**Advantages:**
- Provides a **provable** guarantee of conflict serializability — a rock-solid theoretical foundation.
- Strict/Rigorous variants additionally guarantee strictness (no cascading rollbacks) essentially "for free."
- Conceptually simple to reason about compared to some alternative protocols (Module 8, Module 9).

**Disadvantages:**
- Does not prevent deadlocks — requires pairing with a separate deadlock-handling mechanism.
- Can reduce concurrency, since locks (especially under Strict/Rigorous variants) are held for the transaction's entire duration, blocking others even after a particular item is "done" being used.
- Conservative 2PL, while deadlock-free, is often impractical due to the need to know all locks upfront.

**Best Practices:**
- Access resources in a **consistent global order** across transactions/application code paths to reduce (though not eliminate) deadlock likelihood — a practical mitigation layered on top of Strict 2PL.
- Keep transactions short to minimize how long locks (held until commit under Strict 2PL) block other transactions.
- Use appropriate lock modes (S/U/X, Module 6) to avoid unnecessary conflicts and conversion deadlocks.

**Common Mistakes:**
- Assuming 2PL alone prevents deadlocks — a very common and important misconception to correct in interviews.
- Implementing "Basic 2PL" thinking it's production-safe, without realizing it permits cascading rollbacks.
- Not recognizing that Conservative 2PL's deadlock-freedom comes at the cost of requiring all locks to be known upfront — often impractical for real applications.

**Performance Implications:** Strict/Rigorous 2PL's "hold until commit" rule directly determines how long a hot row stays locked — the single biggest lever affecting throughput under lock-based concurrency control (further explored in Module 16).

**Industry Usage:** Strict 2PL (or Rigorous 2PL) is the practical backbone of lock-based concurrency control in SQL Server's pessimistic locking model, and underlies the `SERIALIZABLE` isolation level's locking-based implementation in many engines (as an alternative to MVCC-based serializable snapshot isolation, covered in Module 10 and Module 11).

---

### 7.11 Chapter Summary

- **2PL** splits every transaction into a **Growing Phase** (acquire only) and a **Shrinking Phase** (release only) — this structural rule guarantees conflict serializability.
- **Basic 2PL**: locks can release early, before commit — risks cascading rollbacks.
- **Strict 2PL**: X-locks held until commit/abort — prevents cascading rollbacks (guarantees Strict schedules).
- **Rigorous 2PL**: ALL locks (S and X) held until commit/abort — commit order matches serial order.
- **Conservative 2PL**: all locks acquired atomically upfront — guarantees deadlock-freedom, but often impractical.
- **2PL guarantees serializability but NOT deadlock-freedom** (except Conservative 2PL) — deadlocks require separate handling (Module 12).

### 7.12 Revision Notes / Cheat Sheet

```
Basic 2PL      : release anytime after growing        → serializable, NOT strict
Strict 2PL     : X-locks held till commit              → serializable AND strict  [MOST COMMON IN PRACTICE]
Rigorous 2PL   : ALL locks held till commit             → serializable AND strict, commit order = serial order
Conservative   : all locks acquired upfront             → serializable AND deadlock-free, but impractical

2PL guarantees:      Serializability ✔
2PL does NOT guarantee: Deadlock-freedom ✘ (except Conservative)
```
