## 11.1 Slow Query Analysis: A Systematic Methodology

### The Diagnostic Framework

```
┌─────────────────────────────────────────────────────────────┐
│              SLOW QUERY DIAGNOSTIC WORKFLOW                    │
└─────────────────────────────────────────────────────────────┘

  1. IDENTIFY the slow query
     (slow query log, APM tooling, pg_stat_statements, etc.)
          │
          ▼
  2. RUN EXPLAIN (ANALYZE, BUFFERS)
     (Module 9) — inside a transaction with ROLLBACK if it's a
     write query!
          │
          ▼
  3. FIND the node with the LARGEST actual time contribution
     (remember: multiply by loops if loops > 1 — Module 9, §9.4.1)
          │
          ▼
  4. CHECK estimated vs. actual rows at that node
     Big gap? → Module 4 (statistics/cardinality) issue
          │
          ▼
  5. CHECK for disk-spill indicators
     (Sort Method: external merge / Batches: N Disk Usage)
     → Module 6/7/8 memory issue
          │
          ▼
  6. CHECK access paths chosen (Module 5)
     Seq Scan where an Index Scan seems "obviously" better?
     Investigate WHY — could be correct (low selectivity) or
     could indicate a missing/unusable index (sargability, §5.10)
          │
          ▼
  7. CHECK join algorithm & order (Module 6, Module 3 §3.3)
     Does the join order make sense given table sizes?
          │
          ▼
  8. FORM A HYPOTHESIS, apply ONE fix, RE-MEASURE
     (never change multiple things at once — you won't know
      which fix actually mattered)
```

### Interview Importance: ⭐⭐⭐⭐⭐
Having a **named, systematic process** (rather than ad-hoc guessing) to describe when asked "walk me through how you'd debug a slow query" is one of the highest-value things you can demonstrate in a senior interview.

## 11.2 Query Rewriting

### Definition

**Query Rewriting** (from the engineer's perspective, distinct from Module 3's automatic optimizer rewrite phase) is the practice of manually restructuring SQL to be more efficient — often because the automatic rewrite/optimization machinery either can't or doesn't reliably apply a particular transformation.

### When Manual Rewriting Beats Relying on the Optimizer

- Deeply nested, multi-level correlated subqueries that some optimizers don't fully decorrelate (Module 3, §3.10).
- Non-sargable predicates wrapping indexed columns in functions (Module 5, §5.10).
- Overly complex `OR` conditions that defeat clean cardinality estimation (Module 4).
- Queries generated by ORMs/BI tools that produce suboptimal structures (excessive joins, redundant subqueries) the optimizer can only partially clean up.

## 11.3 Reducing I/O

### Core Principle

Since I/O (especially random I/O, Module 2 §2.4) is typically the dominant cost factor, the highest-leverage tuning actions are usually the ones that reduce the **number of pages touched**, not just CPU cycles.

### Concrete Techniques

| Technique | Mechanism | Module Reference |
|---|---|---|
| Add a covering index | Enables Index-Only Scan, skips heap entirely | Module 5, §5.3/§5.5 |
| Improve selectivity of filters | Fewer rows/pages need to be read or random-accessed | Module 4, §4.5 |
| Avoid `SELECT *` | Reduces row width, may enable a covering index that wouldn't otherwise apply | Module 3, §3.2 (projection pushdown) |
| Partition large tables | Confines scans to relevant partitions only (partition pruning — related to predicate pushdown, Module 3 §3.1, applied at the storage layer) | Cross-references Part 3 (Storage) |
| Increase cache hit ratio (`shared_buffers`/buffer pool sizing) | More data served from memory instead of disk | Module 9, §9.5; Part 2 |

## 11.4 Choosing Better Joins

### Practical Checklist (Applying Module 6)

- **Is the smaller table correctly identified as the Hash Join build side?** Usually automatic via cost-based optimization, but worth verifying in `EXPLAIN` if performance seems off — a severe cardinality misestimate (Module 4) could cause the optimizer to pick the wrong side.
- **Is there a usable index for an Indexed Nested Loop Join** when one side is small/highly filtered? Missing indexes here are one of the most common, most fixable real-world join performance problems.
- **Are you accidentally forcing a Nested Loop Join** via a non-equality condition that could be rewritten as an equality condition (enabling Hash Join)?
- **Is a Sort-Merge Join possible "for free"** via an existing index that would avoid an explicit sort (Module 6, §6.7)?

### Interview Importance: ⭐⭐⭐⭐

## 11.5 Optimizing WHERE Clauses

### Sargability Checklist (Expanding Module 5, §5.10)

| Non-Sargable (breaks index usage) | Sargable Rewrite |
|---|---|
| `WHERE YEAR(order_date) = 2024` | `WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'` |
| `WHERE UPPER(email) = 'JOHN@X.COM'` | `WHERE email = 'john@x.com'` (normalize case at write time instead) or use a functional index |
| `WHERE amount + 10 > 100` | `WHERE amount > 90` |
| `WHERE column LIKE '%suffix'` | Generally cannot be made sargable for standard B+Tree indexes; consider trigram/full-text index if this pattern is frequent and performance-critical |

### Why This Matters So Much

A non-sargable predicate forces the database to **evaluate the expression for every single row** (defeating index usage, Module 5) rather than allowing a direct index seek — often the difference between milliseconds and minutes on large tables.

### Interview Importance: ⭐⭐⭐⭐⭐
Sargability is one of the most practically important, most frequently tested concepts in real-world query tuning interviews.

## 11.6 Optimizing GROUP BY

### Practical Techniques

- Filter (`WHERE`) **before** grouping whenever possible — reduces the number of rows the aggregation operator (Module 8) needs to process.
- If grouping by a computed expression, consider whether a functional index could enable "sort for free" (Module 5 §5.7 + Module 8 §8.2) for that specific expression.
- For high-cardinality `GROUP BY` columns causing Hash Aggregation to spill (Module 8, §8.1), consider whether Sort Aggregation (potentially via an index) would perform better, or whether increasing memory (`work_mem`) is warranted.

### Interview Importance: ⭐⭐⭐

---

## 11.7 Optimizing ORDER BY

### Practical Techniques

- An index matching the `ORDER BY` columns (in the correct order and direction) can eliminate the sort step entirely (Module 5, §5.7; Module 7).
- For `ORDER BY x LIMIT N` with small N, many optimizers use a specialized **Top-N heapsort**, avoiding a full sort of the entire dataset — worth confirming via `EXPLAIN` rather than assuming a full external sort always happens.
- Multi-column `ORDER BY` requires a **composite index** matching the exact column order/direction to be fully "free" — a partial match (e.g., index on `(a)` for `ORDER BY a, b`) only helps partially.

### Interview Importance: ⭐⭐⭐⭐

## 11.8 Pagination Strategies

### The Problem with `OFFSET`/`LIMIT` Pagination

```sql
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 100000;
```

### Why This Is Slow at Large Offsets

Even though only 20 rows are ultimately returned, the database must typically **compute and discard** the first 100,000 matching rows before it can return rows 100,001-100,020 — the cost of `OFFSET` grows **linearly** with the offset value, regardless of `LIMIT` size. This connects directly to Module 9, §9.4's "Rows Removed by Filter"-style wasted work, though here it's "rows skipped by OFFSET" rather than filtered.

```
OFFSET-based pagination cost profile:
Page 1  (OFFSET 0):      fast
Page 100 (OFFSET 2000):   slower
Page 5000 (OFFSET 100000): SLOW — must still traverse/discard
                            100,000 rows internally
```

### Keyset Pagination (Cursor-Based Pagination) — The Fix

```sql
-- Instead of OFFSET, remember the LAST seen id from the previous page:
SELECT * FROM orders WHERE id > 100020 ORDER BY id LIMIT 20;
```

This transforms the pagination query into a **highly selective, sargable range predicate** (Module 5, §5.10) that can use an index directly — cost stays **roughly constant** regardless of how deep into the result set you are, because the database jumps directly to the right starting point via the index rather than counting through discarded rows.

### Comparison Table

| Aspect | OFFSET/LIMIT | Keyset (Cursor) Pagination |
|---|---|---|
| Cost at deep pages | Grows linearly with offset | Roughly constant |
| Supports "jump to page N directly" | Yes, naturally | Harder (requires knowing the boundary value) |
| Handles concurrent inserts/deletes gracefully | Can skip/duplicate rows if data changes between page requests | More robust to concurrent modifications |
| Implementation complexity | Simple | Slightly more complex (must track last-seen key) |

### Interview Importance: ⭐⭐⭐⭐⭐
The `OFFSET` performance cliff and the keyset pagination fix is an **extremely common, extremely practical interview and real-world topic** — expect this in almost any backend/API design interview touching on databases.

## 11.9 EXISTS vs. IN

### The Comparison

```sql
-- Using IN
SELECT name FROM users WHERE id IN (SELECT user_id FROM orders WHERE amount > 1000);

-- Using EXISTS
SELECT name FROM users u WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 1000
);
```

### Key Differences (Recalling Module 3, §3.8, §3.10)

| Aspect | `IN` | `EXISTS` |
|---|---|---|
| Typical optimizer treatment | Unnested into a semi-join (Module 3, §3.8) — usually just as efficient as `EXISTS` in modern optimizers | Unnested into a semi-join / decorrelated (Module 3, §3.10) |
| NULL handling in the subquery result | `NOT IN` breaks catastrophically with NULLs (Module 3, §3.8's famous gotcha) | `NOT EXISTS` handles NULLs correctly and safely |
| Modern optimizer performance | Often equivalent to `EXISTS` after unnesting, in well-optimized databases | Often equivalent to `IN` after unnesting |

### The Practical Recommendation

For **positive** membership checks (`IN`/`EXISTS`), modern optimizers (PostgreSQL, recent MySQL, Oracle) typically produce **equivalent, well-optimized plans** for both — the choice is often more about readability than performance. For **negative** membership checks, **always prefer `NOT EXISTS` over `NOT IN`** due to the NULL-handling correctness trap (Module 3, §3.8) — this is not just a performance recommendation, it's a **correctness** recommendation.

### Interview Importance: ⭐⭐⭐⭐⭐

## 11.10 JOIN vs. Subquery

### The Comparison

```sql
-- JOIN form
SELECT DISTINCT u.name FROM users u JOIN orders o ON u.id = o.user_id;

-- Subquery form  
SELECT name FROM users WHERE id IN (SELECT user_id FROM orders);
```

### Key Insight

Modern cost-based optimizers (Module 2, Module 3 §3.8) generally **unnest** the subquery form into a semi-join internally — meaning both forms frequently compile down to **very similar or identical execution plans**. The historical folk wisdom "always rewrite subqueries as joins for performance" is **less universally true** with modern optimizers than it once was, though it remains **good practice** for:
- Databases/versions with weaker subquery unnesting (Module 3, §3.10's PostgreSQL/MySQL/Oracle maturity comparison).
- Cases where the subquery form would need `DISTINCT` in the `JOIN` form to avoid row duplication (since a semi-join, unlike a regular join, doesn't duplicate rows for multiple matches — Module 3, §3.8) — this is actually a point **in favor** of the `EXISTS`/`IN` (semi-join) form over a naive `JOIN` + `DISTINCT` rewrite, which can sometimes be *more* expensive due to the extra deduplication step.

### Interview Importance: ⭐⭐⭐⭐
The nuance "this isn't always true anymore with modern optimizers" is a good depth signal versus reciting outdated folk wisdom.

## 11.11 UNION vs. UNION ALL

### The Difference

| Operator | Behavior | Cost |
|---|---|---|
| `UNION` | Combines results AND removes duplicates | Requires an implicit sort/hash-based deduplication step (essentially a `DISTINCT` over the combined results) — extra cost |
| `UNION ALL` | Combines results, keeps duplicates | No deduplication step — much cheaper |

### The Practical Recommendation

**Always use `UNION ALL` instead of `UNION`** unless you specifically need deduplication — this is one of the simplest, most reliably impactful "free" performance wins available, since many developers default to `UNION` out of habit without actually needing duplicate removal.

## 11.12 Additional High-Value Tuning Patterns

### 11.12.1 Avoid Implicit Type Conversions

```sql
-- If order_id is an INTEGER column, but the literal is a string:
WHERE order_id = '12345'   -- may force an implicit cast, breaking sargability
                            -- (behavior varies by database)
```

### 11.12.2 Batch Large Writes

Instead of issuing thousands of individual single-row `INSERT` statements, batch them into fewer, larger statements (`INSERT ... VALUES (...), (...), (...)`) to reduce per-statement parsing/planning overhead (Module 1) and transaction/logging overhead (Part 7 territory).

### 11.12.3 Avoid N+1 Query Patterns (Application-Level, but DB-Adjacent)

A very common application-layer anti-pattern: fetching a list of N parent records, then issuing **N separate queries** (one per parent) to fetch related child records — instead of a single `JOIN` or a single `WHERE parent_id IN (...)` batched query. This is functionally equivalent to manually implementing a very inefficient Nested Loop Join (Module 6, §6.1) **outside** the database, losing all the optimizer's join-algorithm sophistication (Hash Join, Sort-Merge Join, etc.) entirely.

### Interview Importance: ⭐⭐⭐⭐⭐
N+1 queries are an **extremely common, extremely high-value** real-world interview and code-review topic across nearly every backend engineering interview, not just database-specific ones.

## 11.14 Best Practices, Common Mistakes & Edge Cases

### Best Practices
- Always change **one thing at a time** when tuning, and re-measure with `EXPLAIN ANALYZE` after each change — simultaneous changes make it impossible to know what actually helped.
- Prefer fixing root causes (missing index, stale statistics, non-sargable predicate) over "throwing hardware/memory at the problem," which often just delays the same issue at larger scale.
- Test tuning changes against representative data volumes and distributions — a fix validated only on a small dev dataset may behave completely differently at production scale (Module 4's statistics/cardinality concerns scale nonlinearly).

### Common Mistakes
- Adding an index without considering write-path overhead (every index adds cost to `INSERT`/`UPDATE`/`DELETE`) or verifying the optimizer will actually use it for the target query.
- Over-relying on `UNION`/`OFFSET`/`NOT IN` out of habit rather than understanding their specific costs and correctness implications.
- Tuning based on a single anecdotal slow run without checking whether it was a cold-cache fluke (Module 9, §9.12) versus a systemic issue.

### Edge Cases
- Pagination via keyset works cleanly for strictly ordered, unique keys — composite/non-unique sort keys require careful tie-breaking (typically adding a unique column, like `id`, as a secondary sort/comparison key) to avoid skipping or duplicating rows across pages.
- `UNION ALL` is only a safe drop-in replacement for `UNION` when you've verified duplicates genuinely cannot occur or are acceptable for the use case — don't blindly swap without checking correctness first.

## 11.15 Chapter Summary

- Systematic **slow query analysis** (identify → `EXPLAIN ANALYZE` → find the bottleneck node → check cardinality/spill/access-path/join issues → fix one thing → re-measure) is the core methodology of this module.
- **Sargability** (avoiding function-wrapped predicates) is one of the highest-value, most common real-world fixes.
- **Keyset pagination** solves the `OFFSET`'s linear-cost-growth problem, a classic and extremely common real-world performance trap.
- **`NOT EXISTS` over `NOT IN`** is both a correctness fix (NULL handling) and often a performance one.
- **`UNION ALL` over `UNION`** avoids unnecessary deduplication cost when duplicates are acceptable or impossible.
- Modern optimizers often make `JOIN` vs. subquery and `IN` vs. `EXISTS` performance-equivalent via unnesting (Module 3) — much of the old folk wisdom here is less universally true than it once was.
- **N+1 query patterns** are a critical application-level anti-pattern, effectively reimplementing an inefficient manual Nested Loop Join outside the database's optimizer entirely.

## 11.16 Cheat Sheet

```
QUERY TUNING QUICK-REFERENCE
────────────────────────────────
Slow query?             → EXPLAIN (ANALYZE, BUFFERS), find biggest
                           actual-time node, check est-vs-actual rows
Non-sargable predicate?  → rewrite to avoid wrapping indexed column
                            in a function/expression
Deep OFFSET pagination?  → switch to keyset (cursor-based) pagination
NOT IN with subquery?    → switch to NOT EXISTS (correctness + perf)
UNION without need for
  deduplication?          → switch to UNION ALL
N+1 queries in app code? → batch into single JOIN or WHERE IN (...)
Stale statistics after
  bulk load?               → run ANALYZE manually
Sort/Hash spilling to
  disk (EXPLAIN ANALYZE)?  → increase work_mem, or add an index to
                              avoid the sort/hash entirely
```
