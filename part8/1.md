## 1.0 Why This Module Exists

Every time you type a SQL query and hit Enter, something remarkable happens in milliseconds: your English-like declarative sentence — "give me all customers who ordered in the last 30 days" — gets transformed into a precise sequence of low-level operations (scan this file, probe that index, join these two streams, sort this data) that a machine can execute.

You never told the database **how** to do this. You only said **what** you wanted. This gap between "what" and "how" is bridged by **Query Processing**.

This module builds the mental model of that entire journey, step by step, before Module 2 dives into how the optimizer picks the *best* way to do it.

---

## 1.1 What is Query Processing?

### Definition

**Query Processing** is the set of activities involved in translating a high-level declarative query (SQL) into a low-level sequence of operations (an execution plan) that the database engine can physically execute against stored data, and then actually running that plan to produce results.

### Why Does It Exist?

SQL is a **declarative language** — you specify *what* result you want, not *how* to compute it. But physical storage (heap files, B+Trees, hash indexes) only understands imperative, mechanical operations: "read block 42," "compare column X to value Y," "merge these two sorted streams."

Query Processing exists to close this gap. Without it, every application programmer would need to hand-write file scans, index traversals, and join algorithms for every single query — exactly the pain that databases were invented to eliminate.

### The Problem It Solves

Imagine you had to tell a librarian not "find me books on cooking published after 2015" but instead: *"Walk to shelf 3, check every book's copyright page, if it says 'cooking' in the genre tag and year > 2015, put it in the pile, then walk to shelf 4..."* That's absurd for a human, and it's equally absurd to expect application developers to write this by hand for a database. Query Processing automates this translation.

### Real-Life Analogy

Think of Query Processing like ordering food at a restaurant:

- **You (the client):** "I'd like a medium-rare steak with fries." (SQL query — declarative, no cooking instructions)
- **The waiter (Parser):** Writes down your order in a structured ticket, checks it makes sense (they don't take orders for "a purple sound").
- **The kitchen manager (Optimizer):** Decides *how* to cook it — which grill is free, whether to fry potatoes now or after the steak rests — based on current kitchen conditions (statistics).
- **The chefs (Execution Engine):** Actually cook the food following the manager's plan.
- **The plate that arrives (Result Set):** What you actually wanted, without you ever specifying the cooking steps.

## 1.2 The Query Lifecycle (End-to-End Overview)

Before we zoom into each phase, here's the full journey a query takes:

```
┌─────────────────────────────────────────────────────────────────────┐
│                         QUERY LIFECYCLE                              │
└─────────────────────────────────────────────────────────────────────┘

   SQL Text
      │
      ▼
┌──────────────┐   "SELECT * FROM orders WHERE amount > 100"
│  1. PARSING   │   ──────────────────────────────────────────
│  (Lexical +   │   Tokenize → Check grammar → Build Parse Tree
│   Syntax)     │
└───────┬───────┘
        ▼
┌──────────────┐   Does "orders" exist? Does "amount" exist?
│ 2. SEMANTIC   │   Are types compatible? Resolve column/table names
│  ANALYSIS     │   ──────────────────────────────────────────
└───────┬───────┘
        ▼
┌──────────────┐   Parse Tree → Query Tree (relational algebra form)
│ 3. QUERY TREE │   ──────────────────────────────────────────
│  GENERATION   │
└───────┬───────┘
        ▼
┌──────────────┐   Predicate pushdown, subquery unnesting,
│ 4. QUERY      │   constant folding, view merging...
│  REWRITE      │   ──────────────────────────────────────────
└───────┬───────┘
        ▼
┌──────────────┐   Try multiple access paths & join orders,
│ 5. QUERY      │   estimate cost of each using statistics,
│  OPTIMIZATION │   pick the cheapest plan (Module 2-4)
└───────┬───────┘
        ▼
┌──────────────┐   Convert best logical plan → physical operators
│ 6. PLAN       │   (SeqScan, IndexScan, HashJoin, etc.)
│  GENERATION   │
└───────┬───────┘
        ▼
┌──────────────┐   Actually execute operators, pull rows,
│ 7. EXECUTION  │   apply filters, join, sort, aggregate
│  ENGINE       │
└───────┬───────┘
        ▼
   Result Set → returned to client
```

> 💡 **Key Insight:** Steps 1–3 are almost identical across all databases (they're mostly "understanding the query"). Steps 4–6 (rewrite + optimization) are where PostgreSQL, MySQL, and Oracle diverge the most — and where interview questions get interesting.

### Stage-by-Stage Summary Table

| Stage | Input | Output | Primary Goal |
|---|---|---|---|
| Lexical Analysis | Raw SQL text | Stream of tokens | Break text into meaningful units |
| Syntax Analysis | Tokens | Parse tree | Verify grammar correctness |
| Semantic Analysis | Parse tree | Validated parse tree | Verify meaning (tables/columns exist, types match) |
| Query Tree Generation | Validated parse tree | Query tree (relational algebra) | Represent query as relational operations |
| Query Rewrite | Query tree | Optimized (logically equivalent) query tree | Simplify/transform for efficiency |
| Query Optimization | Rewritten query tree | Best execution plan | Choose cheapest physical plan |
| Execution | Execution plan | Result rows | Physically compute the answer |

## 1.3 SQL Parsing

### What is Parsing?

**Parsing** is the process of reading raw SQL text and converting it into a structured, in-memory representation (a **parse tree**) that the rest of the database can work with, while simultaneously checking that the query is grammatically valid.

### Why Does It Exist?

A database engine cannot operate on a raw string like `"SELECT name FROM users WHERE age > 18"`. Strings have no structure a program can traverse. Parsing exists to convert unstructured text into a structured tree the optimizer and executor can walk, inspect, and transform programmatically.

### How Does It Work? (Two Sub-Phases)

Parsing itself has two distinct sub-phases: **Lexical Analysis** and **Syntax Analysis**. Let's cover each.

---

### 1.3.1 Lexical Analysis (Tokenization)

**Definition:** Lexical Analysis (performed by a component called the **Lexer** or **Scanner**) reads the raw SQL string character by character and groups characters into meaningful units called **tokens** — keywords, identifiers, operators, literals, and punctuation.

**Why it exists:** A parser working directly on raw characters (`S`, `E`, `L`, `E`, `C`, `T`, ` `, `*`...) would be needlessly complex. Tokenization abstracts away whitespace, comments, and character-level noise, giving the parser a clean stream of meaningful symbols to work with.

**Example:**

```sql
SELECT name, age FROM users WHERE age > 18;
```

Tokenized into:

| Token Type | Value |
|---|---|
| KEYWORD | SELECT |
| IDENTIFIER | name |
| COMMA | , |
| IDENTIFIER | age |
| KEYWORD | FROM |
| IDENTIFIER | users |
| KEYWORD | WHERE |
| IDENTIFIER | age |
| OPERATOR | > |
| LITERAL (INT) | 18 |
| SEMICOLON | ; |

**Internal working:** The lexer uses a **finite state automaton (FSA)** — the same theoretical concept from Compiler Design / Automata Theory (relevant for GATE!). It scans left to right, matching the longest valid token at each position (this is called **maximal munch**). For example, `>=` is matched as one operator token, not `>` followed by `=`.

**Common mistakes the lexer catches:**
- Unterminated string literals: `'hello`
- Invalid characters: `SELECT @@@ FROM users`

**Interview relevance:** ⭐⭐⭐ (Medium) — Interviewers rarely ask you to write a lexer, but understanding *that tokenization happens before grammar checking* helps explain error messages like `"syntax error at or near ..."`.

---

### 1.3.2 Syntax Analysis (Parsing proper)

**Definition:** Syntax Analysis takes the token stream from the lexer and checks whether it conforms to SQL's **grammar rules** (defined formally using BNF/EBNF — Backus-Naur Form). If valid, it builds a **Parse Tree** (also called a **Concrete Syntax Tree**).

**Why it exists:** Even if every token is individually valid, their *arrangement* might not be. `SELECT FROM WHERE name` has all valid tokens but is grammatically nonsense. Syntax analysis enforces the structural rules of the language.

**How it works:** Databases typically use a **context-free grammar (CFG)** and a parsing algorithm such as:
- **LALR parsing** (Look-Ahead LR) — used by PostgreSQL (generated via a tool called **Bison**, a YACC-family parser generator).
- **Recursive descent parsing** — used by MySQL's parser and many others.

**Example Parse Tree:**

```sql
SELECT name, age FROM users WHERE age > 18;
```

```
                    SELECT_STMT
                   /     |      \
          SELECT_LIST  FROM_CLAUSE  WHERE_CLAUSE
           /      \         |            |
        name      age     users     COMPARISON
                                     /    |    \
                                  age    >     18
```

**PostgreSQL vs MySQL vs Oracle:**

| Database | Parser Technology | Notes |
|---|---|---|
| PostgreSQL | Bison (LALR) + Flex (lexer) | Grammar defined in `gram.y`, very strict ANSI-leaning |
| MySQL | Bison-generated + custom recursive descent for some parts | More lenient with certain non-standard syntax |
| Oracle | Proprietary recursive descent parser | Highly optimized for PL/SQL integration |

**Edge cases:**
- Ambiguous grammar requiring precedence rules (e.g., operator precedence for `AND`/`OR`/`NOT`)
- Dialect-specific syntax (`LIMIT` in MySQL/Postgres vs `ROWNUM`/`FETCH FIRST` in Oracle) — this is why the *same* query text can be a syntax error in one database and valid in another.

**Common mistakes (developer-facing):**
- Missing commas between select-list columns
- Trailing commas before `FROM`
- Mismatched parentheses in subqueries
- Using reserved keywords as identifiers without quoting

**Performance implication:** Parsing is typically **very fast** (microseconds) relative to execution, but it's not free — this is why **prepared statements** (parse once, execute many times with different parameters) exist. We'll revisit this idea when discussing plan caching.

## 1.4 Semantic Analysis

### Definition

**Semantic Analysis** validates that a syntactically correct query is also *meaningful*. It checks things grammar cannot: Do the referenced tables and columns actually exist? Are the data types compatible? Is the user authorized? Does the aggregate usage make sense?

### Why It Exists

A query can be perfectly grammatical yet nonsensical:

```sql
SELECT nonexistent_column FROM users WHERE age > 'abc';
```

This parses fine (it *looks* like a valid `SELECT ... FROM ... WHERE` structure) but fails semantically: the column doesn't exist, and comparing an integer to a string is a type error.

### What Semantic Analysis Checks

| Check | Example Failure |
|---|---|
| Table existence | `SELECT * FROM non_existing_table` |
| Column existence | `SELECT foo FROM users` (no `foo` column) |
| Ambiguous column references | `SELECT id FROM orders JOIN users` (both have `id`) |
| Type compatibility | `WHERE age > 'twenty'` |
| Aggregate/GROUP BY correctness | `SELECT name, SUM(amount) FROM orders` without `GROUP BY name` |
| Privilege/authorization | User lacks `SELECT` grant on table |
| Function signature matching | `UPPER(123, 456)` — wrong arg count |

### Internal Working

Semantic analysis uses the **system catalog** (also called the **data dictionary** — covered in Part 3) to resolve names. This is why `CREATE TABLE` / `DROP TABLE` / schema changes invalidate cached plans — the semantic meaning of a query name (`users`) can change if the underlying object changes.

**Name Resolution Process:**
1. For each table reference in `FROM`, look up the catalog to confirm existence and fetch metadata (columns, types, constraints).
2. For each column reference, resolve which table it belongs to (especially important in joins).
3. Build a **binder** structure that annotates the parse tree with resolved object IDs (OIDs in PostgreSQL) instead of just names — this makes later stages independent of naming and immune to renames mid-processing.

### Real-Life Analogy

Syntax analysis is like a grammar teacher checking "Is this a valid English sentence structurally?" Semantic analysis is like a subject-matter expert checking "Does this sentence actually make sense given real-world facts?" *"The colorless number seven is sleeping"* is grammatically perfect English but semantically absurd — same idea.

### PostgreSQL vs MySQL vs Oracle

| Aspect | PostgreSQL | MySQL | Oracle |
|---|---|---|---|
| Catalog name | `pg_catalog` (system catalog) | `information_schema` + internal dictionary | Data Dictionary (`SYS` schema) |
| Type coercion strictness | Strict, limited implicit casts | More lenient implicit casting | Moderate, with strong implicit numeric/date conversions |
| GROUP BY strictness | Strict (all non-aggregated columns must be in GROUP BY) | Historically lenient (`ONLY_FULL_GROUP_BY` mode toggles this) | Strict |

### Common Mistakes

- Assuming implicit type conversions work the same across databases (they don't!)
- Ambiguous column names in multi-table joins without aliasing
- Forgetting `GROUP BY` strictness differences when migrating between MySQL and PostgreSQL

### Interview Importance: ⭐⭐⭐⭐
Interviewers love asking: *"What's the difference between a syntax error and a semantic error? Give an example of each."* Be ready with the `WHERE age > 'abc'` type example.

## 1.5 Parse Tree

### Definition

A **Parse Tree** (Concrete Syntax Tree) is a tree representation that mirrors the exact grammar structure used to derive the query from the language's formal grammar. Every grammar rule application becomes a node.

### Why It Exists

Text is linear and hard to manipulate programmatically. A tree lets each part of the query (the `SELECT` list, the `WHERE` predicate, the `JOIN` conditions) be inspected, transformed, and validated independently — essential for every subsequent phase.

### Parse Tree vs Abstract Syntax Tree (AST)

A pure parse tree includes *every* grammar rule/token (including things like parentheses and semicolons as nodes), making it verbose. In practice, databases immediately simplify this into an **Abstract Syntax Tree (AST)** — a cleaner version that drops unnecessary syntactic noise but keeps semantic structure.

```
Parse Tree (verbose, grammar-literal)     AST (cleaner, semantic-only)
        SELECT_STMT                              SelectNode
       /    |     \                             /     |     \
  SELECT  SELECT_LIST FROM_CLAUSE      →   [name,age]  users  (age > 18)
    |         |            |
  KEYWORD  column_list   FROM users
```

### Interview Importance: ⭐⭐
Mostly conceptual; know the *difference* between Parse Tree and Query Tree (next section) since interviewers sometimes use these terms loosely and expect you to distinguish them.

## 1.6 Query Tree (Relational Algebra Representation)

### Definition

A **Query Tree** is a tree representation of a query expressed in terms of **relational algebra operators** — `σ` (selection/filter), `π` (projection), `⋈` (join), `∪` (union), `γ` (group/aggregate), etc. — rather than raw SQL grammar constructs.

### Why It Exists

Relational algebra is the **mathematical foundation** of the relational model (this connects back to Part 1's theory foundations). Representing a query this way gives the optimizer a well-understood, formally-defined structure to apply **equivalence rules** to — rules with mathematical guarantees that transformations preserve correctness. SQL grammar structures don't have this property directly; relational algebra does.

### Example

```sql
SELECT name FROM users WHERE age > 18;
```

Query Tree (leaves at bottom, evaluated bottom-up):

```
        π (name)              ← Projection: keep only 'name' column
           │
        σ (age > 18)          ← Selection: filter rows
           │
         users                ← Base relation (table)
```

For a join query:

```sql
SELECT u.name, o.amount
FROM users u JOIN orders o ON u.id = o.user_id
WHERE o.amount > 100;
```

```
              π (name, amount)
                    │
              σ (amount > 100)
                    │
              ⋈ (u.id = o.user_id)
              /                  \
           users                orders
```

### How the Optimizer Uses This

This tree is the **canonical starting point** for optimization. The optimizer applies algebraic equivalence rules (Module 3 covers these in depth: predicate pushdown, join reordering, etc.) to transform this tree into logically-equivalent-but-cheaper trees, then picks physical implementations for each node (Module 6: which join algorithm, which access path).

**Evaluation order:** Trees are evaluated **bottom-up**. Leaves (base tables) are read first, and results flow upward through each operator until the root produces the final result. This bottom-up, node-by-node model is also called the **iterator model** or **Volcano model** (each operator exposes an `open()`/`next()`/`close()` interface) — we'll revisit this in Module 9 (Execution Plans).

### Interview Importance: ⭐⭐⭐⭐⭐
Extremely high. "Draw the query tree / execution tree for this SQL query" is one of the most common senior DB interview and GATE exam questions. Practice converting SQL → relational algebra → tree fluently.

## 1.7 Internal Query Representation

### Definition

Beyond the query tree, real database engines maintain a richer **internal representation** that augments the algebraic tree with metadata needed for optimization and execution: resolved object IDs, data type information, estimated cardinalities, available indexes per table, expression trees for predicates, and more.

### Why It Exists

Relational algebra alone is a *mathematical* abstraction — it doesn't carry engineering details like "which indexes exist on this table" or "how many rows does this table have." The internal representation is the *engineering-grade* version of the query tree, annotated with everything the optimizer will need.

### What's Included

| Component | Purpose |
|---|---|
| Range Table (PostgreSQL term) / Table list | List of all tables/subqueries referenced, with resolved OIDs |
| Target List | Resolved output columns/expressions |
| Qualification (Quals) | WHERE/JOIN/HAVING predicates as expression trees |
| Join Tree | Structure describing how tables connect |
| Sort/Group clauses | ORDER BY / GROUP BY specifications |
| Parameter list | Bind variables for prepared statements |

### PostgreSQL Example (Conceptual)

PostgreSQL's internal representation is literally called a **Query** struct internally, containing a `rtable` (range table), `targetList`, `jointree`, and more. You can actually *see* an approximation of this using:

```sql
EXPLAIN (VERBOSE, FORMAT JSON) SELECT name FROM users WHERE age > 18;
```

This doesn't show the raw internal `Query` struct, but the JSON plan output reveals how the internal representation maps to execution — a good practical way to build intuition.

### Interview Importance: ⭐⭐
Not usually asked to name internal struct fields, but understanding that databases carry *rich metadata* (not just the algebra tree) alongside the query explains how optimizers make informed decisions.

## 1.8 Query Rewrite

### Definition

**Query Rewrite** (also called **Query Transformation**) is the phase where the database applies **logically-equivalent transformations** to the query tree to produce a form that is easier or cheaper to optimize/execute, *before* cost-based plan search begins.

> Note: Module 3 of this handbook is entirely dedicated to Query Transformation techniques (predicate pushdown, subquery unnesting, etc.) in depth. Here we cover the *concept* of why rewrite exists as a distinct phase.

### Why It Exists

Two logically identical queries can be written very differently by developers, and a query as originally parsed is rarely in its most efficient form. Rewriting normalizes and simplifies the tree so the optimizer's search space is smaller and better-behaved. It also handles things that are *impossible* to do well in later phases, such as expanding views.

### Examples of Rewrite (Preview of Module 3)

1. **View Expansion:** A query against a view `SELECT * FROM active_users_view` is rewritten by substituting the view's defining query in place.
2. **Constant Folding:** `WHERE age > 10 + 8` → `WHERE age > 18` (computed once at rewrite time, not per row).
3. **Simplification:** `WHERE TRUE AND age > 18` → `WHERE age > 18`.

### Rule-Based vs Cost-Based Rewrite

Query Rewrite is typically **rule-based** (heuristic) — transformations applied because they are *always* (or almost always) beneficial and cheap to check, regardless of data statistics. This is different from **Cost-Based Optimization** (Module 2), which evaluates *multiple* alternative plans using cost estimates from statistics. Rewrite happens first and narrows/simplifies; CBO happens after and searches/chooses.

```
Original Query Tree
        │
        ▼
 ┌────────────────┐
 │  QUERY REWRITE  │  (rule-based, always applied if valid)
 │  - View expand  │
 │  - Fold consts  │
 │  - Simplify     │
 └────────┬────────┘
          ▼
 Rewritten Query Tree (still logically equivalent, simpler)
          │
          ▼
 ┌────────────────┐
 │ COST-BASED      │  (Module 2: search many physical plans,
 │ OPTIMIZATION    │   pick cheapest using statistics)
 └────────┬────────┘
          ▼
   Best Execution Plan
```

### Interview Importance: ⭐⭐⭐
Know the **distinction** between rewrite (rule-based, always-safe transformations) and optimization (cost-based plan search) — this is a frequently confused pair of terms in interviews.

## 1.9 Execution Engine Overview

### Definition

The **Execution Engine** (also called the **Executor**) is the component that takes the final chosen physical execution plan and actually runs it — reading data from disk/buffer pool, applying filters, performing joins, sorting, aggregating, and streaming results back to the client.

### Why It Exists

Optimization only *decides* what to do; the Execution Engine is what actually *does* it. It's the layer that interacts with storage (Part 1-2), the buffer pool (Part 2), indexes (Part 5-6), and transactions (Part 7).

### The Iterator / Volcano Execution Model

Almost all mainstream relational databases (PostgreSQL, MySQL, Oracle, SQL Server) implement execution using the **Iterator Model**, originally described in the **Volcano** optimizer paper (Goetz Graefe, 1990s). Each node in the physical plan tree is an **operator** exposing a uniform interface:

- `Open()` — initialize the operator (e.g., open a file, position an index cursor)
- `Next()` — produce the next single row (or batch, in vectorized engines) on demand
- `Close()` — release resources

**Pull-based execution:** The root operator calls `Next()` on its child(ren), which recursively call `Next()` on *their* children, all the way down to the leaf (table scan) operators. Data flows **bottom-up**, but *control* flows top-down, one row (or batch) at a time. This is sometimes called **demand-driven** or **pull-based** execution.

```
Client calls: get next row
        │
        ▼
   ┌─────────┐
   │ Project │  Next() called
   │ (name)  │
   └────┬────┘
        │ calls Next() on child
        ▼
   ┌─────────┐
   │ Filter  │  age > 18
   │         │
   └────┬────┘
        │ calls Next() on child
        ▼
   ┌─────────┐
   │ SeqScan │  reads next row from heap file
   │ (users) │
   └─────────┘
```

Each `Next()` call bubbles a **single row** all the way up through the operator tree before the next row starts — this is why this model is also called **row-at-a-time** processing (as opposed to newer **vectorized/batch** execution engines, which process chunks of rows at once for CPU efficiency — a topic for later advanced modules).

### Execution Engine Responsibilities

| Responsibility | Description |
|---|---|
| Access path execution | Perform seq scans, index scans, etc. |
| Join execution | Run chosen join algorithm (Module 6) |
| Expression evaluation | Compute `WHERE`/`SELECT` expressions per row |
| Sorting | External/internal sort as needed (Module 7) |
| Aggregation | Hash/sort based grouping (Module 8) |
| Memory management | Respect `work_mem` (PG) / sort buffers, spill to disk if needed |
| Concurrency control | Coordinate with transaction manager (Part 7) for locks/MVCC |
| Result streaming | Return rows incrementally to the client, not always all-at-once |

### PostgreSQL vs MySQL vs Oracle Execution Engines

| Aspect | PostgreSQL | MySQL (InnoDB) | Oracle |
|---|---|---|---|
| Execution model | Classic Volcano/iterator (row-at-a-time), with some vectorization via extensions | Classic iterator model (row-at-a-time) | Iterator model, with **Rowsource Execution** and optional vectorized modes for analytics |
| Parallelism | Native parallel workers (Gather/Gather Merge nodes) | Limited historically, improving in recent versions | Strong native parallel execution (PX servers) |
| JIT compilation | Yes, for expression evaluation in complex queries (since PG 11) | No | Yes, in some contexts |

### Interview Importance: ⭐⭐⭐⭐⭐
The Iterator/Volcano model (`Open`/`Next`/`Close`, pull-based execution, bottom-up data flow) is a **classic Senior SDE-2/SDE-3 and database-engineer interview topic.** Be ready to explain it and draw the operator tree with `Next()` calls.

## 1.10 Putting It All Together: Full Walkthrough Example

Let's trace one query through **every** phase of this module.

```sql
SELECT u.name, o.amount
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.amount > 100 AND u.age > 18;
```

| Phase | What Happens |
|---|---|
| **1. Lexical Analysis** | Tokenized into `SELECT`, `u.name`, `,`, `o.amount`, `FROM`, `users`, `u`, `JOIN`, `orders`, `o`, `ON`, ... |
| **2. Syntax Analysis** | Grammar validated; Parse Tree built representing `SELECT_STMT → SELECT_LIST, FROM_CLAUSE(JOIN), WHERE_CLAUSE(AND)` |
| **3. Semantic Analysis** | Confirms `users`/`orders` exist, `u.id`, `o.user_id`, `o.amount`, `u.age` resolve to real columns with compatible types, aliases `u`/`o` bound correctly |
| **4. Query Tree Generation** | Converts to relational algebra: `π(name, amount) → σ(amount>100 ∧ age>18) → ⋈(u.id=o.user_id) → {users, orders}` |
| **5. Query Rewrite** | Predicate `age>18` may be **pushed down** to apply directly on `users` before the join (Module 3 detail) |
| **6. Query Optimization** | Optimizer estimates cost of: seq scan vs index scan on each table; hash join vs nested loop vs merge join; join order (users first or orders first) — picks cheapest (Modules 2, 4, 6) |
| **7. Plan Generation** | Produces physical plan, e.g.: `HashJoin(IndexScan(orders, amount>100), SeqScan(users, age>18))` |
| **8. Execution** | Executor calls `Next()` top-down; rows flow bottom-up through scan → filter → join → project; results streamed to client |

### Execution Plan Diagram (Physical, Preview of Module 9)

```
                    Project (u.name, o.amount)
                              │
                        Hash Join (u.id = o.user_id)
                       /                        \
              Seq Scan (users)           Index Scan (orders)
              Filter: age > 18           Cond: amount > 100
```

> This is exactly the kind of tree `EXPLAIN` shows you in PostgreSQL — we'll learn to read these fluently in Module 9.

## 1.11 Comparison Table: Terms That Get Confused

| Term | What It Actually Means | Common Confusion |
|---|---|---|
| Parse Tree | Grammar-literal tree from syntax analysis | Confused with Query Tree |
| Query Tree | Relational-algebra tree (σ, π, ⋈) | Confused with Execution Plan |
| Logical Plan | Query tree describing *what* to do, engine-agnostic operations | Confused with Physical Plan |
| Physical Plan / Execution Plan | Query tree with concrete algorithms chosen (SeqScan vs IndexScan, HashJoin vs NestedLoop) | Confused with Logical Plan |
| Query Rewrite | Rule-based, always-valid simplification | Confused with Cost-Based Optimization |
| Query Optimization | Cost-based search over alternative physical plans | Confused with Query Rewrite |

## 1.12 Best Practices, Common Mistakes & Edge Cases

### Best Practices
- Use **prepared statements** / parameterized queries when running the same query shape repeatedly — this allows the database to reuse parsing and (sometimes) plan work, and importantly, prevents SQL injection.
- Keep predicates in standard, sargable forms (avoid wrapping indexed columns in functions) so semantic analysis and later optimization phases can reason about them cleanly — more on this in Module 5.
- Use `EXPLAIN` early during development to understand how your SQL is being translated internally, not just to check correctness of results.

### Common Mistakes
- Assuming SQL executes in the order you wrote it (`SELECT`, then `FROM`, then `WHERE`) — logically, SQL is evaluated conceptually as `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`, but the **query tree/optimizer** may reorder physical operations entirely differently for efficiency, as long as the result is equivalent.
- Believing parsing/semantic analysis errors and runtime/data errors are the same category of problem (they're caught at completely different phases).
- Forgetting that views are *expanded* at rewrite time — so querying a view isn't inherently "slower" or a black box; the optimizer sees straight through it in most cases (Oracle, PostgreSQL, MySQL all do view merging where possible — detailed in Module 3).

### Edge Cases
- **Dynamic SQL** built via string concatenation bypasses prepared-statement plan reuse and re-parses every time — a common performance pitfall in application code.
- **Correlated subqueries** complicate query tree generation because the inner query references the outer query's columns — this requires special handling (decorrelation), covered fully in Module 3.
- **Ambiguous column names** across joined tables with identical column names must be resolved during semantic analysis or explicitly rejected.

## 1.13 Chapter Summary

- **Query Processing** is the umbrella term for turning declarative SQL into executable low-level operations and running them.
- The pipeline is: **Lexical Analysis → Syntax Analysis → Semantic Analysis → Query Tree Generation → Query Rewrite → Query Optimization → Plan Generation → Execution**.
- **Lexical Analysis** tokenizes; **Syntax Analysis** checks grammar and builds a Parse Tree; **Semantic Analysis** checks meaning using the system catalog.
- The **Query Tree** represents the query in relational algebra (σ, π, ⋈) — the mathematical foundation optimizers reason about.
- **Internal Query Representation** augments the tree with engineering metadata (resolved IDs, types, expressions).
- **Query Rewrite** applies rule-based, always-safe transformations before cost-based optimization narrows down the actual physical plan.
- The **Execution Engine** typically uses the **Iterator/Volcano model**: pull-based, `Open()/Next()/Close()`, row-at-a-time (or vectorized in newer engines), bottom-up data flow with top-down control flow.

---

## 1.14 Cheat Sheet

```
SQL TEXT
   → [Lexer]      → Tokens
   → [Parser]     → Parse Tree           (grammar check)
   → [Binder]     → Semantically valid tree (catalog check)
   → [Translator] → Query Tree            (relational algebra)
   → [Rewriter]   → Simplified Query Tree (rule-based)
   → [Optimizer]  → Best Logical+Physical Plan (cost-based)
   → [Executor]   → Results (Volcano/iterator model, pull-based)
```

**Remember the acronym: L-S-S-Q-R-O-E** (Lexical, Syntax, Semantic, Query-tree, Rewrite, Optimize, Execute)
