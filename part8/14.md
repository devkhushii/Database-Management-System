## 14.10 High-Frequency "Gotcha" Questions (Cross-Module)

These are the specific traps and nuances most likely to distinguish surface-level knowledge from real depth — review this list right before an interview.

| # | Gotcha | Module |
|---|---|---|
| 1 | `NOT IN` + NULL returns ZERO rows for the entire query | Module 3, §3.8 |
| 2 | Predicate pushdown past an OUTER JOIN can change semantics | Module 3, §3.1 |
| 3 | Averaging partial averages across parallel workers is mathematically wrong | Module 8, §8.6 |
| 4 | PostgreSQL is heap-organized by default; MySQL InnoDB is ALWAYS clustered on PK | Module 5, §5.7 |
| 5 | `Gather` has NO order guarantee; `Gather Merge` does | Module 10, §10.6.1-§10.6.2 |
| 6 | `EXPLAIN ANALYZE` actually EXECUTES writes (`INSERT`/`UPDATE`/`DELETE`) | Module 9, §9.10 |
| 7 | `loops > 1` means `actual time`/`actual rows` are PER-LOOP AVERAGES | Module 9, §9.4.1 |
| 8 | PostgreSQL core has NO traditional hints — deliberate design choice | Module 12, §12.5 |
| 9 | `SET enable_seqscan = off` is a SOFT cost penalty, not a hard forbid | Module 12, §12.5 |
| 10 | Index-Only Scan in PostgreSQL still depends on the Visibility Map | Module 5, §5.3 |
| 11 | The independence assumption for `AND` selectivity often fails for correlated columns | Module 4, §4.5.1 |
| 12 | `OFFSET` cost grows LINEARLY with offset value, regardless of `LIMIT` | Module 11, §11.8 |
| 13 | A Sort node's startup cost ≈ total cost (must fully sort before first row) | Module 9, §9.3 |
| 14 | PostgreSQL uses System-R-style DP + GEQO, NOT Cascades | Module 2, §2.9 |
| 15 | `COUNT(DISTINCT)` is NOT simply decomposable across parallel partitions | Module 8, §8.6 |

## 14.11 The "Explain Everything" Master Synthesis Exercise

The single highest-value practice exercise for a senior interview: given ONE moderately complex query, explain **every stage** it passes through, citing every module. Practice this exact exercise repeatedly with different queries.

### Practice Query

```sql
SELECT c.name, SUM(o.amount) AS total
FROM customers c
JOIN orders o ON c.id = o.customer_id
WHERE o.status = 'ACTIVE' AND o.order_date >= '2026-01-01'
GROUP BY c.name
ORDER BY total DESC
LIMIT 10;
```

### The Full Synthesis Template (Fill This In For Any Query)

```
1. PARSING (Module 1, §1.3)
   → Lexical/syntax analysis produces a parse tree

2. SEMANTIC ANALYSIS (Module 1, §1.4)
   → Resolves customers/orders/columns against the catalog

3. QUERY TREE (Module 1, §1.6)
   → π(name, SUM(amount)) → γ(GROUP BY name) → σ(status='ACTIVE' AND
     order_date>=...) → ⋈(c.id=o.customer_id) → {customers, orders}

4. QUERY REWRITE (Module 3)
   → Predicate pushdown: status/order_date filters pushed to orders
     leaf, before the join

5. STATISTICS CONSULTED (Module 4)
   → Selectivity of status='ACTIVE' AND order_date>=... estimated
     (watch for independence-assumption risk if these are correlated)

6. ACCESS PATH CHOSEN (Module 5)
   → Likely Index Scan on orders if the combined filter is selective;
     Seq Scan on customers if no filter applies there

7. JOIN ALGORITHM CHOSEN (Module 6)
   → Likely Hash Join if both filtered inputs are large & unsorted;
     Indexed Nested Loop if outer side is small

8. AGGREGATION STRATEGY (Module 8)
   → Hash Aggregation (few distinct customer names relative to table
     size) or Sort Aggregation if input arrives pre-sorted

9. SORT + LIMIT (Module 7, Module 9 §9.3)
   → Sort by total DESC, then LIMIT 10 — watch for Top-N heapsort
     shortcut avoiding a full sort

10. PARALLEL EXECUTION? (Module 10)
    → If table is large enough, Parallel Seq Scan + Gather/Gather
      Merge + Partial/Finalize Aggregate may appear

11. READING THE ACTUAL PLAN (Module 9)
    → EXPLAIN ANALYZE reveals which of the above actually happened,
      with estimated vs actual rows at each stage

12. IF SOMETHING'S WRONG (Module 11)
    → Systematic diagnosis: biggest actual-time node → cardinality
      gap check → disk-spill check → access path/join sanity check

13. IF STILL WRONG AFTER ALL THAT (Module 12)
    → Consider whether a hint is genuinely justified (last resort)
```

### Interview Importance: ⭐⭐⭐⭐⭐
**This is, without exaggeration, the single most valuable exercise in this entire Part 8 handbook.** An interviewer who sees a candidate fluently narrate this full pipeline for an arbitrary query — unprompted, connecting every stage to the right concept — is seeing genuine, integrated, senior-level mastery, not memorized fragments.
