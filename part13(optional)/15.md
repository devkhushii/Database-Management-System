### 15.1 Capstone Scope and Design Goals

**PicoDB's design goals**, stated as explicit tradeoffs (in the spirit of Module 14.6's "every benchmark result is a tradeoff, not a universal win" framing, applied here to a whole system's design):
1. **Correctness over performance** — every component must be provably correct via tests (15.7) before any optimization is considered.
2. **Single-node, single-file** — no distribution (Module 2's shared-nothing/disaggregation patterns are out of scope for this capstone; they're a natural "Part 14" extension, not this module's job).
3. **A real subset of SQL** — `CREATE TABLE`, `INSERT`, `SELECT` (with `WHERE`, `JOIN`, `ORDER BY`, aggregates), `UPDATE`, `DELETE` — enough to be genuinely useful, not enough to require years of work.
4. **ACID via WAL + strict 2PL + a real B+ tree** — following Module 12's toy engine's architecture, but completed: persistent (not in-memory) indexes, working `UPDATE`/`DELETE`, and a join operator.

**What we are explicitly NOT building** (stated plainly, echoing Module 12.10's honesty about scope): no MVCC, no distributed anything, no cost-based statistics beyond Module 12.7's toy version, no crash-safety hardening beyond ARIES's core three phases. This capstone's value is in **integration and verification**, not in adding new mechanisms beyond what Modules 3, 4, and 12 already covered in depth.

### 15.3 Storage Engine — Page-Backed B+ Tree and the Catalog

**Node serialization** — the piece Module 12 left as an exercise:

```python
import pickle

class PageBackedBPlusTree:
    """Same B+ tree algorithm as Module 12.2, but every node read/write
    goes through the BufferPool, so the tree is durable and its
    working set is bounded by buffer pool capacity, not Python heap size."""
    def __init__(self, buffer_pool, root_page_id):
        self.buffer_pool = buffer_pool
        self.root_page_id = root_page_id
        if self._page_is_empty(root_page_id):
            self._write_node(root_page_id, BPlusTreeNode(is_leaf=True))

    def _page_is_empty(self, page_id):
        page = self.buffer_pool.fetch_page(page_id)
        empty = page.data == bytearray(PAGE_SIZE)
        self.buffer_pool.unpin_page(page_id)
        return empty

    def _read_node(self, page_id):
        page = self.buffer_pool.fetch_page(page_id)
        # first 4 bytes: length prefix, rest: pickled node (toy serialization —
        # a real engine uses a fixed binary layout, not pickle, for speed
        # and cross-version stability; pickle is used here purely for clarity)
        length = struct.unpack("I", page.data[:4])[0]
        node = pickle.loads(bytes(page.data[4:4 + length]))
        self.buffer_pool.unpin_page(page_id)
        return node

    def _write_node(self, page_id, node):
        page = self.buffer_pool.fetch_page(page_id)
        blob = pickle.dumps(node)
        page.data[:4] = struct.pack("I", len(blob))
        page.data[4:4 + len(blob)] = blob
        self.buffer_pool.unpin_page(page_id, is_dirty=True)

    # insert/search/range_scan now call self._read_node(page_id) /
    # self._write_node(page_id, node) instead of holding live object
    # references — the algorithm from Module 12.2 is UNCHANGED;
    # only where the nodes physically live has changed. This distinction —
    # same algorithm, different physical binding — is precisely the
    # storage-engine-vs-algorithm separation flagged back in Module 12.2.
```

**The Catalog** — PicoDB's minimal analog of PostgreSQL's `pg_class`/`pg_attribute` (Module 13.1):

```python
class Catalog:
    """Tracks table schemas and which page_id each table's B+ tree root
    lives at — the metadata layer every query (parse → plan → execute)
    consults to resolve table/column names into physical locations."""
    def __init__(self):
        self.tables = {}  # name -> {"columns": [...], "root_page_id": int, "next_key": int}

    def create_table(self, name, columns, root_page_id):
        self.tables[name] = {"columns": columns, "root_page_id": root_page_id, "next_key": 0}

    def next_key(self, table_name):
        info = self.tables[table_name]
        key = info["next_key"]
        info["next_key"] += 1
        return key
```

### 15.4 Query Engine — Completing UPDATE, DELETE, and JOIN

**`UPDATE`/`DELETE` as WAL-logged, tree-mutating operations** — the capstone's second real engineering task, integrating Module 12.4's WAL with Module 15.3's now-persistent tree:

```python
class UpdateOperator:
    def __init__(self, tree, wal, txn_id, key, new_row):
        self.tree, self.wal, self.txn_id = tree, wal, txn_id
        self.key, self.new_row = key, new_row

    def execute(self):
        old_row = self.tree.search(self.key)
        # WAL-first: log before mutating the tree, per the ARIES invariant
        # re-derived concretely in Module 12.4 and Module 3.2
        self.wal.append(self.txn_id, "UPDATE",
                         page_id=self.key, before=str(old_row), after=str(self.new_row))
        self.tree.update(self.key, self.new_row)   # in-place leaf mutation
        return old_row


class DeleteOperator:
    def __init__(self, tree, wal, txn_id, key):
        self.tree, self.wal, self.txn_id = tree, wal, txn_id
        self.key = key

    def execute(self):
        old_row = self.tree.search(self.key)
        self.wal.append(self.txn_id, "UPDATE",
                         page_id=self.key, before=str(old_row), after="")
        self.tree.delete(self.key)   # real engines tombstone-then-compact
        return old_row               # (Module 4.3) rather than eagerly delete;
                                      # PicoDB takes the simpler eager approach
                                      # deliberately, per this module's scope (15.1)


class NestedLoopJoinOperator:
    """The simplest correct join strategy — O(n*m), but correct, and a
    natural place for the Optimizer (12.7) to later compare against a
    hash-join alternative exactly as Module 12.11 Exercise 4 proposed."""
    def __init__(self, left_child, right_child, join_predicate):
        self.left, self.right = left_child, right_child
        self.predicate = join_predicate
        self._right_rows_cache = None

    def open(self):
        self.left.open()
        self.right.open()
        self._right_rows_cache = []
        while True:
            row = self.right.next()
            if row is None:
                break
            self._right_rows_cache.append(row)
        self._left_row = None
        self._right_idx = 0

    def next(self):
        while True:
            if self._left_row is None:
                self._left_row = self.left.next()
                self._right_idx = 0
                if self._left_row is None:
                    return None
            while self._right_idx < len(self._right_rows_cache):
                r = self._right_rows_cache[self._right_idx]
                self._right_idx += 1
                if self.predicate(self._left_row, r):
                    return {**self._left_row, **r}
            self._left_row = None  # exhausted this left row's matches, advance

    def close(self):
        self.left.close()
        self.right.close()
```

### 15.5 Transactions and Recovery — Unchanged in Mechanism, Now Protecting Real Data

**The key capstone insight, worth stating explicitly:** Module 12's `TransactionManager`, `LockManager`, `WriteAheadLog`, and `RecoveryManager` require **zero changes** to work correctly with the now-persistent, page-backed B+ tree — this is the payoff of the layered architecture Module 12 established: the recovery/transaction layer only ever interacts with the storage layer through the WAL's `before`/`after` values and the buffer pool's `flush_page`, never by assuming anything about whether the underlying tree lives in memory or on disk. **A correctly layered database architecture lets you swap out a storage engine's internals without touching the transaction/recovery machinery above it** — the same principle underlying real engines' pluggable storage APIs (MySQL's storage engine interface, PostgreSQL's Table/Index Access Method APIs, Module 13.8).

### 15.6 Complete Capstone Wiring

```python
class PicoDB:
    """The full system, wired end to end."""
    def __init__(self, filename="pico.db"):
        self.disk = DiskManager(filename)
        self.buffer_pool = BufferPool(self.disk, capacity=64)
        self.wal = WriteAheadLog(filename + ".wal")
        self.lock_mgr = LockManager()
        self.txn_mgr = TransactionManager(self.wal, self.lock_mgr)
        self.catalog = Catalog()
        self._next_page_id = 1  # page 0 reserved for catalog metadata

    def create_table(self, name, columns):
        root_page = self._next_page_id
        self._next_page_id += 1
        self.catalog.create_table(name, columns, root_page)
        return PageBackedBPlusTree(self.buffer_pool, root_page)

    def execute_sql(self, sql, txn_id=None):
        own_txn = txn_id is None
        if own_txn:
            txn_id = self.txn_mgr.begin()
        try:
            ast = Parser(tokenize(sql)).parse()
            table_info = self.catalog.tables[ast.table]
            tree = PageBackedBPlusTree(self.buffer_pool, table_info["root_page_id"])

            if isinstance(ast, InsertAST):
                key = self.catalog.next_key(ast.table)
                row = dict(zip(table_info["columns"], ast.values))
                self.lock_mgr.acquire(txn_id, f"{ast.table}:{key}", "X")
                self.wal.append(txn_id, "UPDATE", page_id=key, before="", after=str(row))
                tree.insert(key, row)
                result = None
            elif isinstance(ast, SelectAST):
                optimizer = Optimizer(
                    table_stats={ast.table: {"row_count": table_info["next_key"]}},
                    indexes={ast.table: {"id"}})
                optimizer.plan(ast)   # chosen plan logged; execution below
                                       # uses the tree directly for simplicity
                rows = [v for _, v in tree.range_scan(float("-inf"), float("inf"))]
                scan = SeqScanOperator(rows, ast.where)
                project = ProjectOperator(scan, ast.columns)
                result = execute(project)
            else:
                result = None

            if own_txn:
                self.txn_mgr.commit(txn_id)
                self.buffer_pool.flush_all()
            return result
        except Exception:
            if own_txn:
                self.txn_mgr.abort(txn_id, None)
            raise

    def recover(self):
        RecoveryManager(self.wal, self.disk).recover()
```

### 15.7 Testing PicoDB

**Why testing is its own capstone section, not an afterthought:** a database that "seems to work" in a manual demo (Module 12.9's `demo()`) and a database that's **verified correct** are different claims — this section is where PicoDB earns the right to be called a real, if small, database engine.

**Unit tests — one per component, isolating each layer:**
```python
import unittest

class TestBPlusTree(unittest.TestCase):
    def test_insert_and_search(self):
        disk = DiskManager(":memory-test-1.db")
        bp = BufferPool(disk, capacity=16)
        tree = PageBackedBPlusTree(bp, root_page_id=1)
        for i in range(50):
            tree.insert(i, {"id": i, "val": i * 2})
        self.assertEqual(tree.search(25)["val"], 50)
        self.assertIsNone(tree.search(999))

    def test_range_scan_after_many_splits(self):
        # Deliberately exceeds MAX_KEYS many times over to force several
        # levels of node splitting (Module 12.2's _split_child) — this
        # test exists specifically because split logic is where B+ tree
        # bugs concentrate in practice.
        disk = DiskManager(":memory-test-2.db")
        bp = BufferPool(disk, capacity=16)
        tree = PageBackedBPlusTree(bp, root_page_id=1)
        for i in range(500):
            tree.insert(i, {"id": i})
        results = tree.range_scan(100, 110)
        self.assertEqual([k for k, _ in results], list(range(100, 111)))


class TestRecovery(unittest.TestCase):
    def test_committed_transaction_survives_crash(self):
        # Simulates the exact scenario Module 12.11 Exercise 5 asked for:
        # a committed write must be redone; an uncommitted one must be undone.
        db = PicoDB("test_recovery.db")
        db.create_table("t", ["id", "val"])
        txn = db.txn_mgr.begin()
        db.execute_sql("INSERT INTO t VALUES (1, 'x')", txn_id=txn)
        db.txn_mgr.commit(txn)
        # simulate crash: skip flush_all(), just recover from WAL
        db.recover()
        # after recovery, a fresh read should reflect the committed insert
        result = db.execute_sql("SELECT id, val FROM t")
        self.assertTrue(any(r for r in result))

    def test_uncommitted_transaction_is_rolled_back(self):
        db = PicoDB("test_recovery2.db")
        db.create_table("t", ["id", "val"])
        txn = db.txn_mgr.begin()
        db.execute_sql("INSERT INTO t VALUES (1, 'x')", txn_id=txn)
        # no commit — simulate crash before commit
        db.recover()
        result = db.execute_sql("SELECT id, val FROM t")
        # the uninserted row's key should not be durably visible after undo
        self.assertEqual(len([r for r in result if r.get("id") == 1]), 0)


class TestLocking(unittest.TestCase):
    def test_conflicting_exclusive_locks_block(self):
        lm = LockManager()
        self.assertTrue(lm.acquire(txn_id=1, resource_id="row:1", mode="X"))
        self.assertFalse(lm.acquire(txn_id=2, resource_id="row:1", mode="X"))
        lm.release_all(1)
        self.assertTrue(lm.acquire(txn_id=2, resource_id="row:1", mode="X"))


class TestOptimizer(unittest.TestCase):
    def test_chooses_index_scan_for_large_table_with_equality_predicate(self):
        stats = {"users": {"row_count": 1_000_000}}
        indexes = {"users": {"age"}}
        ast = SelectAST(columns=["*"], table="users", where=("age", "=", 30))
        plan = Optimizer(stats, indexes).plan(ast)
        self.assertIsInstance(plan, IndexScanPlan)

    def test_chooses_seq_scan_when_no_index_exists(self):
        stats = {"users": {"row_count": 1_000_000}}
        indexes = {"users": set()}
        ast = SelectAST(columns=["*"], table="users", where=("age", "=", 30))
        plan = Optimizer(stats, indexes).plan(ast)
        self.assertIsInstance(plan, SeqScanPlan)
```

**Integration tests — full SQL round-trips through `PicoDB.execute_sql`:** verify `CREATE TABLE` → `INSERT` → `SELECT ... WHERE` → `UPDATE` → `SELECT` again reflects the update → `DELETE` → row is gone, each as one test, exercising every layer of the architecture (15.2) together rather than in isolation.

**Crash-injection tests — the most valuable and most often skipped test category:** deliberately kill the process (or simulate it, as `test_committed_transaction_survives_crash` does above) at specific points — after WAL append but before buffer pool flush, mid-transaction before commit, during a B+ tree split — and verify `recover()` always leaves the database in a consistent state. This directly operationalizes Module 3.2's ARIES correctness claims as executable tests rather than theoretical properties.

### 15.8 Benchmarking PicoDB

**Applying Module 14's principles to your own system, concretely, as that module promised:**

```python
import time, random

def benchmark_ycsb_workload_a(db, num_ops=10_000, num_keys=1000):
    """Workload A per Module 14.5: 50% read / 50% update — a direct,
    minimal reimplementation of YCSB's workload-mix concept against PicoDB."""
    for i in range(num_keys):
        db.execute_sql(f"INSERT INTO bench VALUES ({i}, 'v{i}')")

    latencies = []
    start = time.perf_counter()
    for _ in range(num_ops):
        key = random.randint(0, num_keys - 1)
        op_start = time.perf_counter()
        if random.random() < 0.5:
            db.execute_sql(f"SELECT id, val FROM bench WHERE id = {key}")
        else:
            db.execute_sql(f"UPDATE bench SET val = 'v{key}_upd' WHERE id = {key}")
        latencies.append(time.perf_counter() - op_start)
    total = time.perf_counter() - start

    latencies.sort()
    p50 = latencies[len(latencies) // 2]
    p99 = latencies[int(len(latencies) * 0.99)]
    print(f"Throughput: {num_ops/total:.0f} ops/sec")
    print(f"p50 latency: {p50*1000:.3f}ms   p99 latency: {p99*1000:.3f}ms")
    # Reporting p50 AND p99 — not just average throughput — is a direct,
    # deliberate application of Module 14.7's "measure percentiles, not
    # just averages" guidance to this exact benchmark.
```

**What a real benchmarking exercise on PicoDB would additionally need, per Module 14.6's critical-reading checklist, applied honestly to our own system:**
- **Scale factor honesty**: PicoDB's `num_keys=1000` working set almost certainly fits entirely in the buffer pool's 64-page capacity's worth of cached data — exactly the "unrealistically small working set relative to available cache" pitfall Module 14.2/14.6 warned about; a fair benchmark would need `num_keys` large enough to force real buffer pool eviction and real disk I/O.
- **Steady-state warning**: PicoDB has no compaction (it isn't LSM-based), so the "let the system reach steady state" concern from Module 14.7 applies less here than to Module 4's engines — but buffer pool cache warm-up still means the first N operations of any run are not representative of sustained performance and should be discarded from the measurement window.
- **No price/performance metric applies** (Module 14.2/14.6) since this isn't a hardware/vendor comparison — but the same discipline of contextualizing a raw number (here: buffer pool size and working-set size) rather than reporting throughput in isolation, still fully applies.
