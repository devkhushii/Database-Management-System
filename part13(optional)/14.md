# The Ultimate DBMS Handbook — Part 13: Research & Advanced Engineering

## Module 14 — Database Benchmarking

> **Goal of this module:** Understand what each major benchmark actually measures, why it was designed that way, and — just as importantly — how to recognize when a benchmark result is being used to mislead rather than inform. Benchmarking is where database marketing claims get made and unmade; a systems engineer needs to be able to read a benchmark result the way a mechanic reads a used car's odometer — with informed suspicion.

---

### 14.1 Why Standardized Benchmarks Exist

Before standardized benchmarks, vendors published self-selected, favorable performance numbers with no comparability — the **TPC (Transaction Processing Performance Council)**, founded in 1988 by database vendors themselves, exists specifically to define benchmarks with rigorous, audited, publicly documented rules precisely to prevent this — a TPC benchmark result that's officially published has gone through a formal audit process, making TPC results (when properly published, not just "TPC-C-like" self-reported numbers) meaningfully comparable across vendors in a way ad hoc performance claims are not.

**The critical distinction every engineer must internalize: a benchmark measures a workload *shape*, not "how good a database is" in general.** A database can be excellent at TPC-C's workload shape and poor at TPC-H's, or vice versa — the entire value of knowing multiple benchmarks is being able to match a benchmark's workload shape to your actual production workload shape, not picking whichever benchmark makes a favorite vendor look best.

---

### 14.2 TPC-C — OLTP Benchmark

**What it models:** an order-entry system for a wholesale supplier — warehouses, districts, customers, orders, order-lines, stock — a deliberately realistic, moderately complex transactional schema (9 tables) rather than a toy schema.

**The five transaction types, and their mix ratio (fixed by the spec, not chosen by the tester):**
- **New-Order** (~45%): a customer places a new order — the "heaviest" transaction, touching multiple tables and requiring several rows to be read/written.
- **Payment** (~43%): a customer makes a payment against their account.
- **Order-Status** (~4%): a read-only query of a customer's most recent orders.
- **Delivery** (~4%): a batch transaction processing pending orders for delivery (this one is intentionally allowed to be deferred/queued rather than done synchronously, testing batch-transaction handling).
- **Stock-Level** (~4%): a read-only query checking recent stock levels against a threshold.

**Why the fixed mix ratio matters:** it prevents a vendor from "gaming" the benchmark by only optimizing for the easiest transaction type — the mix is a core, non-negotiable part of the spec precisely to keep the benchmark honest about testing a *realistic combined workload*, not a cherry-picked single query type.

**The metric: tpmC (transactions per minute, specifically New-Order transactions per minute)**, subject to strict **response time constraints** (a percentage of transactions of each type must complete within a specified time limit) — a system can't simply batch/queue everything to inflate raw throughput while ignoring latency; the benchmark's rules explicitly prevent that.

**Scaling rule — the warehouse count:** the benchmark's data size and load scale together via the number of configured "warehouses" (each warehouse's data is a fixed, specified size) — this is deliberate, and it's the origin of one of the most common **misleading benchmark practices**: publishing an impressive tpmC number while quietly using far more warehouses (hence far more total data and far more hardware/memory) than a realistic deployment would need, effectively making the whole working set fit comfortably in RAM in a way a real production deployment's actual data volume might not — always check the warehouse count and total data size alongside the headline tpmC number.

### 14.3 TPC-H — Decision Support (Analytical) Benchmark

**What it models:** a business decision-support / data-warehousing workload — ad hoc, complex analytical queries against a schema modeling a wholesale supplier's business data (parts, suppliers, customers, orders, line-items — a different, larger-scale schema than TPC-C's OLTP schema, generated at a chosen **scale factor**, e.g., SF100 = ~100GB of raw data).

**The 22 query templates:** TPC-H doesn't test one query — it defines **22 fixed query templates**, each with substituted parameters (drawn from a specified randomized range) at benchmark execution time — these templates deliberately span a wide range of analytical query patterns: large aggregations, multi-way joins, correlated and uncorrelated subqueries, and complex `GROUP BY`/`HAVING` combinations, specifically designed to stress a query optimizer's ability to choose good join orders and access paths (directly the planner concerns from Module 13.3) under genuinely complex, business-realistic query shapes rather than simplified benchmark-friendly queries.

**The two execution modes, both required for an official result:**
- **Power test**: runs the 22 queries sequentially, one at a time, measuring raw single-stream query throughput.
- **Throughput test**: runs multiple concurrent query streams simultaneously (plus concurrent "refresh functions" simulating ongoing data loads), measuring the system's ability to sustain analytical query performance under concurrent multi-user load — a meaningfully different stress pattern than the power test, and why both are required.

**The composite metric (QphH@Size — Query-per-Hour performance at a given scale factor)** combines both test results, specifically to prevent a vendor from optimizing narrowly for one execution mode (e.g., tuning purely for single-query latency while ignoring concurrent throughput, or vice versa) at the expense of the other.

**A crucial, commonly-missed methodology note:** TPC-H's per-query templates allow (and expect) query optimizer-level tuning specific to the fixed template structure — this has led to legitimate debate in the research community about how representative TPC-H's specific, fixed query shapes remain for genuinely ad hoc analytical workloads that don't repeat the same 22 templates; this is part of the motivation behind TPC-DS (14.4), designed to be harder to over-fit to.

### 14.4 TPC-DS — Modern Decision Support Benchmark

**What it improves on TPC-H:** TPC-DS uses a considerably larger, more realistic **snowflake schema** (dozens of tables, modeling a retail enterprise across multiple sales channels — store, web, catalog), **99 distinct query templates** (versus TPC-H's 22) spanning a much broader range of analytical patterns including reporting queries, ad hoc queries, iterative OLAP queries, and data mining-style queries — deliberately engineered to be much harder to over-tune for a narrow, fixed query set the way some TPC-H criticism (14.3) suggested was possible.

**Additional realism TPC-DS adds beyond TPC-H:**
- **Multiple sales channels** in one schema, modeling genuinely complex real enterprise data relationships rather than TPC-H's simpler single-channel wholesale model.
- **Data maintenance operations** (`INSERT`/`DELETE` operations interspersed with query execution) modeling the reality that real data warehouses are continuously being loaded/updated even while being queried — directly relevant to the ETL-staleness concerns discussed in Module 1.8/Module 6.
- **Skewed data distributions** deliberately built into the data generator, specifically to stress query optimizers' cardinality estimation (Module 11.4/13.3) under realistic, non-uniform data — TPC-H's more uniform data generation was considered a weaker stress test of this specific, practically crucial optimizer capability.

**Why TPC-DS is now the more commonly cited benchmark for modern cloud data warehouses (Snowflake, BigQuery, Redshift, Databricks)** specifically: it more faithfully represents the query and schema complexity these systems are actually built and marketed for, and its size/complexity make it much harder to "benchmark-special-case" the way a narrower, older benchmark could be gamed.

### 14.5 YCSB — Yahoo! Cloud Serving Benchmark

**Citation:** Cooper et al., *"Benchmarking Cloud Serving Systems with YCSB,"* SoCC 2010.

**Why YCSB exists as a distinct category from TPC-C/H/DS:** the TPC benchmarks predate (and are architecturally oriented around) traditional relational systems with full ACID transactions and complex joins — YCSB was built specifically to benchmark the **NoSQL systems (Module 1.6)** that emerged in the 2000s (Cassandra, HBase, DynamoDB-style systems, MongoDB), which typically don't support the complex multi-table joins TPC-H/DS require, and whose key differentiator is **simple-operation throughput and latency at massive horizontal scale**, not complex query optimization.

**Core design: a small set of simple CRUD-style operations (read, insert, update, scan, read-modify-write) against a single, simple key-value-style table**, with **configurable workload mixes ("Workload A" through "Workload F")** representing different realistic access patterns:
- **Workload A** (50% read / 50% update) — models a session-store-like workload.
- **Workload B** (95% read / 5% update) — models a photo-tagging-like, mostly-read workload.
- **Workload C** (100% read) — models a pure cache/lookup workload.
- **Workload D** (read-latest, 95%/5% read/insert) — models a status-update-feed-like workload where the most recently inserted records are disproportionately read.
- **Workload E** (short-range scans, 95%/5% scan/insert) — models a workload with threaded-conversation-like range queries.
- **Workload F** (read-modify-write) — models a workload needing a read followed by a conditional write back to the same record.

**Why the configurable-workload-mix design matters:** unlike TPC-C's single fixed transaction mix, YCSB's explicit multiple named workloads let an engineer pick the workload closest to their actual production access pattern, rather than being forced to interpret one fixed, possibly-irrelevant workload shape — an explicit acknowledgment that NoSQL systems serve a much wider variety of access-pattern-specific use cases than the relatively uniform "order-entry system" TPC-C models.

**YCSB's key limitation, stated plainly:** it deliberately does **not** test complex queries, joins, or multi-record ACID transactions — this isn't an oversight, it's a scope decision reflecting what NoSQL systems of that era typically didn't offer; benchmarking a modern NewSQL system (Module 1.7) that *does* offer distributed ACID transactions and richer queries against pure YCSB will understate a meaningful part of what such a system actually needs to be evaluated on, which is why **YCSB+T** (an extension explicitly adding transactional workloads) and various vendor-specific extended benchmark suites have emerged to fill this gap.

### 14.6 Reading a Benchmark Result Critically — A Checklist

This section is arguably the most practically valuable part of the module — the specific things to check before trusting *any* published benchmark number, vendor or otherwise:

1. **Is it an officially audited TPC result, or a "TPC-C-like" / "based on TPC-H" self-reported number?** Only the former has gone through independent verification; the latter can (and often does) quietly deviate from the spec in ways that favor the publisher.
2. **What's the scale factor / warehouse count, and does it correspond to a realistic working-set-to-RAM ratio?** As noted in 14.2, an unrealistically small working set relative to available RAM can make a benchmark result reflect "how fast is your RAM" rather than "how fast is your storage/query engine under realistic data volumes."
3. **What hardware and what price was used?** TPC officially requires a **price/performance metric** alongside raw throughput specifically because raw throughput without cost context is easy to inflate with simply more/better hardware — a result's price/performance metric (dollars per tpmC, for instance) is often more informative than the headline throughput number alone.
4. **Was the query optimizer/configuration tuned specifically for this exact benchmark's fixed query set (especially relevant for TPC-H's 22 fixed templates, 14.3), and would that tuning generalize to your actual, different queries?**
5. **Does the benchmark's workload shape (OLTP vs. analytical vs. simple-CRUD-at-scale) match your actual production workload shape at all?** A stellar YCSB Workload C (pure read) result says very little about a system's suitability for a write-heavy, join-heavy workload, and vice versa.
6. **Is this a first-party (vendor's own) benchmark or a third-party, independently reproduced one?** Vendor-published results, even when spec-compliant, are inherently more likely to reflect a configuration tuned to that vendor's specific strengths.

### 14.7 Benchmarking Your Own System — Practical Guidance

Beyond interpreting published TPC/YCSB numbers, engineers frequently need to benchmark a *specific* system for a *specific* production decision — the following principles generalize across all the specific benchmarks above:

- **Benchmark with your actual (or a faithfully representative sample of your actual) data distribution**, not synthetic uniform data — Module 13.3 and Module 14.4 both underscore how badly skewed real data can break cost/cardinality assumptions that uniform synthetic data won't expose.
- **Measure latency percentiles (p50, p95, p99), not just averages/throughput** — a system can have excellent average throughput while having unacceptable p99 tail latency (a classic hidden problem, since averages hide exactly the outlier behavior that hurts real users most) — this connects directly to Module 9.3.1's watermark/latency tradeoff discussion and Module 2's elasticity discussions, where tail latency under load is often the actual production-critical metric.
- **Run for long enough to reach steady state**, including letting caches warm and (for LSM-tree-based systems, Module 4) letting compaction reach its steady-state behavior — a benchmark run that's too short can measure an unrealistically favorable "cold start, no compaction backlog yet" state rather than sustained production behavior.
- **Test failure/degraded scenarios, not just the happy path** — throughput/latency *during* a node failure, network partition, or compaction storm is frequently the number that actually matters for a production SLA, and is almost never what a standard benchmark headline number reports.

### 14.8 Production Examples & Industry Usage

| Benchmark | Where it's cited in real vendor comparisons |
|---|---|
| TPC-C | Traditional OLTP database vendor comparisons (Oracle, SQL Server, and NewSQL vendors like CockroachDB/TiDB publishing tpmC-style results) |
| TPC-H | Legacy data warehouse comparisons; still referenced though increasingly superseded by TPC-DS for modern cloud warehouses |
| TPC-DS | Snowflake, BigQuery, Databricks, Redshift comparisons — the current standard for cloud data warehouse benchmarking |
| YCSB | NoSQL vendor comparisons (Cassandra, MongoDB, DynamoDB, HBase) and increasingly used to benchmark NewSQL systems' simple-operation performance alongside their transactional benchmarks |

### 14.10 MCQs

**Q1.** The purpose of TPC-C's fixed transaction mix ratio (New-Order ~45%, Payment ~43%, etc.) is to:
A) Make the benchmark easier to run
B) Prevent vendors from optimizing narrowly for the easiest transaction type, keeping the benchmark representative of a realistic combined workload
C) Reduce data size requirements
D) Eliminate the need for response time constraints

*Answer: B*

**Q2.** TPC-H requires both a "power test" and a "throughput test" because:
A) They test the same thing twice for reliability
B) They stress genuinely different aspects — single-stream query latency versus sustained concurrent multi-user analytical performance
C) One is optional
D) It doubles the scale factor

*Answer: B*

**Q3.** TPC-DS improves on TPC-H primarily by:
A) Using fewer query templates
B) Using a larger, more complex schema, 99 query templates, and deliberately skewed data to stress cardinality estimation and resist over-fitting
C) Removing the need for a schema entirely
D) Only testing OLTP workloads

*Answer: B*

**Q4.** YCSB was created specifically to address:
A) TPC-C's transaction mix being too simple
B) The lack of a benchmark suited to NoSQL systems' simple-operation, massive-horizontal-scale workloads that don't fit TPC's relational/join-oriented design
C) TPC-H's use of SQL
D) The need for a benchmark with zero configurability

*Answer: B*

**Q5.** A published benchmark result using an unusually small working set relative to available RAM most likely:
A) Accurately reflects real-world storage-layer performance at production data volumes
B) Risks measuring "how fast is your RAM" rather than realistic storage/query engine performance at production scale
C) Is always invalid regardless of context
D) Has no impact on the result's interpretation

*Answer: B*
