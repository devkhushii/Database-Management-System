# Part 6: Transactions & Concurrency Control

## Module 6: Lock-Based Concurrency Control

> Module 5 catalogued everything that can go wrong. Now we start building the machinery that *prevents* it. Locking is the oldest, most widely deployed concurrency control mechanism in relational databases — this module covers the lock manager, lock types, granularity, and the rules governing how locks interact.

---

### 6.1 The Lock Manager

**Definition:** The **Lock Manager** is a component inside the database engine responsible for tracking which transactions hold locks on which resources (rows, pages, tables), granting new lock requests when compatible, making requesting transactions **wait** when a conflicting lock is already held, and detecting/resolving deadlocks (Module 12).

**Why it exists:** Someone has to be the referee. Without a centralized (or logically centralized) authority tracking "who's holding what," transactions could freely stomp on each other's in-progress work — exactly the anomalies from Module 5.

**Internal structure (conceptually):**

The lock manager typically maintains a **lock table** — an in-memory hash table keyed by resource identifier (e.g., row ID, page ID, table ID), where each entry stores:
- The list of transactions currently **holding** a lock on that resource, and the lock **mode** (shared/exclusive/etc.) each holds.
- A **wait queue** of transactions requesting a lock on that resource but currently blocked, along with their requested mode.

```
Lock Table (conceptual):

Resource: row_42
  Holders: { T1: SHARED, T3: SHARED }
  Wait Queue: [ T5 wants EXCLUSIVE ]

Resource: row_88
  Holders: { T2: EXCLUSIVE }
  Wait Queue: [ T4 wants SHARED, T6 wants EXCLUSIVE ]
```

**Real-world analogy:** The lock manager is like a **library front desk** tracking who currently has which books checked out (and in what mode — "reading room only" vs. "take it home"), and maintaining a waitlist for popular titles.

---

### 6.2 Shared Lock (S)

**Definition:** A **Shared Lock** (also called a **Read Lock**) is acquired by a transaction that wants to **read** a data item. Multiple transactions can hold a Shared Lock on the *same* item **simultaneously**, because concurrent reads don't conflict with each other (recall from Module 3.4: R-R pairs never conflict).

**Why it exists:** Reads don't change data, so there's no correctness reason to block other readers — Shared Locks maximize read concurrency while still blocking any *writer* from sneaking in a change mid-read.

**Example:**

```sql
-- Conceptually (most engines don't require explicit S-lock syntax for plain SELECT under 2PL-based engines)
SELECT * FROM accounts WHERE id = 'A';  -- acquires Shared Lock on the row (in lock-based engines)
```

---

### 6.3 Exclusive Lock (X)

**Definition:** An **Exclusive Lock** (also called a **Write Lock**) is acquired by a transaction that wants to **write** (insert/update/delete) a data item. Only **one** transaction may hold an Exclusive Lock on a given item at a time, and **no other transaction** — reader or writer — may hold any lock on that item simultaneously.

**Example:**

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';  -- acquires Exclusive Lock on the row
```

**Why exclusivity is total:** If another reader could still read while a writer holds an X lock, that reader would see a mid-write, inconsistent state — exactly the dirty read anomaly (Module 5.3). If another writer could write concurrently, that's the dirty write anomaly (Module 5.4).

---

### 6.4 Lock Compatibility Matrix

The compatibility matrix defines, for any two lock requests on the *same* resource, whether they can be granted simultaneously:

| Requested \ Held | S | X |
|---|---|---|
| **S** | ✅ Compatible | ❌ Must wait |
| **X** | ❌ Must wait | ❌ Must wait |

**Reading this table:** If Transaction A holds a **Shared** lock and Transaction B requests a **Shared** lock on the same item — granted immediately, both can read. If Transaction A holds a **Shared** lock and B requests **Exclusive** — B must wait until A (and any other S-lock holders) release. If A holds **Exclusive**, any other request (S or X) from a different transaction must wait.

This simple 2×2 table is the absolute foundation of lock-based concurrency control — everything else in this module builds on it.

---

### 6.5 Update Lock (U)

**Definition:** An **Update Lock** is a special, intermediate lock mode used when a transaction intends to **read a row first and possibly update it afterward** (e.g., `SELECT ... FOR UPDATE`, or the pattern behind `UPDATE` statements that first locate rows via a `WHERE` clause before modifying them).

**Why it exists — the classic problem it solves:**

Imagine two transactions both need to read-then-maybe-update the same row (`UPDATE accounts SET balance = balance - 100 WHERE id='A'`, run concurrently by T1 and T2). If both simply requested a **Shared** lock first (compatible, both granted), then both later tried to **upgrade** to Exclusive to perform the write — both would be stuck waiting for the other's Shared lock to release, and neither can proceed. This is a **classic, guaranteed deadlock pattern called "conversion deadlock,"** covered further in Module 12.

**The Update Lock solves this** by being:
- **Compatible with Shared locks** (other pure readers can still read).
- **Incompatible with other Update locks or Exclusive locks** (only one transaction can be "in line" to potentially upgrade to a write at a time).

| Requested \ Held | S | U | X |
|---|---|---|---|
| **S** | ✅ | ✅ | ❌ |
| **U** | ✅ | ❌ | ❌ |
| **X** | ❌ | ❌ | ❌ |

By ensuring only **one** transaction can hold an Update lock on a resource at a time, the database guarantees that when that transaction is ready to upgrade to Exclusive, it won't be competing with another transaction that made the same read-then-maybe-write decision.

**Industry usage:** SQL Server explicitly implements Update locks (`U` mode) as a first-class lock type. PostgreSQL and MySQL achieve similar protection through `SELECT ... FOR UPDATE` semantics and internal next-key/row-locking behavior, without necessarily exposing a distinctly named "U-lock" to the user, but the conceptual purpose is identical.

### 6.6 Intent Locks (IS, IX, SIX)

**Definition:** **Intent Locks** are locks placed on a **coarser-grained** resource (like a table) to signal that a transaction holds, or intends to acquire, finer-grained locks (like row locks) **somewhere within** that coarser resource — without having to check every single row to detect conflicts.

**Why they exist — the core problem:**

Suppose Transaction T1 wants to lock an entire **table** in Exclusive mode (e.g., for a schema change or bulk operation), while Transaction T2 currently holds a row-level Exclusive lock on just one row within that table. For T1's table-level lock request to correctly detect this conflict, the lock manager would otherwise need to scan **every single row** in the table to check for existing locks — an extremely expensive operation. Intent locks solve this by having T2 (or any transaction taking a row-level lock) first acquire a lightweight "intent" lock at the table level, so T1's table-level request can check compatibility with just **one** lock entry at the table granularity, instead of scanning all rows.

**The three intent lock types:**

| Lock | Meaning |
|---|---|
| **IS** (Intent Shared) | "I intend to acquire Shared locks on some rows/pages within this table" |
| **IX** (Intent Exclusive) | "I intend to acquire Exclusive locks on some rows/pages within this table" |
| **SIX** (Shared + Intent Exclusive) | "I hold a Shared lock on the entire table (e.g., I'm scanning all of it) AND I also intend to take Exclusive locks on specific rows within it" — a combination used e.g. when a transaction reads an entire table but only updates a few rows within it |

**Full Intent Lock Compatibility Matrix:**

| Requested \ Held | IS | IX | S | SIX | X |
|---|---|---|---|---|---|
| **IS** | ✅ | ✅ | ✅ | ✅ | ❌ |
| **IX** | ✅ | ✅ | ❌ | ❌ | ❌ |
| **S** | ✅ | ❌ | ✅ | ❌ | ❌ |
| **SIX** | ✅ | ❌ | ❌ | ❌ | ❌ |
| **X** | ❌ | ❌ | ❌ | ❌ | ❌ |

**How the protocol works (hierarchical locking):** Before acquiring a lock at a finer granularity (e.g., a row), a transaction must first acquire the appropriate intent lock at every **coarser** level above it (e.g., the table, and if applicable, the "database" level above that). This is called the **Multiple Granularity Locking (MGL) protocol**.

**Real-world analogy:** Think of intent locks like a **"do not disturb, working inside" sign** on a shared office floor. Instead of someone wanting to lock the whole floor having to check every single room individually for occupants, they just check the floor's sign — if it says "someone's working inside a room," they know to check further or wait, without needing to peek into every door.

### 6.7 Lock Granularity

**Definition:** **Lock granularity** refers to the **size** of the resource being locked — ranging from very fine-grained (a single row) to very coarse-grained (an entire database).

```
Coarse ─────────────────────────────────────► Fine

Database → Table → Page → Row → (Column, rare)
```

| Granularity | Concurrency | Overhead |
|---|---|---|
| **Row-level** | Highest — many transactions can work on different rows simultaneously | Highest overhead (many lock entries to track) |
| **Page-level** | Medium | Medium |
| **Table-level** | Lowest — one writer blocks everyone else on the whole table | Lowest overhead (one lock entry) |

**Trade-off:** Finer granularity = more concurrency but more memory/CPU overhead to track many small locks. Coarser granularity = less overhead but more blocking/contention. This exact trade-off is why **Lock Escalation** (6.8) exists — to dynamically shift toward coarser granularity when fine-grained locking becomes too expensive to track.

**Database engine behavior:**
- **InnoDB (MySQL):** Primarily row-level locking (via its clustered index structure), with intent locks (IS/IX) at the table level.
- **PostgreSQL:** Row-level locking for DML, with additional lightweight table-level locks for DDL operations; also uses page-level locking internally for certain index operations.
- **SQL Server:** Supports row, page, and table-level locking, with automatic **lock escalation** from row/page to table under memory pressure or large lock counts.
- **Oracle:** Row-level locking by default; notably, Oracle does **not** typically escalate locks the way SQL Server does, instead relying heavily on its MVCC-based read consistency to avoid needing broad read locks in the first place.

---

### 6.8 Lock Escalation

**Definition:** **Lock Escalation** is the process by which the database engine automatically **converts many fine-grained locks (e.g., thousands of row locks) into a single coarser-grained lock (e.g., one table lock)**, typically to reduce the memory and management overhead of tracking a huge number of individual locks.

**Why it exists:** Each individual lock consumes memory in the lock table. A transaction that updates millions of rows could exhaust lock manager memory if every single row lock were tracked individually. Escalating to a single table lock trades away fine-grained concurrency for a bounded, predictable memory footprint.

**Example (SQL Server-style):**

```
Transaction updates 500,000 rows in a table with 1,000,000 rows.
→ SQL Server, after crossing an internal threshold (default ~5,000 row locks),
  escalates to a single table-level EXCLUSIVE lock.
→ Now, EVERY other transaction is blocked from touching ANY row in that
  table, not just the ones actually being updated.
```

**Disadvantage:** Lock escalation can cause a sudden, dramatic **drop in concurrency** for a batch job that legitimately only needed to touch a subset of rows — a well-known production gotcha, especially in SQL Server environments, where a poorly-batched bulk update can unexpectedly block an entire table for unrelated read/write traffic.

**Best Practice:** Batch large bulk updates into smaller chunks (e.g., update 1,000 rows at a time, committing between batches) to avoid triggering lock escalation and to reduce the duration any given set of locks is held.

---

### 6.9 Lock Conversion

**Definition:** **Lock conversion** (or **lock upgrade**) is when a transaction that already holds a lock on a resource requests a **stronger** lock mode on that same resource — most commonly, upgrading from Shared (S) to Exclusive (X).

**Example:**

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 'A' FOR UPDATE;  -- acquires appropriate lock upfront
-- vs. the risky pattern:
SELECT balance FROM accounts WHERE id = 'A';              -- acquires S lock
-- ... later ...
UPDATE accounts SET balance = balance - 100 WHERE id = 'A'; -- needs to CONVERT S → X
COMMIT;
```

**The danger — conversion deadlock (preview of Module 12):** If two transactions both hold a Shared lock on the same row and both then try to convert to Exclusive, **neither can proceed** — each is waiting for the other to release its Shared lock first. This is why the **Update Lock** (6.5) exists: using `SELECT ... FOR UPDATE` from the start acquires an Update lock (or, in some engines, goes straight for a lock mode compatible with the eventual write) rather than a plain Shared lock, sidestepping the conversion deadlock entirely.

**Best Practice:** If you know a row you're reading will likely be updated later in the same transaction, use `SELECT ... FOR UPDATE` (or your engine's equivalent) from the start, rather than a plain `SELECT` followed by a later `UPDATE`.

### 6.10 Full Worked Example — Lock Manager in Action

```
T1: BEGIN; SELECT * FROM accounts WHERE id='A';       -- acquires S(A)
T2: BEGIN; SELECT * FROM accounts WHERE id='A';       -- acquires S(A) — compatible, granted
T3: BEGIN; UPDATE accounts SET balance=... WHERE id='A'; -- requests X(A) — MUST WAIT (conflicts with S held by T1, T2)

Lock Table State:
Resource: row_A
  Holders: { T1: S, T2: S }
  Wait Queue: [ T3 wants X ]

T1: COMMIT;   -- releases S(A)
   -- T3 still waits, because T2 still holds S(A)
T2: COMMIT;   -- releases S(A)
   -- NOW T3's X(A) request can be granted

Lock Table State (after both commits):
Resource: row_A
  Holders: { T3: X }
  Wait Queue: []
```

This trace demonstrates the core mechanics: compatible requests are granted immediately and can coexist; incompatible requests queue up and wait; and locks are released (in this simplistic example) at commit — though *when exactly* locks are released is itself a crucial design decision, covered fully in Module 7 (Two-Phase Locking).

### 6.11 Advantages, Disadvantages, Best Practices

**Advantages of Lock-Based Concurrency Control:**
- Conceptually simple and directly enforces correctness by physically preventing conflicting access.
- Mature, extremely well-understood, deployed in every major commercial RDBMS for decades.

**Disadvantages:**
- Blocking: transactions must wait, which can hurt throughput and latency under contention.
- Deadlocks are possible whenever two or more transactions wait on each other's locks (Module 12).
- Overhead of maintaining a lock table, especially at fine granularity.

**Best Practices:**
- Access resources (tables, rows) in a **consistent order** across all transactions in your application to reduce deadlock likelihood (Module 12 covers this as a prevention strategy).
- Keep transactions short to minimize the time locks are held.
- Use `SELECT ... FOR UPDATE` (or equivalent) deliberately when you know a read will be followed by a write in the same transaction.
- Be aware of your engine's lock escalation thresholds if doing large batch operations.

**Common Mistakes:**
- Holding locks across slow, non-database operations (network calls, user input waits) inside an open transaction.
- Not understanding the difference between Shared, Update, and Exclusive locks, leading to avoidable conversion deadlocks.
- Assuming all engines lock identically — MVCC-heavy engines (PostgreSQL, InnoDB, Oracle) use locking quite differently from lock-heavy engines like SQL Server's default `READ COMMITTED` (lock-based, not snapshot-based, unless `READ_COMMITTED_SNAPSHOT` is enabled).

**Performance Implications:** Lock contention (Module 16) is one of the most common real-world causes of database slowdowns — "hot rows" that many transactions want to touch simultaneously create serialized bottlenecks regardless of how much hardware you throw at the problem.

**Industry Usage:** Every major RDBMS uses some form of locking, even those (PostgreSQL, InnoDB, Oracle) that rely heavily on MVCC for reads — writes still require locks to serialize conflicting updates, and DDL/schema changes almost universally require some form of table-level locking.

### 6.12 Chapter Summary

- The **Lock Manager** tracks lock holders and wait queues per resource.
- **Shared (S)** locks allow concurrent reads; **Exclusive (X)** locks are fully exclusive.
- The **compatibility matrix** governs which lock requests can coexist.
- **Update (U)** locks prevent conversion deadlocks in read-then-maybe-write patterns.
- **Intent locks (IS, IX, SIX)** enable efficient conflict checking across granularity levels via the Multiple Granularity Locking protocol.
- **Lock granularity** trades off concurrency vs. overhead (row ↔ table).
- **Lock escalation** automatically shifts to coarser granularity under high lock counts, at the cost of concurrency.
- **Lock conversion** upgrades a held lock to a stronger mode, and is a classic deadlock risk if not handled via Update locks.

### 6.13 Revision Notes / Cheat Sheet

```
S x S  = OK           S x X  = WAIT
X x S  = WAIT         X x X  = WAIT
U x S  = OK            U x U  = WAIT     U x X = WAIT

Granularity:  Row (fine, high concurrency) ←→ Table (coarse, low concurrency)
Intent locks: IS/IX/SIX let coarse-level checks skip scanning every row
Escalation:   many row locks → one table lock (memory-saving, concurrency-costing)
Conversion:   S → X upgrade; risky without U-lock protection
```
