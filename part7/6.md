## Module 6: B-Tree & B+ Tree

> **Where we are:** Module 5 gave you the full taxonomy of index *types* (clustered, covering, composite, etc.). Module 6 answers the deeper question: **what data structure actually implements almost all of them?** The answer, in the overwhelming majority of relational databases, is the **B+ Tree**. This is the single most important data structure in this entire handbook — spend extra time here.

---

## 6.0 Why Trees?

### The problem, restated precisely

We want a structure that supports, all at once:
1. **O(log n) equality lookup** (`WHERE id = 5`)
2. **Efficient range queries** (`WHERE id BETWEEN 10 AND 50`)
3. **Efficient sorted output** (`ORDER BY id`)
4. **Efficient inserts/deletes** without the O(n) shifting cost of a strict sorted file (Module 3, Section 3.3)
5. **Good performance specifically for disk-based storage**, where each node access potentially costs a full page read (Module 1)

A plain **binary search tree (BST)** gives you (1)–(4) reasonably well in memory, but fails badly at (5): a BST has huge **height** relative to the number of keys (height ≈ log₂(n)), and each node typically holds just ONE key — meaning a lookup in a million-row table could require **~20 separate disk page reads** (one per tree level), each paying Module 1's full disk-latency tax. That is far too slow.

**B-Trees and B+ Trees solve this by making each node "fat"** — each node holds **many keys** (dozens to hundreds, sized to fill exactly one disk page), which dramatically reduces the tree's height for the same number of total keys. This single design choice — **optimize node size for disk pages, not for CPU cache lines like an in-memory tree would** — is the entire reason B-Trees exist as a distinct structure from BSTs.

---

## 6.1 B-Tree — Structure

### Definition

A **B-Tree of order *m*** is a self-balancing tree where:
- Every node has **at most *m*-1 keys** and **at most *m* children**.
- Every node (except the root) has **at least ⌈m/2⌉-1 keys**.
- Keys within a node are stored in **sorted order**.
- **Both** internal nodes and leaf nodes store actual data (record pointers/RIDs), **not just keys** — this is the critical distinguishing feature from a B+ Tree (Section 6.2).
- All leaves appear at the **same depth** (perfectly balanced by construction).

### Diagram — a small B-Tree (order 4, so max 3 keys/node)

```
                    [ 30 | 60 ]
                   /     |      \
          [10|20]   [40|50]    [70|80|90]
          (each key here ALSO stores
           its own record pointer/RID --
           data lives at EVERY level, not just leaves)
```

### Why B-Trees exist (historical motivation)

B-Trees were invented specifically to minimize the number of disk accesses for on-disk search structures, by maximizing the number of keys examined per single page read.

---

## 6.2 B+ Tree — Structure (the version databases actually use)

### Definition

A **B+ Tree** is a variant of the B-Tree with two crucial differences:

1. **Only leaf nodes store actual data pointers (RIDs)** — internal nodes store **only keys**, used purely to guide the search down to the correct leaf. Internal-node keys are essentially "signposts," duplicated copies of certain key values that also appear in the leaves.
2. **All leaf nodes are linked together in a sorted, doubly (or singly) linked list** — enabling extremely efficient range scans and full sorted traversal by simply walking the leaf-level linked list, without ever needing to revisit internal nodes.

### Diagram — B+ Tree Structure

```
                         [ 30 | 60 ]                          <- Root (internal node, keys only)
                        /      |      \
              [10|20]      [30|40|50]      [60|70|80|90]      <- Internal or Leaf nodes
                |               |                 |
                v               v                 v
   Leaf: [10->RID][20->RID] <-> [30->RID][40->RID][50->RID] <-> [60->RID][70->RID][80->RID][90->RID]
                                     ^
                       Leaf nodes linked left-to-right (sorted linked list)
                       -> enables fast range scans without revisiting internal nodes
```

### Internal Nodes vs Leaf Nodes vs Root Node

| Node Type | Contents | Purpose |
|---|---|---|
| **Root Node** | Keys only (signposts) | Entry point of every search; may itself be a leaf if the tree is small enough |
| **Internal Node** | Keys only (signposts), pointers to child nodes | Guides search downward; never holds actual row data/RIDs |
| **Leaf Node** | Keys + actual RIDs (or, in a clustered B+ Tree, the actual row data itself) | Where real data pointers live; linked to sibling leaves for range scans |

### Why B+ Trees Are Preferred Over Plain B-Trees (a critical, guaranteed interview question)

| Reason | Explanation |
|---|---|
| **1. Higher fan-out** | Since internal nodes in a B+ Tree store ONLY keys (no data pointers), more keys fit per internal-node page → higher fan-out → shorter tree → fewer disk reads per search, compared to a B-Tree where internal nodes are "diluted" by also carrying data pointers |
| **2. Efficient range queries** | The linked leaf list lets a range scan simply walk sideways at the leaf level after one initial descent — a plain B-Tree has no such leaf-linking, so a range scan would require repeated, more complex in-order-traversal logic across multiple levels |
| **3. Predictable performance** | Because ALL data lives at the leaf level (uniform depth for every actual data lookup), every point-lookup takes exactly the same number of page reads — a B-Tree can find data at ANY level (including the root itself, in the best case), giving inconsistent, less predictable I/O cost per query |
| **4. Simpler leaf-level logic for sequential access** | Since B+ Tree internal nodes never need modification when only a leaf-level value's RID changes (just the data at the leaf changes, not the signpost structure, unless a key insertion/deletion changes the signposts themselves) |

> **Memorize this one-sentence answer:** *"Databases prefer B+ Trees over B-Trees because storing data only at the leaves maximizes fan-out (shorter, flatter trees, fewer disk reads) and the linked-leaf-list structure makes range queries and full sorted scans extremely efficient — both of which matter enormously for disk-based storage."*

## 6.3 Fan-out and Height

### Fan-out

**Fan-out** is the number of children each internal node can have — directly determined by how many keys fit in one page (Module 1/2), which in turn depends on the page size and the size of each key + pointer.

### Height

**Height** is the number of levels from root to leaf. For a B+ Tree with fan-out *f* and *n* total keys, height ≈ **log_f(n)**.

### Why high fan-out matters so much — concrete numbers

Assume a page size of 8 KB, a key size of 8 bytes (e.g., a `BIGINT`), and a pointer size of 8 bytes. Roughly:

```
Keys per internal-node page ≈ 8 KB / (8 bytes key + 8 bytes pointer) ≈ ~500 keys/pointers per node
```

With fan-out ≈ 500:
- 1 level (root only, leaf) → up to ~500 keys
- 2 levels → up to ~500² = 250,000 keys
- 3 levels → up to ~500³ = 125,000,000 keys
- 4 levels → up to ~500⁴ = 62,500,000,000 keys

**This is the single most important practical fact about B+ Trees**: with realistic fan-out values (hundreds per node), a B+ Tree indexing **billions of rows** typically has a height of only **3–4 levels** — meaning a point lookup on a multi-billion-row table costs only 3–4 page reads (and the top 1–2 levels are almost always cached in the buffer pool anyway, per Module 4, since they're accessed by nearly every query using that index — making the *effective* cost often just 1–2 real disk I/Os).

### Interview Importance
⭐⭐⭐⭐⭐ — Being able to derive/estimate B+ Tree height given a page size, key size, and row count is one of the most common Senior SDE/Database Engineer whiteboard exercises. **Practice this calculation until it's automatic.**

## 6.4 B+ Tree Search

### Algorithm (point lookup)

```
function search(node, key):
    if node is a leaf:
        scan leaf's keys for exact match; return RID if found, else "not found"
    else:  // internal node
        find the correct child pointer to follow:
          for signposts [k1, k2, ..., km] in sorted order,
          if key < k1: follow leftmost child
          elif ki <= key < k(i+1): follow child between ki and k(i+1)
          else: follow rightmost child
        recurse into chosen child
```

### Diagram — Searching for key = 45

```
                         [ 30 | 60 ]
                        /      |      \
              [10|20]      [30|40|50]      [60|70|80|90]
                                |
                                v  (45 is between 40 and 50's range in this leaf group)
                    Leaf: [30][40][50] -> scan leaf, find 45 is NOT here in this simplified example
                    (in a real tree, leaf boundaries would be set precisely so 45 lands
                     in the correct leaf; this diagram simplifies for illustration)
```

### Complexity

**O(log_f n)** disk page reads, where *f* is fan-out — as shown in Section 6.3, this is typically just 3–4 reads even for billions of rows.

## 6.5 B+ Tree Insertion — Step by Step

### Algorithm outline

1. Search down to the correct **leaf** where the new key belongs (same traversal as search).
2. If the leaf has room (fewer than max keys), simply insert the key (and its RID) in sorted position — **done, no further changes needed**.
3. If the leaf is **full**, perform a **leaf split** (Section 6.6).

### Worked Example — Order 4 tree (max 3 keys per node), inserting keys 10, 20, 30, 40, 50 one at a time

**Step 1: Insert 10, 20, 30 (all fit in one leaf, no split yet, single-node tree)**

```
[ 10 | 20 | 30 ]     <- single node acts as both root AND leaf (tree is small)
```

**Step 2: Insert 40 — leaf now has 4 keys, exceeding max of 3 -> SPLIT REQUIRED**

```
Before split (overflowing): [ 10 | 20 | 30 | 40 ]

Split: divide into two leaves, promote the middle key up to a new root

        [ 30 ]                 <- new Root (internal node, just the promoted signpost key)
       /       \
 [10|20]      [30|40]          <- two new leaf nodes, linked to each other
```

**Step 3: Insert 50 — goes into the right leaf [30|40], which now has room? No — it has 2 keys already, room for 1 more (max 3), so 50 fits without a further split:**

```
        [ 30 ]
       /       \
 [10|20]      [30|40|50]      <- fits, no split needed this time
```

### Interview Importance
⭐⭐⭐⭐⭐ — Whiteboard B+ Tree insertion (with a specific order/fan-out given) is one of THE most common Database Engineer / Senior SDE coding-round + systems-round hybrid questions. **Practice drawing this from scratch, several times, with different key sequences.**

## 6.6 B+ Tree Split — Detailed Mechanics

### Leaf Split

When a leaf node overflows (exceeds max keys):
1. Divide the leaf's keys into two roughly equal halves.
2. The **first key of the new right leaf** is **copied up** (not removed from the leaf — it still exists in the leaf too) to the parent as a new signpost.
3. Update the leaf-level linked list to include the new leaf in sorted position.
4. If the parent now overflows from receiving this new signpost key, recursively split the parent too (Section 6.6.1).

> **Crucial subtlety, frequently tested:** In a **leaf** split, the promoted key is **copied** up (it remains in the leaf, since leaves must hold ALL actual data). In an **internal node** split (below), the promoted key is **moved** up (removed from the internal node, since internal nodes are pure signposts, and duplicating it there serves no purpose).

### Internal Node Split (when a split propagates upward)

```
Suppose internal node [ 10 | 20 | 30 ] (order 4, max 3 keys) overflows to [ 10 | 20 | 30 | 40 ]
after receiving a promoted key from a child split below it.

Split: middle key MOVES UP (removed from this node, unlike the leaf case):

            [ 20 ]                    <- 20 moves up to THIS node's parent
           /       \
     [ 10 ]       [ 30 | 40 ]         <- remaining keys split into two nodes
```

### Root Split (tree height increases)

If the **root itself** overflows and splits, a **brand new root** is created above it, and the tree's height increases by exactly one level — this is the **only** way a B+ Tree's height ever grows, and it always grows uniformly (all leaves remain at the same depth, preserving perfect balance).

```
Before: Root [ 10 | 20 | 30 | 40 ] overflows (order 4, max 3 keys)

After root split:
                [ 20 ]              <- brand NEW root (height +1)
               /       \
          [ 10 ]     [ 30 | 40 ]    <- old root's contents, split into two
```

### Complexity of Insertion

**O(log_f n)** for the initial descent to the leaf, plus **O(1) amortized** split cost per insertion in the common case (splits don't happen on every insert — only when a node happens to be full) — worst case (a cascading split all the way up to the root) is still bounded by **O(log_f n)** since that's the maximum tree height.

## 6.7 B+ Tree Deletion — Step by Step

### Algorithm outline

1. Search down to the leaf containing the key to delete.
2. Remove the key (and its RID) from the leaf.
3. If the leaf still has **at least the minimum required keys** (⌈m/2⌉-1), **done** — no further action.
4. If the leaf now has **too few keys** (underflow), attempt **redistribution** (borrow from a sibling) first; if redistribution isn't possible, perform a **merge** with a sibling.

### Worked Example — deleting from the tree built in Section 6.5

Starting tree:
```
        [ 30 ]
       /       \
 [10|20]      [30|40|50]
```

**Delete key 20:**

```
Leaf [10|20] loses 20 -> becomes [10]
Minimum required keys (order 4, min = ⌈4/2⌉-1 = 1) -> [10] has exactly 1 key, still valid, NO underflow

Result:
        [ 30 ]
       /       \
   [10]       [30|40|50]
```

**Delete key 10 (now leaf [10] would become empty -> underflow):**

```
Leaf [10] would become [] (0 keys) -> UNDERFLOW (below minimum of 1)

Step A: Try REDISTRIBUTION first — check sibling [30|40|50] (has 3 keys, more than its minimum of 1)
        -> borrow the smallest key (30) from the sibling

Result after redistribution:
        [ 40 ]                     <- signpost updated to reflect new split point
       /       \
   [30]       [40|50]
```

### Redistribution (Borrowing)

**Definition:** When a node underflows, check its immediate sibling — if the sibling has **more than the minimum** number of keys, "borrow" one key from the sibling (moving it into the underflowing node), and update the parent's signpost key to reflect the new dividing point. This avoids a more disruptive merge.

### Merge

**Definition:** If a sibling does **not** have extra keys to lend (it's exactly at its minimum), the underflowing node and its sibling are **merged into one node**, and the corresponding signpost key is **removed** from the parent — potentially causing the parent itself to underflow, requiring the same redistribution-or-merge logic to apply recursively upward.

### Worked Example — Merge scenario

```
Suppose we instead had: 
        [ 40 ]
       /       \
   [30]       [40]        <- both leaves at exactly minimum (1 key each)

Delete 30 from left leaf -> left leaf becomes [] -> UNDERFLOW
Sibling [40] has only 1 key (its own minimum) -> CANNOT lend -> MERGE required

Merge: combine both leaves into one, remove the signpost [40] from parent:

Result:  [ 40 ]     <- single merged leaf (was the parent, now demoted since it had only one child left)
         (if this was the root and now has only one child, the merged child becomes the new root,
          decreasing tree height by one level)
```

### Root Shrinking

If a merge causes the root to end up with only **one child** remaining, that single child **becomes the new root**, and tree height **decreases by one level** — the mirror image of root splitting (Section 6.6) growing the tree.

### Complexity of Deletion

**O(log_f n)** for the descent, plus **O(1) amortized** for redistribution/merge in the common case, worst case **O(log_f n)** for a merge cascade propagating all the way to the root (mirroring insertion's worst case).

## 6.8 Fill Factor Revisited (B+ Tree Context)

Recall Module 2, Section 2.6's fill factor concept — in the specific context of B+ Tree index pages, a lower fill factor at index build/rebuild time deliberately leaves each leaf/internal node partially empty, so that subsequent inserts can be absorbed **without triggering a split** for longer, at the cost of a larger overall index size (more pages needed to store the same number of keys, since each page holds fewer of them by design).

| Fill Factor | Effect |
|---|---|
| High (e.g., 100%) | Maximum storage density, but any insert into a full node triggers an immediate split; best for read-mostly/append-only indexes |
| Low (e.g., 70%) | More headroom before splits occur; best for indexes on frequently-updated/inserted-into columns, especially with non-sequential insert patterns |

## 6.9 Complexity Analysis — Master Table

| Operation | B+ Tree Complexity | Notes |
|---|---|---|
| Search (point lookup) | O(log_f n) | f = fan-out, typically in the hundreds -> effectively O(1)-ish in practice for realistic data sizes (3-4 levels) |
| Range Scan (k results) | O(log_f n + k) | One descent, then sequential leaf-list traversal for k matching results |
| Insertion | O(log_f n) worst case | Amortized much cheaper; splits are relatively rare events |
| Deletion | O(log_f n) worst case | Amortized much cheaper; merges/redistribution relatively rare |
| Space | O(n) | Proportional to number of keys, with some overhead from partially-filled nodes (fill factor) |

## 6.10 Why Databases Prefer B+ Trees — Full Recap (ties Modules 3, 5, 6 together)

1. **(Module 3)** Sorted files give great reads but O(n) insert cost; heap files give great inserts but O(n) reads. B+ Trees give **O(log n) for both**, resolving that entire tension.
2. **(Module 5)** Almost every index type discussed — clustered, non-clustered, composite, covering, unique, partial, expression — is, underneath, implemented as a B+ Tree; only hash indexes (Module 7) and specialized types (BRIN, GiST, GIN — Module 8) deviate from this default.
3. **(This Module)** B+ Trees specifically (over plain B-Trees) win because of higher fan-out (data only at leaves) and efficient range scans (linked leaf list) — both directly serving the disk-I/O-minimization goal established all the way back in Module 1.

## 6.11 Chapter Summary

- **B-Trees** store data (RIDs) at every node level; **B+ Trees** store data **only at leaves**, with internal nodes acting purely as signposts, and leaves linked together for efficient range scans.
- **Fan-out** (keys per node, driven by page size) directly determines tree **height**; realistic fan-outs (hundreds per node) keep B+ Trees at just 3–4 levels even for billions of rows.
- **Insertion**: descend to the correct leaf, insert; if the leaf overflows, **split** (leaf split copies the promoted key up; internal node split moves it up); splits can cascade to the root, increasing tree height by exactly one level when the root itself splits.
- **Deletion**: descend to the correct leaf, remove; if underflow occurs, try **redistribution** (borrow from a sibling) first, falling back to a **merge** if no sibling has spare keys; merges can cascade to the root, decreasing tree height by one level when the root ends up with a single child.
- **Fill factor** in a B+ Tree context trades storage density against how soon splits are triggered by future inserts.
- All major operations are **O(log_f n)**, and databases universally prefer B+ Trees over plain B-Trees because of higher fan-out and efficient linked-leaf range scans.

## 6.12 Cheat Sheet

```
B-Tree           = data (RIDs) stored at EVERY node level
B+ Tree          = data (RIDs) stored ONLY at leaves; internal nodes = pure signposts
                   leaves LINKED together -> fast range scans

Fan-out          = keys per node (driven by page size / key size)
Height           = log_f(n); realistic fan-out (100s) -> height 3-4 for BILLIONS of rows

SEARCH           = O(log_f n)
INSERT           = descend -> insert in leaf -> if full, SPLIT (cascades up to root if needed)
                   Leaf split: promoted key COPIED up (stays in leaf)
                   Internal split: promoted key MOVED up (removed from node)
                   Root split -> new root created -> height +1

DELETE           = descend -> remove from leaf -> if underflow:
                     1st choice: REDISTRIBUTE (borrow from sibling with spare keys)
                     fallback:   MERGE with sibling (removes parent's signpost)
                   Root merge down to 1 child -> that child becomes new root -> height -1

Why B+ > B-Tree: higher fan-out (shorter tree) + linked leaves (fast range scans)
                 + uniform leaf depth (predictable point-lookup cost)
```
