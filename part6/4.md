# Part 6: Transactions & Concurrency Control

## Module 4: Serializability

> Module 3 gave us the vocabulary to *describe* schedules. Now we answer the central theoretical question of concurrency control: **given some non-serial (interleaved) schedule, is it actually "correct" — i.e., does it produce the same result as *some* serial execution of the same transactions?** This property is called **Serializability**, and it is the gold standard of correctness for concurrent transaction execution.

---

### 4.1 Why Serializability Matters

Recall from Module 3: a **serial schedule** is always correct because transactions run one at a time with zero interference. But serial execution has no concurrency, hence poor performance.

**The big idea:** We don't actually need schedules to *be* serial — we only need them to be **equivalent** to some serial schedule in their *effect* on the database. If a highly-interleaved, highly-concurrent schedule still produces a result indistinguishable from *some* valid one-at-a-time ordering of the same transactions, it's just as correct — and much faster.

**Definition:** A schedule is **serializable** if it is *equivalent* to some serial schedule of the same transactions. There are two major, distinct ways to define "equivalent," which give us two different (and non-identical) notions of serializability:

1. **Conflict Serializability** — equivalence based on the order of conflicting operations.
2. **View Serializability** — equivalence based on what each transaction "sees" (reads) and what final writes "win."

---

### 4.2 Conflict Equivalence

**Definition:** Two schedules are **conflict equivalent** if:
1. They involve the same set of transactions with the same operations.
2. Every pair of **conflicting operations** (as defined in Module 3.4: same data item, different transactions, at least one write) occurs in the **same relative order** in both schedules.

**Why this definition?** Non-conflicting operations (e.g., two reads, or operations on different data items) can be freely swapped without changing the final outcome — their relative order doesn't matter to the result. Only conflicting operations "care" about order, because reordering them can change what gets read or what the final written value is.

**Practical example:**

```
S1: R1(A)  W1(A)  R2(A)  W2(A)
S2: R1(A)  R2(A)  W1(A)  W2(A)
```

Are these conflict equivalent? Let's check every conflicting pair:
- `W1(A)` vs `R2(A)`: In S1, `W1(A)` comes before `R2(A)`. In S2, `R2(A)` comes *before* `W1(A)`. **Different order!**

Since this conflicting pair's order differs between S1 and S2, **they are NOT conflict equivalent** — even though the same operations occur, in S1 T2 reads T1's write, while in S2 it doesn't.

---

### 4.3 Conflict Serializability

**Definition:** A schedule is **conflict serializable** if it is conflict equivalent to *some* serial schedule of the same transactions.

**How to test it — the swapping method:**
Starting from a given schedule, repeatedly swap adjacent **non-conflicting** operations (this never changes the schedule's meaning). If you can transform the schedule into a serial schedule this way, the original schedule is conflict serializable.

**Worked example:**

```
S: R1(A)  R2(B)  W1(A)  R2(A)  W2(B)  W2(A)
```

Let's check: T1 touches A only; T2 touches B and A. Attempt to move all of T1's operations before all of T2's operations (or vice versa) by swapping adjacent non-conflicting ops:

- `R2(B)` and `W1(A)` operate on different items — swappable (non-conflicting). Swap to get:
  `R1(A) W1(A) R2(B) R2(A) W2(B) W2(A)`
- Now T1's operations (`R1(A) W1(A)`) are fully before T2's operations (`R2(B) R2(A) W2(B) W2(A)`) — this **is** a serial schedule (T1 then T2)!

Since we reached a serial schedule using only non-conflicting swaps, the original **S is conflict serializable**, equivalent to the serial order **T1 → T2**.

---

### 4.4 Precedence Graph (Serialization Graph)

Manually swapping operations works for small examples, but it doesn't scale. The standard, rigorous, and **exam/interview-favorite** method is the **Precedence Graph** (also called a **Serialization Graph**).

**Definition:** A precedence graph is a directed graph where:
- Each **node** represents a transaction.
- A **directed edge** `Ti → Tj` is added if Ti has an operation that **conflicts with**, and occurs **before**, an operation of Tj on the same data item.

**Construction rules** — draw an edge `Ti → Tj` whenever:
1. Ti reads X, then Tj writes X (`Ti → Tj`)
2. Ti writes X, then Tj reads X (`Ti → Tj`)
3. Ti writes X, then Tj writes X (`Ti → Tj`)

**The Serializability Theorem:** *A schedule is conflict serializable **if and only if** its precedence graph is **acyclic** (contains no cycles).* If the graph has no cycle, a topological sort of the graph gives you a valid equivalent serial order.

**Worked Example 1 — Acyclic graph (serializable):**

```
S: R1(A)  W2(A)  R1(B)  W2(B)  R3(A)  W3(A)
```

Conflicts:
- R1(A) before W2(A) → edge T1 → T2
- W2(A) before R3(A) → edge T2 → T3

```
   T1 ───► T2 ───► T3
```

No cycle → **conflict serializable**, equivalent serial order: **T1 → T2 → T3**.

**Worked Example 2 — Cyclic graph (NOT serializable):**

```
S: R1(A)  W2(A)  R2(B)  W1(B)
```

Conflicts:
- R1(A) before W2(A) → edge T1 → T2
- R2(B) before W1(B) → edge T2 → T1

```
   T1 ───► T2
    ▲       │
    └───────┘
```

This is a **cycle** (T1 → T2 → T1) → **NOT conflict serializable**. No matter how you reorder, you cannot find an equivalent serial schedule — T1 needs to logically go before T2 (because of A) AND after T2 (because of B) simultaneously, which is impossible in a single serial order.

**How to test for cycles in an interview/exam:** Use a simple depth-first search (DFS) — if DFS revisits a node already on the current traversal path (not just already visited overall), you've found a cycle. This is exactly the standard "cycle detection in directed graph" algorithm from your DSA coursework — the DBMS literally reuses this graph theory concept, which is a favorite point of connection interviewers like to probe ("connect this to what you know about graphs").

---

### 4.5 View Equivalence

**Definition:** Two schedules are **view equivalent** if all three of the following conditions hold:

1. **Initial Read Condition:** If transaction Ti reads the *initial* value of data item X in schedule S1, then Ti must also read the initial value of X in schedule S2.
2. **Update (Read-From) Condition:** If Ti reads a value of X that was written by Tj in S1, then Ti must read the value of X written by that **same** Tj in S2.
3. **Final Write Condition:** If Ti performs the **final write** on data item X in S1 (i.e., the last write to X before the schedule ends), then Ti must also perform the final write on X in S2.

**Why a separate definition from Conflict Equivalence?** Conflict equivalence is based strictly on the *order* of conflicting operations. View equivalence is based on *what value everyone actually sees* and *whose write "sticks" as final*. These turn out to be different in the presence of **blind writes** (Module 3.5) — schedules can be view equivalent to a serial schedule without being conflict equivalent to one.

---

### 4.6 View Serializability

**Definition:** A schedule is **view serializable** if it is view equivalent to some serial schedule of the same transactions.

**Key theorem:** *Every conflict serializable schedule is also view serializable, but the reverse is NOT always true.* There exist schedules that are view serializable but **not** conflict serializable — these always involve **blind writes**.

**The classic example — a view serializable but NOT conflict serializable schedule:**

```
S: W1(A)  W2(A)  W3(A)
```

Here all three transactions perform **blind writes** on A (none of them read A first). Let's check view equivalence against the serial schedule **T1 → T2 → T3**:

- **Initial read condition:** No transaction reads A at all in either schedule, so this condition is vacuously satisfied.
- **Final write condition:** In both S and the serial order T1→T2→T3, **T3** performs the last write to A. ✔ Matches.

So S is view equivalent to the serial schedule T1 → T2 → T3, hence **view serializable**.

But is S conflict serializable? Let's build the precedence graph:
- W1(A) before W2(A) → edge T1 → T2
- W2(A) before W3(A) → edge T2 → T3
- W1(A) before W3(A) → edge T1 → T3

```
T1 ──► T2 ──► T3
 └─────────────►
```

No cycle here actually — wait, let's re-examine. Actually with only write-write conflicts in this exact linear order, the graph T1→T2, T2→T3, T1→T3 has **no cycle**, so this particular S actually **is** conflict serializable too (equivalent to T1→T2→T3). The subtlety appears in schedules where the *interleaving* of blind writes breaks the conflict order but not the final-write outcome. Let's use the true classic counterexample instead:

**True classic example (with an interleaved blind write):**

```
S: W1(A)  W2(A)  W1(A)  ...
```

Actually, the textbook standard counterexample uses **three transactions with genuinely non-linear interleaving**:

```
S: W3(A)  W1(A)  W2(A)
```

Precedence graph edges (all write-write conflicts on A):
- W3(A) before W1(A) → T3 → T1
- W3(A) before W2(A) → T3 → T2
- W1(A) before W2(A) → T1 → T2

```
   T3 ──► T1 ──► T2
    └─────────────►
```

No cycle → this is conflict serializable too, equivalent to T3 → T1 → T2. 

**The genuinely non-conflict-serializable-but-view-serializable case requires a cycle in the write-write/read-write graph that still preserves the "final writer" outcome.** The standard textbook example is:

```
S:  R1(A)   W2(A)   W1(A)   W3(A)
```

Conflicts:
- R1(A) before W2(A) → T1 → T2
- W2(A) before W1(A) → T2 → T1
- W1(A) before W3(A) → T1 → T3

```
   T1 ──► T2
    ▲       │
    └───────┘        T1 ──► T3
```

There's a cycle: **T1 → T2 → T1**. So this schedule is **NOT conflict serializable**.

Now check view equivalence against serial order **T1 → T2 → T3** (chosen because T3 must be last since it does the final write on A in S):
- **Initial read:** T1 reads A's initial value in S (since no one wrote A before `R1(A)`). In serial order T1→T2→T3, T1 also reads A's initial value first. ✔
- **Final write:** In S, the last write to A is `W3(A)` by T3. In the serial order T1→T2→T3, T3 also performs the last write. ✔
- **Update condition:** No transaction reads a value *written by another transaction* in S except T1 reading the initial value (already covered) — T2 and T3 never read A at all (blind writes). ✔ trivially satisfied.

All three view equivalence conditions hold → **S is view serializable** (equivalent to T1 → T2 → T3), even though its precedence graph has a cycle and it is **NOT conflict serializable**.

**This is the key exam takeaway:** *Blind writes are exactly the mechanism that allows a schedule to be view serializable without being conflict serializable.* If a schedule has no blind writes at all, **conflict serializability and view serializability become equivalent** for that schedule.

---

### 4.7 Conflict Serializability vs. View Serializability — Comparison Table

| Aspect | Conflict Serializability | View Serializability |
|---|---|---|
| Basis of equivalence | Order of conflicting operations | What is read (from whom) + final writer |
| Testing method | Precedence graph (cycle check) | Requires checking all 3 view-equivalence conditions; harder in general |
| Computational complexity | Polynomial time (graph cycle detection) | **NP-Complete** in general (much harder to test) |
| Relationship | Subset of View Serializable | Superset — includes all Conflict Serializable + some more (via blind writes) |
| Used in practice? | **Yes** — this is what real DB engines' concurrency control protocols effectively guarantee | Rarely used directly in practice due to computational cost |

**Why real databases use Conflict Serializability, not View Serializability:** Testing view serializability is **NP-Complete** — computationally infeasible to check in general for real-time transaction processing. Conflict serializability, by contrast, can be tested in polynomial time via the precedence graph, and — crucially — protocols like **Two-Phase Locking** (Module 7) can be *proven* to only ever produce conflict-serializable schedules, without needing to build a graph at runtime at all. This is why virtually all production systems target conflict serializability (or the even stricter guarantee provided by strict 2PL / serializable snapshot isolation) rather than the theoretically broader but impractical view serializability.

---

### 4.8 Serialization Graph Testing — Full Algorithm

**Step-by-step procedure to test conflict serializability:**

1. **List all transactions** in the schedule as graph nodes.
2. **Scan the schedule left to right.** For every conflicting operation pair (Ti's operation before Tj's operation on the same item, different transactions, at least one a write), add a directed edge Ti → Tj (if not already present).
3. **Check for cycles** in the resulting graph using DFS (track the current recursion path; if you revisit a node already on that path, a cycle exists).
4. **If acyclic:** the schedule is conflict serializable; any valid topological sort gives an equivalent serial order.
5. **If cyclic:** the schedule is NOT conflict serializable.

**Full worked example (exam-style):**

```
S: R1(X)  R2(Y)  W1(Y)  R3(X)  W2(X)  W3(Y)
```

Let's find all conflicting pairs, one by one, scanning left to right:

| Pair | Conflict? | Edge |
|---|---|---|
| R1(X), R2(Y) | Different items | — |
| R1(X), W1(Y) | Different items | — |
| R1(X), R3(X) | Both reads | — |
| R1(X), W2(X) | Same item, R before W, different txns | T1 → T2 |
| R2(Y), W1(Y) | Same item, R before W | T2 → T1 |
| R2(Y), W3(Y) | Same item, R before W | T2 → T3 |
| W1(Y), R3(X) | Different items | — |
| W1(Y), W3(Y) | Same item, W before W | T1 → T3 |
| R3(X), W2(X) | Same item, R before W | T3 → T2 |
| W2(X), W3(Y) | Different items | — |

Edges found: `T1→T2`, `T2→T1`, `T2→T3`, `T1→T3`, `T3→T2`

```
   T1 ──► T2 ──► T3
    ▲      │▲      │
    └──────┘└──────┘
```

Clear cycles: `T1 → T2 → T1` and `T2 → T3 → T2`. **This schedule is NOT conflict serializable** — it has multiple cycles.

### 4.9 Real-World Analogy for Serializability

Think of serializability like **verifying a shuffled deck of cards can be un-shuffled back into some valid, agreed-upon order**. It doesn't matter *how* the deck got shuffled (which is like the interleaved schedule) — what matters is whether there's *some* consistent, non-contradictory way to sort it back into a legitimate single-file order (a serial schedule). If two cards each demand to be both "before" and "after" the other (a cycle), no consistent sorted order exists — the shuffle broke something fundamental, and that's exactly what a cycle in the precedence graph represents.

### 4.10 Advantages, Disadvantages, Best Practices

**Why Serializability matters:**
- It is the strongest, most intuitive correctness guarantee: "behaves as if transactions ran one at a time."
- It's the theoretical foundation behind the `SERIALIZABLE` isolation level (Module 11) offered by every major RDBMS.

**Disadvantages / costs:**
- Achieving true serializability (especially via graph-based or optimistic validation approaches) can require aborting and retrying transactions, reducing throughput under high contention.
- View serializability, while theoretically broader, is impractical (NP-Complete to test) and essentially never implemented directly.

**Best Practices:**
- When reasoning about correctness in an interview or design review, default to **conflict serializability** and precedence graphs — it's what's actually implementable and used.
- Recognize which concurrency control protocol (2PL, OCC, MVCC-based serializable snapshot isolation) your database uses to **guarantee** serializability without needing to construct a graph at runtime.

**Common Mistakes:**
- Confusing "recoverable" (Module 3, about safe rollback) with "serializable" (about correctness of outcome) — a schedule can be one without the other.
- Forgetting that conflict serializability is *sufficient* but not *necessary* for correctness — some non-conflict-serializable schedules are still "fine" in a view-serializability sense, but this nuance rarely matters in production system design.
- Assuming `SERIALIZABLE` isolation level always uses precedence graphs internally — in practice, engines use protocols (2PL, Serializable Snapshot Isolation) that are *proven* to produce only serializable schedules, rather than checking graphs live.

**Industry Usage:** Financial ledgers, inventory reservation systems, and any workload with strict correctness requirements often use `SERIALIZABLE` isolation (Module 11), which is grounded entirely in the theory built in this module.

---

### 4.11 Chapter Summary

- **Serializability**: a schedule is correct if it's equivalent to *some* serial schedule.
- **Conflict Serializability**: equivalence based on order of conflicting (same-item, different-txn, ≥1 write) operations; tested via the **precedence graph** — acyclic = serializable.
- **View Serializability**: equivalence based on initial reads, read-from relationships, and final writes; broader than conflict serializability (captures blind-write cases), but **NP-Complete** to test.
- **Every conflict serializable schedule is view serializable, but not vice versa** — the gap is explained entirely by blind writes.
- Real databases target conflict serializability (efficiently testable, efficiently guaranteed by protocols like 2PL) rather than view serializability.
