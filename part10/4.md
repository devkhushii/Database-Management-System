# Part 10 — Database Internals & Storage Engine Architecture

## Module 4: MySQL InnoDB Internals

> **Recap:** Module 3 covered PostgreSQL's process model and background workers in depth. Now we cover InnoDB — MySQL's default storage engine since MySQL 5.5 — which solves the same underlying problems (buffering, durability, MVCC, free space) with meaningfully different mechanics. Expect direct comparisons back to Module 3 throughout.

---

### 4.0 Why This Module Exists

InnoDB and Postgres are the two engines every serious database-engineer interview expects you to be able to speak to concretely. Where Postgres uses a multi-process model with heap storage and in-heap MVCC, InnoDB uses a multi-**threaded** model with clustered storage and a separate undo-log-based MVCC — these differences cascade into almost everything else: locking behavior, recovery mechanics, and operational tuning.

---

### 4.1 InnoDB Architecture Overview

**Core design decision:** Unlike Postgres's process-per-connection model, MySQL uses a **thread-per-connection** model — the `mysqld` server is a single OS process, and each client connection is handled by a dedicated thread within that process, all sharing the same address space directly (no need for shared memory segments — regular in-process memory sharing suffices).

```
┌───────────────────────────────────────────────────────────────┐
│                         mysqld (single process)                   │
│                                                                     │
│  ┌───────────┐ ┌───────────┐ ┌───────────┐                       │
│  │ Connection │ │ Connection │ │ Connection │  ← one THREAD per    │
│  │  Thread 1  │ │  Thread 2  │ │  Thread N  │     client connection│
│  └─────┬─────┘ └─────┬─────┘ └─────┬─────┘                       │
│        └─────────────┴─────────────┘                              │
│                       │  (shared process memory, no IPC needed)    │
│                       ▼                                            │
│         ┌───────────────────────────────────┐                     │
│         │           InnoDB Storage Engine       │                     │
│         │                                        │                     │
│         │  Buffer Pool │ Redo Log Buffer          │                     │
│         │  Change Buffer │ Adaptive Hash Index     │                     │
│         │  Lock Manager │ Data Dictionary Cache     │                     │
│         └───────────────────────────────────┘                     │
│                       │                                            │
│    ┌──────────────┬───┴──────────┬─────────────────┐              │
│    ▼              ▼              ▼                 ▼              │
│┌─────────┐  ┌────────────┐ ┌────────────┐  ┌──────────────┐      │
││Page      │  │ Log Threads │ │ Purge       │  │ Master Thread │      │
││Cleaner   │  │ (IO Threads)│ │ Thread(s)   │  │               │      │
││Threads   │  │             │ │             │  │               │      │
│└─────────┘  └────────────┘ └────────────┘  └──────────────┘      │
└───────────────────────────────────────────────────────────────┘
```

**Why threads instead of processes here?** Lower per-connection overhead (thread creation/context-switch is cheaper than process fork), and simpler shared-state access since all threads live in one address space. The trade-off: a severe bug (e.g., a crash in server code) can take down the *entire* `mysqld` process — there's no Postgres-style process isolation between connections.

### 4.2 The InnoDB Buffer Pool

**What is it?** InnoDB's equivalent of Shared Buffers — the in-memory cache of data and index pages, configured via `innodb_buffer_pool_size`.

**Sizing guidance:** Commonly recommended at 50–75% of available system RAM on a dedicated database server — notably more aggressive than Postgres's ~25% guidance. This is because InnoDB, unlike Postgres, is designed to largely **bypass** relying on the OS page cache for its own data pages (especially when using `O_DIRECT`), so it needs a proportionally larger dedicated cache of its own to avoid redundant double-buffering.

**Structural detail — buffer pool instances:** For large buffer pools, InnoDB can split the pool into multiple `innodb_buffer_pool_instances`, each with its own set of internal data structures and mutexes, to reduce contention on a single global lock under highly concurrent access — a scalability optimization not really needed in Postgres's design.

**Eviction algorithm:** InnoDB uses a variant of **LRU** (not clock-sweep like Postgres), with a specific twist: the LRU list is split into a "young" sublist (frequently accessed, hot pages) and an "old" sublist (recently loaded, unproven pages) — roughly a 5/8 young, 3/8 old split by default (`innodb_old_blocks_pct`). New pages enter at the head of the *old* sublist, not the young one.

**Why the young/old split matters:** It defends against a classic cache-pollution problem — a large one-time sequential scan (e.g., a full table scan for a report or a `mysqldump`) would otherwise flood the buffer pool with pages that are read once and never again, evicting genuinely hot pages. By inserting new pages into the "old" sublist first, and only promoting them to "young" if accessed again after a configurable delay (`innodb_old_blocks_time`), a single scan's pages get evicted again without ever displacing the truly hot working set.

*(Full generic buffer pool mechanics — pinning, dirty pages, flushing — covered comparatively for both engines in Module 6: Buffer Pool Internals.)*

**Interview importance:** ⭐⭐⭐⭐⭐ The young/old LRU sublist split is one of the most commonly asked InnoDB-specific "why is this smarter than plain LRU" questions.

### 4.3 Redo Log (InnoDB's WAL)

**What is it?** InnoDB's write-ahead log — functionally equivalent to Postgres's WAL, but physically structured differently: a fixed set of pre-allocated, circularly-reused log files (`ib_logfile0`, `ib_logfile1`, ... or, in newer versions, files within `innodb_redo_log_capacity`), rather than Postgres's append-and-recycle segment files.

**Why "redo"?** It records the *physical* effect of changes (page-level modifications) needed to **redo** (reapply) work after a crash, ensuring committed transactions aren't lost even if their data pages hadn't been flushed yet — exactly the same durability principle as Postgres's WAL, just InnoDB-flavored terminology.

**Key parameter — `innodb_flush_log_at_trx_commit`:**

| Value | Behavior | Durability | Performance |
|---|---|---|---|
| `1` (default) | Redo log flushed to disk and `fsync`'d on every commit | Full ACID durability | Slowest |
| `2` | Redo log written to OS cache on every commit, but only `fsync`'d once per second | Survives `mysqld` crash, but not OS crash/power loss (up to 1s of data at risk) | Faster |
| `0` | Redo log written and flushed only once per second regardless of commits | Up to 1s of transactions lost on `mysqld` crash | Fastest |

This is the direct InnoDB analogue of Postgres's `synchronous_commit` trade-off from Module 3 — same underlying trade-off (durability vs. throughput), different knob name.

**Circular reuse:** Because redo log files are fixed-size and reused circularly, InnoDB must ensure it never overwrites a redo log record whose corresponding dirty page hasn't yet been flushed to the actual data file — this is enforced by the **checkpoint** mechanism (conceptually identical purpose to Postgres's checkpointer: bound how much redo log must be replayed, and prevent circular overwrite of not-yet-durable changes).

---

### 4.4 Undo Log

**What is it?** A separate log (physically stored in **undo tablespaces**) recording the *previous* version of data before a modification — used both to **roll back** uncommitted transactions and to support **MVCC** reads of older row versions (covered fully in Module 5).

**This is InnoDB's biggest structural difference from Postgres's MVCC:** Postgres keeps old row versions **in the heap itself** (multiple tuple versions physically on the same or nearby pages, cleaned by VACUUM). InnoDB instead keeps only the **current** row version in the clustered index, and stores **old** versions separately in the undo log, linked from the current row via a hidden `DB_ROLL_PTR` (roll pointer).

**Comparison diagram:**

```
POSTGRESQL MVCC (in-heap versioning)          INNODB MVCC (undo-log versioning)

Heap Page:                                     Clustered Index Leaf:
┌────────────────────┐                        ┌──────────────────────────┐
│ v1: xmin=100,xmax=105│  (old, dead-eventually)│  CURRENT row only          │
│    salary=50000      │                        │  salary=55000               │
├────────────────────┤                        │  DB_TRX_ID=105               │
│ v2: xmin=105,xmax=0   │  (current)            │  DB_ROLL_PTR ──────┐        │
│    salary=55000      │                        └────────────────────┼────┘
└────────────────────┘                                              ▼
                                                              Undo Log:
Cleanup: VACUUM (later, background)                    ┌───────────────────┐
                                                          │ old value: salary=  │
                                                          │   50000, prior ptr  │
                                                          └───────────────────┘
                                                Cleanup: Purge Thread (later, background)
```

**Why this matters:** InnoDB's clustered index (the table itself) only ever holds one version per row, keeping the primary table compact — but a long-running transaction needing an old snapshot forces InnoDB to walk potentially long undo chains, which can degrade read performance under heavy concurrent write load with old open transactions (the InnoDB analogue of Postgres's "long transaction blocks vacuum" problem — here it's "long transaction makes undo chains long, and undo log grows until purge can catch up").

---

### 4.5 Change Buffer (formerly "Insert Buffer")

**What is it?** A special in-memory (and persisted) structure that **buffers modifications to secondary indexes** when the relevant index page isn't currently in the buffer pool, deferring the actual index page update until that page is next read into memory anyway.

**Historical name:** Originally called the **Insert Buffer** (it only buffered inserts); it was later generalized to also cover updates and deletes, and renamed the **Change Buffer**.

**Why does it exist?** Secondary index updates on a large table can require modifying index pages scattered randomly across disk (unlike the clustered index, which benefits from primary-key locality). If every DML on a secondary-indexed column immediately required a random-I/O read-then-write of the relevant index page, write-heavy workloads with many secondary indexes would suffer badly. The Change Buffer defers this: the change is recorded compactly in the buffer, and merged into the actual index page lazily — either when that page is coincidentally read in for another reason, or during a background merge, or at server shutdown.

**Constraint:** Only applies to **secondary, non-unique** indexes (unique indexes need an immediate uniqueness check against the actual page, so buffering doesn't apply the same way).

**Real-life analogy:** Instead of walking to a specific filing cabinet drawer (random I/O) every single time a new memo needs filing, you drop memos in an inbox tray (Change Buffer) and only actually file them into the cabinet the next time you happen to open that drawer anyway.

**Interview importance:** ⭐⭐⭐⭐ A strong InnoDB-specific differentiator question: "Why don't secondary index writes always cause immediate random I/O?"

---

### 4.6 Adaptive Hash Index (AHI)

**What is it?** An automatically-built, in-memory hash index that InnoDB constructs *on top of* frequently-accessed portions of the B-Tree, to speed up equality lookups that would otherwise require a full B-Tree traversal.

**Why does it exist?** If InnoDB observes that certain index key patterns are being looked up extremely frequently (e.g., repeated point lookups via the same query shape), it can build a hash table mapping those keys directly to page addresses, turning an O(log n) B-Tree traversal into an O(1) hash lookup for those hot keys — entirely automatically, with no DBA/application involvement.

**Trade-offs:**
- Adds memory and maintenance overhead (the hash index must be kept in sync as underlying pages change)
- Can occasionally *hurt* performance under highly concurrent, contended workloads (a documented reason `innodb_adaptive_hash_index` is sometimes disabled in production for specific write-heavy, highly concurrent systems — this is a well-known real-world tuning knob, not just a textbook feature)

**Interview importance:** ⭐⭐⭐ Good to know exists and its trade-off; less commonly probed in deep detail than Buffer Pool/Redo Log/Undo Log.

---

### 4.7 Doublewrite Buffer

**What is it?** A special storage area where InnoDB writes a copy of a data page **before** writing that page to its actual final location on disk — a defense against **torn pages** (partial writes).

**Why does it exist — the torn page problem:** InnoDB pages (default 16KB) are typically larger than the atomic write unit guaranteed by the underlying OS/filesystem/disk (often 4KB, or even 512 bytes on some legacy setups). If the system crashes mid-write, a page could end up **half-old, half-new** — corrupted in a way that's *not* fixable by simply replaying the redo log, because redo log replay assumes it's applying changes on top of an intact, if possibly stale, page — not a torn one.

**How it solves this:** Before writing pages to their real locations, InnoDB first writes them sequentially to the doublewrite buffer (a contiguous area, so this extra write is fast and sequential, not randomly scattered). Once that write is confirmed durable, InnoDB proceeds to write the pages to their actual locations. On crash recovery, if a page in its real location is found to be corrupted/torn, InnoDB can recover the last-known-good copy from the doublewrite buffer instead, then apply redo log records on top of *that* intact copy.

**Real-life analogy:** Photocopying an important signed document and filing the photocopy safely before mailing the original through a potentially unreliable postal system — if the original gets damaged in transit, you still have an intact copy to work from.

**Performance implication:** This effectively doubles certain write I/O (hence the name), which is why modern InnoDB has optimized this (e.g., since MySQL 8.0.20, using a more efficient doublewrite buffer file implementation with reduced overhead compared to older versions).

**Interview importance:** ⭐⭐⭐⭐⭐ A classic, high-signal question: "Why does InnoDB need a doublewrite buffer if it already has a redo log?" — testing whether you understand that redo log replay alone can't fix torn pages.

---

### 4.8 Purge Thread(s)

**What is it?** Background thread(s) responsible for physically removing old, no-longer-needed undo log records and deleted row versions — the InnoDB analogue of what VACUUM does for Postgres, but structurally scoped just to the undo log and delete-marked rows rather than the full heap.

**Why does it exist:** Once no active transaction's snapshot could possibly need an old undo record anymore (i.e., every transaction that started before the deleting/updating transaction has since committed), that undo record is garbage and can be purged, reclaiming undo tablespace space and removing delete-marked rows from indexes.

**Relationship to long-running transactions:** Just like Postgres's autovacuum being blocked by long-open transactions, InnoDB's purge is blocked by any transaction still holding an old enough snapshot — this is *the* most common real-world cause of runaway undo tablespace growth in production InnoDB systems.

**Interview importance:** ⭐⭐⭐⭐ Directly parallels the Postgres VACUUM discussion — expect comparative questions ("what's InnoDB's equivalent of VACUUM?").

---

### 4.9 Other Background Threads (Brief Survey)

| Thread | Purpose |
|---|---|
| **Master Thread** | Historically the main coordinator for various periodic InnoDB housekeeping tasks (flushing, merging, purging); in modern InnoDB much of this responsibility has been distributed to more specialized dedicated threads below |
| **Page Cleaner Thread(s)** | Flush dirty pages from the buffer pool to disk in the background — the direct InnoDB analogue of Postgres's Background Writer |
| **IO Threads** | Dedicated threads handling asynchronous read/write I/O operations (separate read threads and write threads, configurable counts via `innodb_read_io_threads`/`innodb_write_io_threads`) |
| **Log Thread(s)** | Handle writing and flushing the redo log — analogous in purpose to Postgres's WAL Writer |

### 4.10 Clustered Index vs. Secondary Index (Recap + InnoDB Specifics)

Module 2 introduced this distinction; here's the InnoDB-specific mechanics in full.

**Clustered index:** Every InnoDB table *is* a B-Tree ordered by primary key, with full row data stored at the leaf level. If no primary key is declared, InnoDB picks the first `UNIQUE NOT NULL` index, or, failing that, silently generates an internal hidden 6-byte row ID (`DB_ROW_ID`) and clusters on that instead — a subtle, commonly-tested fact.

**Secondary index:** Leaf nodes store the indexed column(s) **plus the primary key value** (not a raw physical pointer). Looking up a row via a secondary index therefore requires two B-Tree traversals: (1) the secondary index, to find the primary key, then (2) the clustered index, using that primary key, to fetch the full row. This second traversal is often called a **bookmark lookup**.

```
Query: SELECT * FROM employees WHERE email = 'alice@x.com';
(assume a secondary index exists on email, primary key is id)

Step 1: Traverse secondary index on `email`
         → finds email='alice@x.com' maps to id=101

Step 2: Traverse CLUSTERED index (primary key B-Tree) using id=101
         → finds full row data

Total: 2 B-Tree traversals (unless the secondary index is "covering",
       i.e., contains every column the query needs, in which case
       step 2 can be skipped entirely)
```

**Why monotonic primary keys matter so much in InnoDB (recap from Module 2, now with mechanism):** Every `INSERT` must place the new row in primary-key order within the clustered B-Tree. A random primary key (e.g., a random UUID) means inserts land at random points across potentially many different leaf pages, causing frequent **page splits** and poor buffer pool locality — versus a monotonically increasing key (auto-increment, or a time-ordered UUID variant), where inserts always land at the rightmost edge of the tree, a cheap, predictable operation.

### 4.11 Row Formats

**What is it?** The specific byte-level layout InnoDB uses to serialize a row within a page — configurable per table via `ROW_FORMAT`.

| Row Format | Key Characteristic |
|---|---|
| `REDUNDANT` | Legacy format (pre-5.0.3 compatible); stores full-length placeholders for variable columns even if `NULL` — wasteful, rarely used today |
| `COMPACT` | Default in older MySQL versions; more efficient encoding of variable-length columns and `NULL`s via a compact header |
| `DYNAMIC` | Default since MySQL 5.7+; improves handling of large `TEXT`/`BLOB`/`VARCHAR` columns — stores only a 20-byte pointer inline for fully off-page columns (versus `COMPACT`'s partial-prefix-inline approach), giving more room for other columns to stay inline |
| `COMPRESSED` | Like `DYNAMIC`, but the entire page is also compressed using zlib before writing to disk — trades CPU for reduced storage/I/O, conceptually similar to Module 2's page-level compression preview |

**Interview importance:** ⭐⭐ Lower priority than Buffer Pool/Redo/Undo, but useful to know `DYNAMIC` is the modern default and why it exists (handling large off-page columns better).

### 4.12 Tablespaces

**What is it?** The physical file(s) on disk where InnoDB stores table and index data — the top of InnoDB's storage hierarchy (Tablespace → Segment → Extent → Page, referenced back in Module 2, Section 2.8).

**Types:**
- **System tablespace** (`ibdata1`): historically held all table data plus the data dictionary, undo logs, doublewrite buffer, and change buffer, unless configured otherwise.
- **File-per-table tablespaces** (`innodb_file_per_table = ON`, the modern default): each table gets its own `.ibd` file, making operations like `TRUNCATE TABLE` reclaim disk space immediately (since it's just deleting a file), and making per-table backup/restore far more practical.
- **General tablespaces**: user-created, shared tablespace files that can hold multiple tables — a middle ground between the monolithic system tablespace and strict file-per-table.
- **Undo tablespaces**: since MySQL 8.0, undo logs live in their own dedicated tablespace files (`undo_001`, `undo_002`, ...) rather than inside the system tablespace, making undo space management and truncation far easier operationally.

**Interview importance:** ⭐⭐⭐ "Why would you enable `innodb_file_per_table`?" is a practical, commonly-asked operational question.

---

### 4.13 Data Dictionary

**What is it?** InnoDB's (and, more broadly, MySQL's) metadata store — table definitions, column types, index definitions, foreign keys, and so on — the InnoDB-side counterpart to Postgres's `pg_catalog` (Module 1, Section 1.4.9).

**Evolution:** Prior to MySQL 8.0, metadata was scattered across non-transactional `.frm` files (one per table) plus various InnoDB-internal structures — a source of real operational pain (schema changes weren't fully crash-safe/atomic). Since MySQL 8.0, there's a unified, fully **transactional data dictionary**, stored in InnoDB tables themselves, exposed via `information_schema` — meaning DDL operations (like `CREATE TABLE`) are now properly atomic and crash-safe in a way they previously weren't.

**Interview importance:** ⭐⭐⭐ Knowing that the pre-8.0 `.frm`-file-based metadata was a real historical pain point (and *why* the unified data dictionary was a significant engineering improvement) signals genuine depth beyond textbook knowledge.

### 4.14 PostgreSQL vs. InnoDB — Full Side-by-Side (Module 3 + Module 4 Synthesis)

| Aspect | PostgreSQL | InnoDB (MySQL) |
|---|---|---|
| Concurrency model | Process per connection | Thread per connection |
| Table organization | Heap (unordered) | Clustered by primary key |
| MVCC old versions stored | In-heap, alongside current version | In a separate undo log, linked via roll pointer |
| Old-version cleanup | VACUUM (Autovacuum) | Purge Thread |
| WAL / redo log | WAL (variably-sized segment files) | Redo Log (fixed-size circular files) |
| Torn-page protection | Full-page writes in WAL (first write after checkpoint) | Doublewrite Buffer |
| Secondary index write buffering | Not applicable in the same way (HOT avoids some index writes instead) | Change Buffer |
| Buffer pool eviction | Clock-sweep | Young/old split LRU |
| Query-hot equality lookup optimization | Not built-in equivalently | Adaptive Hash Index |
| Metadata storage | `pg_catalog` (always transactional, native tables) | Unified transactional Data Dictionary (since 8.0; previously `.frm` files) |

**Interview importance:** ⭐⭐⭐⭐⭐ This comparison table, memorized, answers an enormous fraction of "compare Postgres and MySQL internals" interview questions directly.

### 4.15 Chapter Summary

- InnoDB uses a **thread-per-connection** model within a single `mysqld` process, unlike Postgres's process-per-connection model.
- The **Buffer Pool** uses a young/old split LRU (not clock-sweep) specifically to resist pollution from large one-off scans.
- The **Redo Log** is InnoDB's WAL equivalent; `innodb_flush_log_at_trx_commit` mirrors Postgres's `synchronous_commit` durability/performance trade-off.
- InnoDB's MVCC keeps only the **current** row version in the clustered index, with old versions in a separate **Undo Log** — structurally opposite to Postgres's in-heap versioning.
- The **Change Buffer** defers secondary index page updates to avoid random I/O; the **Doublewrite Buffer** protects against torn pages in a way redo log replay alone cannot.
- The **Purge Thread** is InnoDB's VACUUM-equivalent, cleaning up undo records once no transaction snapshot needs them — and is blocked by long-running transactions, just like autovacuum.
- Every InnoDB table is **clustered** by primary key; secondary index lookups require a second traversal ("bookmark lookup") into the clustered index unless the query is covered by the secondary index alone.

---

### 4.16 Cheat Sheet

```
mysqld              → single process, thread-per-connection
Buffer Pool          → InnoDB's page cache, young/old LRU split (anti-scan-pollution)
Redo Log              → InnoDB's WAL; innodb_flush_log_at_trx_commit = durability knob
Undo Log              → old row versions for MVCC + rollback; cleaned by Purge Thread
Change Buffer         → defers secondary index writes to avoid random I/O
                        (Insert Buffer = old name, inserts-only)
Adaptive Hash Index   → auto-built hash on hot B-Tree lookups, O(1) vs O(log n)
Doublewrite Buffer    → sequential pre-write copy, protects against torn pages
                        (redo log alone CANNOT fix a torn page)
Purge Thread          → InnoDB's VACUUM-equivalent; blocked by long transactions
Clustered Index       → the table IS the primary-key B-Tree (full row at leaf)
Secondary Index       → leaf stores indexed col + PK value → needs bookmark lookup
Row Formats           → REDUNDANT (legacy) < COMPACT < DYNAMIC (modern default) <
                        COMPRESSED (+ zlib page compression)
Tablespaces           → system (ibdata1) / file-per-table (.ibd) / general / undo
Data Dictionary       → unified transactional (8.0+) vs legacy .frm files (pre-8.0)
```
