# Part 6: Transactions & Concurrency Control

## Module 1: Transaction Fundamentals

> **Prerequisite check:** This module assumes you're comfortable with Parts 1–5 (relational model, SQL, normalization, indexing basics, and storage fundamentals). If any of those feel shaky, it's worth a quick refresher before diving in — everything here builds on the assumption that you already know *what* a database stores and *how* you query it. Now we focus on *what happens when multiple operations touch that data at the same time, and how the system guarantees nothing breaks.*

---

### 1.1 What Is a Transaction?

**Definition:**
A **transaction** is a single logical unit of work performed against a database that consists of one or more operations (reads and/or writes), and is treated by the database system as **one indivisible whole** — either *all* of its operations succeed and are permanently applied, or *none* of them are.

Formally, a transaction is a sequence:

```
T = { R(x), W(y), R(z), W(x), ... }
```

where `R(x)` means "read data item x" and `W(x)` means "write data item x."

**Why does it exist?**

Imagine a database with no concept of a transaction. Every SQL statement executes independently, and if the system crashes halfway through a multi-step business process, you have no way to know what succeeded and what didn't. Real-world business processes are rarely single operations — they are **groups of operations that only make sense together**. Transactions exist to let the database treat such groups as one atomic step, so the application programmer doesn't have to manually handle every possible partial-failure scenario.

**What problem does it solve?**

1. **Partial failure** — power outage, crash, or network drop mid-operation.
2. **Concurrent interference** — two users modifying the same data at the same time.
3. **Inconsistent business state** — e.g., money leaving one account without arriving in another.

**Real-life analogy:**

Think of a transaction like a **bank wire transfer form** you fill out at a counter. The form has two lines: "Debit ₹5,000 from Account A" and "Credit ₹5,000 to Account B." The clerk does not consider the form "processed" until *both* lines are stamped. If the branch's computer crashes after stamping only the first line, the entire form is torn up and redone from scratch the next day — never accepted half-done. That torn-up, all-or-nothing handling is exactly what a database transaction guarantees for a group of SQL statements.

**Practical example:**

```sql
BEGIN;

UPDATE accounts SET balance = balance - 5000 WHERE account_id = 'A';
UPDATE accounts SET balance = balance + 5000 WHERE account_id = 'B';

COMMIT;
```

If the server crashes after the first `UPDATE` but before `COMMIT`, the database guarantees that **neither** update is permanently visible. On restart, recovery (covered in detail in Part 7) rolls this back automatically.

**Interview importance:** ⭐⭐⭐⭐⭐
"What is a transaction and why do we need it?" is one of the most common opening questions in DB rounds — interviewers use it to gauge whether you understand transactions as a *correctness* mechanism, not just a syntax feature.

### 1.2 Transaction Lifecycle

A transaction moves through a well-defined lifecycle from the moment it starts until its effects are finalized (or discarded).

```
        BEGIN
          │
          ▼
      ┌────────┐   all ops executed   ┌──────────────────────┐
      │ ACTIVE │ ───────────────────► │ PARTIALLY COMMITTED  │
      └────────┘                      └──────────┬───────────┘
          │                                       │
          │ failure/                              │ writes flushed
          │ error detected                          & logged
          ▼                                       ▼
     ┌────────┐                           ┌───────────┐
     │ FAILED │                           │ COMMITTED │
     └───┬────┘                           └─────┬─────┘
         │ rollback                              │
         ▼                                       ▼
   ┌──────────┐                           ┌────────────┐
   │ ABORTED  │ ─────────────────────────►│ TERMINATED │
   └──────────┘                           └────────────┘
```

**Step-by-step walkthrough:**

1. The transaction **begins** — the database allocates it a transaction ID and, depending on the isolation level, a snapshot of the data.
2. It moves into the **Active** state, executing its reads and writes.
3. Once the *last* statement has executed (but before the commit is durably recorded), it is **Partially Committed**.
4. If everything checks out (constraints satisfied, logs flushed), the transaction becomes **Committed**.
5. If at any point something goes wrong — a constraint violation, deadlock victim selection, explicit `ROLLBACK`, or a crash — the transaction becomes **Failed**, then is rolled back into the **Aborted** state.
6. Finally, whether committed or aborted, the transaction reaches **Terminated** — it no longer exists in the system's active transaction table.

---

### 1.3 Transaction States (In Depth)

| State | Meaning | Can it still fail? | Who can move it forward? |
|---|---|---|---|
| **Active** | Transaction has begun; statements are executing | Yes | DB engine executing statements |
| **Partially Committed** | Final statement executed; not yet made durable | Yes (e.g., log flush failure, constraint check) | DB engine's commit protocol |
| **Committed** | All changes durably recorded; visible to others | No | — (final state) |
| **Failed** | An error occurred and normal execution can no longer continue | N/A — already failed | DB engine triggers rollback |
| **Aborted** | Rolled back; all changes undone | No | — (transaction restarts as a *new* transaction if retried) |
| **Terminated** | Transaction removed from the system's active list | No | — |

**Explaining each state like you're new to this:**

- **Active** is like a form that's currently being filled in — nothing is final yet.
- **Partially Committed** is like the form being fully filled but not yet stamped and filed — a last-second check (e.g., "does this violate a `UNIQUE` constraint?") can still reject it.
- **Committed** is the form stamped, filed, and now part of the permanent record. It survives even if the building burns down five minutes later (that's **Durability** — Module 2).
- **Failed** is the form having an error found on it (say, a required field was left blank) — it cannot proceed to filing.
- **Aborted** is the form being physically shredded and its effects erased.
- **Terminated** simply means the paperwork is closed out and archived either way.

**Common misconception:** People often think "Aborted" and "Failed" are the same thing. They're not — **Failed** is a *diagnosis* ("something went wrong"), while **Aborted** is the *action taken* ("we undid everything"). A transaction always passes through Failed before Aborted, never the reverse.

**Database engine behavior:**

- **PostgreSQL**: Once a statement inside a transaction errors out, the *entire transaction* is marked as aborted internally — you'll see `current transaction is aborted, commands ignored until end of transaction block` for every subsequent command until you issue `ROLLBACK` (or roll back to a `SAVEPOINT`).
- **MySQL (InnoDB)**: Statement-level errors are typically more forgiving — a single failed statement does *not* automatically abort the whole transaction unless it's a serious error (e.g., a deadlock victim or a constraint violation depending on `sql_mode`). This is a **major behavioral difference** and a classic interview/production gotcha.
- **Oracle**: Similar to MySQL in that an individual statement failure rolls back *that statement*, not necessarily the whole transaction, unless the error is fatal.

> **Common Mistake:** Developers migrating from MySQL to PostgreSQL are frequently surprised when a single failed `INSERT` inside a transaction poisons the entire transaction block. Always check for and handle SQL errors explicitly, or use `SAVEPOINT`s (Module 13) to isolate risky statements.

### 1.4 Transaction Boundaries

A **transaction boundary** marks exactly where a transaction begins and ends. Everything inside the boundary is treated as one atomic unit; anything outside it is a separate transaction.

```sql
-- Boundary Start
BEGIN;
    UPDATE inventory SET qty = qty - 1 WHERE sku = 'X123';
    INSERT INTO orders (sku, qty) VALUES ('X123', 1);
COMMIT;
-- Boundary End
```

Why boundaries matter: the **narrower** you make a transaction (i.e., the fewer statements and the shorter the time it stays open), the less lock contention and blocking you cause for other transactions. A poorly-bounded transaction — e.g., one that opens, then waits on user input, then finally commits minutes later — is one of the most common causes of production database slowdowns (see Module 16: Performance Considerations).

**Best Practice:** Keep transaction boundaries as tight as possible around only the statements that *must* be atomic together. Don't wrap read-only reporting queries or slow external API calls inside a transaction boundary unless absolutely necessary.

### 1.5 Autocommit

**Definition:** Autocommit is a connection-level mode in which **every individual SQL statement is automatically wrapped in its own implicit transaction** and committed immediately after execution, unless you explicitly start a transaction.

**Why it exists:** Most developers, most of the time, just want to run one statement and have it "just work" without thinking about transaction boundaries. Autocommit provides that convenience as the default behavior in almost all client libraries and command-line tools.

**How it behaves across engines:**

| Engine | Autocommit default | How to disable |
|---|---|---|
| PostgreSQL (`psql`) | ON | `BEGIN;` starts an explicit transaction, temporarily suspending autocommit until `COMMIT`/`ROLLBACK` |
| MySQL | ON (`autocommit=1`) | `SET autocommit=0;` or `START TRANSACTION;` |
| Oracle | Effectively OFF by convention — a transaction is implicitly open from the first DML statement until explicit `COMMIT`/`ROLLBACK` | N/A — Oracle doesn't have a literal "autocommit" flag in the same sense server-side, though client drivers (JDBC, etc.) simulate one |
| SQL Server | ON (autocommit mode) | `BEGIN TRANSACTION` |

**Practical example (MySQL):**

```sql
SET autocommit = 1;   -- default
UPDATE products SET price = 100 WHERE id = 1;  -- committed immediately, on its own

SET autocommit = 0;
UPDATE products SET price = 200 WHERE id = 1;  -- NOT committed yet
UPDATE products SET price = 300 WHERE id = 2;  -- still open
COMMIT;                                        -- both committed together now
```

**Edge case:** In autocommit mode, if a single statement affects multiple rows (e.g., `UPDATE ... WHERE status = 'pending'` touching 10,000 rows), that entire statement is *still* one atomic transaction — either all 10,000 rows update or none do. Autocommit does not mean "no transaction," it means "one statement = one automatically-managed transaction."

### 1.6 Explicit Transactions

**Definition:** An explicit transaction is one where the programmer deliberately marks the boundary using statements like `BEGIN` / `START TRANSACTION` ... `COMMIT` / `ROLLBACK`.

```sql
-- PostgreSQL / standard SQL
BEGIN;
    INSERT INTO orders (customer_id, total) VALUES (42, 999.00);
    UPDATE customers SET loyalty_points = loyalty_points + 10 WHERE id = 42;
COMMIT;
```

```sql
-- MySQL
START TRANSACTION;
    INSERT INTO orders (customer_id, total) VALUES (42, 999.00);
    UPDATE customers SET loyalty_points = loyalty_points + 10 WHERE id = 42;
COMMIT;
```

Explicit transactions give the developer full control over exactly which statements must succeed or fail together — this is essential any time business logic spans more than one write.

**Industry usage:** Virtually every checkout flow, funds-transfer flow, or inventory-decrement flow in production systems uses explicit transactions, because these processes inherently touch more than one table or row that must stay consistent with each other.

---

### 1.7 Implicit Transactions

**Definition:** An implicit transaction is automatically started by the database engine the moment a DML statement (`INSERT`/`UPDATE`/`DELETE`/`SELECT ... FOR UPDATE`) is issued — **without** an explicit `BEGIN` — and remains open until the application explicitly commits or rolls back.

This is subtly different from autocommit:

- **Autocommit** = each statement is its own complete transaction, committed automatically.
- **Implicit transaction mode** (notably in Oracle, and in SQL Server when `SET IMPLICIT_TRANSACTIONS ON` is used) = a transaction silently *begins* on the first statement but does **not** auto-commit; it stays open until you say so.

**Why the distinction matters (a classic interview trap):** Many candidates conflate "implicit" with "autocommit." They are opposite behaviors in terms of *when the transaction ends*, even though both avoid requiring an explicit `BEGIN`.

| Mode | Transaction starts... | Transaction ends... |
|---|---|---|
| Autocommit | Automatically, per statement | Automatically, per statement |
| Implicit transaction | Automatically, on first DML | Only on explicit `COMMIT`/`ROLLBACK` |
| Explicit transaction | On `BEGIN`/`START TRANSACTION` | Only on explicit `COMMIT`/`ROLLBACK` |

### 1.8 Nested Transactions (Overview)

**Definition:** A nested transaction is a transaction started *within* the scope of another already-active transaction.

Most relational databases **do not support true nested transactions**. Instead, they offer **savepoints** (covered fully in Module 13) which simulate a limited form of nesting — you can roll back to an inner savepoint without discarding the entire outer transaction, but there's no independent "commit" for the inner block; everything is only finalized when the *outermost* transaction commits.

```sql
BEGIN;                              -- outer transaction starts
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;

    SAVEPOINT sp1;                  -- "nested" checkpoint
    UPDATE accounts SET balance = balance + 100 WHERE id = 2;

    -- suppose something looks wrong with the second update
    ROLLBACK TO sp1;                -- undo just the second update

COMMIT;                             -- commits only the first update
```

**Why real nested transactions are hard:** If inner transactions could independently commit, they could make changes durable and visible to other sessions *before* the outer transaction decides whether the whole unit succeeds — which would break Atomicity at the outer level. This is why the industry standard approach is savepoints rather than true nesting.

**Database engine behavior:**
- **PostgreSQL, MySQL (InnoDB), SQL Server, Oracle** — all support `SAVEPOINT`, none support true independently-committable nested transactions in standard usage.
- Some ORMs (e.g., Django, SQLAlchemy) fake "nested transactions" in application code using savepoints under the hood — good to know for interviews about ORM internals.

### 1.9 Distributed Transactions (Introduction)

**Definition:** A distributed transaction is a transaction whose operations span **multiple, independent databases or resource managers** — potentially on different physical machines — but which must still behave atomically as a single unit: all participating databases commit, or all of them roll back.

**Why they exist:** Modern systems are rarely a single database. A single business operation ("place an order") might touch:
- An **Orders** database
- An **Inventory** database (possibly a different vendor/technology)
- A **Payments** service backed by its own database

If these are independent systems, a plain local transaction (which only guarantees atomicity within *one* database) cannot protect the operation as a whole. Distributed transactions solve this by coordinating commit/rollback decisions across all participants.

**A quick preview (full depth in Module 14):**
- **Two-Phase Commit (2PC):** A coordinator asks every participant to "prepare" to commit; only if *all* say yes does it tell everyone to actually commit.
- **XA Transactions:** A standardized protocol implementing 2PC across heterogeneous resource managers.
- **SAGA Pattern:** An alternative to 2PC used heavily in microservices, where each step has a compensating "undo" action instead of relying on a blocking coordinator.

We'll cover these in full mechanical detail, trade-offs, and failure scenarios in **Module 14**. For now, just remember: **a local transaction guarantees atomicity in one database; a distributed transaction guarantees it across several.**

### 1.10 Advantages, Disadvantages, Best Practices, Common Mistakes

**Advantages of using transactions:**
- Guarantees correctness under failure and concurrency.
- Simplifies application code — you don't manually handle every partial-failure path.
- Enables safe concurrent access by many users simultaneously.

**Disadvantages / costs:**
- Overhead: locking, logging, and (in MVCC systems) version-chain maintenance all cost CPU, memory, and I/O.
- Long-running transactions increase lock contention and can bloat undo/version storage.
- Improper use (e.g., wrapping unrelated operations together) can create unnecessary blocking.

**Best Practices:**
- Keep transactions short and touch as few rows/tables as possible.
- Never perform slow external calls (HTTP requests, email sending) inside an open transaction.
- Always explicitly handle both the success and failure paths in application code.
- Choose the narrowest isolation level that still gives you correctness (Module 11).

**Common Mistakes:**
- Forgetting to `COMMIT`, leaving a transaction open indefinitely (holding locks and blocking others).
- Assuming autocommit and implicit-transaction behavior are the same across engines.
- Wrapping a giant batch job in a single transaction instead of batching into smaller chunks.
- Not handling the "aborted transaction state" properly in PostgreSQL, continuing to send statements that get silently ignored.

**Performance implications:**
A transaction that's open for a long time — even one just sitting idle in an application connection pool — can prevent `VACUUM` (PostgreSQL) from cleaning up old row versions, or hold locks (any engine) that block other transactions, causing cascading slowdowns cluster-wide. We'll return to this in depth in Module 10 (MVCC) and Module 16 (Performance).

**Industry usage:**
Every payment gateway, e-commerce checkout, banking core system, airline booking engine, and inventory system relies fundamentally on correct transaction boundaries — we dedicate all of Module 15 to walking through these case studies in detail.

### 1.11 Chapter Summary

- A **transaction** is an indivisible logical unit of work: all-or-nothing.
- It moves through the lifecycle: **Active → Partially Committed → Committed/Failed → Aborted → Terminated**.
- **Autocommit** wraps each statement in its own auto-finalized transaction.
- **Implicit transactions** start automatically but stay open until explicitly finished.
- **Explicit transactions** are manually bounded with `BEGIN`/`START TRANSACTION` ... `COMMIT`/`ROLLBACK`.
- True **nested transactions** aren't supported by mainstream RDBMS — **savepoints** simulate the useful parts.
- **Distributed transactions** extend atomicity guarantees across multiple independent databases, via mechanisms like 2PC, XA, or SAGA (previewed here, detailed in Module 14).

### 1.12 Revision Notes / Cheat Sheet

| Concept | One-line takeaway |
|---|---|
| Transaction | All-or-nothing unit of work |
| Active | Statements currently executing |
| Partially Committed | Last statement done, not yet durable |
| Committed | Durable, visible, final |
| Failed | Error detected, cannot continue |
| Aborted | Rolled back, changes undone |
| Terminated | Removed from active transaction table |
| Autocommit | 1 statement = 1 auto-finished transaction |
| Implicit transaction | Auto-starts, but needs explicit end |
| Explicit transaction | Manually starts and ends |
| Savepoint | Partial rollback point inside a transaction |
| Distributed transaction | Atomicity across multiple databases |
