# Part 9: Database Recovery, Logging & Durability
## Module 9: Backup & Restore

> **Recap:** Modules 3–8 covered **crash recovery** in exhaustive depth — the log, WAL, ARIES, checkpoints, buffer policies. All of that machinery answers one narrow question: *"How do I recover from a crash where disk data is still intact?"* But Module 2 introduced failure types — Media Failure, Human Error, Catastrophic Failure — where **disk data itself is compromised or the log is gone.** This module covers the completely different toolkit needed for those: **Backup & Restore.**

---

## 📍 Crash Recovery vs Backup & Restore — The Line That Must Never Blur

This is worth stating as plainly as possible, because it's one of the most consequential distinctions in this entire handbook, and confusing the two is a real, damaging production mistake:

| | Crash Recovery (Modules 3–8) | Backup & Restore (This Module) |
|---|---|---|
| Handles | System crash, power failure, process failure | Media failure, human error, catastrophic failure |
| Relies on | The transaction log (still intact on disk) | A separately stored copy of the data (and often, archived logs) |
| Speed | Seconds to minutes | Minutes to hours |
| Automatic? | Yes, on every restart | No — usually requires a deliberate, manual restore action |
| Data loss risk | Zero for committed data | Possible, bounded by backup frequency (unless PITR is used) |

> ⚠️ A database with a perfect crash-recovery implementation (flawless WAL + ARIES) but **no backups** is still one snapped disk away from total, permanent data loss. The two systems are complementary, not substitutes for each other.

---

## 9.1 Full Backup

### What is a Full Backup?

A **Full Backup** is a complete, standalone copy of the entire database — every table, every index, every piece of data — captured at a specific point in time.

### Why It Exists

It's the foundation everything else builds on: a full backup alone is enough to fully restore a database to *some* working state, with no dependency on any other backup file.

### Real-Life Analogy

A full backup is like photocopying an entire 500-page book, cover to cover, every single week. It's thorough and completely self-sufficient — you never need last week's photocopy to make sense of this week's — but it's also the most time-consuming and storage-hungry approach if done too frequently.

### Advantages
- Simplest to restore from — just copy it back, no dependency chain.
- Self-contained — no risk of a missing intermediate file breaking the restore.

### Disadvantages
- Large storage footprint, especially for big databases.
- Time-consuming to create, especially under continuous write load (though modern engines support **online/hot** full backups without downtime, discussed in Module 11).
- Wasteful to run frequently if most of the data doesn't change between backups.

---

## 9.2 Incremental Backup

### What is an Incremental Backup?

An **Incremental Backup** captures only the data that has **changed since the most recent backup** — whether that previous backup was a full backup or another incremental backup.

### Real-Life Analogy

Instead of photocopying the entire 500-page book every week, you only photocopy the pages that were edited since your *last* photocopy session (which might itself have been an incremental session). To reconstruct this week's full book, you'd need: the original full photocopy, plus every incremental set of edited pages made since, applied **in order**.

### Why It Exists

Dramatically reduces backup time and storage compared to repeated full backups, especially for large databases where only a small fraction of data changes day to day.

### The Dependency Chain Risk

```
Full Backup (Sunday)
     │
     ▼
Incremental (Monday) — changes since Sunday
     │
     ▼
Incremental (Tuesday) — changes since Monday
     │
     ▼
Incremental (Wednesday) — changes since Tuesday
     │
     ▼
   To restore Wednesday's state:
   Full (Sun) + Incremental (Mon) + Incremental (Tue) + Incremental (Wed)
   — ALL must be applied, IN ORDER. If Tuesday's file is
     corrupted or missing, Wednesday's restore is impossible!
```

### Advantages
- Fast to create, minimal storage per backup.
- Efficient for large databases with low daily change volume.

### Disadvantages
- Restore requires the **entire chain** — full backup plus every incremental since, applied in strict order.
- A single corrupted or missing link in the chain breaks the ability to restore to any point after it.
- Restore time can be longer than a differential backup approach (Section 9.3) for the same total elapsed time, since more files must be sequentially applied.

---

## 9.3 Differential Backup

### What is a Differential Backup?

A **Differential Backup** captures all data that has changed **since the last FULL backup** (not since the last backup of any kind, unlike incremental).

### Real-Life Analogy

Rather than photocopying only pages changed since your *last* photocopy session (incremental), you photocopy every page that's different from the **original full copy**, no matter how many sessions have passed since then. Each differential photocopy set grows larger over time (as more changes accumulate since the full backup), but you only ever need **two** documents to reconstruct any point: the original full copy, plus the most recent differential set.

### Visual: Incremental vs Differential

```
INCREMENTAL:
Full (Sun) ──► Incr (Mon, changes since Sun)
           ──► Incr (Tue, changes since Mon)   [small, but ALL needed]
           ──► Incr (Wed, changes since Tue)

DIFFERENTIAL:
Full (Sun) ──► Diff (Mon, changes since Sun)
           ──► Diff (Tue, changes since Sun)   [grows larger each day,
           ──► Diff (Wed, changes since Sun)    but only 2 files needed
                                                  to restore ANY day]
```

### Advantages
- Restore only ever needs **two** files: the full backup plus the latest differential — simpler, faster, more robust restore process than incremental's long chain.
- A single corrupted differential backup only affects that day's restore option, not a whole chain — you can still restore from an earlier differential.

### Disadvantages
- Each differential backup grows larger over time as more changes accumulate since the last full backup — eventually approaching the size of a full backup itself, at which point taking a new full backup becomes worthwhile again.
- Slightly more storage and creation time than a same-day incremental backup would need, since differentials aren't as minimal.

### Comparison Table

| Aspect | Full | Incremental | Differential |
|---|---|---|---|
| Captures | Everything | Changes since last backup (any type) | Changes since last FULL backup |
| Backup Size | Largest | Smallest | Medium, grows over time |
| Backup Speed | Slowest | Fastest | Medium |
| Restore Complexity | Simplest (1 file) | Most complex (full chain needed) | Moderate (2 files needed) |
| Risk of Chain Break | None (self-contained) | High (any missing link breaks restore) | Low (only 2 dependencies) |

## 9.4 Physical Backup

### What is a Physical Backup?

A **Physical Backup** is a copy of the actual raw data files, exactly as they're stored on disk — the literal bytes of the table files, index files, and (often) relevant portions of the transaction log — taken at the filesystem or storage level.

### Real-Life Analogy

This is like photocopying the physical book page by page, exactly as printed — capturing the precise physical layout, formatting, and structure, not just "the words."

### Advantages
- Very fast to restore — it's essentially a direct file copy back into place, with minimal processing required.
- Preserves exact internal structure (indexes, physical layout) — no need to rebuild indexes from scratch after restore.
- Well-suited for large databases where speed of restore matters most.

### Disadvantages
- Tied to the specific database engine (and often, version and even platform) that created it — you generally cannot restore a physical backup from PostgreSQL into MySQL, for instance.
- Larger in size, typically, since it includes index structures and other physical overhead alongside the raw data.

### Examples
- PostgreSQL's `pg_basebackup` tool.
- Physical/binary snapshots taken via filesystem-level tools (e.g., LVM snapshots, cloud block storage snapshots).

---

## 9.5 Logical Backup

### What is a Logical Backup?

A **Logical Backup** captures the database's content in a portable, engine-independent representation — typically as a sequence of SQL statements (`CREATE TABLE`, `INSERT INTO`, etc.) or a structured export format that describes the data's *logical* content rather than its exact physical on-disk layout.

### Real-Life Analogy

Rather than photocopying the exact physical pages, you retype the book's entire content into a fresh word processor document — capturing all the *words* (the logical content) perfectly, but with a completely new physical layout (page breaks, fonts, etc., don't need to match the original at all).

### Advantages
- Portable across database versions, and sometimes even across different database engines (e.g., migrating from one RDBMS to another) — a job crash-recovery-style physical backups simply cannot do.
- Human-readable in many formats (plain SQL dumps can literally be opened in a text editor).
- Selective restore is easier — you can often restore just one table or a subset of data from a logical backup, rather than the entire database.

### Disadvantages
- Slower to create and restore than physical backups, since it must process, generate, or replay statements/records individually rather than performing raw file copies.
- Does not preserve exact physical structures like index internals — indexes are typically rebuilt from scratch during restore, which takes additional time.

### Examples
- PostgreSQL's `pg_dump` / `pg_dumpall`.
- MySQL's `mysqldump`.
- Oracle's Data Pump (`expdp`/`impdp`).

### Physical vs Logical — Comparison Table

| Aspect | Physical Backup | Logical Backup |
|---|---|---|
| Format | Raw data files (binary) | SQL statements / structured export |
| Speed | Fast | Slower |
| Portability | Low (engine/version-specific) | High (portable, sometimes cross-engine) |
| Restore includes indexes as-is? | Yes | No — indexes rebuilt |
| Selective restore | Harder | Easier (per-table, per-schema) |
| Typical Tools | `pg_basebackup`, LVM/cloud snapshots | `pg_dump`, `mysqldump`, Data Pump |

## 9.6 Snapshot Backup

### What is a Snapshot Backup?

A **Snapshot Backup** leverages underlying storage-layer or filesystem-layer capabilities (not the database engine itself) to instantly capture a point-in-time, copy-on-write image of the entire disk volume the database resides on.

### Why It's Fast

Rather than physically copying every byte immediately, a snapshot typically just records "as of this moment, here's the state" using copy-on-write metadata — actual data blocks are only duplicated lazily, as they're later modified, which makes snapshot creation itself nearly instantaneous regardless of database size.

### Real-Life Analogy

This is closer to Module 5's Shadow Paging concept than to traditional file copying: rather than photocopying the book, you simply note "as of 3:00 PM, this is exactly how every page looked" and only start actually duplicating pages if and when the original book gets edited afterward.

### Advantages
- Extremely fast to create, often taking mere seconds regardless of database size — a huge operational advantage for very large databases where a traditional full backup might take hours.
- Minimal impact on live database performance during the snapshot operation itself.

### Disadvantages
- Requires the underlying storage/filesystem layer to explicitly support snapshotting (not all environments do).
- Snapshots are typically tied to the specific storage system that created them — less portable than a logical backup.
- Care must be taken to ensure the database is in a **consistent state** at snapshot time (often requiring a brief coordination step with the database engine, like a checkpoint, to avoid capturing a torn or inconsistent moment).

### Examples
- Cloud provider disk snapshots (AWS EBS Snapshots, Google Persistent Disk Snapshots).
- LVM (Logical Volume Manager) snapshots on Linux.
- SAN/storage array-level snapshots in enterprise data centers.

## 9.7 Point-in-Time Recovery (PITR)

### What is PITR?

**Point-in-Time Recovery** is the capability to restore a database not just to the exact moment a backup was taken, but to **any specific moment in time** between a base backup and the present (or any point before a known bad event) — by combining a full/physical backup with a **replay of archived transaction logs** up to that exact moment.

### Why It's Uniquely Important

Recall Module 2's Human Error discussion: a committed `DROP TABLE` mistake is durably, correctly recorded by the transaction log — ordinary crash recovery will faithfully redo it, not undo it. PITR is precisely the tool built to solve this: restore a base backup, then replay the archived log **only up to the instant just before** the mistaken command, stopping there instead of replaying all the way to the crash/present moment.

### How PITR Works

```
Full Backup taken: Sunday 12:00 AM
     │
     ▼
Archived WAL/Redo Logs continuously accumulate: ─────────────────►
     │                                    │
     │                          Mistake happens: Wednesday 2:47 PM
     │                          (e.g., accidental DROP TABLE)
     ▼                                    ▼
Restore process:
  1. Restore Sunday's full backup onto new/clean storage
  2. Replay archived logs from Sunday 12:00 AM forward...
  3. ...but STOP replaying at Wednesday 2:46:59 PM —
     one second before the mistake
  4. Database is now exactly as it was, right before the disaster
```

### Requirements for PITR

- A base backup (full, physical, or snapshot).
- **Continuous log archiving** since that base backup — every WAL segment / redo log file generated must be preserved, not discarded, until it's no longer needed for any possible future PITR request (a direct connection to Module 6's checkpoint-driven log truncation discussion — PITR retention requirements often override what pure crash-recovery needs would otherwise allow).
- A precise target: a specific timestamp, a specific transaction ID, or a named recovery point.

### Real-World Example — PostgreSQL PITR

PostgreSQL supports PITR via:
1. Taking a base backup with `pg_basebackup`.
2. Continuously archiving WAL segments (via `archive_command` or newer WAL archiving mechanisms).
3. On restore, specifying a `recovery_target_time` (or `recovery_target_xid`/`recovery_target_lsn`) — PostgreSQL replays WAL up to but not including that exact point, then stops and opens the database for use.

## 9.8 Continuous Backup

### What is Continuous Backup?

**Continuous Backup** (sometimes marketed as "continuous data protection") extends the PITR concept to its logical extreme: rather than periodic full/incremental/differential backups plus separately archived logs, the system continuously streams every change (essentially, the log itself, in near-real-time) to a durable, often remote, storage location — minimizing the potential data-loss window (RPO, formally defined in Module 10) to seconds rather than hours or days.

### Why It Matters

For businesses with extremely low data-loss tolerance (financial trading systems, for example — previewed further in Module 13), waiting even a few hours between backups represents an unacceptable amount of potentially lost committed data if a catastrophic failure strikes right before the next scheduled backup. Continuous backup closes that gap.

### Relationship to Replication

Continuous backup is conceptually adjacent to (and sometimes implemented via) **replication** — a live standby copy continuously receiving and applying the primary's log stream. The line between "continuous backup" and "hot standby replica" can blur in practice; Module 10 and Part 10 (Distributed Databases) explore this relationship further.

## 9.9 Backup Verification

### What is Backup Verification?

**Backup Verification** is the practice of actively testing that a backup is genuinely usable — that it can be successfully restored and that the restored data is correct — rather than merely assuming a backup file exists and is fine.

### Why It's Absolutely Essential

This is one of the most repeated, hard-won lessons in all of production database operations:

> **"A backup that has never been restored is not a backup — it's a hope."**

Backups can silently fail for many reasons: disk corruption in the backup storage itself, an incomplete backup process that wasn't properly detected, a software bug in the backup tool, or a misconfigured backup job that's been "succeeding" while actually capturing empty or stale data for months.

### How to Verify

- **Regularly perform full test restores** onto a separate, isolated environment, and validate the restored data against expectations (row counts, checksums, specific known values).
- **Automate integrity checks** where possible (checksums on backup files themselves, connecting back to Module 3's checksum concept, but applied at the backup-file level).
- **Document and rehearse the restore procedure itself** — an untested runbook is nearly as risky as an untested backup file, since restore procedures under real crisis pressure are error-prone if unfamiliar.

## 9.10 Restore Process

### What is the Restore Process?

The **Restore Process** is the deliberate, often multi-step procedure of reconstructing a working database from one or more backup files (and possibly archived logs, for PITR).

### General Restore Steps

```
1. Identify the target: full restore to latest state, or PITR
   to a specific point in time?

2. Provision target storage/environment (new server, new disk,
   or overwrite existing, depending on the failure scenario
   from Module 2).

3. Restore the base backup:
   - Physical backup → copy raw files into place
   - Logical backup → replay SQL statements / import structured data
   - Snapshot → attach/mount the snapshot volume

4. (If PITR) Apply archived logs from the base backup's
   timestamp forward, up to the specified target point.

5. Perform post-restore validation:
   - Check data integrity (row counts, checksums, spot checks)
   - Verify application connectivity and basic functionality

6. Bring the database online / redirect application traffic
   to the restored instance.

7. Document the incident: what failed, what was restored,
   how much data (if any) was lost, and what the recovery
   took (feeding directly into Module 10's RTO/RPO tracking).
```

### Restore Time Considerations

Restore time depends heavily on backup type (physical restores are typically much faster than logical restores for large databases), backup size, network/disk throughput, and — for PITR — how much log needs to be replayed after the base restore completes. This directly determines a system's achievable **RTO**, formally defined in Module 10.

## 9.11 Advantages of a Robust Backup & Restore Strategy

- Provides protection against failure categories (media, human error, catastrophic) that crash recovery fundamentally cannot address.
- PITR specifically provides a safety net against the single most common real-world cause of serious data-loss incidents: human error.
- Enables confident, low-risk operational practices — upgrades, migrations, and risky maintenance can proceed knowing a verified restore path exists if something goes wrong.

## 9.12 Disadvantages / Costs

- Storage cost for retaining backups (and archived logs, for PITR) over time.
- Operational discipline required — backups must be scheduled, monitored, verified, and retained according to a well-thought-out policy, or they silently become worthless.
- Restore time can mean real, sometimes lengthy downtime — directly motivating the RTO/RPO planning covered in Module 10.

## 9.13 Best Practices

- Follow the well-known **3-2-1 backup rule**: at least **3** copies of your data, on **2** different types of storage media, with at least **1** copy stored **off-site** — directly addressing Module 2's Catastrophic Failure concerns.
- Automate backup scheduling, but never fully "set and forget" — schedule regular, mandatory verification restores (Section 9.9).
- Match backup type and frequency to your actual RPO/RTO requirements (Module 10) rather than an arbitrary default.
- Retain archived logs long enough to support your organization's realistic PITR needs, balancing this against storage costs.

## 9.14 Common Mistakes

- Treating "backup job shows success" as equivalent to "backup is restorable" — without verification (Section 9.9), this assumption is unjustified and has caused real, well-documented production disasters.
- Storing backups on the same physical infrastructure as the primary database, defeating the entire purpose for media and catastrophic failure scenarios (a direct callback to Module 2's isolation principle).
- Forgetting to archive logs needed for PITR, meaning that even though a full backup exists, you can only restore to that backup's exact timestamp — not to the more useful "moment right before the mistake."
- Confusing incremental and differential backups when designing a restore plan, leading to an incomplete or impossible restore chain during a real incident.

## 9.15 Edge Cases

- **Schema changes between backups:** A logical backup taken before a schema migration might not cleanly restore into a database that has since evolved — restore procedures must account for schema versioning.
- **Extremely large databases:** For multi-terabyte databases, even physical backups can take considerable time, motivating snapshot-based approaches (Section 9.6) specifically for their near-instant creation time.
- **Backup during peak write load:** Backups taken while the database is under heavy write activity require careful coordination (often via the database engine's own backup-mode APIs) to ensure a consistent, non-corrupted result — simply copying files off a live, actively-written disk without coordination can produce an unusable backup.

---

## 9.16 Chapter Summary

- **Full, Incremental, and Differential backups** trade off backup speed/size against restore complexity and robustness — Full is simplest to restore, Incremental is cheapest to create but riskiest to restore, Differential is a practical middle ground.
- **Physical backups** are fast, engine-specific, raw copies; **Logical backups** are slower but portable, engine-independent representations.
- **Snapshot backups** leverage storage-layer copy-on-write for near-instant backup creation.
- **Point-in-Time Recovery (PITR)** combines a base backup with archived log replay to restore to *any* specific moment — the essential tool against human error.
- **Continuous Backup** minimizes the data-loss window even further, blurring into replication.
- **Backup Verification** is non-negotiable — an unverified backup is not a reliable backup.
- The **Restore Process** is a deliberate, multi-step procedure whose speed directly determines a system's achievable RTO.

| Term | One-Line Meaning |
|---|---|
| Full Backup | Complete, self-contained copy |
| Incremental Backup | Changes since last backup (any type) — full chain needed to restore |
| Differential Backup | Changes since last FULL backup — only 2 files needed to restore |

## 9.19 MCQs (with Answers)

**Q1.** Which backup type is most vulnerable to a single corrupted file breaking the entire restore chain?
A) Full
B) Differential
C) Incremental
D) Snapshot

**Answer: C**

**Q2.** A logical backup is best described as:
A) A raw copy of data files
B) A portable, engine-independent representation like SQL statements
C) A storage-layer copy-on-write image
D) A checksum of the database

**Answer: B**

**Q3.** PITR is primarily useful for recovering from:
A) System crashes
B) Network failures
C) Human error (e.g., accidental DROP TABLE)
D) CPU failures

**Answer: C**

**Q4.** The 3-2-1 backup rule recommends:
A) 3 backups per day
B) 3 copies of data, 2 media types, 1 off-site
C) 3 different databases, 2 servers, 1 network
D) 3-minute backup intervals

**Answer: B**
