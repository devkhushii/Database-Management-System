## 10.0 Why This Module Exists

Modern hardware has many CPU cores, but a single query, executed by a single process/thread, can only use **one** of them. Parallel Query Execution lets a database split a single query's work across **multiple worker processes/threads**, each using a separate CPU core simultaneously, to dramatically reduce wall-clock time for large, expensive queries — without changing what the query means or its final result.

### The Core Trade-off

```
SERIAL EXECUTION                      PARALLEL EXECUTION
──────────────────                    ──────────────────
✓ No coordination overhead            ✓ Uses multiple CPU cores
✓ Simple, predictable                 ✓ Much faster wall-clock time
✗ Uses only ONE CPU core              ✗ Coordination overhead
✗ Slow for large scans/sorts/joins    ✗ Not all operations parallelize well
                                       ✗ Diminishing/negative returns for
                                          small queries (overhead > benefit)
```

## 10.1 Parallel Scans

### Definition

A **Parallel Scan** (PostgreSQL: `Parallel Seq Scan`, `Parallel Index Scan`) divides a table's pages among multiple worker processes, each independently scanning a **disjoint subset** of the table's pages, applying filters concurrently.

### Internal Working

```
Table: 10,000 pages, 4 workers

Worker 1: scans pages [1     - 2,500]
Worker 2: scans pages [2,501 - 5,000]
Worker 3: scans pages [5,001 - 7,500]
Worker 4: scans pages [7,501 - 10,000]

(Each worker applies the WHERE filter independently, on its own
 slice of pages, entirely in parallel with the others)
```

**Coordination mechanism (PostgreSQL specifics):** Workers don't get a pre-assigned fixed range upfront — instead, they cooperatively claim **chunks of pages** from a shared, synchronized "next block to scan" counter, so that if one worker finishes its current chunk faster (e.g., due to filtering out more rows and skipping ahead more quickly), it simply claims the next available chunk — a form of **dynamic load balancing** that keeps all workers busy rather than having faster workers sit idle waiting for a slower one.

### Interview Importance: ⭐⭐⭐⭐
Know the "dynamic chunk claiming" load-balancing detail — a strong depth signal beyond the basic "just divide the table into N parts" surface-level understanding.

## 10.2 Parallel Joins

### Definition

A **Parallel Join** distributes the work of a join operation (Module 6) across multiple workers, with each worker performing the join algorithm on its own slice of data.

### How Parallel Hash Join Works

```
1. Parallel Seq Scan reads the BUILD side (smaller input), each
   worker reading its slice.
2. ALL workers contribute their portion of build-side rows into a
   SINGLE SHARED hash table (not one hash table per worker!) —
   this shared build is a coordinated, synchronized step.
3. Once the shared hash table is fully built, workers independently
   scan their own slice of the PROBE side (larger input), each
   probing the SAME shared hash table concurrently.

           Worker 1 ─┐
           Worker 2 ─┼──► Build SHARED hash table (synchronized)
           Worker 3 ─┘         │
                                ▼
           Worker 1 ──► probes shared hash table with ITS slice of
           Worker 2 ──► probe-side rows, independently & in parallel
           Worker 3 ──►
```

### How Parallel Nested Loop Join Works

Typically, the **outer** side is scanned in parallel (each worker gets a slice of outer rows), while each worker independently performs its **own** inner index lookups for its assigned outer rows — this parallelizes cleanly since each outer row's inner lookup is fully independent of every other outer row's lookup.

### Why Parallel Sort-Merge Join Is Harder

Sort-Merge Join (Module 6, §6.7) requires **globally sorted** input on both sides — partitioning data across workers can break this global ordering unless a coordinated **parallel sort** (with a final merge step across workers' partial sorted outputs) is performed first, making it inherently more complex to parallelize cleanly than Hash Join.

### Interview Importance: ⭐⭐⭐⭐
Know that Hash Join parallelizes especially naturally (shared build + independent probing) — a commonly asked "why is Hash Join often preferred for parallel execution" follow-up.

## 10.4 Parallel Sorting

### Definition

**Parallel Sorting** distributes External Merge Sort's (Module 7) work across multiple workers — each worker independently performs Run Generation (and possibly some merge passes) on its own slice of data, producing multiple **partial sorted streams**, which must then be combined via a final coordinated merge step.

### Internal Working

```
Worker 1: sorts its slice of data → produces Sorted Stream 1
Worker 2: sorts its slice of data → produces Sorted Stream 2
Worker 3: sorts its slice of data → produces Sorted Stream 3

                    │        │        │
                    ▼        ▼        ▼
              ┌──────────────────────────┐
              │   Gather Merge (§10.6)    │  ← merges the 3 already-
              │   (coordinator process)    │     individually-sorted
              └──────────────────────────┘     streams into ONE
                          │                     final globally sorted
                          ▼                     output — this final
                  Final Sorted Output           merge step reuses
                                                 exactly the multi-way
                                                 merge logic from
                                                 Module 7, §7.4!
```

**Key insight:** This is a direct, elegant reuse of Module 7's multi-way merge (§7.4) — instead of merging disk-based runs from a single process, `Gather Merge` merges already-sorted **streams from separate parallel workers**. The underlying "compare the current head of each input, emit the smallest" merge logic is identical.

### Interview Importance: ⭐⭐⭐⭐
A beautiful "connect the dots across modules" topic — showing that Module 7's multi-way merge algorithm isn't just for single-process external sorting; it's the exact same mechanism reused for combining parallel workers' output.

## 10.5 Worker Processes

### Definition

**Worker Processes** are the separate OS-level processes (PostgreSQL) or threads (some other systems) spawned to execute a portion of a parallel query plan, coordinated by a **leader/coordinator process** (typically the original backend process handling the client connection).

### The Leader's Dual Role

The leader process is **not** purely a coordinator sitting idle — it typically **also participates as a worker itself**, executing a slice of the work in addition to its coordination duties (visible in Module 9, §9.8's example, where `loops=4` reflected 3 launched workers **plus** the leader, all contributing).

### Configuration Parameters (PostgreSQL, illustrative)

| Parameter | Meaning |
|---|---|
| `max_parallel_workers_per_gather` | Maximum workers a single query node can request |
| `max_parallel_workers` | System-wide cap on total parallel workers across all queries |
| `max_worker_processes` | Overall system cap on background worker processes (parallel workers are one consumer of this budget, alongside other background processes) |
| `parallel_setup_cost` | Cost model penalty for the overhead of launching parallel workers at all — must be "worth it" per the cost-based optimizer (Module 2) |
| `parallel_tuple_cost` | Cost model penalty per row that must be communicated from workers back to the leader |

### Why "Workers Launched" Can Be Less Than "Workers Planned" (Module 9 Callback)

If system-wide worker budgets (`max_parallel_workers`) are exhausted by other concurrently running queries, a query may be granted **fewer** workers than it planned for at optimization time — the plan structure stays the same, but with reduced parallelism, executing more slowly than originally estimated. This is exactly the gap Module 9, §9.8 flagged between "Workers Planned" and "Workers Launched."

### Interview Importance: ⭐⭐⭐⭐
The leader-also-participates detail and the planned-vs-launched gap are excellent, precise depth signals.

## 10.6 Exchange Operators

### Definition

**Exchange Operators** (a term from general parallel/distributed database theory, sometimes used more broadly than PostgreSQL's specific terminology) are the operators responsible for **moving data between parallel workers** — repartitioning, broadcasting, or gathering rows as needed to maintain correctness across the parallel plan's boundaries.

### Why They Exist

Not every operator can simply "run independently per worker with zero coordination." Data sometimes needs to be **redistributed** between workers (e.g., ensuring all rows with the same join/group key end up processed by the *same* worker, so a distributed hash join/aggregation can be computed correctly) — Exchange Operators are the general abstraction for this data-movement machinery.

### Relationship to PostgreSQL's Concrete Operators

PostgreSQL's `Gather` and `Gather Merge` (§10.6.1 below) are **specific, concrete instances** of the general Exchange Operator concept — specifically, the "many workers → one leader" collection pattern. Some other systems' Exchange Operators support additional patterns like "repartition" (many-to-many redistribution) — a more general capability than PostgreSQL's core parallel query implementation currently provides as of this writing.

### Interview Importance: ⭐⭐⭐
Good conceptual vocabulary for discussing parallel/distributed query execution generally, beyond just PostgreSQL specifics — useful if discussing distributed SQL engines (Spark SQL, Presto/Trino, etc.) in an interview.

## 10.6.1 Gather

### Definition

**`Gather`** is the PostgreSQL operator that **launches parallel workers**, collects rows produced by each worker (and the leader's own contribution), and combines them into a **single, unordered** stream for consumption by operators above it in the plan tree.

### Internal Working

```
                    Gather
                (collects rows from
                 ALL workers, in
                 WHATEVER order they
                 arrive — NOT sorted!)
              /       |        \
        Worker 1  Worker 2  Worker 3 (+ Leader, also contributing)
         (own        (own       (own
          data        data       data
          slice)      slice)     slice)
```

`Gather` makes **no ordering guarantee** — rows arrive at the collecting node in whatever order workers happen to finish producing them, which is perfectly fine for operations that don't care about order (like the input to a `HashAggregate`, Module 8's Finalize Aggregate step).

## 10.6.2 Gather Merge

### Definition

**`Gather Merge`** is like `Gather`, but additionally **preserves sort order** — it assumes each worker produces its output already sorted (e.g., each worker independently ran a Sort or Index Scan), and merges these already-sorted streams together using multi-way merge logic (Module 7, §7.4) to produce a single, correctly globally-sorted output.

### When It's Used Instead of Plain Gather

Whenever the query needs sorted output from the parallel portion (e.g., feeding into a Sort-Merge Join, Module 6 §6.7, or directly satisfying an `ORDER BY`) — `Gather Merge` avoids needing a **separate, additional** sort step after collecting the data, by doing the merge as part of the collection itself (exactly the "sort for free" spirit from Module 5, §5.7, now applied at the parallel-coordination level).

### Gather vs. Gather Merge: Summary

| Aspect | `Gather` | `Gather Merge` |
|---|---|---|
| Preserves order? | No | Yes |
| Requires each worker's input to be pre-sorted? | No | Yes |
| Underlying mechanism | Simple collection (any arrival order) | Multi-way merge (Module 7, §7.4) across worker streams |
| Typical use case | Feeding into Hash Aggregate/Hash Join (order-agnostic) | Feeding into Sort-Merge Join or satisfying `ORDER BY` |

### Interview Importance: ⭐⭐⭐⭐⭐
The `Gather` vs. `Gather Merge` distinction, and *why* you'd need the latter, is a very commonly tested, precise PostgreSQL-parallel-execution detail.

## 10.7 Full Annotated Example: Parallel Query Plan

```sql
EXPLAIN (ANALYZE)
SELECT customer_id, SUM(amount)
FROM orders
WHERE amount > 100
GROUP BY customer_id
ORDER BY customer_id;
```

**Hypothetical annotated output:**

```
Finalize GroupAggregate  (cost=... rows=10000 width=12)
                          (actual time=210.5..245.8 rows=9800 loops=1)
  │ ← Module 8, §8.2 + §8.6: final combine step of parallel Sort
  │   Aggregation (GroupAggregate = the sort-based variant)
  Group Key: customer_id
  ->  Gather Merge  (cost=... rows=30000 width=12)
                     (actual time=205.1..230.4 rows=29500 loops=1)
      │ ← Module 10, §10.6.2: preserves sort order across workers,
      │   since GroupAggregate (sort-based) needs sorted input
        Workers Planned: 3
        Workers Launched: 3
        ->  Partial GroupAggregate  (cost=... rows=10000 width=12)
                                     (actual time=200.2..200.2 rows=9833 loops=4)
            │ ← Module 8, §8.6: each worker computes its own partial
            │   per-customer subtotals independently
              Group Key: customer_id
              ->  Sort  (cost=... rows=75000 width=12)
                         (actual time=180.1..195.3 rows=73750 loops=4)
                  │ ← Module 7: each worker sorts ITS OWN slice by
                  │   customer_id, enabling the sort-based partial
                  │   aggregate above AND the Gather Merge below
                    Sort Key: customer_id
                    ->  Parallel Seq Scan on orders
                        (cost=... rows=75000 width=12)
                        (actual time=0.02..120.5 rows=73750 loops=4)
                        │ ← Module 10, §10.1: each worker independently
                        │   scans its own dynamically-claimed slice of
                        │   the orders table's pages
                          Filter: (amount > 100)
```

### The Full Story (Synthesizing Modules 1-10)

1. **Parallel Scan (§10.1):** 4 execution contexts (3 workers + leader, `loops=4`) each scan a dynamically-assigned slice of `orders`, filtering `amount > 100`.
2. **Parallel Sort (§10.4):** Each worker sorts its own slice by `customer_id` (Module 7 machinery, run independently per worker).
3. **Parallel Aggregation (§10.3 / Module 8 §8.6):** Each worker computes partial per-customer sums using Sort Aggregation (Module 8, §8.2) on its already-sorted slice — genuinely "free" streaming aggregation.
4. **Gather Merge (§10.6.2):** Because the query needs `ORDER BY customer_id` AND the partial aggregation is sort-based, `Gather Merge` collects the workers' streams while **preserving** the sorted order — reusing Module 7's multi-way merge logic across worker outputs.
5. **Finalize Aggregate:** The leader performs the final combine step (Module 8, §8.6), merging each worker's partial per-customer sums into the true final sums — correctly handling `SUM`'s decomposability.

## 10.8 When Does the Optimizer Choose NOT to Parallelize?

### Cost-Based Decision (Module 2 Callback)

Parallelism isn't free — it has real coordination overhead (`parallel_setup_cost`, `parallel_tuple_cost` from §10.5). The optimizer only chooses a parallel plan when its estimated cost (including this overhead) is genuinely **lower** than the best serial plan's cost — exactly Module 2's core cost-based optimization principle, now applied to the parallel-vs-serial decision itself.

### Common Reasons Parallelism Is Skipped

| Reason | Explanation |
|---|---|
| Table too small | Coordination overhead exceeds any possible benefit for tiny tables |
| Query inside a transaction with certain isolation/locking requirements | Some operations aren't safe to parallelize under certain concurrency conditions |
| Functions marked `PARALLEL UNSAFE` | User-defined functions not explicitly marked safe for parallel execution block parallelism for the whole plan (PostgreSQL specifically requires functions to be marked `PARALLEL SAFE` to be used within a parallel plan) |
| `INSERT`/`UPDATE`/`DELETE` (writes) | Historically, and in many systems still, only the read-only portion of a query can be parallelized — the actual write/modification step often remains serial for correctness/locking reasons (though this is an active area of ongoing development across databases) |
| Cursors / certain client-driven fetch patterns | Some execution modes aren't compatible with the parallel workers model |

### Interview Importance: ⭐⭐⭐⭐
Knowing that parallelism is itself a **cost-based decision** (not automatically applied whenever theoretically possible), and knowing at least 2-3 concrete reasons it might be skipped, is valuable, precise interview knowledge.

## 10.9 PostgreSQL vs MySQL vs Oracle: Parallel Execution Maturity

| Aspect | PostgreSQL | MySQL (InnoDB) | Oracle |
|---|---|---|---|
| Parallel scans | Yes (since PG 9.6+) | Very limited historically | Yes, very mature (Parallel Execution / PX servers since early versions) |
| Parallel joins | Yes (Hash, Nested Loop; Merge Join parallelization more limited) | Very limited | Yes, mature, all major join types |
| Parallel aggregation | Yes | Very limited | Yes, mature |
| Parallel DML (INSERT/UPDATE/DELETE) | Limited/restricted historically | Very limited | Yes, mature (Parallel DML, with specific enablement requirements) |
| Parallel index builds/maintenance | Yes (`CREATE INDEX` can use parallel workers) | Limited | Yes |

> 💡 **Practical takeaway:** Oracle has historically had the most mature, broadly-applicable parallel execution engine among these three; PostgreSQL's parallel query support, while genuinely solid for reads (scans, joins, aggregation, sorting), has historically been more conservative/restricted for writes; MySQL's parallel query capabilities have historically lagged both, though this continues to evolve across versions.

### Interview Importance: ⭐⭐⭐
Good comparative/breadth knowledge, useful for "which database would you choose for a heavy analytical workload" style discussion questions.

## 10.10 Best Practices, Common Mistakes & Edge Cases

### Best Practices
- Don't assume parallelism is "always on" for large queries — verify via `EXPLAIN` that a parallel plan was actually chosen, and check `Workers Planned` vs. `Workers Launched` (Module 9, §9.8) under real load.
- Mark user-defined functions used in hot-path queries as `PARALLEL SAFE` (when they genuinely are) if you want them eligible for use within parallel plans.
- Be mindful of system-wide worker budgets (`max_parallel_workers`) under high concurrent query load — many simultaneous parallel queries can end up competing for a limited shared worker pool.

### Common Mistakes
- Assuming more workers always means proportionally faster execution — coordination overhead and Amdahl's-Law-style diminishing returns (the serial portions of a plan cap the maximum possible speedup) are real, practical limits.
- Forgetting that `Gather` (unlike `Gather Merge`) does **not** preserve order — assuming parallel query results arrive in a predictable order without an explicit `ORDER BY` is a common, sometimes subtle correctness mistake in application code.
- Not accounting for reduced actual parallelism (`Workers Launched < Workers Planned`) when reasoning about expected query performance under concurrent production load.

### Edge Cases
- Very small parallel-eligible tables may still be planned as **serial** because `parallel_setup_cost` outweighs any benefit — this is expected, correct cost-based behavior, not a bug.
- Parallel plans interacting with certain transaction isolation levels or explicit locking (`SELECT ... FOR UPDATE`) may be restricted or entirely disabled for correctness reasons.

## 10.11 Chapter Summary

- **Parallel Scans** use dynamic, cooperative chunk-claiming to load-balance table-page scanning across workers.
- **Parallel Hash Join** builds one **shared** hash table cooperatively, then probes it independently per-worker — a naturally parallel-friendly pattern; Sort-Merge Join is comparatively harder to parallelize cleanly.
- **Parallel Sorting** has each worker sort its own slice, with a final `Gather Merge` combining already-sorted streams via Module 7's multi-way merge logic.
- **Parallel Aggregation** (fully detailed in Module 8, §8.6) uses Partial + Finalize Aggregate, physically connected via `Gather`/`Gather Merge`.
- **`Gather`** collects unordered results from workers; **`Gather Merge`** additionally preserves sort order via multi-way merging.
- The decision to parallelize at all is itself **cost-based** (Module 2) — real coordination overhead means small queries, or queries with `PARALLEL UNSAFE` functions, may remain serial.
- Oracle has historically led in parallel execution maturity, followed by PostgreSQL (strong for reads), with MySQL historically lagging both.

## 10.12 Cheat Sheet

```
PARALLEL EXECUTION QUICK REFERENCE
─────────────────────────────────────
Parallel Seq Scan     → dynamic chunk-claiming across workers
Parallel Hash Join     → SHARED hash table build, independent probing
Parallel Sort           → each worker sorts its own slice
Gather                  → collects worker output, NO order guarantee
Gather Merge             → collects worker output, PRESERVES order
                            (reuses Module 7's multi-way merge!)
Partial Aggregate        → per-worker partial aggregate (Module 8 §8.6)
Finalize Aggregate       → leader combines all partial aggregates

WHY PARALLELISM MIGHT BE SKIPPED
────────────────────────────────────
✗ Table/query too small (setup overhead > benefit)
✗ PARALLEL UNSAFE function used in the query
✗ Write (INSERT/UPDATE/DELETE) — often still restricted/serial
✗ Certain locking/isolation requirements (e.g., SELECT FOR UPDATE)
✗ System-wide worker budget exhausted by other concurrent queries
  (→ Workers Launched < Workers Planned)
```
