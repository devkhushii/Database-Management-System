### 5.0 Why This Module Exists

MVCC (Multi-Version Concurrency Control) is arguably **the single most-tested internals topic** across FAANG and database-engineer interviews, because it sits at the intersection of concurrency, storage, and correctness — three things interviewers love to probe simultaneously. If you can precisely explain how a transaction decides which row version it's allowed to see, you've demonstrated real internals fluency.

---

### 5.1 What Is MVCC and Why Does It Exist?

**Definition:** Multi-Version Concurrency Control is a concurrency control scheme where the database keeps **multiple versions** of a row simultaneously, allowing readers to see a consistent snapshot of data **without blocking writers**, and writers to proceed **without blocking readers**.

**The problem it solves — locking-only concurrency control:** Before MVCC-style designs became standard, many systems used pure locking: a reader would take a shared lock, a writer would take an exclusive lock, and readers/writers would simply block each other. This is correct but has an obvious cost: a single long-running report query (a reader) could block writers for its entire duration, and vice versa — a huge throughput problem for read-heavy-and-write-heavy mixed workloads.

**MVCC's core idea:** Instead of readers and writers fighting over a single copy of each row, **let writers create new versions instead of overwriting**, and give each reader a **consistent snapshot** (a specific point-in-time view) so they always see internally-consistent data, without ever needing to block a concurrent writer, and without a writer ever needing to block a concurrent reader.

**Real-life analogy:** Imagine a shared Google Doc with full version history. You (a reader) open the document and start reading — even if someone else starts editing it right now, your view stays exactly as it was when you opened it (your "snapshot"), while the editor freely makes changes that will only be visible to future readers who open a *new* view after the edit is saved.

**What MVCC does NOT eliminate:** Write-write conflicts. Two transactions trying to update the *same* row concurrently still need some form of coordination (locking or conflict detection) — MVCC solves the read/write blocking problem, not the write/write conflict problem.

---

### 5.2 Transaction IDs (XIDs / Transaction Sequence Numbers)

**What is it?** Every transaction, when it begins (or, in some engines, when it first performs a write), is assigned a unique, monotonically increasing identifier.

- **PostgreSQL:** Called an **XID**, a 32-bit unsigned integer (this finite size is precisely why XID wraparound, discussed in Module 3, is a real concern requiring active management via freezing).
- **InnoDB:** Called a **transaction ID** (`DB_TRX_ID`, stored per row in the hidden system column), a 48-bit or larger value in modern versions — still finite, but with a vastly larger range, making practical wraparound far less of an operational concern than in classic Postgres, though InnoDB has its own analogous safeguards.

**Why monotonic ordering matters:** The entire visibility-rule system (Section 5.4) is built on being able to compare two transactions' IDs and determine "did transaction A start before or after transaction B committed?" — this ordering is the foundation snapshot isolation is built on.

---

### 5.3 Version Chains

**What is it?** The linked sequence of all versions of a single logical row, from oldest to newest (or newest to oldest, depending on traversal direction), that a database maintains to support MVCC.

**PostgreSQL's version chain (in-heap, recap + formalized):** Versions live as separate physical tuples, each with `xmin` (creating XID) and `xmax` (deleting/superseding XID, or 0/invalid if still current). There's no single explicit "pointer" field chaining them in the general case (a HOT chain, from Module 3, is a special same-page optimization) — instead, all versions simply exist in the heap, and any given query, when it needs to find the version visible to it, may need to consult the table's indexes or scan to locate candidate versions, filtering by the visibility rules below.

**InnoDB's version chain (undo-log-based, formalized):** The clustered index holds only the **current** version, with a `DB_ROLL_PTR` pointing to an undo log entry describing how to reconstruct the *previous* version. That previous version's undo entry, in turn, points to the version before it, and so on — forming an explicit linked list backward in time, stored entirely in the undo log, separate from the main table.

```
INNODB VERSION CHAIN (explicit linked list via roll pointers)

Clustered Index (current):
┌──────────────────────────────────┐
│ salary=60000  TRX_ID=130  ROLL_PTR │──┐
└──────────────────────────────────┘  │
                                         ▼
                          Undo Log Entry #1:
                          ┌──────────────────────────┐
                          │ salary=55000  TRX_ID=120    │
                          │ ROLL_PTR ────────────────┐  │
                          └──────────────────────────┼──┘
                                                        ▼
                                          Undo Log Entry #2:
                                          ┌──────────────────────┐
                                          │ salary=50000 TRX_ID=100 │
                                          │ ROLL_PTR = NULL (oldest) │
                                          └──────────────────────┘
```

**Why the direction of traversal differs conceptually:** In InnoDB, reconstructing an *old* version requires walking backward through the undo chain from the current version (more chain-walking work for older snapshots). In Postgres, all versions are physically peers in the heap — there's no chain-walking cost in the same sense, but there is the cost of dead tuples occupying page space until vacuumed (a space cost rather than a chain-walk cost).

### 5.4 Snapshot Visibility & Read Views

**What is a snapshot?** A specific point-in-time definition of "which transactions' effects am I allowed to see?" — captured once (timing depends on isolation level, Section 5.7) and used to filter every row version a query examines.

**PostgreSQL's snapshot structure**, conceptually, consists of:
- `xmin`: the earliest XID still active when the snapshot was taken (anything older is guaranteed committed or aborted already)
- `xmax`: one past the latest XID assigned so far when the snapshot was taken (anything ≥ this is definitely in the future, invisible)
- A list of XIDs that were **active (in-progress)** at snapshot time — these are treated as invisible even though their IDs fall between `xmin` and `xmax`

**PostgreSQL's visibility rule (simplified core logic)** for whether a given row version is visible to a snapshot:

```
A row version (with xmin_v = creating XID, xmax_v = deleting XID) is VISIBLE if:
  1. xmin_v is committed AND xmin_v was not "active" (in-progress) at snapshot time
     AND xmin_v < snapshot.xmax   (i.e., it existed before our snapshot began)
  AND
  2. Either xmax_v is invalid (row not yet deleted/updated), OR
     xmax_v's deleting transaction is NOT committed, OR
     xmax_v was "active" at snapshot time, OR
     xmax_v >= snapshot.xmax   (i.e., the deletion happened after our snapshot began)
```

In plain English: *"I can see a row version if the transaction that created it had definitely finished before my snapshot, AND the transaction that deleted it (if any) either hasn't happened yet from my point of view, or hasn't committed."*

**InnoDB's Read View**, conceptually very similar in spirit, consists of:
- The list of transaction IDs that were active (uncommitted) when the Read View was created
- The smallest and largest transaction IDs among those active transactions (`up_limit_id`, `low_limit_id`)

**InnoDB's visibility rule**, when examining a row version with creator `DB_TRX_ID`:

```
A row version created by transaction T is VISIBLE to this Read View if:
  1. T < up_limit_id  (T committed before the oldest active transaction at snapshot time
     started — definitely visible), OR
  2. T is in the Read View's "active list" → NOT visible (T hadn't committed at
     snapshot creation time), OR
  3. T >= low_limit_id → NOT visible (T started after our snapshot, i.e., the future)
  Otherwise (T falls in the gap, committed, not in active list) → VISIBLE

If NOT visible, InnoDB walks the undo chain (via ROLL_PTR) to the PRIOR version
and re-applies this same check, repeating until a visible version is found
(or none exists, meaning the row didn't exist yet from this snapshot's view).
```

**Side-by-side comparison:**

| Aspect | PostgreSQL | InnoDB |
|---|---|---|
| Snapshot structure | `xmin`, `xmax`, active-XID list | `up_limit_id`, `low_limit_id`, active-TRX-ID list (Read View) |
| Where versions live | In-heap, as physical peer tuples | Current in clustered index; old versions in undo log |
| Finding the visible version | Scan/index directly to a matching tuple, check visibility | Start at current version, walk undo chain backward until a visible version is found |
| Cost of an old snapshot | Dead tuples occupy space (cleaned later by VACUUM) | Longer undo chain walk per row access (cleaned later by Purge) |

**Interview importance:** ⭐⭐⭐⭐⭐ Being able to state either engine's visibility rule precisely (not just "it checks if the version is committed") is a top-tier signal of real internals depth.

### 5.5 Undo Records (InnoDB Focus, Recap + Detail)

Already introduced in Module 4; here we tie it explicitly into the MVCC visibility mechanism above.

**What's inside an undo record:** The prior value(s) of the changed column(s) (not necessarily the *entire* row — InnoDB can store a more compact "delta" in many cases), the transaction ID that made the change, and a roll pointer to the *next-older* undo record for that row (continuing the version chain).

**Dual purpose:** Undo records serve **both**:
1. **Rollback** — if the transaction that created this undo record aborts, InnoDB uses the undo record to physically revert the change.
2. **MVCC reads** — as shown in Section 5.4, older snapshots walk this same undo chain to reconstruct a visible historical version.

This dual purpose is precisely why undo log growth is sensitive to long-running transactions from *either* angle: an uncommitted transaction needs its own undo available for potential rollback, and any other transaction with an older snapshot needs undo chains preserved for MVCC visibility.

---

### 5.6 Garbage Collection: VACUUM vs. Purge (Comparative Deep Dive)

Both mechanisms answer the same question — "which old versions are now provably useless and can be reclaimed?" — with the same underlying safety principle: **a version can be reclaimed once no current or future snapshot could possibly need it**, i.e., once every transaction that was active when a newer version superseded it has since completed.

**The shared concept — "OldestXmin" / oldest active Read View boundary:** Both engines must track the oldest snapshot/Read View boundary still in use system-wide. Anything older than that boundary is safe to garbage-collect; anything at or newer must be preserved.

**PostgreSQL VACUUM** (recap from Module 3, now framed as MVCC garbage collection specifically):
- Scans heap pages, identifies dead tuples (`xmax` committed and older than the oldest active snapshot boundary)
- Removes them, compacts the page, updates indexes and the Visibility Map
- **Blocked by:** any transaction holding a snapshot older than the dead tuple's `xmax`

**InnoDB Purge Thread** (recap from Module 4, now framed the same way):
- Walks undo log records, identifies ones older than the oldest active Read View boundary
- Physically removes them from the undo tablespace, and removes any fully delete-marked rows from indexes
- **Blocked by:** any transaction holding a Read View older than the undo record's creating transaction

**Why "blocked by long transactions" is the universal MVCC failure mode:** This isn't an implementation quirk of one engine — it's a direct, unavoidable mathematical consequence of the visibility-rule design itself. *Any* MVCC system that preserves old versions for snapshot correctness must, by definition, be unable to reclaim a version that some open snapshot might still need. This is worth stating explicitly in an interview — it signals you understand this as a fundamental trade-off of MVCC, not a bug.

### 5.7 Isolation Levels & Snapshot Timing

*(Full transaction isolation theory was covered in earlier parts of this handbook; this section focuses specifically on the MVCC mechanism underlying each level.)*

**The key mechanical difference between isolation levels, in MVCC terms, is simply: *when* is the snapshot/Read View taken?**

| Isolation Level | Snapshot Timing | Behavior |
|---|---|---|
| Read Committed | A **new** snapshot/Read View is taken for **every individual statement** within the transaction | Each statement sees the latest committed data as of *that statement's* start — can see different data across statements in the same transaction ("non-repeatable reads" possible) |
| Repeatable Read | A **single** snapshot/Read View is taken **once, at the start of the transaction** (or first statement, depending on engine specifics), and reused for all statements | The entire transaction sees one consistent point-in-time view throughout — no non-repeatable reads |
| Serializable | Builds on Repeatable Read/Snapshot Isolation but adds extra conflict detection to prevent certain anomalies (e.g., write skew) that pure snapshot isolation alone permits | Strictest; may abort transactions that would violate true serializability, even if MVCC visibility alone wouldn't have flagged a conflict |

**Important nuance — Postgres's `REPEATABLE READ` vs. textbook "Snapshot Isolation":** Postgres's default MVCC-based `REPEATABLE READ` is very close to classic Snapshot Isolation, but Postgres's actual `SERIALIZABLE` level (Serializable Snapshot Isolation, SSI) adds genuine additional conflict-detection machinery on top — it is not simply "Repeatable Read plus a bit more locking," it's a distinct algorithm layered on top of the MVCC snapshot mechanism.

**Important nuance — MySQL/InnoDB's `REPEATABLE READ` default:** Unlike the SQL standard's baseline expectation, InnoDB's default isolation level is `REPEATABLE READ` (not `READ COMMITTED`, which is the default for many other systems including Postgres) — a frequently-tested "gotcha" fact.

**Interview importance:** ⭐⭐⭐⭐⭐ "When exactly is the snapshot taken, and how does that differ between Read Committed and Repeatable Read?" is an extremely common, high-signal question.

### 5.8 A Complete Worked Example: Two Concurrent Transactions

```
Time  Transaction A (Repeatable Read)         Transaction B

t1    BEGIN;
t2    SELECT salary FROM emp WHERE id=1;
      → sees salary = 50000 (snapshot taken now)
t3                                             BEGIN;
t4                                             UPDATE emp SET salary=60000 WHERE id=1;
t5                                             COMMIT;
t6    SELECT salary FROM emp WHERE id=1;
      → STILL sees salary = 50000
      (same snapshot as t2, transaction B's
       commit is invisible to it — even though
       it's now the "real" committed value)
t7    COMMIT;
t8                                             ...new transaction, new snapshot...
t9                                             SELECT salary FROM emp WHERE id=1;
      → sees salary = 60000 (new snapshot,
        sees B's committed change)
```

**What's physically happening underneath, per engine:**

- **PostgreSQL:** At t4-t5, a new heap tuple version (`salary=60000`) is created with `xmin` = B's XID; the old version's `xmax` is set to B's XID. Transaction A's snapshot (fixed at t2) still considers the old version visible (its `xmin` predates A's snapshot) and the new version invisible (its `xmin` is not yet "safely committed and predating the snapshot" from A's perspective — specifically, B's XID wasn't active at A's snapshot time in this example, but the rule about `xmax_v >= snapshot boundary` for the *old* row, combined with the *new* row's `xmin` falling after A's snapshot xmax, is what keeps A pinned to the old version).
- **InnoDB:** At t4-t5, the clustered index row is updated in place to `salary=60000`, `DB_TRX_ID`=B's ID, with a roll pointer to an undo record preserving `salary=50000`. When A re-reads at t6, InnoDB sees the current version's `DB_TRX_ID` (B) is not visible to A's Read View (B wasn't committed at Read View creation... more precisely, B is either in A's active list or started after A's snapshot), so InnoDB walks the roll pointer to the undo record and returns `salary=50000` from there instead.

This worked example is exactly the kind of walkthrough interviewers want to see you produce unprompted.

### 5.9 Advantages, Disadvantages, Best Practices

**Advantages of MVCC (general):**
- Readers never block writers, writers never block readers — dramatically better concurrency than pure locking for mixed read/write workloads
- Consistent, repeatable snapshots are essentially free to provide once the versioning machinery exists

**Disadvantages:**
- Old versions must be tracked and eventually cleaned up — a real, ongoing operational cost (VACUUM/Autovacuum tuning in Postgres; undo tablespace and Purge monitoring in InnoDB)
- Long-running transactions have an outsized, sometimes surprising negative impact system-wide, since they pin the garbage-collection boundary
- Extra storage/computation overhead per row (visibility metadata, undo chains) compared to a naive single-version design

**Best practices:**
- Keep transactions as short as possible, especially ones that stay open while idle ("idle in transaction" in Postgres is a particularly dangerous anti-pattern)
- Monitor the oldest open transaction/snapshot age as a first-class operational metric (`pg_stat_activity` in Postgres; `information_schema.INNODB_TRX` in MySQL)
- Understand your isolation level's snapshot timing before assuming "repeatable read" behavior in application logic

**Common mistakes:**
- Assuming MVCC eliminates the need to think about isolation levels entirely — it changes *what kind* of anomalies are possible, but doesn't eliminate all of them (e.g., write skew under snapshot isolation)
- Leaving connections open with uncommitted transactions (common in poorly-written connection-pooled application code) and being surprised by bloat/undo growth later

### 5.10 Chapter Summary

- MVCC lets readers and writers proceed concurrently without blocking each other by maintaining **multiple versions** of each row and giving each transaction a consistent **snapshot**.
- Both Postgres and InnoDB assign monotonically increasing **transaction IDs**, used to determine visibility.
- **Version chains** differ structurally: Postgres keeps versions as physical peer tuples in the heap; InnoDB keeps only the current version in the clustered index, with older versions in a separate, explicitly-linked **undo log**.
- Each engine's precise **visibility rule** compares a row version's creating/deleting transaction ID against the requesting transaction's snapshot boundaries and active-transaction list.
- **Garbage collection** (VACUUM / Purge) can only reclaim versions no open snapshot could still need — which is why long-running transactions are the universal MVCC failure mode across engines.
- Isolation level differences are fundamentally about **when the snapshot is taken**: per-statement (Read Committed) vs. once-per-transaction (Repeatable Read/Serializable).

### 5.11 Cheat Sheet

```
MVCC core idea: multiple row versions + per-transaction snapshot
                → readers never block writers, writers never block readers
                → does NOT solve write-write conflicts

Transaction IDs: PG XID (32-bit, wraparound risk) vs InnoDB TRX_ID (48-bit+)

Version storage: PG = in-heap peer tuples (xmin/xmax)
                 InnoDB = current in clustered index + undo log chain (roll ptr)

Visibility check (both, conceptually):
  "was the creator committed AND before my snapshot?
   AND was the deleter (if any) either absent, uncommitted, or after my snapshot?"

Garbage collection: PG VACUUM / Autovacuum   vs   InnoDB Purge Thread
  BOTH blocked by: any transaction holding an older snapshot/Read View

Isolation level = snapshot timing:
  Read Committed  → new snapshot PER STATEMENT
  Repeatable Read → ONE snapshot for the whole transaction
  Serializable    → Repeatable Read + extra conflict detection

Gotcha: InnoDB's DEFAULT isolation level is REPEATABLE READ (not Read Committed)
```
