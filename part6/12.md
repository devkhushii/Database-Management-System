# Part 6: Transactions & Concurrency Control

## Module 12: Deadlocks

> Module 7 flagged this repeatedly: **2PL guarantees serializability but NOT freedom from deadlock.** This module is the payoff — a complete treatment of what deadlocks are, how to detect them, how to prevent or avoid them entirely, and what happens once one is found.

---

### 12.1 What Is a Deadlock?

**Definition:** A **deadlock** is a situation where two or more transactions are each waiting for a resource (typically a lock) held by another transaction **in the same waiting set**, such that **none of them can ever proceed** without external intervention.

**Real-world analogy:**
Two cars meet at a narrow one-lane bridge from opposite directions. Each is waiting for the other to reverse first, since neither can move forward while the other blocks the path. If neither backs down, both sit there **forever** — that's a deadlock. Someone (a traffic cop, i.e., the deadlock detector) has to force one of them to back up.

**Minimal example:**

```
T1: X-lock(A)  ...  wants X-lock(B) → BLOCKED (T2 holds B)
T2: X-lock(B)  ...  wants X-lock(A) → BLOCKED (T1 holds A)
```

Neither transaction will ever release its held lock, because each is stuck waiting to acquire its *next* lock before it can finish and release anything.

---

### 12.2 The Four Necessary Conditions for Deadlock

A deadlock can only occur if **all four** of the following conditions hold **simultaneously** (this is the classic Coffman conditions framework from operating systems theory, directly applicable to database locking):

1. **Mutual Exclusion:** At least one resource (lock) must be held in a mode that cannot be shared (e.g., an Exclusive lock) — if everything could always be shared, there'd be nothing to wait for.
2. **Hold and Wait:** A transaction holding at least one resource is waiting to acquire additional resources currently held by other transactions.
3. **No Preemption:** A resource (lock) cannot be forcibly taken away from a transaction holding it — it can only be released voluntarily (via commit/abort).
4. **Circular Wait:** There exists a **cycle** of transactions T1 → T2 → ... → Tn → T1, where each Ti is waiting for a resource held by T(i+1).

**Why this matters:** Deadlock **prevention** strategies (Section 12.5) work specifically by breaking **one** of these four conditions, guaranteeing deadlock cannot occur, at some cost to concurrency or practicality. This four-condition framework is the standard way to organize and remember prevention strategies — a favorite exam structure.

---

### 12.3 Wait-For Graph

**Definition:** A **Wait-For Graph** is a directed graph where each node represents a transaction, and a directed edge `Ti → Tj` means "Ti is waiting for a lock currently held by Tj."

**The deadlock detection theorem:** *A deadlock exists in the system if and only if the Wait-For Graph contains a cycle.*

**Constructing a Wait-For Graph from a lock table:**

```
Lock Table:
  Resource A: Held by T1 (X-lock); T2 waiting for X-lock
  Resource B: Held by T2 (X-lock); T1 waiting for X-lock

Wait-For Graph:
  T2 → T1   (T2 waits for T1, who holds A)
  T1 → T2   (T1 waits for T2, who holds B)

   T1 ──► T2
    ▲       │
    └───────┘

CYCLE DETECTED: T1 → T2 → T1  → DEADLOCK EXISTS
```

**Worked example with three transactions (more complex cycle):**

```
T1 holds A, wants B
T2 holds B, wants C
T3 holds C, wants A

Wait-For Graph:
   T1 ──► T2 ──► T3
    ▲              │
    └──────────────┘

CYCLE: T1 → T2 → T3 → T1 → DEADLOCK EXISTS (a 3-way deadlock)
```

**Important nuance:** Not every wait creates a deadlock — a transaction simply waiting for a lock that will eventually be released (no cycle in the wait-for graph) is normal, healthy blocking behavior, not a deadlock. Only a **cycle** signals a deadlock.

---

### 12.4 Deadlock Detection

**Definition:** **Deadlock Detection** is a strategy where the database **allows** deadlocks to potentially occur, but periodically (or on every new wait) checks the Wait-For Graph for cycles, and if one is found, forcibly resolves it by **aborting one of the transactions in the cycle** (the "victim," Section 12.9).

**How it works — the algorithm:**
1. Maintain the Wait-For Graph as transactions request and release locks.
2. Periodically (e.g., every few hundred milliseconds, or triggered on each new blocking wait) run a **cycle-detection algorithm** (standard graph DFS, tracking the current recursion path) over the graph.
3. If a cycle is found, select a **victim** transaction from the cycle and **abort** it, releasing its locks — this breaks the cycle and allows the remaining transactions to proceed.

**Trade-offs of detection-based approaches:**
- **Advantage:** Transactions are never unnecessarily restricted or forced to acquire locks upfront (unlike prevention/avoidance strategies) — maximum flexibility during normal, non-deadlocked operation.
- **Disadvantage:** Deadlocks *do* happen and must be detected (with some detection latency) and resolved via abort, which wastes the aborted transaction's work.

**Industry usage:** **This is the approach used by virtually all major production RDBMS** (PostgreSQL, MySQL/InnoDB, Oracle, SQL Server) — detection-based deadlock handling, rather than prevention or avoidance, because detection is simpler to implement correctly and doesn't require transactions to declare their resource needs upfront (which, as we saw with Conservative 2PL in Module 7, is often impractical).

**Frequency of detection checks — a genuine performance trade-off:**
- Checking too **frequently** wastes CPU cycles running the cycle-detection algorithm when no deadlock exists.
- Checking too **infrequently** means transactions sit deadlocked (uselessly holding locks and blocking others) for longer before being resolved.
- Most engines use a combination: an immediate check when a new "wait" edge would be added to the graph (catching many deadlocks instantly), plus periodic broader scans as a safety net.

---

### 12.5 Deadlock Prevention

**Definition:** **Deadlock Prevention** strategies guarantee deadlocks can **never occur** by ensuring that at least one of the four necessary conditions (Section 12.2) can never hold. Unlike detection, prevention stops deadlocks from ever forming in the first place — at some cost to concurrency or flexibility.

**Common prevention strategies (attacking the "Circular Wait" and "Hold and Wait" conditions specifically, since Mutual Exclusion and No Preemption are usually inherent/necessary properties of locking itself):**

**1. Resource Ordering (attacks Circular Wait):**
Assign a **global, fixed order** to all lockable resources (e.g., by table name, then primary key value). Require every transaction to acquire locks **strictly in that order**. Since no transaction can ever request a "lower-ordered" resource after already holding a "higher-ordered" one, a cycle in the wait-for graph becomes mathematically impossible.

```
Global order: accounts.A < accounts.B < accounts.C  (alphabetical, say)

T1 needs A and B → must acquire A first, then B (correct order)
T2 needs B and A → must ALSO acquire A first, then B (forced by the global rule,
                     even though T2's "natural" logic wanted B first)

→ No transaction can ever hold B while waiting for A, so the classic
  "T1 holds A wants B, T2 holds B wants A" deadlock pattern is IMPOSSIBLE.
```

**Real-world analogy:** This is like requiring everyone in a building fire drill to always exit through stairwells in a fixed, agreed order (e.g., floor by floor) rather than everyone rushing through whichever door is nearest — it eliminates the possibility of two groups meeting head-on and blocking each other in a narrow corridor.

**2. Wait-Die and Wound-Wait Schemes (attack Hold and Wait, using transaction timestamps — connecting directly back to Module 8!):**

These two schemes use transaction **timestamps** (older = smaller timestamp = higher priority in both schemes) to decide, whenever a transaction Ti wants a lock held by Tj, whether Ti should **wait** or be **aborted (die)**:

| Scheme | Ti is OLDER than Tj (`TS(Ti) < TS(Tj)`) | Ti is YOUNGER than Tj (`TS(Ti) > TS(Tj)`) |
|---|---|---|
| **Wait-Die** | Ti **waits** for Tj | Ti is **aborted (dies)** and restarts later with the **same** original timestamp |
| **Wound-Wait** | Ti **"wounds" (forcibly aborts) Tj**, then acquires the lock | Ti **waits** for Tj |

**Why these guarantee no deadlock:** In both schemes, notice that a transaction only ever waits for another transaction with a **specific, consistent relative age** (Wait-Die: only older waits for younger; Wound-Wait: only younger waits for older) — this consistent directional rule makes a circular wait (which would require inconsistent age relationships around the cycle) provably impossible.

**Key difference between the two:**
- **Wait-Die** is "non-preemptive" in spirit toward the *waiting* transaction — Ti (older) simply waits; it's the *younger* Tj that gets aborted if roles were reversed.
- **Wound-Wait** is more aggressive — an older transaction **actively kills** a younger one holding a needed resource, rather than waiting for it.

**Restart with the same timestamp — a crucial detail:** In both schemes, an aborted-and-restarted transaction keeps its **original** timestamp (rather than getting a fresh, later one) — this guarantees it will eventually become the "oldest" transaction in the system and stop being repeatedly aborted, **preventing starvation** (Section 12.10).

---

### 12.6 Deadlock Avoidance

**Definition:** **Deadlock Avoidance** strategies allow transactions to request locks dynamically (unlike strict prevention's rigid rules) but only **grant** a lock request if doing so would **not** lead to a state from which deadlock becomes unavoidable — requiring the system to have some advance knowledge of transactions' future resource needs to make this judgment (conceptually related to the classic Banker's Algorithm from operating systems, applied to the database locking context).

**Why it's less common in practice than detection:** Like Conservative 2PL (Module 7.5), true deadlock avoidance requires knowing transactions' future resource needs in advance — information that's rarely available for typical, conditionally-branching application transactions. This is why **detection** (Section 12.4), not avoidance, dominates in real production RDBMS.

---

### 12.7 Timeout Strategy

**Definition:** A simpler, pragmatic alternative (or complement) to graph-based detection: if a transaction has been **waiting for a lock longer than some configured timeout threshold**, the system assumes it *might* be deadlocked (even without formally verifying a cycle) and **aborts** it automatically.

**Advantages:**
- Extremely simple to implement — no need to maintain and analyze a Wait-For Graph at all.
- Works even in distributed systems where constructing a global Wait-For Graph across multiple nodes is expensive or complex.

**Disadvantages:**
- **False positives:** A transaction might simply be waiting behind a legitimately slow (but not deadlocked) transaction, and get needlessly aborted once the timeout expires.
- **False negatives (delay):** A genuine deadlock might not be caught until the full timeout period elapses, wasting more time than immediate cycle detection would.
- Choosing the "right" timeout value is an inherently imprecise trade-off (too short = excessive false-positive aborts; too long = deadlocks linger, blocking other transactions).

**Industry usage:** Many systems use timeout as a **safety-net backstop** in addition to formal graph-based detection — e.g., "detect cycles actively, but also, just in case, abort anything that's been waiting more than N seconds regardless."

---

### 12.8 Deadlock Resolution — Putting It Together

Once a deadlock is confirmed (via cycle detection or timeout), the system must:
1. **Select a victim** transaction from the cycle (Section 12.9).
2. **Roll back** the victim (undoing all its work via the undo log, Module 2/Part 7).
3. **Release** all locks held by the victim, allowing the remaining transaction(s) in the (former) cycle to proceed.
4. Optionally, **automatically restart** the victim transaction (some application frameworks / drivers do this transparently; others surface the error to the application to handle).

---

### 12.9 Victim Selection

**Definition:** **Victim Selection** is the process of choosing **which** transaction in a detected deadlock cycle to abort, when multiple transactions form the cycle.

**Common victim-selection criteria (often combined with weights):**
1. **Least amount of work done so far** (e.g., fewest log records written, or shortest running time) — minimizes wasted work from the abort.
2. **Fewest locks held** — minimizes the "unwind" cost of releasing locks and rolling back.
3. **Lowest priority** (if the system supports transaction priority levels) — deliberately choosing to sacrifice a lower-priority background job over a user-facing critical transaction.
4. **Avoiding repeated victimization of the same transaction** — most engines track how many times a given transaction has already been chosen as a victim and deliberately avoid picking it again indefinitely, to prevent starvation.

**Real-world analogy:** Think of victim selection like an air traffic controller deciding which of two planes on a collision course should divert — ideally choosing whichever has the least disruption cost (e.g., less fuel spent, fewer passengers affected), while making sure the *same* plane isn't always the one forced to divert every single time.

---

### 12.10 Starvation

**Definition:** **Starvation** occurs when a specific transaction is **repeatedly** delayed or aborted (e.g., always chosen as the deadlock victim, or always losing out to higher-priority transactions) such that it **never** makes progress, even though the system as a whole is not deadlocked.

**Why it's distinct from deadlock:** In a deadlock, **no** transaction in the cycle can proceed. In starvation, **other** transactions in the system make progress just fine — it's only one specific, unlucky transaction that keeps getting sacrificed or delayed.

**How it's prevented:** As mentioned in Section 12.5 (Wait-Die/Wound-Wait) and 12.9 (victim selection), the standard fix is to ensure a transaction that has been aborted/delayed multiple times is given **increasing priority** on subsequent attempts (e.g., by preserving its original, aging timestamp, or by explicitly boosting its priority after N failures) — guaranteeing it eventually "wins" and completes.

---

### 12.11 Livelock

**Definition:** **Livelock** is a related but distinct pathology: transactions are **not blocked** (they're actively "doing something") but make **no real progress**, because they keep reacting to each other in a way that repeatedly undoes any progress made — somewhat like two people trying to pass each other in a narrow hallway, each repeatedly stepping aside in the *same* direction as the other, perpetually blocking each other despite both actively moving.

**Difference from deadlock:** Deadlocked transactions are **stuck waiting**, doing nothing. Livelocked transactions are **actively executing** (e.g., repeatedly aborting and immediately retrying) but never actually complete, because their retries keep colliding with each other in the same unlucky pattern.

**How it's mitigated:** Introduce **randomized backoff** before retrying an aborted transaction (rather than retrying immediately) — this is exactly why exponential backoff with jitter is a standard practice in distributed systems and OCC-style retry logic (Module 9) — it breaks the "synchronized collision" pattern that causes livelock.

### 12.12 Advantages, Disadvantages, Best Practices

**Advantages of Detection-based handling (the industry standard):**
- No upfront restriction on transaction behavior — maximum flexibility.
- Deadlocks, while possible, are typically rare in well-designed applications and resolved quickly.

**Disadvantages:**
- Requires ongoing overhead to maintain and periodically scan the Wait-For Graph.
- The chosen victim's work is wasted and must be retried, at some cost.

**Best Practices:**
- **Access resources in a consistent order** across your application's code paths (the same idea as resource-ordering prevention, applied as an application-level best practice even when the DB uses detection, not prevention) — this dramatically reduces the *likelihood* of deadlocks even in detection-based systems.
- **Keep transactions short** — shorter transactions hold locks for less time, reducing the window during which a deadlock cycle could form.
- **Implement automatic retry logic** in your application for deadlock-victim errors (most database drivers surface a specific error code, e.g., PostgreSQL's `40P01`, MySQL's `1213`) — deadlocks are an expected, normal occurrence in concurrent systems, not a sign of a bug in themselves.
- Monitor deadlock frequency in production — a **rising** rate of deadlocks often signals an application-level access-pattern problem (e.g., inconsistent lock ordering across different code paths) worth fixing at the source.

**Common Mistakes:**
- Not handling deadlock-victim errors gracefully in application code, causing user-facing failures instead of a transparent retry.
- Assuming deadlocks indicate a "broken" database — they're an expected consequence of concurrent locking and are handled by design, not a sign of corruption.
- Ignoring inconsistent lock-acquisition order across different parts of a codebase (e.g., one code path updates `accounts` then `orders`; another updates `orders` then `accounts`) — a classic, entirely preventable deadlock source.

**Performance Implications:** Frequent deadlocks are usually a symptom of a deeper contention or access-pattern problem, and their resolution (aborts + retries) adds real latency and wasted work under load — Module 16 covers monitoring and mitigation strategies further.

**Industry Usage:** All major production RDBMS surface deadlock errors to the application (rather than resolving them silently), requiring application-level retry handling — a critical, practical detail every backend engineer working with relational databases must know and implement correctly.

### 12.13 Chapter Summary

- A **deadlock** is a cycle of transactions each waiting on a resource held by the next.
- The **four necessary conditions**: Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait — all four must hold for deadlock to occur.
- The **Wait-For Graph** models waiting relationships; a **cycle** in it means a deadlock exists.
- **Detection** (build the graph, find cycles, abort a victim) is the dominant real-world strategy.
- **Prevention** (Resource Ordering, Wait-Die, Wound-Wait) guarantees deadlock can never occur, at some cost to flexibility.
- **Avoidance** requires advance knowledge of future needs — rarely practical.
- **Timeout** is a simple, imprecise backstop, often used alongside formal detection.
- **Victim Selection** picks which transaction to sacrifice, balancing wasted-work minimization against starvation prevention.
- **Starvation** (a transaction perpetually loses out) and **Livelock** (transactions actively but fruitlessly collide) are related but distinct pathologies from deadlock itself.

### 12.14 Revision Notes / Cheat Sheet

```
4 Necessary Conditions: Mutual Exclusion + Hold-and-Wait + No Preemption + Circular Wait
Wait-For Graph cycle    ⇔ Deadlock exists

DETECTION   : allow deadlocks, find cycles, abort a victim    [INDUSTRY STANDARD]
PREVENTION  : Resource Ordering | Wait-Die (older waits) | Wound-Wait (older wounds younger)
AVOIDANCE   : needs future knowledge — rarely practical
TIMEOUT     : abort after waiting too long — simple but imprecise

Victim selection: least work done, fewest locks, avoid repeated victimization (anti-starvation)
Starvation ≠ Deadlock : one txn repeatedly loses, others proceed fine
Livelock ≠ Deadlock    : txns actively execute but collide repeatedly, no progress
```
