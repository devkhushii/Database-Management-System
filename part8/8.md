## 8.0 Why This Module Exists

`GROUP BY` and aggregate functions (`SUM`, `COUNT`, `AVG`, `MIN`, `MAX`) are among the most common SQL patterns in real-world analytics, reporting, and dashboards. Computing them efficiently — especially over data too large for memory — requires dedicated algorithms, directly analogous to (and in some cases literally reusing) the join and sort machinery from Modules 6–7.

---

## 8.1 Hash Aggregation

### Definition

**Hash Aggregation** builds an in-memory **hash table** keyed by the `GROUP BY` column(s), maintaining a running aggregate value (sum, count, etc.) per group as rows are scanned — directly analogous to Hash Join's build phase (Module 6, §6.4), but updating an aggregate instead of storing full rows.

### Internal Working

```
Hash Table (keyed by group-by column):
┌──────────────────────────────────────┐
│ 'ACTIVE'   → running_sum=1500, count=12│
│ 'INACTIVE' → running_sum=800,  count=5 │
│ 'PENDING'  → running_sum=200,  count=2 │
└──────────────────────────────────────┘

FOR EACH input row:
    key = row.group_by_column
    IF key NOT IN hash_table:
        hash_table[key] = initialize_aggregate(row)
    ELSE:
        hash_table[key] = update_aggregate(hash_table[key], row)

AFTER all rows processed:
    emit one output row per hash_table entry
```

### Complexity

| Metric | Value |
|---|---|
| Time Complexity | O(N) — single pass over input, O(1) average hash table operations |
| Memory Usage | O(number of distinct groups) — NOT O(N)! |
| Requires input sorted? | No |

### Why It's Often the Default Choice

Unlike Sort Aggregation (§8.2), Hash Aggregation requires **no sort step** — it processes rows in whatever order they arrive, making it the fastest option **when the number of distinct groups is small enough to fit comfortably in memory**, regardless of the total input size.

### When It Struggles

If the number of **distinct groups** is very large (high-cardinality `GROUP BY` column, e.g., grouping by `user_id` across billions of rows with millions of distinct users), the hash table itself can exceed available memory — requiring disk-spilling strategies (conceptually similar to Grace/Hybrid Hash Join's partitioning approach from Module 6, §6.5-§6.6).

### Interview Importance: ⭐⭐⭐⭐⭐
The default, most commonly discussed aggregation strategy — expect detailed questions on when it beats Sort Aggregation.

## 8.2 Sort Aggregation

### Definition

**Sort Aggregation** first **sorts** the input by the `GROUP BY` column(s) (reusing Module 7's External Merge Sort machinery if the data doesn't fit in memory), then makes a **single sequential pass** over the sorted data, computing aggregates for each contiguous run of matching group-by values.

### Internal Working

```
Step 1: SORT input by group_by_column (Module 7 machinery)
        (or read from an index that already provides this order —
         Module 5, §5.7 — "sort for free," exactly as in Sort-Merge Join)

Step 2: SEQUENTIAL PASS over sorted data
        current_key = NULL
        running_aggregate = NULL

        FOR EACH row IN sorted_input:
            IF row.group_by_column != current_key:
                IF current_key IS NOT NULL:
                    EMIT (current_key, running_aggregate)   ← close out previous group
                current_key = row.group_by_column
                running_aggregate = initialize_aggregate(row)
            ELSE:
                running_aggregate = update_aggregate(running_aggregate, row)

        EMIT (current_key, running_aggregate)   ← emit final group after loop ends
```

### Visual Walkthrough

```
Sorted input (by status): ['ACTIVE','ACTIVE','ACTIVE','INACTIVE','INACTIVE','PENDING']
                              amt=100  amt=200  amt=50    amt=300     amt=400   amt=75

Pass:
  Row 1 (ACTIVE, 100): new group → current_key='ACTIVE', sum=100
  Row 2 (ACTIVE, 200): same group → sum=300
  Row 3 (ACTIVE, 50):  same group → sum=350
  Row 4 (INACTIVE,300): NEW group → EMIT ('ACTIVE', 350); current_key='INACTIVE', sum=300
  Row 5 (INACTIVE,400): same group → sum=700
  Row 6 (PENDING,75):  NEW group → EMIT ('INACTIVE', 700); current_key='PENDING', sum=75
  (end of input)        → EMIT ('PENDING', 75)
```

**Key property:** Since input is sorted, all rows belonging to the same group are **guaranteed to be contiguous** — meaning the aggregation pass only ever needs to track **one group's running aggregate at a time**, using O(1) memory for the aggregation itself (the memory cost lives in the sort phase, not the aggregation pass).

### Complexity

| Metric | Value |
|---|---|
| Time Complexity | O(N log N) if sorting needed, O(N) if already sorted (via index) |
| Memory Usage (aggregation pass itself) | O(1) — only current group's running aggregate needs tracking |
| Memory Usage (sort phase, if needed) | Per Module 7's external sort memory requirements |

### Hash Aggregation vs. Sort Aggregation: The Decision

| Factor | Favors Hash Aggregation | Favors Sort Aggregation |
|---|---|---|
| Number of distinct groups | Small (fits comfortably in memory) | Large (sort avoids needing all groups in memory at once) |
| Input already sorted (via index) | No benefit from pre-sort | Huge benefit — "sort for free," effectively O(N) |
| Need for sorted output anyway (e.g., `ORDER BY` on group key) | No synergy | Reuses the same sort, avoiding duplicate work |
| Memory availability | Must hold all distinct groups' running aggregates | Only needs O(1) for the aggregation pass itself (sort phase memory is separate/bounded via external sort) |

### Interview Importance: ⭐⭐⭐⭐⭐
The Hash-vs-Sort aggregation trade-off directly mirrors Module 6's Hash-Join-vs-Sort-Merge-Join trade-off — a very natural, very common interview comparison question.

## 8.3 Group Aggregation

### Definition

**Group Aggregation** is the general umbrella term for computing one aggregate result **per distinct group** defined by `GROUP BY` — as opposed to a single aggregate over the *entire* table (a degenerate case sometimes called "scalar aggregation," e.g., `SELECT COUNT(*) FROM orders` with no `GROUP BY`).

### Relationship to Hash/Sort Aggregation

Group Aggregation isn't a separate *algorithm* — it's the **query pattern** that Hash Aggregation (§8.1) and Sort Aggregation (§8.2) both implement. Think of it as the "what" (compute per-group aggregates), while Hash/Sort Aggregation are the "how" (the physical algorithms achieving it) — directly mirroring the Logical-vs-Physical Plan distinction from Module 2, §2.2.

### Interview Importance: ⭐⭐
Mostly terminology clarification — useful for precisely distinguishing logical intent from physical implementation when discussing aggregation in interviews.

## 8.4 Streaming Aggregation

### Definition

**Streaming Aggregation** refers to computing aggregates **incrementally, row-by-row, as data flows through the query plan**, following the Iterator/Volcano pull-based execution model (Module 1, §1.9) — without necessarily requiring all input to be materialized or fully sorted/hashed upfront in a separate, distinct phase.

### Relationship to Sort Aggregation

Sort Aggregation (§8.2), once its input is sorted (whether via an explicit sort step or "for free" via an index), is inherently **streamable** — it can emit each completed group's result **as soon as** the next differing group-by value is encountered, without waiting for the entire input to be consumed first. This is a genuinely valuable property: the very next operator up the plan tree (Module 1's `Next()` calls) can start consuming aggregated results **before** the aggregation operator has finished processing all its input.

```
STREAMING BEHAVIOR (Sort Aggregation on already-sorted input):

Input arrives: A, A, A, B, B, C, C, C, C
                              │
                    First "B" arrives → group 'A' is COMPLETE,
                    can be emitted UPSTREAM IMMEDIATELY,
                    without waiting for 'C' rows to even arrive!

vs. HASH AGGREGATION (non-streaming, in the general case):
    Cannot emit ANY group's result until the ENTIRE input has
    been scanned — because a later row might still belong to
    an EARLIER group's key (input isn't sorted, so group 'A'
    rows could be scattered anywhere throughout the input,
    including near the very end).
```

### Why This Distinction Matters

Streaming operators integrate more efficiently into the pull-based Iterator model (Module 1, §1.9) — they can begin producing output, and unblock downstream operators, **incrementally**, rather than acting as a hard "pipeline breaker" that must fully consume its input before producing any output at all (Hash Aggregation is a classic **pipeline breaker** in this sense, alongside Sort operators and Hash Join's build phase).

### Interview Importance: ⭐⭐⭐⭐
The "pipeline breaker vs. streaming operator" distinction is a sophisticated, high-signal concept — connects Module 1's execution model directly to this module's aggregation strategies.

## 8.5 Partial Aggregation

### Definition

**Partial Aggregation** computes **intermediate, incomplete** aggregate results early in a query plan — often **before** a join or before data is fully collected across parallel workers/distributed nodes — with a final **combining/merging** step performed later to produce the true final aggregate.

### Why It Exists

Aggregating **before** an expensive join, rather than after, can dramatically reduce the amount of data flowing into (and through) that join — directly analogous to Module 3's predicate/projection pushdown philosophy, but applied to aggregation instead of filtering.

### Before / After Example

```sql
SELECT c.name, SUM(o.amount)
FROM customers c JOIN orders o ON c.id = o.customer_id
GROUP BY c.name;
```

**BEFORE (naive — aggregate AFTER the full join):**
```
     γ (GROUP BY name, SUM(amount))
              │
     ⋈ (c.id = o.customer_id)
     /                        \
  customers               orders (ALL rows, unaggregated,
                            flow through the join FIRST)
```

**AFTER (partial aggregation pushed below the join):**
```
     γ (GROUP BY name, SUM(partial_sum))     ← final combine step
              │
     ⋈ (c.id = o.customer_id)
     /                        \
  customers          γ (GROUP BY customer_id, SUM(amount) AS partial_sum)
                              │
                           orders
```
*Now `orders` is pre-aggregated by `customer_id` (its own natural grouping key relative to the join condition) **before** the join — potentially collapsing millions of individual order rows down to a much smaller number of per-customer subtotal rows, before that smaller intermediate result ever reaches the join operator.*

> ⚠️ **Correctness caveat:** This transformation is only valid when the pre-join grouping key (here, `customer_id`) is a **superset/refinement** of the final grouping key relative to the join relationship (each customer's orders all map to exactly one customer row) — the optimizer must prove this functional-dependency relationship holds before applying the transformation. This connects to Module 3's general theme: transformations must be **provably** safe, not just "usually a good idea."

### Interview Importance: ⭐⭐⭐⭐
An advanced but increasingly common optimization to discuss — shows understanding of how aggregation and join optimization (Modules 3, 6) can interact and compose.

## 8.6 Parallel Aggregation

### Definition

**Parallel Aggregation** splits aggregation work across multiple **parallel worker processes/threads**, each computing a **partial aggregate** (§8.5) over a subset of the data, followed by a final **combine/merge** step (often run by a single coordinating process) that merges the partial results into the true final aggregate.

### Internal Working (Two-Level Pattern)

```
                    Data (large table)
                            │
        ┌───────────────┬───────────────┬───────────────┐
        ▼               ▼               ▼               ▼
   Worker 1          Worker 2         Worker 3         Worker 4
   (scans 1/4        (scans 1/4       (scans 1/4       (scans 1/4
    of the data)       of the data)     of the data)     of the data)
        │               │               │               │
   Partial          Partial          Partial          Partial
   Aggregate 1      Aggregate 2      Aggregate 3      Aggregate 4
   (per-group        (per-group        (per-group        (per-group
    subtotals,        subtotals,        subtotals,        subtotals,
    THIS worker's     THIS worker's     THIS worker's     THIS worker's
    slice only)       slice only)       slice only)       slice only)
        │               │               │               │
        └───────────────┴───────┬───────┴───────────────┘
                                 ▼
                    Gather / Combine (single coordinator)
                    Merges all 4 workers' partial aggregates
                    into the FINAL, complete aggregate per group
                                 │
                                 ▼
                          Final Result
```

### Why This Works Correctly

Most aggregate functions are **decomposable** — meaning a global aggregate can be correctly computed by combining smaller partial aggregates:

| Aggregate Function | How Partial Results Combine |
|---|---|
| `SUM` | Sum of the partial sums |
| `COUNT` | Sum of the partial counts |
| `MIN` / `MAX` | Min/Max of the partial mins/maxes |
| `AVG` | **NOT** directly decomposable as a simple combine of partial averages! Must track partial `SUM` and partial `COUNT` separately, then divide at the very end: `final_avg = total_sum / total_count` |

> ⚠️ **Very common interview trap:** Naively averaging the workers' individual partial averages (`AVG(avg1, avg2, avg3, avg4)`) is **mathematically incorrect** unless every worker processed exactly the same number of rows! The correct approach always tracks `SUM` and `COUNT` as the true partial aggregates, computing the division only once, at the very end.

### PostgreSQL vs MySQL vs Oracle

| Aspect | PostgreSQL | MySQL (InnoDB) | Oracle |
|---|---|---|---|
| Parallel aggregation support | Yes — `Partial Aggregate` + `Finalize Aggregate` nodes visible in `EXPLAIN`, combined via `Gather`/`Gather Merge` (Module 10 territory) | Limited historically; improving in newer versions, generally less mature parallel query support than PostgreSQL/Oracle | Yes, very mature — Parallel Execution (PX) servers with sophisticated partial-aggregate coordination |

### Interview Importance: ⭐⭐⭐⭐⭐
The `AVG` decomposition trap is an **extremely popular, very practical interview question** — "how would you parallelize computing the average of a huge dataset across multiple machines/threads?" Expect this in distributed-systems-adjacent database interviews too.

## 8.7 Master Comparison Table: Aggregation Strategies

| Strategy | Requires Sort? | Memory Usage | Streamable? | Best For |
|---|---|---|---|---|
| Hash Aggregation | No | O(distinct groups) | No (pipeline breaker, in general) | Small number of distinct groups, unsorted input |
| Sort Aggregation | Yes (unless pre-sorted via index) | O(1) for aggregation pass; sort phase cost separate | Yes | Large number of distinct groups, or input already sorted |
| Partial Aggregation | Depends on underlying strategy chosen for the partial step | Reduced (aggregates before further processing) | Depends | Pre-join aggregation, reducing data volume early |
| Parallel Aggregation | Depends on underlying strategy per worker | Distributed across workers + final combine step | Depends | Large tables, multi-core/multi-node execution |

## 8.8 Best Practices, Common Mistakes & Edge Cases

### Best Practices
- If a query already benefits from an index providing sorted order on the `GROUP BY` column, expect (and welcome) Sort Aggregation — it's essentially "free" in that case.
- For high-cardinality `GROUP BY` columns (many distinct groups) on very large tables, be aware Hash Aggregation may spill to disk — monitor via `EXPLAIN ANALYZE`, similar to Module 7's sort-spill monitoring.
- When manually implementing distributed/parallel aggregation logic (e.g., in application code or a custom data pipeline), always track `SUM`+`COUNT` separately for `AVG`-like computations — never naively average partial averages.

### Common Mistakes
- Averaging partial averages directly across parallel workers/shards without weighting by count — a subtle, very common correctness bug (§8.6).
- Assuming Hash Aggregation is always faster than Sort Aggregation — for already-sorted input or very high-cardinality grouping, Sort Aggregation often wins decisively.
- Forgetting that `MEDIAN`, `PERCENTILE`, and similar order-dependent statistical aggregates are **NOT** simply decomposable like `SUM`/`COUNT`/`MIN`/`MAX` — they generally require either the full sorted dataset or specialized approximate/streaming algorithms (e.g., t-digest, reservoir sampling) beyond the scope of simple partial-aggregate combination.

### Edge Cases
- `COUNT(DISTINCT column)` is notoriously **not** simply decomposable across parallel workers either (a value could appear in multiple workers' partitions) — requires either a final distinct-merge step or approximate techniques (e.g., HyperLogLog) for very large-scale distributed distinct counting.
- `GROUP BY` on an expression (not a raw column) may block the "sort for free via index" optimization unless a matching expression/functional index exists (directly connecting back to Module 5's sargability discussion, §5.10).

## 8.9 Chapter Summary

- **Hash Aggregation** builds a hash table keyed by group, tracking running aggregates — O(N) time, O(distinct groups) memory, no sort needed, generally a pipeline breaker.
- **Sort Aggregation** sorts by the group key first (or reuses an index's sorted order for free), then makes a single streaming pass — O(1) memory for the pass itself, and naturally streamable/pipeline-friendly.
- **Group Aggregation** is the general logical pattern; Hash/Sort Aggregation are the physical implementations.
- **Streaming Aggregation** (via sorted input) can emit completed groups incrementally, unlike Hash Aggregation which typically must consume all input before emitting anything.
- **Partial Aggregation** pushes aggregation below joins when safe, shrinking intermediate data volume — directly analogous to Module 3's pushdown philosophy.
- **Parallel Aggregation** distributes work across workers via partial aggregates + a final combine step — critically, `AVG` (and similar) must track `SUM`+`COUNT` separately, never naively averaging partial averages.

## 8.10 Cheat Sheet

```
AGGREGATION STRATEGY SELECTION
──────────────────────────────────
Few distinct groups, unsorted input        → Hash Aggregation
Many distinct groups, or pre-sorted input  → Sort Aggregation
Aggregating before an expensive join        → Partial Aggregation (if safe)
Multi-core / multi-node execution           → Parallel Aggregation
                                                (partial + final combine)

DECOMPOSABLE AGGREGATE FUNCTIONS
────────────────────────────────────
SUM, COUNT, MIN, MAX  → directly combinable across partial results
AVG                    → combine SUM + COUNT separately, divide LAST
COUNT(DISTINCT)        → NOT simply decomposable (needs merge/approx.)
MEDIAN/PERCENTILE      → NOT simply decomposable (needs full sort/approx.)

PIPELINE BREAKER CHECK
──────────────────────────
Hash Aggregation  → pipeline breaker (must consume all input first)
Sort Aggregation  → streamable IF input already sorted
```
