# The Ultimate DBMS Handbook — Part 13: Research & Advanced Engineering

## Module 9 — Streaming Databases

> **Goal of this module:** Understand streaming databases not as "a pipeline with extra steps" but as databases that have made a specific, principled choice about *when* computation happens relative to when data arrives — and the deep consequences that choice has for consistency, state management, and query semantics.

---

### 9.1 Reframing: A Streaming Database Is a Database That Computes Incrementally

**The traditional (batch/OLAP) model:** data is at rest; a query arrives; the system scans the data and computes a result once, on demand.

**The streaming model:** the *query* is at rest (registered once, standing); data arrives continuously; the system incrementally updates the query's result as each new event arrives, without re-scanning everything from scratch.

**Why this reframing matters:** it clarifies that a streaming database is fundamentally a database that maintains **continuously updated materialized views** over unbounded input — this is the same "materialized view" concept from traditional relational databases (a precomputed, stored query result, refreshed on some schedule), except a streaming database refreshes it **incrementally, per-event, with sub-second latency**, rather than via a periodic batch `REFRESH MATERIALIZED VIEW`. Understanding streaming systems as "incremental view maintenance at low latency" is the single most useful mental model this module can give you — it connects streaming directly back to relational database theory rather than treating it as an unrelated "big data pipeline" discipline.

---

### 9.2 Incremental View Maintenance (IVM) — The Theoretical Foundation

**The core problem IVM solves:** given a materialized view `V = Query(Base Tables)`, and a change (insert/update/delete) to a base table, compute the corresponding change to `V` **without re-executing the entire query from scratch**.

**The key technique: differential/delta processing.** For many relational operators, the change to the output can be computed directly from the change to the input plus the operator's existing state, without touching unchanged data:
- **Filter (`WHERE`)**: a change to a base row produces a corresponding change to the view only if it passes the filter — trivially incremental, no state needed beyond the row itself.
- **Projection (`SELECT` columns)**: similarly trivial — the delta is just the projected columns of the input delta.
- **Aggregation (`GROUP BY`, `SUM`, `COUNT`)**: requires maintaining **per-group running state** (the current sum/count per group) — a new event updates only its group's state and emits a delta for that group's new aggregate value, without recomputing other groups.
- **Join**: the hardest case — requires maintaining **state for both sides of the join** (an index of previously-seen rows from each input), because a new row arriving on one side must be matched against *all previously seen* rows on the other side to find new join results — this is why joins are the most state-heavy and resource-intensive operator in streaming systems, directly analogous to why joins are the most expensive operator in traditional query execution, but now the "table" being joined against is unbounded and must be retained indefinitely (or until a windowing/retention policy expires it, 9.4).

**Foundational research reference:** the general theory of incremental view maintenance long predates modern streaming systems — Blakeley, Larson, Tompa's *"Efficiently Updating Materialized Views"* (SIGMOD 1986) established the core algorithmic ideas decades before Flink/ksqlDB existed; modern streaming SQL engines are, in a real sense, a low-latency, continuously-running implementation of this older IVM theory.

### 9.3 Event Time vs. Processing Time

**The single most important, most frequently mishandled concept in stream processing:**

- **Event time**: the timestamp of when the event actually *happened* in the real world (e.g., when a sensor reading was taken, when a user clicked a button).
- **Processing time**: the timestamp of when the streaming system actually *receives and processes* the event.

**Why the distinction matters:** events do not arrive in event-time order in any real distributed system — network delays, retries, mobile devices going offline and syncing later, and upstream system hiccups all mean an event with an earlier event-time can arrive *after* an event with a later event-time. A streaming system that computes windowed aggregates (9.4) based purely on processing time will produce results that don't correspond to any coherent notion of "what actually happened in this time window" — this is a correctness bug, not a minor inconvenience, for any use case where the actual timing of events matters (billing, SLA compliance, financial transaction ordering).

**The engineering consequence:** any correctness-sensitive streaming system must be explicitly designed around **event time semantics**, which introduces the need for watermarks (9.3.1) to know when it's safe to finalize a computation despite the possibility of further, out-of-order data still arriving.

### 9.3.1 Watermarks

**What a watermark is:** a system-generated marker asserting "*no more events with event-time earlier than T should be expected from this point forward*" — it's the mechanism that lets a streaming system decide when a time-windowed computation (9.4) can be considered "complete enough" to emit a final result, despite the stream being fundamentally unbounded and out-of-order.

**How watermarks are generated:** typically based on either a fixed allowed-lateness bound (e.g., "assume no event will ever arrive more than 5 minutes late") or, in more sophisticated systems, adaptively tracked based on the observed maximum event-time seen so far minus some tracked lateness distribution.

**The unavoidable tradeoff watermarks encode:** a *tighter* watermark (assuming less lateness is possible) produces lower-latency results (windows close and emit sooner) but risks **dropping or mishandling genuinely late data** that arrives after the watermark has already passed; a *looser* watermark is more correct/complete but delays result emission — there is no watermark setting that eliminates this tradeoff, only ones that suit a given workload's actual lateness distribution better or worse. This is directly analogous in spirit to the CAP-theorem-style unavoidable tradeoffs seen throughout this handbook (Module 1.6): you cannot simultaneously guarantee minimum latency and complete correctness in the presence of unbounded, unpredictable event lateness.

### 9.4 Windowing

Since aggregation over a truly unbounded stream never "finishes," streaming systems bound aggregation using **windows** — a way of grouping unbounded events into finite, aggregatable chunks based on time (or occasionally count):

- **Tumbling windows**: fixed-size, non-overlapping windows (e.g., every 5 minutes, starting fresh) — each event belongs to exactly one window.
- **Sliding windows**: fixed-size windows that advance by a smaller step than their size (e.g., a 10-minute window recomputed every 1 minute) — each event can belong to multiple overlapping windows, meaning the system must maintain state across several concurrently-open windows simultaneously, at higher state/compute cost than tumbling windows.
- **Session windows**: dynamically sized windows defined by a gap of inactivity (e.g., "group events into a session, closing the session after 30 minutes with no new events") — window boundaries are data-dependent rather than fixed by a clock, requiring a different state-management approach (tracking "is this session still open" per key, rather than a fixed grid of time buckets).

**Late data handling within windowing:** a window's result can be emitted once its watermark (9.3.1) passes the window's end, but many systems allow configuring **allowed lateness** — a grace period during which a window's result can still be *updated/retracted and re-emitted* if late data arrives, rather than being permanently finalized the instant the watermark passes — trading additional state retention and result-revision complexity for improved correctness on late-arriving data.

### 9.5 Exactly-Once Semantics

**Why this is hard:** in a distributed system, any given message can, in the presence of failures and retries, be processed **zero times** (if lost), **more than once** (if a retry occurs after partial processing but before an acknowledgment), or — the goal — **exactly once**, meaning the *effect* of processing is applied precisely once even if the underlying delivery mechanism retries.

**Three semantic levels, in increasing order of strength (and typically increasing cost):**
1. **At-most-once**: a message might be lost, but is never processed twice. Simplest, weakest — acceptable only when occasional data loss is tolerable.
2. **At-least-once**: a message is never lost, but might be processed multiple times (e.g., if a consumer crashes after processing but before committing its offset, it will reprocess on restart). Common default; requires **idempotent** downstream effects (or deduplication) if exact correctness matters.
3. **Exactly-once (effectively-once)**: the observable *effect* of processing each message is applied precisely once, even though the underlying mechanism may internally retry — this is the strongest and most operationally valuable guarantee, and the hardest to implement correctly.

**How exactly-once is actually achieved in practice — two dominant techniques:**
- **Idempotent writes with deduplication keys**: attach a unique, deterministic ID to each logical unit of work (e.g., derived from source partition + offset), and have the downstream sink check-and-skip already-applied IDs — this converts "exactly-once" into "at-least-once delivery + idempotent application," which is easier to reason about and implement correctly than trying to prevent duplicate delivery in the first place.
- **Transactional/two-phase commit across the read-process-write cycle**: (used by Kafka's transactional producer/consumer API, and Flink's checkpoint-based approach) atomically commit "I have consumed up to offset X" together with "I have produced these output records" as a single transaction, so that a failure and restart either redoes the *entire* read-process-write cycle for the affected offsets (safe, because the whole unit is atomic) or none of it — this is architecturally a direct descendant of the same distributed-transaction/2PC ideas from Module 3 (Spanner, Calvin) applied to the stream-processing read-process-write loop specifically.

**Kafka's specific mechanism (for concreteness):** Kafka's exactly-once semantics (introduced in Kafka 0.11) combine an **idempotent producer** (deduplicating retried sends at the broker level using producer ID + sequence number, preventing duplicate writes from producer-side retries) with **transactions** spanning multiple partition writes and consumer offset commits, letting a stream processing application (e.g., Kafka Streams) atomically commit its input offset advancement together with its output writes.

### 9.6 Stream-Table Duality

**A foundational conceptual unification in streaming systems** (popularized heavily by Kafka's ecosystem, especially ksqlDB and Kafka Streams documentation, and independently arrived at by several streaming database designs): a **stream** (an unbounded sequence of events/changes) and a **table** (a materialized, current-state view) are two representations of the same underlying information, convertible into each other:

- A **stream can be converted into a table** by continuously applying its events as upserts keyed by some identifier — e.g., a stream of `(user_id, new_status)` events becomes a table of "current status per user" by always keeping the latest event per key. This is exactly the **changelog** concept: a stream that represents a table's history of changes.
- A **table can be converted into a stream** by treating every update to the table as an emitted change event — this is the mechanism behind **Change Data Capture (CDC)**, where a traditional database's write-ahead log (Module 3.2's ARIES WAL, or a logical-replication-decoding feature like PostgreSQL's `pgoutput`) is read and converted into a stream of insert/update/delete events, letting downstream streaming systems consume a traditional OLTP database's changes in real time — this is the modern, log-based replacement for the batch ETL pattern criticized in Module 6.1, and the specific mechanism that makes real-time HTAP-adjacent architectures (Module 6.3's Raft-learner pattern is a close cousin) practical outside of a single unified database product.

**Why this duality matters practically:** it means a streaming SQL query joining "a stream" with "a table" is not a special or unusual operation — it's the same relational join operator from Section 9.2, just with one input continuously changing via a changelog and the other treated as continuously-updated lookup state; ksqlDB and Flink SQL both expose stream-table joins as a first-class, natural query pattern precisely because of this underlying duality.

### 9.7 Streaming SQL Systems — Architecture Survey

**Apache Flink (and Flink SQL):** a general-purpose distributed stream processing engine built around a **dataflow graph** execution model, with **checkpointing** (periodic, consistent, distributed snapshots of all operator state, using the **Chandy-Lamport distributed snapshot algorithm** as its theoretical basis) providing fault tolerance — if a worker fails, the whole job can be restarted from the last consistent checkpoint, replaying only the data since that checkpoint, rather than losing all progress. Flink SQL compiles standard-looking SQL queries (including windowed aggregations and stream-table joins) down to this dataflow/checkpointing execution model, making Section 9.2's incremental view maintenance concepts directly programmable via SQL.

**ksqlDB (Confluent, built on Kafka Streams):** a streaming SQL engine specifically built around Kafka as both the input stream source and the mechanism for materializing output tables — directly operationalizes the stream-table duality (9.6) as its core abstraction, since Kafka topics natively serve as the durable log underlying both streams and derived tables.

**Materialize:** takes the "streaming database as incremental view maintenance" framing (9.1) to its most literal conclusion — Materialize is built around **Differential Dataflow** (a Rust-based incremental computation framework, itself built on the **timely dataflow** model), designed so that arbitrarily complex SQL (including multi-way joins and nested subqueries) can be maintained incrementally with correct, low-latency updates, aiming to let users write standard SQL (including views most other streaming systems couldn't efficiently maintain incrementally) and get a continuously-updated result "for free," rather than requiring specialized streaming-specific query constructs.

**RisingWave:** a more recent entrant built as a cloud-native streaming database with a disaggregated storage architecture (directly applying Module 2's compute-storage separation pattern to the streaming database category specifically), aiming to combine Flink-like stream processing power with Postgres-like SQL ergonomics and elastic cloud-native scaling.

### 9.8 State Backends — Where Streaming State Actually Lives

Because streaming operators (aggregations, joins) require maintaining potentially large amounts of state (9.2), streaming engines need a **state backend** — a storage layer for operator state, distinct from the data streaming through the system:

- **In-memory state**: fastest, but bounded by available RAM and lost on crash unless checkpointed.
- **Embedded LSM-tree state (RocksDB is the dominant choice, directly reusing Module 4's engine)**: Flink's `RocksDBStateBackend` is the standard choice for large-state jobs — state that doesn't fit in memory spills to a local embedded RocksDB instance per task, giving the same write-optimized, compaction-managed properties Module 4 covered, applied here to streaming operator state rather than primary application data.
- **Checkpointing state backends to durable storage**: periodically, the state backend's contents (or an incremental diff of them) are snapshotted to durable, remote storage (e.g., S3/HDFS) as part of the Chandy-Lamport-style checkpoint (9.7), so a complete cluster failure can still recover state from the last successful checkpoint rather than losing it entirely.

### 9.9 Production Examples & Industry Usage

| System | Core model | Notable production usage |
|---|---|---|
| Apache Flink | Dataflow graph + checkpointing, general-purpose stream processing | Alibaba (real-time recommendation/risk systems), Netflix, Uber |
| ksqlDB / Kafka Streams | Stream-table duality over Kafka | Real-time event-driven microservices, CDC-based data integration |
| Materialize | Differential dataflow, incremental SQL view maintenance | Real-time dashboards over operational data without a separate ETL/warehouse hop |
| RisingWave | Cloud-native, disaggregated streaming SQL | Teams wanting Flink-like power with Postgres-like ergonomics |
| Debezium (CDC tool, not a full streaming database) | Log-based Change Data Capture from OLTP databases | Feeding real-time changelogs into Kafka for downstream streaming consumers |

### 9.11 MCQs

**Q1.** The most useful mental model for understanding a streaming database is:
A) A pipeline that moves files between systems
B) A database performing continuous, incremental materialized view maintenance over unbounded input
C) A message queue with extra features
D) A backup system

*Answer: B*

**Q2.** The distinction between event time and processing time matters because:
A) They are always identical in distributed systems
B) Events can arrive out of order relative to when they actually occurred, and correctness-sensitive computation must use event time
C) Processing time is always more accurate
D) It only matters for batch systems

*Answer: B*

**Q3.** A watermark in stream processing is used to:
A) Encrypt data in transit
B) Assert that no more events earlier than a given event-time are expected, enabling windows to be closed
C) Compress the stream
D) Deduplicate events

*Answer: B*

**Q4.** Exactly-once semantics in practice is typically achieved via:
A) Guaranteeing no failures ever occur
B) Idempotent writes with deduplication keys, or transactional atomic commit of consumption and production
C) Using at-most-once delivery exclusively
D) Avoiding all retries

*Answer: B*

**Q5.** The stream-table duality states that:
A) Streams and tables are unrelated concepts
B) A stream (changelog) and a table (materialized current state) are two representations of the same underlying information, convertible via continuous upserts or CDC
C) Tables cannot be converted to streams
D) Streams must always be finite

*Answer: B*
