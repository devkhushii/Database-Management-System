### 1.0 Why This Module Exists

Every part of this handbook so far has treated the database as something you *talk to* — you send SQL, you get rows back. Starting now, we crack the box open. We're going to answer: **what actually happens, physically, between the moment you hit Enter on a SQL query and the moment results appear on your screen?**

This matters for three reasons:

1. **Debugging** — you cannot reason about a slow query, a deadlock, or a corrupted table without a mental model of the engine underneath it.
2. **Interviews** — "Design a database engine" or "Explain what happens when you run `SELECT * FROM users WHERE id = 5`" are standard Senior SDE-2/SDE-3 and database-engineer interview questions.
3. **System design** — choosing between Postgres, MySQL, or building your own storage layer requires understanding these internals, not just feature lists.

---

### 1.1 What Is a Database Engine?

**Definition:** A database engine (also called a *storage engine* in a broader sense, or a *DBMS kernel*) is the software layer responsible for storing, retrieving, organizing, and managing data reliably, efficiently, and concurrently, while enforcing consistency and durability guarantees.

**Real-life analogy:** Think of a large public library.
- The **catalog desk** (metadata/catalog manager) knows which books exist and where they're shelved.
- The **librarians** (query executor) fetch books for you.
- The **shelving system** (storage manager) organizes books physically for fast retrieval.
- The **security guard** (lock manager) prevents two people from ripping pages out of the same book at the same time.
- The **backup archive room** (recovery manager) can reconstruct the library's exact state if there's a fire.

A database engine is all of these roles working together as software.

**Why does it exist?** Because "just store data in a file" breaks down almost immediately once you need:
- Concurrent access by many users without corrupting data
- Crash recovery (power loss mid-write shouldn't destroy your data)
- Fast lookups on billions of rows
- Enforcement of constraints (uniqueness, foreign keys, etc.)
- Query optimization (users write *what* they want, not *how* to get it)

**What problem does it solve?** It solves the gap between "declarative" user intent (SQL) and the "imperative" physical reality of disks, memory, and CPUs — while guaranteeing ACID properties (Atomicity, Consistency, Isolation, Durability, covered in earlier parts).

### 1.3 The Complete SQL Request Lifecycle

Let's trace a single query end-to-end. Say the application sends:

```sql
SELECT name, email FROM users WHERE id = 42;
```

**Step-by-step walkthrough:**

| Stage | What Happens | Component Responsible |
|---|---|---|
| 1. Connection | Client connection accepted, authenticated, assigned to a backend process/thread | Connection Manager |
| 2. Parsing | SQL text tokenized and parsed into an Abstract Syntax Tree (AST); syntax errors caught here | Parser |
| 3. Semantic Analysis | AST checked against the catalog — does `users` exist? Does it have `id`, `name`, `email` columns? Are types compatible? | Analyzer + Catalog Manager |
| 4. Rewriting | Views expanded, rules applied (e.g., Postgres rewrite system) | Query Rewriter |
| 5. Optimization | Multiple candidate plans generated (e.g., sequential scan vs. index scan on `id`); cost estimated using table statistics; cheapest plan chosen | Optimizer |
| 6. Plan Compilation | The chosen logical plan is turned into an executable physical plan tree of operators | Optimizer/Executor |
| 7. Transaction Context | If no transaction is open, an implicit one is started; a transaction ID / snapshot is assigned | Transaction Manager |
| 8. Locking | Appropriate locks (or MVCC snapshot, depending on isolation level) acquired | Lock Manager |
| 9. Execution | Executor walks the plan tree; for an index scan, it asks the Buffer Manager for the relevant index and heap pages | Executor |
| 10. Buffer Access | Buffer Manager checks if the page is already in memory (cache hit) or must be read from disk (cache miss) | Buffer Manager |
| 11. Disk I/O | On a cache miss, Storage Manager issues a read syscall to fetch the page from the data file | Storage Manager + OS |
| 12. Tuple Extraction | Row(s) matching `id = 42` extracted from the page, projected to just `name, email` | Executor |
| 13. Result Return | Result set streamed back to the client | Executor → Connection Manager |
| 14. Commit | If it was an implicit/auto-commit transaction, it commits: WAL record flushed, locks released | Transaction Manager + Recovery Manager |

**Flowchart view:**

```
SQL Text
   │
   ▼
[Parse] → AST
   │
   ▼
[Analyze] ── consults ──► [Catalog Manager]
   │
   ▼
[Rewrite]
   │
   ▼
[Optimize] ── consults ──► [Statistics in Catalog]
   │
   ▼
Physical Plan Tree
   │
   ▼
[Execute] ──► [Lock Manager]  (acquire locks / snapshot)
   │
   ▼
[Buffer Manager] ──miss──► [Storage Manager] ──► [Disk]
   │hit
   ▼
Tuples returned
   │
   ▼
[Transaction Manager] → commit → [Recovery Manager writes WAL]
   │
   ▼
Result set → Client
```

This single flow is worth memorizing conceptually — nearly every "explain what happens when you run X query" interview question is really just asking you to walk this diagram with specifics filled in.

### 1.4 Component Deep Dives

#### 1.4.1 Parser

**What is it?** The component that converts raw SQL text into a structured, machine-usable representation — typically an **Abstract Syntax Tree (AST)**.

**Why does it exist?** Computers can't reason over strings of characters directly. `"SELECT name FROM users WHERE id = 42"` must become a tree structure the rest of the engine can walk, inspect, and transform.

**How it works internally:**
1. **Lexical analysis (tokenizing):** breaks the string into tokens — `SELECT`, `name`, `FROM`, `users`, `WHERE`, `id`, `=`, `42`, `;`.
2. **Syntactic analysis (parsing):** tokens are matched against SQL grammar rules (usually via a grammar generator like `yacc`/`bison` in Postgres, or hand-written recursive-descent parsers) to build the AST.
3. **Basic validation:** catches syntax errors (`SELECT FROM WHERE` with no columns) but generally does *not* yet check whether `users` table exists — that's semantic analysis, a later stage.

**Example AST (simplified) for the query above:**

```
SelectStmt
 ├── targetList: [name, email]
 ├── fromClause: [users]
 └── whereClause:
      OpExpr(=)
       ├── ColumnRef(id)
       └── Const(42)
```

**Memory-level behavior:** The AST is a tree of heap-allocated nodes (in Postgres, allocated inside a *memory context* — covered in Module 7). It's transient — built fresh per query (unless a prepared statement caches it) and freed after execution.

**PostgreSQL vs MySQL differences:**
| Aspect | PostgreSQL | MySQL |
|---|---|---|
| Parser generator | Bison-based grammar (`gram.y`) | Hand-tuned Bison-based parser (`sql_yacc.yy`) |
| AST reuse | Prepared statements cache the parse tree | Prepared statements also cache parsed representation |
| Extensibility | Highly extensible (custom operators, types) | Less extensible at parser level |

**Interview importance:** ⭐⭐⭐ High for database-engineer-specific interviews; moderate for general backend roles. Common question: "Why is SQL parsed into a tree instead of executed directly?"

---

#### 1.4.2 Optimizer

**What is it?** The component that decides *how* to execute a query — choosing among many logically-equivalent physical execution strategies the one estimated to be cheapest.

**Why does it exist?** SQL is *declarative* — you say *what* you want, not *how* to get it. For `SELECT * FROM orders WHERE customer_id = 5`, the engine could:
- Scan every row in `orders` (sequential scan), or
- Use an index on `customer_id` to jump directly to matching rows (index scan)

These can differ in cost by orders of magnitude. Someone (or something) has to choose. Historically, DBAs chose manually — modern optimizers automate this.

**How it works internally (Cost-Based Optimization, the dominant approach):**
1. Generate multiple candidate plans (different join orders, different access paths per table, different join algorithms — nested loop, hash join, merge join).
2. For each candidate, estimate **cost** using formulas based on:
   - Table cardinality (row counts) from the Catalog Manager's statistics
   - Selectivity of predicates (what fraction of rows match `WHERE id = 42`?)
   - I/O cost (pages to read) vs. CPU cost (tuples to process)
3. Pick the plan with lowest estimated total cost.

**Real-life analogy:** Planning a road trip with multiple possible routes — the optimizer is like a GPS that estimates time-cost for each route (given traffic, distance, road type) and picks the fastest, rather than you manually comparing every possible path.

**Example — two candidate plans for our query:**

```
Plan A (Sequential Scan):
  SeqScan on users
    Filter: id = 42
    Estimated cost: 1000 (scan all 100,000 rows)

Plan B (Index Scan):
  IndexScan using users_pkey on users
    Index Cond: id = 42
    Estimated cost: 4 (B-Tree lookup, ~3 page reads + 1 heap read)

→ Optimizer picks Plan B
```

**PostgreSQL vs MySQL vs Oracle:**
| Aspect | PostgreSQL | MySQL (InnoDB) | Oracle |
|---|---|---|---|
| Optimizer type | Cost-based, uses `pg_statistic` | Cost-based, uses table/index statistics | Cost-based (CBO), highly mature with adaptive plans |
| Join order search | Dynamic programming (exhaustive) for small joins, genetic algorithm (GEQO) for large joins | Greedy search + some DP | Sophisticated DP + hints heavily supported |
| Plan caching | Generic vs custom plans for prepared statements | Query cache removed in MySQL 8.0; relies on optimizer speed | Shared SQL area caches execution plans (cursor sharing) |
| Adaptive execution | Limited (JIT plan choices via `pg_hint_plan` extension) | Adaptive join reordering in some versions | Adaptive query optimization built-in since 12c |

**Common mistakes:**
- Assuming the optimizer will always pick the "obviously best" plan — stale statistics can mislead it badly.
- Forgetting to run `ANALYZE` (Postgres) or update statistics after bulk loads, causing the optimizer to pick terrible plans.
- Over-relying on indexes without understanding selectivity — an index scan on a low-selectivity column (e.g., a boolean `is_active`) can be *worse* than a sequential scan.

**Interview importance:** ⭐⭐⭐⭐⭐ Extremely high. "Why did the optimizer choose a seq scan over my index?" is one of the most common real-world and interview questions.

#### 1.4.3 Executor

**What is it?** The component that actually *runs* the physical plan chosen by the optimizer, producing the result rows.

**How it works:** Most engines (Postgres, MySQL) use the **iterator/Volcano model** (deep dive in Module 8): each node in the plan tree exposes a simple interface — typically `open()`, `next()`, `close()` — and the executor pulls tuples up through the tree one at a time (or in batches, for vectorized engines).

```
        [Project: name, email]
                 │
                 ▼
        [Filter: id = 42]     ← in seq scan case
                 │
                 ▼
        [Sequential Scan: users]
```

or, if the index path was chosen:

```
        [Project: name, email]
                 │
                 ▼
        [Index Scan: users_pkey, cond: id=42]
```

Each `next()` call on the top node cascades down, pulling one row at a time from the leaf (scan) node, filtering/transforming as it bubbles up.

**Memory-level behavior:** Intermediate tuples live in per-query working memory (`work_mem` in Postgres, `join_buffer_size`/`sort_buffer_size` in MySQL). If intermediate results (e.g., a large sort or hash table) exceed this memory, the executor spills to disk (Module 7 covers this in depth).

**CPU interaction:** Tight execution loops here are why modern engines increasingly use **vectorized/batch execution** (processing arrays of values at once) instead of pure row-at-a-time iteration, to better exploit CPU cache lines and SIMD instructions. Classic Postgres/MySQL are primarily row-at-a-time; newer engines (e.g., column stores) favor vectorization.

**Interview importance:** ⭐⭐⭐⭐ High — "Explain the Volcano/iterator execution model" is a standard database-engineer question (fully covered in Module 8).

---

#### 1.4.4 Storage Manager

**What is it?** The subsystem responsible for translating logical data (tables, indexes) into physical bytes on disk, organized into fixed-size **pages** (typically 8KB in Postgres, 16KB in InnoDB).

**Why does it exist?** Disks don't understand "rows" or "tables" — they understand blocks of bytes at offsets. The Storage Manager bridges this gap, deciding how tuples are packed into pages, how pages are grouped into files, and how those files map onto tables/indexes.

**Key responsibilities:**
- Allocating and mapping pages to files
- Reading/writing pages (usually only via the Buffer Manager as an intermediary, not directly)
- Managing free space within and across pages
- Handling overflow for large rows (TOAST in Postgres, overflow pages in InnoDB)

*(Full physical layout — slotted pages, tuple headers, free space maps — is covered in depth in Module 2: Database Storage Engine, since it deserves its own dedicated treatment.)*

**Interview importance:** ⭐⭐⭐⭐⭐ Central to almost every "how does a database store data" question.

---

#### 1.4.5 Buffer Manager

**What is it?** An in-memory cache of disk pages, sitting between the Executor/Storage Manager and the actual disk, to avoid expensive I/O on every access.

**Why does it exist?** Disk I/O (even on SSDs) is orders of magnitude slower than RAM access. Re-reading a "hot" page (like the root of a frequently-queried B-Tree index) from disk on every query would be catastrophically slow.

**Core mechanics (deep dive in Module 6):**
- Pages are held in fixed-size **buffer frames** in a shared memory region (`shared_buffers` in Postgres, `innodb_buffer_pool_size` in MySQL).
- Each frame has a **pin count** (is anyone currently using this page?) and a **dirty flag** (has it been modified since being read from disk?).
- When a requested page isn't in memory (a **cache miss**), the Buffer Manager asks the Storage Manager to read it from disk, evicting another page (per an eviction policy like LRU or Clock-sweep) if the pool is full.

**Real-life analogy:** A librarian who keeps the 50 most-requested books on a desk beside them (buffer pool) instead of walking to the archive (disk) every time someone asks for one. Only when the desk is full and a new book is needed does an old one get returned to the archive.

**Interview importance:** ⭐⭐⭐⭐⭐ One of the highest-yield internals topics — expect deep questions here (fully covered in Module 6).

---

#### 1.4.6 Transaction Manager

**What is it?** The component enforcing ACID transaction semantics — beginning, committing, and rolling back transactions, and assigning each transaction a unique identifier (Transaction ID / XID) used throughout the system (especially for MVCC, Module 5).

**Why does it exist?** Without it, concurrent operations from multiple clients could interleave in ways that violate atomicity or isolation — e.g., a transfer of money debiting one account but crashing before crediting another.

**Core responsibilities:**
- `BEGIN` — start a new transaction context, assign XID
- `COMMIT` — make all changes durable and visible; write a commit record to the WAL
- `ROLLBACK` — undo all changes made in the transaction
- Coordinating with the Lock Manager and MVCC subsystem to enforce the chosen **isolation level** (Read Uncommitted, Read Committed, Repeatable Read, Serializable)

**Interview importance:** ⭐⭐⭐⭐⭐ Transaction semantics are foundational — expect this in nearly every backend/database interview.

---

#### 1.4.7 Lock Manager

**What is it?** The subsystem that manages **locks** — mutual-exclusion mechanisms preventing conflicting concurrent operations on the same data — and detects/resolves **deadlocks**.

**Why does it exist?** Even with MVCC handling reads elegantly, writes still need coordination: two transactions can't be allowed to update the same row simultaneously without one waiting or failing.

**Key concepts:**
- **Lock granularity:** row-level, page-level, table-level (finer granularity = more concurrency, more overhead)
- **Lock modes:** shared (read) locks vs. exclusive (write) locks; intention locks for hierarchical locking
- **Deadlock detection:** a wait-for graph is periodically checked for cycles; if found, one transaction is chosen as a victim and aborted

**Real-life analogy:** A shared office meeting room booking system — a "read-only" glance at the room doesn't need exclusive booking, but if you want to physically hold a meeting (write), you need exclusive access, and the system must prevent two people from double-booking the same slot.

**Interview importance:** ⭐⭐⭐⭐ High — deadlock scenarios are a classic whiteboard question.

---

#### 1.4.8 Recovery Manager

**What is it?** The subsystem ensuring **durability** and **crash recovery** — guaranteeing that once a transaction is committed, its effects survive crashes, and that a crash mid-transaction leaves the database in a consistent state.

**Core mechanism: Write-Ahead Logging (WAL).** Before any data page modification is written to the actual data file, a log record describing that change is written to a sequential log file *first*, and flushed to disk. If the system crashes, recovery replays the log to reconstruct lost in-memory changes (**redo**) and undoes any incomplete transactions (**undo**).

**Why "write-ahead"?** Sequential log writes are fast (no random seeks), and having the log guarantees durability even if the corresponding data page write hasn't happened yet — the log is the source of truth for recovery.

*(Full ARIES-style recovery algorithm, checkpointing, and redo/undo internals will be covered in a dedicated later part on Recovery & Durability — this module only introduces the concept as it fits into the overall architecture.)*

**Interview importance:** ⭐⭐⭐⭐⭐ "Explain WAL / how does crash recovery work" is a top-tier database-engineer question.

---

#### 1.4.9 Metadata Manager / Catalog Manager

**What is it?** The component that stores and serves **data about the data** — table schemas, column types, constraints, indexes, statistics, users/permissions. In Postgres this lives in `pg_catalog` system tables; in MySQL it's the `information_schema` and InnoDB's internal data dictionary.

**Why does it exist?** Every other component depends on it:
- Parser needs to know a table's columns exist
- Optimizer needs row-count and selectivity statistics
- Executor needs to know column types and offsets to correctly read tuples

**Real-life analogy:** The library's card catalog — without it, librarians (executor) wouldn't know what books (tables) exist or where they are.

**Interview importance:** ⭐⭐⭐ Moderate-high; commonly comes up in "how does the optimizer know table sizes" type questions.

### 1.5 Complete Architecture Walkthrough — Two Full Examples

#### Example 1: `SELECT` with an index (happy path)

```sql
SELECT name FROM employees WHERE emp_id = 101;
```

1. Parser builds AST.
2. Analyzer confirms `employees` and `emp_id` exist in the catalog.
3. Optimizer sees an index `employees_pkey` on `emp_id`; estimates index scan is far cheaper than seq scan; picks it.
4. Transaction Manager assigns/uses an existing transaction context, takes an MVCC snapshot (Postgres) or acquires a shared lock as needed (isolation-level dependent).
5. Executor calls `IndexScan.next()`.
6. Buffer Manager is asked for the B-Tree root page → likely a cache **hit** (root pages are hot).
7. Traversal continues down the B-Tree; leaf page found; Buffer Manager fetches leaf page (hit or miss).
8. Leaf entry points to the heap page containing the actual row; Buffer Manager fetches that page.
9. Row extracted, projected to just `name`, returned to client.
10. Implicit transaction commits (trivial — read-only, often no WAL record needed for pure reads).

#### Example 2: `UPDATE` (write path, more components involved)

```sql
UPDATE employees SET salary = salary * 1.1 WHERE emp_id = 101;
```

1–3. Same parse/analyze/optimize steps, but plan is a write plan (index scan + update node).
4. Transaction Manager: transaction begins (explicit or implicit), XID assigned.
5. Lock Manager: exclusive row lock acquired on the target row (or, in MVCC systems, a new row version will be created instead of blocking readers).
6. Executor fetches the current row via Buffer Manager (as above).
7. **Recovery Manager**: a WAL record describing the change is generated and flushed *before* the data page is modified in the buffer pool.
8. The page in the buffer pool is modified in-place and marked **dirty** (not yet written to disk).
9. Lock is held until commit (in most systems) or released early (in some MVCC configurations for readers).
10. On `COMMIT`: Transaction Manager writes a commit WAL record, Recovery Manager ensures it's flushed to disk (`fsync`), lock released.
11. The dirtied data page is *not* necessarily flushed immediately — the Buffer Manager's background writer/checkpointer will flush it later (Module 6 & 10). The WAL guarantees durability even before that happens.

**This second example is the single most important flow to internalize** — it's the backbone of nearly every "how does a database guarantee durability" interview answer.

### 1.6 Comparison Table: Engine Architecture Terminology Across Systems

| Concept | PostgreSQL Term | MySQL (InnoDB) Term | Oracle Term |
|---|---|---|---|
| Process handling connections | Backend process (one process per connection) | Thread (one thread per connection) | Server process / dedicated server |
| In-memory page cache | Shared Buffers | Buffer Pool | Buffer Cache (SGA) |
| Write-ahead log | WAL (`pg_wal`) | Redo Log | Redo Log |
| Undo mechanism | Old row versions kept in heap (via MVCC), cleaned by VACUUM | Separate Undo Log / Undo Tablespace | Undo Tablespace |
| Metadata store | `pg_catalog` system tables | `information_schema` + InnoDB data dictionary | Data Dictionary |
| Periodic disk flush of dirty pages | Checkpointer + Background Writer | Page Cleaner threads | DBWn (Database Writer) processes |
| Statistics for optimizer | `pg_statistic` (populated by `ANALYZE`) | Persistent InnoDB statistics tables | Optimizer statistics (via `DBMS_STATS`) |

### 1.7 Advantages, Disadvantages & Best Practices of This Layered Architecture

**Advantages:**
- Clean separation of concerns — each component can be optimized, tested, and even swapped independently (e.g., MySQL supports pluggable storage engines with the same parser/optimizer layer above).
- Enables the optimizer to be storage-agnostic to a degree, and the storage layer to serve multiple access patterns.

**Disadvantages:**
- Layering introduces overhead — every request pays the cost of parsing, planning, and going through the buffer manager even for trivial queries. This is why prepared statements and connection pooling exist (mitigation).
- Coordinating consistently across so many subsystems (locks + MVCC + WAL + buffer pool) is a major source of engine complexity and historically a major source of subtle bugs.

**Best practices (as an application developer):**
- Use prepared statements to skip repeated parsing/planning overhead.
- Keep transactions short — they hold locks/resources and delay VACUUM/purge work.
- Periodically update statistics (`ANALYZE` in Postgres; InnoDB usually auto-updates but can be forced with `ANALYZE TABLE`).

**Common mistakes:**
- Treating the database as a black box and never checking `EXPLAIN`/`EXPLAIN ANALYZE` output — this bypasses the single most useful debugging tool tied directly to this architecture.
- Assuming all engines behave identically — process-per-connection (Postgres) vs. thread-per-connection (MySQL) has real operational implications (e.g., connection pooling is far more critical for Postgres due to per-connection memory/process overhead).

### 1.8 Chapter Summary

- A database engine is a layered system: **Parser → Analyzer → Rewriter → Optimizer → Executor**, backed by **Transaction Manager, Lock Manager, Buffer Manager, Storage Manager, and Recovery Manager**, all coordinated through a central **Catalog/Metadata Manager**.
- Every SQL statement — read or write — flows through this same skeleton; the write path additionally engages the Lock Manager and Recovery Manager (WAL) more heavily.
- The Buffer Manager is the critical bridge between fast-but-volatile memory and slow-but-durable disk.
- WAL (write-ahead logging) is *the* mechanism underlying durability across virtually all major relational engines.
- Terminology differs across Postgres/MySQL/Oracle, but the underlying architectural roles are nearly identical — recognizing this mapping is a high-value interview skill.

---

### 1.9 Cheat Sheet

```
Query Lifecycle (memorize this order):
Parse → Analyze → Rewrite → Optimize → Execute → (Lock/MVCC) → Buffer → Disk → Commit/WAL

Write path adds: Lock acquisition, WAL record BEFORE data page flush ("write-ahead")

Component → One-line purpose:
Parser            → SQL text to AST
Analyzer          → Validate AST against catalog
Optimizer         → Choose cheapest execution plan
Executor          → Run the plan tree (Volcano/iterator model)
Transaction Mgr   → BEGIN/COMMIT/ROLLBACK, assigns XIDs
Lock Manager      → Prevents conflicting concurrent access, detects deadlocks
Buffer Manager    → In-memory page cache, avoids disk I/O
Storage Manager   → Physical page layout on disk
Recovery Manager  → WAL, crash recovery, durability
Catalog Manager   → Schema + statistics, consulted by everyone
```
