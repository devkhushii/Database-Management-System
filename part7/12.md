## Module 12: Performance Trade-offs

> **Where we are:** Every module so far has occasionally flagged a trade-off and promised "full detail in Module 12." This is that module. ## 12.0 Why This Module Exists

It's tempting, after Modules 5–10, to think "indexes are strictly good — just add more of them." This module exists specifically to correct that instinct with hard numbers and mechanisms, because **over-indexing is one of the most common real-world schema design mistakes**, and diagnosing/fixing it is a very frequent Senior Engineer responsibility.

---

## 12.1 Why Too Many Indexes Are Bad

### The core trade-off, restated with full context

Every index on a table means:
- Every `INSERT` must add an entry to that index too (potential page split, Module 6).
- Every `UPDATE` that touches an indexed column must update that index too (unless it qualifies for PostgreSQL's HOT optimization, Module 9, which only applies to **non-indexed** column changes — so updating an indexed column NEVER gets HOT's benefit).
- Every `DELETE` must remove (or mark for later cleanup, Module 9/11) that index's corresponding entry too.
- The index itself consumes disk space and buffer pool cache space (Module 4) — competing with your table's own data and other indexes for the same limited RAM.

A table with 10 indexes doesn't just cost "10x the write work of no indexes" — it costs the sum of all 10 indexes' individual maintenance costs, compounding for every single write operation, forever.

---

## 12.2 Write Amplification

### What is it?

**Write amplification** is the phenomenon where a single logical write (one `INSERT`/`UPDATE`/`DELETE` statement) results in **multiple physical writes** — to the table's heap/clustered structure AND to every affected index.

### Concrete Example

```
Table 'orders' has 5 indexes (including the primary key).

ONE logical statement:  INSERT INTO orders (...) VALUES (...);

Physical writes actually performed:
  1. Write to the heap/clustered table itself
  2. Write to Index 1 (e.g., customer_id)
  3. Write to Index 2 (e.g., order_date)
  4. Write to Index 3 (e.g., status)
  5. Write to Index 4 (e.g., product_id)
  6. Write to Index 5 (e.g., a composite index)
  = 6 total physical writes for 1 logical INSERT
```

### Connecting Back to Module 9's InnoDB Change Buffer

Recall Module 9, Section 9.9: InnoDB's Change Buffer specifically exists to **soften** write amplification's I/O impact for non-unique secondary indexes on uncached pages, by deferring and batching those writes — but it does not eliminate the underlying cost; it just makes it cheaper and better-scheduled, not free.

### Interview Importance
⭐⭐⭐⭐⭐ — "Explain write amplification in the context of indexing, and name one mechanism a real database engine uses to mitigate (not eliminate) it" — Answer references the Change Buffer directly.

## 12.3 Read Optimization vs Write Cost — The Central Tension

This is simply Module 5, Section 5.2's trade-off, now examined with full quantitative context from every module since:

| | Favors MORE indexes | Favors FEWER indexes |
|---|---|---|
| Read-heavy, write-light workload (e.g., analytics/reporting tables, data warehouses) | ✅ | |
| Write-heavy, read-light workload (e.g., high-throughput event logging, IoT ingestion) | | ✅ |
| Mixed OLTP workload (typical application database) | Selective indexing — index only for actual proven query patterns | |

## 12.4 Insert Cost, Update Cost, Delete Cost — Broken Down Per Operation

### Insert Cost

```
Insert cost ≈ Heap/clustered insert cost
            + (number of indexes × per-index insert cost)
            + occasional B+ Tree page split cost (Module 6) if a node is full
            + occasional clustered table page split cost if primary key insert
              order is non-sequential (Module 3/9's "avoid random UUID PKs" lesson)
```

### Update Cost

```
Update cost depends heavily on WHICH columns changed:

  If NO indexed column changed AND new tuple fits same page (PostgreSQL HOT, Module 9):
     -> cost ≈ just the heap update itself, ZERO index writes needed

  If an INDEXED column changed:
     -> cost ≈ heap update + updates to EVERY index that includes that column
        (potentially ALL indexes, if using a wide composite index covering many columns)

  If row grows and no longer fits its page (row migration/new tuple version elsewhere):
     -> extra cost: potential forwarding pointer overhead (Module 2) or, in PostgreSQL's
        MVCC model, the new tuple version might land on a DIFFERENT page, in which case
        even a HOT-eligible column change loses its HOT optimization (since HOT requires
        same-page placement) -- meaning indexes DO need updating despite the column itself
        being unindexed
```

### Delete Cost

```
Delete cost ≈ (in PostgreSQL) marking tuple's xmax, NOT immediate index cleanup
              -- indexes still contain "stale-looking" entries until VACUUM (Module 11)
              eventually reclaims them

            ≈ (in InnoDB) marking for deletion via undo log mechanism,
              similarly deferred actual cleanup via background purge threads
```

> **Key insight tying Modules 9, 11, and 12 together:** In both PostgreSQL and InnoDB, a logical `DELETE` does **not** immediately and synchronously clean up every index entry — the *visible* effect (the row disappearing from query results) is immediate, but the *physical* cleanup of the underlying index/heap space is deferred to VACUUM (PostgreSQL) or purge threads (InnoDB), which is exactly why sustained heavy delete activity without adequate vacuum/purge tuning leads to the bloat problems discussed in Module 11.

## 12.5 Storage Overhead

### Quantifying Index Storage Cost

Every index roughly needs to store: (key size × number of rows) + (pointer/RID size × number of rows) + internal node overhead (Module 6's signposts) + partially-filled-page overhead (fill factor, Module 6 Section 6.8).

### The InnoDB-Specific Multiplier (tying back to Module 9, Section 9.6)

Recall: InnoDB secondary indexes store the **primary key value**, not a lightweight fixed-size RID. This means:

```
Secondary index storage ≈ (indexed column size + PRIMARY KEY size) × number of rows × number of secondary indexes

If primary key is large (e.g., a 36-byte UUID string, or a wide composite key),
this multiplier applies to EVERY secondary index on the table -- a genuinely
severe, easily-overlooked storage (and performance, since more storage = more
pages = more I/O per traversal) cost.
```

### Interview Importance
⭐⭐⭐⭐⭐ — This is precisely the payoff of Module 3 (Section 3.6, IOT) and Module 9 (Section 9.6)'s repeated warnings: "why does a wide InnoDB primary key bloat every secondary index?" — you should now be able to answer this with a full quantitative mental model, not just a qualitative one.

## 12.6 Index Bloat (Full Detail, Building on Module 11)

### What is it?

**Index bloat** is the accumulation of "dead" or unnecessarily empty space within an index's pages over time — from deleted/updated-away entries not yet reclaimed (PostgreSQL, pending VACUUM, Module 11) or from B+ Tree page splits/merges leaving pages less than fully packed (Module 6).

### Why It Compounds Over Time

Every `UPDATE` to an indexed column effectively performs a delete-old-entry + insert-new-entry pattern within that index (Module 12.4's cost breakdown) — under sustained high-frequency updates to indexed columns, bloat can accumulate **faster than routine autovacuum/maintenance can reclaim it**, requiring more aggressive tuning or periodic manual rebuilds (Module 11, Section 11.1).

### Detecting and Fixing Bloat

- **Detection:** PostgreSQL bloat-estimation queries/extensions (`pgstattuple`), monitoring index size growth relative to row count growth over time.
- **Fixing:** `REINDEX`/`REINDEX CONCURRENTLY` (Module 11, Section 11.1), or ensuring autovacuum is properly tuned to keep pace with the write rate in the first place (prevention over cure).

## 12.7 Choosing the Right Index — A Practical Decision Framework

Bringing together Modules 5–12 into one actionable framework:

### Step 1: Do you actually need this index?
- Is there a real, measured query pattern that would benefit? (Avoid "just in case" indexing — Section 12.1's core warning.)
- Check actual query logs / `pg_stat_statements`-style tooling for real usage evidence, not assumptions.

### Step 2: What type of index? (Module 5 & 8 recap)
- Standard equality/range/sort needs → B+ Tree (the default, safe choice).
- Pure equality-only, no range/sort ever → consider a hash index (Module 7), but weigh the rarity of this exact use case.
- Array/JSONB/full-text containment → GIN (Module 8).
- Spatial/range-overlap → GiST (Module 8).
- Enormous append-mostly table with correlated column → BRIN (Module 8) for massive storage savings.

### Step 3: What column order for composite indexes? (Module 5 & 10 recap)
- Equality-filtered columns first, range/sort columns last.
- Validate against the leftmost prefix rule for your actual query patterns.

### Step 4: Does it need to be a covering index? (Module 5 & 10 recap)
- If a specific hot-path query could benefit from an Index-Only Scan, consider including its `SELECT`-list columns in the index.

### Step 5: Should it be partial? (Module 5 recap)
- If queries only ever care about a well-defined subset of rows, a partial index saves substantial storage and write cost.

### Step 6: What's the write-cost budget?
- For write-heavy tables, be deliberately conservative — every index added here has an outsized, compounding cost (Section 12.2's write amplification).

### Step 7: Plan for maintenance from day one (Module 11 recap)
- Ensure autovacuum/statistics-refresh settings are appropriate for this table's expected write volume BEFORE the index becomes a production bloat problem.

## 12.8 Chapter Summary

- Every index adds real, compounding cost to every write operation — this is **write amplification**, and it's the direct, quantifiable cost side of the read/write trade-off first introduced in Module 5.
- **Insert cost** scales with the number of indexes; **update cost** depends critically on whether an indexed column changed (PostgreSQL's HOT optimization only helps for non-indexed-column, same-page updates); **delete cost** is often deferred (marking now, physical cleanup later via VACUUM/purge threads).
- **Storage overhead** is straightforward for most indexes, but InnoDB secondary indexes carry an extra, easily-overlooked multiplier: they store the full primary key value, so a wide primary key bloats every secondary index on the table.
- **Index bloat** compounds over time under sustained updates to indexed columns, and requires either proactive vacuum/statistics tuning (Module 11) or periodic rebuilds to control.
- The **7-step decision framework** (need it? what type? what column order? covering? partial? write budget? maintenance plan?) is the practical synthesis of Modules 5 through 12 into one actionable checklist for real schema design decisions.

## 12.9 Cheat Sheet

```
Write Amplification = 1 logical write -> MANY physical writes (heap + EVERY affected index)

INSERT cost  = heap insert + (per-index insert × number of indexes) + occasional page splits
UPDATE cost  = ZERO index writes if HOT-eligible (non-indexed col, same page, PostgreSQL)
               ELSE: heap update + updates to EVERY index touching the changed column(s)
DELETE cost  = often DEFERRED (mark now via xmax/undo log, physical cleanup later via VACUUM/purge)

Storage overhead = key size + pointer/RID size + internal node overhead + fill-factor slack
InnoDB multiplier = secondary indexes store FULL PRIMARY KEY VALUE
                    -> wide/composite PK bloats EVERY secondary index (storage AND I/O cost)

Index Bloat  = dead/empty space accumulating over time -> fix via REINDEX or proactive
               autovacuum/statistics tuning (prevention > cure)

7-STEP INDEX DECISION FRAMEWORK:
  1. Do you actually need it? (measured evidence, not guesses)
  2. What TYPE? (B+ Tree default | Hash for pure equality | GIN/GiST/BRIN for specialized data)
  3. Composite column ORDER? (equality first, range/sort last, leftmost prefix rule)
  4. Should it be COVERING? (enable Index-Only Scan for hot-path queries)
  5. Should it be PARTIAL? (subset of rows only)
  6. What's the WRITE-COST budget for this table?
  7. Is a MAINTENANCE plan (autovacuum/statistics) in place from day one?
```

## 12.11 MCQs

**Q1.** Write amplification refers to:
A) A single physical write causing multiple logical changes  B) A single logical write causing multiple physical writes (heap plus every affected index)  C) Increasing a column's storage size  D) Duplicating an entire table
*(Answer: B)*

**Q2.** In PostgreSQL, a HOT update is NOT possible when:
A) No columns changed  B) An indexed column's value changed  C) The table has zero indexes  D) The update is the first one on that row
*(Answer: B)*

**Q3.** Why does a wide InnoDB primary key bloat secondary indexes?
A) Secondary indexes are always the same size regardless of primary key width  B) Secondary indexes store the full primary key value as their pointer to the row  C) InnoDB doesn't support secondary indexes with wide primary keys  D) Wide primary keys disable secondary indexes entirely

**Q4.** Which workload type most favors AGGRESSIVE indexing (many indexes)?
A) High-throughput write-heavy event logging  B) Read-heavy analytics/reporting tables with infrequent writes  C) Tables with constant bulk deletes  D) Tables under constant schema migration
