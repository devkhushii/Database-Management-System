### 14.3 Formula Sheet

```
CAPACITY PLANNING (M3):
  Projected Storage = Current Size + (Growth Rate × Time Horizon)
                     + Index Overhead (20-50% of table size) + Log Buffer + Safety Margin (20-30%)

QUORUM (M6):
  Quorum = floor(N / 2) + 1        → Use ODD node counts to avoid tie votes

UPTIME TARGETS (M6):
  99%     ≈ 3.65 days downtime/year
  99.9%   ≈ 8.76 hours downtime/year
  99.99%  ≈ 52.6 minutes downtime/year
  99.999% ≈ 5.26 minutes downtime/year

RTO vs RPO (M6/M7):
  RTO = Recovery TIME Objective  → "how long until we're back up"
  RPO = Recovery POINT Objective → "how much data can we afford to lose"

MEMORY TUNING HEURISTICS (M3):
  PostgreSQL shared_buffers        ≈ 25% of total RAM
  PostgreSQL effective_cache_size  ≈ 50-75% of total RAM
  MySQL innodb_buffer_pool_size    ≈ 60-70% of total RAM (dedicated DB server)
  work_mem × max_connections  MUST NOT exceed available RAM (worst case)

B+ TREE COMPLEXITY (Part 9-11 / M13):
  Lookup / Insert / Delete = O(log_f n), where f = fan-out (often 100s) → very shallow tree

ALERT THRESHOLDS EXAMPLE (M4):
  Disk space:        Warn @ 70%   → Critical @ 85%   → NEVER wait for 100%
  Replication lag:   Warn @ 10s   → Critical @ 60s
  Connections used:  Warn @ 70%   → Critical @ 90%
```

### 14.4 Master Decision Trees (Consolidated)

**Tree 1 — "What lifecycle rigor does this change need?" (M1)**
```
Production-bound change? → NO → local only, stop.
                          → YES →
   Read-only? → low risk path (test→stage→prod)
   Additive schema? → expand-contract, timed staging test
   Destructive? → deprecation window BEFORE removal
   Major upgrade? → benchmark, choose in-place vs replication cutover
```

**Tree 2 — "What security control does this data need?" (M2)**
```
PII/financial/health? → NO → standard TLS+RBAC+audit
                       → YES →
   Multi-tenant? → add Row-Level Security
   Payment card? → PCI scope: no CVV storage, segmentation, masking
   Health (US)? → HIPAA scope: encryption + audit trail + BAAs
   EU personal? → GDPR scope: right-to-erasure + retention policy
```

**Tree 3 — "Something's slow, where do I look?" (M4/M11)**
```
Unreachable? → disk full? network partition? process crash?
Reachable but slow? → CPU/Mem/Disk saturated? → connections near max? →
   locks/blocking? → new slow query (pg_stat_statements)? → WAL/checkpoint spike?
Stale reads? → replication lag
DB spike right after cache event? → cache stampede
```

**Tree 4 — "Which HA architecture?" (M6)**
```
Strong consistency, single-region OK? → Active-Passive + automatic failover
Need lowest latency globally, can handle conflicts? → Active-Active
Need geo-separated DR only, not full active-active? → Async cross-region standby
Sub-minute RTO mandatory? → aggressive but quorum-safe automatic failover + drills
```

**Tree 5 — "Which DR tier?" (M7)**
```
Hours downtime OK? → Backup & Restore
Tens of minutes RTO? → Pilot Light or Warm Standby
Near-zero RTO/RPO? → Hot Standby / Active-Active multi-region
ALWAYS: validate backups regularly + run drills, regardless of tier.
```

**Tree 6 — "Which database category?" (M10)**
```
Tabular + strong ACID? → need horizontal write scale? → Distributed SQL : else → RDBMS
Flexible/evolving schema? → Document (MongoDB)
Extreme write throughput, simple access, multi-DC? → Wide-column (Cassandra)
Sub-ms caching/session? → Redis
Relationship traversal is the core query? → Graph (Neo4j)
Full-text search/log analytics? → Elasticsearch (secondary store)
Embedded/local only? → SQLite
```

**Tree 7 — "Self-managed vs Kubernetes vs DBaaS?" (M9)**
```
No dedicated DBA/platform team? → DBaaS (default, pragmatic choice)
Already on K8s, need portability? → K8s + Operator
Need max control at extreme scale? → Self-managed VM/bare-metal + Patroni stack
Otherwise → DBaaS remains the default even with an experienced team.
```

### 14.6 Consolidated Checklist — "Is This Database Production-Ready?"

```
LIFECYCLE     [ ] Migrations version-controlled, tested through dev→test→stage
SECURITY      [ ] TLS enforced, least-privilege roles, secrets in a vault, audit logging on
DBA           [ ] Config tuned (not defaults), capacity projected 6-12mo out
MONITORING    [ ] p99 latency, locks, replication lag, disk, all dashboarded + alerted
PERFORMANCE   [ ] Connection pooling in place, caching where appropriate, indexes reviewed
HA            [ ] Automatic failover configured, tested via real drill, odd-node quorum
BACKUP/DR     [ ] Backups validated via real restores, geo-redundant, drilled
MIGRATIONS    [ ] Expand-Contract used for breaking changes, rollback plan exists
DEVOPS        [ ] Infra as code, CI/CD gates migrations, no manual prod changes
SELECTION     [ ] Database choice matches actual workload shape, not just familiarity
```

### 14.7 Last-Minute Interview Notes (Read This Right Before Walking In)

```
1. When asked "design X", ALWAYS clarify: consistency requirements, scale, read/write
   ratio, and team operational capacity BEFORE proposing a specific database.

2. "It depends" is a fine STARTING point but never a final answer — always follow
   with the specific factors that would tip the decision each way.

3. For any schema-change question, mention EXPAND-CONTRACT by name — it signals you
   understand rolling-deployment backward-compatibility, a favorite senior-level signal.

4. For any "how do you scale X" question, explicitly separate READ scaling
   (replicas/caching — easier) from WRITE scaling (sharding/distributed SQL — harder).

5. For any HA question, mention QUORUM and SPLIT-BRAIN by name — these are the
   two words interviewers listen for to confirm real understanding vs. surface knowledge.

6. For any security question, lead with LEAST PRIVILEGE and PARAMETERIZED QUERIES —
   the two highest-signal phrases for database security fundamentals.

7. For any incident/debugging question, narrate your diagnostic process OUT LOUD,
   step by step (Module 11's triage tree) — interviewers grade the PROCESS, not just
   the final right answer.

8. Remember: HA protects against node failure. DR protects against data corruption/
   region loss. Never conflate the two in an answer — interviewers listen for this
   distinction specifically.

9. If discussing a real company's architecture (M12), don't over-claim precision on
   exact current internals — anchor claims in well-known, publicly documented patterns
   and reasoning, not fabricated specifics.

10. When in doubt on a whiteboard question, START by writing down: consistency needs,
    read/write pattern, and scale — visibly anchoring your design process for the
    interviewer to follow, rather than jumping straight to a database name.
```
