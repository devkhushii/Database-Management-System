# The Ultimate DBMS Handbook — Part 13: Research & Advanced Engineering

## Module 7 — Time-Series Databases

> **Goal of this module:** Understand what makes time-series workloads a genuinely distinct engineering problem (not just "SQL with a timestamp column"), and how purpose-built systems exploit the specific structure of time-series data for orders-of-magnitude gains.

---

### 7.1 What Makes Time-Series Data Different

A time-series workload has a distinctive shape that general-purpose databases don't exploit by default:
- **Write pattern**: almost entirely **append-only, in (roughly) monotonically increasing timestamp order** — you rarely update or delete individual historical points; new data is always "now."
- **Query pattern**: dominated by **range scans over time** (`WHERE time > now() - 1h`) combined with **downsampling/aggregation** (`GROUP BY time_bucket, avg(value)`), rather than point lookups by arbitrary key.
- **Cardinality structure**: data arrives tagged by many discrete **series** (e.g., one series per `(host, metric_name)` combination in infrastructure monitoring) — a single ingestion stream fans out into potentially millions of distinct logical time series.
- **Retention/lifecycle**: recent data is queried frequently at full resolution; old data is queried rarely, and usually only at reduced (downsampled) resolution — a strong "temperature gradient" from hot to cold data that general-purpose databases have no built-in concept of.
- **Value distribution**: consecutive values within a series are often close to each other (a temperature sensor doesn't jump wildly between adjacent readings), and timestamps within a series are near-regularly spaced — both properties are highly exploitable by delta/specialized compression (directly building on Module 5.5's compression toolkit).

**Why not just use PostgreSQL/MySQL directly:** you *can*, and many teams do at moderate scale — but a general-purpose B-tree-indexed row store doesn't exploit any of the five properties above by default, so it pays full index-maintenance and storage cost as if the data had no special structure, and provides no built-in retention/downsampling lifecycle management.

---

### 7.2 The Core Architectural Pattern: Time-Partitioned, Series-Indexed Storage

Nearly every purpose-built time-series database (TSDB) converges on the same core structure, regardless of implementation language or storage engine choice underneath:

1. **Time-based partitioning ("chunking")**: data is physically partitioned into fixed time windows (e.g., one partition per day or per hour) — a query filtering to a recent time range can immediately prune (skip entirely) all partitions outside that range, without touching an index at all. This is the time-series-specific version of the min/max zone-map pruning from Module 5.6, but partitioned explicitly by time rather than relying on incidental clustering.
2. **Series identification**: each unique combination of tags/labels (e.g., `host=web1,metric=cpu_usage`) is mapped to a compact internal **series ID** (analogous to dictionary encoding, Module 5.5) — this lets the storage engine group all data points for one series contiguously, which both speeds up per-series range scans and enables per-series delta compression (7.3).
3. **Within each time partition, data is further organized by series ID**, so a query for "CPU usage on host1 over the last hour" touches only the relevant partition(s) and, within them, only the relevant series' contiguous data — combining time-pruning and series-pruning as two independent, compounding filters.

---

### 7.3 Time-Series-Specific Compression

Building directly on Module 5.5's general columnar compression toolkit, applied to the specific statistical properties of time-series data:

- **Delta-of-delta encoding for timestamps**: since timestamps within a series usually arrive at a near-constant interval (e.g., every 10 seconds), storing the *delta of the delta* (i.e., how much the interval itself deviates from the expected interval) compresses to nearly zero bits for perfectly regular series, with only small corrections for jitter. This is the core technique from Facebook's **Gorilla** paper (7.4).
- **XOR-based floating point compression**: for consecutive floating-point sensor/metric values, Gorilla's technique XORs consecutive values and stores only the resulting non-zero bit range (leading/trailing zero counts plus the meaningful bits) — because consecutive readings are usually numerically close, most bits in the XOR result are zero, giving strong compression without the precision loss of lossy techniques.
- **Combining with Module 5's general toolkit**: dictionary encoding for tag values (host names, region labels), RLE for constant-value runs (a sensor reporting the same value repeatedly), and bit-packing for the delta-encoded timestamp/value streams all layer on top of the time-series-specific techniques above.

### 7.4 Gorilla — Facebook's In-Memory Time-Series Compression

**Citation:** Pelkonen et al., *"Gorilla: A Fast, Scalable, In-Memory Time Series Database,"* VLDB 2015.

**Problem:** Facebook needed to hold roughly 26 hours of high-resolution monitoring data (billions of time series data points) entirely **in memory** for fast dashboard/alerting queries, but raw storage at that resolution and scale wouldn't fit in available RAM without aggressive compression that still allowed fast random access.

**Innovation:** The delta-of-delta timestamp compression and XOR-based floating-point compression described in 7.3, combined into a compact in-memory format achieving roughly a **12x compression ratio** compared to naive storage, while remaining fast enough for real-time write and read access (no batch decompression step required before use).

**Impact:** Gorilla's compression techniques were directly adopted (or closely reimplemented) by numerous open-source time-series databases, including **InfluxDB** and **Prometheus**, and are cited as the reference technique whenever a time-series system's documentation mentions "Gorilla-style compression."

---

### 7.5 InfluxDB — Purpose-Built TSDB Internals

**Storage engine (TSM — Time-Structured Merge tree):** InfluxDB's engine is explicitly LSM-tree-inspired (Module 4) but adapted for time-series: writes go to an in-memory cache plus WAL, and are periodically flushed to **TSM files** (analogous to SSTables) that are sorted by series key and time, then compacted in the background similarly to LSM compaction (Module 4.6) — the key adaptation being that compaction is aware of time-based partitioning (7.2), so compaction work and storage tiering can both be organized around time boundaries rather than purely by file size.

**Data model concepts specific to InfluxDB:** a **measurement** (roughly analogous to a table), **tags** (indexed, used for filtering/grouping — analogous to dictionary-encoded dimension columns), and **fields** (the actual numeric/string values being recorded — analogous to measure columns) — this tag/field split directly mirrors the "dimension vs. measure" distinction from general OLAP data modeling, applied specifically to time-series.

**Cardinality as the central operational concern:** because every unique tag combination creates a new series, and InfluxDB (like most TSDBs) maintains an in-memory index over series for fast lookup, **high cardinality tags** (e.g., accidentally tagging by a unique request ID or user ID rather than a bounded dimension like `region`) can cause the series index to grow unboundedly, degrading performance and memory usage catastrophically — this "cardinality explosion" problem is the single most common production incident category specific to time-series databases, and doesn't have a direct analog in general-purpose row/column stores.

**Retention policies and continuous queries/downsampling:** InfluxDB has first-class, built-in support for automatically expiring data older than a configured retention period, and for continuously computing and storing downsampled aggregates (e.g., automatically maintaining an hourly-average rollup alongside raw per-second data) — directly operationalizing the hot/cold data lifecycle from Section 7.1 as a database feature rather than something application code must implement.

---

### 7.6 TimescaleDB — Time-Series as a PostgreSQL Extension

**Core design philosophy — the opposite starting point from InfluxDB:** rather than building a new storage engine from scratch, TimescaleDB is implemented as a **PostgreSQL extension**, giving it full SQL compatibility, joins with regular relational tables, and the entire mature PostgreSQL ecosystem (tooling, drivers, ORMs, `pg_dump`, replication) for free — trading some of the raw ingestion performance a from-scratch engine could achieve for dramatically lower adoption friction and relational feature completeness.

**Hypertables:** TimescaleDB's core abstraction — a **hypertable** looks like a single regular table to the application/SQL layer, but is transparently partitioned underneath into many **chunks**, each chunk covering a fixed time interval (and optionally further partitioned by a "space" dimension, e.g., by `device_id`, for very high-ingestion workloads) — this is a direct, concrete implementation of the time-partitioning pattern from Section 7.2, built on top of PostgreSQL's native table partitioning and inheritance mechanisms rather than a new storage format.

**Chunk exclusion (time-based pruning):** because each chunk's time range is known, PostgreSQL's query planner (extended by TimescaleDB) can exclude entire chunks outside a query's `WHERE time > ...` range at planning time, before scanning any data — the same zone-map-style pruning concept from Module 5.6 and Section 7.2, implemented via PostgreSQL's constraint-exclusion planner mechanism.

**Native compression:** TimescaleDB implements columnar-style compression (Module 5.5's techniques — RLE, delta encoding, dictionary encoding) applied *within* chunks once they age past the "hot, actively written" stage — converting older chunks' row-oriented storage into a compressed, columnar-like format in place, giving much of columnar analytics' compression benefit for historical data while keeping the actively-written recent chunk in fast, uncompressed row format. This is architecturally similar in spirit to the delta-store/main-store HTAP pattern (Module 6.4), but applied at the chunk-lifecycle level specifically for time-series data rather than as a general OLTP/OLAP split.

**Continuous aggregates:** TimescaleDB's equivalent of InfluxDB's continuous queries — materialized, incrementally-maintained rollup views (e.g., a continuously updated hourly-average table) that avoid re-scanning raw data for every dashboard refresh.

### 7.7 InfluxDB vs. TimescaleDB — The Practical Decision

| Property | InfluxDB (TSM engine) | TimescaleDB (Postgres extension) |
|---|---|---|
| Query language | InfluxQL / Flux (purpose-built) | Standard SQL |
| Joins with relational data | Limited/awkward | Native, full PostgreSQL join support |
| Raw ingestion throughput ceiling | Generally higher (purpose-built engine) | High, but bounded by PostgreSQL's underlying write path |
| Ecosystem/tooling maturity | TSDB-specific tooling | Entire PostgreSQL ecosystem |
| Cardinality handling | Explicit tag/field model, but vulnerable to cardinality explosion | Relies on PostgreSQL indexing; high-cardinality dimensions need careful index design |
| Best fit | Pure metrics/monitoring workloads, especially at very high ingestion rates | Teams already on PostgreSQL wanting time-series capability without a new system, or needing relational joins alongside time-series data |

### 7.8 Downsampling and Retention as First-Class Concerns

Both systems (and TSDBs generally) treat the hot/cold data lifecycle (7.1) as a core feature, not an afterthought — this is one of the clearest ways TSDBs differ philosophically from general-purpose databases, which have no opinion at all about data "aging out" or being progressively summarized:
- **Retention policies** automatically drop data older than a configured window, reclaiming storage without manual `DELETE` statements (which, recall from Module 4.3, are expensive tombstone-producing operations in LSM-based engines, and from general row-store mechanics, can also be costly at scale in B-tree engines due to page-level fragmentation from scattered deletes).
- **Downsampling/rollups** precompute and store reduced-resolution aggregates (e.g., 1-minute averages from 1-second raw data), so long-range historical queries (e.g., "show me a year of data") query a much smaller rolled-up dataset instead of aggregating billions of raw points on every query.

### 7.11 MCQs

**Q1.** The primary write pattern that distinguishes time-series workloads from general OLTP workloads is:
A) Random updates to existing rows
B) Near-monotonic, append-only writes ordered by time
C) Frequent deletes
D) Complex multi-table joins on write

*Answer: B*

**Q2.** Gorilla's XOR-based compression technique is effective because:
A) All floating point values are identical
B) Consecutive time-series values are usually numerically close, making most XOR result bits zero
C) It eliminates the need for timestamps
D) It compresses string tags

*Answer: B*

**Q3.** A "cardinality explosion" in a time-series database occurs when:
A) Too much historical data is retained
B) A tag with unbounded/high-cardinality values (e.g., request ID) causes unbounded series index growth
C) Compression ratio is too high
D) Downsampling is enabled

*Answer: B*

**Q4.** TimescaleDB's hypertable chunk exclusion works by:
A) Scanning every chunk and filtering in application code
B) Using PostgreSQL's planner to exclude chunks outside the query's time range before scanning any data
C) Deleting old chunks automatically
D) Compressing all chunks equally regardless of age

*Answer: B*

**Q5.** The main architectural tradeoff InfluxDB makes versus TimescaleDB is:
A) InfluxDB uses SQL, TimescaleDB doesn't
B) InfluxDB is a purpose-built engine (higher raw throughput ceiling, less ecosystem/join support), TimescaleDB is a PostgreSQL extension (full SQL/joins, ecosystem maturity)
C) They are architecturally identical
D) TimescaleDB cannot handle time-series data at all

*Answer: B*
