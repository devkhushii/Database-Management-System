# The Ultimate DBMS Handbook — Part 13: Research & Advanced Engineering

## Module 10 — Vector Databases

> **Goal of this module:** Understand vector search as a specific, well-studied algorithmic problem (approximate nearest neighbor search in high-dimensional space), the major algorithm families that solve it, and how production vector databases turn those algorithms into a full database system with filtering, persistence, and updates.

---

### 10.1 What Problem Vector Databases Actually Solve

**Embeddings**: a numeric vector (typically 100s to low thousands of dimensions, e.g., 768, 1536) produced by a machine learning model (an embedding model, or the intermediate representation of a larger model like an LLM) that represents the *semantic meaning* of some input — text, an image, audio — such that semantically similar inputs produce vectors that are **close together** in that high-dimensional space, under some distance/similarity metric.

**The core query**: given a query vector, find the `k` vectors in a large collection that are **closest** to it (nearest neighbors) — this is the basis of semantic search, recommendation ("items similar to this one"), retrieval-augmented generation (RAG, Module 11), image similarity search, and deduplication.

**Distance/similarity metrics used:**
- **Euclidean (L2) distance**: straight-line distance in the vector space.
- **Cosine similarity**: the angle between two vectors, ignoring their magnitude — the dominant metric for text embeddings, because embedding magnitude often reflects something incidental (like text length) rather than semantic content, so angle-only comparison is more meaningful.
- **Dot product**: related to cosine similarity but retains magnitude sensitivity; used when the embedding model was specifically trained such that magnitude carries meaningful information (some retrieval-tuned models are trained this way deliberately).

**Why this is a genuinely hard systems problem, not just "add a new index type":** exact nearest-neighbor search in high-dimensional space suffers from the **curse of dimensionality** — as dimensionality grows, the distinction between "near" and "far" points erodes (in very high dimensions, under many natural data distributions, most points end up roughly equidistant from each other), and exact search degrades toward having to compare the query against **every single vector** (brute-force, `O(n)` per query) because traditional spatial indexing structures (like R-trees, k-d trees) that work well in 2-3 dimensions stop providing any real pruning benefit once dimensionality gets into the hundreds. This is precisely why vector databases universally rely on **Approximate** Nearest Neighbor (ANN) search — trading a small, controllable amount of recall (missing some true nearest neighbors) for orders-of-magnitude speedup, an unavoidable and deliberate engineering tradeoff, not a shortcut.

---

### 10.2 The ANN Algorithm Landscape — Three Families

All practical ANN algorithms fall into one (or a hybrid) of three families, each exploiting a different structural idea to avoid brute-force comparison:

**Family 1 — Graph-based (HNSW)**: build a navigable graph structure over the vectors, where searching means traversing the graph greedily toward the query, similar in spirit to index-free adjacency traversal (Module 8.2) but for a proximity graph rather than an explicit relationship graph.

**Family 2 — Partition/cluster-based (IVF)**: partition the vector space into clusters ("cells"), and at query time only search within the clusters nearest to the query vector — analogous conceptually to the time/zone-map pruning ideas from Modules 5 and 7, but partitioning by vector-space proximity rather than by time or column value range.

**Family 3 — Quantization-based (PQ)**: compress each vector into a much smaller approximate representation, enabling many more vectors to fit in memory and be compared per unit time — analogous in spirit to the compression techniques from Module 5.5, but lossy in a way specifically designed to preserve approximate distance relationships rather than exact values.

**Critically, production systems combine these families rather than using just one** — e.g., IVF+PQ (partition first, then compress within partitions) is a standard combination; FAISS (10.6) supports building indexes that layer all three ideas together.

---

### 10.3 HNSW — Hierarchical Navigable Small World Graphs

**Citation:** Malkov & Yashunin, *"Efficient and Robust Approximate Nearest Neighbor Search Using Hierarchical Navigable Small World Graphs,"* IEEE TPAMI 2018 (building on the authors' earlier NSW work).

**Core idea:** build a **multi-layer graph** where each vector is a node, connected to a small number of its approximate nearest neighbors. The **hierarchy** is the key innovation over flat "small world" graphs: the top layer contains a small, sparse subset of nodes with long-range connections (enabling fast coarse navigation across the whole space), while lower layers become progressively denser, with the bottom layer containing *all* nodes and their finer-grained local connections — this hierarchy is directly analogous to a **skip list** (the same data structure LSM-tree memtables use, Module 4.2), generalized from one dimension (sorted order) to many dimensions (vector space proximity).

**Search algorithm:** start at an entry point in the top (sparsest) layer, greedily move to the neighbor closest to the query at that layer until no closer neighbor exists, then **drop down** to the next denser layer and repeat the greedy search from the current best position — continuing until reaching the bottom layer, where a final, more thorough greedy search (maintaining a candidate list of size `ef_search`, a key query-time tuning parameter controlling the recall/speed tradeoff) produces the final approximate nearest neighbors.

**Why it works well:** the hierarchical structure means a search touches a **logarithmic** number of nodes relative to the total dataset size on average (like a skip list's `O(log n)` search), rather than needing to traverse the dense bottom layer's full connectivity from the start — long-range top-layer connections let the search "jump" across the vector space quickly before refining locally.

**Key tuning parameters:**
- `M` (build-time): the number of connections per node — higher `M` improves recall but increases memory usage and index build time.
- `ef_construction` (build-time): candidate list size during index construction — higher values produce a higher-quality graph at the cost of slower build.
- `ef_search` (query-time): candidate list size during search — the primary recall/latency dial an operator tunes per-query or per-workload, directly trading search speed for result accuracy.

**Weaknesses:** HNSW graphs are memory-hungry (the full graph structure, plus typically the full, uncompressed vectors, must reside in memory for good performance) and are comparatively expensive/slow to build and update incrementally (inserting a new node requires finding its neighbors at each layer) compared to some partition-based approaches — this is why HNSW is often combined with quantization (10.5) in production to reduce its memory footprint.

### 10.4 IVF — Inverted File Index

**Core idea:** partition the vector space into `nlist` clusters (typically via **k-means clustering** run once at index-build time on a representative sample of the vectors), producing `nlist` **centroids**. Each vector is assigned to (and stored under) its nearest centroid's "inverted list" (borrowing the term "inverted index" from text search, where a term maps to a list of documents containing it — here, a centroid maps to a list of vectors assigned to it).

**Search algorithm:** given a query vector, first find the `nprobe` centroids closest to the query (a cheap comparison against only `nlist` centroids, not the full dataset), then perform an exhaustive (or further-optimized) search only within the vectors assigned to those `nprobe` clusters — pruning away the vast majority of the dataset (all clusters *not* among the `nprobe` nearest) without ever examining their vectors.

**Key tuning parameters:**
- `nlist`: number of clusters/centroids — more clusters mean finer partitioning (less data to search per cluster) but more centroids to compare against at query time, and a risk of clusters near the query boundary being missed if `nprobe` is too small.
- `nprobe`: number of nearest clusters actually searched at query time — the primary recall/latency dial, directly analogous to HNSW's `ef_search` role.

**Weaknesses:** vectors near a cluster boundary might have their true nearest neighbors in an *adjacent* cluster that wasn't among the `nprobe` searched clusters — increasing `nprobe` mitigates this at a direct, linear-ish latency cost. IVF also requires an upfront k-means training step (needing representative sample data before the index is fully usable) unlike HNSW, which can be built incrementally from an empty index.

---

### 10.5 Product Quantization (PQ)

**Core idea:** compress each high-dimensional vector into a compact code by splitting it into `m` sub-vectors (segments), and independently quantizing each segment against its own small codebook (typically 256 entries per segment, learned via k-means clustering on that segment's values across the training data) — each segment is then represented by just **one byte** (an index into its 256-entry codebook) instead of the original floating-point sub-vector, giving a dramatic compression ratio (e.g., a 768-dimension float32 vector, normally 3072 bytes, might compress to `m=96` bytes — roughly a 32x reduction).

**Why this enables faster search, not just less memory:** distance computation between a query and a PQ-compressed vector can be approximated via **precomputed distance lookup tables** — for each segment, precompute the distance from the (uncompressed) query's corresponding segment to all 256 possible codebook entries once, then approximate the total distance to any compressed database vector as the sum of `m` table lookups (cheap) instead of `m` full floating-point sub-vector distance computations — this "asymmetric distance computation" (query stays uncompressed/precise, database vectors are compressed) is the key trick that makes PQ both memory-efficient *and* fast at query time, not merely a compression scheme applied for storage's sake.

**Weaknesses:** PQ introduces genuine approximation error into distance calculations (not just a recall/latency tuning dial like HNSW/IVF's parameters, but a systematic quantization error baked into the representation itself) — this is why PQ is typically combined with a re-ranking step: retrieve a larger candidate set using fast, approximate PQ-based distance, then re-rank the top candidates using their original, uncompressed vectors (if available) for a final, more accurate ordering.

### 10.6 FAISS — The Reference Library

**Citation:** Johnson, Douze, Jégou, *"Billion-Scale Similarity Search with GPUs,"* IEEE Transactions on Big Data, 2019 (describing FAISS, developed at Facebook AI Research).

**What it is:** not a standalone database, but a highly-optimized **library** implementing the algorithm families above (HNSW, IVF, PQ, and combinations like `IVF-PQ`, plus GPU-accelerated implementations of several of them) — FAISS is the foundational building block many production vector databases (Milvus, and others) use internally for their actual vector-search core, rather than reimplementing ANN algorithms from scratch.

**Why it matters to understand separately from the databases built on it:** FAISS demonstrates that "vector search algorithm" and "vector database" are conceptually separable layers, exactly parallel to the storage-engine/database-system separation seen throughout this handbook (e.g., RocksDB as an embeddable engine vs. a full database built around it, Module 3.13) — a production vector database adds durability, filtering, distributed sharding, updates/deletes, and a query API around a core ANN algorithm implementation that FAISS (or an equivalent) provides.

### 10.7 From ANN Algorithm to Full Database — What Production Systems Add

**Metadata filtering ("filtered vector search"):** real queries are rarely pure nearest-neighbor lookups — they're typically "find the nearest neighbors *among documents where category = 'X' and date > Y*" — combining vector similarity with traditional predicate filtering. This is architecturally nontrivial: applying the filter *before* ANN search (pre-filtering) can break the ANN index's structure-dependent efficiency (e.g., HNSW's graph connectivity assumes searching the full graph; restricting to a filtered subset can disconnect the effective search graph), while applying the filter *after* ANN search (post-filtering) risks retrieving fewer than `k` results if too many top candidates get filtered out. Production systems use varying hybrid strategies — some maintain filtered sub-indexes, others use hybrid pre/post-filtering with over-fetching (retrieve more than `k` candidates, then filter, then trim) as a practical compromise.

**CRUD support (inserts, updates, deletes) on top of algorithms not designed for it:** HNSW graphs, in particular, are naturally suited to append-only insertion but awkward for deletion (removing a node can disconnect the graph around it) — production systems typically implement deletes as **tombstones** (directly reusing the LSM-tree tombstone concept, Module 4.3) with periodic index rebuilding/compaction to actually reclaim space and repair graph connectivity, rather than true in-place removal.

**Persistence and durability:** unlike FAISS (an in-memory library by default), production vector databases need WAL-based durability (Module 3.2's ARIES concepts, applied here) and the ability to reload/rebuild indexes after a restart without losing data — an engineering layer entirely orthogonal to the ANN algorithm itself.

**Sharding/distribution for billion-scale collections:** partitioning a vector collection across multiple nodes (directly reusing shared-nothing partitioning concepts, Module 2.2) and merging top-k results from each shard's local search (a scatter-gather pattern, also from Module 2.2) — since a single machine's RAM/compute often can't hold or search a truly massive vector collection alone.

**Hybrid search (vector + keyword/BM25):** many production systems combine dense vector similarity search with traditional sparse keyword search (BM25/TF-IDF-style text ranking, a decades-old information-retrieval technique) and fuse the two rankings (e.g., via **Reciprocal Rank Fusion**) — because pure semantic vector search sometimes misses queries that need exact keyword/entity matching (e.g., a specific product SKU or proper noun) that keyword search handles more reliably.

### 10.8 Production Vector Database Survey

**Pinecone:** a fully managed, cloud-native vector database (no self-hosting option) — architecturally applies compute-storage separation (Module 2.6) specifically to vector search, with pod-based or serverless deployment models; emphasizes operational simplicity and managed scaling over self-hosted flexibility.

**Milvus:** an open-source, distributed vector database built with a disaggregated architecture (separate query nodes, data nodes, index nodes, and a coordinator layer) directly following the cloud-native patterns from Module 2 — uses object storage (S3-compatible) for durable segment storage and supports multiple underlying ANN index types (including FAISS-based implementations, HNSW, and others) selectable per collection.

**Qdrant:** an open-source vector database written in Rust, notable for its filtering-first design — implements a custom filtering approach specifically built to integrate efficiently with HNSW search (addressing the pre/post-filtering tension from 10.7 directly in its index structure) rather than treating filtering as a bolt-on afterthought.

**pgvector:** a PostgreSQL **extension** (directly parallel in philosophy to TimescaleDB's approach in Module 7.6 — add specialized capability to Postgres rather than building a new system) adding a vector column type and both exact and approximate (IVF-Flat and HNSW) index support directly within PostgreSQL — trading some of the raw performance/scale a purpose-built vector database offers for full SQL integration, joins with relational data, and reuse of PostgreSQL's mature transactional/operational ecosystem, exactly the same tradeoff calculus as Section 7.7's InfluxDB-vs-TimescaleDB comparison, applied to the vector search domain.

**Weaviate:** an open-source vector database with a built-in, first-class **object/schema model** (rather than treating vectors as an addition to arbitrary key-value/document storage) and native support for hybrid search (10.7) and built-in vectorization modules (calling out to embedding models directly as part of the ingestion pipeline, rather than requiring the application to pre-compute embeddings externally).

**Chroma:** designed specifically for simplicity and developer ergonomics in the retrieval-augmented generation (RAG, Module 11) application-development workflow — commonly used as an easy-to-embed, local-first vector store for prototyping and smaller-scale production use, prioritizing ease of integration into LLM application frameworks over massive-scale distributed operation.

### 10.9 Choosing a Vector Database — Decision Framework

| Consideration | Favors purpose-built (Milvus/Pinecone/Qdrant/Weaviate) | Favors extension-based (pgvector) |
|---|---|---|
| Scale (billions of vectors, high QPS) | Yes — purpose-built distributed architecture | Bounded by single-Postgres-instance/cluster scaling limits |
| Need for relational joins with vector data | Awkward — typically requires separate lookup/join in application code | Native — vectors live alongside relational data in the same transactional system |
| Operational simplicity for teams already on Postgres | Adds a new system to operate | Reuses existing Postgres operational expertise/tooling |
| Advanced filtering + hybrid search needs | Often more mature/optimized (esp. Qdrant, Weaviate) | Improving, but historically less specialized |
| Managed/serverless preference | Pinecone specifically targets this | Depends on your Postgres hosting provider's support |

### 10.12 MCQs

**Q1.** Vector databases rely on Approximate (not exact) Nearest Neighbor search primarily because:
A) Exact search is impossible in any dimension
B) The curse of dimensionality makes exact search degrade toward brute-force comparison in high dimensions, making ANN's speed/recall tradeoff necessary
C) Approximate search is always more accurate
D) Exact search requires GPUs

*Answer: B*

**Q2.** HNSW's hierarchical multi-layer structure is conceptually most similar to:
A) A B-tree
B) A skip list, generalized from one dimension to many
C) A hash table
D) A bloom filter

*Answer: B*

**Q3.** IVF's `nprobe` parameter controls:
A) The number of dimensions in each vector
B) How many nearest clusters are actually searched at query time, trading recall for latency
C) The compression ratio
D) The number of GPUs used

*Answer: B*

**Q4.** Product Quantization enables faster search (not just compression) because:
A) It reduces the number of vectors in the dataset
B) Distance to compressed vectors can be approximated via precomputed per-segment distance lookup tables instead of full floating-point computation
C) It eliminates the need for a query vector
D) It only works with GPUs

*Answer: B*

**Q5.** pgvector's core architectural tradeoff, compared to a purpose-built vector database, is:
A) It cannot store vectors at all
B) Full SQL/relational integration and operational simplicity for Postgres users, at the cost of scale ceiling versus purpose-built distributed systems
C) It only supports exact search
D) It requires no indexing

*Answer: B*
