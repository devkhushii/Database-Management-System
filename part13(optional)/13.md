### 13.1 Source Code Layout

PostgreSQL's source tree is organized by functional layer, closely mirroring the architecture diagram from Module 12.1:

```
postgresql/
├── src/backend/
│   ├── parser/         # SQL lexer (scan.l) and grammar (gram.y) — Module 12.6, but generated via flex/bison
│   ├── optimizer/       # Planner: path/plan generation, cost estimation — Module 13.3
│   │   ├── path/        # Access path generation (seq scan, index scan, join paths)
│   │   ├── plan/        # Converts best Path into an executable Plan tree
│   │   └── util/        # Selectivity/cost estimation functions
│   ├── executor/        # The actual Volcano-model execution engine — Module 13.4
│   ├── access/          
│   │   ├── heap/        # Heap (row-store table) access method — Module 13.5
│   │   ├── nbtree/       # B-tree index implementation — the production analog of Module 12.2
│   │   ├── transam/      # Transaction management, XID (transaction ID) handling, clog
│   │   └── rmgrdesc/     # WAL "resource manager" descriptions — Module 13.6
│   ├── storage/
│   │   ├── buffer/       # Buffer pool manager — the production analog of Module 12.3
│   │   ├── lmgr/         # Lock manager — deadlock detection lives here (lock.c, deadlock.c)
│   │   └── page/         # Generic page layout routines
│   ├── commands/         # DDL command implementations (CREATE TABLE, VACUUM command entry point, etc.)
│   ├── catalog/          # System catalog (pg_class, pg_attribute, etc.) access routines
│   ├── tcop/             # "Traffic cop" — top-level query processing loop, ties parser→planner→executor together
│   └── utils/
│       ├── adt/          # "Abstract Data Types" — built-in type implementations (int8, text, jsonb, etc.)
│       ├── mmgr/          # Memory context management (Postgres's own allocator hierarchy)
│       └── cache/         # Catalog/relation caches (syscache, relcache)
├── src/include/          # Header files mirroring the backend/ structure
├── src/bin/              # Client-side utilities: psql, pg_dump, pg_ctl, initdb
├── src/interfaces/libpq/ # The C client library underlying virtually every driver in every language
└── contrib/              # Optional bundled extensions — the best real-world templates for 13.7
```

**How to navigate this practically:** if you're investigating "how does PostgreSQL decide whether to use an index," you now know to look in `src/backend/optimizer/path/` (Path generation) and `src/backend/optimizer/util/` (cost/selectivity estimation) — rather than grepping blindly through 1.5 million lines.

### 13.2 The Query Processing Entry Point — `tcop`

**"tcop" (traffic cop)** is where a query string first enters the backend process, in `src/backend/tcop/postgres.c`, specifically the function `exec_simple_query()` for simple protocol queries. This function's call sequence is the concrete, production version of Module 12.9's `demo()` function:

```
exec_simple_query()
  → pg_parse_query()      # scan.l + gram.y → raw parse tree (Module 12.6, generated not hand-rolled)
  → pg_analyze_and_rewrite()  # semantic analysis + view/rule rewriting → Query tree
  → pg_plan_queries()     # invokes the planner (13.3) → PlannedStmt
  → PortalRun()           # invokes the executor (13.4) on the PlannedStmt
```

**Why this matters for contributing:** almost every bug report or feature request maps to exactly one of these four stages — a "wrong syntax error" bug is a parser (`gram.y`) issue; a "chooses a bad plan" issue is a planner issue; a "wrong query results" or "crash during execution" issue is an executor issue. Correctly identifying which stage owns a given bug is the single most useful triage skill for a new contributor.

### 13.3 The Planner (`src/backend/optimizer/`)

**Two-stage plan generation**, directly extending the System R lineage from Module 1.4/3.2:

1. **Path generation** (`optimizer/path/`): for each table/join, the planner generates multiple candidate **Paths** — a `SeqScan` path, one `IndexScan` path per usable index, `NestLoop`/`HashJoin`/`MergeJoin` paths for each join, etc. — each annotated with an estimated cost (startup cost + total cost, both estimated in a made-up but internally-consistent unit calibrated to disk-page-fetches, from `optimizer/path/costsize.c`).
2. **Plan generation** (`optimizer/plan/`): the single lowest-total-cost Path (per the `cost` field) is converted into an executable **Plan** tree — the same "Volcano tree of physical operators" concept from Module 12.7's toy `Optimizer`, just handling a vastly larger space of Paths (this is `create_plan()` in `optimizer/plan/createplan.c`).

**Join ordering** (`optimizer/path/joinrels.c` and `optimizer/plan/planmain.c`) uses **dynamic programming** for a bounded number of tables (the classic System R algorithm — build up optimal join orders for subsets of size 1, then 2, then 3, reusing smaller subsets' optimal solutions), falling back to the **GEQO (Genetic Query Optimizer)** — a genuinely genetic-algorithm-based heuristic search — once the number of joined tables exceeds `geqo_threshold` (default 12), because exhaustive dynamic programming becomes computationally infeasible beyond that point.

**Selectivity estimation** (`optimizer/util/selfuncs.c` — the largest and most statistically dense file in the planner) is where PostgreSQL's answer to Module 11.4's cardinality estimation problem lives: it uses per-column **statistics** (most-common-values lists, histograms, null fractions — collected by `ANALYZE` and stored in `pg_statistic`) to estimate how many rows a predicate will match, generally **assuming independence between columns** unless **extended statistics** (`CREATE STATISTICS`, added in PostgreSQL 10+) have been explicitly created to capture known column correlations — a direct, concrete instance of exactly the cardinality-estimation weakness discussed abstractly in Module 11.4.

**A good first planner contribution:** improving a specific selectivity estimation function in `selfuncs.c` for an underserved data type/operator combination, or adding test cases to the regression suite (`src/test/regress/`) that expose a planner cost-estimation edge case.

### 13.4 The Executor (`src/backend/executor/`)

**A textbook Volcano/iterator-model implementation** — directly the production-scale version of Module 12.8's toy `SeqScanOperator`/`ProjectOperator`:

- Each Plan node type has a corresponding executor file: `nodeSeqscan.c`, `nodeIndexscan.c`, `nodeHashjoin.c`, `nodeNestloop.c`, `nodeAgg.c`, etc.
- Each implements the same three-function interface conceptually: `ExecInit*` (open), `Exec*` (next — called repeatedly, once per output row), and `ExecEnd*` (close) — `execProcnode.c` dispatches to the right function based on node type.
- **Tuple flow**: rows are passed between operators as `TupleTableSlot` structures, which abstract over different underlying tuple representations (heap tuples, virtual tuples, minimal tuples) to avoid unnecessary copying as tuples flow up the operator tree.

**Where PostgreSQL has moved toward vectorization (Module 5.4):** the core executor remains fundamentally row-at-a-time/Volcano, but `execExprInterp.c`'s expression evaluation was rewritten (PostgreSQL 10+) to use a compiled, JIT-able "expression steps" model rather than a naive recursive tree-walking interpreter, and PostgreSQL supports optional **JIT compilation** (`src/backend/jit/`, via LLVM) of expression evaluation and tuple deforming for CPU-bound analytical queries — a targeted, partial answer to the vectorized/compiled execution advantage described in Module 3.11 (Hekaton) and Module 5.4, without a full architectural rewrite to batch-at-a-time processing.

**A good first executor contribution:** many executor bugs are found via the regression test suite catching an edge case (e.g., a NULL-handling bug in a specific aggregate function) — `nodeAgg.c` and `nodeWindowAgg.c` are active areas given ongoing SQL standard window-function feature additions.

### 13.5 The Heap — PostgreSQL's Row Storage

**"Heap" here means "heap file" (unordered collection of pages), not a heap data structure** — this is PostgreSQL's on-disk row-store format, in `src/backend/access/heap/`.

**MVCC implementation specifics (the concrete version of Module 3.11's abstract MVCC discussion):** every row (tuple) carries `xmin` (the transaction ID that inserted it) and `xmax` (the transaction ID that deleted/updated it, or invalid if still live) hidden system columns. A transaction with snapshot `S` can see a tuple if `xmin` committed before `S` was taken and `xmax` either doesn't exist or belongs to a transaction not yet committed as of `S` — this **snapshot visibility check** (`tqual.c`/`heapam_visibility.c`) is called for essentially every tuple read and is one of the hottest code paths in the entire engine.

**The consequence of this MVCC design — PostgreSQL's specific "no in-place update" behavior:** an `UPDATE` in PostgreSQL does not modify a row in place; it inserts an entirely **new tuple version** (with a fresh `xmin`) and marks the old version's `xmax`, leaving the old version's space physically occupied until cleaned up — this is why VACUUM (13.6) is such a fundamental, unavoidable part of operating PostgreSQL rather than an optional maintenance nicety.

**TOAST (The Oversized-Attribute Storage Technique)** (`access/heap/tuptoaster.c` historically, now `access/toast/`): values too large to fit efficiently in a regular page (the default threshold is roughly 2KB) are automatically compressed and/or moved to a separate "TOAST table," with the main tuple storing only a small pointer — this is PostgreSQL's answer to the general large-value-handling problem also solved differently by WiscKey's key/value separation (Module 4.11).

### 13.6 VACUUM

**Why VACUUM must exist, precisely, given 13.5's MVCC design:** dead tuple versions (old row versions superseded by an `UPDATE`, or rows removed by `DELETE`) are never automatically removed at write time — VACUUM is the process that reclaims this space, and it's not optional maintenance; without it, a busy table's physical size grows unboundedly even if its logical row count stays constant (this is PostgreSQL's version of the space-amplification concern from Module 4.7, but arising from MVCC tuple versioning rather than LSM-tree compaction).

**What VACUUM actually does (`src/backend/commands/vacuum.c`, `access/heap/vacuumlazy.c`):**
1. Scans the table (or uses the **visibility map** — a compact bitmap tracking which pages contain no dead tuples, to skip pages that don't need scanning) to find dead tuples.
2. Removes dead tuples from their pages and updates each page's free space accordingly, making that space available for future inserts/updates — but critically, **VACUUM does not usually return space to the operating system**; it makes it available for reuse by PostgreSQL itself. (`VACUUM FULL` is the separate, much more expensive operation that actually rewrites the whole table to compact and return space to the OS, requiring an exclusive lock — a tradeoff directly analogous to LSM-compaction's cost-vs-thoroughness spectrum from Module 4.6.)
3. Updates the **Free Space Map (FSM)** so future inserts know which pages have room.
4. Critically, also handles **transaction ID (XID) wraparound prevention** — PostgreSQL's transaction IDs are a 32-bit counter that wraps around; VACUUM must periodically "freeze" old tuples (marking them as permanently visible to all transactions, avoiding the need to compare their XID against a wrapping counter) to prevent catastrophic data-appears-to-vanish bugs if the XID counter were allowed to wrap around unfrozen tuples. This is a PostgreSQL-specific correctness mechanism with no close analog in the other systems covered in this handbook, and a common source of production incidents when VACUUM is misconfigured or unable to keep up ("transaction ID wraparound" outages are a well-known PostgreSQL operational failure mode).

**Autovacuum** (`postmaster/autovacuum.c`): a background process that automatically triggers VACUUM (and `ANALYZE`, refreshing planner statistics from 13.3) based on configurable thresholds of dead-tuple accumulation per table — the vast majority of production PostgreSQL deployments rely on autovacuum rather than manual VACUUM scheduling, and autovacuum tuning is one of the most common real-world PostgreSQL operational deep-dives.

### 13.7 WAL in PostgreSQL — The Production ARIES Implementation

**Directly the production-scale version of Module 3.2 and Module 12.4** — `src/backend/access/transam/xlog.c` is the core WAL implementation.

**Resource managers (`rmgr`):** PostgreSQL's WAL is genuinely generic — rather than one monolithic log-record format, different subsystems (heap, btree, sequences, etc.) each register a **resource manager** (`access/rmgrdesc/`) responsible for generating and replaying their own specific WAL record types — this is a more modular evolution of the same core ARIES idea from Module 3.2, letting each access method define exactly what needs to be logged and how to redo/undo it, rather than forcing every change through one generic physical-logging format.

**Physical vs. logical WAL:** PostgreSQL's core WAL is fundamentally **physical** (recording literal byte-level changes to specific pages), but **logical decoding** (`access/transam/xlogreader.c` combined with output plugins, e.g., `test_decoding` or `pgoutput`) reinterprets the physical WAL stream as a sequence of logical row-level insert/update/delete events — this is the exact mechanism underlying PostgreSQL's built-in **logical replication** and is precisely the CDC (Change Data Capture) mechanism referenced in Module 9.6's stream-table duality discussion; tools like **Debezium** consume this logical decoding output directly.

**Checkpointing** (`access/transam/xlog.c`'s `CreateCheckPoint()`): periodically flushes all dirty buffer pool pages to disk and records a checkpoint WAL record, bounding how far back crash recovery ever needs to replay from — directly the production implementation of the "bound recovery time" motivation behind checkpointing described more abstractly across Module 3/4's discussion of recovery and compaction tradeoffs.

**Streaming replication:** physical WAL records are shipped to standby servers, which continuously apply them (replaying the same REDO logic used for crash recovery) to stay synchronized — this is why PostgreSQL's replication and its crash recovery share so much underlying code: a replica is, conceptually, a server perpetually "recovering" from a WAL stream that never stops arriving.

### 13.8 Extension Development

**PostgreSQL's extension mechanism (`CREATE EXTENSION`) is the single most impactful way most contributors actually add functionality**, without needing to modify PostgreSQL core at all — this is exactly the architectural pattern behind both **pgvector** (Module 10.8) and **TimescaleDB** (Module 7.6) discussed earlier in this handbook.

**Minimal extension anatomy:**
```
my_extension/
├── my_extension.control       # metadata: name, version, default schema
├── my_extension--1.0.sql      # SQL: defines functions/types/operators exposed to users
├── my_extension.c             # C implementation of any functions needing native code
└── Makefile                   # uses PGXS (PostgreSQL's extension build system)
```

**A minimal C function callable from SQL:**
```c
#include "postgres.h"
#include "fmgr.h"

PG_MODULE_MAGIC;

PG_FUNCTION_INFO_V1(my_add_one);
Datum
my_add_one(PG_FUNCTION_ARGS)
{
    int32 arg = PG_GETARG_INT32(0);
    PG_RETURN_INT32(arg + 1);
}
```
```sql
-- my_extension--1.0.sql
CREATE FUNCTION my_add_one(integer) RETURNS integer
AS 'MODULE_PATHNAME', 'my_add_one'
LANGUAGE C STRICT;
```

**Extension categories, roughly in order of how deeply they hook into the engine:**
- **Simple SQL/PLpgSQL functions and views** — no C required at all.
- **C functions** (as above) — for performance-critical logic, exposed via the `fmgr` (function manager) calling convention.
- **Custom data types** — requires implementing input/output functions (text ↔ binary representation) and, for types needing indexing, operator classes.
- **Custom index access methods** (the mechanism `pgvector`'s HNSW/IVFFlat indexes and `RUM`/other contrib indexes use) — implemented against the generic **Index Access Method (IAM) API** (`access/amapi.h`), the same abstraction B-tree (`nbtree`), GiST, GIN, and BRIN indexes all implement — this is the correct, supported way to add a fundamentally new index structure (like an ANN algorithm, Module 10.3-10.5) without forking PostgreSQL core.
- **Foreign Data Wrappers (FDWs)** — implement the FDW API to let PostgreSQL query external data sources (other databases, files, APIs) as if they were regular tables.
- **Background workers** — for extensions needing their own continuously-running process (e.g., pg_cron-style scheduling, or an extension doing asynchronous replication-like work).

**The `contrib/` directory as your best learning resource:** every extension bundled with PostgreSQL itself (`contrib/pg_stat_statements`, `contrib/btree_gin`, `contrib/pageinspect`) is real, production-quality, reviewed code demonstrating exactly these patterns — reading `contrib/` before writing your first extension is the highest-leverage single step a new contributor can take.

### 13.9 How to Actually Contribute — The Process

1. **Subscribe to `pgsql-hackers`** (the primary development mailing list — PostgreSQL development happens over email, not GitHub pull requests, which surprises many engineers coming from a GitHub-native workflow).
2. **Start with the Commitfest process**: PostgreSQL uses periodic "Commitfests" where submitted patches are reviewed; a new contributor's most valuable first contribution is often **reviewing someone else's patch** (testing it, checking it against the coding conventions, verifying documentation is updated) rather than submitting original code — this is explicitly encouraged and is how most contributors build the reputation needed for their own patches to get timely review.
3. **Follow the coding conventions** in `src/tools/pgindent` (an actual code formatter enforcing PostgreSQL's C style) and read `doc/src/sgml/sourcerepo.sgml`/the community wiki's "Developer FAQ" for submission norms.
4. **Small, focused patches** — the project strongly favors small, reviewable, single-purpose patches over large, sprawling ones; a large feature is typically broken into a patch series.
5. **Test coverage is mandatory** — any behavioral change needs corresponding additions to `src/test/regress/` (SQL-level regression tests) and, for replication/recovery features, `src/test/recovery/` (TAP-based Perl test framework driving actual server instances).

### 13.12 MCQs

**Q1.** PostgreSQL's planner falls back from dynamic programming to GEQO (genetic algorithm) join ordering when:
A) There are fewer than 2 tables
B) The number of joined tables exceeds `geqo_threshold`, since exhaustive DP becomes computationally infeasible
C) An index is missing
D) VACUUM hasn't run

*Answer: B*

**Q2.** PostgreSQL's `UPDATE` statement, due to its MVCC design:
A) Modifies the row in place
B) Inserts a new tuple version and marks the old version's xmax, leaving old-version cleanup to VACUUM
C) Locks the entire table
D) Requires no WAL record

*Answer: B*

**Q3.** VACUUM's freeze mechanism exists primarily to:
A) Improve query performance
B) Prevent transaction ID (XID) wraparound from causing tuples to incorrectly appear invisible
C) Compress table data
D) Rebuild indexes

*Answer: B*

**Q4.** PostgreSQL's logical decoding mechanism works by:
A) Maintaining a completely separate logical log
B) Reinterpreting the physical WAL stream as logical row-level change events via resource-manager-aware decoding
C) Polling tables periodically
D) Requiring triggers on every table

*Answer: B*

**Q5.** The correct, supported way to add a fundamentally new index structure (e.g., an ANN algorithm) to PostgreSQL without forking core is:
A) Editing `nbtree` directly
B) Implementing a custom index access method against the generic Index Access Method (IAM) API
C) Writing a PLpgSQL function
D) Modifying the heap format

*Answer: B*
