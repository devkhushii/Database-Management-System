# Part 10 — Database Internals & Storage Engine Architecture

## Module 6: Buffer Pool Internals

> **Recap:** Modules 3 and 4 referenced Shared Buffers and the InnoDB Buffer Pool as concrete facts. This module treats buffer pool management as a subject in its own right — the generic theory of buffer frames, pinning, dirty pages, eviction algorithms, and flushing, with both engines used as running examples.

---

### 6.0 Why This Module Exists

The buffer pool is the single most performance-critical data structure in any database engine — it's the boundary between "fast" (memory) and "slow" (disk), and nearly every tuning decision, cache-hit-ratio metric, and I/O bottleneck traces back to how it's managed. This is consistently one of the highest-yield internals topics in interviews because it combines classic CS concepts (LRU, caching) with database-specific constraints (durability ordering, concurrency).

---

### 6.1 What Is a Buffer Pool?

**Definition:** A buffer pool is a fixed-size region of memory holding cached copies of disk pages, sitting between the query executor and the storage manager, so that repeated access to the same data doesn't require repeated disk I/O.

**Why it exists (recap + formalized):** Disk I/O latency, even on fast NVMe SSDs, is measured in tens to hundreds of microseconds; RAM access is measured in tens of **nanoseconds** — a gap of roughly 3–4 orders of magnitude. A buffer pool exploits the fact that real-world query workloads exhibit **locality** (some data is accessed far more often than other data — the "hot" working set), letting a comparatively small amount of RAM absorb the vast majority of logical page accesses.

---

### 6.2 Buffer Frames

**What is it?** A **buffer frame** is a single fixed-size slot within the buffer pool, capable of holding exactly one disk page. The buffer pool is, structurally, just a large array (or set of arrays) of these frames, plus metadata describing what each frame currently holds.

**Per-frame metadata typically includes:**

| Field | Purpose |
|---|---|
| Page identifier (table/file + block number) | Which disk page is currently loaded in this frame (or "empty" if unused) |
| Pin count | How many active operations currently need this page — prevents eviction while in use |
| Dirty flag | Whether this frame's contents have been modified since being read from disk |
| Access/reference metadata | Used by the eviction algorithm (e.g., a "usage count" for clock-sweep, or LRU-list position) |
| Latch/lock | A short-duration internal synchronization primitive protecting concurrent access to the frame's metadata itself (distinct from the SQL-level row/table locks discussed in Module 1 — this is lower-level, protecting the buffer pool's own internal bookkeeping) |

**Diagram — buffer pool as an array of frames:**

```
Buffer Pool (e.g., 1000 frames of 8KB each = ~8MB, for illustration)

┌────────┬────────┬────────┬────────┬────────┬─────────────┐
│Frame 0  │Frame 1  │Frame 2  │Frame 3  │Frame 4  │  ...         │
│Page:    │Page:    │Page:    │Page:    │Page:    │              │
│ T1.pg42 │ T1.pg43 │ empty   │ IDX.pg7 │ T2.pg1  │              │
│Pin:2    │Pin:0    │  -      │Pin:1    │Pin:0    │              │
│Dirty:Y  │Dirty:N  │  -      │Dirty:N  │Dirty:Y  │              │
└────────┴────────┴────────┴────────┴────────┴─────────────┘
```

### 6.3 Pin Count

**What is it?** A per-frame counter tracking how many concurrent operations are currently actively using that page. A page with a pin count > 0 **cannot be evicted**, regardless of how the eviction algorithm would otherwise rank it.

**Why does it exist?** Without pinning, the eviction algorithm could theoretically select a page for eviction *while* another thread/process is in the middle of reading or modifying it — a correctness catastrophe (reading garbage, or losing an in-progress write). Pinning is the mechanism that makes "currently in use" and "eligible for eviction" mutually exclusive states.

**Lifecycle:**
1. An operation needing a page calls something conceptually like `pin_page(page_id)`
2. If already cached: pin count incremented, page returned immediately (a **cache hit**)
3. If not cached: a free (or evictable) frame is found, the page is read from disk into it, pin count set/incremented (a **cache miss**)
4. When the operation is done with the page, it calls `unpin_page(page_id)`, decrementing the count
5. Only when pin count reaches 0 does the page become eligible for the eviction algorithm to consider

**Real-life analogy:** A library book currently checked out (pinned) can't be given to another patron or returned to storage/discarded, even if it's the "oldest" book by some ranking — it's simply unavailable until returned.

**Interview importance:** ⭐⭐⭐⭐ "Why can't the buffer manager just evict any page based on LRU alone?" — pin count is the precise answer.

---

### 6.4 Dirty Pages

**What is it?** A page whose in-memory contents have been modified since it was read from disk (or since it was last written back), meaning the on-disk copy is now **stale** relative to memory.

**Why tracking this matters:**
1. **Correctness:** A dirty page must eventually be written back to disk, or the modification is lost — this is a distinct concern from durability-via-WAL (the WAL/redo log guarantees the change *can be replayed* on crash, but the data file itself still needs the actual page write eventually, for normal non-crash operation to reflect reality and to bound WAL replay time via checkpoints).
2. **Efficiency:** A clean page (not dirty) can be evicted "for free" — just discard it, since an identical copy already exists on disk, ready to be re-read if needed later. A dirty page must be **flushed** (written to disk) *before* eviction, which is strictly more expensive — this asymmetry is a major factor in eviction algorithm design (all else equal, preferring to evict clean pages over dirty ones reduces I/O).

**The critical ordering rule (ties directly to Module 1 and 2's page header LSN discussion):** A dirty page must **never** be flushed to disk before its corresponding WAL/redo log record has itself been durably flushed. This is the **Write-Ahead Logging invariant** (sometimes stated as "log flush precedes data flush") — violating it would mean a crash could leave a data file reflecting a change that the log can't explain or redo consistently, breaking crash recovery correctness.

### 6.5 Eviction Algorithms

**The core problem:** When the buffer pool is full and a new page must be loaded, which currently-cached (and unpinned) page should be evicted to make room?

**Goal:** Evict the page **least likely to be needed again soon**, to maximize the future cache hit ratio.

#### 6.5.1 Naive LRU (Least Recently Used)

**How it works:** Maintain pages in a strict list ordered by most-recently-accessed to least-recently-accessed; evict from the least-recently-accessed end.

**Why naive LRU is problematic for databases specifically:**
1. **Maintaining exact recency order under high concurrency is expensive** — every single page access would need to update a shared, globally-ordered list, creating serious lock/contention overhead in a highly concurrent multi-process/multi-thread database engine.
2. **Sequential scan pollution:** A single large sequential scan (e.g., `SELECT * FROM huge_table` for a report) touches every page of a huge table exactly once. Under naive LRU, all of those pages would rush to the "most recently used" end, evicting the actual hot working set — even though none of those scanned pages will likely be needed again soon. This is the exact problem InnoDB's young/old LRU split (Module 4, Section 4.2) was specifically designed to defend against.

#### 6.5.2 Clock-Sweep (PostgreSQL's Approach)

**What is it?** An approximation of LRU that avoids maintaining a strict ordered list, using a circular ("clock face") traversal instead.

**How it works:**
- Each frame has a small integer **usage count**, incremented (up to some cap) each time the page is accessed.
- A "clock hand" pointer sweeps around the buffer pool array looking for a victim.
- At each frame the hand visits: if the usage count is 0 **and** the pin count is 0, that frame is chosen as the eviction victim. Otherwise, if the usage count is > 0, it's **decremented** and the hand moves on to the next frame.
- Over one or more full sweeps, frequently-accessed pages keep getting their usage count "refreshed" by ongoing access and survive; rarely-accessed pages eventually decay to 0 and become eviction targets.

```
Clock Sweep Illustration (simplified, usage counts shown):

        Frame 0 (usage=3)
       ↗                  ↘
Frame 5 (usage=0) ← HAND    Frame 1 (usage=1)
       ↖                  ↗
        Frame 4 (usage=2)  Frame 2 (usage=0, pinned!)
              ↖          ↗
              Frame 3 (usage=1)

Hand at Frame 5: usage=0, pin=0 → EVICT this frame
```

**Why this is cheaper than strict LRU:** No global reordering needed on every access — just an in-place counter increment (a cheap, localized operation), and the sweep itself only touches frames as needed to find a victim, rather than maintaining perfect global order continuously.

#### 6.5.3 Young/Old LRU Split (InnoDB's Approach — Recap + Formalized)

Already covered in Module 4, Section 4.2 — restated here as a formal eviction algorithm alongside its peers:
- The LRU list is divided into a "young" head sublist (~5/8 by default) and an "old" tail sublist (~3/8 by default)
- New pages enter at the head of the **old** sublist, not the young one
- A page is only promoted to the young sublist if accessed again *after* a minimum delay (`innodb_old_blocks_time`) — access within that delay window (as happens rapidly within a single sequential scan) does **not** trigger promotion
- Eviction always takes from the tail of the old sublist

**This directly solves the sequential-scan-pollution problem** that naive LRU suffers from, without needing clock-sweep's approximation trick — a different solution to the same underlying problem.

#### 6.5.4 Other Real-World Algorithms (Brief Survey)

| Algorithm | Idea | Where seen |
|---|---|---|
| **LRU-K** | Tracks the time of the *K*-th most recent access (not just the most recent), better distinguishing "accessed once, long ago" from "accessed twice, recently" | Academic origin, informs several production designs |
| **2Q** | Maintains two queues — one for pages seen once, one for pages seen more than once — cheaply approximating LRU-K's benefit | Used in some storage system designs |
| **Clock with adaptive replacement** | Hybrid approaches combining clock-sweep's cheapness with recency/frequency tracking | Various modern systems |

**Interview importance:** ⭐⭐⭐⭐⭐ "Why not just use plain LRU for a database buffer pool?" — expect this, and the sequential-scan-pollution answer, in nearly every serious internals interview.

### 6.6 Page Flush Strategies

**The question:** Once a page is dirty, *when* does it actually get written to disk?

**Three triggers, all of which exist in both major engines (recap, now framed generically):**

1. **Eviction-time flush (reactive, worst case):** A dirty page is chosen as an eviction victim, and must be flushed *before* the frame can be reused — this blocks whatever operation needed that frame, directly hurting that operation's latency. This is the scenario every other proactive mechanism below exists to *minimize the frequency of*.
2. **Background/continuous flush (proactive):** A dedicated background process (Postgres's Background Writer; InnoDB's Page Cleaner threads) continuously flushes some dirty pages during normal operation, well before they'd otherwise be forcibly needed — smoothing I/O and reducing how often case #1 happens.
3. **Checkpoint flush (periodic, bulk, log-bounding):** A periodic process (Postgres's Checkpointer; InnoDB's checkpoint mechanism tied to its Page Cleaner and redo log) forces a broader flush of dirty pages specifically to bound how much log must be replayed on crash recovery — this is about **recovery time**, not just cache management.

**Why all three are needed simultaneously:** Relying only on #1 would create unpredictable latency spikes for user queries. Relying only on #2 without #3 wouldn't bound WAL/redo log growth or crash recovery time, since some dirty pages could theoretically linger unflushed indefinitely if they're rarely evicted. #3 provides the hard guarantee; #2 makes reaching that guarantee smoother; #1 is the fallback safety net.

---

### 6.7 Checkpoint Interaction (Formalized)

Recall from Modules 3 and 4: a checkpoint's purpose is to create a point in the log from which crash recovery can safely begin replaying, instead of from the very beginning of the log.

**The buffer-pool-specific guarantee a checkpoint provides:** *"As of this checkpoint, every page that was dirty has now been flushed to disk."* This means recovery only needs to replay log records **written after** the checkpoint — anything before it is already durably reflected in the data files themselves.

**Trade-off tuning:**

| More frequent checkpoints | Less frequent checkpoints |
|---|---|
| Faster crash recovery (less log to replay) | Slower crash recovery (more log to replay) |
| More I/O overhead during normal operation (frequent bulk flushing) | Less I/O overhead during normal operation |
| Smaller log retention needed | More log must be retained until the next checkpoint |

This exact trade-off is why both `checkpoint_timeout`/`max_wal_size` (Postgres) and InnoDB's analogous redo log capacity/checkpoint-age settings are standard production tuning knobs.

---

### 6.8 Prefetching (Read-Ahead)

**What is it?** Proactively reading pages into the buffer pool **before** they're explicitly requested, based on a prediction that they'll likely be needed soon.

**Why does it exist?** If the executor is performing a sequential scan and knows it will need pages 1, 2, 3, 4, ... in order, waiting to issue each page's disk read only at the moment it's needed wastes an opportunity: the disk (especially spinning disks, but SSDs benefit too via queue depth parallelism) could be reading page 5 *while* the CPU is still processing page 3's data — overlapping I/O wait time with useful computation instead of serializing them.

**Common prefetching strategies:**
- **Sequential/linear read-ahead:** Detects a scan pattern (accessing consecutive block numbers) and issues reads for the next N pages ahead of actual demand.
- **Bitmap-heap-scan prefetch (Postgres-specific):** When executing a bitmap index scan (first collect matching row locations via an index into an in-memory bitmap, then visit heap pages), Postgres can look ahead in the bitmap to prefetch heap pages it knows it will need soon, even though the *order* of those heap pages isn't strictly sequential.
- **InnoDB's linear/random read-ahead:** InnoDB monitors access patterns within an extent (a 1MB/64-page unit, recall Module 2) and, if enough of an extent's pages have recently been accessed sequentially, will prefetch the rest of that extent.

**Real-life analogy:** A waiter who, noticing a table is almost finished with their appetizers, starts preparing the main course *before* being asked — anticipating demand rather than reacting to it.

**Interview importance:** ⭐⭐⭐ Good to mention as part of a complete buffer pool discussion; less frequently the sole focus of a question compared to eviction algorithms.

### 6.9 Buffer Pool Sizing & Cache Hit Ratio

**Cache hit ratio:** The fraction of page requests satisfied from the buffer pool without needing disk I/O — the single most important high-level buffer pool health metric.

```
Hit Ratio = (Page Requests Served From Buffer Pool) / (Total Page Requests)
```

**Why this matters practically:** A hit ratio of 99% sounds excellent, but the remaining 1% miss rate, multiplied by a large enough request volume and disk latency, can still dominate overall query latency — a useful reminder that aggregate metrics like this need to be interpreted alongside actual query-level latency, not treated as a standalone success signal.

**PostgreSQL:** `pg_statio_user_tables` (`heap_blks_hit` vs. `heap_blks_read`) gives per-table hit ratios.
**MySQL/InnoDB:** `SHOW ENGINE INNODB STATUS` and `information_schema.INNODB_METRICS` expose buffer pool read/hit statistics directly.

**Sizing trade-off (recap, formalized):** Too small a buffer pool → excessive disk I/O for a working set that should fit in memory. Too large → memory pressure on the OS (risking swapping, which is catastrophic for database performance) and, for Postgres specifically, potential double-buffering waste given its reliance on the OS page cache alongside Shared Buffers.

### 6.10 Comparison Table: Buffer Pool Mechanics Across Engines

| Aspect | PostgreSQL | InnoDB |
|---|---|---|
| Structure name | Shared Buffers | Buffer Pool |
| Eviction algorithm | Clock-sweep | Young/old split LRU |
| Sequential scan defense | Ring buffers for large sequential scans/VACUUM (a separate, smaller dedicated buffer area used for big scans, to avoid touching the main clock-sweep pool at all) | Young/old LRU split with time-delayed promotion |
| Background flush process | Background Writer | Page Cleaner threads |
| Checkpoint-bounding process | Checkpointer | Checkpoint mechanism (tied to Page Cleaner + redo log capacity) |
| Typical size guidance | ~25% of RAM (relies partly on OS page cache too) | ~50–75% of RAM (aims to largely bypass OS cache) |
| Prefetch mechanisms | Sequential read-ahead, bitmap heap scan prefetch | Linear and random read-ahead based on extent access patterns |

**Note on Postgres's ring buffers (new detail beyond Module 3):** For large sequential scans, `VACUUM`, and bulk operations like `COPY`, Postgres deliberately uses a small, separate **ring buffer** instead of cycling pages through the main Shared Buffers clock-sweep pool — this is functionally the same *goal* as InnoDB's young/old split (protect the main cache from single-pass bulk operations) achieved via a structurally different mechanism (an isolated buffer area rather than a promotion-delay rule within one shared structure).

### 6.11 Advantages, Disadvantages, Best Practices

**Advantages of a well-tuned buffer pool:**
- Converts the vast majority of logical I/O into cheap memory access for well-behaved workloads with strong locality
- Eviction algorithms like clock-sweep and young/old LRU protect the cache from being polluted by one-off large scans

**Disadvantages / inherent limits:**
- No buffer pool algorithm can help a workload with genuinely no locality (e.g., truly random access across a dataset far larger than available RAM) — this is a fundamental limit, not a tuning failure
- Buffer pool internal metadata/latch contention can itself become a bottleneck at very high concurrency, motivating optimizations like InnoDB's multiple buffer pool instances

**Best practices:**
- Size the buffer pool based on your actual working set size, not just "as large as possible" — monitor hit ratio and OS-level memory pressure together
- Be aware of which operations (bulk loads, large reports, `VACUUM`) your engine treats specially to avoid cache pollution, and don't assume every large scan will always evict your hot data
- Watch for buffer-pool-related contention symptoms (e.g., high wait events specifically tied to buffer access) as a signal to consider sharding the pool (multiple instances) or reducing connection/thread concurrency

**Common mistakes:**
- Setting the buffer pool so large it starves the OS or other processes of memory, leading to swapping — a far worse outcome than a slightly lower buffer-pool hit ratio
- Ignoring that Postgres's Shared Buffers and the OS page cache work together — sizing Shared Buffers as if it were the *only* cache layer (as InnoDB's design more closely assumes) is a common Postgres-specific misconception

### 6.12 Chapter Summary

- The buffer pool is an array of fixed-size **frames**, each tracking a **pin count** (prevents eviction while in use) and a **dirty flag** (must be flushed before reuse, and only after its WAL record is durably flushed — the write-ahead invariant).
- Naive **LRU** is unsuitable for database buffer pools due to concurrency-maintenance cost and vulnerability to **sequential scan pollution**.
- PostgreSQL uses **clock-sweep** (a cheap LRU approximation) plus separate **ring buffers** for large scans/VACUUM; InnoDB uses a **young/old split LRU** with delayed promotion — two different mechanisms solving the same scan-pollution problem.
- Dirty pages are flushed via three overlapping mechanisms: reactive eviction-time flush (worst case), proactive background flush (Background Writer / Page Cleaner), and periodic checkpoint flush (bounds crash recovery time).
- **Prefetching** overlaps I/O wait with useful computation by anticipating future page needs based on detected access patterns.
- **Cache hit ratio** is the primary buffer pool health metric, but must be interpreted alongside actual query latency, not in isolation.

### 6.13 Cheat Sheet

```
Buffer Frame  → one slot, holds one page + metadata (pin count, dirty flag, usage info)
Pin Count     → >0 means "in use," CANNOT be evicted regardless of algorithm ranking
Dirty Flag    → must flush before reuse; NEVER flush before WAL/redo record is durable
              (write-ahead invariant)

Eviction algorithms:
  Naive LRU        → bad: expensive to maintain, polluted by sequential scans
  Clock-Sweep (PG) → cheap LRU approximation, usage-count decay via sweeping hand
  Young/Old LRU (InnoDB) → new pages enter "old" sublist, promoted only after delay
  PG Ring Buffers  → separate small buffer area for big scans/VACUUM (isolates pollution)

Flush triggers: eviction-time (reactive, worst) / background (proactive, smooth) /
                checkpoint (periodic, bounds recovery time)

Checkpoint guarantee: "everything before this point in the log is already on disk"
                       → recovery only replays log AFTER the last checkpoint

Prefetching: read pages before they're demanded, overlapping I/O wait with compute

Sizing: PG ~25% RAM (uses OS cache too) | InnoDB ~50-75% RAM (aims to bypass OS cache)
```
