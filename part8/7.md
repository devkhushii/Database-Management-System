## 7.0 Why This Module Exists

Sorting shows up **everywhere** in query processing: `ORDER BY`, `GROUP BY` (sort-based aggregation, Module 8), Sort-Merge Join (Module 6, §6.7), `DISTINCT` (dedup via sort), and window functions. The catch: **real-world tables are often far too large to fit in memory**, so an in-memory sorting algorithm (quicksort, mergesort — familiar from general CS/DSA study) simply cannot be applied directly. Databases need a fundamentally different approach: **External Sorting**.

---

## 7.1 Internal Sorting

### Definition

**Internal Sorting** refers to classic in-memory sorting algorithms — Quicksort, Mergesort, Heapsort — that operate entirely within RAM, assuming the entire dataset fits comfortably in available memory.

### Why It's Covered (Briefly) Here

Internal sorting is the **building block** used within each "chunk" of External Sorting (§7.2) — every phase of external sorting eventually needs to sort a memory-sized chunk of data, and that's done using a standard internal sorting algorithm (typically a variant of Quicksort or Heapsort).

### Quick Comparison (Assumed Prior Knowledge from DSA)

| Algorithm | Average Time | Worst Time | Space | Stable? |
|---|---|---|---|---|
| Quicksort | O(N log N) | O(N²) | O(log N) | No (typically) |
| Mergesort | O(N log N) | O(N log N) | O(N) | Yes |
| Heapsort | O(N log N) | O(N log N) | O(1) | No |

Most database engines use a **hybrid** approach for in-memory chunk sorting — e.g., PostgreSQL uses a variant of quicksort for in-memory sorts, switching strategies based on data characteristics (nearly-sorted detection, etc.).

### Interview Importance: ⭐⭐
Mostly assumed background knowledge from general algorithms study — the real interview focus is External Sorting (§7.2 onward).

## 7.2 External Sorting

### Definition

**External Sorting** is a family of algorithms for sorting datasets **too large to fit in memory**, by using disk as auxiliary storage and carefully minimizing the number of disk I/O passes required.

### Why It Exists

If you tried to run standard in-memory Quicksort on a 100 GB table with only 4 GB of RAM available, the algorithm's random-access assumptions would translate into catastrophic amounts of disk thrashing (each comparison potentially requiring random disk access) — utterly impractical. External sorting is purpose-built to sort data that exceeds memory, using **sequential** disk I/O patterns wherever possible (much cheaper than random I/O, per Module 2, §2.4).

### Real-Life Analogy

Imagine sorting 10,000 paper exam scripts, but your desk can only hold 200 at a time. You can't just "shuffle them all around" the way you would with a small deck of cards you can hold entirely in your hands. Instead, you sort small batches of 200 at a time (creating sorted "piles"), then merge those sorted piles together in an organized way — this is the essence of External Merge Sort (§7.3).

---

## 7.3 External Merge Sort

### Definition

**External Merge Sort** is the standard external sorting algorithm used by essentially all production databases. It operates in two distinct phases: (1) a **Run Generation** phase that creates sorted "runs" (chunks) small enough to fit in memory, and (2) a **Merge** phase that repeatedly merges these sorted runs together until a single, fully sorted output remains.

### The Two-Phase Structure

```
┌───────────────────────────────────────────────────────────┐
│                  EXTERNAL MERGE SORT                        │
└───────────────────────────────────────────────────────────┘

  PHASE 1: RUN GENERATION
  ─────────────────────────
  Read data in memory-sized chunks (e.g., B pages at a time),
  sort each chunk IN MEMORY (using internal sorting, §7.1),
  write each sorted chunk back to disk as a "RUN."

  Unsorted Data (huge, on disk)
         │
    ┌────┼────┬────┬────┐
    ▼    ▼    ▼    ▼    ▼
  [Chunk1][Chunk2][Chunk3][Chunk4][Chunk5]
    │      │      │      │      │
  (sort in memory, one chunk at a time)
    │      │      │      │      │
    ▼      ▼      ▼      ▼      ▼
  [Run1] [Run2] [Run3] [Run4] [Run5]     ← each RUN is now SORTED,
   (sorted) (sorted)(sorted)(sorted)(sorted)   written back to disk

  PHASE 2: MERGE
  ────────────────
  Repeatedly merge sorted runs together (like the merge step of
  standard mergesort, but reading from DISK, using only a small
  number of memory buffers per run being merged) until one single
  sorted run remains.

  [Run1][Run2][Run3][Run4][Run5]
      \    |    |    |    /
       \   |    |    |   /
        (merge multiple runs together per pass)
                  │
                  ▼
          [Final Sorted Output]
```

### Worked Numeric Example

Suppose we're sorting a table occupying **1,000 pages**, with **10 pages** of memory available for sorting.

**Phase 1: Run Generation**
```
1,000 pages / 10 pages-per-chunk = 100 sorted runs produced,
each run = 10 pages, each internally sorted using in-memory sort.
```

**Phase 2: Merge**
If we can merge **9 runs at a time** (reserving 1 buffer page for output, using a 10-page memory budget — this is the classic "B-1 way merge" pattern, explained fully in §7.4):
```
Pass 1: merge groups of 9 runs → ⌈100/9⌉ = 12 runs remain
Pass 2: merge groups of 9 runs → ⌈12/9⌉  = 2 runs remain
Pass 3: merge the final 2 runs → 1 fully sorted run (DONE)

Total merge passes needed: 3
```

### I/O Cost Formula

$$\text{Total I/O passes} = 1 (\text{run generation}) + \lceil \log_{B-1}(\text{number of initial runs}) \rceil (\text{merge passes})$$

where **B** = number of memory buffer pages available.

Each **pass** reads and writes the **entire dataset once** — so total I/O cost (in page reads+writes) is approximately:

$$\text{Total I/O} \approx 2 \times \text{pages}(\text{table}) \times \text{number of passes}$$

### Worked I/O Cost Calculation (continuing the example above)

```
pages(table) = 1,000
passes = 1 (run gen) + 3 (merge) = 4 total passes

Total I/O ≈ 2 × 1,000 × 4 = 8,000 page transfers
(compare this to a naive approach without any external sort
 strategy, which would be completely infeasible for data this
 size relative to available memory)
```

### Interview Importance: ⭐⭐⭐⭐⭐
**The core algorithm of this entire module.** Be ready to walk through both phases, calculate the number of passes for given table size / memory size, and derive the total I/O cost — this is a classic, very frequently asked GATE and senior-interview whiteboard exercise.

## 7.4 Multi-way Merge

### Definition

**Multi-way Merge** refers to merging **more than 2** sorted runs simultaneously in a single pass (as opposed to simple binary/2-way merging), dramatically reducing the total number of merge passes needed.

### Why It Exists

A naive **2-way merge** (merging only 2 runs at a time, like classic textbook mergesort) requires $\log_2(\text{number of runs})$ passes. With hundreds or thousands of initial runs, that's a lot of full-dataset read/write passes. **Multi-way merging** uses **all available memory buffers simultaneously** — merging as many runs together in one pass as memory allows — reducing the number of passes to $\log_{B-1}(\text{number of runs})$, where B is the number of memory buffer pages.

### Why "B-1" and Not "B"?

With **B** total memory buffer pages available: **B-1** buffers are used as **input** buffers (one page reserved per run being merged, so we can read from B-1 different runs simultaneously), and **1** buffer is reserved as the **output** buffer (to accumulate and periodically flush the merged, sorted result back to disk).

```
Memory Layout During Multi-way Merge (B=10 total buffer pages):

┌────┬────┬────┬────┬────┬────┬────┬────┬────┬────┐
│Run1│Run2│Run3│Run4│Run5│Run6│Run7│Run8│Run9│OUT │
│ in │ in │ in │ in │ in │ in │ in │ in │ in │ put│
│buf │buf │buf │buf │buf │buf │buf │buf │buf │buf │
└────┴────┴────┴────┴────┴────┴────┴────┴────┴────┘
   ← 9 INPUT buffers (B-1) →          ← 1 OUTPUT buffer →

At each step: compare the "current" value from each of the 9
input buffers, pick the SMALLEST, write it to the output buffer.
When an input buffer is exhausted, refill it from disk with the
next unread page of that same run.
When the output buffer fills up, flush it to disk and continue.
```

### Complexity Improvement: 2-way vs. Multi-way

| Merge Strategy | Passes Needed (for R initial runs) |
|---|---|
| 2-way merge | $\lceil \log_2 R \rceil$ |
| (B-1)-way merge | $\lceil \log_{B-1} R \rceil$ |

**Example:** 100 initial runs, B=10 (so B-1=9-way merge):
- 2-way: $\lceil \log_2 100 \rceil = 7$ passes
- 9-way: $\lceil \log_9 100 \rceil = 3$ passes — **more than 2x fewer passes**, directly translating to less total I/O.

### Interview Importance: ⭐⭐⭐⭐
The "why B-1 and not B" question is a classic, precise detail interviewers use to test whether a candidate truly understands the mechanism versus having memorized a surface-level description.

## 7.5 Replacement Selection

### Definition

**Replacement Selection** is a technique for **Run Generation** (Phase 1 of External Merge Sort) that produces sorted runs **longer than the available memory size** — typically averaging **twice** the memory buffer size — by cleverly reusing memory as output rows are emitted, using a data structure like a **min-heap (priority queue)**.

### Why It Exists

Standard run generation (§7.3) is limited to producing runs exactly the size of available memory (read a memory-full chunk, sort it, write it out). Replacement Selection breaks this limit — by continuously replacing emitted rows with newly-read rows **while still respecting sort order**, it can produce runs that are, on average, **2x** the size of memory alone — **halving** the number of initial runs, which directly reduces the number of merge passes needed in Phase 2 (§7.3, §7.4).

### Internal Working (Conceptual, Min-Heap Based)

```
1. Fill memory buffer with the first B pages of unsorted input,
   organize as a MIN-HEAP keyed by the sort column.

2. REPEAT:
   a. Extract the MINIMUM value from the heap → this is the next
      row for the CURRENT output run (write it to the current run).
   b. Read the NEXT unread input row.
   c. IF this new row's key >= the just-emitted row's key:
         → it can still belong to the CURRENT run (insert into heap,
           it will be picked up in future extraction steps of THIS run)
      ELSE (new row's key < just-emitted row's key):
         → it CANNOT belong to the current run (would violate sort
           order within this run) — instead, mark it for the NEXT
           run, and temporarily "freeze" it out of the active heap.
   d. IF the heap has no more values eligible for the current run:
         → close off the current run, start a new one with the
           frozen/held-back rows.
```

### Visual Intuition: Why Runs Can Exceed Memory Size

```
Memory holds only 4 values at a time, but watch how the RUN
grows past 4 elements because we keep replacing consumed slots
with new values that STILL qualify for the current run:

Heap: [3,7,9,12]  → emit 3 (run so far: [3])
      read new value: 5. Is 5 >= 3 (last emitted)? YES → add to heap
Heap: [5,7,9,12]  → emit 5 (run so far: [3,5])
      read new value: 2. Is 2 >= 5 (last emitted)? NO → hold for NEXT run
Heap: [7,9,12]    → emit 7 (run so far: [3,5,7])
      read new value: 15. Is 15 >= 7? YES → add to heap
Heap: [9,12,15]   → emit 9 (run so far: [3,5,7,9])
      ... continues, producing a run LONGER than the original
          memory capacity of 4, because "2" was the only value
          that had to be excluded and deferred to the next run.
```

### Expected Run Length (Classical Result)

Under a **random input distribution** assumption, the expected run length produced by Replacement Selection is approximately **2 × (memory buffer capacity)** — a well-known, often-cited result from database systems literature (originally analyzed in the context of tape-based sorting systems, where minimizing the number of runs/passes was especially critical due to tape's purely sequential access nature).

### Interview Importance: ⭐⭐⭐⭐
A genuinely advanced, high-signal topic — most candidates only know basic External Merge Sort; understanding Replacement Selection's min-heap mechanism and the "2x memory" result signals deep, textbook-level database internals knowledge (this is a classic **GATE-favorite** topic too).

## 7.6 Full Worked Example: Disk-Based Sorting End-to-End

### Setup
- Table size: **200 pages**
- Available memory: **5 pages** (B=5)

### Using Standard Run Generation (No Replacement Selection)
```
Phase 1: Run Generation
  200 pages / 5 pages-per-run = 40 initial sorted runs

Phase 2: Merge (using B-1 = 4-way merge)
  Pass 1: 40 runs → ⌈40/4⌉  = 10 runs
  Pass 2: 10 runs → ⌈10/4⌉  = 3 runs
  Pass 3: 3 runs  → 1 final sorted run

  Total merge passes: 3
  Total I/O passes: 1 (run gen) + 3 (merge) = 4
  Total I/O ≈ 2 × 200 × 4 = 1,600 page transfers
```

### Using Replacement Selection (Expected ~2x run length)
```
Phase 1: Run Generation (Replacement Selection)
  Expected run length ≈ 2 × 5 = 10 pages per run
  200 pages / 10 pages-per-run ≈ 20 initial sorted runs
  (HALF as many initial runs as standard run generation!)

Phase 2: Merge (using B-1 = 4-way merge)
  Pass 1: 20 runs → ⌈20/4⌉ = 5 runs
  Pass 2: 5 runs  → ⌈5/4⌉  = 2 runs
  Pass 3: 2 runs  → 1 final sorted run

  Total merge passes: 3 (same number in this particular example,
                          but with FEWER runs feeding into each pass
                          — for larger inputs, the pass-count
                          reduction becomes more pronounced)
```

> 💡 **Key takeaway:** Replacement Selection's benefit scales with data size and distribution — for very large tables with many initial runs, halving the run count can eliminate an entire additional merge pass, a meaningful I/O savings.

## 7.8 PostgreSQL vs MySQL vs Oracle: Sorting Implementation Notes

| Aspect | PostgreSQL | MySQL (InnoDB) | Oracle |
|---|---|---|---|
| Memory sort limit config | `work_mem` (per sort operation) | `sort_buffer_size` | `PGA_AGGREGATE_TARGET` / `SORT_AREA_SIZE` (legacy) |
| External sort trigger | Sort exceeds `work_mem` → spills to disk (`temp_files`) | Sort exceeds `sort_buffer_size` → uses disk-based merge sort | Sort exceeds allocated PGA sort area → spills to temp tablespace |
| Visible in EXPLAIN as | "Sort Method: external merge" vs. "quicksort" (in-memory) | "Using filesort" (may or may not be disk-based, depends on size) | "SORT (Disk)" vs. "SORT (Memory)" operator variants |

> 💡 **Practical tip:** PostgreSQL's `EXPLAIN (ANALYZE, BUFFERS)` output explicitly reports `Sort Method: external merge Disk: NNNkB` when a sort spills to disk — an extremely direct, practical signal that a query might benefit from increased `work_mem` (Module 9 will cover reading this output in full).

## 7.9 Best Practices, Common Mistakes & Edge Cases

### Best Practices
- Monitor for disk-based ("external") sorts in production `EXPLAIN ANALYZE` output — they're a strong, direct signal to consider increasing sort memory budgets for that workload.
- When designing indexes for frequently-sorted query patterns (`ORDER BY` on a specific column), consider whether an index can eliminate the sort step entirely (Module 5, §5.7).
- Be mindful that increasing memory budgets (`work_mem`, `sort_buffer_size`) is a **per-operation, potentially per-connection** setting in many databases — setting it too high globally can risk out-of-memory conditions under concurrent load, since many sorts might run simultaneously.

### Common Mistakes
- Assuming a sort with a small `LIMIT` (e.g., `ORDER BY x LIMIT 10`) requires a full external sort of the entire dataset — many optimizers use a specialized **Top-N heapsort** for this exact pattern, avoiding a full sort entirely (worth knowing as a distinct optimization).
- Blindly increasing memory limits without checking whether an index could eliminate the sort requirement altogether — often a far more effective, more scalable fix than throwing memory at the problem.
- Forgetting that `DISTINCT` and `GROUP BY` can also trigger sort-based execution strategies (Module 8), not just explicit `ORDER BY`.

### Edge Cases
- **Nearly-sorted input:** Some sorting algorithm variants detect and exploit nearly-sorted data for a speedup — worth knowing this exists, though the exact detection mechanisms vary by database/version.
- **Extremely skewed sort keys** with massive duplicate groups can complicate multi-way merge logic slightly (comparisons need tie-breaking), though this doesn't change the fundamental algorithm.

## 7.10 Chapter Summary

- **Internal sorting** algorithms (Quicksort, Mergesort, Heapsort) handle in-memory chunks; **External Sorting** handles data too large for memory.
- **External Merge Sort** has two phases: **Run Generation** (produce memory-sized sorted chunks) and **Merge** (repeatedly combine sorted runs until one remains).
- **Multi-way merge** uses B-1 input buffers + 1 output buffer to merge many runs per pass, reducing passes from $\log_2 R$ to $\log_{B-1} R$.
- **Replacement Selection** uses a min-heap to produce sorted runs averaging **2x** memory capacity, halving the number of initial runs and further reducing merge passes.
- Sort-Merge Join (Module 6) directly depends on this machinery — and can skip it entirely if inputs are already sorted via an index.
- Total I/O cost for external sorting ≈ `2 × pages × number_of_passes` — a formula worth memorizing for whiteboard/GATE-style calculations.

## 7.11 Cheat Sheet

```
EXTERNAL MERGE SORT FORMULAS
───────────────────────────────
Initial runs (standard)      = ⌈pages / B⌉
Initial runs (repl. select.) ≈ ⌈pages / (2×B)⌉   (expected, ~2x improvement)
Merge passes needed           = ⌈log_(B-1) (initial runs)⌉
Total I/O passes              = 1 (run gen) + merge passes
Total I/O (page transfers)   ≈ 2 × pages × total I/O passes

MEMORY LAYOUT DURING MERGE (B total buffer pages)
────────────────────────────────────────────────────
(B-1) input buffers  +  1 output buffer  =  B total

WHY REPLACEMENT SELECTION WORKS
──────────────────────────────────
Min-heap + "replace consumed slot with new row, keep in current
run if new row's key >= last emitted key" → runs grow past
memory size, averaging ~2x memory capacity.
```
