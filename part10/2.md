### 2.0 Why This Module Exists

So far, a "row" or "tuple" has been an abstract concept. In reality, disks store bytes, not rows. Somewhere, a decision is made about:
- How many bytes does this row occupy?
- Where exactly on disk does it live?
- What happens when a row is too big to fit on one page?
- What happens when a row shrinks or grows after an `UPDATE`?

This module answers all of that — the physical layer beneath every table you've ever queried.

---

### 2.1 What Is a Storage Engine (Physical Layer)?

**Definition:** The storage engine is the part of the database responsible for the **physical organization of data on disk** — how tables and indexes are broken into fixed-size **pages**, how rows are packed into those pages, and how free space is tracked and reused.

**Why does it exist?** Disks (and even SSDs) are addressed and transferred in fixed-size blocks, not arbitrary byte ranges. Reading 10 bytes still costs a full block read. Databases exploit this by aligning their internal unit of storage — the **page** — with the disk's natural transfer granularity, batching many rows into each page to amortize I/O cost.

**Real-life analogy:** Think of a shipping warehouse. You don't ship one item at a time — you pack items into standard-sized boxes (pages) because trucks (disk I/O) are most efficient moving full boxes. The warehouse also keeps a manifest of what's in each box and how much room is left (free space management), so new items can be placed efficiently.

---

### 2.2 The Page: The Fundamental Unit of Storage

**What is a page?** A fixed-size block of bytes — the smallest unit the storage engine reads from or writes to disk.

| System | Default Page Size |
|---|---|
| PostgreSQL | 8 KB (configurable at compile time only) |
| MySQL (InnoDB) | 16 KB (configurable: 4K/8K/16K/32K/64K) |
| Oracle | 8 KB default (configurable per tablespace) |
| SQL Server | 8 KB |

**Why fixed size?** Predictability. Fixed-size pages simplify:
- Buffer pool slot management (every frame is the same size)
- Disk offset calculation (`page_number × page_size = byte_offset`)
- Free space bookkeeping

**Disk-level behavior:** When the Storage Manager wants page #57 of a table's data file, it computes the byte offset (`57 × 8192` for Postgres) and issues a read at that offset — no scanning required, this is **O(1)** addressing.

**OS interaction:** Pages are typically read/written via standard `read()`/`write()`/`pread()`/`pwrite()` syscalls, sized to page boundaries. Some engines (InnoDB in certain modes) use direct I/O (`O_DIRECT`) to bypass the OS page cache and manage caching entirely themselves, avoiding double-caching between the OS and the database's own buffer pool.

### 2.3 Storage Models: Heap, Clustered, and Append-Only

Before diving into page internals, it's important to understand the three dominant ways tables organize their rows across pages.

#### 2.3.1 Heap Storage

**What is it?** Rows are stored in **no particular guaranteed order** — new rows are simply placed wherever there's free space (often physically appended, but not required to be in insertion or key order).

**Used by:** PostgreSQL (all tables are heap-organized by default), MySQL's `MyISAM` (legacy), and as the default table organization in many systems.

**Why it exists:** Simplicity and fast inserts — you don't need to maintain any physical ordering invariant when inserting; just find a page with free space and drop the row in.

**How it works:** A **Free Space Map (FSM)** tracks which pages have room. On `INSERT`, the engine consults the FSM, finds a page with enough free space, and places the row there. If no primary-key clustering is used, retrieving rows by primary key requires an index lookup that points to a `(page_number, slot_number)` — this pointer is often called a **TID (Tuple Identifier)** in Postgres or a **RowID** conceptually elsewhere.

**Advantages:**
- Fast, cheap inserts (no re-sorting/re-balancing needed)
- Simple free-space reuse after deletes

**Disadvantages:**
- Range scans on a secondary key can be scattered across many non-contiguous pages (poor locality)
- An extra indirection (index → heap page) is needed for every non-covering index lookup

---

#### 2.3.2 Clustered Storage

**What is it?** Rows are physically stored **in the order of a specific key** (usually the primary key) — the table *is* effectively a B-Tree with actual row data at the leaf level, rather than pointers.

**Used by:** MySQL's InnoDB (every InnoDB table is clustered by primary key; if no primary key is defined, InnoDB generates a hidden one), SQL Server (clustered index tables).

**How it works:** The primary key B-Tree's leaf nodes contain the full row, not just a pointer. Secondary indexes store the primary key value (not a physical row pointer) and require an extra lookup into the clustered index to fetch the full row — this extra step is why it's sometimes called a "bookmark lookup."

**Advantages:**
- Extremely fast primary-key range scans and point lookups (data is physically co-located in key order)
- No extra indirection for primary-key access

**Disadvantages:**
- Secondary index lookups require two B-Tree traversals (secondary index → primary key → clustered index)
- Inserts with random primary keys (e.g., random UUIDs) can cause expensive page splits and poor locality — this is why sequential/monotonic primary keys (e.g., auto-increment, or UUIDv7) are strongly preferred in InnoDB

**Comparison diagram:**

```
HEAP (Postgres-style)                    CLUSTERED (InnoDB-style)

Secondary Index               Primary Key B-Tree (IS the table)
  key → (page, slot) ──┐            key → [full row data]
                        │
                        ▼
                  Heap Page
               [full row data]

Secondary Index
  key → primary_key_value ──► lookup in
                               Primary Key B-Tree ──► [full row data]
```

---

#### 2.3.3 Append-Only Storage

**What is it?** New versions of data are always appended to the end of a file/log; old versions are never overwritten in place. Deletion and update are represented as new append entries (tombstones or new versions), and old space is reclaimed later by a background compaction process.

**Used by:** Log-Structured Merge (LSM) tree engines — Cassandra, RocksDB, LevelDB, MyRocks (MySQL storage engine). Not the default model for Postgres/InnoDB's core heap, though WAL itself (Module covered later) is append-only by nature.

**Why it exists:** Sequential writes are dramatically faster than random writes, especially on spinning disks and even with real-world SSD write amplification patterns. Append-only designs turn *all* writes into sequential writes.

**Trade-off:** Reads may need to check multiple locations (memtable + multiple on-disk sorted files) and periodic **compaction** is required to merge and garbage-collect old versions — this is a major operational cost of LSM-based systems.

**Interview importance:** ⭐⭐⭐⭐ Comparing heap vs. clustered vs. LSM/append-only storage is a very common "why would you choose X database for Y workload" system-design question.

### 2.4 Anatomy of a Page: The Slotted Page Layout

This is the single most important diagram in this module — nearly every relational database uses some variant of the **slotted page** layout.

**What problem does it solve?** Rows are **variable length** (a `VARCHAR(500)` might be 5 bytes or 500 bytes). If you stored rows at fixed offsets, you'd waste huge amounts of space. The slotted page design allows variable-length rows to be packed tightly while still supporting **stable references** to each row (needed so indexes can point at rows without needing to update every index entry every time row lengths change).

**The core idea:** Data grows from one end of the page; a directory of "slots" (pointers/offsets) grows from the other end. They meet in the middle, and free space is whatever's left between them.

```
┌────────────────────────────────────────────────────────────────┐
│                          PAGE HEADER                             │
│  (page ID, checksum, LSN, free space pointers, flags, etc.)      │
├────────────────────────────────────────────────────────────────┤
│  Slot 0  │  Slot 1  │  Slot 2  │  Slot 3  │   ...   →  (grows →) │
│ (offset, │ (offset, │ (offset, │ (offset, │                      │
│  length) │  length) │  length) │  length) │                      │
├────────────────────────────────────────────────────────────────┤
│                                                                    │
│                         FREE SPACE                                │
│                    (shrinks as page fills)                        │
│                                                                    │
├────────────────────────────────────────────────────────────────┤
│              ← (grows ←)     ...    │ Tuple 3 │ Tuple 2 │ Tuple 1 │ Tuple 0 │
└────────────────────────────────────────────────────────────────┘
        Data (tuples) packed from the END of the page backward
```

**Why grow from opposite ends?** This lets both the slot directory and the tuple data grow independently, using exactly as much space as needed, meeting wherever free space runs out. No wasted pre-allocation.

**Why is this "stable"?** An index doesn't store a raw byte offset for a row — it stores `(page_number, slot_number)`. If a row is updated and its length changes, the engine only needs to update the slot's `(offset, length)` entry — the slot number itself, which is what's referenced externally, doesn't change. This is what makes it possible to move a tuple around within a page without breaking every index that points to it.

**PostgreSQL specifics:** Called `ItemId` array (the slots) pointing to `HeapTupleHeaderData` structures (the tuples). Slot numbers combined with block number form the **CTID** (`(block, offset)`), Postgres's physical row identifier.

**InnoDB specifics:** InnoDB pages use a similar slotted structure but organize records in a **singly linked list in primary-key order** within the page, plus a sparse "page directory" of slots pointing to groups of records to speed up binary search within the page.

### 2.5 Page Header

**What is it?** A fixed-size region at the start of every page containing metadata *about* the page itself.

**Typical fields (conceptually, across engines):**

| Field | Purpose |
|---|---|
| Page ID / block number | Identifies this page's position in the file |
| LSN (Log Sequence Number) | The WAL position of the last change applied to this page — critical for crash recovery (this page must not be considered durably written until WAL up to this LSN is flushed — the core WAL invariant) |
| Checksum | Detects corruption (e.g., from a torn write or disk error) |
| Free space pointers | Offsets marking where the slot directory ends and tuple data begins (the "free space" boundary in Section 2.4) |
| Number of items/slots | How many tuples currently live on this page |
| Flags | E.g., "this page has been through a HOT update chain" (Postgres), "compressed page" flag, etc. |

**Why the LSN matters so much:** This single field is the linchpin of the **WAL protocol** (introduced in Module 1, detailed in the Recovery part): a dirty page can only be flushed to disk *after* its corresponding WAL record (with LSN ≤ this page's LSN) has itself been flushed. This ordering guarantee is what makes crash recovery correct.

**Interview importance:** ⭐⭐⭐ "What's stored in a page header and why does the LSN matter?" is a strong signal question for internals depth.

---

### 2.6 Tuple Header

**What is it?** Metadata stored alongside (usually immediately before) each individual row's actual column data.

**Typical fields:**

| Field | Purpose |
|---|---|
| Null bitmap | One bit per column indicating whether that column is `NULL` (so `NULL` columns don't need to store any actual bytes) |
| Column count / schema version | How many columns this tuple has (relevant if the table schema changed after this row was written) |
| Transaction visibility info (MVCC) | *(Postgres)* `xmin`/`xmax` — the transaction IDs that created and (if applicable) deleted/updated this row version; *(InnoDB)* a hidden `DB_TRX_ID` and `DB_ROLL_PTR` (roll pointer into the undo log) — full detail in Module 5 |
| Row length | Total byte length of this tuple (redundant with the slot's length field in some engines, primary source of truth in others) |
| Flags | E.g., "this tuple has been updated" (HOT chain marker in Postgres), "compressed", "has external/overflow data" |

**Example — simplified PostgreSQL heap tuple header conceptually:**

```
┌───────────────────────────────────────────────────────────┐
│  xmin (4 bytes)  │  xmax (4 bytes)  │  ctid (6 bytes)       │
├───────────────────────────────────────────────────────────┤
│  infomask flags (2 bytes)  │  null bitmap (variable)        │
├───────────────────────────────────────────────────────────┤
│                     Actual column data...                    │
│           name: "Alice"   |   email: "a@x.com"   | ...       │
└───────────────────────────────────────────────────────────┘
```

**Why this matters for MVCC:** Because `xmin`/`xmax` live *in the tuple itself*, a single physical page can contain multiple **versions** of the same logical row simultaneously — old versions not yet vacuumed, plus the current version — which is the physical foundation of how MVCC snapshot isolation works (fully covered in Module 5).

### 2.7 Free Space Management

**What is it?** The mechanism by which the storage engine tracks how much usable space remains on each page, so `INSERT`s can be routed to pages with room, without needing to scan every page.

**PostgreSQL: the Free Space Map (FSM)**
- A separate, compact auxiliary structure (stored as its own file, `<relfilenode>_fsm`) that tracks an approximate amount of free space per page, organized as a tree for fast lookup.
- On `INSERT`, Postgres consults the FSM to find a page with enough space *before* falling back to extending the file with a new page.
- The FSM is deliberately **approximate** — exact tracking would itself be expensive to maintain; slight staleness is an acceptable trade-off (worst case: engine tries a page, finds it doesn't actually fit, moves on).

**InnoDB: extent and segment-based free space tracking**
- InnoDB tracks free space at multiple granularities: individual pages within an **extent** (a group of 64 consecutive pages, 1MB by default), and free extents within a **segment** (part of a tablespace dedicated to an index or table).
- This hierarchical approach reduces fragmentation and helps keep related data physically close together.

**Real-life analogy:** A parking garage attendant who keeps a rough tally of how many spots are free on each floor (not tracking every single spot precisely) so they can quickly direct incoming cars to a floor likely to have space, without walking every floor first.

**Common mistakes / edge cases:**
- Heavy `UPDATE`/`DELETE` churn without `VACUUM` (Postgres) or without adequate `innodb_file_per_table` management can lead to **bloat** — pages with lots of free space from dead tuples, wasting both disk space and buffer pool cache efficiency.
- `FILLFACTOR` (Postgres) / not filling pages to 100% intentionally leaves headroom for future in-place updates (especially relevant to **HOT updates**, covered later in this handbook) — a deliberate trade of some space for update speed.

---

### 2.8 Page Directory (and Table-of-Pages Metadata)

**What is it?** At a level *above* individual pages, the storage engine needs to know: given a table, what set of pages (i.e., what data file(s), and how many pages) belong to it. This overall bookkeeping is sometimes referred to as a "page directory" or handled implicitly by file/segment structure.

- **PostgreSQL:** Each table (relation) is stored as one or more OS files named by its `relfilenode`, split into 1GB segments (`base/<db_oid>/<relfilenode>`, `.1`, `.2`, ...) purely to avoid OS file-size limits. Pages within are addressed simply by block number × page size.
- **InnoDB:** Uses **tablespaces** containing **segments**, which are made up of **extents**, which are made up of **pages** — a more elaborate internal hierarchy (detailed further in Module 12: Database File Structure).

**Why it matters:** This is the layer that answers "which physical bytes on disk correspond to table `employees`, page #4821?" — the necessary address-resolution step below every page access described in Module 1's request lifecycle.

### 2.9 Record Storage: Packing a Row Into Bytes

Putting it together — here's conceptually how a row like this:

```sql
INSERT INTO employees (id, name, salary, is_active)
VALUES (101, 'Alice', 75000.50, true);
```

...gets serialized:

```
Tuple Header:
  xmin = 501, xmax = 0 (not deleted)
  null_bitmap = 0000  (no nulls)
Column Data (packed per fixed layout defined by the catalog schema):
  id        : 4 bytes   → 00 00 00 65        (101)
  name      : varlen    → [len=5]"Alice"
  salary    : 8 bytes   → (IEEE754 double / numeric encoding)
  is_active : 1 byte    → 0x01
```

**Key design decision — fixed-length columns first:** Most engines place fixed-length columns before variable-length columns in the physical layout, so offsets to fixed columns can be computed directly (`base + sum of prior fixed widths`), while variable-length columns require walking a small length-prefix chain — a performance/complexity trade-off.

---

### 2.10 Variable-Length Records & Overflow Pages

**The problem:** A page is only 8KB/16KB. What happens when a single row (e.g., a row with a huge `TEXT` column) is bigger than that?

**PostgreSQL's answer: TOAST (The Oversized-Attribute Storage Technique)**
- Individual column values over a threshold (~2KB, so at least 4 fit per 8KB page) are automatically:
  1. **Compressed** in place, if that gets them under the threshold, or
  2. Moved **out-of-line** into a separate hidden TOAST table, broken into chunks, with the main tuple storing just a small pointer.
- This is fully transparent to SQL — you `SELECT` the column normally and Postgres reassembles it behind the scenes.

**InnoDB's answer: overflow pages**
- For `VARCHAR`/`TEXT`/`BLOB` columns that don't fit in the main record, InnoDB stores a prefix inline and the rest in separately-allocated **overflow pages**, linked via pointers — conceptually similar to TOAST but with different thresholds and mechanics depending on row format (`COMPACT`, `DYNAMIC`, `COMPRESSED`).

**Diagram:**

```
Main Row (in heap/clustered page)
┌─────────────────────────────────────────────┐
│ id=101 │ name="Alice" │ bio: [TOAST pointer]───┐
└─────────────────────────────────────────────┘  │
                                                     ▼
                                    ┌──────────────────────────┐
                                    │   TOAST / Overflow Pages   │
                                    │  chunk 1 │ chunk 2 │ ...   │
                                    └──────────────────────────┘
```

**Performance implication:** Accessing a TOASTed/overflowed column requires *additional* page reads beyond the main row — this is why `SELECT *` on tables with large text/blob columns can be much slower than selecting only the columns you need, even when you'd expect projection not to matter for I/O (it does, precisely because of this out-of-line storage).

**Interview importance:** ⭐⭐⭐⭐ "What happens when a row doesn't fit on a page?" is a strong internals-depth question, and TOAST specifically is a very common Postgres-specific interview topic.

### 2.11 Compression (Overview)

*(Full deep-dive with dictionary/prefix compression trade-offs is in Module 9: Storage Optimizations — this is a preview so the storage-layout picture is complete.)*

- **Row-level compression:** Individual large values (TOAST, InnoDB `ROW_FORMAT=COMPRESSED`) compressed independently.
- **Page-level compression:** Some engines/extensions compress entire pages before writing to disk, decompressing on read into the buffer pool.
- **Trade-off:** Compression reduces I/O and storage cost but adds CPU cost on every read/write — a classic space/time trade-off, increasingly favorable as CPUs have gotten much faster relative to disk I/O over the last decade.

### 2.12 PostgreSQL vs MySQL (InnoDB) vs Oracle — Storage Layout Summary

| Aspect | PostgreSQL | InnoDB (MySQL) | Oracle |
|---|---|---|---|
| Page size | 8 KB (fixed at compile time) | 16 KB (configurable) | 8 KB default |
| Table organization | Heap (unordered) | Clustered by primary key | Heap by default; index-organized tables (IOT) optional |
| Row identifier | CTID `(block, offset)` — **not stable** across `VACUUM FULL`/updates that move rows | Primary key value (stable) | ROWID (physical, mostly stable) |
| Oversized column handling | TOAST (out-of-line + compression) | Overflow pages (row-format dependent) | Chained rows / LOB segments |
| MVCC data location | In-place in heap tuple (`xmin`/`xmax`) | Separate undo log, referenced via roll pointer | Undo tablespace |
| Free space tracking | Free Space Map (separate file per relation) | Extent/segment-based within tablespace | Extent/segment-based within tablespace |

### 2.13 Advantages, Disadvantages, Best Practices

**Advantages of slotted-page design:**
- Efficient packing of variable-length rows
- Stable external references (page, slot) survive in-page row movement
- Clean separation between "where is data" (slots) and "what is the data" (tuples)

**Disadvantages:**
- Page-level free-space fragmentation over time (bloat) requires maintenance (`VACUUM`, `OPTIMIZE TABLE`)
- Extra indirection (slot lookup) on every row access, though this is cheap (in-page, in-memory once the page is buffered)

**Best practices:**
- Choose primary keys that are monotonically increasing where clustered storage (InnoDB) is used, to avoid expensive random-insert page splits.
- Avoid excessively wide tables with many large `TEXT`/`BLOB` columns you don't always need — consider splitting rarely-accessed large columns into a separate table.
- Set an appropriate `FILLFACTOR` (Postgres) for tables with frequent in-place updates, to leave room for HOT updates.

**Common mistakes:**
- Assuming `SELECT *` costs the same regardless of column selection — TOAST/overflow makes this false for wide-column tables.
- Ignoring table bloat from heavy update/delete churn and never running maintenance (`VACUUM`, `OPTIMIZE TABLE`).
- Using random UUIDs as InnoDB primary keys at high insert volume without understanding the page-split cost (mitigated in newer designs via UUIDv7's time-ordered structure).

### 2.14 Chapter Summary

- Data is physically organized into fixed-size **pages** (8KB Postgres / 16KB InnoDB by default), the atomic unit of disk I/O.
- Three storage models exist: **heap** (unordered, Postgres default), **clustered** (ordered by primary key, InnoDB default), and **append-only/LSM** (sequential-write optimized, used by Cassandra/RocksDB/MyRocks).
- Pages use a **slotted page layout**: a slot directory grows from one end, tuple data grows from the other, meeting at a free-space boundary — enabling variable-length rows with stable external references.
- Every page has a **page header** (critically including the LSN, which ties into WAL-based recovery) and every tuple has a **tuple header** (critically including MVCC visibility metadata like `xmin`/`xmax`).
- **Free space** is tracked via auxiliary structures (Postgres's FSM; InnoDB's extent/segment hierarchy) to route inserts efficiently.
- Oversized column values escape the page via **TOAST** (Postgres) or **overflow pages** (InnoDB), which is why projecting only needed columns can meaningfully reduce I/O.

---

### 2.15 Cheat Sheet

```
Page = fixed-size disk block (8KB PG / 16KB InnoDB)
Slotted Page = [Header][Slot Dir →]......[← Tuple Data][free space between]

Page Header key field: LSN → governs WAL-before-flush rule
Tuple Header key field: xmin/xmax (PG) or DB_TRX_ID+roll ptr (InnoDB) → MVCC

Storage Models:
  Heap       → unordered, Postgres default, needs index→page indirection
  Clustered  → ordered by PK, InnoDB default, PK access is direct
  Append-only/LSM → sequential writes only, needs compaction (Cassandra/RocksDB)

Oversized values:
  Postgres → TOAST (compress or move out-of-line + chunk)
  InnoDB   → Overflow pages (prefix inline + rest linked externally)

Free space tracking:
  Postgres → Free Space Map (separate file, approximate)
  InnoDB   → Extents (1MB/64 pages) + Segments within tablespace
```
