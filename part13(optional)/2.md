# The Ultimate DBMS Handbook — Part 13: Research & Advanced Engineering

## Module 2 — Modern Database Architectures

> **Goal of this module:** Every distributed database paper you read (Module 3) opens with an architecture diagram assuming you know these patterns cold. This module gives you the vocabulary and the internal tradeoffs behind each shape.

---

### 2.1 The Fundamental Question Every Architecture Answers

Given N machines, what do they **share**, and what do they **own privately**? The answer to that single question determines scalability, failure blast-radius, and coordination cost. There are three classical answers, plus a fourth (disaggregation) that broke the classical trichotomy.

---

### 2.2 Shared Nothing

**Definition:** Each node owns its own CPU, RAM, and disk. Nodes communicate only via network messages — no shared physical resource.

**Internal working:**
- Data is **partitioned** (sharded) across nodes, typically by hash or range of a partition key.
- A query touching one partition's data runs entirely on that node (no coordination needed) — this is the ideal case.
- A query spanning partitions (a cross-shard join, a global aggregate) requires a **coordinator** to scatter-gather: send sub-queries to relevant nodes, merge results.
- Failure of one node only affects the partitions it owns — the rest of the cluster keeps serving other partitions (this is *partial availability*, not full availability).

**Representative systems:** Cassandra, MongoDB (sharded), Google Bigtable, Vitess, CockroachDB, Snowflake's compute layer.

**Strengths:** Near-linear horizontal scalability — add nodes, add partitions, add throughput. No shared-resource contention bottleneck.

**Weaknesses:** Cross-partition transactions and joins are expensive (network round trips) and often require 2PC or similar. **Repartitioning** (rebalancing when you add/remove nodes) is a nontrivial live-migration problem — this is one of the hardest operational problems in shared-nothing systems (see consistent hashing, discussed further in Module 3's Dynamo summary).

---

### 2.3 Shared Disk

**Definition:** Multiple compute nodes, each with private CPU/RAM, all attached to the **same** shared storage (typically a SAN — Storage Area Network).

**Internal working:**
- Any node can read/write any block of data because storage is a shared physical resource — no partitioning of *data* required, only partitioning of *load*.
- Because multiple nodes can cache the same block in local RAM, a **distributed lock manager (DLM)** or cache-coherence protocol is required to prevent two nodes writing stale/conflicting versions (this is directly analogous to CPU cache coherence protocols like MESI, but across a network).

**Representative systems:** Oracle RAC (Real Application Clusters), IBM Db2 pureScale.

**Strengths:** No data repartitioning needed to add compute capacity — just add another node pointed at the same storage. Simpler consistency model than shared-nothing because there's one source of truth (the disk).

**Weaknesses:** The DLM/cache-coherence traffic becomes the scalability bottleneck as node count grows — this is why shared-disk systems scale to tens of nodes, not thousands. The shared storage fabric can itself become a single point of contention.

---

### 2.4 Shared Memory

**Definition:** Multiple CPUs share the same physical RAM and disk — this is really "scale-up," not "scale-out." A single powerful machine (or NUMA cluster acting like one).

**Internal working:** Threads/processes on different cores coordinate via shared memory (locks, latches, lock-free data structures) rather than network messages — coordination is nanoseconds/microseconds instead of milliseconds.

**Representative systems:** Traditional single-node PostgreSQL/MySQL, SQL Server, most in-memory databases (Hekaton, VoltDB single-node mode) at their core.

**Strengths:** Lowest coordination latency of all three models — no network involved. Simplifies transaction implementation enormously (no distributed consensus needed).

**Weaknesses:** Hard ceiling on scale — bounded by the biggest single machine you can buy (vertical scaling), and by memory bandwidth/NUMA effects once core counts get very high.

---

### 2.5 Comparison Table

| Property | Shared Nothing | Shared Disk | Shared Memory |
|---|---|---|---|
| Scale limit | Very high (1000s of nodes) | Moderate (10s of nodes) | Low (1 machine) |
| Coordination cost | High (network, per cross-partition op) | Medium (DLM/cache coherence) | Very low (in-process) |
| Failure blast radius | Partition-local | Storage-fabric dependent | Whole machine |
| Rebalancing complexity | High (data movement) | Low (storage is already shared) | N/A |
| Example | Cassandra, CockroachDB | Oracle RAC | Single-node Postgres |

### 2.6 Compute-Storage Separation (Disaggregation)

**The architectural break that defines the 2010s–2020s:** instead of choosing shared-nothing vs. shared-disk for the *whole stack*, separate the two layers and let each scale independently:
- A **stateless compute layer** (query execution, transaction coordination) that can be spun up, torn down, or resized in seconds.
- A **durable storage layer** (log-structured, replicated, often network-attached) that holds the actual data and is scaled/managed completely separately.

**Why this beats classical shared-nothing/shared-disk:** compute and storage have *different* growth curves in real workloads — you might need 10x more query throughput but the same data volume (or vice versa). Coupling them (as in shared-nothing, where each node owns both compute and its data partition) forces you to over-provision one to get enough of the other.

**Internal working — Amazon Aurora as the canonical example:**
- The database engine (a modified MySQL/PostgreSQL) treats the storage layer as a distributed, append-only redo log service, not a filesystem.
- Only **log records** (not full data pages) are shipped over the network to storage nodes — this is Aurora's key innovation, cutting network I/O drastically compared to shipping whole pages (full paper coverage in Module 3).
- Storage nodes apply the log asynchronously to reconstruct data pages on demand, handle replication (6-way across 3 AZs) and self-healing independently of the compute layer.
- Compute nodes can crash and restart, or a read-replica can be added, without touching the storage layer at all.

**Other examples:** Snowflake (compute = "virtual warehouses," storage = columnar files in S3/Blob), Google BigQuery (Dremel-based compute over Colossus storage), Neon (Postgres compute over a multi-tenant storage/log service).

---

### 2.7 Cloud-Native Databases

**Definition:** Databases architected from the ground up assuming cloud primitives (object storage, elastic compute, managed networking) rather than databases merely *hosted* on cloud VMs.

**Distinguishing traits:**
- Built on disaggregated compute/storage (Section 2.6) as a default, not an add-on.
- Assume failure is constant and design for it via replication and fast failover rather than treating hardware failure as exceptional.
- Billing and resource allocation are usage-based rather than fixed-capacity.

**Representative systems:** Aurora, Spanner, Snowflake, CockroachDB Cloud, Neon, PlanetScale.

**Contrast with "cloud-hosted":** running vanilla PostgreSQL on an EC2 instance is cloud-*hosted*, not cloud-*native* — it still has a single point of failure at the VM/disk level and doesn't scale compute and storage independently.

---

### 2.8 Multi-Tenant Databases

**Definition:** A single database deployment (or cluster) serves many independent customers ("tenants"), who must be isolated from each other's data and resource usage.

**Isolation models (in increasing order of isolation, decreasing order of efficiency):**

1. **Shared table, tenant-ID column** — every table has a `tenant_id`; all queries filter on it (often via row-level security policies). Cheapest to operate, weakest isolation — a bug in a `WHERE` clause leaks data across tenants.
2. **Shared database, separate schema per tenant** — each tenant gets its own schema/namespace within one database instance. Middle ground.
3. **Database-per-tenant** — each tenant gets a fully separate database (possibly on shared underlying compute/storage infrastructure). Strongest isolation, most operational overhead (migrations must run N times).

**Internal challenges specific to multi-tenancy:**
- **Noisy neighbor problem**: one tenant's expensive query starves others sharing the same compute — solved via resource governance (query cost limits, separate resource pools, or Snowflake-style fully isolated virtual warehouses).
- **Schema migration at scale**: rolling out a schema change across thousands of tenant schemas/databases safely.

---

### 2.9 Elastic Databases

**Definition:** Systems that can add or remove capacity (compute and/or storage) **while running**, without downtime, ideally automatically in response to load.

**Internal working:**
- Requires disaggregation (Section 2.6) as a prerequisite — you can't elastically resize compute if compute and storage are coupled to the same node.
- Autoscaling policies typically monitor CPU/memory/queue depth and trigger horizontal (add nodes) or vertical (resize node) scaling.
- For shared-nothing systems, elasticity also requires online **rebalancing** — moving partitions between nodes without blocking reads/writes (e.g., Vitess's `MoveTables`/reshard workflows, Cassandra's virtual nodes making rebalancing incremental rather than all-or-nothing).

**Representative systems:** Aurora Serverless v2 (fine-grained compute scaling in fractional ACU increments), DynamoDB on-demand mode, CockroachDB (elastic range rebalancing).

---

### 2.10 Serverless SQL

**Definition:** A query interface where you submit SQL and pay per query/bytes-scanned, with zero cluster management — the extreme end of elasticity, scaling not just up/down but to **zero**.

**Internal working:**
- Query compute is provisioned **per query** (or per short-lived session), often from a shared multi-tenant compute pool, and destroyed after — this is why cold-start latency is the central engineering problem for this category.
- Storage is always disaggregated object storage (S3, GCS) with a metadata/catalog layer to plan around file statistics.
- Billing model shifts from "cluster-hours" to "bytes scanned" or "compute-seconds consumed" — which also changes how query optimizers are incentivized (minimizing bytes scanned becomes a first-class optimizer goal, not just an engineering nicety).

**Representative systems:** Amazon Athena (Presto/Trino over S3), Google BigQuery, Snowflake (serverless tasks/functions), Databricks SQL Serverless.

**Key tradeoff vs. always-on clusters:** lower cost for spiky/infrequent workloads, but higher per-query latency floor (cold start) — which is why serverless SQL dominates ad hoc analytics but rarely powers low-latency OLTP.

---

### 2.11 How These Layers Combine in Practice

A real modern system usually mixes several of these patterns at different layers simultaneously. Example — **Snowflake**:
- **Storage layer**: shared-disk-like in spirit (all compute clusters read the same underlying columnar files in object storage) but implemented via disaggregation, not a SAN.
- **Compute layer**: shared-nothing "virtual warehouses" — each warehouse is an independent MPP (massively parallel processing) cluster with no shared state between warehouses.
- **Elasticity**: warehouses can be resized or auto-suspended (scale to zero) independently per workload.
- **Multi-tenancy**: each customer account is logically isolated; Snowflake itself runs as a multi-tenant cloud-native service across customers at the metadata/control-plane level.

This is why "what's the architecture of X" questions in interviews expect you to decompose the answer by layer (storage / compute / coordination), not give one label.

### 2.12 Production Examples & Industry Usage

| Architecture | System | Why chosen |
|---|---|---|
| Shared Nothing | Cassandra @ Netflix | Massive write throughput, multi-region availability over strict consistency |
| Shared Disk | Oracle RAC @ large enterprises | Legacy OLTP workloads needing HA without repartitioning |
| Compute-Storage Separation | Aurora @ many AWS-native SaaS companies | MySQL/Postgres compatibility + cloud elasticity |
| Cloud-Native + Elastic | Snowflake @ data teams | Pay-per-use analytics without cluster ops |
| Serverless SQL | Athena / BigQuery @ ad hoc analytics teams | Zero-ops querying of data lakes |
| Multi-Tenant (schema-per-tenant) | Many B2B SaaS platforms | Balance of isolation and operational cost |

### 2.14 MCQs

**Q1.** In a shared-nothing architecture, a cross-partition join typically requires:
A) A distributed lock manager
B) A scatter-gather query coordinator
C) Nothing extra — it's automatic
D) A shared disk

*Answer: B*

**Q2.** The primary scalability bottleneck of shared-disk architectures is:
A) Network bandwidth to compute nodes
B) Distributed lock manager / cache-coherence traffic
C) Query planning
D) SQL parsing overhead

*Answer: B*

**Q3.** Amazon Aurora's key innovation over traditional replication is:
A) Using shared-nothing compute
B) Shipping only redo log records to storage instead of full data pages
C) Removing the WAL entirely
D) Storing data only in memory

*Answer: B*

**Q4.** Serverless SQL systems like Athena/BigQuery typically bill based on:
A) Fixed monthly subscription
B) Number of tables
C) Bytes scanned / compute-seconds
D) Number of users

*Answer: C*

**Q5.** Multi-tenancy isolation via "database-per-tenant" trades off:
A) Lower isolation for higher efficiency
B) Higher isolation for higher operational overhead
C) No isolation at all
D) Isolation is unrelated to tenancy model

*Answer: B*
