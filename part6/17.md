# Part 6: Transactions & Concurrency Control

## Module 17: Interview Mastery

> This module is a consolidated, high-density interview preparation reference spanning everything covered in Modules 1–16. It's organized for rapid review before an interview, and includes progressively harder whiteboard scenarios and production-incident-style discussions that senior candidates are actually asked.

---

### 17.1 ACID Interview Questions — Rapid Fire

1. Expand ACID and define each property in one sentence.
2. Which ACID property is responsible for preventing partial writes after a crash? *(Atomicity)*
3. Why is Consistency considered partly the application's responsibility? *(The DB only enforces declared constraints, not undeclared business rules.)*
4. What mechanism underlies both Atomicity and Durability? *(Write-Ahead Logging.)*
5. What's the durability trade-off with `innodb_flush_log_at_trx_commit=0`? *(Up to ~1 second of committed transactions can be lost on crash, in exchange for lower commit latency.)*
6. Can a system be atomic without being durable? *(Conceptually yes — they protect against different failure modes — though real WAL-based systems typically provide both together.)*
7. Give a real-world example where weak Consistency (missing a constraint) caused a bug you can imagine in production. *(E.g., a missing `CHECK (price >= 0)` allowing a negative price via a buggy discount calculation.)*

---

### 17.2 Isolation Level Interview Questions — Rapid Fire

1. Name the four SQL standard isolation levels in order.
2. Which anomalies does Read Committed prevent, and which does it still allow?
3. What's PostgreSQL's default isolation level? What's InnoDB's? *(Read Committed; Repeatable Read.)*
4. Why does MySQL default to a stricter level than PostgreSQL? *(InnoDB's gap-locking makes REPEATABLE READ practical and safe as a default; PostgreSQL's cheap per-statement snapshot makes READ COMMITTED sufficient by default.)*
5. Does Snapshot Isolation prevent Write Skew? *(No — this is the critical distinction between Snapshot Isolation and true Serializable.)*
6. What is Serializable Snapshot Isolation (SSI), and how does it differ from lock-based Serializable? *(SSI tracks read-write dependencies on top of MVCC to detect dangerous structures including write skew, without predicate locks; lock-based Serializable uses 2PL with range/predicate locking.)*
7. If your application gets a "could not serialize access" error from PostgreSQL, what should it do? *(Retry the transaction — this is expected, normal behavior under stricter isolation levels, not a bug.)*

---

### 17.3 Locking Interview Questions — Rapid Fire

1. What's the difference between a Shared lock and an Exclusive lock?
2. What problem does an Update lock solve? *(Conversion deadlocks from two transactions both holding Shared locks and both trying to upgrade to Exclusive.)*
3. What are Intent locks, and why do they exist? *(To let a coarse-grained lock request check compatibility without scanning every fine-grained lock individually — the Multiple Granularity Locking protocol.)*
4. What is lock escalation, and what's its main downside? *(Converts many row locks into one table lock to save memory, at the cost of a sudden, discontinuous drop in concurrency.)*
5. Explain the Growing Phase and Shrinking Phase of 2PL.
6. Does 2PL guarantee freedom from deadlock? *(No — except Conservative 2PL. 2PL guarantees serializability, not deadlock-freedom; these are separate concerns.)*
7. What's the difference between Strict 2PL and Rigorous 2PL? *(Strict holds X-locks until commit; Rigorous holds ALL locks — S and X — until commit.)*

---

### 17.4 Deadlock Interview Questions — Rapid Fire

1. What are the four necessary conditions for deadlock?
2. What is a Wait-For Graph, and how do you detect a deadlock using it? *(A directed graph of "waiting for" relationships; a cycle in it means a deadlock exists.)*
3. Compare Wait-Die and Wound-Wait. *(Wait-Die: older waits for younger, younger dies if it wants a lock held by older. Wound-Wait: older wounds/aborts younger if younger holds something older needs; younger waits for older.)*
4. Why do most production databases use deadlock detection rather than prevention? *(Prevention strategies like Conservative 2PL require knowing all future lock needs upfront — often impractical for real, conditional application logic.)*
5. What's the difference between deadlock, starvation, and livelock? *(Deadlock: no one in the cycle proceeds. Starvation: one specific transaction repeatedly fails to progress while others succeed. Livelock: transactions actively execute but repeatedly collide, making no real progress.)*
6. How does victim selection typically decide which transaction to abort? *(Least work done, fewest locks held, and avoiding repeatedly picking the same transaction to prevent starvation.)*

---

### 17.5 MVCC Interview Questions — Rapid Fire

1. What core guarantee does MVCC provide? *("Readers never block writers, writers never block readers.")*
2. What are `xmin` and `xmax`? *(The transaction that created a row version, and the transaction that superseded/deleted it, respectively.)*
3. Why does PostgreSQL need VACUUM? *(Old row versions ("dead tuples") accumulate directly in the table heap and must be reclaimed; also prevents transaction ID wraparound.)*
4. How does InnoDB's MVCC implementation differ structurally from PostgreSQL's? *(InnoDB updates rows in place and reconstructs old versions on-demand from the undo log; PostgreSQL keeps old versions directly in the heap.)*
5. Does MVCC alone guarantee full Serializability? *(No — write skew is the classic counterexample; true Serializable requires additional mechanisms like SSI.)*
6. What's the "first-committer-wins" rule? *(For write-write conflicts under MVCC, if another transaction committed a conflicting write after your snapshot began, your write is rejected/must retry.)*

---

### 17.6 Schedule / Serializability Interview Questions — Rapid Fire

1. What makes two operations "conflict"? *(Different transactions, same data item, at least one is a write.)*
2. What's the difference between Recoverable, Cascadeless, and Strict schedules? *(Recoverable: no txn commits before a txn it read dirty data from. Cascadeless: no dirty reads at all. Strict: no dirty reads OR dirty writes — items untouched until the previous writer commits/aborts.)*
3. How do you test Conflict Serializability? *(Build the precedence graph; acyclic = conflict serializable.)*
4. What's the relationship between Conflict Serializability and View Serializability? *(Conflict Serializable ⊂ View Serializable; the gap is explained by blind writes.)*
5. Why do real databases target Conflict Serializability rather than View Serializability? *(View Serializability is NP-Complete to test in general; Conflict Serializability is polynomial-time via the precedence graph, and 2PL can be proven to guarantee it without runtime graph construction.)*

### 17.7 Whiteboard Scenarios (Progressive Difficulty)

**Scenario 1 (Junior/Mid level): Design a "like" button's backend transaction logic for a social media post.**
*Talking points expected:* atomic increment vs. read-then-write race (Lost Update, Module 5.2); whether strict consistency of the exact count matters in real time (probably not — eventual consistency / approximate counters, tied to hot-row mitigation from Module 16.2, may be acceptable here).

**Scenario 2 (Mid/Senior level): A flash-sale checkout system is overselling a limited-stock item. Diagnose and fix.**
*Talking points expected:* identify the missing `SELECT ... FOR UPDATE` / atomic conditional update (Module 6.5, Module 15.3); explain the Lost Update mechanism precisely; propose the fix and discuss the throughput trade-off of adding locking to a hot path (Module 16.2's hot-row mitigation options as an extension).

**Scenario 3 (Senior level): Design the transaction/consistency strategy for a hospital's on-call doctor scheduling system.**
*Talking points expected:* recognize this as the canonical Write Skew scenario (Module 5.8); explain why Snapshot Isolation is insufficient; recommend true Serializable isolation (SSI or 2PL-based) or explicit application-level locking around the invariant check; discuss retry-handling implications.

**Scenario 4 (Senior/Staff level): A microservices-based order checkout spans an Inventory Service, Payment Service, and Orders Service — each with its own database. Design the transaction strategy.**
*Talking points expected:* recognize this can't use a single local transaction (Module 14.1); compare 2PC/XA vs. SAGA (Module 14.7); recommend SAGA for microservices given blocking/scalability concerns; design the specific compensating actions; explicitly address the intermediate-state-visibility trade-off (Module 14.6).

**Scenario 5 (Staff level): Production incident — checkout latency has risen from 50ms to 800ms over a month with no code deploys. Diagnose.**
*Talking points expected:* systematic diagnostic approach — check for lock-wait time specifically (Module 16.1), check for long-running/idle-in-transaction sessions (Module 16.3), check for table bloat correlating with vacuum health (Module 10.8, Module 16.7), check for a payment-gateway-inside-transaction anti-pattern creep (Module 15.7), consider whether traffic growth has pushed a previously-fine hot row into serious contention (Module 16.2).

### 17.8 Production Incident Discussion Framework (A Reusable Structure for Any Incident Question)

When asked any "diagnose this production issue" question, structure your answer as:

1. **Clarify the symptom precisely** — latency? errors? data correctness? Which specific operation?
2. **Form 2–3 concrete hypotheses**, each tied to a specific mechanism (lock contention, long-running transaction, wrong isolation level, missing index, hot row, deadlock rate spike, external-call-inside-transaction).
3. **State how you'd validate each hypothesis** — specific monitoring views, logs, or metrics you'd check (Module 16.1's diagnostic signals).
4. **Propose a fix for the most likely hypothesis**, and explicitly name the trade-off it introduces (e.g., "adding `FOR UPDATE` fixes correctness but increases lock hold time on that row").
5. **Propose a longer-term preventive measure** (monitoring, code review practice, architectural change) — this demonstrates senior-level thinking beyond the immediate fix.

Interviewers at the Senior SDE-2/SDE-3 level are frequently evaluating this **structured diagnostic process** as much as (or more than) the specific final answer.

### 17.9 GATE-Style Numerical Question Bank (Consolidated Review)

**Q1.** Given `S: R1(A) W2(A) R2(B) W1(B)`, is this schedule conflict serializable?
<details><summary>Answer</summary>Edges: T1→T2 (R1(A) before W2(A)); T2→T1 (R2(B) before W1(B)). Cycle exists → NOT conflict serializable.</details>

**Q2.** `TS(T1)=5, TS(T2)=15`. Current `R-ts(A)=10, W-ts(A)=3`. T1 attempts `R1(A)`. Outcome?
<details><summary>Answer</summary>Check: TS(T1)=5 < W-ts(A)=3? No. ALLOWED. R-ts(A) remains max(10,5)=10.</details>

**Q3.** Classify `S: R1(A) W1(A) R2(A) W2(A) C2 C1` (recoverable/cascadeless/strict).
<details><summary>Answer</summary>T2 reads A after T1's write (while T1 uncommitted) and commits BEFORE T1 → this is NOT recoverable (irrecoverable), hence also not cascadeless or strict.</details>

**Q4.** A transaction acquires locks on X, then Y, releases X, then wants to acquire Z. Valid under 2PL?
<details><summary>Answer</summary>No — releasing X begins the shrinking phase; acquiring Z afterward violates 2PL.</details>

**Q5.** Wait-For Graph has edges T1→T2, T2→T3, T3→T1, T3→T4. Is there a deadlock, and which transactions are involved?
<details><summary>Answer</summary>Yes — cycle T1→T2→T3→T1. T4 is NOT part of the deadlock (no cycle involves T4; T3 simply also waits on T4, which is ordinary blocking, not deadlock, unless T4 also waits back on someone in the cycle).</details>

### 17.11 The "Explain It Simply" Challenge (A Powerful Interview Prep Technique)

For each concept below, practice explaining it in **under 30 seconds**, without jargon, as if to a smart non-technical stakeholder. This is exactly what distinguishes candidates who *understand* a concept from those who've merely *memorized* its definition.

1. Why do we need transactions at all?
2. What is a deadlock, in plain terms?
3. Why can't two people "safely" both check "is there at least one doctor on call" and both go home?
4. Why does a database sometimes say "please try again" instead of just doing what you asked?
5. Why shouldn't a checkout button call a slow payment provider while holding the database "locked"?

*(Model answers for all five are implicitly built from Sections 15.5, 15.7, 12.1, 9.x, and 5.8 — if you can explain each fluently without notes, you've internalized this Part.)*

### 17.12 Final Consolidated Cheat Sheet — The Whole of Part 6 in One Page

```
ACID: Atomicity (all-or-nothing, undo log) | Consistency (constraints) |
      Isolation (concurrency control mechanisms) | Durability (redo log + fsync before ack)

SCHEDULES: Serial ⊂ Strict ⊂ Cascadeless ⊂ Recoverable ⊂ All Schedules
           (Irrecoverable = forbidden, outside Recoverable)

SERIALIZABILITY: Conflict Serializable (precedence graph acyclic) ⊂ View Serializable (NP-Complete, blind writes)

ANOMALIES → MIN ISOLATION LEVEL TO PREVENT:
  Dirty Read        → Read Committed
  Non-Repeatable Read → Repeatable Read
  Phantom Read      → Serializable (or engine-specific gap locks)
  Write Skew        → Serializable ONLY (Snapshot Isolation does NOT prevent this)

LOCKING: S/X/U/IS/IX/SIX, Multiple Granularity Locking
2PL: Growing (acquire) → Shrinking (release) | guarantees serializability, NOT deadlock-freedom
  Basic (release anytime) < Strict (X held to commit) < Rigorous (ALL held to commit) < Conservative (all upfront, deadlock-free)

TIMESTAMP ORDERING: reject if TS(Ti) < W-ts(X) [read] or TS(Ti) < R-ts(X)/W-ts(X) [write]
  Thomas Write Rule: ignore (don't abort) if only the W-ts check fails
  Deadlock-free by construction; can suffer high abort rates under contention

OCC: Read (buffer writes) → Validate (check overlap w/ committed txns) → Write (apply or abort)
  Best for low contention; deadlock-free; wastes work on abort under high contention

MVCC: Readers never block writers, writers never block readers
  xmin/xmax version tags | Snapshot Isolation prevents everything EXCEPT write skew
  PostgreSQL: heap-stored versions + VACUUM | InnoDB/Oracle: undo-log reconstruction

DEADLOCKS: 4 conditions (Mutual Exclusion, Hold-and-Wait, No Preemption, Circular Wait)
  Wait-For Graph cycle = deadlock | Detection (industry standard) > Prevention (Resource Order, Wait-Die, Wound-Wait) > Avoidance (impractical)
  Deadlock ≠ Starvation ≠ Livelock

TCL: BEGIN/COMMIT/ROLLBACK, SAVEPOINT/RELEASE/ROLLBACK TO, SET TRANSACTION, SET CONSTRAINTS

DISTRIBUTED TXNS: 2PC (blocking risk on coordinator crash) | 3PC (reduces but doesn't eliminate) |
  XA (vendor-neutral 2PC standard) | SAGA (local txns + compensation, no blocking, eventual consistency, exposes intermediate state)

PERFORMANCE: shorten transactions, mitigate hot rows (shard/ledger), batch moderately,
  choose isolation level per-transaction, monitor long-running/idle txns and vacuum health
```
