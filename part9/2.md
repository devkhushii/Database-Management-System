# Part 9: Database Recovery, Logging & Durability
## Module 2: Types of Failures

> **Recap:** In Module 1, we established *why* recovery exists and the high-level workflow the DBMS follows. Now we zoom into the actual **causes** of failure — because a Recovery Manager can't design the right response until it knows precisely what it's responding to. Different failures demand fundamentally different recovery strategies, and mixing them up is a classic interview trap.

---

## 📍 Why Classify Failures at All?

Not all failures are equal. A single transaction quietly failing a constraint check is a non-event handled in microseconds. A meteor taking out a data center is a multi-day disaster recovery operation. If you use the same tool for both, you either massively over-engineer the common case or catastrophically under-prepare for the rare one.

So every serious DBMS — and every serious systems interview — categorizes failures along a **severity spectrum**:

```
LOW SEVERITY                                                    HIGH SEVERITY
────────────────────────────────────────────────────────────────────────────►

Transaction     System        Media/Disk       Catastrophic
Failure         Crash         Failure          Failure

(seconds,       (seconds to   (hours, needs    (days, needs
 auto-handled)   minutes,      backup restore)  full DR plan,
                 log-based)                     off-site data)
```

We'll now walk through each category in detail.

## 2.1 Transaction Failure

### What is it?

A **Transaction Failure** occurs when an individual transaction cannot complete successfully, even though the DBMS software, operating system, and hardware are all working perfectly fine. The failure is local to that one transaction.

### Causes

- **Logical errors:** e.g., a program tries to insert a duplicate primary key, or divide by zero in a computed column.
- **Constraint violations:** e.g., a `CHECK` constraint or foreign key constraint is violated.
- **Deadlocks:** Two or more transactions are waiting on each other's locks forever (covered in depth in Part 6 — Concurrency Control). The DBMS picks a "victim" transaction and aborts it.
- **Explicit application `ROLLBACK`:** The application logic itself decides to cancel the transaction (e.g., a validation check outside the DB fails).
- **Resource limits:** Running out of temporary sort space, exceeding a statement timeout, etc.

### Real-Life Analogy

Think of filling out a paper bank form at a counter. You start filling it in, then realize you wrote the wrong account number. You don't need to call the fire department or shut down the bank — you simply tear up *that one form* and start over. The bank itself, the counter, the staff — everything else keeps functioning normally.

### Recovery Strategy

- The Recovery Manager performs a **local undo** — using the log records generated by that specific transaction, it reverses only *its* changes.
- No system-wide restart or downtime is needed.
- This is the cheapest and fastest of all recovery types, often completing in microseconds to milliseconds.

### Example

```sql
BEGIN TRANSACTION;
UPDATE inventory SET stock = stock - 10 WHERE product_id = 101; -- succeeds
UPDATE inventory SET stock = stock - 5 WHERE product_id = 999;  -- FAILS: no such product_id
-- DBMS automatically triggers a transaction failure here
ROLLBACK; -- first UPDATE is undone; inventory for 101 reverts
```

## 2.2 System Crash

### What is it?

A **System Crash** (also called a **soft crash**) happens when the DBMS process, operating system, or entire machine stops functioning unexpectedly — but critically, the **persistent storage (disk) remains intact and uncorrupted**. Only the contents of **volatile memory (RAM)** — including the buffer pool — are lost.

### Causes

- Operating system kernel panic / Blue Screen of Death.
- DBMS process crash due to a software bug (e.g., segmentation fault).
- Power failure to the machine (though sustained power failure has its own nuances — see Section 2.6).
- Someone accidentally running `kill -9` on the database process.
- Virtual machine or container being forcibly terminated.

### Real-Life Analogy

This is exactly like the laptop battery dying while writing an essay, from Module 1. The hard drive itself is fine — nothing is scratched or destroyed. It's only the *unsaved, in-progress* work sitting in RAM that vanishes.

### Recovery Strategy

This is where the full machinery from Module 1's "Recovery Workflow" kicks in:

1. On restart, the DBMS detects the crash (missing clean-shutdown marker).
2. It reads the persistent log (which survived, because logs are always flushed to disk ahead of data — the WAL rule from Module 4).
3. It performs the **Analysis, Redo, and Undo** passes (fully detailed in Module 7 — ARIES).
4. Committed transactions whose data pages hadn't yet reached disk are **redone**.
5. Uncommitted transactions are **undone**.

### Why System Crash is "The Main Event" of Recovery Theory

Almost the entirety of WAL, ARIES, and checkpoint theory (Modules 4, 6, 7) exists specifically to handle system crashes efficiently and correctly. It's the most common serious failure type in production, and it's fully automatic — no human decision-making or backup tapes required, just the transaction log.

## 2.3 Process Failure

### What is it?

A **Process Failure** is a narrower case, closely related to system crash but scoped specifically to **one client connection or one backend process/thread** dying — while the rest of the DBMS server continues running normally for everyone else.

### Causes

- A specific client's network connection drops mid-transaction.
- A single backend worker process (e.g., a PostgreSQL backend process handling one client) crashes due to a bug or resource exhaustion (like running out of memory for that one connection).
- An application server times out and forcibly disconnects.

### Real-Life Analogy

Imagine a large call center. One customer's phone call drops mid-conversation because of a bad signal on *their* end. The call center itself — the building, the other agents, the phone system — is completely unaffected. Only that one call needs to be handled (the agent notes the call ended abnormally and doesn't act on an incomplete instruction).

### Recovery Strategy

- The DBMS detects the terminated connection/process.
- Any transaction that process was running, if not committed, is **aborted and undone** — treated much like a transaction failure, scoped to just that session.
- Other active connections and transactions are completely unaffected.
- No system-wide restart is needed; this is handled continuously as a routine background responsibility of the DBMS.

| Aspect | Transaction Failure | Process Failure |
|---|---|---|
| Scope | One transaction | One connection/session (may span transaction boundaries) |
| Cause | Logic/constraint issue | Client disconnect / worker crash |
| Rest of system affected? | No | No |
| Typical resolution | Automatic rollback | Automatic rollback + connection cleanup |

## 2.4 Media Failure (Disk Failure)

### What is it?

A **Media Failure**, also called **Disk Failure**, occurs when the actual persistent storage device — the hard disk drive (HDD), solid-state drive (SSD), or storage array — is physically or logically damaged, such that data on it becomes **partially or completely unreadable**.

This is fundamentally different and more severe than a system crash: in a system crash, disk data is *safe*; in a media failure, disk data itself is *compromised*.

### Causes

- Physical disk head crash (HDDs) or NAND cell wear-out (SSDs).
- Firmware bugs in the storage controller.
- Filesystem corruption.
- Faulty RAID controller or cabling causing silent data corruption.
- Bit rot (extremely rare, gradual degradation of stored bits over long time periods).

### Real-Life Analogy

This is like your essay's saved file itself being on a USB drive that then gets physically snapped in half. Autosave and undo history don't help you anymore — the storage medium that held everything is gone. Your only hope is a **backup copy** stored somewhere else entirely.

### Recovery Strategy

Because the log itself may live on the *same* failed disk (a critical design consideration!), ordinary log-based recovery (used for system crashes) is often **not sufficient or not even possible**. Media failure recovery instead relies on:

1. **Restoring the most recent full/incremental backup** (Module 9) onto new, healthy storage.
2. **Replaying archived transaction logs** since that backup was taken, to bring the database as close as possible to the moment of failure — this is **Point-in-Time Recovery (PITR)**, previewed in Module 9 and covered again in Module 11 for PostgreSQL specifically.
3. In highly available setups, **failing over** to a replica that has its own independent, healthy copy of the data (a concept expanded in Module 10 — Disaster Recovery, and fully in Part 10's distributed systems coverage).

> ⚠️ **Best Practice Callout:** This is precisely why production databases are configured to write logs and archived logs to **physically separate storage** from the main data files — so that a single disk failure doesn't take out both the data *and* the means to recover it.

## 2.5 Power Failure

### What is it?

A **Power Failure** is the sudden loss of electrical power to the machine(s) running the database, without any advance warning or graceful shutdown sequence.

### Why It's Treated as Its Own Category

Power failure is technically a *cause*, and it typically *results in* a system crash (Section 2.2) — but it deserves its own discussion because:

- It affects **everything at once**: RAM, CPU, and potentially even in-flight disk writes (a write that was only half-completed to disk when power died can leave a **torn page** — a page that's part-old-content, part-new-content, part-garbage).
- It can affect multiple machines simultaneously if they share a power source (e.g., an entire server rack or data center).
- It has unique mitigation strategies distinct from ordinary crash recovery.

### The "Torn Page" Problem

Disk writes typically happen in fixed blocks (e.g., 512 bytes or 4 KB sectors), while a database page might be 8 KB or 16 KB. If power dies mid-write, only *some* of the sectors that make up that page might have been updated — resulting in a page that's neither fully old nor fully new. This is a subtle and dangerous edge case that specific engine mechanisms are built to defend against (for example, InnoDB's **Doublewrite Buffer**, which we cover in full in Module 11).

### Recovery Strategy

- Same fundamental approach as system crash recovery (Analysis/Redo/Undo via the log).
- Additional defenses against torn pages: checksums on pages, doublewrite buffers (InnoDB), or full-page image logging on first modification after a checkpoint (PostgreSQL's `full_page_writes` setting).
- Data centers mitigate the *frequency* of power failure with Uninterruptible Power Supplies (UPS) and redundant power feeds — but recovery mechanisms must still assume it can happen.

## 2.6 Network Failure

### What is it?

A **Network Failure** occurs when communication between components — client and server, or server and a replica/distributed node — is disrupted, without necessarily any actual data corruption or process crash occurring.

### Causes

- Cable disconnection or switch failure.
- DNS resolution failure.
- Network partition in a distributed/clustered database setup (a deep topic in Part 10).
- Firewall misconfiguration blocking traffic mid-session.

### Real-Life Analogy

Imagine mailing a letter, but the postal truck breaks down halfway and the letter never arrives — yet the letter itself (if recovered) is perfectly intact, and you (the sender) are perfectly fine too. The problem is purely in the *path between* sender and receiver.

### Recovery Strategy

- For a simple client-server disconnection: treated like a process failure (Section 2.3) — the in-flight transaction is aborted and undone if not committed.
- For distributed/replicated systems: network failures can cause **split-brain** scenarios (two nodes both believing they're the authoritative primary) — these require consensus protocols and quorum-based recovery, which is a major topic reserved for **Part 10 (Distributed Databases)**.
- The critical design principle: a network failure should **never**, by itself, corrupt data — it should only ever result in incomplete communication that the retry/recovery logic can safely clean up.

---

## 2.7 Software Failure

### What is it?

A **Software Failure** is a bug or defect in the DBMS engine itself, the operating system, or a dependent library, causing incorrect behavior, a crash, or (in the worst case) silent data corruption.

### Causes

- A bug in the DBMS's own code (yes, even production-grade engines like PostgreSQL and MySQL have had recovery-related bugs over the years — this is precisely why extensive testing of the recovery path is a huge part of database engineering).
- Operating system bugs affecting filesystem behavior.
- Faulty third-party extensions or plugins.
- Incompatible version upgrades introducing regressions.

### Recovery Strategy

- If it causes a crash: handled like a system crash (Section 2.2).
- If it causes silent corruption (much scarier — no crash, just wrong data): this is where **checksums** (Module 3), **backup verification** (Module 9), and rigorous **testing/QA of the recovery path itself** become critical.
- Vendors typically respond to confirmed software failures with patches; DBAs mitigate risk by staying on stable, well-tested versions for critical systems and thoroughly testing upgrades before production rollout.

---

## 2.8 Hardware Failure

### What is it?

A broader category than media failure alone — **Hardware Failure** covers any physical component malfunction: CPU, RAM (bit flips), motherboard, power supply, network card, or storage.

### Causes

- Manufacturing defects.
- Component aging/wear.
- Overheating.
- Cosmic ray-induced bit flips in RAM (rare but real — this is why servers use **ECC RAM**, which can detect and correct single-bit memory errors).

### Recovery Strategy

- Depends entirely on *which* component failed:
  - CPU/RAM failure → typically manifests as a system crash → standard crash recovery.
  - Storage failure → media failure recovery (Section 2.4).
  - Network card failure → network failure handling (Section 2.6).
- Redundancy is the primary defense: RAID for disks, ECC for memory, redundant power supplies, and — at the highest level — full server/data-center redundancy (Module 10).

## 2.9 Human Error

### What is it?

**Human Error** — often underestimated, yet one of the **most common real-world causes of serious data loss** — occurs when a person (developer, DBA, or operator) performs a mistaken, destructive action.

### Causes

- Accidentally running `DELETE FROM orders;` without a `WHERE` clause.
- Dropping the wrong table or even the wrong database (common when production and staging environment names look similar).
- Misconfigured scripts run against production instead of a test environment.
- Granting excessive permissions leading to accidental or malicious changes.

### Real-Life Analogy

This is the database equivalent of highlighting your entire essay and hitting "delete" instead of "copy." The computer, disk, and software all worked *exactly as instructed* — the instruction itself was the mistake.

### Why Ordinary Crash Recovery Doesn't Help Here

This is a crucial and frequently tested interview point:

> **A destructive but successfully committed transaction is, from the recovery system's point of view, indistinguishable from a correct one.**

If you `COMMIT` a `DROP TABLE`, the WAL/redo log faithfully guarantees that drop is durable — recovery will happily *redo* it after a crash, not undo it! Crash recovery guarantees the database matches what was *instructed*, not what was *intended*.

### Recovery Strategy

- **Point-in-Time Recovery (PITR):** Restore a backup and replay the log only up to the moment *just before* the mistaken command (Module 9).
- **Flashback features** (Oracle) or similar time-travel query capabilities that let you view/recover data as it existed before the error, without a full restore.
- **Soft deletes / audit logging** at the application layer as a preventative measure.
- **Access controls and review processes** (e.g., requiring a second engineer to approve destructive production scripts) as the actual best defense — prevention over cure.

| Failure Type | Can Standard Crash Recovery (Redo/Undo) Fix It? |
|---|---|
| Transaction Failure | ✅ Yes (undo) |
| System Crash | ✅ Yes (redo + undo) |
| Media Failure | ❌ No — needs backup restore |
| Human Error (committed mistake) | ❌ No — needs PITR/backup, not crash recovery |

---

## 2.10 Catastrophic Failure

### What is it?

A **Catastrophic Failure** is total, often permanent, destruction or unavailability of the entire primary system — including its storage, logs, and often the physical facility itself.

### Causes

- Natural disasters: fire, flood, earthquake.
- Data center-wide power grid failure with no working backup generators.
- Large-scale cyberattacks (e.g., ransomware encrypting all accessible storage, including local backups).
- Extreme, simultaneous multi-disk failure beyond what RAID redundancy can tolerate.

### Recovery Strategy

This is the domain of full **Disaster Recovery (DR)** planning, covered comprehensively in Module 10:

- **Off-site / geo-redundant backups:** Backups must exist in a *physically separate location*, or they'll be destroyed along with the primary system.
- **Geo-replication:** A live standby copy of the database running in a different region entirely.
- **Failover procedures:** Pre-planned, often automated, processes to redirect traffic to the surviving copy.
- **Business Continuity Planning:** Beyond just the database — the entire organization's ability to keep operating.

### Real-Life Analogy

If a fire burns down your house, your backed-up essay saved on a USB drive that was *also in the house* is gone too. Only a copy stored somewhere else entirely — a cloud drive, a friend's house, a bank vault — survives. Catastrophic failure recovery is built entirely around this principle: **never let your only backup share a blast radius with your primary system.**

## 2.11 Master Comparison Table — All Failure Types

| Failure Type | Scope | Disk Data Intact? | Typical Cause | Recovery Mechanism | Downtime |
|---|---|---|---|---|---|
| Transaction Failure | 1 transaction | ✅ Yes | Logic/constraint error, deadlock | Local undo | None |
| Process Failure | 1 session | ✅ Yes | Client disconnect, worker crash | Session-scoped undo | None |
| System Crash | Whole DBMS instance | ✅ Yes | OS crash, power blip, `kill -9` | Log-based redo/undo (ARIES) | Seconds–minutes |
| Media/Disk Failure | Storage device | ❌ No | Physical/logical disk damage | Backup restore + log replay | Minutes–hours |
| Power Failure | Whole machine(s) | ⚠️ Usually, but torn pages possible | Electrical outage | Crash recovery + torn-page defenses | Seconds–minutes |
| Network Failure | Connections/cluster links | ✅ Yes | Cable, DNS, partition | Session cleanup / consensus protocols | Seconds–minutes |
| Software Failure | Varies | ⚠️ Depends on bug | DBMS/OS/library bug | Crash recovery or patching + verification | Varies |
| Hardware Failure | Varies (CPU/RAM/disk/NIC) | ⚠️ Depends on component | Physical component defect | Redundancy + component-specific recovery | Varies |
| Human Error | Varies, often whole tables/DBs | ✅ Yes (but wrong data) | Mistaken destructive command | PITR / Flashback / backup restore | Minutes–hours |
| Catastrophic Failure | Entire site/facility | ❌ No | Disaster, large-scale attack | Off-site backup + geo-failover (DR plan) | Hours–days |

## 2.12 Industry Usage Notes

- **Banking systems** design explicitly around Media Failure and Catastrophic Failure scenarios because regulatory requirements often mandate near-zero data loss (RPO close to zero) — covered with real numbers in Module 10.
- **Cloud-managed databases** (Amazon RDS, Google Cloud SQL, Azure SQL) automate most system-crash and media-failure recovery, but **human error remains squarely the customer's responsibility** — cloud providers don't stop you from running a bad `DELETE`.
- **Airline reservation systems** must handle process and network failures gracefully because a huge volume of concurrent, geographically distributed connections is the norm — a single flaky connection must never corrupt a shared seat map.

---

## 2.13 Performance Implications

- Designing defenses against *rare* failures (media, catastrophic) has an ongoing performance cost even when nothing is failing — e.g., synchronous replication to a remote site adds latency to every commit, in exchange for surviving catastrophic failure with zero data loss.
- The more failure types a system defends against synchronously (before acknowledging commit), the higher the latency per transaction. This is the central trade-off explored further in Module 12.

---

## 2.14 Best Practices

- Match your recovery investment to the actual failure types your business cares about — a small internal analytics tool doesn't need geo-redundant DR; a payments platform does.
- Always assume logs and backups can be destroyed alongside primary data unless you've deliberately isolated them (different disk, different rack, different region).
- Build guardrails against human error (e.g., requiring `WHERE` clauses, confirmation prompts, staged rollouts) — it is statistically one of the most common real-world causes of serious incidents.
- Regularly *test* recovery from each failure type — untested recovery procedures routinely fail when actually needed.

## 2.15 Common Mistakes

- Assuming RAID protects against everything — RAID protects against certain *disk* hardware failures, not against human error, software bugs, or catastrophic site loss.
- Treating "we have backups" as equivalent to "we have disaster recovery" — a backup with no tested restore procedure and no off-site copy is a false sense of security.
- Failing to distinguish committed human error from an in-flight crash — trying to use ordinary crash recovery to fix a bad `DROP TABLE` will not work, because that drop was durably committed.

## 2.16 Edge Cases

- A failure can **cascade**: a power failure can cause a system crash, which reveals a latent software bug in the recovery code itself, which then causes further corruption. Real recovery engineering must consider these chains, not just isolated single failures.
- **Silent corruption** (from software or hardware failure) is the most dangerous edge case of all, because there's no crash to trigger recovery — the corrupted data is simply queried and trusted. This is why checksums (Module 3) and regular backup verification (Module 9) exist as safety nets.

---

## 2.17 Chapter Summary

- Failures range across a severity spectrum: from **Transaction Failure** (cheapest, automatic, instant) up to **Catastrophic Failure** (most severe, requires full disaster recovery planning).
- **Transaction, Process, and System failures** are typically handled automatically via **log-based redo/undo**, with disk data remaining intact.
- **Media, Human Error, and Catastrophic failures** typically require **backup restoration and/or Point-in-Time Recovery**, because the log-based approach alone is insufficient or the log itself is unavailable/compromised.
- **Human Error is uniquely tricky**: a committed mistake looks identical to a committed correct action from the recovery system's point of view, so PITR/Flashback tools exist specifically to address it.
- Real production systems must defend against **combinations and cascades** of these failure types, not just each in isolation.

## 2.20 MCQs (with Answers)

**Q1.** Which failure type is scoped to a single transaction and resolved without any system-wide impact?
A) System Crash
B) Media Failure
C) Transaction Failure
D) Catastrophic Failure

**Answer: C**

**Q2.** A committed `DELETE` executed by mistake is best recovered using:
A) Standard crash undo
B) Point-in-Time Recovery
C) RAID rebuild
D) Doing nothing, it self-corrects

**Answer: B**

**Q3.** ECC RAM primarily protects against:
A) Disk media failure
B) Bit flips in memory (a hardware failure)
C) Human error
D) Network partition

**Answer: B**

**Q4.** Which of the following is true about Catastrophic Failure recovery?
A) It relies solely on the local transaction log
B) It requires off-site/geo-redundant backups
C) It never involves any downtime
D) It is identical to system crash recovery

**Answer: B**
