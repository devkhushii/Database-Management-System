# Part 10 — Database Internals & Storage Engine Architecture

## Module 12: Database File Structure

> **Recap:** Modules 2, 3, and 4 mentioned specific files (`ib_logfile0`, `pg_wal`, `.ibd` files) as they came up. This module maps the **complete filesystem layout** of both engines — every file type, its purpose, and how they relate to the Tablespace → Segment → Extent → Page hierarchy first previewed in Module 2.

---

### 12.0 Why This Module Exists

Understanding on-disk file layout is what turns database administration from guesswork into precise diagnosis — knowing exactly which file grew, why, and what it's for is essential for real production incident response (disk full alerts, backup/restore procedures, corruption recovery) and is frequently probed directly in operationally-focused interviews.

---

### 12.1 The Physical Hierarchy: Tablespace → Segment → Extent → Page

**Recap and formalization** of the hierarchy previewed in Module 2, Section 2.8, now presented as the unifying structure for this entire module:

```
Tablespace  (a logical grouping of physical storage, often ≈ one or more OS files)
    │
    ▼
  Segment  (all the space used by ONE database object, e.g., one table or one index)
    │
    ▼
  Extent   (a group of contiguous pages, allocated/freed as a unit — reduces
            fragmentation and per-allocation bookkeeping overhead)
    │
    ▼
   Page    (the fundamental fixed-size I/O unit — Module 2's slotted page)
```

**Why this hierarchy exists at all — the core motivation:** Allocating and freeing individual pages one at a time, for every insert/growth event, would create excessive bookkeeping overhead and fragmentation (many small, scattered free-space entries instead of a few large contiguous ones). Grouping pages into **extents** (typically a fixed number of contiguous pages, e.g., InnoDB's 64-page/1MB extents) lets the engine allocate and track space in larger, more efficient chunks, while **segments** group all the extents belonging to one logical object (so a table's data and a table's indexes, being logically distinct objects, get their own separate segments, tracked and grown independently).

**Interview importance:** ⭐⭐⭐⭐ This hierarchy, stated cleanly, is the backbone answer to "how does physical storage relate to logical tables/indexes?"

### 12.2 PostgreSQL File Layout — Complete Reference

**Top-level data directory structure** (`$PGDATA`):

```
$PGDATA/
├── base/                  ← actual table/index data, one subdirectory per database
│   └── <db_oid>/
│       ├── <relfilenode>       ← a table's or index's data file (one per relation,
│       │                          split into 1GB segments: <relfilenode>, .1, .2, ...)
│       ├── <relfilenode>_fsm   ← Free Space Map (Module 2, 3) for that relation
│       └── <relfilenode>_vm    ← Visibility Map (Module 3) for that relation
├── pg_wal/                ← Write-Ahead Log segment files (16MB each by default)
├── pg_xact/                ← Commit log (CLOG) — tracks commit/abort status per XID
├── pg_multixact/           ← Multi-transaction status (for shared row locks, advanced)
├── global/                 ← cluster-wide catalog tables (shared across all databases)
├── pg_tblspc/               ← symlinks to any user-defined tablespace locations
├── postgresql.conf          ← main configuration file
├── pg_hba.conf              ← host-based authentication (client connection access rules)
└── PG_VERSION                ← a plain text file recording the data directory's format version
```

**Key facts worth memorizing:**

- **Relation files are split at 1GB boundaries** purely to avoid historical OS maximum-file-size limitations — `<relfilenode>` holds the first 1GB, `<relfilenode>.1` the next, and so on; this is an implementation detail, not a logical partitioning feature.
- **`relfilenode` vs. table OID:** A table's identity (`OID` in `pg_class`) is generally stable, but its **relfilenode** (which determines the actual filename on disk) can *change* — notably during `VACUUM FULL`, `TRUNCATE`, or certain `ALTER TABLE` operations that rewrite the table — because those operations build an entirely new physical file and then swap it in, rather than modifying the existing file in place. This is a commonly-tested subtlety: OID identity and physical file identity are related but distinct.
- **`pg_wal`** (renamed from `pg_xlog` in Postgres 10, a notable historical renaming worth knowing if you encounter older documentation) holds WAL segment files, each a fixed 16MB by default, named as a 24-character hexadecimal sequence number.
- **`pg_xact`** (renamed from `pg_clog` in Postgres 10, same renaming wave as `pg_wal`) — the commit log — is a compact bitmap-like structure recording, for every transaction ID, whether it committed, aborted, or is still in progress; this is consulted heavily during MVCC visibility checks (Module 5) as part of determining whether a given `xmin`/`xmax` transaction actually committed.

### 12.3 MySQL/InnoDB File Layout — Complete Reference

**Typical data directory structure** (`datadir`):

```
datadir/
├── ibdata1                    ← system tablespace (legacy: could hold everything;
│                                  modern default: mainly holds the change buffer,
│                                  doublewrite buffer, and some system data)
├── ib_logfile0, ib_logfile1    ← Redo Log files (older versions; capacity-based
│    (or #innodb_redo/ in 8.0.30+)  files in newer versions instead of fixed count)
├── undo_001, undo_002, ...      ← dedicated Undo Tablespaces (8.0+; separated out
│                                   from the system tablespace for easier management)
├── <database_name>/
│   └── <table_name>.ibd          ← one file-per-table tablespace (when
│                                    innodb_file_per_table=ON, the modern default)
├── #innodb_temp/                 ← session temporary tablespaces (for internal
│                                    temp tables used during query execution)
├── binlog.000001, binlog.000002  ← MySQL's Binary Log (server-level, not InnoDB-
│    ...                             specific — records logical statement/row
│                                    changes, used for replication and point-in-time
│                                    recovery; DISTINCT from the InnoDB Redo Log)
├── my.cnf / my.ini                ← main configuration file
└── mysql/                          ← the mysql system database, holding the unified
                                       Data Dictionary (Module 11), user accounts, etc.
```

**Key facts worth memorizing:**

- **Redo Log vs. Binary Log — a critical, commonly-confused distinction:** The **Redo Log** (`ib_logfile*`) is InnoDB-storage-engine-internal, physical (page-level), and exists purely for **crash recovery** of InnoDB's own data. The **Binary Log** (`binlog.*`) is a MySQL-server-level (not storage-engine-specific) log recording logical statement or row-level changes, used primarily for **replication** and **point-in-time recovery** (restoring to an exact moment by replaying binlog events after a base backup). A single transaction commit, under default durable settings, actually involves coordinated writes to *both* logs (via MySQL's internal two-phase commit protocol between the binlog and the InnoDB redo log, ensuring both stay consistent with each other even across a crash) — a genuinely important, frequently-tested distinction.
- **`innodb_file_per_table` (modern default: ON):** Each table gets its own `.ibd` file, meaning `TRUNCATE TABLE` or `DROP TABLE` can immediately reclaim disk space (deleting a file), unlike the legacy shared `ibdata1`-holds-everything model, where space freed within the shared file wasn't necessarily returned to the OS.
- **Undo Tablespaces (8.0+):** Previously (older MySQL versions) undo logs lived inside the shared system tablespace, making them awkward to shrink after unusual growth (e.g., from a very long-running transaction, Module 5). Dedicated undo tablespace files can be more easily managed, truncated, and monitored independently.

### 12.4 WAL Files / Redo Logs — Comparative Deep Dive (File-Level View)

| Aspect | PostgreSQL `pg_wal` | InnoDB Redo Log |
|---|---|---|
| File naming/structure | Sequentially-numbered 16MB segment files (grows by adding new segment files) | Fixed-capacity circular set of files (or a capacity-managed pool in 8.0.30+), reused in place rather than growing indefinitely |
| Growth behavior | New segments created as needed (up to `max_wal_size` guidance, with older segments recycled/removed after being no longer needed for crash recovery or replication) | Fixed total capacity (`innodb_redo_log_capacity`); wraps around circularly, requiring checkpoints to keep pace so old records aren't overwritten before their corresponding data pages are flushed |
| Retention beyond crash recovery needs | Can be retained longer for replication (`pg_wal` segments needed by replication slots) or archiving (`archive_command` for continuous backup/PITR) | Binary Log (a separate file set entirely) serves the replication/PITR role; the Redo Log itself is not typically retained beyond InnoDB's own crash-recovery needs |

**Why this structural difference exists:** Postgres deliberately designed WAL to serve **both** crash recovery **and** replication/archiving from the same log stream — a single unified log with multiple consumers. MySQL instead **separates** these concerns into two distinct logs (Redo Log for storage-engine crash recovery, Binary Log for server-level replication/PITR) — a different but equally valid architectural choice, with its own trade-off (the two-phase commit coordination overhead needed to keep them consistent, mentioned above).

**Interview importance:** ⭐⭐⭐⭐⭐ "Why does MySQL have both a Redo Log and a Binary Log, and what's the difference?" is a very commonly-asked, high-signal question specifically because it's frequently confused.

### 12.5 Control Files

**What is it?** A small, critical file recording essential metadata *about the database instance itself* — not table data, but facts needed to even begin the process of starting up and validating the instance's consistency.

**PostgreSQL's `pg_control`** (found in `$PGDATA/global/pg_control`): Records the current WAL position, the timestamp/state of the last checkpoint, the database's catalog version, and various critical consistency-check fields. On startup, Postgres reads this file *first*, before anything else, to determine whether the previous shutdown was clean or whether crash recovery (replaying WAL from the last recorded checkpoint) is needed.

**Oracle's control files** (mentioned for comparative completeness, as Oracle is referenced throughout this handbook's comparison tables): Track the physical structure of the database (which data files, redo log files belong to it), critical for Oracle's more elaborate multi-file, multi-tablespace architecture — typically maintained as multiple redundant copies specifically because losing all control files is catastrophic (though recoverable via advanced procedures).

**Why this file is so small yet so critical:** It's read and consulted first, before larger structures are even opened — corruption of this tiny file can render an otherwise perfectly intact multi-terabyte database instance unable to start cleanly (though various recovery procedures typically exist as a last resort in every major engine, precisely because this file's criticality is well understood).

**Interview importance:** ⭐⭐⭐ Good for demonstrating awareness that a very small file can be the single most operationally critical piece of a database instance's on-disk footprint.

### 12.6 Configuration Files

**PostgreSQL:** `postgresql.conf` (the main tunable-parameters file — `shared_buffers`, `work_mem`, `checkpoint_timeout`, and every setting discussed across this Part), `pg_hba.conf` (client authentication rules — which hosts/users/databases can connect and via what authentication method), `pg_ident.conf` (user name mapping for certain authentication methods).

**MySQL:** `my.cnf` (Linux/Unix) or `my.ini` (Windows) — holds all the `innodb_*` and general server settings referenced throughout Modules 3, 4, 6, and 7.

**Operational note relevant to interviews:** Many settings in both engines require a full server **restart** to take effect (e.g., `shared_buffers` in Postgres, `innodb_buffer_pool_size` resize behavior historically), while others can be changed dynamically at runtime (`SET` in Postgres for session/some system-wide settings; `SET GLOBAL` in MySQL) — knowing which category a given setting falls into is a real, practically useful piece of operational knowledge.

---

### 12.7 Temporary Files

**What is it?** Files created transiently during query execution or maintenance operations, specifically to hold data that has **spilled to disk** (Module 7) because it exceeded its allotted in-memory budget — sorts, hash joins/aggregates exceeding `work_mem`/`sort_buffer_size`, or `CREATE INDEX`/`VACUUM` operations exceeding `maintenance_work_mem`.

**PostgreSQL:** Stored under `$PGDATA/base/pgsql_tmp/` (or a configured `temp_tablespaces` location) by default, named distinctively (e.g., `pgsql_tmp<pid>.<counter>`), and automatically cleaned up when the operation completes or the connection closes.

**MySQL/InnoDB:** Session temporary tablespaces (`#innodb_temp/` directory, Section 12.3) — a dedicated, separate tablespace area specifically for internal temporary tables created during query execution, distinct from user-created explicit `CREATE TEMPORARY TABLE` tables (which, depending on version/configuration, may also use this same mechanism).

**Why this matters operationally:** A sudden, unexpected spike in disk usage under `pgsql_tmp`/`#innodb_temp` during a specific time window is one of the most direct, actionable pieces of evidence that a query is spilling heavily to disk (Module 7) — monitoring these directories' size over time is a genuinely useful, concrete diagnostic technique, not just theoretical knowledge.

### 12.8 Segments and Extents (Formalized, Both Engines)

**Segment (recap, formalized):** The complete set of storage allocated to *one* database object (one table, or one index) — in Postgres, this maps fairly directly to "the relation's data file(s)" (Section 12.2); in InnoDB, a table's clustered index data and each of its secondary indexes are each their own distinct segment(s) within the relevant tablespace, explicitly tracked as such internally.

**Extent (recap, formalized):**
- **InnoDB:** A fixed-size group of 64 consecutive pages (1MB, assuming the default 16KB page size) — the fundamental unit of space allocation *within* a segment, striking a balance between allocation granularity (not too coarse, avoiding excessive waste) and bookkeeping overhead (not too fine, avoiding excessive per-page allocation tracking cost).
- **PostgreSQL:** Does not use an explicit "extent" concept in quite the same formally-named way — Postgres's relation files simply grow page-by-page (or in somewhat larger increments in some code paths) as needed, with the Free Space Map (Module 2) handling space-tracking bookkeeping instead of a formal extent-allocation hierarchy. This is a genuine structural difference worth being able to state directly if asked to compare the two engines' physical allocation strategies.

**Interview importance:** ⭐⭐⭐ Knowing that InnoDB has an explicit extent concept while Postgres does not (relying instead on its FSM) is a solid differentiator fact.

### 12.9 A Complete "Where Does X Live On Disk?" Reference Table

| What | PostgreSQL Location | InnoDB Location |
|---|---|---|
| Table/index data | `base/<db_oid>/<relfilenode>[.N]` | `<db>/<table>.ibd` (file-per-table) or `ibdata1` (system tablespace) |
| Free space tracking | `<relfilenode>_fsm` | Extent/segment bookkeeping within the tablespace itself |
| Visibility tracking | `<relfilenode>_vm` | N/A (no direct InnoDB equivalent — MVCC handled via undo log instead, Module 5) |
| Write-ahead/redo log | `pg_wal/` | `ib_logfile*` or `#innodb_redo/` |
| Undo/rollback data | In-heap (no separate file — old versions live alongside current ones, Module 5) | `undo_001`, `undo_002`, ... (dedicated Undo Tablespaces, 8.0+) |
| Commit status tracking | `pg_xact/` (formerly `pg_clog`) | Encoded within row/undo metadata (`DB_TRX_ID`), no separate dedicated commit-status file structure in the same explicit sense |
| Cluster-wide/shared catalog | `global/` | `mysql/` system database (Data Dictionary, Module 11) |
| Temporary spill files | `base/pgsql_tmp/` | `#innodb_temp/` |
| Configuration | `postgresql.conf`, `pg_hba.conf` | `my.cnf` / `my.ini` |
| Startup/consistency control | `global/pg_control` | Distributed across redo log headers + Data Dictionary state (no single, identically-scoped "control file" concept in InnoDB) |
| Replication/point-in-time-recovery log | `pg_wal/` (dual-purpose, also serves crash recovery) | `binlog.*` (separate from Redo Log) |

**Interview importance:** ⭐⭐⭐⭐⭐ This table, memorized, is an extremely strong "rapid-fire file location" reference — exactly the kind of thing a strong operational interview answer draws on fluently.

### 12.10 Advantages, Disadvantages, Best Practices

**Advantages of file-per-object / segment-based organization (as opposed to one giant monolithic file for everything):**
- Enables independent backup, monitoring, and (for `innodb_file_per_table`) space reclamation per table
- Localizes corruption risk — a single damaged file more often affects one object rather than the entire instance (though this benefit has limits, especially for genuinely shared structures like the system tablespace/catalog)

**Disadvantages:**
- More files to manage operationally — filesystem-level overhead (inode usage, `ls`/backup tooling performance) can become genuinely relevant at very large table counts (thousands of tables × multiple files each)
- Separate log files for distinct purposes (Redo Log vs. Binary Log in MySQL) require careful coordination (the two-phase commit protocol, Section 12.4) to avoid consistency gaps — added complexity compared to a single unified log

**Best practices:**
- Monitor `pg_wal`/Redo Log/Binary Log directory sizes as first-class operational metrics — unbounded growth in any of these is a strong, specific signal (e.g., a stuck replication slot preventing WAL cleanup in Postgres; binlog retention misconfiguration in MySQL)
- Understand which configuration changes require a restart vs. which can be applied live, to plan maintenance windows accurately
- For Postgres specifically, remember that `relfilenode` can change independently of a table's OID — don't assume a captured filename reference remains valid indefinitely across operations like `VACUUM FULL`

**Common mistakes:**
- Confusing InnoDB's Redo Log with the Binary Log (a very common, easy-to-make error, given both are "logs" involved in durability/recovery-adjacent concerns) — remember: Redo Log = storage-engine crash recovery; Binary Log = server-level replication/PITR
- Assuming freeing space within a database (e.g., after large deletes) automatically shrinks on-disk file sizes — as covered in Modules 3 and 9, this is often not true without an explicit rebuild/compaction operation (`VACUUM FULL`, `OPTIMIZE TABLE`)

### 12.11 Chapter Summary

- Physical storage follows a **Tablespace → Segment → Extent → Page** hierarchy, balancing allocation efficiency against bookkeeping overhead.
- PostgreSQL's data directory (`$PGDATA`) organizes table/index data under `base/`, WAL under `pg_wal/`, commit status under `pg_xact/`, with relation files split at 1GB boundaries and a `relfilenode` that can change independently of a table's stable OID.
- InnoDB's data directory holds per-table `.ibd` files (with `innodb_file_per_table` ON), Redo Log files (`ib_logfile*`), dedicated Undo Tablespaces (8.0+), and — critically distinct — the server-level Binary Log for replication/PITR.
- The **Redo Log vs. Binary Log** distinction in MySQL (storage-engine crash recovery vs. server-level replication/point-in-time recovery) is one of the most commonly confused, high-value facts in this module.
- **Control files** (`pg_control`) are tiny but critical — read first at startup to determine whether crash recovery is needed.
- **Temporary spill files** (`pgsql_tmp/`, `#innodb_temp/`) provide direct, monitorable evidence of Module 7's disk-spill behavior in practice.

### 12.12 Cheat Sheet

```
Hierarchy: Tablespace → Segment (one object) → Extent (page group) → Page

PostgreSQL ($PGDATA):
  base/<db_oid>/<relfilenode>[.N]  → table/index data (1GB segments)
  <relfilenode>_fsm / _vm           → Free Space Map / Visibility Map
  pg_wal/                            → WAL segments (16MB each)
  pg_xact/                           → commit status (formerly pg_clog)
  global/pg_control                  → tiny, critical, read FIRST at startup
  base/pgsql_tmp/                    → disk-spill temp files

InnoDB (datadir):
  <db>/<table>.ibd        → per-table data (innodb_file_per_table=ON, default)
  ibdata1                  → system tablespace (change buffer, doublewrite, etc.)
  ib_logfile* / #innodb_redo/  → Redo Log (storage-engine crash recovery ONLY)
  undo_001, undo_002...     → dedicated Undo Tablespaces (8.0+)
  binlog.*                    → Binary Log (SEPARATE: replication/PITR, NOT crash recovery)
  #innodb_temp/                → disk-spill temp files
  mysql/                        → Data Dictionary (Module 11)

KEY GOTCHA: Redo Log ≠ Binary Log
  Redo Log   → InnoDB-internal, physical, crash recovery only
  Binary Log → server-level, logical, replication + point-in-time recovery
  → single commit involves BOTH via 2-phase commit coordination

relfilenode (PG) can CHANGE (VACUUM FULL, TRUNCATE) independent of stable OID
```
