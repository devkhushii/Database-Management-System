# DBMS Handbook — Part 7: Indexing, File Organization & Storage Structures
## Module 11: Index Maintenance

> **Where we are:** Modules 5–10 covered index design and the optimizer's use of indexes, assuming everything is in good operational health. Module 11 addresses the reality that indexes **degrade over time** in a live, changing database, and covers the operational discipline — rebuilding, statistics refresh, VACUUM — required to keep them healthy.

---

## 11.0 Why This Module Exists

Every concept from Modules 2, 6, 9, and 10 has a shared, recurring theme: **things get worse over time under sustained write activity** — pages fragment (Module 2), B+ Tree nodes become unevenly filled after many splits/merges (Module 6), dead tuples accumulate (Module 9), and statistics grow stale (Module 10). Module 11 is the maintenance discipline that fights back against all of this simultaneously.

---

## 11.1 Rebuilding Indexes

### What is it?

**Rebuilding** an index means completely reconstructing it from scratch — reading all current data and building a brand-new, freshly-organized index structure to replace the old one, discarding all accumulated fragmentation/bloat in the process.

### Why does it exist?

After many insertions, deletions, and updates, a B+ Tree index (Module 6) can accumulate **partially-filled pages** (from splits that created two half-full nodes, and merges/redistributions that didn't perfectly compact things back) — a rebuild restores the index to a compact, optimally-filled state (subject to whatever fill factor, Module 6 Section 6.8, is configured).

### How it works

```
PostgreSQL:  REINDEX INDEX index_name;         -- rebuilds one index
             REINDEX TABLE table_name;         -- rebuilds all indexes on a table
             REINDEX INDEX CONCURRENTLY ...    -- rebuilds WITHOUT holding a long exclusive lock
                                                   (available since PostgreSQL 12+)

MySQL:       ALTER TABLE table_name ENGINE=InnoDB;   -- historically used to force a table rebuild
             OPTIMIZE TABLE table_name;               -- rebuilds table + indexes, reclaims space
```

### Locking Considerations (critical operational detail)

A plain `REINDEX`/rebuild traditionally requires an **exclusive lock** on the table for its duration — unacceptable for most production systems with continuous traffic. This is exactly why **online/concurrent rebuild variants** exist (`REINDEX CONCURRENTLY` in PostgreSQL, online DDL support in MySQL 8.0+) — these work by building the new index structure alongside the old one while still allowing reads/writes, then briefly swapping them at the end, at the cost of using more temporary disk space and taking longer overall than a blocking rebuild.

### Interview Importance
⭐⭐⭐⭐ — "How would you rebuild a large index on a production table without causing downtime?" — Answer: use the concurrent/online rebuild variant, understanding the trade-off of longer duration and extra temporary space for avoiding an exclusive lock.

## 11.2 Reorganizing Indexes

### What is it?

**Reorganizing** is a lighter-weight alternative to a full rebuild — compacting an existing index's pages in place (or via a less disruptive process) to reduce fragmentation, without necessarily creating an entirely new structure from scratch the way a full rebuild does.

### Rebuild vs Reorganize — Comparison

| Aspect | Rebuild | Reorganize |
|---|---|---|
| Approach | Fully reconstructs the index from scratch | Compacts/defragments the existing structure in place |
| Resource cost | Higher (more CPU, I/O, temp space) | Generally lower |
| Effectiveness | Complete — fully restores optimal density | Partial — reduces fragmentation but may not achieve the same density as a full rebuild |
| Typical trigger | Severe fragmentation, or after a bulk data change | Routine, lighter maintenance for moderate fragmentation |

*(Note: SQL Server has explicit, separately-named `ALTER INDEX ... REORGANIZE` vs `ALTER INDEX ... REBUILD` commands embodying this exact distinction; PostgreSQL and MySQL don't always draw as sharp a terminological line, but the underlying concepts — full reconstruction vs. lighter compaction — still apply operationally.)*

## 11.3 Fragmentation (Operational Recap)

Already introduced structurally in Module 2, Section 2.7. From an **operational maintenance** perspective: fragmentation is monitored via engine-specific metrics (e.g., PostgreSQL's `pg_stat_user_indexes`/bloat-estimation queries using extensions like `pgstattuple`; MySQL's `SHOW TABLE STATUS` data-free-space indicators) and addressed via the rebuild/reorganize operations above once it crosses an operationally significant threshold (commonly, teams set alerting around index bloat percentage — e.g., "alert if estimated bloat exceeds 30–40% of index size").

## 11.4 Statistics Update

### Recap and Extension

Module 10, Section 10.4 established *why* statistics (including histograms) matter for optimizer decisions. This section covers *how* they're kept fresh operationally.

### PostgreSQL: `ANALYZE`

`ANALYZE` scans a **sample** of a table's rows (not necessarily every row, for large tables — a statistically representative sample is used for efficiency) and recomputes cardinality estimates, most-common-value lists, and histograms, storing them in PostgreSQL's system catalogs for the optimizer to consult.

```sql
ANALYZE orders;              -- update statistics for one table
ANALYZE;                     -- update statistics for the entire database
```

### 11.4.1 Auto Analyze

**Auto Analyze** is PostgreSQL's background process (part of the broader autovacuum subsystem, Section 11.5.1) that automatically triggers `ANALYZE` on a table once its estimated fraction of changed rows (inserts/updates/deletes) since the last analyze crosses a configurable threshold (`autovacuum_analyze_scale_factor` plus a base threshold), removing the need for manual, scheduled `ANALYZE` runs in most routine cases.

### MySQL Equivalent

MySQL's optimizer relies on InnoDB's own persistent statistics (`innodb_stats_persistent`), refreshed automatically on significant table changes or via explicit `ANALYZE TABLE table_name;`.

### Common Mistake
- Disabling or ignoring auto-analyze/autovacuum "because it seemed to cause I/O spikes during business hours" without properly tuning its scheduling/aggressiveness instead — this trades a small manageable cost now for much worse, unpredictable query performance regressions later (a very common real production anti-pattern).

## 11.5 VACUUM (Overview, Building on Module 9)

### Recap and Extension

Module 9, Section 9.1.2 introduced *why* VACUUM exists (reclaiming dead tuple space from PostgreSQL's MVCC model). This section covers its operational mechanics in more depth.

### What `VACUUM` Actually Does

1. Scans the table for **dead tuples** (rows expired via `xmax`, no longer visible to any active transaction).
2. Marks the space occupied by dead tuples as reusable, updating the **Free Space Map** (Module 2/9).
3. Updates the **Visibility Map** (Module 9, Section 9.3) for pages now confirmed to contain only live, all-visible tuples.
4. Does **NOT** by default shrink the table's file size on disk (dead space becomes reusable **within** the existing file, not returned to the OS) — this is a very commonly misunderstood point.

### `VACUUM` vs `VACUUM FULL`

| Aspect | `VACUUM` (plain) | `VACUUM FULL` |
|---|---|---|
| Locking | Allows concurrent reads/writes (non-blocking, mostly) | Requires an **exclusive lock** on the table for its duration |
| Disk space | Reclaims space for reuse WITHIN the file; does not shrink the file on disk | Physically rewrites the entire table into a new, compact file, then replaces the old one — actually shrinks disk usage |
| Typical usage | Routine, frequent (often automatic via autovacuum) | Rare, deliberate maintenance windows only, due to the exclusive lock cost |

### 11.5.1 Auto Vacuum Overview

**Autovacuum** is PostgreSQL's background daemon that automatically triggers both `VACUUM` and `ANALYZE` (Section 11.4.1) on tables based on configurable thresholds tracking how many rows have been inserted/updated/deleted since the last run — removing the operational burden of manually scheduling these critical maintenance tasks, though tuning its aggressiveness (how often it runs, how much I/O it's allowed to use per run) remains an important production DBA responsibility, especially for very large or very high-write-throughput tables.

### Interview Importance
⭐⭐⭐⭐⭐ — "Why doesn't `VACUUM` (without `FULL`) shrink a PostgreSQL table's file size, and when would you actually need `VACUUM FULL`?" is an extremely common, high-value PostgreSQL-specific interview question.

## 11.6 Chapter Summary

- **Rebuilding** an index fully reconstructs it, eliminating fragmentation entirely, but traditionally requires an exclusive lock — modern engines provide online/concurrent variants (`REINDEX CONCURRENTLY`) to avoid downtime at the cost of longer duration and extra temp space.
- **Reorganizing** is a lighter-weight, less complete alternative to a full rebuild for routine fragmentation maintenance.
- **Statistics updates** (`ANALYZE` in PostgreSQL, persistent InnoDB statistics in MySQL) keep the optimizer's selectivity/cardinality estimates (Module 10) accurate; **Auto Analyze** automates this based on change thresholds.
- **`VACUUM`** reclaims dead tuple space (PostgreSQL MVCC, Module 9) and updates the Free Space Map and Visibility Map, but does **not** shrink the table file on disk by default; **`VACUUM FULL`** does shrink the file, at the cost of an exclusive lock.
- **Autovacuum** automates both `VACUUM` and `ANALYZE`, and disabling/under-tuning it is a common, costly real-world anti-pattern.

---

## 11.7 Cheat Sheet

```
Rebuild Index     = full reconstruction, eliminates fragmentation, traditionally EXCLUSIVE LOCK
                    -> use CONCURRENTLY/online variant for zero-downtime (slower, more temp space)
Reorganize Index  = lighter, in-place compaction, less complete than a full rebuild

ANALYZE           = recompute cardinality/histograms/MCVs for optimizer accuracy (PostgreSQL)
Auto Analyze      = automatic ANALYZE trigger based on % rows changed since last run

VACUUM (plain)    = reclaim dead tuple space WITHIN the file, update FSM + Visibility Map
                    does NOT shrink file on disk, mostly non-blocking
VACUUM FULL       = physically rewrites table into new compact file -> SHRINKS disk usage
                    -> requires EXCLUSIVE LOCK, use only in maintenance windows
Autovacuum        = automates VACUUM + ANALYZE based on configurable change thresholds

KEY FACT: Never disable autovacuum without proper tuning -- it trades small manageable
          cost now for much worse unpredictable regressions later.
```

## 11.9 MCQs

**Q1.** Which operation requires an exclusive lock and physically shrinks a PostgreSQL table's file on disk?
A) Plain `VACUUM`  B) `VACUUM FULL`  C) `ANALYZE`  D) `REINDEX CONCURRENTLY`
*(Answer: B)*

**Q2.** Auto Analyze is triggered based on:
A) A fixed daily schedule only  B) The percentage of rows changed since the last analyze, crossing a configurable threshold  C) Manual DBA commands only  D) Table size alone, regardless of changes
*(Answer: B)*

**Q3.** `REINDEX CONCURRENTLY` avoids an exclusive lock by:
A) Skipping the rebuild entirely  B) Building the new index structure alongside the old one, then briefly swapping them  C) Only rebuilding half the index  D) Running only during maintenance windows
*(Answer: B)*

**Q4.** Plain `VACUUM` (without `FULL`) primarily:
A) Shrinks the table's file size on disk immediately  B) Reclaims dead tuple space for reuse within the existing file, without shrinking the file  C) Rebuilds all indexes from scratch  D) Updates only the query cache
*(Answer: B)*

**Q5.** Disabling autovacuum without proper alternative tuning typically leads to:
A) Improved performance with no downsides  B) Table bloat, stale statistics, and potential Index-Only Scan fallback over time  C) Immediate data loss  D) Faster query planning
*(Answer: B)*
