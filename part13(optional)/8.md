# The Ultimate DBMS Handbook — Part 13: Research & Advanced Engineering

## Module 8 — Graph Processing

> **Goal of this module:** Understand why relationship-heavy queries break relational query planners, how graph databases physically store data to avoid that failure mode, and the distinct execution models (native graph traversal vs. bulk graph analytics) that graph systems split into.

---

### 8.1 Why Relational Databases Struggle with Graph Queries

Consider a "friends of friends of friends" query — a 3-hop traversal — in a relational schema with a `friendships(user_id, friend_id)` table. Expressed in SQL, this requires **self-joining the table 3 times**:

```sql
SELECT DISTINCT f3.friend_id
FROM friendships f1
JOIN friendships f2 ON f1.friend_id = f2.user_id
JOIN friendships f3 ON f2.friend_id = f3.user_id
WHERE f1.user_id = 42;
```

**Why this degrades badly as hop count increases:** each additional join multiplies the intermediate result set size (a "join explosion"), and the query planner must estimate cardinalities for each join level — for graph data, these estimates are notoriously inaccurate (real-world graphs have highly skewed degree distributions, so an "average" cardinality estimate is often wildly wrong for high-degree nodes), leading to poor query plans. A 6-hop query (common in fraud-ring detection or recommendation systems) becomes essentially unplannable with a relational optimizer built around join-order cost estimation for tabular data.

**The core structural mismatch:** a relational join must locate matching rows via an index lookup or scan **every time**, re-deriving the relationship from scratch at each hop. A graph database instead makes relationships **physically stored, first-class pointers** that can be followed directly — turning "find matching rows" into "dereference a pointer," which is where the fundamental performance difference comes from.

---

### 8.2 Index-Free Adjacency

**The defining internal technique of native graph databases** (pioneered and popularized by Neo4j): each node stores **direct physical pointers/references to its adjacent relationships**, rather than relying on a global index to find them.

**How it works internally:**
- Each node record contains a pointer to its **first relationship** in a doubly-linked list of relationships for that node.
- Each relationship record contains pointers to the **next and previous relationship** for *both* the start node and end node it connects (forming two separate linked lists simultaneously — one from each endpoint's perspective).
- Traversing from a node to its neighbors means following these in-record pointers directly — an **O(1) operation per hop**, regardless of how large the total graph is, because you never touch a global index; you only ever touch the local, already-in-hand node/relationship records.

**Why this is fundamentally different from a B-tree index lookup on a foreign key:** a B-tree index lookup for "all relationships involving node X" is `O(log n)` in the *size of the whole index*, and its cost doesn't shrink as you narrow to a specific node — every hop pays that same `O(log n)` index-traversal cost again. Index-free adjacency's per-hop cost depends only on the node's own **degree** (number of relationships), not on the total graph size — this is why native graph traversal remains fast even on graphs with billions of nodes, for a query that only touches a small, localized neighborhood.

**The tradeoff:** index-free adjacency is excellent for **localized, multi-hop traversal queries** (the dominant graph database use case — "find X's friends' friends," "find the shortest path between A and B"), but is not inherently faster for queries that need to touch a large, non-localized fraction of the graph (e.g., "compute PageRank over the entire graph") — that class of workload is better served by the bulk graph-analytics engines discussed in 8.4, not by a traversal-optimized native graph database.

### 8.3 The Property Graph Model

**Core data model** (used by Neo4j and most native graph databases, standardized informally as the "Property Graph" model, now being formalized via the **ISO GQL** standard, 2024):
- **Nodes**: entities, each with a set of **labels** (types, e.g., `Person`, `Product`) and a set of key-value **properties**.
- **Relationships**: directed, typed connections between two nodes, which can *themselves* have properties (e.g., a `PURCHASED` relationship might have a `date` and `amount` property) — this is a meaningful modeling capability relational schemas lack without an explicit join/association table, but here it's a first-class, directly-traversable primitive rather than an extra table.

**Contrast with RDF/triple stores** (the other major graph data model, used by systems like Amazon Neptune's RDF mode, Apache Jena, GraphDB): RDF represents everything as `(subject, predicate, object)` triples — a more uniform, schema-flexible model favored for knowledge graphs, semantic web applications, and data integration across heterogeneous sources, typically queried with **SPARQL** rather than the property-graph-oriented **Cypher** or **Gremlin** query languages. RDF's uniform triple model makes schema evolution and merging data from different sources easier, at some cost to the intuitive "node with rich properties" ergonomics property graphs offer for typical application development.

**Query languages:**
- **Cypher** (originated at Neo4j, now also an open standard direction feeding into GQL) — a declarative, pattern-matching language where you describe the *shape* of the subgraph you want (`(a:Person)-[:FRIENDS_WITH]->(b:Person)-[:FRIENDS_WITH]->(c:Person)`), and the query engine finds matches — conceptually similar to how SQL describes desired result shape rather than execution steps.
- **Gremlin** (Apache TinkerPop) — an imperative, step-based traversal language, more explicit about *how* to walk the graph (`g.V().has('name','X').out('FRIENDS_WITH').out('FRIENDS_WITH')`), used across multiple graph database vendors as a common traversal API.
- **SPARQL** — the query language for RDF triple stores, pattern-matching over triples.

### 8.4 Two Fundamentally Different Graph Workloads

This is the most important conceptual split in this module, and the one most often missed by engineers new to graph systems:

**A. OLTP-style graph traversal** — "find the shortest path from A to B," "find all products purchased by people who also purchased X" — localized, low-latency, touches a small neighborhood of the graph. This is what **native graph databases** (Neo4j, Memgraph, Amazon Neptune) with index-free adjacency (8.2) are optimized for.

**B. OLAP-style graph analytics** — "compute PageRank for every node," "find all connected components," "detect communities via label propagation" — global, batch, touches the **entire graph** and typically requires many iterative passes over all nodes/edges. This is what **graph processing frameworks** (Pregel, GraphX, distributed graph-analytics engines) are optimized for, and it requires a completely different execution model — index-free adjacency doesn't help here, because there's no "localized neighborhood" to exploit; you're processing everything, every iteration.

**Using the wrong tool for each:** running a whole-graph PageRank computation against a native graph database via repeated traversal queries is dramatically slower than a purpose-built batch analytics engine designed for full-graph iteration; conversely, using a batch graph-analytics framework for a single low-latency "shortest path between these two specific nodes" query is massive overkill (spinning up a distributed batch job for a query that should take milliseconds).

---

### 8.5 Pregel — The Bulk Synchronous Parallel Model for Graph Analytics

**Citation:** Malewicz et al., *"Pregel: A System for Large-Scale Graph Processing,"* SIGMOD 2010.

**Problem:** Google needed to run iterative algorithms (PageRank, shortest paths, connected components) over graphs with billions of vertices/edges — far too large for a single machine, and MapReduce's design (Module-agnostic background: a batch job model with no efficient support for iteration, since each MapReduce "round" requires materializing all output to disk and restarting) was a poor fit for genuinely iterative graph algorithms.

**Innovation: "Think Like a Vertex" + Bulk Synchronous Parallel (BSP).** Express a graph algorithm from the perspective of a single vertex: in each iteration ("superstep"), every vertex independently (a) receives messages sent to it in the previous superstep, (b) updates its own state, and (c) sends messages to its neighbors for the next superstep — all vertices execute the same per-vertex logic in parallel, and a global barrier synchronizes all vertices between supersteps (no vertex proceeds to the next superstep until all vertices have finished the current one) — this synchronization barrier is what "Bulk Synchronous Parallel" refers to, and it dramatically simplifies reasoning about correctness (no partial/interleaved state to worry about within a superstep) at the cost of the whole computation being only as fast as its slowest vertex/partition each round (a "straggler" problem).

**Internal Architecture:** the graph is partitioned across a cluster of worker machines (each holding a subset of vertices and their outgoing edges); a master coordinates superstep barriers; vertices communicate only via message-passing (never direct memory access across machines), and a vertex can "vote to halt" once it has no more work to do, with the whole computation terminating once all vertices have voted to halt and no messages remain in flight.

**Impact:** Established the vertex-centric BSP model as the dominant paradigm for distributed graph analytics; directly inspired **Apache Giraph** (open-source Pregel implementation, used at Facebook for social graph analytics) and **GraphX** (Apache Spark's graph processing library, which reimplements the vertex-centric model on top of Spark's RDD abstraction rather than a from-scratch distributed system).

---

### 8.6 GraphX and the "Graph as a Special Case of Tables" View

**GraphX** (part of Apache Spark) takes a distinct architectural stance from Pregel's from-scratch system: it represents a graph as **two Spark RDDs/DataFrames** — a vertex table and an edge table — and implements graph-parallel operations (including a Pregel-API-compatible interface for vertex-centric iteration) as operations over these tables, reusing Spark's existing distributed execution, fault tolerance, and optimization machinery rather than building bespoke graph-specific infrastructure.

**Why this matters conceptually:** it demonstrates that "graph processing" and "relational/tabular processing" aren't as fundamentally separate as Section 8.1 might suggest for the *batch analytics* case specifically — a graph algorithm can be compiled down to a sequence of joins and aggregations over vertex/edge tables, and get reasonable performance, *as long as the workload is the bulk/iterative kind (8.4-B) rather than the low-latency localized traversal kind (8.4-A)*, where index-free adjacency's per-hop advantage genuinely has no tabular equivalent.

---

### 8.7 Graph Query Optimization — Why It's a Different Problem

Even within native graph databases, query planning for pattern-matching queries (Cypher/Gremlin) has distinct challenges from relational query planning:
- **Worst-case optimal join algorithms**: traditional relational query optimizers plan joins pairwise (choosing an order to join tables two at a time), which can be provably suboptimal for certain graph pattern queries (specifically, cyclic patterns like triangle-finding) — this motivated a body of research into **worst-case optimal join algorithms** (e.g., the **Leapfrog Triejoin** algorithm) that process multiple relations simultaneously rather than pairwise, provably avoiding the worst-case blowup pairwise join planning can hit on cyclic query patterns. This research area (originating in complexity theory work by Ngo, Ré, Rudra and others) has influenced modern graph and relational query engines alike.
- **Cardinality estimation on skewed degree distributions**: as noted in 8.1, real graphs have highly skewed vertex degree distributions (a small number of "hub" nodes with enormous degree, most nodes with small degree) — graph query planners need degree-aware statistics (not just overall table-size statistics) to avoid catastrophically bad plans when a query pattern happens to touch a hub node.

### 8.8 Production Examples & Industry Usage

| System | Model / Workload type | Notable production usage |
|---|---|---|
| Neo4j | Native property graph, index-free adjacency (OLTP-style traversal) | Fraud detection, recommendation engines, identity/access graphs |
| Amazon Neptune | Supports both property graph (Gremlin) and RDF (SPARQL) | AWS customers needing managed graph traversal at scale |
| Memgraph | In-memory native property graph | Real-time fraud detection, network/IT operations graphs |
| Apache Giraph | Pregel-model batch graph analytics | Facebook's large-scale social graph analytics (historically) |
| Apache Spark GraphX | Table-based batch graph analytics | General-purpose graph analytics within existing Spark pipelines |
| TigerGraph | Native distributed property graph, both traversal and analytics | Large-scale enterprise graph analytics combining OLTP and OLAP-style graph queries |

### 8.10 MCQs

**Q1.** The core reason relational self-joins degrade badly for multi-hop graph queries is:
A) SQL doesn't support joins
B) Each additional join multiplies intermediate result set size and cardinality estimates are unreliable on skewed graph data
C) Relational databases can't store graph data at all
D) Indexes are not allowed on foreign keys

*Answer: B*

**Q2.** Index-free adjacency achieves O(1)-per-hop traversal cost because:
A) It uses a global B-tree index
B) Each node/relationship stores direct pointers to adjacent relationships, avoiding any index lookup
C) It precomputes all possible paths
D) It compresses the graph

*Answer: B*

**Q3.** The Bulk Synchronous Parallel (BSP) model in Pregel uses global barriers between supersteps primarily to:
A) Improve compression
B) Simplify correctness reasoning by ensuring no partial/interleaved state across vertices within a superstep
C) Eliminate the need for message passing
D) Avoid using a master coordinator

*Answer: B*

**Q4.** GraphX's approach of representing a graph as two Spark RDDs demonstrates that:
A) Native graph databases are never necessary
B) Bulk/batch graph analytics can be effectively expressed as table operations, unlike low-latency localized traversal
C) Graphs cannot be represented as tables
D) Spark cannot process graph data

*Answer: B*

**Q5.** Worst-case optimal join algorithms (e.g., Leapfrog Triejoin) were developed primarily to address:
A) Storage compression
B) Provable suboptimality of pairwise join planning on cyclic graph query patterns like triangle-finding
C) Network latency
D) Index-free adjacency implementation

*Answer: B*
