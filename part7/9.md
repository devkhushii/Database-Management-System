# PART A: PostgreSQL Internals

## 9.1 PostgreSQL Heap Storage

### Recap and Full Detail

PostgreSQL tables are, by default, **heap files** (Module 3, Section 3.1) — unordered collections of slotted pages (Module 2, Section 2.1). Every tuple's header includes two crucial MVCC fields:

- **`xmin`**: the transaction ID that **created** this tuple version.
- **`xmax`**: the transaction ID that **deleted/updated away** this tuple version (0/null if the tuple is still the current, live version).

### How UPDATE Actually Works in PostgreSQL (MVCC-based)

An `UPDATE` in PostgreSQL does **not** modify a row in place. Instead:

1. The **old tuple version** is marked with `xmax` = the updating transaction's ID (logically "expired," but its bytes remain on the page for now).
2. A **brand-new tuple version** is inserted (either on the same page, if there's room — enabling HOT, Section 9.1.1 — or on a different page if not), with `xmin` = the updating transaction's ID.
3. Every existing index that isn't a HOT-eligible case must now also be updated to point to this new tuple version's RID.

This is precisely why Module 1's "durability requires care" discussion and this module's MVCC explanation connect directly to **Part 9 (Transactions & Concurrency Control)**: multiple concurrent transactions can see *different* versions of the same logical row simultaneously, each version tagged with the `xmin`/`xmax` that determines its visibility to a given transaction's snapshot.

### 9.1.1 HOT (Heap-Only Tuple) Updates

**What is it?** A **HOT update** is a PostgreSQL optimization where, if (a) the new tuple version fits on the **same page** as the old version, AND (b) **none of the indexed columns changed value**, then PostgreSQL can avoid updating any index at all — the new tuple is linked directly from the old tuple's location via an in-page "HOT chain," and existing index entries (which point at the *original* row's `ctid`) can still find the current version by following that chain.

**Why it matters:** Without HOT, every single-column update to a heavily-indexed table would require updating **every index** on that table, even indexes on completely unrelated columns. HOT dramatically reduces this write amplification for the extremely common case of updating a non-indexed column.

```
Before HOT update:
  Page 10, Slot 4: Tuple v1 (xmax = 0, still current)
  Index entry: key='X' -> ctid=(Page10, Slot4)

UPDATE changes a non-indexed column, new version fits on same page:
  Page 10, Slot 4: Tuple v1 (xmax = T5, now expired)  -> HOT chain -> Slot 9: Tuple v2 (xmin=T5, current)
  Index entry UNCHANGED: still key='X' -> ctid=(Page10, Slot4)
  Lookup via index: find Slot 4 -> see it's expired -> follow HOT chain -> find live Slot 9 -> done
  (NO index write was needed for this update!)
```

### 9.1.2 Why VACUUM Exists (tied directly to MVCC)

Because `UPDATE`/`DELETE` never immediately erase old tuple versions, **dead tuples** (expired versions no longer visible to any active transaction) accumulate over time, consuming page space and inflating table size — this is exactly the **bloat** problem. `VACUUM` is the process that scans for dead tuples no longer needed by any active transaction and marks their space as reusable (updating the Free Space Map, Section 9.1.4). *(Full VACUUM mechanics, `VACUUM FULL`, and autovacuum tuning are the primary subject of Module 11: Index Maintenance.)*

## 9.2 TOAST (The Oversized-Attribute Storage Technique)

### What is it?

**TOAST** is PostgreSQL's mechanism for storing column values that are too large to fit reasonably within a single page (recall Module 1/2's page size of 8 KB) — such as long `TEXT`, `BYTEA`, or large `JSONB` values.

### How it works

When a row's total size (or a single attribute's size) exceeds a threshold (roughly ~2 KB, since PostgreSQL wants to fit multiple tuples per 8 KB page comfortably), PostgreSQL may apply, in order of preference:

1. **Compression** — compress the large value in place, if that alone brings it under the threshold.
2. **Out-of-line storage (TOAST table)** — if compression alone isn't enough, move the value's data to a separate, automatically-created **TOAST table** (one per table needing it), storing only a small pointer to it in the original row's slot.

```
Main table row:
  [ id | name | bio_pointer -> TOAST table, chunk_id=42 ]
       (the actual long bio TEXT lives in the associated TOAST table instead)

TOAST Table (separate, automatically managed):
  [ chunk_id=42, chunk_seq=0, chunk_data (up to ~2KB per chunk) ]
  [ chunk_id=42, chunk_seq=1, chunk_data (next ~2KB chunk) ]
  ... (large values are split across multiple chunk rows if needed)
```

### Why it matters
- Keeps the main heap table's pages dense and fast to scan (large blobs don't bloat every page).
- Directly connects to Module 2, Section 2.2's "overflow pointer" concept — TOAST **is** PostgreSQL's concrete implementation of that general idea.

### Interview Importance
⭐⭐⭐⭐ — "What happens when you store a 50 KB string in a PostgreSQL `TEXT` column?" — Answer: TOAST compresses and/or moves it out-of-line to a separate TOAST table, leaving only a small pointer in the main row.

## 9.3 Visibility Map

### What is it?

The **Visibility Map** is a small, compact bitmap (one or two bits per page) that PostgreSQL maintains per table, tracking whether **every tuple** on a given page is guaranteed visible to **all** current and future transactions (i.e., no dead/uncommitted versions remain to worry about on that page).

### Why it exists — two critical uses

1. **Index-Only Scans (Module 5, Section 5.7's caveat, explained fully here):** If a query can be satisfied entirely by a covering index, PostgreSQL still normally needs to verify each candidate row is visible to the current transaction's snapshot (an MVCC visibility check) — normally requiring a heap page fetch anyway. But if the Visibility Map says "this page is all-visible," PostgreSQL can **skip the heap fetch entirely**, trusting the index alone — this is what actually makes a true Index-Only Scan possible.
2. **VACUUM efficiency:** `VACUUM` can skip pages already marked all-visible (with no dead tuples), since there's nothing to clean up there, significantly speeding up routine vacuum runs on large, mostly-static tables.

### Interview Importance
⭐⭐⭐⭐⭐ — This resolves the caveat flagged back in Module 5: "a covering index enables an Index-Only Scan **only when the Visibility Map confirms the relevant page is all-visible**; otherwise, PostgreSQL must still fall back to a heap fetch to perform the MVCC visibility check."

---

## 9.4 Free Space Map (Full Detail)

Already introduced in Module 2, Section 2.5 — to recap with full context now that VACUUM (Section 9.1.2) and TOAST (Section 9.2) are understood: the **Free Space Map (FSM)** is a small forest-like structure, one per relation, summarizing how much free space each page has, letting `INSERT` (and non-HOT `UPDATE`, which needs a new tuple slot somewhere) find a page with sufficient room without scanning the whole heap. `VACUUM` is the process that **updates** the FSM after reclaiming dead tuple space, closing the loop between Sections 9.1.2 and 2.5.

# PART B: MySQL InnoDB Internals

## 9.5 InnoDB Clustered Index (Full Detail)

### Recap and Extension

Already established in Module 3 (Section 3.4) and Module 5 (Section 5.3): **every InnoDB table is clustered on its primary key** — the table's data pages ARE the primary key's B+ Tree leaf pages. If no primary key is declared, InnoDB automatically generates a hidden, internal 6-byte row ID to serve as the clustering key instead.

### Why choosing the right primary key matters enormously (tied to Module 6's B+ Tree mechanics)

Because the clustered B+ Tree's leaf pages hold the **actual row data** (not just small key+RID entries), inserting rows in **non-sequential** primary key order (e.g., random UUIDs) causes page splits (Module 6, Section 6.6) that must relocate **entire rows**, not just small index entries — a far more expensive operation than a similar split in a lightweight secondary index. This is the concrete mechanical reason behind the widely-repeated advice: *"prefer sequential/auto-incrementing primary keys in InnoDB."*

---

## 9.6 InnoDB Secondary Index (Full Detail — the "Double Lookup")

### Recap and Extension

Already established in Module 2 (Section 2.3) and Module 3 (Section 3.6): InnoDB secondary indexes store the **primary key value** (not a raw page/slot RID) as their pointer to the actual row, because the row's physical location can change due to clustered B+ Tree page splits — a raw RID would go stale immediately, whereas the primary key value remains a stable, permanent identifier.

### The Double Lookup, Precisely

```
Query: SELECT * FROM orders WHERE customer_email = 'khushi@example.com';
  (secondary index exists on customer_email; primary key is order_id)

Step 1: Traverse SECONDARY index B+ Tree on customer_email
         -> find matching entry -> retrieve stored primary key value, e.g. order_id = 8842

Step 2: Traverse PRIMARY (clustered) index B+ Tree using order_id = 8842
         -> find the leaf containing the ACTUAL row data -> return full row

TOTAL: TWO separate B+ Tree traversals for one query (vs ONE traversal in a
       clustered-primary-key-only lookup, or one traversal + one heap fetch in PostgreSQL)
```

### Why this matters for schema design

A **wide or composite primary key** in InnoDB doesn't just bloat the clustered index itself (Module 3, Section 3.6's IOT discussion) — it also bloats **every single secondary index** on that table, since each one must carry a full copy of that (now large) primary key value. This is one of the most impactful, easily-overlooked InnoDB schema design considerations (fully expanded in Module 12).

## 9.7 InnoDB Pages (Full Detail)

Recap from Module 1/2: InnoDB's default page size is **16 KB** (configurable at instance initialization via `innodb_page_size`, not changeable afterward without a full reinitialization). Every InnoDB page belongs to exactly one **B+ Tree** — either the clustered primary key tree, a secondary index tree, or an internal system structure (like the data dictionary or undo logs) — reinforcing that, architecturally, **"InnoDB storage" essentially means "a collection of interlinked B+ Trees,"** unlike PostgreSQL's separate heap-file-plus-indexes model.

---

## 9.8 InnoDB Buffer Pool (Full Detail)

Recap from Module 4: InnoDB's buffer pool (`innodb_buffer_pool_size`) is typically sized much larger (50–75% of system RAM) than PostgreSQL's `shared_buffers`, because InnoDB aims to be the **primary, authoritative cache** rather than relying heavily on the OS page cache the way PostgreSQL does. InnoDB's buffer pool uses a variant of the **LRU** algorithm (Module 4, Section 4.6.1) with a specific refinement: a **midpoint insertion strategy** — newly-read pages are inserted not at the very "most recently used" head of the LRU list, but at a **midpoint**, and only promoted to the true head if accessed again within a short window. This is InnoDB's own specific defense against **sequential flooding** (Module 4's weakness of naive LRU) — a large one-time scan's pages enter at the midpoint and get evicted relatively quickly without ever reaching (and evicting) the genuinely "hot" pages sitting at the true head of the list.

## 9.9 InnoDB Change Buffer

### What is it?

The **Change Buffer** is a special InnoDB structure that **caches modifications to secondary index pages** when those specific pages are **not currently in the buffer pool** (i.e., would otherwise require an immediate disk read just to apply a small change) — deferring the actual index page update until that page is naturally read into the buffer pool later for some other reason (or during background merge operations).

### Why it exists

Recall Module 6: a random insert into a secondary index B+ Tree might touch a page that isn't cached — normally requiring an immediate disk read (to load the page), apply the change, then eventually write it back. If that page **isn't currently needed for anything else**, this is wasted, premature I/O. The Change Buffer instead **buffers the pending change in memory** (persisted safely via the redo log for durability) and applies it lazily, batching multiple changes to the same page together and avoiding random I/O that might turn out to be unnecessary if the page is rarely accessed anyway.

### Key restriction

The Change Buffer can **only** be used for **secondary indexes** (never the clustered primary key index, and never unique secondary indexes, since uniqueness must be verified immediately against the real, current data — deferring that check would risk allowing a duplicate to slip through undetected).

### Diagram

```
INSERT causes a change to Secondary Index page P (currently NOT in buffer pool):

  Without Change Buffer:  Read Page P from disk NOW -> apply change -> mark dirty -> (eventually flush)
                          (immediate random I/O cost paid right away)

  With Change Buffer:     Record the pending change in the Change Buffer (in memory + redo-logged)
                          -> continue, no immediate disk read needed
                          -> LATER, when Page P is eventually read into the buffer pool for any
                             reason (or during a background merge), apply all buffered changes at once
```

### Interview Importance
⭐⭐⭐⭐ — "What is InnoDB's Change Buffer, and why can't it be used for unique secondary indexes?" is a strong, specific InnoDB internals question that separates candidates with genuine hands-on MySQL experience from purely theoretical knowledge.

## 9.10 InnoDB Adaptive Hash Index (Full Detail)

### Recap and Extension

Already introduced in Module 7, Section 7.7: the **Adaptive Hash Index (AHI)** is an automatic, **in-memory-only** hash structure InnoDB builds dynamically **on top of** existing B+ Tree indexes, specifically over pages that are observed to be accessed very frequently via equality lookups.

### How it works (conceptual)

InnoDB monitors access patterns to its B+ Tree pages; if a particular page (or search pattern) is accessed repeatedly via equality comparisons, InnoDB builds a hash index entry pointing directly to that page/row, allowing future identical lookups to bypass the full B+ Tree traversal (Module 6) entirely and jump directly via the hash — combining Module 6's B+ Tree's general-purpose flexibility with Module 7's hash index's O(1) equality-lookup speed, automatically, for whichever data happens to be "hot" at any given time.

### Why it's automatic, not user-controlled

Unlike a regular index, the DBA/developer cannot directly create or choose columns for the Adaptive Hash Index — InnoDB decides, adaptively, based on observed real-time access patterns, which is exactly why it's named "adaptive." It can also be disabled entirely via a server variable (`innodb_adaptive_hash_index`) if benchmarking shows it isn't helping (or is even hurting, due to its own maintenance overhead) for a specific workload.

## 9.11 Master Comparison Table — PostgreSQL vs InnoDB Internals

| Concept | PostgreSQL | InnoDB |
|---|---|---|
| Default table organization | Heap (unordered) | Always clustered on primary key |
| MVCC implementation | Old + new tuple versions coexist in heap (`xmin`/`xmax`) | Undo logs reconstruct old versions separately from the clustered data |
| Large value storage | TOAST (compress, then move out-of-line if needed) | Off-page storage for large `BLOB`/`TEXT` columns (conceptually similar, different mechanism) |
| Secondary index pointer | `ctid` (physical page/slot, can go stale) | Primary key value (stable, but bloats every secondary index if PK is wide) |
| Dead tuple cleanup | VACUUM (manual or autovacuum) | Automatic via undo log purge threads (no user-facing VACUUM equivalent) |
| Buffer replacement | CLOCK-sweep with usage count (Module 4) | LRU variant with midpoint insertion (this module) |
| Deferred index writes | No direct equivalent | Change Buffer (secondary, non-unique indexes only) |
| Automatic hot-data hash acceleration | No direct equivalent | Adaptive Hash Index |
| Covering index full benefit | Requires Visibility Map "all-visible" confirmation | Not applicable in the same way — clustered PK access already avoids the equivalent lookup for primary-key-covered queries |

## 9.12 Chapter Summary

- **PostgreSQL**: heap-organized tables with MVCC (`xmin`/`xmax` tuple versioning), **HOT updates** avoiding index writes for non-indexed-column changes, **TOAST** for oversized values, the **Visibility Map** enabling true Index-Only Scans, and the **Free Space Map** for insert placement — with **VACUUM** tying dead-tuple cleanup back to both the Visibility Map and FSM.
- **InnoDB**: mandatory clustered primary key storage (data pages ARE the primary key B+ Tree), the secondary-index **"double lookup"** (traverse secondary index for the PK value, then the clustered index for the row), 16 KB pages, an **LRU-with-midpoint-insertion** buffer pool defense against sequential flooding, the **Change Buffer** for deferring non-unique secondary index writes on uncached pages, and the **Adaptive Hash Index** automatically accelerating hot equality-lookup patterns on top of existing B+ Trees.
- The single most repeated architectural contrast across this entire handbook holds true here in full technical depth: **PostgreSQL separates heap and indexes (with RID/`ctid` indirection); InnoDB unifies table and primary-key index (paying for it via secondary-index double lookups and PK-width-sensitive index bloat).**

## 9.13 Cheat Sheet

```
POSTGRESQL:
  Heap + MVCC (xmin/xmax) -> UPDATE creates NEW tuple version, doesn't overwrite
  HOT Update    = same page + no indexed column changed -> SKIP index updates entirely
  TOAST         = compress and/or move large values to separate TOAST table
  Visibility Map = per-page "all visible?" bitmap -> enables true Index-Only Scans, speeds VACUUM
  FSM           = per-relation free-space tracker for INSERT placement
  VACUUM        = reclaims dead tuple space, updates FSM + Visibility Map

INNODB:
  Clustered PK  = table data pages ARE the primary key's B+ Tree leaves (mandatory)
  Secondary Idx = stores PK VALUE (not RID) -> "double lookup" (secondary index -> clustered index)
  Pages         = 16 KB default, every page belongs to some B+ Tree
  Buffer Pool   = LRU with MIDPOINT INSERTION -> defends against sequential flooding
  Change Buffer = defers SECONDARY, NON-UNIQUE index writes on uncached pages
  Adaptive Hash Index = automatic, in-memory hash layer OVER hot B+ Tree access patterns

KEY CONTRAST: PostgreSQL = separate heap+indexes (ctid indirection, can go stale)
              InnoDB     = unified table+PK-index (no raw RID; PK value bloats secondary indexes)
```
