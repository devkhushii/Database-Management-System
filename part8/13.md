## 13.1 Case Study: Banking (Transaction Ledger Queries)

### Scenario

A bank's `transactions` table (500 million rows) records every transaction. A common query fetches a customer's recent transaction history:

```sql
SELECT * FROM transactions
WHERE account_id = 88213
ORDER BY transaction_date DESC
LIMIT 50;
```

This query is fast for most accounts but **catastrophically slow** for a small number of high-volume corporate accounts with millions of transactions.

### Diagnosis

```
EXPLAIN ANALYZE reveals:
  Index Scan on idx_account_id (cost=0.43..85000.12 rows=50)
                                (actual time=0.5..12000.3 rows=50 loops=1)
    Filter: none additional
    Index Cond: (account_id = 88213)
```

The index on `account_id` alone finds all matching rows (potentially millions for this account), but must then **sort** all of them by `transaction_date` before the `LIMIT 50` can be applied — unless a composite index also covers the sort order.

### Root Cause (Connecting to Modules 5, 7, 11)

- **Module 5, §5.10 (sargability/index design):** The existing index on `account_id` alone doesn't cover the `ORDER BY`, forcing a large in-memory or disk-based sort (Module 7) over potentially millions of rows before the `LIMIT` can trim it down.
- **Module 4 (statistics):** Highly skewed data — most accounts have few transactions, a handful of corporate accounts have millions (a classic long-tail distribution, Module 4 §4.7) — the "average case" plan works fine, but the skewed accounts blow past reasonable expectations.

### Fix

```sql
-- Composite index covering BOTH the equality filter AND the sort order:
CREATE INDEX idx_account_date ON transactions(account_id, transaction_date DESC);
```

With this index, the database can directly seek to `account_id = 88213`'s entries **already in `transaction_date DESC` order** (Module 5, §5.7 — "sort for free"), and stop after just 50 rows — **without ever needing to sort or even scan the full set of matching rows.**

### Execution Plan After Fix

```
Limit  (cost=0.43..12.50 rows=50)
       (actual time=0.02..0.45 rows=50 loops=1)
  ->  Index Scan using idx_account_date on transactions
      (cost=0.43..185000.00 rows=2500000)
      (actual time=0.02..0.40 rows=50 loops=1)
        Index Cond: (account_id = 88213)
```

**Result: ~12,000ms → ~0.5ms**, even for the highest-volume corporate accounts — because the plan now stops after exactly 50 rows, regardless of how many total matching transactions exist.

### Lessons
- Composite indexes matching **both** the filter AND sort clause are essential for "top-N per group" query patterns (Module 5 §5.7, Module 11 §11.7).
- Skewed data distributions (Module 4) mean average-case testing can miss catastrophic worst-case behavior — always test with realistic outlier data.

## 13.2 Case Study: E-Commerce (Product Search & Filtering)

### Scenario

An e-commerce platform's product search combines multiple filters:

```sql
SELECT * FROM products
WHERE category = 'Electronics'
  AND price BETWEEN 100 AND 500
  AND in_stock = true
ORDER BY popularity_score DESC
LIMIT 20;
```

During a flash sale, this query becomes extremely slow.

### Diagnosis

```
EXPLAIN ANALYZE reveals:
  Sort (actual time=1500.2..1520.5 rows=20)
    Sort Key: popularity_score DESC
    ->  Bitmap Heap Scan on products
        (actual rows=850000)
          Recheck Cond: (category='Electronics' AND price BETWEEN 100 AND 500)
          Filter: (in_stock = true)
          Rows Removed by Filter: 50000
```

**900,000 rows** matched category+price (a huge fraction of the flash-sale-boosted Electronics category), and the database had to **fully sort** all 900,000 rows by `popularity_score` before returning just the top 20 (Module 7's expensive full external sort).

### Root Cause (Connecting to Modules 4, 5, 7, 11)

- **Module 4 (cardinality):** The `category = 'Electronics'` + price range predicate is far **less selective** during a flash sale than normal statistics (Module 4, §4.10-§4.11) would suggest — a temporary, event-driven data distribution shift not yet reflected in stale statistics.
- **Module 7:** A full sort of 900,000 rows for a `LIMIT 20` is enormously wasteful — a **Top-N** pattern (Module 11, §11.7) that should ideally avoid a full sort.

### Fix Options

**Option A — Composite index covering the sort:**
```sql
CREATE INDEX idx_category_popularity ON products(category, popularity_score DESC)
WHERE in_stock = true;   -- partial index, only indexing in-stock rows
```
This is a **partial index** (indexing only `in_stock = true` rows) — since out-of-stock products are irrelevant to this query pattern, excluding them keeps the index smaller and more effective, directly reducing the number of pages the index itself occupies (Module 5's cost model).

**Option B — Ensure statistics reflect the flash-sale reality:**
```sql
ANALYZE products;   -- Module 4, §4.10 — refresh stale statistics
                     -- to reflect the current (temporarily different)
                     -- data distribution
```

### Execution Plan After Fix (Option A)

```
Limit  (actual time=0.8..1.2 rows=20)
  ->  Index Scan using idx_category_popularity on products
      (actual time=0.8..1.1 rows=20)
        Index Cond: (category = 'Electronics')
        Filter: (price BETWEEN 100 AND 500)
```

The scan now reads rows **already in `popularity_score DESC` order** (within the `Electronics` category, via the partial index), applying the `price` filter as it goes, and stopping as soon as 20 qualifying rows are found — no full sort needed.

### Lessons
- **Partial indexes** (Module 5 extension) are a powerful tool when a query pattern only ever cares about a subset of rows (e.g., `in_stock = true`).
- Event-driven traffic spikes (flash sales) can expose latent statistics/indexing gaps that normal traffic never surfaces — proactive load testing with realistic event-scenario data distributions is valuable.

## 13.3 Case Study: Healthcare (Patient Record Joins with Strict Correctness Requirements)

### Scenario

A hospital system needs a report of patients who have **no** completed follow-up appointment after a diagnosis:

```sql
SELECT p.name FROM patients p
WHERE p.id NOT IN (
  SELECT patient_id FROM appointments
  WHERE appointment_type = 'FOLLOWUP' AND status = 'COMPLETED'
);
```

The report unexpectedly returns **zero rows**, even though staff can manually confirm several such patients exist.

### Diagnosis (Correctness Bug, Not Performance)

This is **exactly** Module 3, §3.8's `NOT IN` + NULL trap. If **even one row** in `appointments.patient_id` is `NULL` (e.g., an appointment record with a data-entry gap, or a walk-in appointment not yet linked to a patient), the entire `NOT IN` subquery's semantics break — `NOT IN` against a set containing NULL evaluates to `UNKNOWN` for every comparison, causing the outer `WHERE` to reject **every single row**.

### Fix

```sql
SELECT p.name FROM patients p
WHERE NOT EXISTS (
  SELECT 1 FROM appointments a
  WHERE a.patient_id = p.id
    AND a.appointment_type = 'FOLLOWUP'
    AND a.status = 'COMPLETED'
);
```

`NOT EXISTS` correctly handles NULLs because it's checking **row existence with a join condition**, not evaluating a NULL-containing set membership test (Module 3, §3.8's detailed explanation).

### Why This Case Study Matters Especially in Healthcare

In a domain where a report drives **real clinical follow-up decisions**, a silent correctness bug (returning "no patients need follow-up" when the true answer is "we don't actually know, because the query is broken") is **far more dangerous** than a slow query — this case study is a reminder that Module 3's correctness-focused transformations aren't just performance topics; they're patient-safety-adjacent correctness topics in domains like this.

### Lessons
- Always default to `NOT EXISTS` over `NOT IN` when subquery columns could ever be NULL — especially in domains where correctness has real-world consequences beyond "slow page load."
- Add `NOT NULL` constraints at the schema level where business logic genuinely requires it (e.g., `appointments.patient_id NOT NULL`) — a proactive, schema-level defense (Part 1 territory) complementing the query-level fix.

## 13.4 Case Study: Analytics (Large-Scale Aggregation Over Event Data)

### Scenario

An analytics dashboard computes daily active users:

```sql
SELECT event_date, COUNT(DISTINCT user_id) AS dau
FROM events
WHERE event_date >= '2026-06-01'
GROUP BY event_date
ORDER BY event_date;
```

The `events` table has 5 billion rows. This query takes over a minute.

### Diagnosis

```
EXPLAIN ANALYZE reveals:
  GroupAggregate (actual time=45000.1..62000.8)
    Group Key: event_date
    ->  Sort (actual time=40000.2..48000.1)
          Sort Key: event_date
          ->  Seq Scan on events
              (actual rows=500000000)
                Filter: (event_date >= '2026-06-01')
```

`COUNT(DISTINCT user_id)` is a notoriously expensive operation (Module 8, §8.6's "not simply decomposable" callout) — the database must track every **distinct** `user_id` seen per `event_date`, which for high-cardinality data requires substantial memory/sort work.

### Root Cause (Connecting to Modules 5, 6, 8, 10)

- No index supports "sort for free" on `event_date` combined with efficient distinct-counting.
- `COUNT(DISTINCT ...)` doesn't parallelize as cleanly as `SUM`/`COUNT(*)` (Module 8, §8.6) because deduplication must ultimately happen against the **global** set of `user_id`s per group, not just per-worker partial results.

### Fix Options

**Option A — Index to avoid the sort:**
```sql
CREATE INDEX idx_events_date ON events(event_date);
```
Enables Sort Aggregation (Module 8, §8.2) via "sort for free" (Module 5, §5.7), though `COUNT(DISTINCT)`'s inherent cost remains.

**Option B — Approximate distinct counting (a common, industry-standard analytics trade-off):**
```sql
-- PostgreSQL example using the HyperLogLog extension (illustrative)
SELECT event_date, hll_cardinality(hll_union_agg(user_id_hll)) AS approx_dau
FROM events_daily_hll_rollup
WHERE event_date >= '2026-06-01'
GROUP BY event_date;
```
This assumes a **pre-aggregated rollup table** maintaining HyperLogLog sketches per day (an advanced technique beyond this handbook's core scope, but an extremely common real-world analytics pattern) — trading a small amount of statistical accuracy (~1-2% error, typically) for dramatically better performance and parallelizability, since HLL sketches (unlike exact distinct sets) **are** cleanly combinable across partial aggregates (directly solving Module 8 §8.6's `COUNT(DISTINCT)` decomposability problem).

**Option C — Pre-aggregation / materialized rollup tables:**
Maintain a `daily_active_users` summary table, updated incrementally (e.g., via a nightly batch job or streaming pipeline) — turning an expensive 5-billion-row scan into a query against a tiny, pre-computed table. This connects to Module 3's general philosophy (do expensive work once, reuse the result) taken to its logical extreme at the data-pipeline/architecture level.

### Lessons
- Exact `COUNT(DISTINCT)` at massive scale is fundamentally expensive — real-world analytics systems very commonly trade exactness for approximate algorithms (HyperLogLog) or pre-aggregation.
- This case study shows the limits of pure query-level tuning — sometimes the right fix is an **architectural** one (rollup tables, approximate algorithms), not just a better index or rewritten query.

## 13.5 Case Study: Inventory Management (High-Concurrency Updates + Reads)

### Scenario

A warehouse inventory system frequently checks and updates stock levels:

```sql
-- Read-check
SELECT quantity FROM inventory WHERE sku = 'ABC123' AND warehouse_id = 5;

-- Followed by an application-level update
UPDATE inventory SET quantity = quantity - 1
WHERE sku = 'ABC123' AND warehouse_id = 5 AND quantity > 0;
```

Under high concurrency (many simultaneous orders for the same popular SKU), this pattern causes significant lock contention and occasional overselling bugs.

### Diagnosis (Connecting to Part 7 — Transactions/Concurrency, Cross-Referenced Here)

This case study primarily illustrates a **concurrency control** issue (Part 7 territory) rather than a pure query-optimization one — but it's included here because query *plan choice interacts* with locking behavior: an inefficient access path (e.g., a full table scan instead of an index seek on `sku, warehouse_id`) holds locks on **far more rows/pages** than necessary, dramatically worsening contention under concurrent load.

### Fix (Query/Index Layer)

```sql
CREATE UNIQUE INDEX idx_inventory_sku_warehouse ON inventory(sku, warehouse_id);
```
Ensures the `UPDATE`'s row-locating step (Module 5) uses a precise Index Scan, touching and locking **only** the exact target row — not scanning/locking unrelated rows, which would otherwise unnecessarily serialize unrelated concurrent transactions on other SKUs/warehouses.

### Fix (Application/Transaction Layer — Cross-Reference to Part 7)

Combining the check-and-update into a **single atomic statement** avoids the read-then-write race condition entirely:
```sql
UPDATE inventory SET quantity = quantity - 1
WHERE sku = 'ABC123' AND warehouse_id = 5 AND quantity > 0
RETURNING quantity;
```
If this returns zero rows, the stock was insufficient — this pattern relies on the database's atomic row-level locking (Part 7) rather than a separate, race-condition-prone application-level check.

### Lessons
- Query optimization (this Part 8) and concurrency control (Part 7) are **deeply intertwined** in high-concurrency systems — a "slow query" symptom sometimes has a locking root cause, not a cost-model root cause.
- Precise indexing (Module 5) reduces lock scope/duration, directly improving concurrent throughput, not just single-query latency.

## 13.6 Case Study: Logging (High-Volume, Append-Heavy, Time-Range Queries)

### Scenario

A logging system ingests millions of log rows per hour and needs to support queries like:

```sql
SELECT * FROM logs
WHERE service = 'payment-api' AND log_level = 'ERROR'
  AND timestamp BETWEEN '2026-07-17 00:00:00' AND '2026-07-18 00:00:00'
ORDER BY timestamp DESC;
```

The `logs` table has 10 billion rows total, growing continuously.

### Diagnosis and Fix: Table Partitioning (Connecting Forward to Part 3/10 Territory)

While a composite index (`service, log_level, timestamp`) helps significantly (Module 5), at this scale, **range partitioning by timestamp** (a storage-layer strategy, cross-referencing Part 3) becomes essential — dividing the table into smaller physical chunks (e.g., one partition per day) so that:

```
Query filtering on timestamp BETWEEN '2026-07-17' AND '2026-07-18'
        │
        ▼
PARTITION PRUNING: the optimizer recognizes only ONE day's partition
                    could possibly contain matching rows, and skips
                    scanning the other 10+ billion rows' worth of
                    partitions ENTIRELY — not even touching their
                    pages, page count, or statistics at plan time.
```

This is conceptually a **storage-layer analog of predicate pushdown** (Module 3, §3.1) — instead of filtering rows after reading them, entire physical partitions are excluded from consideration before any scanning happens at all.

### Execution Plan Illustration

```
Append  (cost=... )
  ->  Index Scan on logs_2026_07_17 
      (only this ONE partition scanned!)
        Index Cond: (service='payment-api' AND log_level='ERROR')
        Filter: (timestamp BETWEEN ...)
  (all OTHER date partitions: pruned entirely, not shown/touched)
```

### Lessons
- At sufficiently large scale, **schema/storage design** (partitioning) becomes as important as query-level tuning (Modules 1-12) — this handbook's Part 8 focus on query processing works *in concert with*, not as a replacement for, good physical schema design (Part 3).
- Append-heavy, time-series-like workloads (logging, IoT, event data) are a canonical use case for time-based range partitioning.

## 13.7 Case Study: Social Media (Feed Generation — Fan-out Query Patterns)

### Scenario

A social media feed query fetches recent posts from accounts a user follows:

```sql
SELECT p.* FROM posts p
JOIN follows f ON p.author_id = f.followed_id
WHERE f.follower_id = 42
ORDER BY p.created_at DESC
LIMIT 20;
```

For users following thousands of accounts, this becomes slow.

### Diagnosis (Connecting to Modules 5, 6, 7, 11)

```
EXPLAIN ANALYZE reveals:
  Limit (actual time=800.1..800.3 rows=20)
    ->  Sort (actual time=795.2..799.8 rows=20)
          Sort Key: p.created_at DESC
          ->  Nested Loop  (actual rows=45000)
                ->  Index Scan on follows (actual rows=3000)
                      Index Cond: (follower_id = 42)
                ->  Index Scan on posts (actual rows=15 loops=3000)
                      Index Cond: (author_id = f.followed_id)
```

This is Module 6, §6.3's Indexed Nested Loop Join — reasonable for a *small* number of followed accounts, but with 3,000 followed accounts (`loops=3000`), it performs **3,000 separate index probes**, then must fully sort the combined ~45,000-row result by `created_at` before taking just the top 20 — a classic **"fan-out then sort"** bottleneck common in social feed systems.

### Fix Options (This Is a Genuinely Hard, Industry-Famous Problem)

**Option A — Composite index to at least avoid the separate sort per author:**
```sql
CREATE INDEX idx_posts_author_created ON posts(author_id, created_at DESC);
```
Helps each individual inner-loop probe return results pre-sorted, but the **global** merge across 3,000 different authors' individually-sorted streams still requires combining them — conceptually similar to Module 10, §10.4's parallel multi-way merge concept, but applied here across *different join keys* rather than parallel workers.

**Option B — Fan-out-on-write (a well-known, industry-standard architectural pattern):**
Instead of computing the feed **at read time** (fan-out-on-read, as the query above does), pre-compute and maintain a **per-user feed table**, updated whenever someone they follow posts (fan-out-on-write):
```sql
-- On new post creation, insert into every follower's precomputed feed:
INSERT INTO user_feeds (user_id, post_id, created_at)
SELECT follower_id, NEW.post_id, NEW.created_at
FROM follows WHERE followed_id = NEW.author_id;

-- Feed read becomes a trivially fast, simple query:
SELECT * FROM user_feeds WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;
```

**The classic trade-off:** Fan-out-on-write makes **reads** extremely fast (simple, single-table, indexed query) at the cost of making **writes** more expensive and complex (a single post by a celebrity with millions of followers triggers millions of feed-table insertions — the famous "celebrity problem" in social media system design) — usually solved with a **hybrid** approach (fan-out-on-write for normal users, fan-out-on-read merged in at query time specifically for celebrity/high-follower-count accounts).

### Lessons
- Some performance problems are **fundamentally architectural**, not fixable via indexing/query rewriting alone (Modules 1-12) — recognizing when to escalate from "better SQL" to "different data model/architecture" is a critical senior engineering judgment call.
- This exact fan-out trade-off is an **extremely common system design interview topic**, directly building on this handbook's join/sort/aggregation theory (Modules 6-8).

## 13.8 Case Study: Reporting Systems (Complex Multi-Join BI Queries)

### Scenario

A business intelligence tool generates a monthly revenue report joining 8 tables (customers, orders, order_items, products, categories, regions, promotions, payment_methods):

```sql
SELECT r.region_name, c.category_name, SUM(oi.quantity * oi.unit_price) AS revenue
FROM orders o
JOIN customers cu ON o.customer_id = cu.id
JOIN regions r ON cu.region_id = r.id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON oi.product_id = p.id
JOIN categories c ON p.category_id = c.id
LEFT JOIN promotions pr ON o.promotion_id = pr.id
JOIN payment_methods pm ON o.payment_method_id = pm.id
WHERE o.order_date >= '2026-06-01' AND o.order_date < '2026-07-01'
GROUP BY r.region_name, c.category_name;
```

This 8-table join query occasionally produces wildly different plans (and performance) across runs.

### Diagnosis (Connecting to Module 2, §2.7)

An 8-table join sits right at PostgreSQL's default `join_collapse_limit` (8) — and depending on exact configuration/version and how the query is structured, could potentially cross into GEQO (Genetic Query Optimizer, Module 2 §2.7) territory if additional implicit joins push the count higher, explaining **plan instability across runs** (GEQO's randomized nature, Module 2 §2.7).

### Fix Options

**Option A — Restructure to reduce effective join count for the optimizer:**
Pre-aggregate `order_items` by `order_id` **before** joining to reduce downstream join input sizes (Module 8, §8.5's Partial Aggregation pattern), and consider whether `payment_methods`/`promotions` (likely small, mostly-static lookup tables) could be joined last, after the larger fact-table joins have already reduced the row count.

**Option B — Increase `join_collapse_limit`/`geqo_threshold` (with caution):**
```sql
SET join_collapse_limit = 12;
SET geqo_threshold = 14;
```
Forces full dynamic-programming exhaustive search (Module 2, §2.8) instead of falling back to GEQO — trades longer **planning** time for a more consistently optimal, non-randomized **execution** plan. Reasonable for infrequent, expensive BI/reporting queries (Module 2's planning-time-vs-execution-time trade-off is very favorable here, since these reports run occasionally, not thousands of times per second).

**Option C — Materialized view for frequently-run reports:**
```sql
CREATE MATERIALIZED VIEW monthly_revenue_by_region_category AS
  <the query above>;

-- Refreshed on a schedule (e.g., nightly):
REFRESH MATERIALIZED VIEW monthly_revenue_by_region_category;
```
For a report run repeatedly by many dashboard viewers but only needing to reflect data as of the last refresh, materializing the result entirely sidesteps the join-optimization problem for every read after the first computation — the ultimate expression of Module 3's "do expensive work once, reuse the result" philosophy.

### Lessons
- Very wide multi-table joins are exactly where Module 2's search-space/enumeration-strategy theory (DP vs. GEQO) becomes practically, directly relevant — not just academic.
- For expensive, infrequently-changing, frequently-read reports, **materialized views** are often a better architectural answer than continuously re-optimizing/re-executing the full join every single time.

## 13.10 Chapter Summary

- Real-world performance problems rarely map to a single, isolated concept — they require **synthesizing** access paths (Module 5), join algorithms (Module 6), sorting (Module 7), aggregation (Module 8), statistics (Module 4), and sometimes concurrency (Part 7) or physical schema design (Part 3) all at once.
- Some problems are genuinely **correctness** bugs disguised as performance complaints (Healthcare case study) — always verify results are actually correct, not just fast.
- Some problems require **architectural**, not just query-level, solutions (Social Media fan-out, Analytics approximate counting, Reporting materialized views) — recognizing this boundary is a critical senior engineering skill.
- The systematic diagnostic methodology from Module 11 (`EXPLAIN ANALYZE` → find the bottleneck → form a hypothesis → fix one thing → re-measure) applies universally across every domain and scale.
