# The Ultimate DBMS Handbook — Part 13: Research & Advanced Engineering

## Module 4 — LSM Trees (Log-Structured Merge Trees)

> **Goal of this module:** By the end, you should be able to explain, tune, and reason about the tradeoffs of any LSM-based storage engine (RocksDB, LevelDB, Cassandra, HBase, ScyllaDB, TiKV) at the level required to configure it correctly in production or discuss its design in an interview.

---

### 4.1 Origin and Core Idea

**Citation:** O'Neil, Cheng, Gawlick, O'Neil, *"The Log-Structured Merge-Tree (LSM-Tree),"* Acta Informatica, 1996 — predates Bigtable/LevelDB by a decade; Bigtable (Module 3.3) was the paper that popularized it in a real distributed system.

**The core idea in one sentence:** Turn random writes into sequential writes by never updating data in place — instead, buffer writes in memory, flush them sequentially to disk as immutable sorted files, and periodically merge those files in the background to bound how many a read has to check.

**Why this matters:** disks (and to a lesser but still real extent, SSDs) are dramatically faster at sequential I/O than random I/O. A B-tree (Module 4 of an earlier Part, assumed known) updates a page in place — which, at scale, means random writes scattered across the disk. An LSM-tree converts every write into an append, which is sequential, at the cost of doing extra work later (compaction) to keep reads fast.

---

### 4.2 The Write Path

**Step 1 — Write-Ahead Log (WAL):** every incoming write is first appended to a durable, sequential on-disk log (same durability principle as ARIES, Module 3.2) — this is what makes the write crash-safe *before* it's reflected anywhere else.

**Step 2 — MemTable:** the write is then applied to an in-memory sorted structure — typically a **skip list** (LevelDB, RocksDB default) because skip lists support efficient concurrent lock-free-ish inserts and ordered iteration, though some engines use in-memory B-trees or hash tables for specific memtable variants.

**Step 3 — Flush:** when the memtable reaches a configured size threshold, it is **frozen** (made immutable, a new empty memtable takes over new writes — this avoids blocking writers during flush) and written out to disk as a new **SSTable** (Sorted String Table) — a single sequential write of the entire sorted contents.

**Step 4 — WAL truncation:** once the memtable's contents are safely on disk as an SSTable, the corresponding portion of the WAL can be discarded, since recovery no longer needs it.

```
Write → WAL (durable, sequential) → active MemTable (sorted, in-RAM)
                                          │ (fills up)
                                          ▼
                                  immutable MemTable ──flush──► new SSTable (L0)
```

---

### 4.3 SSTables in Detail

An **SSTable** is an immutable file containing sorted key-value pairs, plus supporting structures for efficient lookup:
- **Data blocks**: the actual sorted key-value pairs, typically grouped into fixed-size blocks (e.g., 4–64KB) for compression and I/O efficiency.
- **Index block**: maps key ranges to data block offsets, so a lookup doesn't need to scan the whole file — a binary search on the index locates the right block, then one block read (not a full-file scan) retrieves the value.
- **Bloom filter block**: (detailed in 4.5) a compact probabilistic structure letting a read quickly determine "this key is *definitely not* in this SSTable" without touching disk at all, for the common case of a lookup missing most files.
- **Footer/metadata**: file-level statistics (min/max key, number of entries) used by compaction and query planning.

**Immutability is the whole point:** because an SSTable never changes after being written, there's no need for locking during reads, no risk of partial/torn writes being visible, and background compaction can safely read old files while writing new ones without any coordination with foreground readers.

**Deletes in an LSM tree** are **not** physical removals — a delete writes a special **tombstone** marker for the key. The actual space is reclaimed later, during compaction, when the tombstone and the original value are both encountered and can be dropped together (or the tombstone itself is dropped once compaction is certain no older version of the key survives beneath it).

---

### 4.4 The Read Path

A read for a specific key must check, in order, from newest to oldest data (since a key may have multiple versions across different memtables/SSTables, and the newest must win):
1. **Active memtable** — check first, it has the newest data.
2. **Immutable memtable(s)** (if any are still being flushed).
3. **L0 SSTables** — these may have *overlapping* key ranges (since each comes from a separate memtable flush), so potentially **all** L0 files must be checked.
4. **L1 and deeper SSTables** — within each level, files are compacted to be **non-overlapping**, so at most **one file per level** needs to be checked (a binary search over that level's file key ranges finds the candidate file).

**This is why read amplification exists** (4.7): a single logical `GET` can require checking many files, each potentially requiring a disk read, before finding the value (or determining it doesn't exist) — bloom filters (4.5) exist specifically to cut this cost.

A **range scan** (`SELECT ... WHERE key BETWEEN a AND b`) is handled via a **merging iterator**: an iterator is opened over the memtable and every relevant SSTable simultaneously, and a k-way merge (like merge-sort's merge step) produces the combined sorted output, resolving duplicate keys by preferring the newest version and skipping tombstoned keys.

---

### 4.5 Bloom Filters

**What it is:** a compact, probabilistic set-membership data structure. Given a key, a bloom filter answers either "**definitely not present**" or "**possibly present**" — it has no false negatives, but can have false positives (with a tunable rate).

**Internal working:**
- A bit array of size `m`, plus `k` independent hash functions.
- To **insert** a key: compute `k` hash values, set those `k` bit positions to 1.
- To **query** a key: compute the same `k` hash values; if *any* of those bit positions is 0, the key is **definitely not** in the set (a 0 could never have been set for a present key). If *all* are 1, the key is **possibly** in the set (could be a true positive, or a false positive from bit collisions with other keys).
- The false positive rate is tunable via `m` (bits per key) and `k` (number of hash functions) — RocksDB's common default of ~10 bits per key gives roughly a 1% false positive rate; more bits per key reduce false positives at the cost of more memory.

**Why LSM trees need them specifically:** without a bloom filter, a lookup for a key that doesn't exist anywhere would still have to check every relevant SSTable at every level (worst case) before concluding "not found" — a very expensive negative lookup. With a bloom filter per SSTable, the vast majority of files can be skipped instantly (in-memory bit check) for keys that aren't actually in them, turning an expensive disk-bound negative lookup into a cheap memory-bound one.

**Tradeoff:** bloom filters cost memory (proportional to the number of keys, not the data size) and don't help at all for *positive* lookups that need the value anyway, or for range scans (bloom filters only answer point-membership questions, not range questions) — some engines use **prefix bloom filters** to partially extend benefit to range queries with a known prefix.

---

### 4.6 Compaction

**Why compaction is necessary:**
1. Bound the number of files a read must check (read amplification).
2. Reclaim space from overwritten keys and tombstoned deletes.
3. Keep L0's overlapping-range files from accumulating indefinitely.

**Leveled Compaction** (LevelDB's original design, RocksDB's default):
- Levels `L0, L1, L2, ...` with **exponentially increasing size limits** per level (e.g., L1 = 256MB, L2 = 2.5GB, L3 = 25GB — roughly a 10x growth factor by default in RocksDB).
- `L0 → L1` compaction: since L0 files can overlap, this compaction reads *all* overlapping L0 files together and merges them into new, non-overlapping L1 files.
- `Ln → Ln+1` compaction: when a level exceeds its size limit, one (or a few) files from that level are selected and merged with all *overlapping* files in the next level down, producing new non-overlapping files in `Ln+1`.
- **Result:** read amplification is bounded (at most 1 file check per level, plus all of L0), and space amplification is low (each key's obsolete versions get cleaned up relatively promptly as they cascade down) — but **write amplification is high**, because a single key can be rewritten many times as it cascades through several levels of compaction over its lifetime.

**Universal (Tiered) Compaction** (an alternative strategy, available in RocksDB, and the default philosophy in Cassandra's "Size-Tiered Compaction Strategy"):
- SSTables of similar size are grouped together and merged into a larger file once enough similarly-sized files accumulate, without maintaining the strict non-overlapping-levels invariant of leveled compaction.
- **Result:** much lower write amplification (each key is rewritten fewer times overall) at the cost of higher space amplification (more redundant/obsolete data sits around longer before being merged away) and higher read amplification (more files may need checking, since the strict per-level non-overlap guarantee is relaxed).

**The fundamental compaction tradeoff (the "RUM conjecture" in miniature):** you cannot simultaneously minimize Read amplification, Write amplification, and space (Memory/storage) amplification — improving one generally worsens at least one other. Leveled compaction optimizes for read+space at the cost of write; universal/tiered compaction optimizes for write at the cost of read+space.

---

### 4.7 Write Amplification and Read Amplification, Precisely

**Write Amplification (WA):** the ratio of *total bytes actually written to disk* (including all compaction rewrites over a key's lifetime) to *bytes the application logically wrote once*.
- Example: if a key is written once by the application, then gets rewritten during L0→L1, L1→L2, and L2→L3 compaction before being overwritten by a newer value, the physical bytes written to disk over that key's lifetime are a multiple of the logical write — that multiple is the write amplification factor. Leveled compaction with a 10x level size ratio typically produces WA in the range of ~10-30x in real deployments, depending on workload.
- **Why it matters for SSDs specifically:** flash storage has a finite number of program/erase cycles per cell; high write amplification at the database layer compounds with the SSD's own internal write amplification (from its flash translation layer), shortening device lifespan and consuming write bandwidth that could otherwise serve foreground traffic.

**Read Amplification (RA):** the ratio of *actual disk reads/blocks touched* to serve one logical read, versus the theoretical minimum (one read, if the data were in exactly one place).
- Bounded by bloom filters (avoiding unnecessary file touches for negative lookups) and by leveled compaction (bounding files-per-level to check), but never fully eliminated — a positive lookup in leveled compaction still may need to check L0 (multiple files) plus one file per subsequent level down to where the key actually lives.

**Space Amplification (SA):** the ratio of *actual disk space used* to the *logical size of the current (non-obsolete) data* — driven by how long obsolete versions and tombstones linger before compaction reclaims them.

**These three amplification factors trade off against each other** — this is precisely why compaction strategy (4.6) is the single most important tuning decision in any LSM-based system, and why production engines (RocksDB especially) expose it as a first-class configurable choice rather than a fixed algorithm.

### 4.8 LSM Trees vs. B-Trees — The Practical Decision

| Property | LSM-Tree | B-Tree |
|---|---|---|
| Write pattern | Sequential (fast) | In-place, often random (slower on spinning disk, wears SSDs) |
| Write amplification | Higher (compaction rewrites) | Lower (in-place update, though page splits add some) |
| Read amplification | Higher (multiple files to check) | Lower (single tree traversal, O(log n) page reads) |
| Space efficiency | Better with compression (sorted immutable blocks compress well) | Fragmentation from page splits reduces density |
| Point-lookup latency | Slower on average (bloom filters mitigate) | Faster, more predictable |
| Range scan | Excellent (sorted files, merge iterator) | Excellent (sorted leaf pages) |
| Best fit | Write-heavy workloads, time-series, logging, embedded/mobile (SSD write endurance) | Read-heavy or balanced OLTP workloads needing predictable point-lookup latency |

**Rule of thumb used by practitioners:** if your workload is dominated by writes/ingestion (logging, metrics, event streams, write-heavy OLTP) or you're on flash storage where write endurance matters, LSM trees usually win. If your workload is read-heavy or latency-sensitive for point lookups with a moderate write rate, a B-tree (or B+tree) engine is often simpler and faster (this is why PostgreSQL and traditional MySQL/InnoDB remain B+tree-based by default, while MongoDB via WiredTiger, and MyRocks, offer LSM as an alternative for write-heavy tenants).

### 4.9 RocksDB — Applied Internals

(Building on the paper summary in Module 3.13 — this section is the practitioner's tuning-level view.)

**Key tunables an engineer must understand:**
- `write_buffer_size` — memtable size before flush; larger = fewer flushes but more memory and longer recovery replay from WAL after a crash.
- `max_write_buffer_number` — how many memtables (active + immutable, unflushed) can exist simultaneously; controls how much write buffering absorbs bursts before writes stall.
- `level0_file_num_compaction_trigger` — how many L0 files accumulate before triggering L0→L1 compaction; too high increases read amplification (more L0 files to check per read) and can cause **write stalls** (RocksDB deliberately throttles/blocks writes if L0 grows too large, to prevent unbounded read amplification).
- `target_file_size_base` / level size multiplier — controls the exponential level-size growth (4.6) directly trading off write amplification vs. space amplification.
- `bloom_bits_per_key` — direct control over the read-amplification/memory tradeoff from 4.5.
- Compaction style choice: `kCompactionStyleLevel` (leveled, default) vs. `kCompactionStyleUniversal` (tiered) — the single biggest lever for the WA/RA/SA tradeoff triangle (4.7).

**Column Families** (from Module 3.13) let you apply *different* tuning per logical dataset within one RocksDB instance sharing a single WAL — e.g., a small, hot, read-heavy column family can use a small memtable with aggressive bloom filters, while a large, write-heavy column family uses universal compaction, all within one process.

### 4.10 LevelDB — The Reference Implementation

(Building on Module 3.15.) LevelDB remains valuable to study specifically *because* of its simplicity — it implements exactly the mechanics described in 4.2–4.6 with almost no additional tuning knobs, making its source code (a few thousand lines of readable C++) the best first codebase for an engineer who wants to actually read a real LSM-tree implementation end to end, before tackling RocksDB's much larger, more heavily optioned codebase.

**Key files to read, in order, if studying the LevelDB source:** `memtable.cc` (skip list + memtable), `db/version_set.cc` (level/file bookkeeping and the manifest), `table/table_builder.cc` (SSTable writing), `db/db_impl.cc` (write path, flush, compaction orchestration).

### 4.11 Beyond RocksDB/LevelDB — Other LSM Variants Worth Knowing

- **Cassandra**: uses Size-Tiered Compaction Strategy (STCS, a universal/tiered variant) by default, with Leveled Compaction Strategy (LCS) available as an option — directly exposing the WA/RA/SA tradeoff (4.7) as a per-table configuration choice to the operator.
- **ScyllaDB**: a C++ rewrite of Cassandra's data model with a shard-per-core LSM implementation designed to avoid lock contention on modern multi-core hardware.
- **Pebble**: CockroachDB's own Go-native LSM engine (replacing RocksDB), designed to remove the CGo boundary overhead of calling into C++ RocksDB from Go, while preserving RocksDB-compatible on-disk format concepts.
- **Badger**: a pure-Go LSM engine (used by Dgraph) notable for separating keys and values into different files (a **WiscKey**-style design, from the paper *"WiscKey: Separating Keys from Values in SSD-Conscious Storage,"* Lu et al., FAST 2016) — since compaction only needs to move sorted *keys*, leaving large values in a separate append-only log, this significantly reduces write amplification for workloads with large values.

### 4.12 Production Examples & Industry Usage

| System | LSM engine used | Why LSM was chosen |
|---|---|---|
| Facebook/Meta (MySQL fleet) | MyRocks (RocksDB) | Reduced storage footprint and write amplification vs. InnoDB at Facebook's write-heavy scale |
| MongoDB | WiredTiger (offers LSM table type) | Write-heavy collections benefit from LSM's sequential write pattern |
| CockroachDB | Pebble (originally RocksDB) | High write throughput for distributed OLTP + range/compaction control |
| TiKV (TiDB's storage layer) | RocksDB | Same rationale — high write throughput distributed KV |
| Apache Kafka Streams | RocksDB (state store) | Embeddable, high write throughput for stream processing state |
| Cassandra | Custom (STCS/LCS) | Write-optimized wide-column store for massive ingestion workloads |

### 4.14 MCQs

**Q1.** The primary reason LSM-trees convert random writes into sequential writes is:
A) To use less memory
B) Sequential I/O is dramatically faster than random I/O on disk/SSD
C) To avoid using a WAL
D) To simplify SQL parsing

*Answer: B*

**Q2.** A bloom filter query result of "possibly present" means:
A) The key is definitely in the SSTable
B) The key may or may not be in the SSTable (false positives possible, false negatives impossible)
C) The key is definitely not in the SSTable
D) The bloom filter is corrupted

*Answer: B*

**Q3.** L0 SSTables require checking *all* of them on a read (unlike deeper levels) because:
A) L0 files are always empty
B) L0 files can have overlapping key ranges since each comes from a separate memtable flush
C) L0 uses a different compression format
D) L0 has no bloom filters

*Answer: B*

**Q4.** Universal/tiered compaction compared to leveled compaction typically offers:
A) Lower write amplification, higher space/read amplification
B) Lower everything
C) Higher write amplification only
D) No difference in any amplification factor

*Answer: A*

**Q5.** A tombstone in an LSM-tree is:
A) A corrupted SSTable
B) A marker recording a delete, physically removed later during compaction
C) An index structure
D) A type of bloom filter

*Answer: B*

### 4.16 Research Questions

1. Can compaction strategy be chosen dynamically per-workload (rather than statically configured) using observed read/write ratios, and what would the switching cost/hysteresis need to look like to avoid thrashing?
2. As SSDs and emerging storage-class memory (e.g., Intel Optane's successors, CXL-attached memory) narrow the sequential-vs-random I/O gap that motivated LSM-trees originally, does the LSM-tree's core justification weaken, and for which workloads first?
3. Could machine-learned models predict which SSTables are "cold" (safe to leave uncompacted longer) versus "hot" (should be prioritized for compaction) better than RocksDB's current heuristics, and how would you validate such a model doesn't regress tail latency under adversarial access patterns?
