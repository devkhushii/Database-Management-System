# Part 9: Database Recovery, Logging & Durability
## Module 5: Recovery Techniques

> **Recap:** Module 4 established the WAL rule — log before data. But WAL alone is a *principle*, not a complete algorithm. This module covers the actual **techniques** built on top of (or as alternatives to) WAL: pure Undo Logging, pure Redo Logging, combined Undo/Redo Logging, and the entirely different philosophy of Shadow Paging. Think of Module 4 as "the law," and this module as "the specific legal procedures that follow that law" — plus one alternative legal system (Shadow Paging) that doesn't follow it at all.

---

## 📍 Why Multiple Techniques Exist

If WAL is the universal rule, why do we need three different logging *techniques* built on it? Because the rule alone doesn't tell you:

- **When** are you allowed to write a dirty data page to disk relative to commit?
- **What** information must be in the log to make that timing choice safe?

Different answers to these two questions produce fundamentally different recovery techniques, each with its own trade-offs. This directly sets up **Module 8 (Buffer Recovery)**, where we'll formalize this timing question as the STEAL/NO-STEAL, FORCE/NO-FORCE framework — but you need to see the techniques concretely first before that abstraction will click.

---

## 5.1 Log-Based Recovery — Overview

**Log-Based Recovery** is the umbrella term for any recovery technique that relies on the transaction log (Module 3) as the source of truth for reconstructing database state. All three techniques in this section — Undo, Redo, and Undo/Redo logging — fall under this umbrella. Shadow Paging (Section 5.5) does not; it's a completely different, non-log-based philosophy, discussed separately.

---

## 5.2 Undo Logging

### What is Undo Logging?

**Undo Logging** is a recovery technique where:

1. The log only needs to store the **before-image** (old value) of each changed data item — not the after-image.
2. A strict rule is enforced: **all of a transaction's modified data pages must be flushed to disk *before* its commit record is written.**

This second rule is the crucial, defining constraint of pure Undo Logging — and it directly foreshadows the **FORCE** policy formalized in Module 8.

### The Undo Logging Rule, Precisely

> **Rule:** A transaction's data page changes must reach disk *before* (or exactly at) commit. The log's only job is to allow undoing a transaction if it never reaches commit.

Because data is guaranteed to be on disk by the time commit happens, there is **never any need to redo anything** — if the commit record is in the log, the data is already correctly on disk, guaranteed. This is why it's called *Undo-only* logging: recovery, if needed, only ever performs undo, never redo.

### Undo Logging Recovery Algorithm

On restart after a crash, scan the log:

- For every transaction with a **commit record** present → do nothing (its data was already safely flushed before commit, by the rule above).
- For every transaction **without** a commit record (i.e., it was active or aborted at crash time) → **undo** all its changes, using the before-images, in reverse LSN order.

### Visual: Undo Logging Timeline

```
LSN 1: T1 BEGIN
LSN 2: T1 UPDATE (before-image: X=10)
LSN 3: T1 UPDATE (before-image: Y=20)
       ── T1's data pages FORCE-FLUSHED to disk here, BEFORE commit ──
LSN 4: T1 COMMIT
       CRASH!

Recovery: T1 has a commit record → do nothing. Data already safely on disk.
```

```
LSN 1: T2 BEGIN
LSN 2: T2 UPDATE (before-image: Z=50)
       ── T2's data page flushed to disk (dirty page written early) ──
       CRASH! (before commit record was ever written)

Recovery: T2 has NO commit record → UNDO using before-image: set Z back to 50.
```

### Why This Technique is Rarely Used Alone in Modern Systems

Forcing **all** of a transaction's dirty pages to disk before every commit is extremely expensive — it defeats the entire performance benefit of WAL's lazy data-page flushing (Module 4). This is precisely the **FORCE** policy that Module 8 will show is generally avoided in high-performance systems. Undo Logging is taught primarily as a conceptual stepping stone and is rarely the *sole* mechanism in production engines today.

### Advantages
- Simple recovery algorithm — only undo, ever.
- No redo phase needed at all.

### Disadvantages
- Forces (mandatory disk flush) all dirty pages before every commit — a severe, non-negotiable performance cost on every single transaction.
- Doesn't scale well under high write throughput.

## 5.3 Redo Logging

### What is Redo Logging?

**Redo Logging** is, in a sense, the mirror image of Undo Logging:

1. The log stores the **after-image** (new value) of each changed data item — not the before-image.
2. A strict rule is enforced: **a transaction's data page changes must NOT be flushed to disk until *after* its commit record is safely on the log.**

### The Redo Logging Rule, Precisely

> **Rule:** No dirty data page belonging to an uncommitted transaction may ever be written to disk. Only after commit is a page allowed to be flushed — and even then, it can be delayed (deferred) further for performance.

Because uncommitted data is *guaranteed never to reach disk*, there's never any need to undo anything on recovery — an uncommitted transaction's changes, by construction, never made it to disk in the first place! This is why it's called *Redo-only* logging.

### Redo Logging Recovery Algorithm

On restart after a crash, scan the log:

- For every transaction **with** a commit record → **redo** all its changes using the after-images, in forward LSN order (since its data pages might not have made it to disk yet, even though it committed).
- For every transaction **without** a commit record → do nothing (its changes, by the rule, were never written to disk at all).

### Visual: Redo Logging Timeline

```
LSN 1: T1 BEGIN
LSN 2: T1 UPDATE (after-image: X=99)
LSN 3: T1 UPDATE (after-image: Y=88)
LSN 4: T1 COMMIT
       ── T1's data pages have NOT yet been flushed to disk (deferred) ──
       CRASH!

Recovery: T1 has a commit record → REDO: apply X=99, Y=88 to disk.
```

```
LSN 1: T2 BEGIN
LSN 2: T2 UPDATE (after-image: Z=77)
       (T2's data page is NOT allowed on disk yet — no commit record exists)
       CRASH! (before commit)

Recovery: T2 has NO commit record → do nothing. Its data was never on disk.
```

### Why This Requires Something Called NO-STEAL

Notice the constraint this technique imposes: the buffer manager is **not allowed to evict/write an uncommitted transaction's dirty page to disk**, even under memory pressure. This maps directly onto the **NO-STEAL** buffer policy formalized in Module 8. If the buffer pool runs low on memory and an uncommitted transaction has modified a huge number of pages, the system is in a bind — it cannot flush them (violating the rule) and cannot easily reclaim that memory either.

### Advantages
- No data ever needs undoing — uncommitted work never touches disk.
- Can defer data page writes indefinitely after commit, batching them efficiently.

### Disadvantages
- Requires holding all of a large transaction's dirty pages in the buffer pool until commit — problematic for very large transactions (memory pressure, the NO-STEAL constraint above).
- Recovery must always redo every committed transaction since the last checkpoint, even ones whose data was actually already on disk (a possible source of redundant, though still correct, work).

## 5.4 Undo/Redo Logging (Combined)

### What is Undo/Redo Logging?

**Undo/Redo Logging** is the technique used by virtually every production database engine today, precisely because it removes the rigid constraints of both pure Undo Logging (Section 5.2) and pure Redo Logging (Section 5.3). It is the technique implicitly assumed throughout Modules 3 and 4, and it's the technique ARIES (Module 7) formalizes and perfects.

### The Core Idea

1. The log stores **both** the before-image (for undo) and the after-image (for redo) of every change — as introduced back in Module 3's log record structure.
2. **No strict ordering constraint** is placed on when data pages are flushed relative to commit — a dirty page can be flushed to disk **either before or after** its transaction commits. This flexibility is precisely what the **STEAL** and **FORCE**/**NO-FORCE** combinations in Module 8 formalize.

Because data pages can be flushed at essentially any time, recovery must be prepared to do **both**:

- **Redo** any committed transaction's changes that might not have made it to disk yet.
- **Undo** any uncommitted transaction's changes that might have made it to disk early (because, unlike pure Redo Logging, this technique *permits* early flushing of uncommitted pages — the STEAL policy).

### Undo/Redo Logging Recovery Algorithm (Simplified Preview of ARIES)

On restart after a crash:

1. **Determine** which transactions committed (have a commit record) and which did not.
2. **Redo** all changes made by committed transactions, in forward LSN order — ensures durability, restoring anything that hadn't reached disk.
3. **Undo** all changes made by uncommitted transactions, in reverse LSN order — ensures atomicity, removing anything that had reached disk early.

This three-step shape should look extremely familiar — it's the direct ancestor of the Analysis/Redo/Undo phases you'll study formally, with full mechanics and a numeric walkthrough, in **Module 7 (ARIES)**.

### Visual: Undo/Redo Logging Timeline

```
LSN 1: T1 BEGIN
LSN 2: T1 UPDATE X (before=10, after=99)
       ── T1's dirty page IS flushed to disk early (before commit — allowed here!) ──
LSN 3: T1 COMMIT
LSN 4: T2 BEGIN
LSN 5: T2 UPDATE Y (before=20, after=88)
       ── T2's dirty page has NOT been flushed yet ──
       CRASH! (T2 never committed)

Recovery:
  T1 (committed): REDO X=99 (in case disk write happened but wasn't confirmed — redo is always safe to reapply, more on this idempotency point in Module 7)
  T2 (uncommitted): UNDO Y back to 20 (its early or late disk state doesn't matter — undo guarantees correctness either way)
```

### Why Undo/Redo Logging "Wins" in Practice

| Technique | Constraint on Buffer Manager | Real-World Fit |
|---|---|---|
| Undo Logging | Must FORCE-flush before commit | Poor — hurts commit latency badly |
| Redo Logging | Must NEVER flush before commit (NO-STEAL) | Poor — hurts memory flexibility for large transactions |
| **Undo/Redo Logging** | **No constraint — flush anytime (STEAL + NO-FORCE)** | **Excellent — maximum buffer manager flexibility, best performance** |

This table is a direct preview of Module 8's full STEAL/NO-STEAL/FORCE/NO-FORCE matrix — Undo/Redo Logging is precisely what enables the most performant combination, **STEAL + NO-FORCE**, which is what virtually all production engines use.

### Advantages
- Maximum flexibility for the buffer manager — pages can be flushed whenever convenient, in whatever order, for best performance.
- No artificial constraints on transaction size (unlike pure Redo Logging's NO-STEAL requirement).
- No forced synchronous data flush on every commit (unlike pure Undo Logging).

### Disadvantages
- Requires storing both before- and after-images, slightly larger log records than either pure technique alone.
- Recovery algorithm is more complex, requiring careful bookkeeping (dirty page tables, transaction tables — introduced properly in Module 7) to be efficient.

## 5.5 Shadow Paging

### What is Shadow Paging?

**Shadow Paging** is a fundamentally different approach to recovery that achieves atomicity and durability **without using a log at all** in the traditional sense. Instead, it relies on maintaining two complete "versions" of the database's page-mapping table.

### How It Works

1. The database maintains a **page table** — a mapping from logical page numbers to physical disk locations (a concept connecting back to Part 7's storage engine internals).
2. At the start of a transaction, a **shadow copy** of the current page table is preserved (the "shadow page table") — this represents the last known-good, consistent state.
3. As the transaction makes changes, it **never modifies pages in place**. Instead, it writes changed data to **new, previously unused disk locations**, and updates a separate, working copy of the page table (the "current page table") to point to these new locations.
4. If the transaction **commits**, the current page table is made the new official page table — typically via a single atomic pointer/disk-block swap.
5. If the transaction **aborts** or the system **crashes** before commit, the current page table is simply **discarded**. The old shadow page table — which was never touched — is still perfectly valid, and the database instantly reverts to its pre-transaction state.

### Real-Life Analogy

Imagine editing a shared Google Doc, but instead of editing the live document directly, you're actually working on a private draft copy the entire time. Only when you click a single "Publish" button does the system atomically swap "the official document" pointer to your finished draft. If your browser crashes mid-edit, the official document was never touched — your incomplete draft is simply thrown away, no cleanup needed.

### Visual: Shadow Paging Concept

```
BEFORE TRANSACTION:
  Shadow Page Table ──► Page A (disk location 100)
                    ──► Page B (disk location 200)

DURING TRANSACTION (modifying Page A):
  Shadow Page Table ──► Page A (disk location 100)   [untouched, still valid]
                    ──► Page B (disk location 200)

  Current Page Table ──► Page A' (disk location 500)  [NEW copy, modified]
                     ──► Page B (disk location 200)   [unchanged, shared]

ON COMMIT:
  Current Page Table becomes the new official Shadow Page Table
  (single atomic swap — old Page A at location 100 can now be reclaimed)

ON CRASH/ABORT BEFORE COMMIT:
  Current Page Table is simply discarded.
  Shadow Page Table (pointing to original Page A) is still valid — no undo needed!
```

### Why No Undo or Redo is Needed

This is the defining, elegant property of Shadow Paging: because changes are never made in place, an incomplete transaction simply **never becomes visible** — there's nothing to undo. And because the commit is a single atomic pointer swap, a committed transaction's changes are immediately, fully durable — there's nothing to redo either.

### Advantages of Shadow Paging

- **No undo/redo logic needed at all** — recovery is nearly instantaneous (just verify which page table is currently valid).
- **Simpler recovery algorithm** conceptually — no log parsing, no Analysis/Redo/Undo phases.
- **Naturally atomic commits** via the single pointer swap.

### Disadvantages of Shadow Paging

- **Data fragmentation:** Because modified pages are written to new locations rather than updated in place, related data can become scattered across disk over time, hurting sequential read performance.
- **Garbage collection overhead:** Old, now-unreferenced pages (like the original Page A above) must eventually be identified and reclaimed — a non-trivial background process.
- **Poor support for concurrent transactions:** Shadow paging was originally designed with single-transaction-at-a-time semantics in mind; making it work efficiently with fine-grained concurrency control (Part 6) is considerably harder than with log-based approaches.
- **No natural support for partial rollback (savepoints):** Log-based undo can roll back to any arbitrary point using LSNs; shadow paging's all-or-nothing page-table swap doesn't naturally support that granularity.
- **Larger write overhead per transaction:** Copying entire modified pages, rather than logging small deltas, can mean more physical I/O for the same logical change.

### Shadow Paging vs WAL — Direct Comparison

| Aspect | Shadow Paging | WAL (Log-Based, Undo/Redo) |
|---|---|---|
| Recovery mechanism | Discard/keep page table version | Replay log (redo/undo) |
| Undo needed? | No (in-place changes never happen) | Yes |
| Redo needed? | No (commit = atomic pointer swap) | Yes |
| Data fragmentation | High (copy-on-write pages) | Low (in-place updates) |
| Concurrency support | Historically weak | Strong, mature (used by all major engines) |
| Recovery speed | Very fast (no replay needed) | Fast, but requires log replay |
| Production usage today | Rare (some copy-on-write filesystems/DBs use variants, e.g., certain NoSQL/LSM-adjacent designs conceptually echo it) | Universal — PostgreSQL, MySQL, Oracle, SQL Server |
| Partial rollback (savepoints) | Not naturally supported | Naturally supported via LSNs |

> 💡 **Interview Insight:** A frequently asked question is *"Why did the industry converge on WAL instead of Shadow Paging, even though Shadow Paging sounds simpler?"* The honest answer: Shadow Paging's weaknesses around concurrency and fragmentation made it impractical for high-throughput, highly concurrent OLTP workloads — exactly the workloads most production databases must serve. WAL's complexity is a worthwhile trade for its performance and flexibility under concurrency.

## 5.6 Performance Implications Across Techniques

| Technique | Commit Latency | Buffer Flexibility | Recovery Speed | Log Storage Needed |
|---|---|---|---|---|
| Undo Logging | High (forced flush before commit) | Low | Fast (undo only) | Before-images only |
| Redo Logging | Low | Low (NO-STEAL constraint) | Moderate (redo everything committed) | After-images only |
| Undo/Redo Logging | Low | **High (STEAL + NO-FORCE)** | Moderate (redo + undo, but bounded by checkpoints — Module 6) | Both before- and after-images |
| Shadow Paging | Low | N/A (different model entirely) | Very fast | No traditional log; page table versions instead |

## 5.7 Industry Usage

- **PostgreSQL, MySQL (InnoDB), Oracle, SQL Server:** All use **Undo/Redo Logging**, layered with ARIES-style algorithms (Module 7) — this is the industry-standard, near-universal choice for relational OLTP databases.
- **Shadow Paging:** Rarely used in its pure textbook form today in mainstream relational databases, but the *conceptual philosophy* echoes in copy-on-write filesystems (like ZFS or Btrfs) and in some specialized database designs that favor immutability, such as certain LSM-tree-based or append-only storage engines — worth knowing as a connecting thread to modern storage engine design, previewed further in Module 15.

---

## 5.8 Best Practices

- Understand why Undo/Redo Logging (with STEAL + NO-FORCE, Module 8) is the near-universal industry default — it's not an arbitrary choice, it's the result of these very trade-offs.
- If evaluating a database or storage engine that uses a shadow-paging-like or copy-on-write design, specifically investigate its story on concurrent write throughput and fragmentation/compaction overhead before assuming it behaves like a traditional log-based RDBMS.

## 5.9 Common Mistakes

- Assuming "Undo Logging" and "Redo Logging" are just two names for the same thing — they impose **opposite** constraints on when data can be flushed, which is the entire point of studying them separately.
- Believing Shadow Paging is strictly "worse" — it has genuine advantages (fast recovery, conceptual simplicity) that make it a reasonable choice for certain workloads, particularly those with low write concurrency.
- Forgetting that Undo/Redo Logging is what enables STEAL — a common exam mistake is pairing "Undo/Redo Logging" with a NO-STEAL policy, which defeats its entire purpose.

## 5.10 Edge Cases

- A transaction that both reads and writes the same page multiple times within Undo/Redo Logging needs its log records to reflect a coherent chain of before/after images (this is where PrevLSN chaining from Module 3 becomes essential in practice).
- In Shadow Paging, concurrent transactions attempting to modify the *same* page simultaneously require additional coordination beyond the basic model described here — a core reason it doesn't scale naturally to highly concurrent OLTP workloads.

---

## 5.11 Chapter Summary

- **Undo Logging** requires data pages to be flushed *before* commit (FORCE) — simple recovery (undo-only), but poor commit performance.
- **Redo Logging** forbids flushing uncommitted data pages at all (NO-STEAL) — good commit performance for data writes, but poor memory flexibility for large transactions.
- **Undo/Redo Logging** removes both constraints — data pages can be flushed anytime (STEAL + NO-FORCE) — this is the technique virtually every production database uses today, and it directly motivates ARIES (Module 7).
- **Shadow Paging** is a non-log-based alternative: transactions write to new page copies, and commit is an atomic page-table swap. It offers fast, log-free recovery but suffers from fragmentation and weak concurrency support, which is why it lost out to WAL-based approaches in mainstream production RDBMS design.

## 5.12 Cheat Sheet

| Technique | Flush Before Commit? | Undo Needed? | Redo Needed? | Used By |
|---|---|---|---|---|
| Undo Logging | Required (FORCE) | Yes | No | Rare/legacy, teaching tool |
| Redo Logging | Forbidden (NO-STEAL) | No | Yes | Rare/legacy, teaching tool |
