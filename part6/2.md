# Part 6: Transactions & Concurrency Control

## Module 2: ACID Properties

> Recall from Module 1: a transaction is an all-or-nothing unit of work. But *how* does the database actually guarantee that "all-or-nothing" promise, that correctness is preserved, that concurrent transactions don't corrupt each other, and that committed data survives a crash? The answer is four properties, famously abbreviated **ACID**: **Atomicity, Consistency, Isolation, Durability**. This module dissects each one completely.

---

### 2.1 Overview: Why ACID as a Package?

Each ACID property protects against a *different* kind of failure:

| Property | Protects against |
|---|---|
| **Atomicity** | Partial execution (crash mid-transaction) |
| **Consistency** | Violating business/data-integrity rules |
| **Isolation** | Interference between concurrent transactions |
| **Durability** | Loss of committed data after a crash |

They are often taught together because a *real* transactional guarantee requires **all four simultaneously** — dropping any one of them reopens a class of bugs. For example, if you have Atomicity and Durability but not Isolation, two transactions could still see each other's uncommitted, half-finished changes and produce a wrong result even though each one individually completes correctly.

---

### 2.2 Atomicity

**Definition:** Atomicity guarantees that a transaction's operations are treated as a **single, indivisible unit**: either every operation in the transaction is applied, or none of them are. There is no partial state visible to anyone, ever — not even for a moment.

**Why needed:** Without atomicity, a crash or error partway through a multi-step operation (like the bank transfer from Module 1) could leave the database in an inconsistent state — money debited from one account but never credited to another.

**Internal implementation:**

Atomicity is primarily implemented using the **transaction log** (also called the **Write-Ahead Log / WAL** in PostgreSQL, or the **redo/undo log** in InnoDB and Oracle) — a topic we cover in full depth in Part 7 (Recovery). The short version:

1. Before any data page is modified, the database first writes a **log record** describing the change, to durable storage.
2. If the transaction later aborts (or the system crashes before commit), the database uses the log's **undo information** to reverse any changes already applied to data pages.
3. If the transaction commits, the log's **commit record** is what makes the change official and recoverable — even if the actual data pages haven't been flushed to disk yet, the log guarantees the change can be redone on restart.

This "log first, data pages later" discipline is called **Write-Ahead Logging (WAL)**, and it's the backbone of atomicity (and durability) in virtually every serious relational database.

**Real-world analogy:**
Think of atomicity like a **video game checkpoint save**. If your game crashes mid-level, you don't resume "half inside a wall with half your inventory changed" — you either resume from the last checkpoint (as if nothing happened, i.e., rollback) or, if the checkpoint was fully saved, you resume exactly at that saved point (commit). There's no in-between state the game ever shows you.

**Practical example:**

```sql
BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 'A';
-- system crashes right here
UPDATE accounts SET balance = balance + 500 WHERE id = 'B';
COMMIT;
```

On restart, the database's recovery process reads the log, sees no commit record for this transaction, and **undoes** the first `UPDATE`. Account A's balance is restored — atomicity preserved.

**Database engine implementation:**
- **PostgreSQL:** Uses WAL + an internal "transaction status" bit stored in `pg_xact` (formerly `pg_clog`) to mark each transaction ID as committed or aborted. Readers check this status to know whether a row version is valid.
- **InnoDB (MySQL):** Uses a combination of the **redo log** (for durability of committed changes) and **undo log** (for rolling back uncommitted changes, and also for MVCC snapshots — see Module 10).
- **Oracle:** Uses **redo logs** for durability and **undo segments** (rollback segments) for atomicity/rollback and read consistency.

**Common misconceptions:**
- "Atomicity means the transaction runs instantly." — False; atomicity is about *all-or-nothing outcome*, not speed.
- "Atomicity applies only to multi-statement transactions." — False; even a single `UPDATE` affecting many rows is atomic (all rows change, or none do).

### 2.3 Consistency

**Definition:** Consistency guarantees that a transaction takes the database from **one valid state to another valid state**, never violating any defined integrity constraints (primary keys, foreign keys, `CHECK` constraints, `UNIQUE` constraints, triggers enforcing business rules, etc.).

**Why needed:** A database is only useful if its data actually reflects reality and follows the rules the schema designer defined. Consistency is the guarantee that transactions can't "cheat" their way into breaking those rules, even temporarily as seen by other users.

**Important nuance:** Unlike the other three ACID properties, **Consistency is partly the application's responsibility and partly the database's responsibility.** The database enforces *declared* constraints (schema-level rules); it cannot enforce business rules you never told it about. For example, if your application logic has a bug where it inserts a negative product price and there's no `CHECK (price >= 0)` constraint, the database will *not* stop you — consistency was never declared for that rule.

**How it works internally:**
- Before a transaction is allowed to commit, the database checks all declared constraints: primary key uniqueness, foreign key references, check constraints, `NOT NULL`, unique indexes, and any deferred constraints (evaluated at commit time — see Module 13's `SET CONSTRAINTS`).
- If any constraint is violated, the transaction is forced into the **Failed** state (from Module 1) and rolled back.

**Real-world analogy:**
Consistency is like a **notary verifying a legal contract** before it's filed. The notary doesn't care about your business strategy (that's on you), but they *will* refuse to file a contract missing a required signature or containing an internally contradictory clause. The notary enforces the *procedural* rules; you're responsible for the *substantive* wisdom of the deal.

**Practical example:**

```sql
CREATE TABLE accounts (
    id TEXT PRIMARY KEY,
    balance NUMERIC CHECK (balance >= 0)
);

BEGIN;
UPDATE accounts SET balance = balance - 1000 WHERE id = 'A';  -- would make balance negative
COMMIT;  -- REJECTED: violates CHECK constraint, transaction rolled back
```

**Database engine behavior:**
- **PostgreSQL:** Supports immediate and `DEFERRABLE` constraints; deferred constraints are checked only at `COMMIT`.
- **MySQL (InnoDB):** Foreign key constraints are enforced, but historically MySQL was more lenient with certain constraint types depending on `sql_mode` (e.g., strict mode vs. non-strict silently truncating/coercing invalid data in older versions/configurations) — a common point of criticism versus PostgreSQL's stricter defaults.
- **Oracle & SQL Server:** Both support full constraint enforcement including deferred constraints (Oracle) and check constraints with more configurable enforcement timing.

**Common mistakes:**
- Assuming the database enforces business rules that were never written as constraints.
- Not using `CHECK` constraints at all and relying purely on application-level validation, which can be bypassed by a different service, script, or direct DB access.

### 2.4 Isolation

**Definition:** Isolation guarantees that **concurrently executing transactions do not interfere with each other's intermediate (uncommitted) states.** Each transaction should behave as if it were running alone, even though in reality many transactions run at the same time for performance reasons.

**Why needed:** Without isolation, one transaction could read another's half-finished work (a **dirty read**), or two transactions could clobber each other's updates (a **lost update**) — both of which we'll examine in full detail with timelines in Module 5.

**How it works internally:** Isolation is enforced using **concurrency control mechanisms** — this is really the heart of the rest of this entire Part 6:
- **Locking protocols** (Module 6–7): transactions acquire locks on data they touch, blocking others from conflicting access.
- **Timestamp ordering** (Module 8) and **Optimistic Concurrency Control** (Module 9): alternative, non-locking approaches.
- **MVCC** (Module 10): instead of blocking readers, the database keeps multiple *versions* of each row so readers see a consistent snapshot without waiting on writers.

Different **isolation levels** (Module 11) offer different trade-offs between strictness and performance — full isolation from every anomaly is possible (`SERIALIZABLE`), but it's the most expensive; weaker levels trade some correctness guarantees for higher throughput.

**Real-world analogy:**
Imagine two people editing the same shared Google Doc, but *without* the live collaborative-editing feature — instead, each person's edits only become visible to the other once they explicitly "save and publish." Isolation defines exactly what "in-progress" edits the other person is allowed to see: nothing (strict isolation) versus a stale, possibly outdated version (weaker isolation) versus real-time raw edits (no isolation at all, which is what we want to avoid for critical data).

**Practical example — without proper isolation, a lost update:**

```sql
-- T1                                  -- T2
BEGIN;                                 BEGIN;
SELECT balance FROM accounts           SELECT balance FROM accounts
  WHERE id='A';  -- reads 1000           WHERE id='A';  -- also reads 1000
-- T1 computes 1000 + 100 = 1100       -- T2 computes 1000 + 200 = 1200
UPDATE accounts SET balance=1100
  WHERE id='A';
COMMIT;
                                        UPDATE accounts SET balance=1200
                                          WHERE id='A';
                                        COMMIT;
-- Final balance = 1200 -- T1's +100 update is LOST!
```

Proper isolation (via locking or MVCC conflict detection) prevents this outcome. We dissect this exact anomaly, and many others, with full timelines in Module 5.

**Database engine behavior:**
- **PostgreSQL:** Implements isolation primarily via **MVCC**, with `READ COMMITTED` as default.
- **MySQL (InnoDB):** Also MVCC-based, but defaults to `REPEATABLE READ` — a notably stricter default than PostgreSQL, and a very common interview trivia point.
- **Oracle:** MVCC-based (calls its mechanism "multiversion read consistency"), defaults effectively to `READ COMMITTED`.
- **SQL Server:** Primarily lock-based by default (`READ COMMITTED` using locks), though it also offers an MVCC-style `READ_COMMITTED_SNAPSHOT` / `SNAPSHOT` isolation mode that must be explicitly enabled.

We revisit this comparison table in full in Module 11.

### 2.5 Durability

**Definition:** Durability guarantees that once a transaction has committed, its changes are **permanent** — they will survive any subsequent crash, power failure, or system restart.

**Why needed:** A "commit" is a promise to the application and the end user. If a system could say "your payment succeeded" and then lose that data on a crash five seconds later, no one could trust the database (or the application) again.

**How it works internally:**
Durability is achieved through the same **Write-Ahead Log** mechanism as atomicity, plus a critical guarantee: **the log record for a commit must be flushed to durable storage (disk, or a replicated durable medium) *before* the commit is acknowledged to the client.**

The sequence for a durable commit:
1. All log records for the transaction's changes are written to the log.
2. The **commit log record** is written and physically flushed (`fsync`) to durable storage.
3. Only *after* that flush succeeds does the database engine tell the client "COMMIT successful."
4. The actual data pages in the buffer pool/cache can be flushed to disk *later*, asynchronously — because if a crash happens before that, the log alone is enough to redo the change on recovery.

**Real-world analogy:**
Durability is like getting a **certified, stamped receipt** at a government office. Even if the building loses power the moment you walk out, the department has a duplicate copy of your stamped receipt in an offsite archive — so your transaction is safe regardless of what happens to the building afterward.

**Practical example:**

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
COMMIT;   -- as soon as this returns "success," a crash 1 millisecond later
          -- CANNOT lose this change.
```

**Database engine behavior:**
- **PostgreSQL:** Uses `fsync` on WAL by default (`fsync = on`); can be tuned via `synchronous_commit` (`on`, `off`, `local`, etc.) trading some durability guarantee for latency — a very popular performance-vs-durability interview topic.
- **MySQL (InnoDB):** Controlled via `innodb_flush_log_at_trx_commit`:
  - `1` (default, safest): log flushed and `fsync`'d on every commit — full durability.
  - `0`: log written and flushed roughly once per second — faster, but up to ~1 second of committed transactions can be lost on crash.
  - `2`: log written on commit but only flushed to disk once per second — safer than `0` regarding OS-level crashes, but still risky on full power loss.
- **Oracle:** Uses redo log with configurable "commit write" behavior similar in spirit (`COMMIT WRITE BATCH/IMMEDIATE, NOWAIT/WAIT`).
- **SQL Server:** Write-ahead logging to the transaction log file, `fsync`-equivalent flush guarantees on commit by default.

**Performance implications:** Durability's core cost is the mandatory disk flush on every commit — this is often the single biggest per-transaction latency cost in an OLTP system, which is why databases offer tunable durability trade-offs (`synchronous_commit`, `innodb_flush_log_at_trx_commit`) for workloads that can tolerate a small risk of data loss on crash in exchange for lower commit latency.

**Common misconception:** "Durability means the data is written to the table's data file immediately." False — durability is guaranteed by the **log**, not the data file. The actual table pages ("heap pages" in PostgreSQL, "tablespace pages" in InnoDB) can be flushed to disk lazily; the log is what makes recovery possible.

### 2.6 ACID Properties — Master Comparison Table

| Property | Guards Against | Primary Mechanism | Verified/Enforced At |
|---|---|---|---|
| Atomicity | Partial execution | Write-ahead log (undo) | Commit / crash recovery |
| Consistency | Constraint violations | Constraint checks, triggers | Statement execution & commit |
| Isolation | Concurrent interference | Locking / MVCC / Timestamp ordering | Throughout transaction execution |
| Durability | Loss of committed data | Write-ahead log (redo) + fsync | Commit |

### 2.7 Advantages, Disadvantages, Best Practices

**Advantages of full ACID compliance:**
- Predictable, correct behavior even under crashes and concurrency — critical for financial, medical, and any mission-critical system.
- Frees application developers from manually reasoning about every interleaving of concurrent operations.

**Disadvantages / trade-offs:**
- Strict ACID compliance (especially strong isolation and full durability) comes at a real performance cost — this is precisely why NoSQL systems historically relaxed some ACID guarantees (often trading Consistency/Isolation for availability and partition tolerance, per the CAP theorem) for higher throughput at scale.
- Durability's mandatory log flush adds latency to every commit.
- Full serializable isolation can significantly increase lock contention or transaction abort/retry rates.

**Best Practices:**
- Declare your real constraints (`CHECK`, `FOREIGN KEY`, `UNIQUE`) — don't rely solely on application-layer validation for Consistency.
- Understand your engine's durability tuning knobs (`synchronous_commit`, `innodb_flush_log_at_trx_commit`) and make a deliberate, documented choice rather than accepting silent defaults blindly.
- Choose the isolation level based on actual anomaly tolerance for the specific transaction — don't default to `SERIALIZABLE` everywhere "just to be safe," as this can tank throughput unnecessarily (Module 11 covers this decision framework).

**Common Mistakes:**
- Tuning `innodb_flush_log_at_trx_commit = 0` or `2` for performance without realizing the durability trade-off, then being surprised by data loss during a crash.
- Assuming "the database has ACID, so my application logic can never produce a wrong result" — Consistency and Isolation still require the application to use transactions and constraints correctly.

**Performance Implications:**
Each ACID property has a distinct performance cost center:
- Atomicity/Durability → log flush I/O.
- Isolation → lock contention or MVCC version-chain bookkeeping (Module 10, Module 16).
- Consistency → constraint-check CPU cost, generally small compared to the others.

**Industry Usage:**
Full ACID transactions are the backbone of banking cores, payment processors, airline reservation systems, and inventory management. We explore concrete failure scenarios for each of these in Module 15.

### 2.8 Chapter Summary

- **Atomicity**: all-or-nothing, implemented via undo logging.
- **Consistency**: valid-state-to-valid-state, enforced via constraints (partially the app's job too).
- **Isolation**: concurrent transactions don't interfere, enforced via locking/MVCC/timestamp ordering.
- **Durability**: committed data survives crashes, implemented via redo logging + mandatory log flush before acknowledging commit.
- All four properties work together; weakening any one reopens a specific class of correctness bugs.
- Real engines make deliberate trade-offs (tunable durability, different default isolation levels) — know these differences cold for interviews.
